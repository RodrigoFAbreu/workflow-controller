## Goal

The owner wants to change harness, git host or backlog tool without rewriting the Controller (`ADAPTERS-AND-BACKLOG-DESIGN.md`, settled 2026-10-18). This is the first of five steps. Today the review harnesses are a closed registry in `controller/review.py` (`HARNESSES`), their model family is a second table in `controller/review_mode.py` (`HARNESS_FAMILY`), the worker is Claude Code only and is named by a constant in `controller/telemetry.py` (`HARNESS`), the git host is a `Forge` protocol with one `gh` implementation that `milestone_branch.Context.forge` builds directly, and a job's tokens and cost are rebuilt from the raw stream each time they are read.

After this milestone each of those is reached through one named seam: a harness adapter that declares what it can do, a git-host adapter in a registry with its capabilities, and one usage record that every harness converts into. Nothing the Controller decides, prints or launches changes.

Out of scope, by the design page: Codex as a worker (A5), a second git host (a later adapter), any consumer reading the usage record instead of the telemetry block (A3 and the router), and routing.

## Decisions

Each decision states one principle.

- **D1. A refactor is proven by tests that do not change.** The existing contract tests (`tests/test_fake_codex_contract.py`, `tests/test_review.py`, `tests/test_review_claude.py`, `tests/test_review_mode.py`, `tests/test_forge.py`, `tests/test_telemetry.py`, `tests/test_worker_stream.py`, `tests/test_no_rewrite_invariants.py`) pass without an edit. A test that must change to pass is a behaviour change and stops the checkpoint for a plan amendment. New behaviour is covered only by new test files. The one allowed edit to an existing test is a registration, not an expectation change: `tests/test_package_structure.py` requires `controller.__all__` to equal the set of `controller/*.py` modules and to follow its own `DEPENDENCY_ORDER` list, so each new module is inserted into that list (and into `controller/__init__.py`'s eager `from . import (...)` literal and `__all__`) at the position D1a names. No assertion of that test changes; `DependencyGraphTest` then checks the position, and so the import-cycle risk, mechanically.
- **D1a. Where the two new modules sit in the import order.** `harness` goes immediately after `errors`: it imports only `controller.errors`, and `review_mode` and `telemetry`, which import it, come later. `usage_record` goes immediately after `worker_stream`: it imports `worker_stream` (for `session_telemetry`) and `harness`, both earlier, and `job`, which uses it, comes later. Both positions are inserted in the same way in `controller/__init__.py` (the eager import literal and `__all__`) and in `DEPENDENCY_ORDER`.
- **D2. An adapter wraps the existing code; it does not move it.** `ReviewHarness`, `CODEX`, `CLAUDE`, `GhForge` and the worker launch stay where they are. The new module holds plain declarations (names, roles, family, capabilities, pinned version) and the registry; it imports only `controller.errors` (which imports no `controller` module, so no cycle), and the existing objects stay the ones that launch (D3 says how the two are tied). Moving code is a larger diff with no benefit for a step whose gate is "nothing changed".
- **D3. The adapter registry is the one declaration of a harness's names and family, and every other place that holds one derives from it or is pinned to it by a test.** An adapter has a `name` (`claude-code`, `codex`: what the worker records and `telemetry` print) and, for the reviewer role, a `reviewer_name` (`claude`, `codex`: the key of `review.HARNESSES`, the `reviewer.harness` setting and the verdict's harness). One adapter carries both, so `claude-code` and `claude` stay two user-visible names of one adapter. The declarations that exist today and what becomes of each:
  - `review_mode.HARNESS_FAMILY` (`{"codex": "openai", "claude": "anthropic"}`) becomes `{a.reviewer_name: a.family}` over the registry, a derived value.
  - `telemetry.HARNESS` (`"claude-code"`) becomes the `name` of the registry's worker-role adapter, a derived value.
  - `ReviewHarness.verdict_family` (the literal in the `CODEX` and `CLAUDE` constructors in `review.py`) stays, because D2 moves no code; it is pinned: a test asserts it equals the adapter's `family` for each reviewer. The existing pin of `verdict_family` to `HARNESS_FAMILY` in `tests/test_review_claude.py` keeps passing unchanged.
  - `review_mode.WORKER_FAMILY` (`"anthropic"`) and `review_mode.SAME_PROVIDER_HARNESS` (`"claude"`) stay as literals, pinned: a test asserts `WORKER_FAMILY` equals the family of the registry's worker-role adapter and `SAME_PROVIDER_HARNESS` equals that adapter's `reviewer_name`.
  - `review.PINNED_VERSION` (`"codex-cli 0.162.1"`) and `review.CLAUDE_PINNED_VERSION` (`"2.1.296 (Claude Code)"`) stay, pinned: a test asserts each equals the `pinned_version` of the matching adapter, so the version is declared once in effect and cannot drift.
  - the keys of `review.HARNESSES` stay, pinned: a test asserts they equal the registry's reviewer names.

  A literal-equality test also asserts the derived values equal the literals they replace, so a mismatch cannot pass. No name a user sees changes.
- **D4. A capability the adapter does not declare is refused, never silently skipped.** An adapter declares: model family, supported roles (`worker`, `reviewer`), whether it can enforce single-agent and tool restrictions, how it reports usage (`reported`, `derived` or `none`), its pinned version, and that it fails closed on an unknown version. Asking for a role an adapter lacks (Codex as a worker) raises `HarnessRoleError`, and asking for a name the registry lacks raises `UnknownHarnessError`; both are `ControllerError` subclasses in `controller/errors.py` (the only type `controller.cli` catches), the first naming the harness, the role and the declared roles, the second the registered names. Nothing calls either path yet, so no existing flow reaches it.
- **D5. The git host is a registry of adapters with declared capabilities, over the `Forge` protocol that already exists, and it shares its closed set with the repository policy.** The policy already names the host: `controller/repo_policy.py` requires `forge.kind` and refuses a kind outside `FORGE_KINDS = frozenset({"github"})` at parse time, and `RepositoryPolicy.forge_kind` carries it. So there is no "policy names none" case and this milestone adds no default for one. `forge.py` gains a `FORGES` registry (`github`) and a capability record (pull requests, draft pull requests, squash merge, check reports, releases with assets). `FORGE_KINDS` stays where it is, pinned: a test asserts `set(FORGES) == repo_policy.FORGE_KINDS`, so a host cannot be added to one set and not the other. The kind reaches `Context.forge` through a new `Context.forge_kind` field, defaulting to `"github"`, the only value the policy admits; `Context.forge(repository)` keeps its signature, so its callers in `milestone_branch.py` (they pass `record["repository"]["forge_repository"]`, which carries no kind) do not change. The four places that build a `Context` (`cli.py` line 999, `job.py` lines 5676, 7227, 7334) are untouched too; the day a second host exists they set `forge_kind` from `RepositoryPolicy.forge_kind`, which is that adapter's work. `Context.forge` resolves `forge_kind` through `FORGES` and an unregistered kind raises `ForgeKindUnregisteredError`, a `ControllerError` in `controller/errors.py` naming the kind and the registered names; no policy reaches it today. The check runs on the default branch only: a `forge_factory`, when set, still wins outright as today (`milestone_branch.py` lines 289-292), so a test context with a factory never reaches the registry. The `gh` vetting, the explicit `--repo` rule and the "workers get no forge access" branch guard in `controller/routing.py` are untouched.
- **D6. The usage record is one frozen shape, built at the moment a job ends, and it only adds.** Fields: harness, provider, model id, input, output, cache-read, cache-write and reasoning tokens, each with one meaning defined by the record and not by any harness: **input** is the prompt tokens that were neither read from nor written to a cache; **cache-read** is the prompt tokens served from a cache; **cache-write** is the prompt tokens written to a cache; **output** is every generated token, reasoning included; **reasoning** is the reasoning share of output, informational, never priced on its own; wall time, turns, a quality flag per figure group (`reported` exact, `derived` computed from harness output, `unknown`), the cost with its source, the price-table version and the currency. A figure the harness does not give is `null` with quality `unknown`; a number is never invented. It is written to the job record as a new `usage_record` key next to `telemetry`, and rebuildable from the raw stream. Which jobs get one is part of the shape (D9a). The `telemetry` block, `inspect`, `status`, `follow` and the `telemetry` command keep reading the telemetry block, so their output is byte-identical (D1). Moving those consumers is later work. **One output surface does change, additively:** `controller resume --json` prints every returned job record as its durable shape (`controller/cli.py` lines 2225-2229, which strips only `reconciled_this_call`), and `job.resume` returns terminal records too, so a job that carries `usage_record` or `usage_record_failed` shows the key there; a record without the key prints exactly as before. That is the existing contract (the JSON is the durable record), not a new consumer: no reader is migrated and no key is removed or renamed, and CP4 pins it with a test. The plain-text lines of every command are unchanged.
- **D7. Cost is computed once, from tokens and a versioned price table, unless the harness reports it.** A Claude result reports `total_cost_usd`: the record keeps it with source `reported`. Where only tokens exist (a Codex review), cost is computed from `controller/prices.json` (price of input, cache-read, cache-write and output per token; reasoning is not a priced group, being inside output) and marked `derived`; a model absent from the table gives cost `null` and quality `unknown`. The table carries a `version` and a `currency`; changing a price adds a table version and never rewrites a stored record, which keeps the version it was computed under. The table ships in the package (`pyproject.toml` package data) and a test pins that it loads from the installed wheel layout, not only from the checkout.
- **D8. One converter per harness, and a captured sample is the contract.** `claude-code` converts the stream's `result` events through the existing `worker_stream.session_telemetry`, so its figures equal the telemetry block's by construction; a test over every captured stream in `tests/harness_contract/` asserts the record's figures equal the block's. `codex` converts the rollouts of a review job, by these rules. Within one rollout the figures are the last `token_count` event's `total_token_usage` (cumulative inside a rollout), mapped onto D6's meanings, because Codex's `input_tokens` includes its cached tokens and its `output_tokens` includes the reasoning ones, as in the OpenAI usage object, while Claude's `input_tokens` excludes `cache_read_input_tokens`: record input = `input_tokens` - `cached_input_tokens`; cache-read = `cached_input_tokens`; cache-write = `cache_write_input_tokens`, taken as reported and not subtracted from input (the captured sample has 0 and does not show whether Codex counts it inside `input_tokens`; a later capture that shows it does is a new converter version). Until that is shown, a Codex rollout with a **positive** cache-write figure keeps the figure but claims no exact disjoint input breakdown: its input group and its cost are `unknown` (cost `null`), never a computed number; a zero cache-write figure, which is every capture we hold, gives the exact derivation; output = `output_tokens`; reasoning = `reasoning_output_tokens`. A rollout whose cached figure exceeds its input leaves input `unknown`. The Claude converter maps `input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and `output_tokens` straight across, and reasoning is read from `usage.output_tokens_details.thinking_tokens` of the result event (quality `reported`; the captured streams carry 211, 1384 and 530) and is `unknown` only when that field is absent from every result of the job. `worker_stream.session_telemetry` omits this field and stays unchanged, so the `telemetry` block is untouched: the converter takes the reasoning figure through an additive usage-only path (a sum over the job's `result` events, read directly by `usage_record`), and every other figure still equals the block's by construction. A review's Claude attempts keep it the same way: `review.result_figures` and `add_figures` stay as they are (so `review.telemetry` is unchanged), and a sibling helper reads the reasoning figure of each attempt's `result` event, summed across attempts and stored under a new `usage_reasoning` result key that `_obtained` does not copy, as D9a does for `usage_rollouts`. Across rollouts the root sessions are summed, the first and the one D5's retry writes. A sub-agent rollout (`session_meta.payload.source.subagent.thread_spawn` set) is not added into those figures, because whether a parent's total already contains its children is not shown by the captured sample and double counting is the risk; the record carries the sub-agents' summed `total_tokens` as a separate `subagent_total_tokens` field, the figure the existing review note already reports per sub-agent. The rollouts come from the job's one end-of-job scan (D9a), so a root rollout is counted once whatever the retry did. The model id for the price lookup is the model the attempt was launched with (`AttemptContext.model`), not a value read from the rollout. A rollout with no `token_count` contributes nothing, and a job whose rollouts give no figure at all has every token figure `unknown`. `scan_rollouts` keeps only `total_tokens` of sub-agent rollouts today; CP4 adds the per-rollout figures to `RolloutScan` only (not to `Attempt`, which is per attempt and would double count, D9a) as a new field with a default, so no existing construction or assertion changes (D1). The captured `rollout_excerpt.jsonl` is the contract for one rollout; the multi-rollout case is a derived sample, built from that excerpt and labelled as derived, since the repository holds no capture of a retry or a sub-agent. Adding a harness later means one converter and one captured sample.
- **D9a. The record is written where the figures exist, and the key's place is fixed per job kind.** A worker job gets `usage_record` on exactly the two completion paths that build the `telemetry` block (`job.py` lines 4365 and 7901), as a top-level key beside `telemetry`; a worker job that ends FAILED, INCOMPLETE or drained outside those paths has no telemetry block and gets no record. A review job has no top-level `telemetry` key (its Claude figures live in `review.telemetry`), so its `usage_record` is a top-level key written by the one terminal write, `finish()` in `_run_review_job`, on every terminal status (completed, refused, failed, INCOMPLETE) in which a harness attempt ran, because the run was paid for on those paths too (`exc.figures`); it is absent when no attempt ran. A Codex review's figures come from one source: the clean-up step's `scan_rollouts(home)` (`review.py` line 1919, under `keeps_sessions`), which runs on every path and sees every rollout of the job's single Codex home exactly once. Both attempts share that home (one `AttemptContext`, `review.py` lines 1782-1784) and `_codex_attempt` rescans the whole tree after each run (line 1370), so a per-`Attempt` source would count the first root rollout twice and would be absent when an attempt raises. The clean-up step stores the per-rollout figures in the result dict under a new key, `usage_rollouts`, which `_obtained` does not copy, so the `review` block is unchanged; `finish()` reads that key to build the record.
- **D9. The record is advisory data and cannot steer a job.** Like the telemetry block (I6), a failure while building it is caught at the job boundary; it never changes a status, an outcome or a reconciliation. "Caught" means: the job record is identical to the record of the same run without this milestone, except that the `usage_record` key is absent and a new top-level key `usage_record_failed` holds the exception text. The problem is kept in that separate key, never inside the `telemetry` block's `problems`, so the telemetry block D1 freezes is unchanged. A test injects an exception into the converter and compares the job record to a control run.
- **D10. Documentation changes with the behaviour, in place.** The worker and development guides describe the adapter registry, the capabilities and the usage record; the roadmap marks A1 complete at acceptance. No narrative of the change is added to a guide.

## Risks

- **A hidden behaviour change.** Deriving `HARNESS_FAMILY` and `telemetry.HARNESS` from a registry could reorder an import or change a value. D1 and D3 make the unchanged suite and the literal-equality test the gate; a failure stops the checkpoint.
- **An import cycle.** `controller/harness.py` sits between `review.py`, `review_mode.py` and `telemetry.py`. It holds plain declarations and imports only `controller.errors`, which imports nothing from `controller` (D2), so `review_mode` and `telemetry` import it at module level, `telemetry` stays a light module, and `review.py` is not imported by it; D1a fixes the module's place in the dependency order, which `DependencyGraphTest` enforces; CP1 asserts the import set is exactly `{controller.errors}` and imports each of the three modules first in a fresh interpreter. The cost is that the family literal lives in two places (the adapter and the `review.py` constructors), which is why D3 pins them with a test.
- **The price table goes stale.** A derived cost is only as right as the table. The record keeps the table version and marks the cost `derived`, and the table's date is in the file; a price change is a new version, not an edit of history.
- **Scope creep into consumers.** Moving telemetry, budgets or `inspect` onto the record is tempting and is explicitly later (D6); a diff that touches a printed line is out of scope.
