Pull request title: `feat: run the functional review in an isolated tester so acceptance clears itself`

## Goal

Under an automatic acceptance gate the Controller launches the checklist writer (row 37, `functional.prepare`) and the findings applier (row 38, `functional.apply_findings`) already. What it cannot do is the middle: **row 38e** (`functional_evidence_needed`, action `functional.evidence.external`) says the Workflow awaits one `functional_evidence` result per flow at the approved head, and today the orchestrating session runs the checklist by hand (an independent tester, then `record-external-result`) and the Controller stops with `user_gate` until it has. After this milestone the Controller runs that middle itself:

1. at row 38e it builds an **isolated sandbox** for the item's head, launches an **independent tester** on the checklist, and checks afterwards that nothing outside the sandbox changed;
2. it records every flow's result with the Workflow's `record-external-result` (kind `functional_evidence`);
3. when a flow fails it puts the tester's findings where a person's findings go, so the next step is row 38 and the existing applier fixes them, and the loop returns to a fresh run at the new head;
4. when every flow passed, the Workflow's own answer moves on to rows 38f to 38h and acceptance by policy.

A person is asked only where one is needed: a tester that could not run, results the Controller cannot read, or an isolation breach.

Out of scope: the Workflow (the Controller only reports, as in C10b); a Codex tester (`harness.CODEX` declares only the reviewer role, so a Codex tester is a recorded follow-up); the post-acceptance defect loop (C10d); removing the lane's watchdog (after C12).

## Decisions

Each decision states one principle.

- **D1. The Workflow decides, the Controller runs and reports.** The step acts only at an `external_gate` whose action id is `functional.evidence.external`, whose `satisfied_by` is `functional_evidence` and whose policy object names an **automatic** acceptance gate (row 38e). Everything else about the gate (what is current, what the head is) is read from the Workflow's answer and its `record-external-result` refusals; the Controller evaluates no requirement itself. The Controller reads no `GATE_POLICY.json` and the answer's `policy` object is only `{source, digest, gate, mode}`, so it **cannot know** a policy's `required_flows`: this milestone does not support them (D4, D7). Row 37 (no current checklist) and row 38 (unconsumed findings) are launched as before and take precedence, because the Workflow answers them first.
- **D2. The tester is a job of its own, on the review harness's disposable-copy machinery, not a worker in the repository.** A new job kind (`functional_test`) reuses `controller/review.py`'s bounded runner, minimal harness home, environment allowlist and before/after snapshot guard, and adds a `functional` run kind that differs in exactly the ways a test run must: the disposable tree is a real Git clone (D3), the tester may run shell commands and write inside it and its output folder, and nothing else is writable. **Enforcement is required, detection is the second layer, and the boundary is closed, not assumed.** The tester's launch uses Claude Code's own sandbox (bubblewrap, present on this host). Claude's sandbox covers **shell commands only**; its file tools run outside it, and blocking Unix sockets on Linux needs the optional seccomp component. So the launch states a **closed tool set**: the only tool is `Bash` (no `Write`, `Edit`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Task` or MCP tool; the tester writes `RESULTS.json` and its logs with shell redirection, inside the sandbox), `Read` is not granted either (the shell reads the clone), and the run settings fix `allowUnsandboxedCommands` false (no unsandboxed retry), no `excludedCommands`, and no dependency fallback: **every launch requires the enforcement components** (bubblewrap and the seccomp filter) and a launch whose probe finds one missing or not enforcing ends at `functional_tester_unavailable`, never at a weaker run. The sandbox must refuse, by the process itself: writes outside the sandbox folder and the output folder (absolute paths to a stand-in home or config location, the shared temporary directories `/tmp`, `/var/tmp` and `/dev/shm`), network access, connection to a host Unix-domain socket, and **any write to the candidate itself (I2): anywhere in the clone except the writable locations D5 derives, and the clone's `.git` always**. D3's checks then verify. CP2 is a spike checkpoint of its own that proves each of these on the pinned CLI (D10); if the pinned Claude CLI cannot enforce any one of them, CP2 stops and amends this plan; detection alone is not an accepted fallback and an unsupported boundary is never narrowed silently. It runs on Claude (`claude-sonnet-5-5`, effort `medium`, user rule of 2026-10-09: the tester is cheaper than the implementation), through a new routing role `functional-tester` that `--role-model` and the settings file's `roles` object can override like every role. It is not a lifecycle worker: it holds no work-item lock, writes no state and never reads the Workflow's state files.
- **D3. Isolation is built by the Controller, before the tester starts, and verified after.** The sandbox is a folder `<runtime root>/functional/<job_id>/` holding: a clone of the item's branch at its head (`git clone --no-hardlinks`, so it shares no object file with the real repository) whose origin is a **scratch bare repository** (the branch pushed to it), so a push or fetch of `origin` reaches nothing real; a `bin/` directory first on `PATH` with a **fake `gh`**, a **fake `claude`**, a **fake `codex`** and a **fake `ssh`** (each logs its argv and exits non-zero); `GIT_ALLOW_PROTOCOL=file` and `GIT_SSH_COMMAND=false` so a push or fetch by URL over any network transport fails inside Git itself; scratch `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `TMPDIR`, and `PYTHONDONTWRITEBYTECODE=1` (so Python does not need a writable `__pycache__` beside the sources); the tester's shell `PATH` is `bin/` plus the system directories, never the real `claude` or `codex` directory (the runner starts the tester by absolute path); the review harness's environment allowlist for everything else. **The sandbox's limits are stated, not discovered:** no network, no real GitHub (the fake `gh`), no real `claude`, `codex` or `ssh`, and a `PATH` of `bin/` plus the system directories. The `PATH` carries **no** allowlisted extra tool in this milestone (a pipx binary such as `workflow-manager` lives under the real home and reads real state; allowing named tools is a recorded follow-up). **The fakes ship inside the package** (`controller/sandbox_fakes/`, four small refuse-and-log programs; `pyproject.toml` lists `packages = ["controller"]` explicitly, which setuptools does not extend to subpackages, so CP2 lists `controller.sandbox_fakes` there; a file under `tests/` does not exist for an installed Controller driving another repository). **The `bin/` entries are launcher scripts the Controller writes** when it builds the sandbox, not copies of package files whose mode a wheel may not keep: each is `#!/bin/sh` then `exec <sys.executable> -m controller.sandbox_fakes.<name> "$@"` with `PYTHONPATH` set to the directory that holds the running `controller` package, and the Controller sets mode 0755 itself. **The pull-request flows are not supported in this milestone, and that is stated rather than bridged** (I4): the Controller's forge boundary (`controller/forge.py` `vet_gh`) refuses a `gh` located inside the repository or a temporary directory, and the Workflow's (`scripts/workflow_forge.py` `origin_repository`) requires a `github.com` origin, whereas the sandbox's `gh` is a scratch launcher and its origin a scratch bare repository. Neither production check is relaxed or given an exception for sandboxes. So a checklist flow that needs a pull request, a forge call or a `step` through the pull-request rows cannot run in the sandbox and is `environment` (D4); the fake `gh` only refuses and logs, so a tester that tries it learns so at once. A sandbox-side forge model is a recorded follow-up (CP6).
After the run the Controller compares the real repository's snapshot (`review.snapshot_repository`: worktree digest, `HEAD`, refs, **reflogs**, status, the Workflow state file) before and after. An **isolation breach** is evidence that something real was reached, and only that: any difference in that snapshot; a real session beyond the tester's own in the job's private Claude home (the job home is private, so any other session or project entry is a nested real `claude`); a change to the real origin's refs, **read only when the real origin is a local path** (its refs are listed with a local `git for-each-ref` before and after; a URL origin is never read, because the Controller makes no network call: for it the prevention of D2 and `GIT_ALLOW_PROTOCOL` is the only layer, and a failed local read of a path origin is `isolation_breach` with the read error as its detail). A call of a fake (`claude`, `codex`, `gh`, `ssh`) is logged and is **not** a breach: it reached nothing, and neither is a Git push or fetch by URL over a network transport, which `GIT_ALLOW_PROTOCOL` and the sandbox's network limit refuse before anything is reached. The Controller does not try to detect a prevented attempt; it relies on the enforcement of D2 plus the snapshot, nested-session and origin checks above, and the fake logs are kept only for the gate message. A breach fails the run (D7) and nothing is recorded; it keeps the sandbox, which lives at the path above, which the gate message and `explain` name; the step removes a kept sandbox of the item when the next functional job for it starts, so at most one is kept per item.
- **D4. Flows come from the checklist, results come in one file.** The tester's prompt gives the checklist (`docs/ACTIVE_MILESTONE.md`'s "Functional review checklist" section at the evidence commit, read from the clone) and the exact result format: a file `RESULTS.json` in the output folder, a list of `{flow_id, status, summary, log}` plus, **required on a `failed` entry and refused on a `passed` one,** `reason`: `defect` (the product did not behave as the flow expects) or `environment` (the flow could not be run or judged in the sandbox: it needs the network, the real GitHub, a pull request or any forge call, a tool not on the sandbox `PATH`, or a real model). `status` is `passed` or `failed` (the Workflow's only two statuses, so an `environment` flow is still recorded `failed`), `log` is the name of a file the tester wrote in the output folder, and every flow in the checklist has at most one entry. The ids are `flow-1`, `flow-2`, and so on, in the order the checklist lists its flows (the Controller numbers them; the tester does not choose ids). **Recognising a flow** is fixed by the shapes this repository's own checklists use, because `/prepare-functional-review` fixes no shape. The checklist is the section under the heading `Functional review checklist` (any level), up to the next heading of the same or a higher level; sub-headings belong to it. Lines inside fenced code blocks (``` or ~~~, to the matching close) are never headings, table rows, labelled paragraphs or list items, for the section end and for every rule, so a `# comment` or a numbered line in a setup block neither ends the section nor becomes a flow. The Controller applies the **first** of these rules that finds at least one flow, to that section only, so one checklist never mixes numbering schemes: (1) **table rows** whose first cell is a short label (one letter, or one or two digits) below a header row and a separator row (the shape at `eeeb4fa`: `| A | do | expect |`); (2) **bold labelled paragraphs** that start a line with `**<label>.`, `**<label>)` or `**<label>:` where `<label>` is one letter or one or two digits (the shape at `454ffe7`: `**A. The local build's version.**`); `**Setup.**`, `**Flows.**`, `**Test data.**` and `**Known limitations and out of scope.**` are not flows; (3) **headings** below the section's own whose text starts with such a label or with `Flow`, other than `Setup`, `Flows`, `Test data` and `Known limitations`; (4) a **top-level numbered list**. A section whose only content is a link to a repository file (the "link to a short file" that `/prepare-functional-review` allows) is read from that file at the evidence commit, from the clone, by the same rules; a link that leaves the repository or names a missing file finds no flow. The tester's prompt gives each flow its id, its label and the text of its row, paragraph, heading block or item, **and the sandbox's limits above with the rule for `reason`: a flow the sandbox cannot run is `failed` with `environment`, never `defect`, and the summary names what was missing.** The checklist writer (row 37) is told the same limits in the prompt the Controller gives that worker, so new checklists prefer flows that run offline against the fake `gh`; an older checklist keeps its flows and relies on `environment`. **When no rule finds a flow the step stops before any tester starts** with the gate `checklist_unrecognised` (D7): no sandbox is built, no usage is reserved and no job record is written. **A flow of the checklist the file leaves out** is not an invalid file and is **not a product defect** (O1): the Controller adds a `failed` entry for it with `reason` `environment`, a Controller-written **log file** and a Controller-written summary that names the cause, "not run: the tester ended at the timeout" when the bounded runner ended it for `functional.timeout_seconds`, otherwise "not run: the tester left this flow out of the results file", and never silently drops it. The Workflow refuses a record without a valid `log_digest` (`evidence_malformed`), so the Controller writes, for each such entry, a short log of its own into the output folder (cause, `functional.timeout_seconds` where it applies, the job id) and digests that file like any other; the entry is then recorded and the run reaches `flows_not_runnable` rather than `recording_refused`. Such a flow ends at `flows_not_runnable` (D7) and spends no applier round. A **missing required key or entry of an entry that is present** is a structural fault below, not an omission. The validator refuses (`results_invalid`, D7) only a structural fault: a missing or unparsable file, an unknown key, a duplicate id, an id that is no checklist flow, a bad status, a missing `reason` on a failed entry or a `reason` on a passed one, a log outside the output folder. **Symlinks are resolved before a path is trusted (O2):** a `log` that is a symlink, or whose resolved path leaves the output folder, and a `RESULTS.json` that is a symlink or resolves outside it, is `results_invalid`; the Controller opens neither, so it never digests or quotes (D6) a host file the sandbox could not read. The Controller validates before it records anything. Policy `required_flows` are not supported (D1): there is no required id to check.
- **D5. One report per flow, at the head the sandbox ran.** For each entry the Controller builds the Workflow's `functional_evidence` input (`flow_id`, `status`, `head` = the head of the sandbox clone, `ran_at`, a `summary` object holding the tester's text, the flow's exit evidence, **and the entry's `reason`** (O2: a later inspection tells an environment limit from a product failure) and the captured checklist blob id, `log_digest` = the sha256 of the flow's log file, `run_ref` = `controller:<job_id>`, `reporter` = `workflow-controller <version>`) and calls `record-external-result` once. The Workflow recomputes the implementation identity at `head`; a refusal of any entry stops the step with the Workflow's own code in the message and records the entries already accepted as they stand. The Controller never records a flow whose log it did not read and digest. **Passing evidence is recorded only when the bytes the tester exercised are bound to the captured candidate (I2), and the binding trusts nothing the tester could write in the clone's `.git` (I1).** The Workflow checks the commit identity at `head`, not the tester's mutable filesystem, so the Controller does. The tester has a shell with write access to the whole clone including `.git/`, so after the run a Git command run in the clone would run the tester's code (`diff.external`, `core.fsmonitor`, config hooks, `filter.<d>.clean` and `textconv` drivers chosen through `.git/info/attributes`) outside the sandbox, and the clone's index and ignore files can hide an edit (`skip-worktree`, `assume-unchanged`, `.git/info/exclude`, `core.excludesFile`, a rewritten object). So **the Controller never runs Git in the clone, and never reads the clone's index, config, attributes, exclude file or objects as evidence.** Before the run it records, from the **real** repository's tree at `head` (a Controller-run `git ls-tree -r` and `cat-file`, hardened with the command-scope overrides `controller/workflow_contract.py` already holds, not a third list), a **manifest** of every tracked path: mode, size and sha256 of the blob (for a symlink, its target), and it copies the tree's `.gitignore` files as the ignore rules; the checklist blob is read from the manifest and compared with the blob at the same head in the real repository. After the run it walks the clone's worktree directly in Python (the `.git` directory and the output folder aside), **with `lstat` and no-follow throughout (O1): a symlink is compared by its target string and never opened or traversed, and an entry that is not a regular file, a directory or a symlink (a socket, FIFO or device) is an extra file and fails the check, in the worktree and under `.git`**, and requires: every manifest path present with the same mode, size and sha256 (so a modified, staged, `skip-worktree`, `assume-unchanged` or deleted file, and altered checklist bytes, all fail); and **no file the manifest does not list**, except one that the manifest's own ignore rules ignore. The ignore rules are evaluated by Git run on a **Controller-owned git dir** (a fresh scratch bare repository, never the clone's) with the clone as `--work-tree`, run through the same shared helper and `_GIT_PINNED_CONFIG` of `controller/workflow_contract.py` as the manifest read (O3: no second, separately enumerated list; the pinned `core.fsmonitor` value is the compatibility-preserving empty one, not `false`), plus a private `GIT_INDEX_FILE`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `core.excludesFile=/dev/null`, `--no-ext-diff --no-textconv`, and only the copied `.gitignore` files in force: **any `.gitignore` or `.gitattributes` file the manifest does not list is itself an extra file and fails the check, wherever it is** (an untracked `.gitignore` containing `*` cannot hide a directory). The fixture and build-output locations the repository's own `.gitignore` declares are the explicit allowance; nothing else. **The fresh clone is verified against the manifest before the tester starts (O2).** The manifest is built from raw blobs, so a checkout conversion (`core.autocrlf`, a `.gitattributes` `text`/`eol`/`filter` rule, or a filesystem that cannot hold a symlink) would make every clean run disagree with it. The Controller clones with `core.autocrlf=false` and every `filter.*` driver unset, walks the fresh clone with the same comparison as the post-run walk, and a disagreement ends at `functional_tester_unavailable` (D7) with the first differing path, before any tester is launched and any usage reserved. The clone's `HEAD` and refs are read as plain files (`.git/HEAD`, `packed-refs`, `refs/**`) and compared with the captured values, with no Git command. **A change under the clone's `.git` beyond the expected ones is `tested_bytes_unbound`:** the only allowed changes are the `index`, files under `logs/`, `FETCH_HEAD`, and new loose objects (existing object files are byte-identical); a changed `config`, `hooks/`, `info/`, `HEAD`, `packed-refs`, `refs/` entry, `shallow` or any other file is a failure, because a manifest comparison needs none of them to have changed and such a change shows the tester tried to steer Git. Every later Git call the Controller makes about the sandbox (cleanup is plain file removal, not Git) follows the same rule. The recorded `summary` carries the checklist blob id. **The candidate is read-only for the whole run, not only compared afterwards (I2).** The comparison above proves the final bytes only: a tester could save a source file, edit it, run a check that passes on the edit, and restore the original before it reports `passed`, and the manifest, the `.git` change check and the Workflow's identity check at `head` would all agree. So the tester's launch (D2) makes the candidate unwritable **by the process itself**, with no reliance on a later comparison: the sandbox's write allowlist holds only the output folder, the scratch `HOME`, `XDG_*` and `TMPDIR`, and the **writable locations** derived by the rule below, and its deny list covers the **clone root recursively** (so every tracked path, every new file beside one, the checklist and `.git` are denied, with one entry however many files the tree holds: no per-file entry scales with the tree, R7-004). An in-place write, a rename or replace over a tracked file, a deletion, a new file beside one, a `chmod` and the restoring write are all refused. **Precedence (R7-001):** a more specific allow path beats the enclosing deny, so a writable location below the denied clone root is writable while its parents stay denied; a deny on `.git` or on a manifest path always wins, because no writable location can be one (the derivation refuses a pattern whose directory is, holds or lies under a manifest path or `.git`). CP2 proves exactly this ordering on the pinned CLI. **Derivation of the writable locations from `.gitignore` (R7-001):** only the clone's root `.gitignore` is read, and a line is admitted only when it is a glob-free, non-negated, single-component directory pattern: it ends with one `/`, has no other `/` except an optional leading one, and holds none of `*`, `?`, `[`, `\` or a leading `!`. The Controller creates each admitted directory empty **at the clone root only**, and that is the whole allowance: a same-named directory deeper in the tree (`controller/__pycache__/`) is not writable. Everything else is refused as a writable location: globs, patterns without a trailing `/` (file patterns), multi-component patterns, negations, a nested `.gitignore`, and any pattern that names `.git` or a manifest path. A refused pattern still serves as an ignore rule for the post-run walk, which is harmless because the tester cannot write there. In this repository the root `.gitignore` admits `__pycache__/`, `.venv/`, `.idea/`, `.vscode/`, `.ai-review/`, `.controller/`, `build/` and `dist/` (each at the root) and refuses `*.py[cod]`, `*.pyc`, `*.egg-info/` and the files `controller/BUILD_INFO.json` and `.claude/settings.local.json`. So a flow that runs `pip wheel .` or `pip install .` **in the clone** cannot write `*.egg-info/` or `controller/BUILD_INFO.json` and is refused by the sandbox: the tester's prompt tells it to build from a copy of the clone made under its `TMPDIR` (D5, trust boundary below), and the `flows_not_runnable` gate message and `explain` list the patterns the derivation refused, so a person sees why. A flow whose check has to write elsewhere in the clone is `environment` (D4), and the tester's prompt states the limit. **What the binding does not cover (R7-002):** the Controller binds the candidate it handed over and keeps it unchanged for the whole run; it cannot bind which bytes the tester chose to execute. A tester with a writable `TMPDIR` can copy the clone there, edit the copy, run a check that passes on the copy and report `passed`: the clone stays unchanged, every poll and the post-run walk agree, and the Workflow's identity check at `head` passes. This is the same act as a restored edit, moved to a copy, and no sandbox closes it, because which bytes a model executed is part of the tester's trust boundary, like a bare `passed`. The tester's prompt requires that any copy is made from the clone unchanged (for example `cp -a`) and that no flow edits product source; a copy that is edited is a tester fault, outside what is enforced, and the record names the run reference so it can be audited. What this design claims is only that **the candidate cannot be changed during the run**. The post-run walk stays as the second layer and as the check of the Controller's own build. CP2 proves the deny list and its precedence on the pinned CLI with the restore probe of D10; if it cannot be enforced, CP2 stops and amends this plan, because detection after the fact cannot see a restored edit. A clone that fails the post-run check **records nothing** (not even a failed entry) and ends at the gate `tested_bytes_unbound` (D7); the evidence it would have produced is not about the candidate.
- **D6. A failed flow becomes findings through the same door a person uses.** When any entry is `failed` with `reason` `defect`, the Controller writes the findings text to the Workflow's `functional_review_path` (the path the Workflow's own contract answers, `workflow_contract.py`; never a hard-coded layout) in the format `/apply-functional-review` already reads, naming each defect flow, the tester's summary and the log excerpt, **under a Controller-written header that names the tested head, the checklist blob and the run (`controller:<job_id>`)** (I3). The Workflow refuses a findings file whose bytes it already recorded as applied (`workflow_fingerprint.assert_functional_review_not_already_consumed` compares a content hash), so a fix that leaves the same failure with identical text would otherwise be refused at row 38 and skipped to 38i; the header makes every fresh failed run's file different, and the identical failure text after a head change stays actionable. `environment` flows are recorded `failed` (D5) but never written as findings: the applier is not asked to change code for a limit of the sandbox, and the gate of D7 names them. When **every** failed entry is `environment` no findings are written at all. The file is uncommitted, exactly as a person's would be. The next `step` meets row 38 and launches the applier. The failed results are recorded first (D5), so the Workflow's own record shows the failure, and a fixed head makes them stale rather than cleared, which is the Workflow's rule.
- **D7. The step's stops are few, named, and ask a person only for a fault.** Outcomes: `recorded` (all passed and the next decision is the Workflow's), `findings` (some defect flows failed; findings written; the next decision is row 38), `environment_limited` (every failed flow is `environment`; all results recorded, no findings written, the gate below), `unchanged`, and the gates below.
  - `unchanged` fires where row 38e **re-answers at a head the Controller already tested**: the last functional job for this item ran the same head and checklist blob and recorded every flow, and the Workflow still says evidence is needed. That is a requirement the checklist cannot satisfy, for example a policy's `required_flows` this milestone does not read (D1). The step does not run again and returns one `lane_blocked` whose message carries the Workflow's own 38e detail. It is **not** the finite-cycle argument for a failed flow: once a failed record is current at the anchor the Workflow answers row **38i** (`gate_evidence_unmet`, blocked), not 38e, so a tester false positive that the applier disposes of without a change (the "no code change" or "deferred" dispositions) ends at 38i, which is a person's stop.
  - The cycle that can repeat is a fix that moves the head: a fix, a new technical approval, a fresh tester run that fails again. `functional.apply_findings` is not in `review_rounds.CAPPED_ACTIONS` and no existing cap counts tester runs, so the Controller bounds it itself: it counts the item's `functional_test` jobs that ended `findings` (job records, no Workflow state) and at **3** stops with the gate `functional_rounds_exhausted`. **The remedy** is a person's: test the head by hand and record the evidence as before (the gate message says so and names `functional.automated` false, which restores today's stop for the repository so the step does not launch the tester again). The count is over the item's whole life and nothing resets it; it is read from job records, so a pruned record lowers it, which only grants further runs and is accepted. A cap setting like the review caps is a recorded follow-up (CP6), not part of this milestone.
  - `flows_not_runnable` is the gate after `environment_limited`: it sends `user_gate`, names each such flow and its summary, lists the writable-location patterns D5 refused, and says the remedy: run those flows by hand and record them, or change the checklist so they run offline. It does not launch the applier, and the job does not count towards the round bound (only `findings` jobs do).
  - Gates: `flows_not_runnable`, `tested_bytes_unbound`, `checklist_unrecognised`, `functional_tester_unavailable`, `results_invalid`, `isolation_breach`, `recording_refused`, `functional_rounds_exhausted`. `checklist_unrecognised` is raised by the pre-launch read of D4 and sends `user_gate`; its message names the section, the four shapes, and that the checklist writer's output (or the section) has to carry one of them, or `functional.automated` can be set false to keep the person's stop. `functional_tester_unavailable` has four causes, each returning the gate at once and sending `user_gate`: **no `claude` binary**, **the role is refused**, **the sandbox enforcement is missing or its launch probe fails** (D2: a missing component, a refused setting) and **the fresh clone does not match the manifest (D5, O2)**. A usage limit is not one of them: the job is handled like every job by the existing usage-limit rules. `results_invalid`, `isolation_breach`, `tested_bytes_unbound`, `recording_refused`, `flows_not_runnable` and `functional_rounds_exhausted` send `user_gate`; `unchanged` sends `lane_blocked`. A tester that runs past `functional.timeout_seconds` is ended by the bounded runner and is `results_invalid` when it left no valid file.
- **D8. ## Risks

- **The review harness may not fit a test run.** It is read-only by design; CP3 adds a `functional` kind and its argv check and CP2 proves Claude Code's own sandbox on the pinned CLI first (D2). If the pinned CLI cannot grant a shell-only, write-, network- and socket-limited run, CP2 stops and amends this plan rather than widening the boundary or falling back to detection alone.
- **Flow ids are the Controller's, and `required_flows` are not supported.** A checklist whose flows change between rounds renumbers its flows. A repository whose policy lists `required_flows` the checklist does not cover meets `unchanged` and a `lane_blocked` stop naming the Workflow's detail; reading the policy needs a Workflow query that returns it, a recorded follow-up (CP6).
- **A tester is a model.** The Workflow trusts reported evidence (its trust boundary says so). The Controller binds the candidate it handed over and keeps it unchanged, but it cannot bind which copy the tester ran: a copy edited under `TMPDIR` that passes is not detectable (D5), so the prompt forbids it and the run reference allows an audit; the record names the digest, reporter and run reference, and `functional.automated` false returns the gate to a person.
- **Pull-request flows do not run in the sandbox.** The production forge checks (`controller/forge.py`, `scripts/workflow_forge.py`) stay unrelaxed, so older checklists with such flows end at `flows_not_runnable` until a person runs them or a later milestone adds a safe sandbox-side forge model (CP6 follow-up).
- **The vendored tree is 2.12.0.** Row 38e answers there; a newer Workflow's changes are follow-up work, as for C13b.
