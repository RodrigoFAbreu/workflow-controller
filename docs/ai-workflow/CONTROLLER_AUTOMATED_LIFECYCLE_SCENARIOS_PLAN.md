## Goal

Today a functional review is a manual act. A worker writes a checklist, an independent tester runs its flows in scratch clones, and the orchestrating session records each flow as `functional_evidence`. C10 will let the Controller accept a milestone on automated functional evidence instead, but nothing yet produces such evidence: the lifecycle is exercised by about 13 000 lines of unit and end-to-end tests whose results are a pass/fail count, not a record that says *which user-visible path ran, against which commit, and what it observed*.

After this milestone the repository has a **scenario catalogue**: named, whole-lifecycle paths (a milestone from trunk start to the merge, a human gate and its resume, a worker that fails, a process killed and resumed, notifications on a run, a usage pause and its resume, the read-only commands). Each scenario runs in a hermetic environment (a scratch bare origin, a scratch clone, a fake `gh`, a fake `claude`, a fake SignalHub, scratch `HOME`/XDG/runtime directories), proves afterwards that nothing outside that environment changed, and yields one evidence record in the exact shape of the protocol's `functional_evidence` input (`flow_id`, `status`, `head`, `ran_at`, `summary`, `log_digest`, `run_ref`, `reporter`). One command, `python3 tools/run_scenarios.py`, runs the catalogue and writes the records; the ordinary test suite runs the same scenarios, so CI keeps them green.

1. A scenario kit builds the hermetic environment and runs each scenario in a **sandbox process** (a user, network and mount namespace that every descendant inherits, entered in two phases so the scenario process holds no capability, D3), enforces it (the fakes are what `PATH` resolves, no model runs, no network leaves the sandbox, the real locations are unwritable) and proves, after every scenario, that the real repository's code, refs and index are content-identical and that nothing of the scenario reached a real location.
2. A runner lists, runs and checks the catalogue and writes evidence records bound to the exact `HEAD` it ran against (it refuses a tree whose code differs from `HEAD`, because a record for uncommitted code binds to nothing; Workflow bookkeeping may be dirty, D4).
3. Ten scenarios cover the paths a functional review of the last milestones walked by hand (the catalogue in D5).
4. The development guide, the roadmap and `docs/ACTIVE_MILESTONE.md` say what exists and what C10 consumes.

Out of scope: **submitting** the records (`record-external-result`, `/satisfy-gate`) and any policy that accepts on them (C10); the automated functional review workers (checklist, tester, apply: C10, ROADMAP 11.9); everything under `controller/` (the Controller gains no code); the live-worker test (`CONTROLLER_LIVE_WORKER=1`) which stays opt-in; a real forge or a real model; a new CI job.

## Decisions

- **D1. Scenarios are test-side code, not a Controller feature.** They live in `tests/scenarios/` and `tools/run_scenarios.py`. `controller/` does not change, so no release, no new exit code and no new public command. C10 calls the runner as a subprocess and submits what it wrote. This keeps the interface (a JSON file per run) narrow and lets the catalogue grow without a Controller release.
- **D2. A scenario is a function over a kit, not a pile of test ids.** `@scenario(flow_id, covers=...)` (the registry refuses a flow id that does not match the Workflow's `FLOW_ID_RE`, D4) registers `def run(kit) -> None`; it drives the real `cli.main` (or the real module as a child process), records observations with `kit.observe(name, value)` and asserts with plain `assert`-style helpers that raise `ScenarioFailure` with a message. A scenario's `summary` is the ordered observations (step exit codes, phases, commit subjects, worker invocation count, event types sent, selected record fields and the digest of each normalised record, D9), so the record says what happened, not only that it passed. `tests/test_scenarios.py` wraps every registered scenario in one `unittest` method (one generated `TestCase` class per variant, O1) so the suite and the runner share one code path. Existing end-to-end tests are **not** refactored; scenarios import their builders (`tests/fixtures.py`, `tests/fake_claude.py`, `tests/fake_gh.py`, `tests/fake_signalhub.py` and the `Lifecycle` model imported by its exact name, `tests.test_lifecycle_orchestration.Lifecycle`, not the unrelated `Lifecycle` of `tests/test_protocol_lifecycle.py:213`) and copy no logic.
- **D3. Hermeticity is enforced by construction, then verified, never assumed.** Each scenario runs in its own **sandbox process**: the runner and the test wrapper start the scenario worker through the **two-phase launch** below (probed at start as a whole chain, see "Isolation unavailable"), so every descendant (shells, git hooks, Workflow interpreters, the existing fixtures' `python -E` children, the Controller's re-exec) inherits two kernel-enforced properties that no environment variable, interpreter flag or capability can drop:
  - **Two-phase launch (decision, revision 5).** A single `unshare` cannot do both jobs: under `--map-current-user` the process runs as the invoker's non-zero uid and the kernel clears its effective capabilities on `execve`, so it can neither mount nor bring up loopback (measured: `CapEff` 0, `mount` and the `SIOCSIFFLAGS` ioctl fail `EPERM`); under `--map-root-user` every descendant is uid 0 with full capabilities in the namespace, and read-only binds made in that same namespace are not locked, so a descendant can `umount` or `remount,rw` them. The kit therefore (1) **setup phase**: starts `unshare --user --map-root-user --net --mount` running the kit's setup, which mounts the scratch tmpfs, makes every real location read-only or hides it under an empty tmpfs, and brings loopback up; then (2) **drop phase**: the setup `exec`s `unshare --user --map-user=<invoker uid> --map-group=<invoker gid>`, a nested user namespace with **no new mount namespace**, so the setup's mounts stay in a mount namespace owned by the outer user namespace, and the scenario worker runs there as the invoker's uid with `CapEff` 0. In that process scratch writes succeed, a write to a real location fails `EROFS`, `umount`/`remount,rw` of a protected location fails `EPERM`, and a connection to anything but loopback fails `ENETUNREACH`. The drop may instead use `setpriv`/`capsh` if the probe finds that more portable; either way the capabilities are shed explicitly and the probe proves it. **Tool resolution**: the launcher resolves `unshare` (util-linux 2.38+ for `--map-user`/`--map-group`) and any drop tool from the invoker's `PATH` *before* the scenario environment is built, since that environment's `PATH` holds only the scratch `bin/`; the probe records the resolved path and `--version` so a later "not found" is not misread as an unavailable namespace. The launcher and its probe live in `kit.py`, not split between the runner and the test wrapper.
  - **Network**: a network namespace whose only interface is a loopback the setup phase brings up itself (an `ioctl` on the interface flags while it still holds capabilities, no `ip` binary needed). A connection to anything but the scenario's own loopback fakes fails with the kernel's `ENETUNREACH`, whatever the program, its proxy variables or its URL say.
  - **No PID namespace (decision, revision 4).** The sandbox deliberately has no `--pid`. The Controller's own liveness and lock answers depend on seeing the host's process namespace: `worker._proc_numbers_own_namespace` is false under an inherited `/proc` in a PID namespace (so `start_ticks` is not captured and `assess_worker_liveness` falls back to a `killpg`-only test that answers `UNVERIFIABLE` for a zombie), a sandbox init that does not reap leaves a killed Controller's worker a zombie so `resume` exits 45 instead of reconciling, and with `--mount-proc` `lock.probe_lifecycle_lock`/`probe_file_lock` answer `unknown` where the host answers `free` (`controller/lock.py:288`, `:336`). Dropping `--pid` keeps those answers identical to a host run and to the diagnostic mode, so the two differ only in network and write enforcement, which no Controller output observes. Leftover processes are bounded by D8 instead.
  - **Permission bits.** After the drop the scenario process is the invoker's uid with no effective capability in every namespace-mode run, so DAC permission failures behave as on the host and there is no `CAP_DAC_OVERRIDE`; there is no root-mapped variant of the scenario process. **No scenario relies on a permission bit to make a write fail** (it would also fail differently in the diagnostic mode, where the process is the invoker anyway) (an unwritable runtime root or settings file is built by making the path a directory or a read-only mount in the scratch tree, not by `chmod`), and the kit test asserts the fixture helper does not use `chmod` for that purpose.
  - **Writes**: a mount namespace in which every *real location* is remounted read-only or hidden under an empty tmpfs, so a write fails with `EROFS` inside the scenario and fails it, attributably (nothing else could be writing in that namespace). The real locations are: the real checkout; `~/.config/workflow-controller`, `~/.local/state/workflow-controller` and any `XDG` override the invoker had; the real SignalHub directory (CP1 enumerates it from the notifier tooling's location and environment); the resolved runtime root of the invoker, including a checkout `.controller` and any `--runtime-dir` or environment override; and `/tmp/workflow-controller-tests`; and the checkout's **resolved Git metadata** (decision, revision 6): the kit resolves, with the sanitised Git environment, `git rev-parse --absolute-git-dir` (the worktree's own directory: `HEAD`, `index`, per-worktree refs) and `git rev-parse --git-common-dir` (shared refs, packed refs, config, hooks, objects), and protects each resolved directory that is not inside the checkout tree with its own read-only bind (a directory inside the checkout is already covered by the checkout bind), so `git update-ref`, an index write, an `index.lock` creation or a ref pack from inside fails `EROFS`. The resolution runs before the namespace is entered; if it fails, or a resolved path is not an existing directory that can be bind-mounted (a dangling gitfile, a submodule layout, an unreadable parent), the kit **refuses before executing any scenario**, naming the path (exit 2 for the runner, a failing atom for the wrapper), rather than running with unprotected metadata. Reads stay possible, so a `git clone --shared` or alternates reference to the real object store still works. The scratch tree (origin, clone, `bin/`, `HOME`, `XDG_*`, runtime root, `TMPDIR`) is a fresh tmpfs inside the namespace and is the only writable area.
  **Execution**: the sandbox environment is *built*, not filtered: an allow-list (`PATH`, `HOME`, `XDG_*`, `TMPDIR`, `LC_ALL=C`, `PYTHONHASHSEED=0`, the pinned Git variables below) and nothing else, so no proxy variable, `SIGNALHUB_URL` or credential is inherited. `PATH` is the scratch `bin/` alone: it holds the three fakes (`claude`, `gh`, `workflow-manager`) and symlinks to exactly the tools the fixtures use (`git`, `sh`, `python3`, `sleep`, `timeout`, `setsid` and the coreutils CP1 enumerates from the fixtures), so a real `claude`, `gh`, `workflow-manager` or `curl` cannot be found *by name* by any descendant. An absolute-path `exec` is not prevented by `PATH`; D7 says what detects it and what it does not cover.
  **Git**: every inherited `GIT_*` variable is dropped (a prefix rule, not an enumeration, so `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_CONFIG_*`, `GIT_EXEC_PATH` and the rest cannot redirect a write or a `HEAD` lookup, and the Controller's git runner, which inherits `os.environ` at `controller/gitrepo.py:57`, sees only the sanitised set); then the kit sets `GIT_CONFIG_GLOBAL=<scratch>/gitconfig`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0` and `GIT_AUTHOR_*`/`GIT_COMMITTER_*` (D9). The scratch `gitconfig` sets `core.hooksPath` to an empty scratch directory, `init.defaultBranch`, `core.autocrlf=false`, and no `url.*.insteadOf`. Every remote is a path to a scratch bare repository, and the kit refuses, at fixture creation, at snapshot time and at scenario start, a remote that resolves outside the scratch tree. The environment is built before the Controller is imported, so the in-process `cli.main` and every child share it.
  **Isolation unavailable: fail closed (decision, revision 6).** The probe runs the **whole chain** in a throwaway directory: the user-namespace launch, the setup (scratch tmpfs, a read-only bind, loopback up) and the drop, then checks from inside the dropped process that `CapEff` is 0, the uid is the invoker's, a protected write fails `EROFS`, `umount` fails `EPERM` and a non-loopback connection fails. It reports **which step failed** (`user-namespace`, `setup` or `drop`; an AppArmor or sysctl restriction on unprivileged user namespaces, as on Ubuntu 24.04, fails the first), and a drop that fails while `unshare` itself succeeds is *unavailable*, never a silent downgrade to root-mapped execution. The built environment, the `PATH` of fakes and the token scan cannot stop an absolute-path `exec`, a socket opened by a descendant, or a token-free overwrite or deletion, so **without the sandbox no scenario that can reach real data or the network is run, and none produces evidence**:
  - **The test-suite wrapper** (`tests/test_scenarios.py`) runs the probe once. If the sandbox is unavailable it **runs no registered scenario**: every scenario atom is skipped with a reason naming the failed step, except when the environment variable `CI` is set (GitHub Actions sets it), where the atoms **fail** with the same text, so a green CI run always means the namespace enforcement was exercised and an image that restricts user namespaces is a red build to be fixed or amended in the plan, never a quiet pass. CP1 measures the probe on the CI runner image first; if it fails there, CP1 stops and the plan is amended before CP2 starts. **That CP1 measurement was not made as written** (the branch first ran on CI after CP5); CP6 now covers it. **Amendment (revision 7):** the measurement the implementation could only make once the branch ran on CI showed exactly this: GitHub's `ubuntu-latest` image (Ubuntu 24.04, and the coming Ubuntu 26 image) sets `kernel.apparmor_restrict_unprivileged_userns=1`, the probe's `user-namespace` step is refused, and every scenario atom fails red. The decision stays fail-closed (no downgrade, no skip under `CI`); the fix is on the runner, not in the sandbox. CP6 adds a step to the CI `tests` job, generated through `tools/ci_workflows.py`, that lifts the restriction with `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` (guarded by the existence of the sysctl, so an image without it passes the step unchanged), so the scenarios run fully protected on CI. The sandbox code, the probe and the fail-closed behaviour are unchanged by it.
  - **The runner** (`tools/run_scenarios.py run`) exits 2 with the failed step and writes **nothing** (no record, no `index.json`). The only override is `--degraded-diagnostic`, a developer's explicit acceptance of the exposure for local debugging: it runs the scenarios without enforcement and writes `<output>/degraded/<name>.report.json` files that are **not** in the `functional_evidence` shape (no `flow_id`/`head`/`status` keys), plus a `degraded/index.json` stating `evidence: false` and the failed step. The test wrapper never passes it, CI never runs it, and the evidence ingestion cannot be fed a degraded report because the runner's `check` and C10 read only `<output>/<flow_id>.json` and `<output>/index.json`; a test asserts that a forged `isolation: "degraded"` in a record's `summary` is not what protects ingestion (the protection is that no such record is ever written).
  - **Evidence eligibility.** A `functional_evidence` record exists only for a namespace-mode run: its `summary` carries `isolation: "namespace"`, and the runner refuses to write a record for any other mode (it asserts the mode at the write). The write-containment claim of R2 therefore applies to every record that exists; the degraded diagnostic claims nothing and produces no record.
  - **Developer without user namespaces:** the wrapper skips the scenario atoms with the reason and the unit tests still run; to see scenarios pass, enable the namespaces or use `--degraded-diagnostic` knowing what it exposes. The development guide says so and states the CI result of CP1's measurement.

  **D3b. Verification after the scenario.** (a) **Real checkout, content-sensitive**: the kit snapshots, before and after, `git rev-parse HEAD`, a digest of `git for-each-ref`, a digest of `git ls-files -s` (the index, entry by entry) and a sha256 over the *content* of every tracked and every untracked non-ignored file under the code paths of D4 (`controller/`, `tests/`, `tools/`, `pyproject.toml`, `setup.py`), taken with the sanitised Git environment above. A porcelain-status digest is not used: it records change categories, not contents, so a file already dirty and changed twice would not differ. Workflow bookkeeping (`docs/ai-workflow/`, `docs/ACTIVE_MILESTONE.md`, `.ai-review/`) is outside the digest because a concurrent lane writes it legitimately; the kit test shows a scenario writing there under the diagnostic mode is not detected and states that. (b) **Real user directories, diagnostic mode only** (`--degraded-diagnostic`; in the namespace they are unwritable and no other mode exists): the environment proof (each child records the values it resolved and a child that resolved a real directory fails the scenario) and the **token leak scan** (every scratch directory name embeds a unique token `scn-<flow>-<random>`; the kit walks the real directories and fails if an entry created or modified since the scenario started carries the token or scratch path in its name or, up to 1 MiB, content). The scan cannot see a token-free overwrite or deletion, which is why it is a diagnostic aid and never the proof, and why its runs write no evidence. A live Controller writing the real directories during the scenario cannot fail either check, because its writes carry no token and are outside the code-path digest; the kit tests keep the stand-in "real" directory with concurrent unrelated writes, and add a stand-in with a token-free overwrite and deletion to show what each check detects and what it does not.
- **D4. Evidence records match the protocol, are accepted by the real ingestion, and bind to a commit.** `tools/run_scenarios.py run [--output DIR] [names...]` writes `DIR/<flow_id>.json` with exactly the keys of `controller/protocol_schema.json`'s `functional_evidence` (`flow_id`, `status` `passed`/`failed`, `head`, `ran_at` in UTC, `summary` object, `log_digest` sha256 of the captured scenario log, `run_ref` always `null` (the runner is not run in CI, Q3), `reporter` `workflow-controller-scenarios/<source version>`), and one `index.json` (the catalogue, the order, each record's digest, the isolation mode and the runner's own exit status). **Flow ids are `scenario-<name>` and `scenario-kill-and-resume-<point>`**, matching `scripts/workflow_gate_policy.py`'s `FLOW_ID_RE` (`^[a-z0-9][a-z0-9_-]{0,63}$`); a dotted id is refused by `ingest_functional_evidence` with `evidence_malformed`, and the JSON sub-schema only checks that `flow_id` is a string, so the schema check alone would not have caught it. The registry refuses a non-matching id at registration. The runner validates every record against the sub-schema before writing it, and `tests/test_run_scenarios.py` additionally feeds **every record of every registered flow and variant** (the selftest scenarios included) through the real `workflow_gate_policy.ingest_functional_evidence` in a disposable Workflow repository, as `tests/test_gate_policy*.py` builds one, and asserts, as two separate facts (they are different identifiers, a 40-character commit and a 64-character review content id), that (i) the stored evidence's `head` equals the runner's own `head` (`git rev-parse HEAD` of the checkout it ran against, with the sanitised Git environment), and (ii) the stored identity equals `workflow_gate_policy.identity_at(...)` (the implementation-stage `review_content_id` the Workflow recomputes) evaluated independently by the test at that `head`. The disposable ingestion repository is created as a clone of the checkout at that `head`, so the source commit exists in it. It **refuses** (exit 2, nothing written) when any path that can change a scenario's outcome differs from `HEAD`: a tracked file modified or staged, or an untracked file, under `controller/`, `tests/`, `tools/`, `pyproject.toml` or `setup.py`, because a record for uncommitted code binds to no commit. Everything else is ignored, in particular the Workflow bookkeeping a review stage leaves uncommitted (`docs/ai-workflow/`, `docs/ACTIVE_MILESTONE.md`, `.ai-review/`) and the output directory; the boundary is documented and tested: every input a scenario executes comes from the verified commit or from fixtures committed under `tests/`, so dirty bookkeeping cannot change an outcome. `tests/test_run_scenarios.py` pins both sides: a modified `WORKFLOW_STATE.json` is accepted, a modified `controller/` or `tests/` file, and a new untracked file under `tools/`, are refused. A failed scenario still writes a `failed` record (a failure is evidence), and the exit status is 1.
- **D5. The catalogue: ten scenarios, one flow id each (`scenario-<name>`).**
  1. `full-lifecycle-to-merge`: a `"2.2"` target from trunk start through the scripted `/milestone-plan`, bind, plan approval commit, Draft PR, checkpoint steps with sync pushes, `MILESTONE_COMPLETE`, ready, the human merge on the fake forge, close-out and the next trunk start; asserts the exact ordered command sequence, the PR states and that no command was launched twice.
  2. `human-gates-stop-and-resume`: at the plan-approval, technical-approval and acceptance gates `run` stops with the gate exit code and launches no worker (invocation count 0), and after the user-only act is simulated `run` resumes at the right step.
  3. `worker-failure-fails-closed`: a worker that exits non-zero, one that times out and one whose effect does not verify each end the step with their documented exit code and record, never advance the phase and are not retried without a new decision.
  4. `kill-and-resume` (six variants, flow ids `scenario-kill-and-resume-<point>` with `<point>` one of `binding-before`, `binding-after`, `job-before`, `job-after`, `run-before`, `run-after`): the child Controller is `SIGKILL`ed just before and just after each of three durable writes of one lifecycle, and the recovery is then driven by the commands the Controller actually offers. **Persistence boundaries are measured, not assumed**: CP1's first act is an inventory test that traces one uninterrupted lifecycle and lists, per record kind, the primitive that publishes it (the milestone binding is published by `runtime.write_exclusive`, whose last step is `os.link` and not `os.replace`, `controller/runtime.py:203`; the job and run records by whatever the trace shows, `os.replace` or `rename_exclusive`), and the kill-point wrapper in the child bootstrap patches *that* primitive for that kind, so a variant cannot name a primitive the Controller does not call. The injection is scenario-side (the child bootstrap); `controller/` gains no hook. **The oracle is per variant, with a before-resume and an after-resume assertion**: `resume` only reconciles job records and never launches a worker (`controller/cli.py:1954`), so it cannot advance a lifecycle to scenario 1's end state; the end state is reached by the continuation `run`. Each variant therefore states (i) what is on disk after the kill (the record exists or not, the lock is free, the worker leftover is gone), (ii) what `resume` does (reconciles the dead job to its documented terminal status and exits with the documented code, or, at `binding-*` where no pending job exists, legitimately does nothing: exit 0, no record changed, which the variant asserts) and (iii) that the continuation `run` converges to scenario 1's normalised end state. **Mutation checks match the variant**: replacing `resume` by `true` must fail every variant whose before-resume state holds a non-terminal job record (the record stays non-terminal and the continuation `run` refuses with exit 20); for the `binding-*` variants where `resume` legitimately does nothing, the mutation replaces the continuation `run` and must fail on the end-state comparison, so no variant passes vacuously. **Pre-spawn and post-spawn variants are distinct classes, and each names its occurrence** (revision 6). `RunRecord.__init__` publishes the initial run record and `controller/job.py` publishes the initial job record (`planned`, `controller/job.py:6287`) before `_launch_job` spawns a worker, so a kill there leaves **no worker** and cannot wait for a worker's readiness file. CP1's inventory fixes, per variant, the exact write occurrence and the state the Controller is in; the plan commits to these classes: `binding-before`/`binding-after` (the first publication of the milestone binding) and `run-before`/`run-after` (the initial run-record publication) are **pre-spawn**: no worker exists, the oracle's worker-leftover assertion is "no tagged process was ever started", and the kill is synchronised by a **persistence-boundary handshake**, not a timer: the child bootstrap's kill-point wrapper writes `<scratch>/kill/<point>.reached` (before the primitive for `*-before`, after it returns for `*-after`) and blocks until killed, and the scenario `SIGKILL`s the child only after that file appears (10 s deadline, a named failure otherwise). `job-before`/`job-after` (`job-before` with the measured oracle stated below) target the **later job write that follows the spawn** (the publication that records the spawned worker, found by the inventory in `_launch_job`'s path): they are **post-spawn**, a fake worker exists, the children run with `FAKE_CLAUDE_ORPHAN_SECONDS=2` and the `FAKE_CLAUDE_ORPHAN_READY_FILE` handshake, and the kill-point wrapper's `.reached` marker is honoured only after the worker's watchdog readiness file exists (both conditions, 10 s deadline), then the leftover is awaited by polling `/proc` for the scenario's tagged processes with a 10 s deadline, never a fixed sleep and never the 300 s orphan default. If the inventory finds no job write after the spawn, CP1 stops and the plan is amended (the variant is not silently redefined). The oracle is stated per class: a pre-spawn variant asserts no worker process and no worker record; a post-spawn variant asserts the worker is gone after its deadline and that `resume` reconciles the job. **The `job-before` oracle (revision 8, measured, replacing the earlier "no pending job" wording):** the kill lands before the publication that records the spawned worker, so a worker exists but no record names it, and the killed Controller's stdin anchor still holds the lifecycle lock. (1) After the kill: a `LAUNCHED` job record, no worker left after its deadline, one anchor holding the lock. (2) The first `resume` exits 45 (`EXIT_WORKER_ACTIVE`) and changes nothing. (3) The scenario ends the anchor itself, the operator action the exit-45 text names. (4) `resume` then reconciles the job to `FINISHED`, exits 0 and frees the lock. (5) The continuation `run` reaches the bound step's end state. Its mutation check replaces `resume` by `true`: the job stays `LAUNCHED`, the oracle's step (2) and (4) assertions fail (`tests/test_scenarios_negative.py` pins `scenario-kill-and-resume-job-before` with `resume-true`). The committed scenario (`tests/scenarios/lifecycle.py`) already implements this oracle; CP6 settles the plan to match it. Every wait in the catalogue states its condition and deadline.
  5. `trunk-drift`: trunk advances mid-milestone; readiness gates, nothing is integrated, and a human merge from `PR_OPEN` converges to `CLOSED`.
  6. `squash-merge-and-release-classification`: scenario 1 under a squash policy, and the `tools/release.py` classification of the resulting trunk history (no release for `test:`/`docs:`, a minor for `feat:`).
  7. `notifications-never-steer`: the same lifecycle with the fake SignalHub up, answering 500, slow and down produces identical step outcomes, exit codes and normalised records (D9), and the up case receives the documented ordered events with unique `Idempotency-Key`s and no secret in any output or log.
  8. `usage-pause-and-resume` (C8's **admission** pause only): the shared usage record is seeded through the path the existing usage tests use (CP4's first act pins it; the clock and the pause sleep are injected through `job.usage_now` and `cli._usage_sleep`, so nothing waits in real time) so that a worker would exceed the repository cap in a timed window; `run` then exits 17 with the invocation count 0 and a message naming the resume time, a run-cap variant exits 17 with no timed wait, and, after the injected clock passes the reset, a second **`run`** (not `resume`, which never launches a worker) launches the worker and completes the segment. **Not claimed**: a limit reached *mid-job*. Today such a job ends `FAILED` with `result_is_error` and exit 30, and the distinct classification and the reset recovery are C8b's (`docs/ROADMAP.md`, 11.6.1); the two 2026-09-24 streams are therefore not used here, and the development guide says the scenario does not cover that path until C8b adds it.

- **D6. No duplicated assertions with the unit suite; atoms and timing are measured.** A scenario asserts the observable outcome of a path (exit codes, phases, files, commits, requests received). It does not re-test a function's branches; those stay where they are. The whole catalogue must run in at most 120 s serial on the CI runner (a budget the runner prints and `tests/test_scenarios.py` does not enforce, to avoid a timing flake; the runner's `--check-budget` does, for local use). CP2, CP3 and CP4 each add the measured seconds of the variants they introduce to `tools/test_timings.json` (the runner's printed timings do not update CI estimates), and CP5 reports the planner's projected per-shard estimates before and after, **including the complete added cost**: the catalogue, the two complete determinism runs of D9, the mutation checks and the kit contract tests, each timed, and the largest resulting planner atom (the estimates above cover the catalogue alone): four shards remain the ceiling (the six-runner budget of the CI peak change), and the catalogue's added wall time is reported against the roughly 679 s per shard of today's plan rather than assumed.
- **D7. The runner never launches a model or touches the network; what is enforced, and what is only detected.** The enforcement is the sandbox and the built environment of D3, which every descendant inherits: no network beyond loopback (network namespace), no write to a real location (read-only mounts a capability-free process cannot undo), no real `claude`/`gh`/`workflow-manager` by name (`PATH`). Stray processes are bounded by D8, not by a namespace. A scenario run with a real `claude` first on the invoker's `PATH` still runs the fake, because the invoker's `PATH` is not inherited. On top of that sits a **detector**, not a guarantee: a `sys.addaudithook` (the technique `tests/test_settings.py:1229` uses) on `subprocess.Popen`, `os.exec*`, `os.posix_spawn` and `os.system`, which fails the scenario when an executable whose resolved path is outside the scratch `bin/` is launched. An audit hook sees only the interpreter that installed it: it does not see what an allowed shell or a git hook launches internally, it is absent from interpreters started with `-E` (the existing fixtures do), and the Controller's unpinned re-exec replaces `PYTHONPATH` with its snapshot directory (`controller/cli.py:174`), dropping the bootstrap's `sitecustomize.py`. The plan therefore claims the hook only for the in-process Controller and for child Controllers started through the kit's bootstrap (`bounded_controller_argv` plus a scratch `PYTHONPATH` directory holding only `sitecustomize.py`, which also installs the kill-point patch and logs the environment the child resolved), and scenarios that need the hook past a re-exec pin the source (an installed-style identity) so no re-exec occurs. **CP1 verifies the enforcement with safe stand-ins, not with the hook**: a TCP listener the test opens *outside* the sandbox, and a stand-in "real" directory and "real" executable, are attacked from inside through each path (a shell child, a git hook in a stand-in repository whose `core.hooksPath` the test sets, a `python -E` child, a child Controller before and after the re-exec): every connection fails, the listener accepts none, every write to the stand-in fails `EROFS`, `umount` and `remount,rw` of the stand-in fail, and the stand-in executable is not found by name. R1's wording and the development guide say exactly this split.
- **D8. Leftovers are bounded, identically in both modes.** Scenarios use the existing lifetime machinery from C12a (`tests/process_fixtures.py`: `popen_bounded`, `bounded_controller_argv`, the fake's orphan watchdog) so a killed scenario run leaves nothing past `LEFTOVER_LIFETIME_SECONDS`, and `tests/test_scenarios.py` checks that no process tagged with a scenario's scratch directory remains after the scenario returns. Reaping of a killed Controller's worker is done by the host's init, as in every other run, which is what scenario 4's recovery oracle assumes. The C12a source-inventory completeness test (`tests/test_fake_claude_contract.py:1534`) scans only `tests/*.py` and keys sources by `path.name`; CP1 extends it to `tests/**/*.py` keyed by the path relative to `tests/`, so `tests/scenarios/__init__.py` does not collide with `tests/__init__.py` and a process start introduced under `tests/scenarios/` is inventoried.
- **D9. Evidence is reproducible, not signed.** Two runs against the same `HEAD` in the same isolation mode yield the same `summary`, and, because the sandbox has no PID namespace and no `/proc` change, a namespace run and a diagnostic-mode run of a selftest flow yield the same `summary` apart from the `isolation` label (CP1 kit test, selftest scenarios only; real scenarios are never run in the diagnostic mode by the suite, and no record is made in it) (observations are normalised, and the digest of a job, run or binding record is computed over the **normalised record**, never over the raw one). Normalisation drops or replaces: scratch paths (`<scratch>`), every timestamp field (`*_at`, `ts`, `started`, `ended`, `reset_at`), pids, owner tokens and random identifiers, and replaces commit SHAs with `<sha>` positions; records whose other fields are unstable are summarised by selected fields (phase, exit status, step name, counts) instead of a digest. The kit pins `GIT_AUTHOR_NAME/EMAIL/DATE` and `GIT_COMMITTER_NAME/EMAIL/DATE` and a fixed `core.autocrlf=false`/`init.defaultBranch` so any commit identity that does appear is stable. `log_digest` and `ran_at` differ between runs. A test pins this on a scenario that observes a job record digest and a commit subject, and a negative case adds an unnormalised timestamp and sees the determinism test fail. The records carry no provenance guarantee beyond the workflow's own: C10's policy decides whether the reporter and the commit are trusted, as the Workflow's gate policy already says for orchestrator-reported evidence. **Determinism is tested on the whole catalogue**: `tests/test_run_scenarios.py` runs the complete catalogue twice against one `HEAD` (in CP5, after every scenario exists; in CP2 with the selftest scenarios) and compares every normalised summary, not one selftest.

No "Open decision" row in `docs/TECHNICAL_DECISIONS.md` is touched: that document describes the Android application's prototype, not the Controller (the file is absent in this repository).

## Risks

- **A scenario that duplicates a unit test and doubles the suite time.** D6 caps the catalogue at 120 s serial and forbids branch-level assertions; the runner prints the budget.
- **The real-repository snapshot flakes when another process writes in the checkout** (a concurrent lane, an editor, a second test shard). The snapshot is limited to `HEAD`, refs, the index and the contents of the code paths of D4, and ignores Workflow bookkeeping and `.ai-review/`. A differing snapshot reports which of them moved. If sharded CI runs race, the check runs on a copy (`git worktree` is not used: a plain `git clone --shared` of the checkout).
- **Scenario observations leak scratch paths or pids and break determinism.** D9 normalises them; the determinism test fails loudly on a new leak.
- **Scripted fake workers drift from the real `claude`.** The fake already has a contract suite (`tests/test_fake_claude_contract.py`); scenario 8 drives the admission check, which reads no worker stream, so the usage path does not depend on the fake's imagination.
- **The sandbox is unavailable on a runner** (unprivileged user namespaces restricted, or the capability drop failing). Measured on `ubuntu-latest` (AppArmor restriction): CP6 lifts it in the `tests` job. A future image that restricts namespaces some other way is still a red build, by design. D3 fails closed (the suite skips locally and fails under `CI`; the runner writes nothing; the diagnostic override makes no evidence), names the failed step, and CP1 measures the probe on the CI image before any scenario relies on it and stops if it fails there, and the audit hook, which cannot follow a re-exec or an `-E` interpreter, is a detector only (D7).
- **Evidence trusted too much.** A record proves that a scripted path ran on a commit, not that the real worker behaves; the live-worker test stays opt-in and C10's policy decides what to require. The documentation says so.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10).
