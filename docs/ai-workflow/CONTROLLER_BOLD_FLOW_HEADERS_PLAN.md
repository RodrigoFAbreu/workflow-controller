## Goal

Close [#288](https://github.com/RodrigoFAbreu/workflow-controller/issues/288). In `functional_review.read_flows`, `**Flow 1: title.**` starts with the word `Flow`, so `_BOLD_RE` (`**K. Title.**`, a label then a marker) reads nothing; the heading shape does read `### Flow 1: title`. Alone, a checklist of such lines is refused (no flow found). Next to one flow another shape reads (`### Flow 10 (user, outside the sandbox)`), the other nine lines are dropped without a word and a round can pass with nine flows never run. FL2 (#271) cannot see them: it accounts for items *another shape recognised*, and no shape recognised these. Two parts, either alone is incomplete: read the spelling, and refuse the class of bold `Flow` line that no shape reads.

## Decisions

Each decision states one principle.

- **D1. A bold flow header may begin with the word `Flow`.** `**Flow K: Title.**`, `**Flow K. Title.**`, `**Flow K) Title.**`, `**Flow K - Title.**` (a hyphen, en dash or em dash set off by spaces) and `**Flow K**` (the label closes the bold) start a flow exactly as `**K. Title.**` does, with `K` under the existing label rule (`LABEL_RULE`; a digit-bearing token that is not a label is already refused as unrecognised by the bold shape, so `**Flow 123: x**` is refused, not dropped). The word is `Flow` in any case followed by blanks, after an optional qualifier (`**Optional, Flow 2: x**`, `**Then, Flow 2. x**`), and it is one shared piece of the bold spelling: `_BOLD_RE`, `_BOLD_LABELLED_RE` and `_SECTION_END_RE` (the line that ends the flow before it) all get it, so a line that starts a flow also ends the one above it and a line that ended a flow never starts none. The dash and closing-`**` markers are accepted only when the `Flow` word is present, so `**A - x**` and every other spelling read today read the same. A heading flow (`### Flow K`) is untouched.
- **D2. A bold `Flow` line no shape reads is refused unless a flow holds it.** A line outside a code fence that begins `**`, optional blanks and the word `Flow` (any case, a word boundary after it) and that D1's spelling does not read (`**Flow: title**`, `**Flow 1 title**`, `**Flow one.**`) is a flow-looking item. It is accounted for by the same rule as FL2's items: it must start inside a flow a shape read, hold a deciding row of a table (a row the deciding table shape reads shares its span), or lie in a non-flow region (`_nonflow_regions`), or the checklist is refused with `ChecklistUnrecognised`, naming the first eight lines by file line and the fix (use `**Flow K: Title.**`, a heading, or put the line inside a flow). It is never itself a deciding shape. Its span is a bold flow's span (`_paragraph_found`): from the line to the next heading, labelled bold line or other unread bold `Flow` line, a blank line not ending it, so a `**Flow: cases**` line followed by a blank line and a table whose row `A` the reader takes (it reads `['A']` at the base) holds that row and the checklist keeps reading `['A']`; a one-line span would make the "holds a deciding row" clause dead and refuse a checklist that reads today. Ending the span at the next unread bold `Flow` line (round 2, I2) means only the line directly above a table holds its rows: `**Flow 1 one**`, prose, `**Flow 2 two**`, prose and a table with row `A` is refused for the first line, not read as `['A']` with both flows unrun; with the table first, a `**Flow: y**` line below it is not held by it either. The accounting applies on every exit of `_flows_of_lines`, the table-only exit included: a checklist of widened-label rows only (`| F1 | a | b |`) next to `**Flow: y**` or `**Flow 123: y**` is refused, not read as `['F1']`. When no shape finds a flow, the existing "none of the four shapes finds a flow" refusal names those lines too. A prose line such as `**Flow chart**` inside a flow's own text is held by that flow and keeps reading as before. A region a bold line opens (`**Setup.**`) ends, in addition to what ends it today (`_nonflow_regions`, `controller/functional_review.py:503`-`:508`), at the next bold `Flow` line, read or unread (round 2, I1): otherwise an unread `**Flow: the login**` after `**Setup.**` stays inside the region and is accounted for, so a checklist refused at the base would read `['2']` with the login flow never run. A heading-opened region (`### Setup`) is unchanged, and `### Setup` followed by `**Flow: x**` reads as before.
- **D3. Mixed spellings keep FL2's answer.** The issue's case after D1 is nine `**Flow K: ...**` lines and `### Flow 10 ...`: the bold shape decides nine flows and the heading flow neither starts inside one of them nor holds a table row, so FL2's existing refusal names `10` (heading) and says to give the section one shape. This is not a new rule; it replaces a silent skip of nine flows by a refusal that names the tenth, and the author fixes the checklist. The plan does not make the reader merge two shapes.
- **D4. History reads as before, and the measurement is a test.** The new spelling changes a line only if the word `Flow` follows `**` directly or after one qualifier (D1), and D2 adds a refusal only for a line that begins `**` and `Flow`. A case-insensitive search over all checked-in markdown (`git grep -niE '^\*\*[ \t]*(([a-z]+),[ \t]*)?Flow\b' -- '*.md'`) at the base finds four lines and no qualified one, all in `docs/milestones/completed/workflow-controller-protocol-warn-status.md`, whose checklist heading is not the exact section title (the reader already refuses it as a missing section), so no checked-in checklist that reads today changes. A test pins the claim on the files that never change: `docs/milestones/completed/**` and `tests/fixtures/**`. For each one that has an exact checklist section and no `**Flow` line, it asserts that the file reads or refuses exactly as the base does, against a list of labels frozen per file when the test is written. `docs/ACTIVE_MILESTONE.md` and the rest of `docs/milestones/**` are not compared, because they are rewritten for every milestone (the checklist there is replaced before this item's acceptance). A file not on the list is not compared; a listed file that is gone (a retention item, CL1) is skipped, not failed. This pins the claim D4 makes instead of leaving it to the review.
- **D5. The operator pages say what is read and refused.** `docs/guide/automation.md` (the recogniser paragraphs near the qualifier text) gains the `Flow` spelling and the refusal; `docs/common-problems.md` gains the refusal's message, cause and remedy. No new setting.

## Out of scope

Merging two shapes in one checklist, reading `Flow` after other words (`**Optional extra Flow 1.**` stays in the flow above, as before; a qualified near-miss of D1's spelling such as `**Optional, Flow 9 y**` or `**Optional Flow: y**` is dropped as before, because D2's pattern begins `**` and `Flow`), a `**Flow K**` line with trailing text on the same line, and any change to the heading, table or numbered shapes. #288's wider guard for other bold label words (`**Step 1: x**` next to a recognised flow, and `**Flow1: x**`, which the word boundary excludes) is not done here: the roadmap row asks for the word `Flow` only. It is recorded, with the qualified near-miss, as a follow-up issue filed at acceptance (Optional finding O1, rounds 1 and 2).
