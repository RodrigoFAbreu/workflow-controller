## Goal

A pull request that changes only documentation runs the same jobs as a code pull request: plan, six test shards of about 20 CPU-minutes each, package, `tests-result`. The three documentation pull requests profiled in #317 (313, 314, 316) took 24.9, 25.6 and 25.8 minutes. About a third of the recent pull requests touch no code (19 of the last 60 first-parent commits of `main`, D1; the item page's "about half" was an estimate and CP3 rewords it). This item skips the plan and the six shards for a pull request whose every changed path is documentation, keeps the required check `tests-result` green and honest, and runs the documentation checks that stay meaningful on every pull request. Expected saving: about 24 minutes on a documentation-only pull request, nothing on a code pull request. Main still runs everything.

One mechanism: **change detection at job level.** Nothing else changes: not the shards, the timings or the atoms (CI1b), not parallel workers (CI1c), not the conformance workflow.

## Decisions

Each decision states one principle.

- **D1. A pull request is documentation-only when every changed path is on a fixed list of paths that no test reads as input, and anything else, or any doubt, runs everything.** The classifier is a pure function over path strings in a new stdlib-only `tools/ci_changes.py`. The documentation set is: everything under `docs/items/` and `docs/releases/`; the top-level pages `docs/*.md` except `docs/ACTIVE_MILESTONE.md` and `docs/roadmap-archive.md`; and `docs/backlog.yaml`. It is written as data (prefixes and a pattern), each entry with its reason. Everything else is code, including what tests outside the gate read at the base commit: `docs/guide/` (`tests/test_plan_document_consistency.py` parses every guide's invocation lines with the live parser, `tests/test_cli.py` reads `docs/guide/commands.md`, `tests/test_functional_sandbox.py` reads `docs/guide/automation.md`), `docs/adr/` (`tests/test_plan_document_consistency.py` reads ADRs 0001 and 0002), `docs/roadmap-archive.md` (`tests/test_functional_sandbox.py` pins exact phrases), and also `docs/ai-workflow/` (workflow state, plans, registries: tests and the Workflow scripts parse them), `docs/milestones/`, `docs/ACTIVE_MILESTONE.md`, `tools/`, `controller/`, `tests/`, `scripts/`, `.github/`, `.claude/`, `README.md`, `pyproject.toml` and every path not named. A changed path that is renamed counts under both names (`--no-renames`). An empty diff, an unreadable diff, a failed `git` call or an event that is not a pull request is `code`, never `docs`. Measured at the base commit: replaying this rule over the last 60 first-parent commits of `main` classifies 19 as documentation-only, the same 19 as the earlier wider set (release notes, item pages, backlog edits), so removing the guide, ADR and archive paths costs none of the saving.
- **D2. The set is kept honest by a test, and it shrinks rather than the gate growing.** A guard test finds the readers of the set by an AST scan, not a text search, over every `.py` file of `tests/` (not `tests/workflow_releases/`: those are frozen copies of released trees, run by no test of this repository), `scripts/` (which includes `scripts/*_test.py`), `tools/` and `controller/`. One rule decides what is a read:
  - **A path position.** Only a string at a *path position* is a path: an operand of a `/` chain, any argument of `Path(...)` or `os.path.join(...)` (so `Path(ROOT, "docs/run.md")` and `os.path.join(ROOT, "docs", "run.md")` are chains of those segments), a `.joinpath(...)` call (its receiver is the first segment, its arguments the rest, so `ROOT.joinpath("docs", "run.md")` folds to `docs/run.md`), the first argument of `open(...)`, or the receiver of a `.glob`/`.rglob` call (whose pattern is appended). A whole literal anywhere else (a dictionary key, a table of declared paths, an argument to a function that is not one of these, a message) is a mention, not a read, and is never flagged: `scripts/workflow_fingerprint.py` and `scripts/workflow_state.py` declare `docs/ROADMAP.md` and `docs/PROJECT_BRIEF.md` that way. The same literal inside `Path(...)` is a path.
  - **Names are resolved.** A module-level or function-level name bound once to a string constant or to a folded chain is replaced by its value, transitively, so `BACKLOG_FILE = "docs/backlog.yaml"` then `REPO_ROOT / BACKLOG_FILE` folds to `docs/backlog.yaml` (`tests/test_backlog.py:28`, `:276`), and `GUIDE_DIR = REPO_ROOT / "docs" / "guide"` then `GUIDE_DIR.glob("*.md")` folds to `docs/guide/*.md` (`tests/test_plan_document_consistency.py:94`, `:544`). A name bound more than once, or from anything else, is unresolved.
  - **Folding.** Each chain of constant segments folds to one relative path, so `REPO_ROOT / "docs" / "adr" / "0001-x.md"` is `docs/adr/0001-x.md`. A folded path that equals, or lies inside, a member of the set (or matches its pattern) is a candidate; a bare parent such as `docs` is not one.
  - **Read or fixture, decided by a table, not by a naming heuristic.** A candidate is a *fixture* only when its chain root, written as an expression (`root`, `repo.root`, `self.root`), is on the **fixture table** under the candidate's own module. The table is data in `tools/ci_changes.py`: one entry per module and root expression (not per site or per path), each with its reason ("a temporary repository the module builds itself") and each checked for staleness. Every other candidate, whatever its root (a repository-root name bound from `Path(__file__)` and its `parent`/`parents`, a parameter, an attribute, a name returned by a helper, a root the scan cannot classify), is a *read of the repository*, so the guard fails closed: a reader through an unlisted parameter or attribute root is flagged. **Refusal of a fixture entry, defined by what it protects.** A fixture entry says one root expression is temporary, so the guard refuses an entry (module and root expression *E*) only when a **repository-root value can reach *E*** in that module. A *repository-root value* is a `Path(__file__)` chain (with optional `.resolve()`/`.absolute()`, then `.parent` steps or a `.parents[n]` index, then any constant segments) whose climb ends at the repository root or above it: counted from the module's own directory, `.parent` once from a module in `scripts/` or `tests/` is that directory and is **not** a root value, a second `.parent` (or `parents[1]`) is the root, and `parents[2]` is above it. A chain that ends at or below a directory under the root (`scripts/`, `tests/`) is a *directory name*, never a root value, so a listed module may bind it freely. A root value *reaches* *E* in exactly four ways: (a) *E* is a name assigned from a root value, or from a call to a local helper whose `return` is a root value (`root = _repo_root()`); (b) *E* is an attribute (`self.root`) assigned from either; (c) a root value (or a name bound from one) is passed as an argument to a function of the module whose parameter is *E*; (d) *E* is assigned from another name that one of these reaches, transitively. A candidate whose chain root is itself a root value, a root-bound name or a call to such a helper (`_repo_root() / "docs" / "run.md"`) is not a fixture whatever the table says: it is a read.
  - **Allowed readers.** A read must be in one of three places, each entry with its reason: the two docs-gate test modules of D3 (`tests.test_docs`, `tests.test_backlog`); the *gate tools*, which the documentation gate itself runs, `tools/check_docs.py` (run by the `docs` job; it reads the page lists of `USER_PAGES`/`COMMAND_PAGES`/`LINK_GLOBS` through `root / rel`) and `scripts/workflow_backlog.py` (run through `tests.test_backlog`); and a short list of mentions that do not read the file, each with its reason. A path read by any other module leaves the documentation set. The gate of D3 never takes a third test module.
  - **Stale, defined for each kind of entry, and a test refuses a stale entry of each kind.** A *gate module* entry is stale when its test module file no longer exists; a *gate tool* entry is stale when its file no longer exists (the tools have no candidate under this scan, see the known limit, so "no read found" is not the test for them and they are not refused for it); a *mention* entry (module and folded path) is stale when the scan no longer finds that candidate in that module; a *fixture* entry (module and root expression) is stale when the scan finds no candidate with that root in that module. A stale entry fails the guard and is removed in the same change.
  - **Known limit.** A path whose segment is not a constant (`root / rel` with `rel` from a loop) does not fold and is not seen; that is why the gate tools are named as a status rather than discovered, and why D1's independent evidence matters. A fixture entry covers every use of its root expression in the module, which is why the guard refuses an entry that a repository-root value reaches. The scan follows assignment, a local helper's `return` and a call argument inside one module; a root value that reaches *E* through another module's function, a container or `setattr` is not seen, and D1's independent evidence (the removal of the whole set in a clone) is what backs that.
  The expected result of this rule at the base commit, stated so that review can check it and measured by a throwaway replay of the same scan (the round-3 review's replay: 48 candidate sites in 8 modules): the reads are the five sites in `tests/test_backlog.py` (`docs/backlog.yaml` through the constant, `docs/ROADMAP.md`), an allowed docs-gate module; the other 43 sites (22 module-and-path pairs) are fixtures in seven modules, each root on the fixture table: `scripts/workflow_state_completion_obligations_test.py` (29 sites, 14 paths), `scripts/workflow_acceptance_matrix_test.py` (3), `scripts/workflow_fingerprint_test.py` (4), `scripts/workflow_gate_policy_test.py` (1), `scripts/workflow_test_harness.py` (1), `tests/test_evidence.py` (4) and `tests/test_identity.py` (1); their roots are `root`, `repo.root`, `d.root`, `ev.root`, `self.scratch.root`, `self.root` and `checkout`, so the table is expected to hold about one entry per module and root expression, roughly ten to twelve entries, and the first run states the exact table. By the refusal rule above, **all seven modules satisfy it and none of their entries is refused** (checked against the base commit): five of them bind a `Path(__file__)` name, and none of those names is a table root or is passed to one. `scripts/workflow_acceptance_matrix_test.py:9364` binds `templates` (a root value extended by constants, not a table root), `scripts/workflow_fingerprint_test.py:2412`, `:3412` and `:4393` bind `script`/`commands` (one is a root value extended by `.claude/commands`, none is a table root), `scripts/workflow_gate_policy_test.py:35` binds `SCRIPTS` and `scripts/workflow_test_harness.py:443` binds `_SCRIPTS_DIR` (both a *directory name*: one `.parent` from `scripts/`), and `scripts/workflow_state_completion_obligations_test.py:924` binds `real_scripts_dir` (a directory name). `tests/test_evidence.py` and `tests/test_identity.py` use `Path(__file__)` only in `sys.path.insert`. In `scripts/workflow_state_completion_obligations_test.py`, `_repo_root()` (line 53, `return Path(__file__).resolve().parent.parent`) is a helper returning a root value: it is a **read root and is not on the fixture table**; its uses (`:469`, `:3522`, `:3579`, `:3588`) read `docs/ai-workflow/` paths outside the set and are never assigned to a table root or passed to one, and if a later change wrote `root = _repo_root()` for a listed root `root`, the guard would refuse that entry. `tools/check_docs.py` and `scripts/workflow_backlog.py` are the gate tools; the declaration tables above are not reads. So the named list of mentions is expected to be empty or nearly so, well under ten entries. **Limits:** the ten-entry limit applies to the list of mentions only; the fixture table is counted separately, one entry per module and root expression, and is bounded by the fixture sites it explains, never by that limit. The independent check is the round-2 review's removal of all 162 set files in a disposable clone of the base commit: only `tests.test_docs` and `tests.test_backlog` fail (19 of 20 failures), and the twentieth is a process-timing test that reads no documentation. If the first run of the guard disagrees with the expected result (a candidate whose fixture entry a repository-root value reaches counts as a read), the checkpoint's report states what the scan found and the set shrinks; if the list of mentions would need more than ten entries, the checkpoint stops and the plan is amended: there is no weaker substitute guard.
- **D3. What skipping the shards must not lose is run on every pull request, in a job of its own: the documentation gate.** A `docs` job, parallel to `changes` and not needed by the shards, runs `python3 tools/check_docs.py` and `python3 -m unittest tests.test_docs tests.test_backlog` after the editable install: the offline link, anchor and command check, the generated harness table, and the backlog and roadmap checks that read the real files. It runs for every event, so a code pull request also sees a documentation break early, and a failing gate fails `tests-result` in every mode. Its checkout is shallow (history is only for `changes`). It is separate from `changes` so that a documentation failure never hides the shards' feedback on a code pull request.
- **D4. Detection is a job, never a workflow-level filter.** `validate.yml` gains a `changes` job: checkout with full history, then a step with id `detect` running `python3 tools/ci_changes.py detect`, and the job declares `outputs: {code: ${{ steps.detect.outputs.code }}}` (without that mapping `needs.changes.outputs.code` is empty and `require` fails every pull request). `detect` reads the event name from the environment and writes `code=true` or `code=false` to `$GITHUB_OUTPUT`. On a `pull_request` run `HEAD` is the merge ref, so the diff is `git diff --name-only --no-renames HEAD^1 HEAD`: exactly what the merge introduces, independent of `pull_request.base.sha` (which is not read, so a stale base cannot matter). A `HEAD` that is not a merge commit (no second parent) is `code`. For anything but a `pull_request` event (the push to `main`, a manual dispatch) it writes `code=true` without reading git, so main runs everything. `plan` has `needs: ["changes"]` and `tests` has `needs: ["changes", "plan"]` (the `needs` context holds direct dependencies only, so `tests` must list `changes` to read its output); both carry `if:` on `needs.changes.outputs.code == 'true'` (the existing `tests-from-run` condition stays on `tests` and is combined with it). A workflow-level `paths-ignore` is not used: the required check is `tests-result`, and a skipped workflow would leave it pending forever.
- **D5. `tests-result` still succeeds only when something proves the change safe, and fails closed otherwise.** A new step, `python3 tools/ci_changes.py require --changes <result> --docs <result> --code <output>`, runs in every mode and exits non-zero unless the `changes` job succeeded, the `docs` job succeeded and `code` is exactly `true` or `false`; an empty or unknown `code` (the `changes` job failed or was cancelled) fails. It is the **last** step of `tests-result` with `if: always()`: a step with an `if:` and no status function keeps the implicit `success()`, so a `require` placed first would skip the downloads and the aggregate when the gate fails, hiding the shard report on a code pull request (D3). Placed last, every other step skips or runs by its own condition exactly as before, and a failing gate still fails the job after the report. `record the tree` and the timings upload keep `always()` combined with the code condition (`always() && needs.changes.outputs.code == 'true'`), because `tests/test_ci_workflows.py` and re-run behaviour depend on `always()`. When `code` is `true` the existing steps run exactly as before (their `if:` gains the condition) and the aggregate still proves every planned test ran exactly once. When `code` is `false` the download, aggregate, verify, record-the-tree and timings upload steps are skipped, so the job's success means: changes succeeded, the gate passed, and every changed path is documentation. Nothing is uploaded in that mode, so a later `CI_MAIN_REUSE` search finds no results of this run to reuse (`tools/ci_reuse.py` fails closed on a missing artifact) and main runs the shards, as the item page requires.
- **D6. The `package` job and the conformance workflow are untouched.** `package` builds and checks the wheel in a few minutes and stays unconditional; it is not on the critical path of the saving. `workflow-conformance.yml` runs in parallel and is out of scope.
- **D7. The workflow files are generated.** Every workflow change goes through `tools/ci_workflows.py` and `python3 tools/ci_workflows.py --write`; `--check` and `tests.test_ci_workflows` assert the committed bytes equal the render. `tools/ci_changes.py` is a script the workflow runs, not a new emitter, and it is tested like `tools/ci_reuse.py`.
- **D8. This pull request is not the proof, and the milestone says so.** The change touches `tools/` and `.github/`, so its own CI runs everything. The unit tests prove the classifier and the generated conditions; the live proof is the first documentation-only pull request after the merge, whose `tests-result` duration is read through the public API as in #317 and recorded on the item page. If that duration is not well under the 24.9-25.8 minutes of #317, the item page states the shortfall.
- **D9. Documentation changes with the behaviour, in place.** `docs/guide/ci-and-releases.md` describes the two new jobs, the documentation set (and that the guides, ADRs and the archive are code because tests read them), the fail-closed rules and the skipped mode of `tests-result`; `docs/guide/development.md` says how to run the documentation gate locally and that a new reader of a documented path moves it out of the set. `README.md` names the jobs of `validate.yml` and is updated with them; `docs/items/workflow-controller-ci1a.md` records the replay measurement. The closing roadmap and `docs/ACTIVE_MILESTONE.md` records go in the acceptance, as for every milestone.
- **D10. Every deliverable of this item is protected at the implementation stage, so the approval binds the bytes GitHub runs.** `docs/ai-workflow/registry/workflow-controller-ci1a-artifacts.json` lists as `implementation_stage.protected_paths` the three deliverables that the broad `.github/`, `README.md` and `docs/items/` classes would otherwise leave `excluded`: `.github/workflows/validate.yml` (CP2), `README.md` (CP2) and `docs/items/workflow-controller-ci1a.md` (CP3); the exact `README.md` exclusion is removed so no path is in both lists. The implementation classifier checks exact protected paths first (`classify_path_implementation_stage` in `scripts/workflow_fingerprint.py`), so the three paths classify `protected` while the rest of those classes, including `.github/workflows/ci.yml` and `main.yml`, which this item does not change, stay excluded. The other deliverables are already protected by the prefixes `tools/`, `tests/` and `docs/guide/`. This is the only part of the declaration this revision changes.

## Out of scope

Changing the shards, the timings or the test atoms (CI1b); parallel workers or test selection by changed paths for code pull requests (CI1c); the conformance workflow; skipping `package`; any change to what `main.yml` does after validation.
