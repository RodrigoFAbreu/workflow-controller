## Goal

`tools/ci_changes.py` skips the test shards for a change that touches only the **documentation set** (`DOCS_PREFIXES`, `DOCS_TOP_LEVEL`, `DOCS_FILES`). That skip is safe only if no test outside the documentation gate reads a path of the set. Today `tests/test_ci_changes.py` argues it from source text: about 1,200 lines of AST scanning (`ModuleScan`, `Chain`, `touches_set`, the reach of a repository-root value, four allow-lists in `tools/ci_changes.py`: `GATE_MODULES`, `GATE_TOOLS`, `MENTIONS`, `FIXTURES`). It is inferred, hard to review, and every new reader style needs a scanner change ([#322](https://github.com/RodrigoFAbreu/workflow-controller/issues/322), also [#317](https://github.com/RodrigoFAbreu/workflow-controller/issues/317)).

One mechanism replaces it: **the shards run with the documentation set absent.** A shard that passes without those files proves, by running, that no test it ran needs them, so a change confined to them cannot change a shard's result. It costs no runner: it is a step inside the shard jobs that already run.

## What exists

- **The set and the gate.** `tools/ci_changes.py` holds `is_documentation`; the two modules that legitimately read the set (`tests.test_docs`, `tests.test_backlog`) and the tool they run (`tools/check_docs.py`) are the documentation gate. `tools/ci_workflows.py` runs the gate in `docs-tests` (`DOCS_TEST_MODULES`, `DOCS_TEST_PATTERN = "test_[bd][ao]c*.py"`) and `docs`, on every event.
- **The shards.** `tests.yml`'s `tests` job checks out, installs, runs `python3 tools/run_tests.py exec-shard ...`. The plan (`plan --profile ci --ci-placement`) currently **also** contains `tests.test_docs` and `tests.test_backlog` (checked: both appear in the plan), so the gate runs twice.
- **`CI_PLACEMENT`** in `tools/test_shards.py` moves modules out of the shards (`main`, `package`, `excluded`), each with a reason a test checks.
- **The static guard.** `tests/test_ci_changes.py`, from the "The guard (D2): the scan" section to the end, and the four tables above.

## Decisions

- **D1. The check is the shards run blind.** `python3 tools/ci_changes.py hide` lists the tracked files (`git ls-files -z`) that `is_documentation` accepts, deletes them from the working tree and marks each `git update-index --skip-worktree`, so `git status` stays clean and a test that inspects the checkout sees the same tree except for the missing files. It refuses to run outside a Git work tree, never deletes a path that is not in the set, and prints the count. A `--dry-run` lists without touching. The `tests` job runs it as a step between the install and `exec-shard`. The runner checkout is disposable, so there is no restore step; a local run uses a scratch clone (the page says so). Only the shards run blind: the `plan` job stays sighted, so `exec-shard --expect-digest` compares a plan discovered with the set present against an inventory discovered without it. They agree today because no test is generated from a set path, and a mismatch fails loudly; a future generated test is a D3 reader, not a mysterious digest failure.
- **D2. The documentation gate leaves the shards.** `tests.test_docs` and `tests.test_backlog` read the set by design, so they cannot run blind. `CI_PLACEMENT` places both as `excluded` with the reason "run by `docs-tests` on the real checkout (`DOCS_TEST_MODULES`)"; a test ties the two names to `DOCS_TEST_MODULES` and to what `DOCS_TEST_PATTERN` selects, so the gate cannot lose a module. This also removes the duplicate run. The planner's committed timings keep their entries; the staleness ratchet is checked in CP2 and the timings file is not regenerated by hand.
- **D3. A reader the blind run finds shrinks the set.** If a shard fails blind because a test reads a path of the set, the path leaves the set (it becomes code, never the test excluded). How depends on where the path is classified: `is_documentation` consults only `DOCS_PREFIXES`, `DOCS_FILES` and `DOCS_TOP_LEVEL` (less `DOCS_TOP_LEVEL_EXCEPTIONS`), never `NOT_DOCUMENTATION`, which is a record of directories already outside the set. A path under `DOCS_PREFIXES` (`docs/items/`, `docs/releases/`) or a `DOCS_FILES` entry therefore leaves by changing that classification (removing or narrowing the entry), and a top-level page leaves by a `DOCS_TOP_LEVEL_EXCEPTIONS` entry with its reader; adding a `NOT_DOCUMENTATION` line alone does not move anything. This repository's test policy (`CLAUDE.md`, "Running tests") forbids a full-suite run at a checkpoint, so CP2 does not run every planned shard. CP2 runs only its own named test modules blind in a scratch clone; the full shard set runs blind for the first time on the pull request's CI (the `tests` job now runs it blind), and any reader that shows is moved by D3 in a fix pass. The single self-review full run stays sighted, as the policy has it. No sighted-versus-blind count comparison is planned: the runner does not supply the evidence for one (D5, limit 3), so the blind CI run's only signal is a shard that fails or errors, and that is what D3 acts on.
- **D4. The static scanner is deleted, not kept as a second opinion.** Two mechanisms that must agree are the cost this item removes. `GATE_MODULES`, `GATE_TOOLS`, `MENTIONS` and `FIXTURES` and the scan section of `tests/test_ci_changes.py` go; `ClassifyTests`, `DetectRepoTests`, `PushDetectTests`, `DraftDetectTests` and `RequireTests` stay. Their replacement tests are: `hide` on a temporary repository removes exactly the set (including a nested `docs/items/` file and a deleted-then-restored one), leaves every other file and a clean `git status`, refuses outside a work tree; the generated `tests.yml` runs `hide` before `exec-shard` in the `tests` job and nowhere else; `CI_PLACEMENT` and `DOCS_TEST_MODULES` agree; and a fixture test module that reads a set path fails when run after `hide` (the proof the check can fail). That module is written into a temporary repository by the CP1 test, never kept as a file under `tests/`, so discovery never puts it in a shard.
- **D5. What the check does not prove, stated.** It proves a path of the set is not needed by the tests the shards run. The conformance, package and `main` modules are not in the shards, so they are not run blind; they already ran on every pull request before this item and a documentation-only change still skips only the shards (CI2d), so their coverage is unchanged. A test that reads a set path only on a branch the shards never reach is not seen; the previous scan could not see it either. Three further limits, stated because they are real. (1) **Git-object reads.** `hide` removes the files from the working tree and the index view only; the blobs stay in `HEAD` and the object database. A test that reads the set through Git (`git clone <REPO_ROOT>`, `git show HEAD:<path>`, `git archive`, `git ls-tree`, a worktree pinned at a commit) sees it and passes blind while still depending on it. Two such readers exist today: `tests/test_run_scenarios.py` (`CloneCase`, which clones `REPO_ROOT`) and `scripts/workflow_state_demo_test.py` (a pinned worktree at a commit). CP2 checks each existing Git-object reader of `REPO_ROOT` and records why it does not depend on the set (or moves the path by D3); the mechanism does not close the class, because committing the removal in the runner checkout would change `HEAD`, the merge base and every identity derived from them. (2) **Tolerant readers.** A shard test that globs `docs/*.md` or `docs/items/`, or skips when a page is absent, iterates over nothing blind and passes, so its assertions never run against the real files; the deleted scanner was the only thing that flagged such a reader, and nothing replaces that enforcement. It is not made a check. (3) **Successful subtests are invisible.** `RecordingResult.addSubTest` in `tools/test_shards.py` discards a subtest that passes: a record keeps only the parent test's outcome, and the summary prints no subtest count, so a blind run that executes fewer passing subtests than a sighted one produces the same record. Local and CI shard assignments also differ, so shard totals are not comparable. No count comparison is planned and none is claimed; instrumenting the runner is out of scope for this item. A reader found by a failing shard on the pull request is a D3 move.
