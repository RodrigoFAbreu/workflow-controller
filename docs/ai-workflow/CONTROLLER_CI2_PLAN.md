## What exists

- **The planner.** `tools/test_shards.py`: `estimate_atoms` (known atom: recorded seconds; unknown conformance atom: `DEFAULT_CONFORMANCE_SECONDS`; unknown controller atom: tests times a mean per test), `assign_lanes` and `lane_seconds` (the longer of a shard's two lanes times `LANE_CONTENTION = 1.15` when both lanes have work), `update_timings` (EWMA, `EWMA_WEIGHT = 0.5`) and `CI_MAX_SHARDS = 3`.
- **The refresh route.** `python3 tools/run_tests.py timings merge --into tools/test_timings.json DIR...` folds the `timings-ci-attempt-<a>` artifacts of a CI run into the profile (`docs/guide/development.md`, "Timings").
- **The guard that exists.** `CommittedTimingsTest` in `tests/test_test_shards.py` rejects names that are not in the inventory, a profile not measured on CI, and a multi-test class atom above 200 s (the CI1b ratchet). Nothing rejects missing atoms, by design ("coverage may drift until the next reviewed refresh").

## Decisions

Each decision states one principle.

- **D1. The timings come from real CI, never from a guess or a local run.** The source is the `timings-ci-attempt-<a>` artifact (highest attempt) of the latest runs of `ci.yml` on `main` or on a code pull request that ran the shards, merged with `timings merge`, as CI1b D4 did: two or three runs, oldest first, the count stated in the commit and on the item page. **The operator downloads the artifacts, the worker does not** (amendment 0: the worker has no GitHub credentials and the artifact download returns 401). The operator placed the `timings-ci-attempt-1` artifacts of the three latest code-pull-request runs of `ci.yml` (runs 43855824846, 43864443959 and 43879797542, oldest first) in `/tmp/claude-c1/ci2-timings/<run-id>/`; each directory holds `shard-0.json` to `shard-2.json`, `plan.json` (the run's plan) and `tree.txt` (the commit the run tested). CP1 merges from those directories, oldest first: `python3 tools/run_tests.py timings merge --into tools/test_timings.json /tmp/claude-c1/ci2-timings/43855824846 /tmp/claude-c1/ci2-timings/43864443959 /tmp/claude-c1/ci2-timings/43879797542`. The shard records carry each shard's `wall_seconds`, so D3 reads them from the same directories. The number of atoms before and after, the 113 Codex atoms and the new `updated_from` digests are recorded. A `main` run that reused a pull request's results (`CI_MAIN_REUSE`) does not qualify: it re-uploads that pull request's records byte for byte, and `update_timings` would fold the same observation twice. Duplicate `shard-*.json` records (same run, same shard, same content) are dropped before `timings merge`, and the count of runs states how many distinct runs were used. If those directories are missing or unreadable, the checkpoint **stops and reports a blocker** and never tries to download the artifacts itself; it never hand-edits the file and never seeds it from a local run (functional review F1 of the adaptive-sharding milestone: a local seed underestimated CI 1.6 times).
- **D2. A ratchet keeps the file from going stale unnoticed, with a limit that ordinary work cannot cross between refreshes.** `CommittedTimingsTest` gains a check: the atoms absent from the committed profile hold at most `MAX_UNTIMED_TEST_SHARE` of the tests of the **atoms the CI plan places on a shard** (the denominator; `main`, `package` and `excluded` atoms are never refreshed by a pull request's records and are not counted). The limit is derived, not chosen: on the whole inventory the untimed share went from near zero at the last full refresh (`065ca1e`, 2026-11-08) to 9.95 percent (671 of 6741 tests) at the base commit, about 1.2 points a day. The refresh is manual until ci2d automates it, so the limit must hold for the longest gap the owner accepts, 14 days, with margin: the constant is **20 percent** and CP1 re-derives it from the CI-placed share it measures (drift per day from the git history since `065ca1e`, times 14 days, rounded up to a multiple of 5 points) and records the numbers on the page. Crossing it then means the refresh is overdue by a clear margin, not that a pull request added a few tests. A negative case beside the check feeds a synthetic profile that omits enough atoms and asserts the failure, one just under the limit that passes, and one that omits only `main`/`package`/`excluded` atoms and passes (the denominator), as the CI1b ratchet does. The check reads only the committed file and the inventory, so it is deterministic. The automation that makes the limit unreachable belongs to ci2d.
- **D3. The acceptance-matrix slowdown is a measured constant, measured at the shard.** The planner multiplies a shard's expected duration by one `LANE_CONTENTION` (1.15) when both lanes have work, but the shard holding the acceptance matrix runs about 1.50 times slower than estimated. That 1.50 is a shard-level figure, so the measured quantity is too: for each shard of the runs D1 uses, the observed `wall_seconds` (from each run's `shard-<n>.json` record) over the **uncontended** estimate, `max(lanes)` of that shard's plan, recomputed from the plan's atoms with the profile CP1 commits (each run's `plan.json` names the atoms of each shard). **Split class (amendment 1):** those historical plans name the original `tests.test_codex_apply_regeneration.PlanRegenerationTest` atom with all ten tests, a ten-test key, while the refreshed profile holds `PlanRegenerationTest` with only the five tests CP1's split leaves in it (the name is kept for one half), so `estimate_atoms` would scale that five-test entry to the historical ten-test atom (`seconds / 5 * 10`) and leave out the sibling `PlanRegenerationRecordTest` altogether, not fall back to the unknown-atom mean. Every historical comparison therefore first maps the original atom to **both** replacement atoms (the two keys CP1's split creates, each with its five tests), placed on the **same shard** as the original, each exactly once, so the ten tests are preserved and the shard's cost is the combined cost of both halves (illustratively, from one arbitrary five-and-five partition and not CP1's own, 77.246 s and 130.936 s, 208.182 s, against 154.492 s for a single ten-test atom scored from half the data). The mapping is one function, used by the D3 ratios and by D5's rescoring alike. The ratio is a calibration of the planner's estimator **using the refreshed profile**, not a quantity independent of the refresh: `update_timings` folds the very observations of D1's runs into the profile that feeds the denominator, so the fit is partly against data the profile already contains. The shard-level calculation keeps it from comparing a recorded second to itself (the denominator is the planner's `max(lanes)` over the shard's atoms, the numerator the shard's observed wall time), and the page states that the fitted value is in-sample. The ratio is taken separately for shards that hold the matrix and shards that hold no conformance suite or hold other suites, so the matrix shard's factor is compared with the global one on the same runs. Where the matrix shard's ratio is stably above 1.15 in at least two runs, it is recorded in a named constant (`CONFORMANCE_CONTENTION`, suite key to factor, each value with the runs it came from in a comment) that `lane_seconds`/`assign_lanes` apply **in place of** the global factor, never on top of it, for a shard that holds that suite, has Controller atoms and has conformance atoms (both lanes have work; a shard with the matrix and no Controller atoms is a single lane and takes no factor). Double counting: recorded seconds of Controller atoms were observed beside the matrix, so some contention is already inside them; the factor is fitted against `max(lanes)` computed from those same recorded seconds, so whatever they already contain is absorbed into the fitted value rather than added, and the page states this. The matrix is the only suite expected to qualify; any other suite stays on the global factor. Alternatives rejected: keeping the matrix on a shard of its own (three shards cannot spare one: the controller lane's roughly 79 minutes would then run on two), and a per-atom factor stored in the timings file (the file stays a plain record of seconds, so the merge and the schema do not change).
- **D4. Estimates never add, drop or condition a test.** The key set of `estimate_atoms` and the plan's selected test ids are unchanged by D2 and D3 (I3). A test asserts it: plans built over the same selection with and without `CONFORMANCE_CONTENTION` have identical `selected_ids` and identical test-id sets across shards.
- **D5. The pull request's own CI is the proof, and the page says so.** The change touches `tools/` and `tests/`, so every shard runs. The checkpoint that finishes the item records the planner's estimated longest shard against the average before and after from the plans CI itself builds: `python3 tools/run_tests.py plan --profile ci --ci-placement --output <file>`, the exact selection and parameters of the `plan` job (`.github/workflows/tests.yml`), never a plan without `--ci-placement`, which also places the `main`, `package` and `excluded` atoms and overstates the longest shard (8,175 s against 3,260 s on the files at the base commit). The planner balances exactly the numbers it reports, so two self-balanced plans always show a longest shard of about 1.00 times the mean (3,260.066, 3,260.067 and 3,260.067 s at the base commit) and comparing them shows only the estimator's level, never a gain. The predicted gain is therefore the **base plan rescored with the after estimator**: save the plan at the base commit (`--ci-placement --output`, before CP1's refresh), keep its shard atom sets unchanged except for the one substitution D3 names (the original `PlanRegenerationTest` atom becomes both replacement atoms, on the original's shard, each once, the ten tests preserved), and score each shard with the after estimator (the refreshed profile plus `CONFORMANCE_CONTENTION`, through `estimate_atoms` and `lane_seconds`, in a throwaway computation that is not committed). The page records that rescored plan's longest shard and mean against the new plan's longest shard and mean (the plan saved after CP2, from `shards[].estimate_seconds`); the difference between the rescored base plan's longest shard and the new plan's longest shard is the predicted gain. It also records, for the runs D1 uses, each shard's observed `wall_seconds` next to its estimate, before (the base estimator) and after (the after estimator), since the imbalance the goal names (1.08 to 1.50 times the average) is observed on CI and not visible in the planner's own plan. Once the pull request's CI has run, the elapsed CI time is the proof, measured as one interval for both sides (`run_started_at` to the `completed_at` of `tests-result`) against the 35 to 41 minute baseline. The page states the result either way; a gain smaller than the planner predicts is reported, not argued away.
- **D6. The page and the guides change with the behaviour, and the backlog is split in place.** `docs/guide/development.md` (the "Timings" paragraph and the ratchet paragraph), `docs/guide/ci-and-releases.md` (the estimate paragraph, both places that state the 1.15 rule, at the lane-contention sentence near line 164 and the one near line 317, the refresh date, and the sentence that calls the acceptance matrix the floor of the longest shard, which the measurements contradict: the controller lane is always the longer one) and `docs/adr/0005-adaptive-test-sharding.md` (a dated amendment beside the 2026-10-13 one: the estimate rule "the longer of its two lanes, times 1.15 when both have work", line 73, now takes the per-suite factor for a shard holding the matrix) are updated in place. The CI1b review follow-ups of [#324](https://github.com/RodrigoFAbreu/workflow-controller/issues/324) are a documentation change and are done here: reword the pre-plan summary on the CI1b item page, say "blends" for the next merge, add the two missing D4 rule parts and the "base without test methods" wording to the development guide, and record the fixture keys and the derivation inputs. The backlog gains the four follow-up items of the table above (ci2b to ci2e) directly after `workflow-controller-ci2` (every later item's `order` is renumbered by the number added, since orders are unique contiguous integers; each new item carries `depends_on: [workflow-controller-ci2]`), each `next`, with a page that states its scope items from the owner's list; [#317](https://github.com/RodrigoFAbreu/workflow-controller/issues/317) (the 20-minute target) stays open and is referenced by every slice, to be closed by the last slice to merge; `workflow-controller-ci2` is retitled to this slice and `docs/ROADMAP.md` is regenerated.
