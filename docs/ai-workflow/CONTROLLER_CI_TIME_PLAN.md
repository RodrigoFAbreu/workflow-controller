## Goal

Since the automated functional review (C10c, 1.18.0) a pull request's CI takes far longer than the owner's budget of 15-20 minutes (owner rule, 2026-10-22: over 30 minutes, improving CI is the next item). The recorded timings in `tools/test_timings.json` total about 11,300 seconds of test time, and about 46 minutes of wall time per pull request even after the timings refresh of 2026-10-22 ([#119](https://github.com/RodrigoFAbreu/workflow-controller/issues/119)). One flake, `FollowCommandTest.test_a_running_run_is_chosen`, races a fixed 0.3-second timer and costs a full CI rerun each time ([#121](https://github.com/RodrigoFAbreu/workflow-controller/issues/121)).

The owner's chosen scope, which this revision follows, is: raise the shard ceiling to **six** (`CI_MAX_SHARDS = 6`, about eight concurrent Linux runners with `package` and the managed `workflow-conformance` job); move **both** whole-catalogue checks, the determinism comparison and the negative-mutation module, off the pull request and into the `main` run, where they **gate the release** (D2); share the lifecycle fixtures (D3); and fix the flake (D5). The complete successful pull-request check duration, every required check included, is what is measured (D7). #121 is closed by the flake fix; #119 is closed only if that measured duration is at most 20 minutes, and otherwise stays open, re-scoped to the shortfall.

## Wall-time estimate

The inputs are `tools/test_timings.json` (11,335 seconds in total; 9,685 seconds of controller atoms, about 1,650 of vendored conformance suites) and `tools/test_shards.py` (`LANE_CONTENTION = 1.15`, the two-lane allocator). A shard's wall time is set by its controller lane, and by the conformance lane when that is longer, times the contention factor when both lanes have work.

- **What moves off the pull request.** The determinism atom (`CatalogueDeterminismTest.test_two_complete_runs_agree_on_every_normalised_summary`) is 1,075 seconds. The 46 atoms of `tests.test_scenarios_negative` total **959.797 seconds** (committed timings). The positive functional scenarios (`tests.test_scenarios`) stay on pull requests: the figure of about 1,250 seconds earlier revisions used combined positive scenarios with mutations, and moving the negatives alone does not claim it. Together the two moves take about 2,035 seconds of controller work out of the pull-request shards; the subset determinism check adds back under 100.
- **What the fixtures save (D3).** The lifecycle classes named in D3 (about 2,500 seconds) are converted and cut to about a third, saving about 1,700 seconds, of which about 540 come from four one-test functional atoms that a per-process snapshot does not help unless CP4 finds a cheaper drive for each. The `tests.test_pr_report` classes (about 960 seconds) save up to about 650 if their cost is the repeated drive. CP4 states which of these were reached.
- **Six shards.** With the two moves, the one-third fixture costs and a 100-second subset allowance, the real two-lane allocator at six shards places about **17.0 to 18.7 minutes** of wall time on the longest shard **before** planning, per-shard setup and aggregation. The vendored `workflow_acceptance_matrix_test.py` atom (846.744 seconds) alone sets a floor of about **16.2 minutes** with `LANE_CONTENTION`, because it is one indivisible atom beside a busy controller lane. At the slow end (18.7 minutes) only about **77 seconds** of the 20-minute budget remain for the plan job, per-shard checkout, setup and install, result aggregation, and the separately running `package` and managed `workflow-conformance` checks.
- So the plan **may** land inside 20 minutes and does not promise it: the slow end leaves almost no room for overhead. CP5 recomputes these figures with the allocator on refreshed timings and then measures the real pull request (D7). If the measured complete duration is above 20 minutes, the milestone states the shortfall and #119 stays open.
- Not in this saving: the next atoms after the ones named (`test_review_same_provider`, `test_review_job`, `test_usage_record_job`, `test_protocol_outcome`, 50-85 seconds each) and the vendored acceptance atom, which is the Workflow's own code and is placed, not shortened.

## Decisions

Each decision states one principle.

- **D1. Cut work, not coverage: every check that runs today still runs, but not every check runs on every pull request, and a check moved after the merge still blocks the release.** The two ways to remove time are doing a thing once instead of many times (D3) and doing it where it can fail (D2). Dropping a test, or lowering what it asserts, is not an option.
- **D2. The two checks that depend only on the whole catalogue run after the merge, on the release candidate commit, and the release waits for them (#119).** `CatalogueDeterminismTest.test_two_complete_runs_agree_on_every_normalised_summary` (1,075 seconds) runs every scenario twice, and `tests.test_scenarios_negative` (46 mutation atoms, 959.797 seconds) runs a scenario once per mutation. Neither is a property of a change to one flow. Four things change.
  - (a) **Placement mechanism.** The determinism class moves out of `tests/test_run_scenarios.py` (where it shares a module with about 40 other tests, and CI placement is keyed by module) into its own module, `tests/test_catalogue_determinism.py`, which subclasses `CloneCase` through `from tests import test_run_scenarios as base`, so the test loader does not re-collect it. `tools/test_shards.py` gains a placement kind `MAIN = "main"` and two `CI_PLACEMENT` entries, `tests.test_catalogue_determinism` and `tests.test_scenarios_negative`, each with its reason; the `--ci-placement` plan keeps both modules out of the shard matrix, as it does for the `package` and excluded modules. `tests.test_scenarios` (the positive scenario atoms) keeps its shard placement. `tools/ci_workflows.py` derives `MAIN_TEST_MODULES` from the same table (as `PACKAGE_TEST_MODULES`). A local `python3 tools/run_tests.py run` (no `--ci-placement`) and `unittest discover` still run both modules, so every check still runs somewhere (D1). Moving modules changes the plan digest once, which the `CI_MAIN_REUSE` digest comparison sees on the first merge (it then runs fresh, by design).
  - (b) **Two jobs in `main.yml`, with the same setup as the shard jobs.** `main_workflow()` gains `after-merge-determinism` (runs `tests.test_catalogue_determinism`) and `after-merge-mutations` (runs `tests.test_scenarios_negative`, whose atoms are split by `MAIN_TEST_MODULES`). Each job has the steps of the `tests` job in `tools/ci_workflows.py`: checkout, Python setup, the editable install and the `allow unprivileged user namespaces` step (`ALLOW_USERNS`, as at `tools/ci_workflows.py:186-187`), then the run. They have no `needs`, so they start beside `reuse` and `validate`; they are not shards, so `CI_MAIN_REUSE` never reuses or skips them, and they run fresh on the commit of the run (`GITHUB_SHA`), so every `main` commit is checked whether or not it releases. Two further jobs, `release-target-determinism` and `release-target-mutations`, run the same commands on the **publication target** (see (d)).
  - (c) **They fail closed, and a run cannot pass without executing.** `CloneCase.setUpClass` raises `SkipTest` when `kit.probe_isolation()` fails (`tests/test_run_scenarios.py:52-55`), and `unittest` exits 0 when every test is skipped. The moved determinism class therefore overrides `setUpClass` to apply `kit.isolation_gate` (as `tests/test_scenarios.py:42-47` does): under `CI` a failing probe fails the run, locally it still skips. The mutation atoms already do this (`tests/test_scenarios_negative.py:75`). Beyond that, each job's run command is wrapped so that it exits non-zero when the selected set is empty, when the number of tests run differs from the planner's inventory of that module, or when any selected test is skipped (CP2 chooses the mechanism, preferring the planner's own runner; `tests/test_ci_workflows.py` pins the command, and a unit test covers an empty selection and a skip). An empty or skipped run therefore cannot establish coverage.
  - (d) **The release depends on checks of the exact commit it publishes, fail-closed.** The commit `build` and `publish` act on is `release-plan.outputs.commit`, which `controller/release_txn.py` can set to an ancestor of `GITHUB_SHA`: a `RESUME` classification returns the older tagged commit as the target (`release_txn.py:556-558`, `Classification.outputs()` at `:154-156`; `ConventionalClassificationTest._interrupted` covers it), and `tools/ci_workflows.py` builds and publishes that commit. Successful checks of `GITHUB_SHA` do not establish anything for such a target, so the gate is bound to the target and the target is resolved **before** its checks run:
    - `release-plan` keeps `needs: ["validate"]` and its condition, unchanged, so the target is selected first and the new jobs do not sit in front of it.
    - `release-target-determinism` and `release-target-mutations` have `needs: ["release-plan"]` and the condition `_after('release-plan') && _publishing_condition() && needs.release-plan.outputs.commit != github.sha`. The explicit `_after('release-plan')` is required: `release-plan` is itself gated by `_after('validate')`, and an implicit `success()` would look at the skipped `reuse` ancestor whenever `CI_MAIN_REUSE` is not `on`, so an ancestor `RESUME` could never publish in the default mode. They have the steps of the `after-merge-*` jobs but check out `ref: ${{ needs.release-plan.outputs.commit }}` with full history and run the same fail-closed command against that tree. When the target is `GITHUB_SHA` (every ordinary release) they are skipped and cost nothing.
    - `_publishing_condition()` is **unchanged** (trunk and a publishing state, `tools/ci_workflows.py:483-486`): it answers "does this run publish?", which the `release-target-*` jobs need. The coverage term is a **separate helper, `_coverage_condition()`**, used only by `build` and `publish`, because it reads the results of the `release-target-*` jobs and a job's own `if` must never depend on its own result. It is, for each of the two checks, `(needs.release-plan.outputs.commit == github.sha && needs.after-merge-<check>.result == 'success') || (needs.release-plan.outputs.commit != github.sha && needs.release-target-<check>.result == 'success')`, each `result` compared explicitly to `'success'`. The full generated conditions are: `build`: `_after('validate', 'release-plan') && _publishing_condition() && _coverage_condition()`; `publish`: `_after('validate', 'release-plan', 'build') && _publishing_condition() && _coverage_condition()`; `release-target-<check>`: `_after('release-plan') && _publishing_condition() && needs.release-plan.outputs.commit != github.sha`. **No generated `if` refers to a job outside its own `needs`**: `release-target-*` need only `release-plan`, so their `if` reads only `needs.release-plan`; `build` and `publish` list every job their `if` names. `build` and `publish` list `validate`, `release-plan`, the two `after-merge-*` jobs and the two `release-target-*` jobs in `needs` (and, for `publish`, `build`), but their `_after(...)` names only `validate` and `release-plan` (`build`: `_after('validate', 'release-plan')`; `publish`: `_after('validate', 'release-plan', 'build')`). The four check jobs are deliberately **not** in `_after(...)`: `_after` means "every named prerequisite succeeded", and the `release-target-*` jobs are skipped in every ordinary release, so naming them would block every release. The four are required only through `_coverage_condition()`, which means "one of two alternatives succeeded". A missing, unscheduled, pending, failed, cancelled or skipped covering job therefore prevents publication, whether or not `CI_MAIN_REUSE` is on, and a success for another commit cannot satisfy the term for the target.
    - The fail-closed command is runnable against an older target tree or fails closed there: if the target predates the moved module the selection is empty or short and the command exits non-zero, so a pre-change `RESUME` target blocks the release for the owner to decide (a one-time case, documented) rather than publishing unchecked. CP2 places the wrapper so that this holds and tests it.
    - The `main-release` concurrency group (`cancel-in-progress: false`) is unchanged. Timing: an ordinary release publishes after `validate` and the slower `after-merge-*` job (about 18 minutes plus setup), not a few minutes after the merge; a `RESUME` of an ancestor adds the target checks after `release-plan` (about 18 minutes plus setup more) before `build`. A following merge's run waits behind the slot as today. CP6 states both timings in `docs/guide/ci-and-releases.md`. No separate workflow file is needed.
  - (e) **Subset on every pull request.** `tests/test_run_scenarios.py` keeps a determinism check on a small fixed subset of the catalogue: three real catalogue flows (not `selftest-*`, which `DeterminismTest` already covers), two cheap flows and one variant, chosen in CP2 from the recorded timings. The assertions that carry over are `assert_ingested` and equality of the normalised summaries, plus an exact expected name set for the subset; today's `len(first) >= 15` and no-`selftest` assertions describe the whole catalogue and stay with the moved test. A change to the normaliser or to the runner still fails before merge. The positive scenario atoms and `ScenarioInventoryTest` stay in the shards.
- **D3. A fixture that is expensive and read-only after it is built is built once per test process and copied per test.** Every case of `OutcomesTest`, `TheFaultStopsTest`, `ThePreLaunchStopsTest`, `SatisfyGateLifecycleTest`, `PrDefectLoopLifecycleTest` and the functional lifecycle tests (`IsolationTest`, `CycleClosesTest`, `PersonStopsTest`, `NoRunTest`) starts a managed repository and drives the vendored Workflow from the plan to the same row (38e, 38h or a pull-request row) before it does the one thing it tests; that drive is most of each case (about 45 seconds each). The fixture builds the repository to that row once, in a snapshot, and each test gets its own copy. CP4 also reads the `tests.test_pr_report` classes and converts those whose cost is the same repeated drive. The positive `functional_*` scenario atoms are out of scope, and so are the `Mutation_*` atoms, which now run after the merge (D2): each is a one-test class that drives its flow in a sandbox process of its own, and sharing a snapshot with that process would change the isolation boundary (D4), which this step does not do. A snapshot is shared once per test process, so it saves time only for the cases of one class that the shard planner keeps together; many of these atoms hold one test each (about 200-275 seconds), so CP4's measurement states which atoms gain and which do not, and a one-test atom gains only by making its own drive cheaper. A copy must be indistinguishable to the test from a fresh build: the same head and ids where a test asserts them, no path of the first build left inside the copy, and no state shared between tests (D4).
- **D4. Sharing must not let one test see another's writes, and must not cross the isolation boundary.** The snapshot lives only in the test process; it is never mounted or passed into a scenario sandbox, whose protect and scratch mounts are unchanged. Each test works on its own copy of the snapshot (a directory copy, not a link), the snapshot is never opened for writing after it is built, and a test that today asserts something that depends on the drive itself (a count of jobs, the first job id, the clock) is changed to assert what it means or keeps a fresh build, with the reason in a comment. A run where the snapshot cannot be built (a missing tool) falls back to a fresh build per test, so the test suite never depends on the snapshot to be correct, only to be fast.
- **D5. A flake is explained, then fixed by removing the dependence on the scheduler, never by lengthening a timer (#121).** The end of the run waits for a signal that `follow` has attached: the run is ended from inside the first poll or after the first event is read, so it does not matter how late the follower starts. **Both** timer-dependent `FollowCommandTest` cases are covered: `test_a_running_run_is_chosen` and the orphan-job case at `tests/test_cli.py` that kills a sleeper after 0.3 seconds. Each gets the same signal-based fix and its own delayed-start regression; a case that CP1 finds already free of the race gets a test that shows it (a follower started late), not silence. The regressions widen the window (a follower started past the old 0.3 seconds) and fail on the old test shapes.
- **D6. The shard plan is fed the measured durations, so no shard holds most of the slow tests (#119).** The shard ceiling is **six** (`CI_MAX_SHARDS = 6`): the runner budget becomes 6 shards, `package` and the managed `workflow-conformance` job, about eight concurrent Linux runners, and the budget comment in `tools/test_shards.py`, `docs/guide/ci-and-releases.md` and the assertions in `tests/test_test_shards.py` and `tests/test_scenarios.py` (`MAX_CI_SHARDS` and `test_the_ci_plan_stays_within_four_shards`, renamed for six) follow it. After D2 and D3 the timings are refreshed from a real pull-request run's recorded results (`tools/run_tests.py timings merge`, the same path as the refresh of 2026-10-22), and the plan is checked on them: the expected wall time of the longest shard, and the spread between the shards, are stated in the milestone's narrative. A test left over 200 seconds is named, with the reason it stays (the vendored Workflow's own conformance suites, such as `workflow_acceptance_matrix_test.py` at about 850 seconds, are the Workflow's code and are not changed here; they are placed, not shortened).
- **D7. The target is measured on CI as the complete successful pull-request check duration, and #119 closes only on that measurement.** The duration is read from the CP5 head's runs through the public API when `gh` is not available, from the start of the earliest required run to the completion of the last: the plan job, every shard with its setup, the aggregation (`tests-result`), `package`, **and** the separate managed `workflow-conformance` check (`tests-result` depends only on `plan` and `tests`, so it is not the end of the pull request). Every one of those checks must have succeeded; a failed or cancelled check is not a measurement. The pull request closes #121 always, and closes #119 only if that duration is at most 20 minutes. A local estimate from the timings file is a plan input, not evidence. If the measured duration is above 20 minutes, the milestone states the shortfall and the next biggest atoms, the pull request body says "refs #119", and #119 stays open, re-scoped to the shortfall; the owner decides whether to continue (the owner rule, 2026-10-22, makes CI the next item again while a pull request is over 30 minutes).
- **D8. Documentation changes with the behaviour, in place.** `docs/guide/ci-and-releases.md` and `docs/guide/development.md` say where the two moved checks run, that they gate the release and the resulting release timing, the six-shard runner budget, and how a test fixture is shared; the closing roadmap and `docs/ACTIVE_MILESTONE.md` records go in the acceptance, as for every milestone.

## Risks

- **The target may not be reached even with six shards (D7).** The estimate is 17.0 to 18.7 minutes of shard work before setup and aggregation, with a floor of about 16.2 minutes from the indivisible vendored acceptance atom, and only about 77 seconds of margin at the slow end. The plan measures the complete duration, states the shortfall, keeps #119 open if it is above 20 minutes and does not claim the target; the owner decides on a further step.
- **A shared snapshot can hide a bug or add a coupling (D4).** Tests that today pass because each builds its own can fail when one copy leaks into another. The directory copy, the never-writable snapshot, the any-order done and the fresh-build fallback bound that.
- **Releases are later and a `main` run is longer (D2(d)).** Moving the checks after the merge keeps them release-blocking, so a release publishes about 18 minutes (determinism, with setup) after the merge instead of a few minutes after, and a failing after-merge job stops that release. That is the deliberate trade: the checks leave the pull request, not the release. The `main-release` group is unchanged, so the serialisation behaviour is as today; `tests/test_ci_workflows.py` pins the dependency, the fail-closed conditions and the wrong-commit (ancestor `RESUME`) regression. A `RESUME` of an ancestor target pays the target checks again after `release-plan`, and a target that predates the moved module blocks the release (fail-closed) for the owner to decide.
- **A check that moves after the merge can find a break only after the merge (D2).** The subset check on every pull request catches a normaliser or runner change; a scenario added to the catalogue that is non-deterministic, or a flow that stops failing under a mutation, is found on `main`, before the release but after the merge. This is the trade the issue proposes.
- **New `main` jobs run next to `CI_MAIN_REUSE` (D2).** The four jobs are not shards, so reuse never skips them; `tests/test_ci_workflows.py` pins that. Their placement changes the plan digest once, so the first `main` run after the merge does not reuse the pull request's results.
- **The flake may have other causes (D5).** The class is read for every timer; if the cause on CI is not the timer, the diagnostic is added and #121 stays open.
- **No `docs/TECHNICAL_DECISIONS.md` "Open decision" row is touched** (the file does not exist in this repository).
