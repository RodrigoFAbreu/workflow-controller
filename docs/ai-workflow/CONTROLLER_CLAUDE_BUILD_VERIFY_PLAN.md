## Goal

The automated functional review (1.18.0) launches the tester only when the `claude` it would run is an ELF whose SHA-256 is in `VERIFIED_NATIVE_BUILDS` (`controller/functional_review.py`), which lists one build, Claude Code 2.1.303. The Claude CLI updates itself often (this machine runs 2.1.308), so on most operators' machines the step stops at `functional_tester_unavailable` and falls back to a person's manual review until a Controller release adds the digest ([#113](https://github.com/RodrigoFAbreu/workflow-controller/issues/113)). The fallback is safe; the feature is simply off.

The owner's decision (2026-10-22) is option 1 of #113: an operator command that runs the live enforcement probes against the build and, **only when every probe holds**, records its digest in the Controller's state, never in the settings file. The launch admits the built-in list plus the recorded digests. A Claude update then needs one command and no release.

## Decisions

Each decision states one principle.

- **D1. A build is admitted by what was measured on it, and the measurement is the one the release process already trusts.** The command runs the same three live probes as `LiveEnforcementTests` in `tests/test_functional_enforcement.py` (the boundary probe of D10, the unsandboxed-retry and file-tool probe, and the missing-component refusal), through one shared implementation in a new module `controller/claude_build.py`. The live tests are changed to call that module, so the command and the release check cannot drift apart. The fourth live test (the working-directory precedence of D5) pins the reason `tester_settings` names the output folder as the working directory. It asserts that a write is *refused* in a configuration the Controller never uses, so a build where it changes does not weaken the boundary; it stays a release-side test and is not a condition of admission, with the reason in a comment. **A probe is evidence only when its operation was executed, never on the model's say-so.** For the boundary probe the command reads the stream for exactly one `Bash` tool call whose `command` equals the probe command it sent, byte for byte, and judges `judge_probe` against **that call's matched tool result** (by `tool_use_id`), not the model's final text; a missing call, a call whose command differs, a second call, or a result that does not match is inconclusive (exit 20, nothing recorded, "run it again"), so a model that skips the Unix-socket connection and reports `PROBE unix BLOCKED` cannot authorise a digest. The unsandboxed-retry probe is only evidence when the model actually attempted the call: the command reads the stream for the attempted `Bash` call with `dangerouslyDisableSandbox` and counts "no attempt seen" as inconclusive (exit 20, nothing recorded, "run it again"). If the CLI does not surface the parameter when `allowUnsandboxedCommands` is false, the exact tool list and the settings check are the whole evidence for that probe and the output says so (CP2 settles which from the real stream).
- **D2. Fail closed on everything that is not a clean pass.** A digest is recorded only when the host passes the host part of the static probe (bwrap, socat, seccomp; `static_probe` is split into `host_probe` and the identity check, so the command runs the host checks plus an ELF check in place of the identity check, which an unrecorded build always fails) for an ELF, the model is reachable, `judge_probe` returns no failure, every host-side check of the live test holds (the tracked files and checklist unchanged, no new file, no write to the stand-in home, `/tmp`, `/var/tmp` or `/dev/shm`, no connection to the host's Unix or TCP listener, the writable and output locations written), the tool list is exactly `["Bash"]`, and the unsandboxed retry changed nothing. A refused launch, a login or limit error, a timeout, an unreadable result or a missing probe line records nothing and exits 20 with the failing probe named. Nothing is recorded for a build the command could not finish checking. **The digest recorded is the digest of the file every probe ran** (time-of-check/time-of-use): the command resolves the real path once (`os.path.realpath`), hashes it, runs every probe with that resolved path as `argv[0]` (the native build is one ELF, so `claude_environment`'s `PATH` from `binary.parent` still works), re-hashes it after the last probe and records only when the two digests are equal; otherwise it refuses and records nothing. Another session's installer re-pointing the `~/.local/bin/claude` symlink during the run therefore cannot make the command record a build it did not probe: the probes keep executing the original resolved file and its digest is what is recorded; only a change to that file's own bytes, which the re-hash catches, refuses with `build_changed`.
- **D3. The record lives in the Controller's runtime root, never in the settings file.** `<runtime root>/verified-claude-builds.json` holds `{"schema_version": 1, "builds": {<sha256>: {"version", "verified_at", "controller_version", "probes"}}}`, written through `runtime.write_json` (new file primitives belong in `runtime.py`, and the write-containment test allows no other). The settings file stays the operator's own; the Controller does not edit it. The file is host-level evidence about one binary, read at launch. An unreadable, malformed or wrong-schema record counts as empty (only the built-in list is admitted) and the stop text says it was ignored, so a damaged record can never admit a build. **Who may write the record, and what is rejected (the trust boundary).** The record is operator-level evidence, not an authenticated one: the principal it is defended against is the *tester*, which is sandboxed, and the principal it trusts is the operator's own session (the command, and the lifecycle workers, which run as the operator with the operator's authority over the repository, the settings file, the usage record and the Controller's own source). A lifecycle worker able to write the runtime root could equally rewrite the settings or the Controller, so the Controller does not claim to defend against it, and the guide says so (D7); no key or signature is added, because any secret the Controller could keep in the runtime root is readable and writable by the same principal. What *is* enforced, fail closed, so the record cannot be redirected into tester-controlled space: (a) the tester cannot write the runtime root (outside every allowed location of `tester_settings`), and the launch refuses (`functional_tester_unavailable`, naming the reason) when the resolved runtime root lies inside the tester's clone or output folder, so a configured runtime root cannot place the record where the tester writes; (b) `read_verified` opens the record with `O_NOFOLLOW` on a path whose parent is the resolved runtime root, takes one file descriptor, and checks on that descriptor (`fstat`) a regular file, owned by the effective user, with no group or world write bit, then parses from the same descriptor, so a record that is a symlink (into the tester's output or anywhere), a replaced file, a foreign-owned or writable-by-others file, or one swapped between the check and the read is empty and the stop text says it was ignored; (c) `record_verified` never writes through a symlink at the record's path (it refuses, and records nothing, instead of `_atomic_write`'s resolve-and-preserve) and creates the file mode 0600. Several lanes share a runtime root, so `record_verified` does its read-merge-write under an exclusive lock taken through a `runtime.py` helper (as `usage_lock` does), so two concurrent runs cannot lose an entry.
- **D4. The admitted set is the built-in list plus the recorded digests, matched by the digest of the file that will run.** `_is_native_executable` and `static_probe` take the recorded digests and the resolved `claude` path; the launch passes the binary it will execute (`review.resolve_binary`), not a second `which("claude")` lookup. The launch also **executes the resolved real path whose digest it admitted**, not the symlink (`functional.binary` becomes that absolute path), so a symlink re-pointed between the check and the exec cannot run an unadmitted build. That makes the probe and the launch use one resolved binary ([#114](https://github.com/RodrigoFAbreu/workflow-controller/issues/114)) and lets the command verify exactly what a launch would run. The residual window (a versioned file rewritten in place between the hash and the exec) is not closed: the installer writes each version to its own file and re-points the link, never rewriting a version, so the window is accepted and stated in the guide. **Which binary a launch uses is unchanged:** the functional launch takes `review.CLAUDE.default_binary`, `claude` on the Controller's `PATH` (`controller/cli.py:1436-1445`, `controller/review.py:1716`); the global `--claude-binary` reaches only the lifecycle worker (`controller/cli.py:1990`) and this change does not make the launch honour it. The identity rule is unchanged: an ELF whose SHA-256 is in the set; a launcher, script or package CLI is still refused, and the verification command refuses a non-ELF before any model call.
- **D5. The command is `workflow-controller verify-claude`, short and explicit about its cost.** It resolves the binary as a launch does, `claude` on `PATH` through `review.resolve_binary`; `--claude-binary` is accepted only as "which build to verify" and, when it names a different file from the `claude` on `PATH`, the output says that a launch runs the `PATH` one, which stays unadmitted until it is verified or the `PATH` is changed. It prints the version (`claude --version`), the resolved path, the digest and each probe's result, and exits 0 when the build is verified (newly recorded, already recorded or built in; an already admitted build is reported and not re-probed unless `--force` is given) and 20 when it is not. It uses the operator's existing Claude credentials the way a launch does (a private copy of the credential file in a scratch home), spends up to two short model turns at low effort and never passes through the usage budget gate; the help text and the output say so. It writes only the record and its own scratch folder, which it removes. It is not a read-only command in the runtime sense (it writes the runtime root), but it is **settings-read-only**: dispatch resolves the settings with `settings.load` (the file loaded, never filled, never created, never updated), so a successful or failed verification leaves the settings file absent or byte-identical, as R1 says; the exception to the generic `write = not read_only` rule is a named set beside `READ_ONLY_COMMANDS` in `controller/cli.py`.
- **D6. A refused build names its remedy.** `functional_tester_unavailable` for an unadmitted build now says to run `workflow-controller verify-claude` (and still names the built-in versions), so the person who meets the stop knows the one step. A refusal carries the digest, so the operator sees which build was meant.
- **D7. Documentation changes with the behaviour, in place.** `docs/install.md`, `docs/compatibility.md`, `docs/common-problems.md`, `docs/exit-codes.md`, `docs/guide/commands.md`, `docs/guide/automation.md`, `docs/guide/runtime.md` and `docs/guide/development.md` say what is admitted, the new command, where the record lives, that it is per runtime root, that deleting it makes the build refused again until re-verified, and the trust boundary of D3 (defended against the tester and against redirection; not against a lifecycle worker holding the operator's own authority); the closing roadmap and `docs/ACTIVE_MILESTONE.md` records go in the acceptance, as for every milestone.

## Risks

- **A real probe needs a model and credentials.** The unit tests use fakes; the real run is the opt-in live test and the operator's own use, and a model that is unreachable is a refusal, never a pass (D2).
- **The probe's model turn is not deterministic.** It reuses the existing prompt, which the release check already depends on; a build that produces a garbled probe is not recorded and the operator can run the command again.
- **Moving the harness out of a test module.** The live tests keep their assertions; CP2 shows they still pass on this machine's claude before the module is relied on.
- **The installer re-points the `claude` symlink while lanes run.** Handled by D2/D4: one resolved path, hashed before and after, executed by the launch; the in-place-rewrite window is stated, not closed.
- **A record is per runtime root.** A source checkout's `.controller` and the shared install's state keep separate records; a build verified in one is not admitted in the other. This is documented, not hidden (D7).
- **Out of scope:** the credential-read denial and `file://` origin detection ([#115](https://github.com/RodrigoFAbreu/workflow-controller/issues/115)), and running the probes in CI on the newest CLI (option 2 of #113). Neither is needed for this command.
