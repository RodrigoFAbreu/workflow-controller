Twelve open GitHub issues are minor review findings (label `review-follow-up`), small defects (label `bug`) or the owner's route decision for `/satisfy-gate`: #78, #79, #82-#87, #91 and #93-#95. This milestone fixes all twelve in one pull request, whose body closes each with `Closes #n`. After it `review-follow-up` and `bug` hold no issue that existed at its start, except #88, which waits for a Workflow release (workflow#43) and is not part of this milestone, and #82 if its cause cannot be reproduced (D7), in which case the pull request body closes eleven issues and #82 stays open with its diagnostic.

## Decisions

Each decision states one principle.

- **D1. One checkpoint per kind of change, so a reviewer reads one kind at a time.** Documents (CP1), small code fixes with their tests (CP2), tests only (CP3), the route split (CP4), and the closing documentation and roadmap (CP5). The order is by risk: the cheapest and safest first, the one design last.
- **D2. The `/satisfy-gate` route is chosen by the stage that is validated, because the stages ask different things of the worker (#91).** Plan approval and technical approval are a mechanical check and one transaction; acceptance also writes the milestone narrative, the roadmap and `docs/ACTIVE_MILESTONE.md` edits and the minor-findings table. So the built-in routes become:

  | Role | Launched for | Model | Effort | Single agent |
  | --- | --- | --- | --- | --- |
  | `satisfy-gate` | `plan.satisfy`, `implementation.satisfy` | `claude-haiku-5-5` | `high` | yes |
  | `satisfy-gate-acceptance` (new) | `acceptance.satisfy` | `claude-sonnet-5-5` | `medium` | yes |

  Both stay overridable like every role: `--role-model`, `--role-effort`, the routing file and the settings file's `routing` section. Full model ids are used because #72 refuses a family-style name.
- **D3. What makes the transaction safe is the single-agent route and the Workflow's own re-check, not the model's size, so a smaller model is safe here (#91).** C10a made the validator Opus because it runs a transaction that commits. The protection is the route: `Agent`, `Workflow` and `Skill` are disallowed for a single-agent worker, and the Workflow re-evaluates every requirement inside its own transaction, so no model can record an approval whose requirements are unmet. A weak run's worst outcome is a refusal or a failed job, which stops the run. Both new routes are single-agent, and a test pins that.
- **D4. The new role is a table-generation change and says what an older Controller does with it.** The settings table generation goes from 10 to 11 (a key or a routing role raises it); no key is added and no value moves. An older Controller refuses `satisfy-gate-acceptance` in a `--routing-config` file and ignores it, with a warning, in the settings file; its `settings clean` refuses a file a newer release filled. A value an owner already pinned for `satisfy-gate` now applies to plan and technical approval only; acceptance takes its own built-in route until the owner names it, and the runtime guide says so, as do the release notes written after the release.
- **D5. A model change is proven on the real model before release, once per route.** The unit tests pin the routes; they cannot show that Haiku completes a plan approval or that Sonnet completes an acceptance. The functional review includes one real Haiku 5.5 `high` plan approval and one real Sonnet 5.5 `medium` acceptance on a scratch repository in an isolated scratch installation (the harness below). If the real Haiku run cannot finish the approval, the milestone stops at the functional-review gate for an owner decision; the plan does not choose a different route on its own. A run that does not complete the transaction does not satisfy the functional review, and both runs complete before release.

  **The harness (the real worker reaches the real transaction and no forge).** The scratch repository is a copy of a managed repository whose `origin` is the GitHub-shaped URL `https://github.com/owner/repo.git`, because `origin_repository` (`scripts/workflow_forge.py:89`) refuses anything else with `forge_unavailable`; the URL is never contacted. No `insteadOf` rule is set on it: `git remote get-url origin` (which `origin_repository` reads) expands `insteadOf` and would print the bare repository's path, which `_REMOTE_RE` rejects with the same `forge_unavailable`. The acceptance gate runs no git network command, so nothing needs redirecting; if a push or fetch must also fail closed, use `git config url."<scratch bare repository>".pushInsteadOf <that URL>` (`get-url` without `--push` does not expand it) and `GIT_ALLOW_PROTOCOL=file` in the worker's environment. The `gh` the Workflow finds is a fake script on the worker's `PATH`, installed in a directory outside the scratch repository, every worktree and the temporary directory, mode `0755` in a directory that is not world-writable (for example under the lane's `~/.local/share/` tree), because `resolve_gh` (`scripts/workflow_forge.py:130`) refuses a `gh` inside the repository or a temporary directory with `forge_undecidable`. The fake answers only the one `gh pr list --search <commit>` query the acceptance gate makes, with the same scripted pull request JSON that `_SATISFY_ACCEPTANCE` in `tests/test_protocol_lifecycle.py` returns through its `run` seam (a green `statusCheckRollup`, `headRefOid` equal to the searched commit), appends each argv to a log, and exits non-zero for any other argument, so the log shows that nothing else ran. The real `satisfy_acceptance_gate` runs unmodified with its real `resolve_gh`, so the run proves the actual acceptance transaction; the plan and technical approvals need no forge. **Starting state of the scratch item.** For the acceptance run, the item is at `AWAITING_FUNCTIONAL_REVIEW` with a recorded technical approval (the anchor `gate_policy.anchor_of` needs), the automatic acceptance policy adopted, the functional checklist prepared and committed with its `Workflow-Functional-Checklist` trailer (without it `next-action` answers row `37`, `functional.prepare`, before row `38h`), and one passing flow recorded at the scratch repository's `HEAD` through `workflow_state.record_functional_evidence`, as `_FUNCTIONAL_EVIDENCE` and `_ADOPT_ACCEPTANCE_POLICY` do in `tests/test_protocol_lifecycle.py`; `next-action` then answers row `38h` and the gate evaluates as `satisfiable` apart from the pull request fact the fake `gh` supplies. Without this the real run ends in `GateNotSatisfiableError` and never shows that Sonnet completes the transaction. For the plan-approval run, the item is at the plan-approval gate with both plan-review stages recorded. **Account isolation (the real workers touch nothing of the owner's).** A worker launched by `worker.launch` inherits the Controller's own environment (`controller/worker.py:1346`); the isolated environment of `claude_environment` (`controller/review.py:1477`) belongs to the review harness only. No `CODEX_HOME`, no `GH_TOKEN`/`GITHUB_TOKEN`, no `SSH_AUTH_SOCK`. **Worker-free isolation check, before either real worker:** run the candidate's virtual-environment interpreter with `-I` (`$S/pipx/venvs/workflow-controller/bin/python`, the one `$S/bin/workflow-controller` starts, not `/usr/bin/python3`, which cannot import `controller` under `-I` or without `PYTHONPATH`, and not the shared install's) under that same `env -i` environment and print `settings.resolve_path()`, `runtime.resolve_runtime_root(...)` with its ladder row, `notify.find_credentials()` (`configured` is false and `tried` lists only paths under `$S`), the Claude configuration directory `controller/cli.py:1411` resolves, and `Path.home()`; every path must lie under `$S` and `configured` must be false. - **D6. A diagnostic that cuts text cuts it where the requirement is, not where a word happens to repeat (#84, #93).** `_worker_report` cuts a long report from the last `unmet:` that is followed by a requirement. When no `unmet:` qualifies it does not look at `unmet:` again for the first choice: it cuts at the first requirement the policy names (`_POLICY_REQUIREMENTS`), then, if none is named, at the last `unmet:`, then at the first word `unmet`, as today. So a trailing `unmet: see above` after a named requirement beyond character 400 cannot hide the requirement. "Followed by" means the next non-space character after `unmet:` is `[`, or the text from there up to the next `;` or the end starts with a name in `_POLICY_REQUIREMENTS`; a mention of `unmet:` followed by a requirement name only much later does not qualify. Row 38f's stop text is a preamble followed by its unmet entries joined with `; ` (`scripts/workflow_protocol.py:1868-1873`), e.g. `the automatic acceptance gate awaits a pull-request fact: ci_green: the checks are pending`. `pending_checks` therefore recognises the `ci_green` requirement as `ci_green: ` at the start of the text, or right after `: ` or `; ` where that follows the preamble or a previous entry's end; a `ci_green` that sits inside another entry's detail (for example a `pr_fact_current` detail that mentions the word) is not the requirement. Neither rule changes the outcome for today's Workflow wording (the single-entry `CI_TEXT` still waits); each closes a misreading that a later wording could cause.
- **D7. A flaky test is explained before it is changed (#82).** The exit -14 (`SIGALRM`) is reproduced under CPU pressure (pinned to two CPUs, several copies in parallel, as for the earlier CI flakes) and the process that returned it is identified from its captured output before any change. The lead in the issue (a guarded process that re-execs under an interval timer) is a hypothesis, not a finding. If the cause is found, the fix removes it and a test shows it; if the cause is in `controller/` code rather than in the tests, CP3 (tests only) does not cover the fix and the plan is amended. The followers run as `python -m controller … follow` through `process_fixtures.popen_bounded` behind GNU `timeout -s KILL`, not under `PARENT_GUARD`, so the `timeout` wrapper's own signal handling is a second place to look. If it is not reproduced within a bounded effort, the test is changed to say which follower ended and with what stderr, no guess is committed as a fix, and #82 is left open with the new diagnostic noted on it rather than closed; that outcome is recorded at acceptance as a deferred item.
- **D8. Every test fix and every behaviour fix must still fail on the defect it guards.** For the changes that alter behaviour (#79, #83, #84, #93, #94, #91) the milestone shows, by restoring the old behaviour in a scratch copy, that the new or changed test fails without the fix. Two changes preserve behaviour and cannot be shown failing: #86 (a docstring) and #95 (an always-true `getattr` becomes a constructor argument; `Context.forge` sets `vet_root` to `repo_root` before and after). Their done is stated apart: for #86 the docstring names all five elements; for #95 the existing `test_the_production_context_vets_the_gh_it_builds` still passes, a new case shows a `GhForge` built with `vet_root=` has it set at construction, and the `getattr` is gone.
- **D9. Documentation changes with the behaviour, in place.** The pages and guides that describe a changed behaviour are edited in place, with no narrative of the change; the closing roadmap and `docs/ACTIVE_MILESTONE.md` records go in the acceptance, as for every milestone.

## Risks

- **Haiku may not complete a plan approval (CP4, D5).** The unit tests cannot show it. The real check is in the functional review; if it fails the milestone stops for an owner decision, and the worst outcome of a weak run is a refusal or a failed job, never a recorded approval whose requirements are unmet (D3).
- **A pinned `satisfy-gate` entry changes meaning (D4).** An owner who set one for all three stages now sets it for two. The runtime guide says so, and so do the release notes written after the release (as for every release); the lane's own routing file has no entry, so it takes the new built-in routes.
- **#82 may not reproduce (D7).** A flake that needs a rare ordering may not appear in a bounded effort. The plan then ships the diagnostic and leaves the issue open instead of closing it on a guess; the pull request body closes eleven issues in that case.
- **Eleven small changes in one pull request.** Each is independent and the checkpoints are by kind. If CP2 grows past one session it is split by amending the plan, not by dropping an issue.
- **No `docs/TECHNICAL_DECISIONS.md` "Open decision" row is touched** (the file does not exist in this repository).
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages. The declaration is the previous milestone's reviewed classification with this item's ids and wording; every path the checkpoints name is classified.
