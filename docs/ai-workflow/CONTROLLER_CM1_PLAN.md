## Goal

Today the Codex adapter declares one model, `gpt-6.1-sol`, and `routing.check_route_values` refuses any other model unless the operator adds it to `harness.models`. The owner wanted `gpt-6.1-terra` and had to edit a private settings file. After this item a route that names a model the adapter does not declare makes the Controller ask the Codex CLI what it lists (`codex debug models`), keeps the answer in a cache with a timestamp, and accepts any listed model; the pinned list is the floor when the lookup fails. A model that is still unknown is refused with a message that names every accepted model and where each came from, and the setting that adds one.

This item builds one mechanism: the lookup and its use by the route check. The read-only command that prints the accepted models (item scope 2) and the "unpriced" report for a model without a price entry (item scope 4) are follow-ups, as the item page's own split suggestion says and the sizing rule asks.

## What exists

- **The declaration.** `controller/harness.py` `CODEX` has `models=("gpt-6.1-sol",)` and `efforts=("high", "xhigh")`. `CLAUDE_CODE` declares seven models and five efforts. The `harness.models` setting (`controller/settings.py`, `HARNESS_MODELS_KEY`) adds models per harness name.
- **The route check.** `controller/routing.py` `check_route_values(role, harness_name, model, effort, extra_models)` raises `ValueError` when the model is in neither the adapter's list nor `extra_models[harness_name]`. `RoutingOptions.__post_init__` calls it for each role's resolved route and each later entry of the fallback chain, and wraps the error in `RoutingConfigError` (exit 20) with `evidence` holding the role, harness, model, effort and sources; a model refusal ends with `; add a model the harness accepts with the harness.models setting`.
- **The construction point.** `controller/cli.py` `_routing_options(args)` builds the options from the effective settings (`harness_models` from `harness.models`); `cmd_explain`, `cmd_step` and `cmd_run` call it and each has the runtime root.
- **The source.** `codex debug models` (codex-cli 0.167.0) prints JSON `{"models": [...]}`; each entry has `slug`, `visibility` (`list` or `hide`), `supported_in_api` and `supported_reasoning_levels` (the item page records a sample).
- **Primitives.** `review.run_bounded` runs a command under a hard deadline; `runtime.write_json_best_effort` and `runtime.read_json` read and write a file under the runtime root. `tests/test_write_containment.py` scans `controller/` for write calls outside `runtime.py`.

## Decisions

- **D1. Look up only when a route needs it.** The lookup runs when `RoutingOptions` refuses a model for a harness that has a lookup (today `codex`). A configuration whose models are all declared or added never launches `codex`, so ordinary runs, tests and the default routing are unchanged. `cli._routing_options` builds the options once without a lookup; on a `RoutingConfigError` whose evidence marks a model refusal (`field: "model"`, with `harness`), it looks the models up for that harness and builds the options again with them. A second refusal is raised as is, so it carries the full list. **`explain` never runs the lookup and never writes** (it stays read-only, as `cmd_explain`'s docstring and the pages `docs/guide/commands.md`, `docs/guide/troubleshooting.md`, `docs/common-problems.md` and `docs/run.md` say): `cmd_explain` calls `_routing_options(args, runtime_root, allow_run=False)`, which passes `allow_run=False` to `lookup`, so the answer comes from the cache only (`cache` or `stale`) or is `not looked up` when there is none, and a route still refused is swallowed as today. `step` and `run` call it with the default `allow_run=True`.
- **D2. Discovered models add to the declared list, never replace it.** `RoutingOptions` gains `discovery`, a mapping from a harness name to a `ModelDiscovery` record (its `models`, `source`, `fetched_at` and `reason`), empty by default and frozen like `harness_models`. **The record type and the source names live in `controller/routing.py`, not in `model_discovery`**: `routing.py` defines the frozen dataclass `ModelDiscovery` and the string constants `SOURCE_CACHE`, `SOURCE_DISCOVERED`, `SOURCE_STALE`, `SOURCE_NOT_LOOKED_UP`, `SOURCE_UNAVAILABLE` and `SOURCE_UNSUPPORTED`. `model_discovery` imports `routing` for them and builds the record; `routing.py` never imports `model_discovery`, because `model_discovery` needs `review` (D5), which comes after `routing` in `DEPENDENCY_ORDER` (`tests/test_package_structure.py` rejects an import of a later module, in a function or under `TYPE_CHECKING` too). `cli.py`, last in the order, imports both. The record, not a bare tuple, is what lets the refusal of D6 tell `not looked up` from `unavailable` from `stale`, and it carries the reason and the time. `check_route_values` receives the union of each record's `models` and `harness.models` as `extra_models`; `cli._routing_options` fills `discovery` from the lookup. A pinned model is therefore never newly refused by a lookup that returns less.
- **D3. Only `visibility: "list"` counts.** A `hide` model (`gpt-reserve`, `codex-auto-review`) is internal; routing to one needs the `harness.models` setting, which stays the explicit way. A slug must be a non-empty string that does not start with `-` (the rule the settings file applies); anything else makes the whole answer unreadable. An answer with no listed model is unreadable too.
- **D4. The cache is `model-catalog/<harness>.json` under the runtime root.** It holds `schema_version`, `fetched_at` (UTC, ISO 8601) and `models`. It is fresh for 24 hours (a module constant). A fresh cache is used without running `codex`; a stale or absent one runs the lookup; a successful lookup rewrites the file through `runtime.write_json_best_effort` (a failed write is ignored: the answer is still used). A cache that is not JSON (`json.JSONDecodeError`, `OSError` from `runtime.read_json`), is not an object, has another `schema_version`, has a `fetched_at` that does not parse as UTC ISO 8601, or has a `models` entry that fails the D3 slug rule counts as absent: the lookup runs and rewrites it, and no exception reaches the caller. A `fetched_at` later than `now` makes the cache stale, never fresh. With `allow_run=False` (D1) the lookup runs nothing and writes nothing: a fresh cache answers `cache`, a stale one `stale`, and an absent or invalid one `not_looked_up`. When the lookup fails and a stale cache exists, the stale models are used and the refusal names that they are stale; with neither, only the declared and added models are accepted and the refusal names the reason.
- **D5. The lookup is a bounded, minimal read.** It resolves `codex` with `review.resolve_binary(review.CODEX.default_binary)`, the resolver a launch uses, so the listed models belong to the `codex` a launch would run. It runs `<codex> debug models` through `review.run_bounded` with a 20 second deadline and the runtime root as the working directory. The environment is exactly `PATH` (the binary's directory, its interpreter's directory from `review.interpreter_dir`, then `review.SYSTEM_PATH`, so the `node` the launcher needs is found), `HOME` and `CODEX_HOME` (both taken from the Controller's own environment; a variable the Controller does not have is left out, never set to an empty string, because `codex` then falls back to `~/.codex`) and `WORKFLOW_CONTROLLER_OWNERSHIP` (the inherited tags plus a tag unique to this call, `model-lookup-<pid>-<random hex>`, joined as `review.child_environment` joins them, so `run_bounded` can kill a native child that left the process group on a deadline; the tag is never a constant, because `_kill_owned` kills every process of the user whose environment holds that exact value, and a fixed tag would let one Controller's post-exit sweep kill another Controller's running lookup, as every other launch avoids by using its unique job id); no credentials of any other kind. `run_bounded` reads the whole output and caps nothing, so an answer over 1 MiB is refused by a size check after the read. A binary that cannot be resolved, an `OSError` from the spawn (a missing runtime root, `EACCES`), a non-zero exit, a timeout, an oversize or malformed answer is a failed lookup with a one-line reason, never an exception to the caller.
- **D6. The refusal names the accepted list and its sources.** The `RoutingConfigError` message keeps its present text and its tail (`add a model the harness accepts with the harness.models setting`) and gains `(accepted for <harness>: declared [...]; discovered [...] | not looked up | unavailable: <reason> | stale cache from <time> [...]; added by harness.models [...])`, built in `routing.py` from the `ModelDiscovery` record of D2 by its `source` constant: `discovered` and `cache` give `discovered [...]`, `not_looked_up` gives `not looked up`, `unavailable` gives `unavailable: <reason>`, `stale` gives `stale cache from <fetched_at> [...]`. A harness without a lookup (`unsupported`, today `claude-code`) leaves the discovery part out, so its refusal keeps today's text plus `(accepted for claude-code: declared [...]; added by harness.models [...])`. The evidence gains `field` and `accepted` (the three lists).
- **D7. Efforts stay declared.** The adapter's effort list is not looked up in this item (the item page's note that it could be). `docs/items/workflow-controller-cm1.md` records it as a follow-up with the command and the price report.
- **D8. Tests are hermetic.** No test runs a real `codex`: the lookup takes the runner and the resolver function as parameters, and the CLI-level tests stub the one module attribute the CLI calls. A test of a refusal that names an unknown Codex model without a stub is changed to stub it.
