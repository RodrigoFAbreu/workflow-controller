Pull request title: `chore: render a Workflow command for a Codex worker (H4a, #242)`

## Goal

Turn a shared Workflow command file (`.claude/commands/<name>.md`, whose contract is `docs/ai-workflow/COMMAND_FILES.md`) and an argument string into the prompt a Codex run would be sent, with no per-harness copy of any command file. The renderer applies exactly what the contract tells an adapter to do for each frontmatter key, substitutes `$ARGUMENTS` as the contract says, and refuses the user-only commands. It launches nothing: the Codex launch is H4b.

## What exists

- `docs/ai-workflow/COMMAND_FILES.md`: the file format (frontmatter of single-line `key: value` pairs between two `---` lines; the body is the prompt), the key table (`disable-model-invocation` and `state_writer` are Honour, `review-subject` is Carry, `description` and `argument-hint` are Hint), the `$ARGUMENTS` rules (verbatim, every occurrence, body only, empty string when none; "an unknown key is ignored and never fails the launch") and the nine user-only commands ("The agent must never invoke any of them on the user's behalf, including as a step of another command's execution, whatever the flag says").
- `controller/decision.py`: `carries_disable_model_invocation_flag(text)`, `carries_user_confirmation_guard(text)`, `classify_command_files` and `derive_user_only_commands(commands_dir)` (the union of the two recognisers, fail closed), `MissingCommandsDirectoryError` for an absent directory.
- `controller/worker.py`: `USER_ONLY_COMMANDS` (a literal four-name copy) and `_assert_not_user_only(task)`, the whole-token scan `launch` runs on a task before any process starts; it raises `UserOnlyCommandError` (code `USER_ONLY_COMMAND`, `controller/errors.py`).
- `controller/harness.py` and `controller/worker_launch.py`: `CODEX.roles` is `(REVIEWER, FUNCTIONAL_TESTER)`, `LAUNCHERS` holds Claude Code only, and a test requires its keys to equal the adapters that declare the worker role. This item changes neither.
- Today Claude runs a command natively: the task string is `/<command> <arguments>` and Claude Code reads the file itself.

## Decisions

Each decision states one principle.

- **D1. One new module, one pure function.** `controller/command_files.py` holds `render_command(name, arguments, commands_dir) -> RenderedCommand`. `RenderedCommand` is a frozen dataclass with `name`, `prompt`, `description`, `argument_hint`, `state_writer` (a bool) and `review_subject` (`bundle`, `verdict`, `none` or `None`). The function reads one file and writes nothing; it spawns no process and imports `controller.decision`, `controller.worker` (only for the user-only token scan) and `controller.errors`. Package registration is the only reference the module gets in `controller/`: `tests/test_package_structure.py` requires every module to be listed in `controller.__all__` and eagerly imported by `controller/__init__.py` (`EagerLoadTest`) in the order of its `DEPENDENCY_ORDER`, so CP1 adds `command_files` to `controller/__init__.py` (the import list and `__all__`) and to `DEPENDENCY_ORDER`, directly after `worker` (the module imports `decision`, `worker` and `errors`, all earlier). No other module in `controller/` imports it: a test searches `controller/` and allows `__init__.py` only.
- **D2. The file format is parsed as the contract states it, and a malformed file is refused.** The first line must be exactly `---`, a later line exactly `---` closes the frontmatter, every non-blank line between is `key: value` (the key matches `[A-Za-z0-9_-]+`, the value is stripped and one pair of matching quotes removed), and a duplicate key is malformed. The body is everything after the closing line's newline, unchanged. A missing opening or closing line, a line without a colon, a duplicate key, a `state_writer` that is not `true` or `false` (the contract says every command declares it), a `disable-model-invocation` that is present and not `true` or `false`, and a `review-subject` that is present and not `bundle`, `verdict` or `none` are each `CommandRenderError` with cause `malformed_frontmatter` naming the file and the line. An unknown key is ignored. `$ARGUMENTS` in the frontmatter is not substituted.
- **D3. The class of each key is applied and no more.** `disable-model-invocation: true` is refused (D4). `state_writer` is carried as a bool for the launcher to honour (H4b gives the worker the checkout and the scripts); this item does not interpret it. `review-subject` is carried unchanged. `description` and `argument-hint` are carried for display and for D5; neither changes the prompt.
- **D4. A user-only command is refused by the union of the two recognisers, before the frontmatter is parsed.** The order inside `render_command` is: the name check and the file lookup (D7), the read, the user-only refusal, the task scan, then the frontmatter parse (D2) and the substitution (D6). The refusal reads the whole file text through `decision.carries_disable_model_invocation_flag` and `decision.carries_user_confirmation_guard` and refuses when either is true, so a file the frontmatter parser would call malformed is still refused as user-only when a recogniser claims it. Only this union rule is shared with `decision.classify_command_files`, not its partition into selected, not-selected and user-only: the renderer never calls `classify_command_files` or `derive_user_only_commands`, because both raise `NoSupportedActionError` on this repository's live `.claude/commands/` (`apply-pr-review.md` is in none of the Controller's selected or not-selected sets). It raises the existing `UserOnlyCommandError` with `evidence` naming the command and the file. The set is never a copied list in this module. The refusal then reads the parsed frontmatter value (D2) as well: a `disable-model-invocation` whose value, after the quote removal, is `true` is refused as `UserOnlyCommandError` too, whatever its spelling (unquoted, single-quoted or double-quoted), because `decision.carries_disable_model_invocation_flag` recognises only the unquoted literal line and a quoted `"true"` on a file whose body lacks the confirmation guard would otherwise pass both recognisers. The earlier recogniser refusal is kept, so a file is refused if either the recognisers or the parsed value say so. The arguments are scanned against the whole user-only set, not the four literal names: the set is every file of `commands_dir` that the union refuses (the recognisers applied file by file, without `classify_command_files`) plus `worker.USER_ONLY_COMMANDS`, and an argument string with any whitespace-delimited, punctuation-stripped token equal to `/<name>` or `<name>` for a member is refused as `UserOnlyCommandError`, using `worker._task_tokens` for the tokenising so the renderer and the launch split text the same way. The use of that private function and of `worker._assert_not_user_only` (called on `f"/{name} {arguments}"`, the launch's own scan, as a second independent layer) is deliberate: they are the single tokeniser and scan the launch runs, and a test calls the scan for each name in `worker.USER_ONLY_COMMANDS`, so a rename inside `worker.py` fails a test instead of silently dropping a layer.
- **D4a. The union refuses eleven files over the live directory, two more than the contract's nine, and that is accepted for H4a.** Run over this repository's `.claude/commands/`, the union refuses the nine `COMMAND_FILES.md` lists (`accept-milestone`, `adopt-gate-policy`, `approve-review`, `archive-finished-item`, `prune-archives`, `release-checkpoint-start`, `request-plan-amendment`, `resume-implementation`, `retire-legacy-work-item`) plus exactly `recover-implementation-provenance` (it carries the confirmation guard only) and `satisfy-gate` (its body contains the literal `workflow_state.validate_policy_satisfied_confirmation`, so `carries_user_confirmation_guard` is true, although its own description calls it an automated validation and the lane runs it from workers). Refusing more than the contract requires is the fail-closed direction, so it stands. It is not a decision about `/satisfy-gate` on Codex: running it there (H4e to H4g) needs a deliberate rule change, made and reviewed in that step, and the real-directory test pins the eleven names so a Workflow release that changes either file's recogniser status fails a test instead of silently changing what Codex may run.
- **D5. "As a step of another command's execution" is a property of the agent's behaviour, and the renderer says so rather than pretending to enforce it.** The contract's sentence binds the agent, and the control it names is each command's own literal-confirmation check, which stays in the body. A body of an allowed command that mentions a user-only command (for example `/milestone-plan` names `/approve-review plan` as the next step for a person) is sent verbatim, because the body is the prompt and an edited body would be a per-harness copy. The renderer therefore guarantees three things, each tested: it never renders a user-only command as the requested command; it refuses an argument string that names any of the eleven (D4); and it never alters the body. What stops a Codex agent from running a user-only command named in a body is the body's confirmation check plus the launch policy of H4b and the safety review of H4e and H4f, which this item records as out of scope and carries into the guide text. This item does not scan bodies: every allowed body mentioning them is documentation, and a scan would refuse most of the lifecycle.
- **D6. `$ARGUMENTS` is substituted in the body only, verbatim and in one pass.** Every occurrence of the literal token in the body becomes the argument string exactly as given (including the empty string, and an argument string that itself contains `$ARGUMENTS`, which is not substituted again). The substitution uses `str.split` and `str.join`, not `str.replace`, because `tests/test_write_containment.py` flags any call named `replace` in `controller/`. The renderer does not append the arguments after the body (the contract's rule for bodies makes appending unnecessary). Two fail-closed cases keep an argument from being dropped silently: a non-empty argument string for a command whose `argument-hint` is absent or empty, and a non-empty argument string for a body with no `$ARGUMENTS` token, are each `CommandRenderError` with cause `arguments_not_accepted`.
- **D7. Names are checked, files are looked up, the directory must exist.** `name` is a bare command stem matching `^[a-z0-9][a-z0-9-]{0,63}$` (a leading `/` is not accepted, so a path cannot be built from it). A name that does not match, or whose `<commands_dir>/<name>.md` is not a file, is `CommandRenderError` with cause `unknown_command`; an absent `commands_dir` is the existing `MissingCommandsDirectoryError`; an unreadable file is `CommandRenderError` with cause `unreadable`. The closed set of causes is `unknown_command`, `unreadable`, `malformed_frontmatter` and `arguments_not_accepted`; user-only is the existing class.
- **D8. Not wired in.** The module is only registered in the package (D1). `harness.CODEX.roles` is unchanged, `worker_launch.LAUNCHERS` is unchanged, `worker.py`, `decision.py`, `review.py`, `codex_bridge.py`, `codex_tester.py` and the Claude launch are unchanged, and there is no setting, option, exit code or gate. A test pins that Codex still does not declare the worker role. H4b declares it and registers the launcher.
- **D9. Release type.** `chore:`. The module has no caller and the new error class is reached only by the module. If review finds an operator-visible change, the title becomes `feat:` before the plan is approved, not after.

## Risks

- **The renderer cannot make the contract's "nested invocation" sentence true by itself.** D5 says so and names what carries it; the guide text repeats it so that H4b and H4e do not assume the renderer is the control.
- **A new command file the Controller does not classify.** `decision.classify_command_files` already fails closed on a file it cannot classify; the renderer refuses a user-only file by the same recognisers and renders any other well-formed file, so a future Workflow release that adds a command changes the real-directory test's counts, not the renderer.
- **The refused set is wider than the contract.** D4a: `recover-implementation-provenance` and `satisfy-gate` are refused because their bodies carry the confirmation guard. The direction is fail closed; a later step that wants `/satisfy-gate` on Codex must change the rule on purpose, and the pinned test makes a quiet change impossible.
- **Frontmatter strictness.** D2 refuses a `state_writer` that is absent. All 25 shipped commands declare it today (the real-directory test shows it); a future release that dropped the key would be refused rather than launched without knowing whether the worker writes state.
- **Out of scope:** the launch (H4b), job records and reaping (H4c), usage windows (H4d), routing review roles to Codex (H4e), `milestone-implement` on Codex (H4f), the remaining roles (H4g), any change to the Claude worker launch, the Codex reviewer or tester, settings, options, exit codes or gates.
