## Goal

At the two manual external review gates, the Controller stops today (`GATE_BLOCKED`, exit 10) and a person or a lane script runs the cross-model review by hand: build a disposable copy, run `codex exec`, check the verdict's header lines against `MANIFEST.md`, paste it into the feedback file, resume. That work is outside the Controller, so its Codex usage is not counted by the usage budget (ROADMAP 11.6 lists it as a gap), and a mistyped content id (C6, rev 8) left a run stuck.

After this milestone a repository that opts in (`reviewer.harness = "codex"` in its settings file) gets that review from the Controller itself:

1. At `plan.review.external` (row 14) and `implementation.review.external` (row 28) only, instead of stopping, the Controller admits a Codex job against the usage budget, runs a **review-only** Codex worker in a disposable copy of the worktree, and checks the verdict it produced.
2. A verdict whose header lines equal the bundle's exact values is ingested through the Workflow's own `record-external-result` (protocol section 5.6; obligation 8: the orchestrator never writes the feedback path), recorded with `--run-ref codex:<job id>`. The phase moves on, so no Claude `/record-manual-*` worker is needed for these rows.
3. The Codex job is a first-class job record with its own route (harness, model, effort), usage reservation, completion, and `usage` block. Admission goes through the usage gate like a Claude job: a hold at admission pauses and resumes exactly like one (D8). A limit that hits *during* the job is different and is stated once in D8: the job ends `INCOMPLETE`, `run` ends with exit 35, and a new `run` re-admits.
4. Without the setting, behaviour is what it is today: every gate decision, route, status, exit code and usage decision is unchanged, and no job record changes. The only intended exceptions are two additions that do not depend on the opt-in and are pinned by name: the settings file gains the five `reviewer.*` rows with their defaults (settings generation 6, recorded in `controller_settings`), and `WORKER_LIFECYCLE_NOTE` gains the `command rm -f` / `command cp -f` line (D11), which changes the production argv of every Claude worker by that one line.

It is "the smallest slice of section 5": one new **review-only** seam (a verdict-producing harness behind a small interface, one implementation, Codex). Implementation workers stay Claude-only; routing roles are unchanged; the Workflow still never names a provider (it says `external`; the Controller chooses the harness).

Out of scope: a Codex implementer or planner, harness fields in `routing`, the functional review (C10, which will reuse the seam), a mid-job Codex limit recogniser that waits for the reset in place (a limit ends the job `INCOMPLETE` and `run` with exit 35; a new `run` re-admits, D8), repositories on a Workflow without Orchestration Protocol v1 (they keep today's gate), and stuck-worker detection (C12).

## Decisions

**D1. Opt-in, off by default (decision for the user).** A review costs the user's Codex allowance and runs a Codex model that can execute commands inside a `workspace-write` sandbox confined to a disposable copy, approval policy `never`, command network access off and an environment allowlist (D4); the worker is not started with `--approve-for-me`. Turning it on for everyone would spend allowance nobody asked to spend. The setting is `reviewer.harness`, unset by default. This is the one choice in the plan the user may want the other way round; the plan states it so approval is informed.

**D2. Where it hooks in: the protocol path only, rows 14 and 28 only.** `protocol_decision.from_answer` turns `external_gate` into a `HumanGate` today. `execute_step` gains one branch before it records that gate: when the answer is `external_gate` whose `action.id` is `plan.review.external` (row 14) or `implementation.review.external` (row 28) **and** the decision's `snapshot.phase` is `AWAITING_MANUAL_EXTERNAL_PLAN_REVIEW` (for `plan.review.external`) or `AWAITING_MANUAL_EXTERNAL_IMPLEMENTATION_REVIEW` (for `implementation.review.external`) **and** a reviewer harness is configured, it runs the review job instead of `_no_launch_record(GATE_BLOCKED)`. *The discriminator:* `action.id` alone cannot separate the rows, because row 21 also emits `plan.review.external` and rows 31a and 35 also emit `implementation.review.external` (`ORCHESTRATION_PROTOCOL.md` lines 741, 757, 761, against rows 14 and 28 at lines 730 and 750). Obligation 4 is kept: the action is still chosen by `action.id` and `arguments`; the phase only narrows *whether the Controller couriers it*. The phase is read from the decision's `snapshot` (always present; `snapshot` is defined in section 5.4, `next-action`), not from `row`, because section 5.5 lets a decision omit `row`; an answer whose snapshot phase is not one of those two phases, or has no snapshot, stays a gate. The other rows whose `satisfied_by` is a review verdict -- 21 (`1`), 31a (`1`/`2.1`, `review_block_pinned`) and 35 (`1`/`2.1`) -- are feedback-only rows in protocol section 5.6 (the ingest records nothing and the phase does not move) and sit in other phases; they are pinned **unchanged** (the gate stops as today) by CP3 tests with the harness configured, each answered with its own `action.id` and phase. Any other human or external gate, an *unset* harness, or a target without the protocol is unchanged. An *unknown* harness name is not "unchanged": it refuses (D3). `AUTOMATIC_WORKER_ROLES` is not widened: `external` is still never a Claude worker, so the blocked-role refusal stays exactly as it is for everything else.

*Protocol obligation 5 (a consumer runs an `automatic` action only, never a gate's action; section 5.5: a gate is resolved outside the orchestrator's run, by a person or by `record-external-result`).* The reading this plan relies on, recorded here and in ADR 0013: the action of an `external_gate` is **produce a verdict by a party other than the orchestrator's own harness and hand it to the Workflow**. The Controller does not run the gate's action as an `automatic` action and does not resolve the gate itself. A Codex process of a distinct harness and vendor, in a disposable copy, produces the verdict; the verdict enters only through `record-external-result`, which applies every Workflow guard (content id, distinct reviewer models, stage already recorded) and may refuse; the Controller then calls `next-action` again (obligation 7) and follows whatever the Workflow answers. The Controller is the courier for an external party, as a lane script or a person is today, not the party that satisfies the gate. **Acceptance condition (CP1 does not pass without it):** the Workflow side confirms or clarifies the reading -- an issue on the Workflow repository whose answer is recorded in ADR 0013 (and in the CP1 checkpoint evidence), or a protocol clarification that names a distinct-provider courier as admissible. The installed protocol says consumers never run a gate's action; choosing a distinct provider does not by itself amend that contract. If the answer is that the reading is not allowed, the milestone stops at CP1 instead of shipping a design that rests on an unstated reading; D1's opt-in keeps the default untouched in the meantime.

**D3. The seam.** New `controller/review.py` defines `ReviewHarness` (a frozen description plus three functions: `argv(...)`, `end_readings(...)`, `verdict_family`) and a closed registry `HARNESSES = {"codex": CODEX}`. A harness only produces a verdict file from a bundle; it never touches the repository, the state file or a job record. Adding a harness later is a registry entry plus its fake. An *unset* harness keeps today's gate (D2); an *unknown* name in the settings file refuses at the first review step with a clear error (not silently ignored: a mistyped harness must not fall back to a human gate and look configured).

**D4. Review-only, in a disposable copy.** The worker runs with `-C <copy>`, where `<copy>` is `<runtime>/reviews/<job id>/tree`, built from the worktree excluding `.git`, `.controller`, the resolved runtime directory by path (so a `--runtime-dir` inside the worktree cannot copy itself), `__pycache__`, build directories and `*.egg-info`, and removed on every exit path including failure. **`.git` is never copied.** In a linked worktree `<worktree>/.git` is a `gitdir:` file pointing into the main repository's `.git/worktrees/<name>`; copying it would let Git commands that Codex runs in the copy write the real object store, refs, config and that worktree's index. The copy instead gets its own repository: after the tree is copied, `git init` plus one commit of the copied tree's current bytes (the worktree's bytes, not the base commit's tree, so `git diff` in the copy shows nothing and the review sees what the worktree holds), with `GIT_CEILING_DIRECTORIES` set to the copy's parent for the Codex process so no Git command can discover an enclosing repository. (The review reads files and `git diff` against that private commit; it needs nothing from the real history. If a bundle's instructions need real history, the bundle carries it as files.) The verdict goes to `<runtime>/reviews/<job id>/verdict.md` (via `-o`). *Detection (additional to the enforced boundary below, never instead of it).* The Controller records the real repository's `HEAD`, `git status --porcelain`, `git for-each-ref` output, a manifest of every non-ignored worktree file (path, size, SHA-256 -- so a second edit to an already modified file is seen, which unchanged `status --porcelain` cannot show) and the protocol's `basis.state_identity` (from `next-action`, obligation 8: not a read of the state file's path) before and after, and compares the repository's `config` file digest as well as a digest of the real feedback directory, located with `resolve-artifact review_feedback` rather than a composed path (a legacy `feedback_layout` item can resolve to the flat `.ai-review/feedback/`; `.ai-review/` and `.controller/` are gitignored, so `status --porcelain` cannot see a write there; the bundle itself is re-verified at ingest); any difference voids the verdict (`INCOMPLETE`, the verdict is never ingested). The bundle and the cited sources are inside the copy.

*Tool surface: an allowlist (fail closed).* The installed Codex (`codex-cli 0.162.1`) ships many built-in features that are on by default and are not operator-configured: `browser_use`, `browser_use_external`, `browser_use_full_cdp_access`, `computer_use`, `in_app_browser`, `apps`, `plugins`, `remote_plugin`, `skill_mcp_dependency_install`, `image_generation`, `multi_agent` and others. A browser or CDP tool reaches the network the way built-in web search does, a computer-use tool acts on the desktop outside the command sandbox, and plugin, remote-plugin and skill-dependency installation are further tool and network paths. Naming them one by one would leave the boundary open to the next default-on feature a Codex update adds, so D4 states the surface as an allowlist: `review.CODEX` carries a short, named `TOOL_ALLOWLIST` (the shell/exec tools, file read and patch tools a reviewer needs, and the inert non-tool features the pre-step capture shows are required for `codex exec` to run), and `review.CODEX.argv` passes `--disable <feature>` for **every feature the pinned Codex version reports as enabled that is not on the allowlist**. The disable set is derived once, from the captured `codex features list` of the pinned version (CP2's operator pre-step, D12), and stored as a pinned constant beside the allowlist; it is part of the pinned set of overrides below. **Drift fails closed:** at launch the Controller runs `<reviewer.binary> features list` (no model call, no allowance) in the same allowlisted environment and refuses the launch (`FAILED`, nothing started; the preflight is itself a Codex invocation that loads inherited configuration, so it runs with the same `notify`-clearing, hook-disable and no-profile overrides, in the same allowlisted environment and with the same Controller-written minimal home as the review) when a feature is reported enabled that is neither allowlisted nor in the pinned disable set -- a feature added or turned on by a Codex upgrade stops the review until a person extends the allowlist or the disable set. The argv also passes `--strict-config` (or the equivalent the pre-step shows the installed Codex honours) so an unrecognised override fails closed instead of being ignored; the pre-step records whether the installed Codex rejects an unknown `--disable` name, and if it does not, the launch check above is the only guard and the plan relies on it.

*Enforced boundary (prevention, not detection).* The worker is not started with `--approve-for-me`. `review.CODEX.argv` is the only constructor of the Codex command line and sets, by explicit overrides that outrank the operator's own Codex configuration: the `workspace-write` sandbox with the copy as the working root, **no additional writable roots** except the private disposable `TMPDIR` named below (so a reviewer that runs the test suite can create temporary files), the real temporary-directory writable roots (`/tmp`, the platform temp root) excluded, **command network access off** (Codex itself still reaches its model endpoint; commands it runs cannot), approval policy `never` (no escalation prompt can widen the sandbox), **no MCP servers or other configured external tools, by a closed configuration boundary and not by an override** (on the installed Codex `-c mcp_servers={}` was probed and merges with, rather than replaces, the inherited server table, so an inherited MCP server command still runs at session startup despite the read-only/workspace sandbox, approval `never`, cleared `notify` and disabled hooks and plugins, and disabling feature flags does not exclude it; an override list therefore cannot exclude a server the operator adds later under an arbitrary name): the review and the `features list` preflight always run with `CODEX_HOME` set to a Controller-written minimal home under `<runtime>/reviews/<job id>/codex-home/` that the Controller builds with only a private writable copy of the operator's credential file (so Codex's own token refresh works; see the paragraph below), a `sessions/` directory for the run's rollout, and a Controller-written `config.toml` (Codex then writes its own state entries into the home during the job's up to four invocations; the check below is defined over what Codex *loads*, not over the directory's exact contents) containing exactly the pinned overrides and **no** `mcp_servers`, `hooks`, `notify`, `profiles`, `plugins` or project-trust table, so no inherited server, hook, profile or notify entry exists to be disabled, including one added after the capture; project configuration layers are excluded too, because the disposable copy is never marked trusted in that home and the Controller deletes any `.codex/` directory from the copy before launch (the reviewer's inputs are the bundle and the tree, not repository-local Codex configuration); before **each** Codex invocation, `mcp list` itself included (the startup-load check runs first; the `mcp list` check then runs before the `features list` preflight and the review launches; `mcp list`, `features list`, the review and D5's bounded retry alike) the Controller verifies the home as it stands, **not** rebuilt between invocations, against the invariant *what Codex loads at startup is exactly the Controller's* (see "The minimal home's startup-load check" below) and runs `<reviewer.binary> mcp list` (no model call, no allowance) in that home and environment, refusing the launch (`FAILED`, nothing started) unless it lists zero servers, **a closed tool surface** (an allowlist, below, never a list of named escapes), **all hook sources disabled before startup** (startup, plugin and any other hooks inherited from the operator's Codex configuration are switched off by explicit overrides; the installed Codex warns that a trusted hook "can run outside the sandbox", so a hook is a path to real-worktree, feedback, state or runtime writes and network access that command sandboxing does not cover, and it must be excluded rather than trusted), **inherited notification commands disabled** (the `notify` command of the operator's Codex configuration, at top level and in any profile the configuration selects, is an external program Codex runs on turn events outside the command sandbox; the installed Codex reads it through a legacy path separate from hooks, and `notify` is not a feature, so neither the hook-disable override nor the feature allowlist is shown to exclude it: `review.CODEX.argv` overrides it to an empty command with `-c notify=[]`, and no `--profile` is passed, so profile-selected executable configuration is never chosen by the Controller; the minimal home above is the only *user* configuration loaded, so no operator profile, `notify`, `hooks` or similar executable entry is read from the operator's files, the layers outside the home are handled by the effective-configuration boundary below, and the empty override is a second layer that the D12 pre-step records as honoured or not), **built-in web search off** (command network denial does not specify it), and an explicit model, effort and non-fast service tier (D10). The process environment is an allowlist built by the Controller: a private `HOME`/`TMPDIR` under `<runtime>/reviews/<job id>/`, the Controller-written minimal Codex home (a private credential copy and a `sessions/` directory, owned and settled as the paragraph below states; the operator's hook, plugin, MCP and `notify` sections and any profile-selected equivalents are never loaded), and none of the Controller's own variables except the ownership tag `OWNERSHIP_VAR` (`WORKFLOW_CONTROLLER_OWNERSHIP`, D9; the one Controller variable passed), forge or cloud credentials, or `.controller` paths. Real worktree, feedback directory, Workflow state and Controller runtime data are therefore outside every writable root. A launch is refused (`FAILED`, nothing started) unless `argv` reproduces the pinned set of overrides (sandbox, writable roots, command network, approval, hooks off, `notify` cleared, the minimal home with no `mcp_servers`, web search off, every non-allowlisted feature disabled, model, effort, tier): a contract test compares it with the captured real invocation, and the D12 operator pre-step also captures one sandbox probe (a tiny real `codex exec` asked to write outside the copy and to open a network connection from a command, both expected to be denied, launched from the Controller-built minimal home and the stripped copy, while the operator's own home is seeded with an arbitrarily named MCP server, a trusted startup hook and a `notify` command (top level and in a selectable profile) and the copy's project `.codex/config.toml` with an MCP server, each carrying a scripted command that would write a marker outside the copy and open a connection: no marker may appear and no connection may be made, and the same probe launched from the operator's own home with `-c mcp_servers={}` alone is recorded as the counter-example, showing the inherited server still runs (the reason for the minimal home), and web search must be reported off, plus one browser or computer-use action, expected unavailable) as a fixture. If the installed Codex cannot be shown to deny those writes, CP2 stops at its boundary reporting the pre-step as open and the harness stays unregistered; it never falls back to detection alone. The fake honours the same flags (it refuses writes outside its working root and records the attempt, runs a scripted "inherited hook" from its isolated configuration home only if the hook-disable override is absent, runs a scripted inherited `notify` command (top level and profile-selected) only if the `notify` clearing is absent or a profile is passed, runs every scripted MCP server of the home it is given (an arbitrarily named inherited one, one added after capture, and one in a project `.codex/config.toml` in the copy) unless that home is the Controller's minimal one with the project layer removed, and reports `mcp list` truthfully for the home in use, records a web-search use only if the web-search-off override is absent, and records a use of any non-allowlisted tool family (browser, computer use, plugin install, image generation, sub-agent) whose `--disable` override is absent) so executable tests prove the Controller passes the boundary and detects a breach; no test spends Codex allowance.

*The effective-configuration boundary (round-13 finding I3).* The dedicated home excludes the operator's user file and nothing else. The installed protocol's `ConfigLayerSource` documents further layers (packaged defaults, system, MDM, enterprise/cloud-managed and legacy-managed), the installed diagnostics name `/etc/codex/config.toml`, `/etc/codex/requirements.toml` and `/etc/codex/managed_config.toml`, and the exposed `Config` schema permits additional properties, so no per-key exclusion proof exists and D4 does not claim one. It states six controls instead, each a pinned constant of `review.CODEX` recorded by the D12 pre-step for the pinned version, each failing closed (`FAILED`, nothing started), all applied together to **every** invocation: `mcp list`, `features list`, the initial `exec` and D5's bounded retry.

(a) **Configuration-source inventory `CONFIG_SOURCES`.** One entry per layer category the pinned Codex reports (operator user file, profiles and `$CODEX_HOME/<name>.config.toml`, packaged defaults, system `config.toml`, `managed_config.toml`, `requirements.toml`, MDM, enterprise/cloud-managed, legacy-managed, project and ancestor `.codex/config.toml` with `projects.*.trust_level` and `project_root_markers`, execpolicy `.rules`, `AGENTS*.md` and instruction files, skills, plugins) with exactly one disposition: *excluded by construction* (the dedicated home, the removed `.codex/`, no trust entry, no profile argument); *absent-or-empty required* (every file-backed layer outside the home, such as the three `/etc/codex/` files: the Controller reads each path, and a path that exists with content, or that it cannot read, refuses the launch, naming the path); or *validated after composition* (layers the Controller cannot read, MDM and cloud-managed policy, which control (b) checks). A layer category the pinned Codex reports that is not in the inventory refuses the launch like an unlisted feature, and the pre-step records whether the installed Codex offers a relocation variable or flag for the system layers.

(b) **Effective-configuration check, before anything can execute.** The pre-step records the one read-only command the installed Codex offers that composes all layers and prints the composed values with their source layer *without* starting a server, hook, notification command or provider authentication command (and which flags that command, specifically, accepts: `codex features` rejects `--strict-config`, so each invocation kind has its own pinned flag list and none is assumed to accept another's). Before each invocation the Controller runs it in the same home and environment and compares the composed values with `EFFECTIVE_POLICY`: `model_provider` equals `openai`; no custom `model_providers.*` entry, no provider `auth` command, and `openai_base_url`/`chatgpt_base_url` unset (so the endpoint and authentication path are Codex's own, with the private credential copy); `model`, `model_reasoning_effort` and `service_tier` as D10 pins; `sandbox_mode` `workspace-write`, `sandbox_workspace_write` roots and network access as above, approval policy `never`, no `auto_review`, no `permissions`/`default_permissions` profile; `mcp_servers`, `hooks` and `notify` empty; `features` as the allowlist and disable set state; `project_root_markers` as pinned. Any difference refuses the launch, and the error names the source layer and the conflicting key and value. **If the installed Codex has no command that composes the layers without executing them, a layer that cannot be read by control (a) is excluded by an outer isolation mechanism that the pre-step shows works (for example a mount or user namespace that hides the system paths, or the recorded relocation), or the harness stays unregistered: CP2 stops at its boundary reporting the pre-step as open and never falls back to detection.**

(c) **Pinned policy in argv.** `review.CODEX.argv` also passes `model_provider="openai"` beside `model`, effort and the non-fast tier (D10), `project_root_markers=[".git"]` (the copy's own repository is the project root, so discovery stops there and no ancestor layer is read), and `--ignore-rules` where the pre-step shows the invocation accepts it. The argv comparison alone is not taken as proof that an override survived composition; control (b) is.

(d) **Exact environment membership `ENV_ALLOWLIST`.** The child environment is exactly: `PATH` (a fixed Controller value), `HOME`, `TMPDIR`, `CODEX_HOME`, `GIT_CEILING_DIRECTORIES`, `LANG`, `LC_ALL` and `OWNERSHIP_VAR` -- no pattern match and no other inherited variable. `OWNERSHIP_VAR` is the one Controller-set member: its value is the job id added to any inherited tags exactly as `controller/worker.py:1345-1346` does today, so D9's ownership recovery (`resume` finding the group by tag, CP3's spawn-before-flush replay, R7) and an outer Controller's recognition of its own descendants keep working. `PATH` is not an arbitrary fixed value: it is the directory of the resolved `reviewer.binary` and the directory of its interpreter (the `#!` line of a script binary, such as the `node` of the installed `codex.js`), followed by the system directories `/usr/local/bin:/usr/bin:/bin`; the D12 pre-step records the directories the installed Codex needs, and a binary or interpreter that cannot be resolved refuses the launch naming it. Credentials come only from the private `auth.json` copy, never from the environment. By construction this excludes inherited endpoint overrides (`OPENAI_BASE_URL`, `CODEX_AUTHAPI_BASE_URL`, refresh and revoke URL overrides), `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN` and identity-token variables, `CODEX_EXEC_SERVER_*`, `CODEX_PERMISSION_PROFILE`, `CODEX_SQLITE_HOME`, connector credentials, proxy and CA variables, shell initialisation variables and interpreter or loader injection (`LD_*`, `PYTHON*`, `NODE_*`, `BASH_ENV`, `ENV`, `ZDOTDIR`, `GIT_*` other than the ceiling).

(e) **Project-local discovery.** Besides `.codex/`, the Controller removes from the copy `.agents/skills`, `.agents/plugins` and `AGENTS.override.md` (the bundle, the tree and `AGENTS.md` stay: they are the review's inputs), and rules files are neutralised by `--ignore-rules` or, where the invocation does not accept it, by control (b) reporting no rules source.

(f) **Refusals are diagnosable.** Every refusal of (a)-(e) names the source and the conflicting effective value, so an operator whose host carries a managed configuration sees why the review will not start rather than a hung or silently re-pointed one.

The fake honours this contract: a seam stands in for the system tree (`/etc/codex/`: `config.toml`, `managed_config.toml`, `requirements.toml`) and for one managed/MDM layer, and the fake composes the layers the way the pre-step capture shows, reports the composed values and their sources through the recorded command, runs a scripted MCP server, hook, `notify` command, custom provider authentication command or permission profile from any such layer only if the launch was not refused by control (a) or (b), records the endpoint and authentication path it was given, records its environment and the sandbox roots and network policy it ended with, rejects `--strict-config` on `features` as the installed Codex does, and discovers project rules, skills and plugins from the copy (and from its ancestors) only where the removal in (e) or `project_root_markers` is absent.

*The minimal home's startup-load check (I6).* The home is a long-lived, multi-invocation directory, and Codex itself writes into whatever home it runs in (the operator's own home shows, by entry name, `history.jsonl`, `session_index.jsonl`, `installation_id`, `version.json`, `models_cache.json`, `cache/`, `tmp/`, `.tmp/`, `shell_snapshots/`, `thread-writer-locks/`, `*.sqlite`/`-wal`/`-shm` state databases, and Codex-populated `skills/` and `plugins/`), so a check of "exactly these files" would refuse the second launch, including D5's retry. The check therefore has two parts, both pinned constants in `review.CODEX` beside the feature allowlist and recorded by the D12 pre-step: (a) **configuration-bearing entries**: `config.toml` equals the pinned digest, and no other configuration, hook, rules, skills, plugin, prompt or instruction source exists in the home -- the pinned `STARTUP_LOADED` set (every entry class the pre-step shows the pinned Codex reads at startup, e.g. a second `*.toml`, `hooks*`, `rules/`, `skills/`, `plugins/`) must be absent; (b) **Codex-written state**: every other entry must be on the pinned allowlist `CODEX_STATE_ENTRIES` (the entries the pre-step shows Codex creates in an empty home during `mcp list`, `features list` and one `exec`; a directory on it is accepted only because the pre-step shows it carries no startup-loaded content in an empty home). **Codex-created `skills/` and `plugins/` content (I8)** is admitted only through a third pinned constant, the **sub-entry allowlist** `CODEX_STARTUP_SUBENTRIES`, recorded by the D12 pre-step as exact child paths (for example `skills/.system/`, `skills/.codex-system-skills.marker`, `plugins/cache/`, `plugins/.remote-plugin-install-staging/`, as the pinned Codex creates them in an empty home). A sub-entry is listed only when the pre-step shows that the disabled `plugins` / skill features keep it unread or that it is the pinned binary's own bundled content, and the pre-step also records whether the bundled system skills are loaded into the review's context with those features disabled (if they are, that is a startup-loaded surface D4 excludes, and CP2 stops at its boundary reporting the pre-step as open). **Precedence:** a `STARTUP_LOADED` match refuses the launch unless it is exactly a path on `CODEX_STARTUP_SUBENTRIES`; for `skills/` and `plugins/` the check matches below the directory, so any other child (`skills/<x>/`, `plugins/<x>/`) refuses the next launch and the error names it, and the listed sub-entries are the only content of those directories the check lets through. A Codex upgrade that adds a bundled skill or plugin path fails closed like the feature allowlist. An entry in neither set refuses the next launch (`FAILED`, nothing started) with an error that **names the unexpected entry**; a Codex upgrade that writes a new state entry stops the review until a person extends the allowlist, exactly like the feature allowlist, and never relaxes to "allow whatever Codex writes". Between launches the Controller does not rebuild the home: it carries `auth.json` (the refreshed copy), `sessions/` and the Codex state forward, and re-checks the whole home before the next launch.

*The minimal home: owner, credentials, readings and lifecycle.* The review job owns `<runtime>/reviews/<job id>/codex-home/` from before the launch until its settlement, and the `resume` review-job branch (D9) owns it for a killed Controller's job. **Credentials.** The operator's `auth.json` is a ChatGPT login whose `tokens.refresh_token` and `last_refresh` Codex rewrites when the token ages, and a rotating refresh token would invalidate the operator's original. The Controller therefore copies it into the minimal home as a private, writable file (mode 0600, so a refresh succeeds inside the review rather than failing at an unpredictable time), recording the SHA-256 of both files at capture. When the job ends on any path, including the `resume` branch, it takes the lock `<runtime>/reviews/codex-auth.lock` (`flock`) and copies the minimal home's `auth.json` back **only if** it differs from the captured copy, parses as a credential file, and the operator's `auth.json` still has the captured digest: an atomic replace (temp file and rename in the operator's home directory, same mode). If the operator's file changed meanwhile (an interactive Codex refreshed it, so the copy's refresh token may now be revoked) nothing is copied back, the operator's file is untouched, and a review that failed to authenticate ends `FAILED` and is not retried. `codex-auth.lock` only orders Controller reviews against each other: an interactive Codex does not take it, so the digest check and the rename are not atomic with respect to the interactive client (the window is tiny) and nobody should assume the lock excludes it. If the pre-step shows a rotating refresh token, the operator's original token is revoked from the in-review refresh until the copy-back at job end (up to `reviewer.timeout_seconds`): an interactive Codex that refreshes in that window fails, and one that rewrites the file means nothing is copied back and the operator logs in again; the Risks section and `docs/common-problems.md` name this window as well as the reverse direction. The operator's `auth.json` is never opened for writing otherwise, and a copy-back failure is reported in the job's detail and never deletes it. The minimal home's `auth.json` and `config.toml` are deleted after the copy-back on every path; an operator home without a credential file refuses the launch (`FAILED`, nothing started). The D12 pre-step records whether and how the installed Codex rewrites `auth.json` and `config.toml` during `mcp list`, `features list` and `exec` (a `config.toml` rewrite would make the digest check refuse the second launch, so it stops CP2 at its boundary), and which entries it creates in an empty home during those three invocations (the `CODEX_STATE_ENTRIES`, `STARTUP_LOADED` and `CODEX_STARTUP_SUBENTRIES` sets above); the fake has a scripted refresh case; `docs/common-problems.md` names the symptom of a logged-out interactive Codex. **Readings and sessions.** Each reading comes from a stated home (D7): admission from the operator's home merged with the retained review homes, the end readings from the job's own minimal home, read before anything of it is removed. The `sessions/` directory (the review's rollout, and with it the rate-limit evidence a later admission must see, D8) is kept after the job ends and removed by the usage sweep once every rate-limit window it records has passed its reset; the remainder of the job's directory is removed with the copy, stated explicitly: every other Codex state entry in the home (`history.jsonl`, the state databases and the rest of `CODEX_STATE_ENTRIES`) carries review content and is deleted at settlement on every path, leaving only `sessions/`.

**D5. The Controller verifies the header; it does not write it.** The prompt gives Codex the exact header values. The bundle is located with `resolve-artifact review_bundle` (obligation 8 allows it for hand-off to a reviewer), and `Reviewed bundle ID`, `Reviewed base commit`, `Work item` both `Reviewed review content ID:` and `Reviewed review_content_id:` lines, and the stage's revision are read from its `MANIFEST.md`. The mapping from `MANIFEST.md` machine keys to verdict labels is a single table in `review.py`, one row per label: `bundle_id` to `Reviewed bundle ID:`, `base_commit` to `Reviewed base commit:`, `work_item_id` to `Work item:`, `review_content_id` to both content-id labels, and the stage revision (`plan_revision` to `Plan revision reviewed:` at the plan stage, `implementation_revision` to `Implementation revision reviewed:` at the implementation stage, labels pinned by a CP2 fixture of a hand-run verdict). The Workflow's verdict parser does not parse the revision headers, so this comparison is the only check of them: a verdict with the current ids but a wrong, missing or malformed revision line is a mismatch and is never ingested. Two values are not in `MANIFEST.md`: `Reviewer role` is fixed by the stage the decision's `snapshot.phase` selects (`MANUAL_EXTERNAL_PLAN_REVIEW` or `MANUAL_EXTERNAL_IMPLEMENTATION_REVIEW`, the roles `record-external-result` checks in `workflow_state.py`), and `Reviewer model` is `openai/<reviewer.model>`. After the run, `review.verify_verdict` compares each header line **exactly** against the expected values (the C6 lesson: Codex dropped five characters of an id). A mismatch is one bounded retry in the same job with an exact-values note; a second mismatch ends the job `FAILED` with the diff in the evidence and the gate left as it was. The Controller never edits a verdict and never composes a header on the reviewer's behalf. The header check is a pre-filter that makes the bounded retry possible; `record-external-result`'s own guards stay authoritative (D6). Both content-id labels are requested (`Reviewed review content ID:` and `Reviewed review_content_id:`); section 5.6 requires only the second, and the first is kept for older Workflow releases, so a later reader must not drop it as noise.

**D6. Ingest through the Workflow.** The job calls `next-action --expect-state-identity` immediately before launching Codex and again immediately before `record-external-result` (obligation 6): a review can run up to `reviewer.timeout_seconds` (3600 s) and outlive the state it was started for; a changed identity ends the job `INCOMPLETE` with the verdict discarded, and the next step re-decides. `controller/protocol.py` gains a typed `record_external_result(root, work_item, kind, input_file, run_ref)` wrapper, schema-validated like the other operations. Any `not_applicable` or `refused` answer (stale content, `DistinctReviewerModelsRequiredError`, a stage already recorded) ends the job `FAILED` with the Workflow's code in the evidence and leaves the gate open; a person can then resolve it as today. An admissible `BLOCK` is ingested like the other two verdicts, and the Workflow's own next answer is the user gate it already is.

**D7. Usage.** `cli._usage_gate` takes the provider; the review job calls `usage.admit(provider=codex, role="external-review", model=<model>, ...)` before launch, `usage.bind_job` after, the renewal ticker while it runs, and `usage.complete` after the terminal record. **Fresh Codex readings on every admission.** `usage.admit` reads no rollout file itself and today's `_usage_gate` supplies no `readings`, so the review path passes `readings=` the merge of `usage.read_codex_home` over **both** the operator's Codex home (`cli._codex_home()`: `$CODEX_HOME`, else `~/.codex`, where allowance spent outside the Controller is visible) **and** every retained review sessions directory `<runtime>/reviews/*/codex-home/sessions/` (where earlier Controller reviews, including one that hit a limit, recorded theirs), merged by the usage reader's freshness rule (the newest observation per window wins; a window whose reset has passed is stale), a `usage.read_codex_homes` generalisation of the existing reader (Codex provider only), into every admission attempt -- the first, each re-attempt after a hold wait, and the first admission of a second `run` -- so allowance spent outside the Controller (a lane script, an interactive session) is seen. Claude and Codex readings are kept per provider: a Codex hold never uses a Claude reading and vice versa. A hold at admission names the Codex provider and the settings that set its caps (the `usage.*` rows that apply to Codex). End readings come from the **job's own minimal home** (`<runtime>/reviews/<job id>/codex-home/`, which holds the rollout of this review; the operator's home does not), read by `usage.read_codex_home` (the same reader `usage --release` uses) before `usage.complete` and before the home is settled (D4's paragraph), and the reader needs the session file Codex writes, so the worker is **not** started with `--ephemeral` (a deliberate departure from the lane script: an ephemeral run leaves no rate-limit reading and the delta would always be charged at the forecast). Missing or not-newer readings are already handled by `usage.complete` (charged at the forecast). Codex usage stays reported under its existing provider rows; no new budget keys.

**D8. Limit and capacity (stated once; Goal 3, R6, CP4 and `docs/common-problems.md` follow it).** Admission goes through the usage gate: a hold at admission pauses and resumes exactly like a Claude job (`run --wait`). A non-zero Codex exit, or a run that produced no verdict, with 429/limit text in its output ends the job `INCOMPLETE` (the reservation is completed with outcome `ok`, charged by the measured delta, if the job started; never a zero-charge release), never `FAILED`. `INCOMPLETE` maps to exit 35 (`cli.py` status table), which ends `run`, and the job event is `lane_blocked`. "Empty run" means exit 0 with no verdict; a non-zero exit without limit text (and no verdict) is `FAILED`, so this paragraph and CP3's outcome table are the one source. Exit 35 applies to a limit, a timeout and an empty run; an in-run Ctrl-C is the exception stated in D9 (exit 130). So a limit during the job is **not** an in-run wait: the operator or the watchdog starts a new `run`, and that run's admission passes the usage gate again and pauses until the reset: its admission reads the operator's home **and** the retained minimal home of the review that hit the limit (D7), so the 99% reading in that rollout holds it even when the operator's home holds an older, lower one. CP4 pins this as two `run` invocations. A mid-job in-place wait is C8b's pattern and stays out of scope.

**D9. Supervision and `resume`.** The Codex process is started in its own session with the ownership tag in its environment (`OWNERSHIP_VAR`, the job id as tag), a hard `reviewer.timeout_seconds` deadline, and a kill of its process group on timeout or interrupt; descendants are reaped by the existing subreaper handling, and the lifecycle lock is held by the Controller process alone: the Codex group gets **no lock descriptor** (no `pass_fds`, no anchor). So when the Controller dies the lock is free, `resume` takes it in phase 2 as usual, and the pending non-terminal record is what stops a new `step` before `resume` (a test pins both). This is a lasting precedent for C10's reuse of the seam and is recorded in ADR 0013 beside the obligation-5 reading. It does not reuse `worker._Supervision` (that parses Claude stream-json); it reuses the process-group, ownership and reaping primitives. The record carries `worker_process` (pid, start ticks, process-group id, ownership tag) from launch, and `worker_state` is not used (no session lifecycle), so `validate_record`/`_worker_state_breach` apply no session rule to it.

*Launch evidence and settlement.* `job.never_launched` classifies any `INTERRUPTED` record without `expected_transition` as never started, which would settle a launched, interrupted review as `not_started` with no charge. A review record therefore carries **durable launch intent written before the spawn**, following `_launch_job` (`controller/job.py:6444-6497`), which persists `LAUNCHED`, `expected_transition` and the ownership tag before `Popen`: before the Codex process is started the record is flushed with `LAUNCHED`, `launched: true` in the review's own block and the ownership tag (the job id) it will carry in the process environment. The `worker_process` block (pid, start ticks, process-group id) is written and flushed after the spawn as additional evidence, but it is not what decides whether the job started. Ownership recovery is independent of that block: `resume` finds a process by the ownership tag in its environment, so a Controller killed between the spawn and the block's flush still has its Codex group found and killed. Settlement is conservative: a review record that is `INTERRUPTED` with launch intent present is treated as launched, whether or not `worker_process` exists, and is charged at the forecast (`unknown`); only a record with no launch intent, or one whose outcome is confirmed never started (the spawn call itself failed and was recorded), is `not_started` and released with a zero charge. Both `never_launched` (live settlement) and the sweep's accounting apply this rule. Idempotent replay: the ledger entry and the settled-token map are keyed by the **reservation token** (`controller/usage.py:832`, `1272`), not by the job id, so replaying the same record reuses its token and settles once.

A killed Controller leaves a live Codex in its own session. `resume` therefore has a **review-job branch**. Phase 1 (the supervision pre-pass) skips any record without `worker_state` (`_supervision_candidate`, `job.py:3919-3926`), so the branch runs in phase 2, under the lifecycle lock the dead Controller no longer holds; it is chosen by the record's kind before `_reconcile_protocol` (which accepts `automatic` decisions only and would fail the record): it finds the recorded process group by ownership tag and start ticks, kills it or verifies it dead, removes the disposable copy, writes the record terminal (`INTERRUPTED`; `INCOMPLETE` when the deadline had passed. An in-run interrupt (Ctrl-C) kills the Codex group, writes the record `INCOMPLETE` and completes the reservation with outcome `ok`, charged by the measured delta, if started, then lets the `KeyboardInterrupt` propagate unchanged, so `run` exits **130** as `docs/exit-codes.md` row 130 and `cli.SIGINT_EXIT_STATUS` document; exit 35 is not used for Ctrl-C and no documented contract changes. This is a deliberate departure from the Claude convention (`job.py:6600-6607` leaves the worker running for `resume`): nothing outside the Controller ingests a Codex verdict, so there is nothing to recover and the group is killed at once; a job ended `INTERRUPTED` by `resume` is settled by the sweep as `unknown`, which is a charge at the forecast, not a release) **without calling `reconcile`**, and only then lets `usage.settle_pending` settle the reservation (it settles terminal records only; a non-terminal one is left to supervision). The next step re-runs the review, which is idempotent. `resume --abandon` on such a record uses the same branch. A record whose process cannot be judged (ticks unreadable) is refused as any other worker the Controller cannot judge, never guessed.

## Risks

- **Codex CLI drift.** A new default-on feature after an upgrade is drift in this sense: the tool surface is an allowlist, and a launch whose `features list` reports an unlisted enabled feature is refused (D4). Flags (the `--sandbox` and `-c` sandbox, approval-policy and network overrides, `-o`, `-c model_reasoning_effort` and the service-tier override) are Codex's; a change breaks the argv. Mitigation: the captured real fixture, the `reviewer.binary` seam, and a clear `FAILED` (non-zero exit, no verdict) rather than a hang.
- **Sandbox escape.** Codex runs commands inside its `workspace-write` sandbox (approval `never`, command network off). Mitigation: disposable copy, the enforced sandbox boundary and environment allowlist (D4), the before/after guard on the real repository, and no credentials copied into the tree. Prevention is Codex's own sandbox, configured by D4's enforced boundary and refused at launch if the pinned overrides are missing; the before/after guard is the second layer. Inherited hooks, inherited `notify` commands, built-in web search and every non-allowlisted default-on feature (browser, computer use, plugins, image generation, sub-agents) are disabled by the same overrides (MCP servers by the minimal home, since `-c mcp_servers={}` does not exclude inherited ones), with an operator probe from a home that carries a trusted hook and a `notify` command. Residual: the boundary is only as strong as the installed Codex's sandbox, which the operator probe fixture pins.
- **Configuration outside the dedicated home.** The home excludes the operator's user file, not system, managed, MDM or cloud-managed layers, and the `Config` schema permits keys no inventory certifies. Mitigation: D4's source inventory, composed-value check against the pinned effective policy and exact environment allowlist, refusing a launch on any difference; residual: a layer that the installed Codex neither exposes through a composing command nor lets an outer isolation hide cannot be validated, and then the harness stays unregistered.
- **Session files accumulate** under `<runtime>/reviews/<job id>/codex-home/sessions/` because the run is not ephemeral (D7). Accepted: they are what makes the usage delta measurable and what a later admission reads (D8); the usage sweep removes one once its windows have reset (D4).
- **Credential refresh.** A review can refresh the copied login (D4); copy-back is conditional on the operator's file being unchanged, so a concurrent interactive refresh can still revoke the copy's token and fail that one review (`FAILED`, nothing retried), but the operator's own login is never overwritten with a stale one. The reverse direction is also named: a rotating refresh inside the review revokes the operator's original token at once, so an interactive Codex holds a revoked token until the copy-back at job end (up to `reviewer.timeout_seconds`), and if it rewrites the file meanwhile nothing is copied back and the operator logs in again; the lock orders Controller reviews only and does not exclude an interactive Codex.
- **Review cost.** An implementation review has used 200-300k tokens. Mitigation: the prompt carries the usage-economy instructions (long output to a file, never re-run identical commands); the admit forecast and caps apply; the feature is opt-in (D1).
- **A verdict that arrives after the bundle moved.** The Workflow's own guards (`assert_local_generation_matches`, content id) refuse it at ingest (D6); the job is `FAILED` and the gate is open.
- **Process leftovers.** The C12a lesson applies: the new runner and fake have numeric bounds and an inventory entry, and CP3 adds the replay of a killed Controller mid-review through `resume`.
