## Goal

C10g-3b2a added `codex_tester.run_tester`: the controls, `codex exec`, the outcome and the credential copy-back. This item adds everything `review.launch_functional` does around its `_claude_run`, so that one new function returns the same dict as `launch_functional` for a Codex tester: the build gate before any process starts, the before-and-after comparison of the real repository and its local origin, the binding check, the fake-call log, every refusal mapped to `functional_tester_unavailable`, and the sandbox removed on every exception. It also declares the tester role for Codex, retargets the `build_verification` declaration, and lands the three carried findings. Nothing calls the new function: routing and the fallback to the other harness are C10g-3c.

## What exists

- `review.launch_functional` (`controller/review.py`): the Claude launch. Its surroundings are the model for this item and it stays unchanged, as do `settle_functional`, `functional_review` and the Codex reviewer. `settle_functional` removes `<runtime>/functional/<job id>`, which is also the Codex bridge's folder (`codex_sandbox.TesterLayout` uses area `functional`), so it works for both testers.
- `controller/codex_tester.py`: `run_tester(bridge, flows, *, binary, operator_home, timeout, ...)` returns `outcome`, `detail`, `tester_message`, `readings`, `first_readings`, `subagents`, `credentials`, `telemetry`, `exit_code`; it removes the credential copy on every path.
- `controller/codex_bridge.py`: `build_bridge` (clone, scratch origin, output folder, writable links, clone verified against the manifest; a failure removes the folder), `check_bound`, `prompt`.
- `controller/codex_build.py`: `is_verified(runtime_root, binary)` reads a fresh digest and the record and writes nothing.
- `controller/harness.py`: `CODEX.roles == (REVIEWER,)` and `build_verification=None`; its comment says C10g-3 changes that one value. `controller/routing.py` accepts a role/harness pair when the adapter declares the role the routing role runs as (`ADAPTER_ROLE`), so declaring the tester role for Codex would make `routing.roles.functional-tester.harness=codex` valid in a settings file or `--role-harness`, while `job.py` launches Claude regardless.
- Guides that state the old facts: `docs/guide/harnesses.md` (the generated table and the C10g-3b2b prose), `docs/guide/commands.md` and `docs/guide/workers.md` ("nothing consults the record until C10g-3"), `docs/guide/runtime.md` and `docs/guide/automation.md` (the refusal wording).

## Decisions

Each decision states one principle.

- **D1. A new function in `codex_tester.py`; the Claude launch untouched.** `launch_codex_functional(candidate=..., flows=..., runtime_root=..., job_id=..., work_item_id=..., operator_home=..., timeout=..., model=..., effort=..., binary_name="codex", system_dir=..., inherited_env=..., on_spawn=..., out=None, run=None)` returns the dict `launch_functional` returns (`outcome`, `breach`, `unbound`, `fake_calls`, `output_dir`, `sandbox`, `keep`, `credentials`, `detail`, `readings`, `first_readings`, `head`, `checklist_blob`, `writable`, `refused`, `tester_message`, `telemetry`). It reuses `review.snapshot_repository`, `compare_snapshots`, `_local_origin_refs`, `functional_review.check_bound`'s Codex twin `codex_bridge.check_bound`, `read_fake_calls`, `sweep_kept` and `remove_sandbox` through their current signatures. The result keeps `subagents` and `exit_code` from `run_tester` as two extra keys (C10g-3b2a's D6 says the launch merges `run_tester`'s dict; C10g-3c's independence and telemetry need the sub-agent sessions, as the reviewer path records them), so the step still reads the Claude keys unchanged. `review.py`, `settle_functional` and `job.py` are not changed; a test shows `git diff 01c67ac..HEAD --stat -- controller/review.py controller/job.py controller/functional_review.py` is empty.
- **D2. The order, with the gate first.** In order: the role check (`harness.for_role("codex", FUNCTIONAL_TESTER)`, cause `role_refused`), the binary (`review.resolve_binary`, cause `no_binary`; the path it returns is used **with its symlink kept**, as `verify-codex`, the reviewer, `codex_build.build_digest`, `_interpreter` and `codex_install_roots` all do, so the `node` next to the launcher is the interpreter that runs and the one `verify-codex` probed; `os.path.realpath` is not applied to the executed path), the build gate (which also records `os.path.realpath(binary)` and the admitted digest), `sweep_kept`, the runtime-root containment check against the clone and output folders (cause `enforcement`, as the Claude launch), the snapshots before, `build_bridge`, `run_tester`, the snapshots after, the binding check, the fake-call log. No process starts and nothing is written before the gate passes.
- **D3. The gate refuses a build the record does not admit, naming `verify-codex`.** `codex_build.is_verified(runtime_root, binary)` false refuses with cause `enforcement` and the verdict's own note, and says to run `workflow-controller verify-codex`. A missing record, an untrustworthy record, an unbound digest and a digest not in the record are the four notes `is_verified` already gives; they all refuse. The gate runs before `sweep_kept`, the snapshot and the bridge, so a refusal leaves no sandbox behind.
- **D4. A build that changes during the run is a breach.** After `run_tester` the gate is evaluated again for the same path; the check compares the fresh digest with **the digest the gate admitted** and `os.path.realpath(binary)` with the target the gate recorded, as well as `Verified.ok`: a build replaced by another that is also recorded passes `is_verified` but is not the build that was launched, and a re-pointed symlink is the same. If the target or digest differs, or the build is no longer verified (the record vanished or became untrustworthy), a `breach` entry `codex build: <note>` is added, which keeps the sandbox, as every breach does. The tester runs a Codex it could in principle overwrite only if the profile let it write there, which the profile does not; the check makes that assumption observable rather than silent.
- **D5. Breach is the Claude launch's set, minus Claude's session search.** `compare_snapshots(before, after)` (worktree digest, `HEAD`, refs, reflogs, status), `origin refs` when the real origin is a local path (an unreadable origin before or after is `origin: <error>`), and D4's build entry. There is no `session:` entry: Codex writes its rollouts into the job's own Codex home on every run, which is not a breach, and the operator's real home is outside the profile's readable roots (a probe the live round measured).
- **D6. Every refusal is `functional_tester_unavailable`; the sandbox goes on every exception.** A `ReviewLaunchRefusedError` from `build_bridge` or `run_tester` (the controls, the argv, a missing binary the controls found) is re-raised as `functional_review.unavailable(UNAVAILABLE_ENFORCEMENT, ...)` with the original as `__cause__` and its message; a `TesterUnavailable` already raised (a clone mismatch) passes through unchanged; any other exception propagates. The exception contract differs from the Claude launch on purpose: there a control or argv refusal propagates as `ReviewLaunchRefusedError` and `job.py` records a `FAILED` job with `FUNCTIONAL_REFUSED_CODE`; here it becomes the `functional_tester_unavailable` gate, as #231 asks, so C10g-3c's call site handles `TesterUnavailable`, not `ReviewLaunchRefusedError`. The launch's own removal, `functional_review.remove_sandbox(runtime_root, job_id)`, covers only exceptions raised **after `build_bridge` returns** (the `run_tester` call, the snapshots after, the binding check, the fake-call log), the credential copy having already been removed by `run_tester`; `build_bridge`'s own failures are its to clean up, and its refusal of an existing `<runtime>/functional/<job id>/` leaves that folder untouched, as the Claude launch's `build_sandbox` before its `try` does. On a clean run the sandbox is **not** removed (the caller reads the output folder and calls `settle_functional`), exactly as `launch_functional`.
- **D7. `keep` and `unbound` follow the Claude launch.** `unbound = codex_bridge.check_bound(bridge)`, `keep = bool(breach or unbound)`, `fake_calls = functional_review.read_fake_calls(layout.fake_logs)`. `output_dir` is `bridge.out`, `sandbox` is `bridge.layout.base`, `writable` and `refused` come from the bridge, so the step reads the result without a new branch.
- **D8. The tester role is declared for Codex, and routing keeps refusing it until C10g-3c.** `harness.CODEX.roles` becomes `(REVIEWER, FUNCTIONAL_TESTER)` and the comment on `FUNCTIONAL_TESTER` says Claude Code and Codex declare it. Because `routing.check_role_harness` reads the registry, `routing.py` gains one explicit, named exception: `NOT_YET_ROUTABLE`, the set of `(routing role, harness)` pairs that are declared but not selectable (`("functional-tester", "codex")`), refused with the message "harness 'codex' declares the functional-tester role but routing cannot select it until C10g-3c". Nothing else about routing changes, so a Claude-only configuration and every settings file valid today behave as before, and C10g-3c deletes the set. Every place that enumerates a harness's roles was checked: `harness.py`, `routing.py` (`ADAPTER_ROLE`, `check_role_harness`, `_pair_refusal_evidence`), the harness table generator (`tools/harness_table.py`, reads the registry), `route_select` and the settings validators (all go through `check_role_harness`), the tests that pin the old declaration (`tests/test_harness.py`, `tests/test_routing.py`, `tests/test_functional_sandbox.py`, `tests/test_docs.py`, `tests/test_harness_table.py`) and the guides; `job.py` reads no role list.
- **D9. `build_verification` for Codex becomes `verify-codex`.** It is the command that admits a build for the one launch that checks one, the tester, as `verify-claude` is for Claude's; the reviewer keeps its fail-closed feature, layer, state and flag checks. The comment is rewritten to say so, the generated table row follows, and the prose in `docs/guide/harnesses.md`, `commands.md` and `workers.md` that says "nothing consults the record until C10g-3" now says the Codex tester launch consults it (from C10g-3b2b; routing still does not select it).
- **D10. Carried findings from C10g-3b2a's review.**
  - F-1431bf53b732: `codex_bridge.build_bridge` rejects a `prompt` option (a `TypeError`-style refusal naming why: the tester's prompt is always standard input), since `run_tester` always rebuilds the command with `prompt=None`.
  - F-b0ad422b8b03: `codex_sandbox.Built` records the `binary` it was built with (`binary: str = ""`, defaulted like `credential_digest`, `build` fills it) and `run_tester` refuses, as a control before `check_argv`, a `binary` that differs from a non-empty recorded one. The launch function passes the one resolved path to both.
  - F-8cce040d9e72: `tests/test_codex_tester_live.py` skips when the `CI` environment variable is set, as its docstring and the guide say, with its reason.
- **D11. Release type.** `chore:`. The launch function has no caller, the registry change is invisible to every command (the settings still refuse the pair, with a changed message that only a Codex-tester route reaches), and the table and guide text are documents. If review finds an operator-visible change, the title becomes `feat:` before the plan is approved, not after.

## Functional review

Every flow is offline and unit-level, run one module at a time (`tests.test_codex_tester_launch`, `tests.test_codex_tester`, `tests.test_codex_bridge`, `tests.test_codex_sandbox`, `tests.test_harness`, `tests.test_routing`, `tests.test_harness_table`, `tests.test_functional_sandbox`, `tests.test_docs`), plus `python3 -B tools/check_docs.py`, `python3 -B tools/harness_table.py --check`, `git diff 01c67ac..HEAD --stat -- controller/review.py controller/job.py controller/functional_review.py` (expected empty) and a search showing nothing outside `controller/codex_tester.py`, its tests and `controller/__init__.py` references `launch_codex_functional`. The tester's `/tmp` is read-only and these tests create temporary folders, so a flow runs with `TMPDIR` set to the tester's scratch area; a flow that cannot is `environment` and operator-run (any test that starts the real `app-server` or builds a deep path). There is no live flow: the one opt-in live test of C10g-3b2a is unchanged apart from its guard, and the operator-run Codex functional round is C10g-3c (`CONTROLLER_LIVE_CODEX_TESTS=1`). The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **A declared role that routing refuses is a two-place fact.** `NOT_YET_ROUTABLE` is the one place; a test pins that it is exactly the pair above and that C10g-3c must delete it.
- **The build gate trusts `codex_build.build_digest`'s identity.** A layout it cannot bind refuses (fail closed); the launcher is gated and executed with its symlink kept, as `verify-codex` records it, and a launcher re-pointed during the run is a breach because D4 compares the gate's `realpath` and digest with fresh ones.
- **The Codex home is inside the sandbox folder.** The credential copy is removed by `run_tester` on every path and the folder by the launch on every exception after `build_bridge` returns (a refused existing folder is left alone); a clean run leaves the folder (as the Claude launch) with the copy already gone.
- **Out of scope:** routing selection, the fallback chain, telemetry dimensions, independence and the operator-run Codex round (C10g-3c); the step and `job.py`; the Codex worker (H4a to H4g); any change to the reviewer, `verify-codex`, settings, options, exit codes or gates.
