## Goal

Launch one rendered command as a headless Codex worker in the job's worktree, under the H4b1 sandbox, and return the `worker.WorkerResult` the Claude launch returns. The launcher renders the command (`command_files.render_command`), refuses a build `verify-codex` has not admitted before it starts or writes anything, runs the controls, runs `codex exec` under a deadline, compares the `.git` guard digest and the nested-repository scan around the run, copies the credential back and removes the copy on every path, and maps what happened to one of the four outcomes. It also adds the two controls H4b1 left open: the composed-configuration check for the worker profile and the nested-repository refusal. It is registered for a **fixture role only**; nothing an operator runs can reach it.

## What exists

- `controller/codex_worker_sandbox.py` (H4b1): `WorkerLayout`, `check_worktree`, the `worker` profile, `argv`/`check_argv`, `check_home`, `check_launch`, `build` (starts no process), the probes, `guard_digest` and `check_guard`. The module's own docstring and the harness guide name two open limits: the composed-configuration check and the nested `.git` entry.
- `controller/codex_sandbox.py` and `controller/codex_tester.py`: the tester's counterparts. `check_composed`, `effective_policy`, `check_effective` and `compose_argv` there are typed to the tester's layout; `codex_tester.run_tester` is the tester's run and `codex_tester._build_breach` the generic post-run build comparison. Neither is edited.
- `controller/command_files.py`: `render_command(name, arguments, commands_dir)`, pure, refuses the user-only commands.
- `controller/codex_build.py`: `is_verified(runtime_root, binary, system_path=...)`, the `verify-codex` record. `controller/review.py`: `resolve_binary`, `run_bounded`, `scan_rollouts`, `copy_back_credentials`, `check_outside_layers`.
- `controller/worker.py`: `WorkerResult` and the four outcomes (`SUCCESS`, `FAILURE`, `AMBIGUOUS`, `INTERRUPTED`). `controller/worker_launch.py`: the `WorkerLauncher` protocol and `LAUNCHERS`, whose keys a test requires to be exactly the adapters declaring the worker role. `controller/harness.py`: `CODEX.roles` is the reviewer and the functional tester.

## Decisions

Each decision states one principle.

- **D1. The launcher is a new module; the sandbox module gains only controls.** `controller/codex_worker.py` holds the launch, the classification, the settling and the `CodexLauncher`. The composed-configuration check and the nested-repository scan are controls of the sandbox, so they join `controller/codex_worker_sandbox.py` (CP1). `codex_sandbox`, `codex_tester`, `review`, `worker`, `worker_launch`, `harness`, `command_files`, `codex_build` and their tests are not edited. A helper of those modules that depends only on strings and paths is called; one typed to the tester's layout is written again over `WorkerLayout`, small, and a test pins the two to the same behaviour where they overlap, as in H4b1.
- **D2. The composed-configuration check is the tester's, over the worker's profile.** `compose_argv` builds `codex app-server --strict-config` with the exec's own `--disable` and `-c` items (`required_overrides`) and `--listen stdio://`; `check_compose_argv` refuses an omitted pinned item, an unpinned `-c`, a banned flag and any line that differs from `compose_argv`. `effective_policy` is every value the worker's composed `config` must equal: the argv-pinned values parsed back from `required_overrides`, the profile parsed back from `profile_toml`, the sandbox keys unset, and the reviewer's remaining scalar defaults. `check_effective` compares leaf by leaf (a `null` is unset, an unexpected leaf refuses), requires every origin to be an allowed layer, forbids a layer other than the packaged defaults from setting a forbidden key, and refuses a disabled feature reported enabled. `check_composed` composes through the `run` seam with the worktree as `cwd`, checks the home again (the composing command writes Codex state into it), then compares. The refusal names the leaf, its value and its origin layer. Residual window (also stated for the tester): the composition is read from a separate app-server process started just before the launch, not from the `exec` itself.
- **D3. A nested `.git` entry is refused before and after the run.** `nested_git_entries(worktree)` walks the worktree without following a symlink, prunes the top-level `.git`, and returns the relative path of every entry named `.git` below the root, of any type (a directory, a file as a submodule or linked worktree has, a symlink). `check_nested(worktree)` refuses on the first, naming it. A nested repository holds hooks and a config that run later, outside the sandbox, when git is next used in that directory, and `guard_digest` covers only the top-level `.git`. Refusing it before the run keeps the baseline clean (a vendored repository is refused; the fixture role accepts that), refusing it after the run catches one the worker created.
- **D4. The launch order is fixed, and nothing is written before the gate.** In order: (a) the task must be `/<name>` with optional arguments, else refused; the command is rendered from `commands_dir` (default `<cwd>/.claude/commands`), which refuses a user-only command; (b) the binary is resolved with `review.resolve_binary` (symlink kept); (c) the build gate: `codex_build.is_verified` must admit the build, else a `ReviewLaunchRefusedError` naming `workflow-controller verify-codex`, before any process starts and before anything is written; (d) `cwd` must equal `WorkerLayout(runtime_root, job_id).worktree` (the launcher does not create the tree; preparing a clone there is H4c's), `check_worktree` and `check_nested` accept it, the runtime root must not lie inside the worktree or the scratch area, and `<runtime>/worker/<job>/codex-home/` must not exist yet, so a reused `job_id` cannot carry an earlier run's rollouts or credential copy into `scan_rollouts` (a launch takes a fresh `job_id`; allocating one is H4c's); (e) `guard_digest` before; (f) the settling scope opens, then `build` (D6) with `ownership_tag=job_id`, never `build`'s default `"worker"`: `review.run_bounded` kills every process of the user whose environment carries exactly that tag on the deadline (`review._kill_owned`), so a tag shared by all worker jobs would let one launch's deadline kill another job's Codex (or a fake Codex in another test shard), and the other Codex callers pass the job id (`controller/codex_verify.py`); H4c may still own tag allocation and reaping beyond the deadline; (g) the controls: `check_argv`, `check_launch`, `check_composed`; (h) `review.run_bounded` with the prompt on standard input, the deadline and `on_spawn`; (i) the settling (D6), also when `build` or a control raised; (j) `guard_digest` after and `check_guard`, `check_nested`, the build comparison. A refusal at (a) to (g), `build`'s own included, raises `ReviewLaunchRefusedError` (or the renderer's own error) and no `codex exec` has started.
- **D5. Four outcomes, one precedence, no new class.** The run's `ran`, `timeout`, `limit` and `failed` (classified over the rollout scan, the exit code and the `-o` file, with the worker's wording) map to `WorkerResult.outcome`: a clean run with a final message and no breach is `SUCCESS`; the precedence is the Claude classifier's (`controller/worker_stream.py`): the deadline, then termination by a signal (a negative exit code, no timeout), both `INTERRUPTED` so that `job.py`'s `_VERIFYING_WORKER_OUTCOMES` still verifies a worker killed after it committed; then a Codex usage-limit record, then a non-zero exit, both `FAILURE`; then a zero exit with no final message, `AMBIGUOUS`. A breach found after the run (the guard digest, a nested `.git`, the build changed) turns any outcome into `FAILURE` with `is_error` true and `subtype` `sandbox_breach`, because the worktree can no longer be trusted; the breach entries are in `stream_diagnosis`. `returncode` is the exit code, `result` the final message, `stdout` and `stderr` the decoded output. Fields Codex does not give (`session_id`, `total_cost_usd`, `raw_json`, `num_turns`, `terminal_reason`, `stop_reason`, `permission_denials`) are `None`, and `duration_ms` is the wall time measured around `run_bounded`; `owned_processes_seen` is `None` because ownership tags and reaping on a timeout are H4c's. `run_bounded` already kills the group and every process carrying the child's tag on the deadline.
- **D6. The credential copy is settled on every path.** The settling scope opens before `build` is called, because `build` writes the credential copy (`review.build_home`) before its own later steps and controls can raise. After the run, and on a refusal at any step from `build` on, the launcher reads the usage readings and the rollout scan, copies the credential back (`review.copy_back_credentials`, only if it differs and the operator's file is unchanged) and removes the credential copy. If `build` raised there is no `Built` and no captured digest: nothing is copied back and the copy at `WorkerLayout(runtime_root, job_id).rel("codex-home", review.CODEX.credential_file)` is removed. Each step is guarded so that one failure never skips the next and never replaces the exception already propagating. The readings, sub-agents, rollout figures and the copy-back result are put in `stream_diagnosis` for H4c, which derives the job record.
- **D7. Registered for a fixture role, not for the harness.** `CodexLauncher` implements `worker_launch.WorkerLauncher` (`launch(task, **options)` calls the launch). The options are `runtime_root`, `job_id`, `operator_home`, `cwd`, `timeout`, `on_spawn`, `commands_dir`, `model`, `effort` and the `run`, `system_path` and `real_home` seams (`on_spawn` is called as `run_bounded` calls it, `on_spawn(pid, pgid)`, not with `worker.launch`'s `on_spawn(worker_process, anchor=..., ownership_tag=...)`, so H4c adapts its callback); those of `worker.launch` that Codex has no counterpart for (`stdout_path`, `stderr_path`, `permission_mode`, `ownership_tag`) are not accepted, and an unknown option raises `TypeError` (`ownership_tag` is not an option because the launcher fixes it to `job_id`, D4(f)). H4c maps its job fields onto these. It is **not** added to `worker_launch.LAUNCHERS`, whose keys a test requires to equal the worker-role adapters, and `harness.CODEX.roles` is unchanged. The registration is exercised by a test that patches both `harness.ADAPTERS` (a fixture adapter declaring the worker role added, the real `harness.CODEX` untouched) and `LAUNCHERS`, for the test only, and shows `for_harness` reaches `CodexLauncher`. No setting, option, exit code or gate selects it.
- **D8. Tests use a fake Codex; one opt-in test uses the real one.** The offline tests run a fake `codex` executable (a script that answers `mcp list`, `features list`, the app-server `config/read` exchange and `exec`, and, in `exec`, edits and commits in the worktree and writes the `-o` file), with a recorded `verify-codex` entry for it and a fake credential file; no network and no real Codex. The opt-in test (`CONTROLLER_LIVE_CODEX_TESTS=1`, `codex`, `bwrap` and a credential file; skipped by default and on CI with the reason) runs one real `codex exec` turn through the launcher on a scratch clone with a trivial rendered command and asserts the result, the commit in the clone, the guard digest unchanged beyond a commit and the credential removed. The measured result is recorded in `tests/harness_contract/codex/worker_launch.txt`.
- **D9. Release type.** `chore:`: no caller outside the fixture registration, no operator-visible change. If review finds one, the title becomes `feat:` before the plan is approved.
- **D10. The recorded local approval was another work item's; revision 4 requires a local review of this plan.** The external review of revision 3 (EXT-001) found that the `LOCAL_MODEL_PLAN_REVIEW` `APPROVE` recorded for this item had a `verdict_sha256` equal to a verdict whose `Work item:` is `workflow-controller-codex-tester-fallback`, with other bundle, base and content ids. The finding is accepted: that approval is not evidence about this plan. The plan text is otherwise unchanged by this revision (D1 to D9 stand); the new revision gives the content a new `review_content_id`, so both review stages read as absent and a local review of this item's own revision 4, bound to its own ids and `Work item:` header, must precede any external review or approval.

## Functional review

Every flow is offline and unit-level except the one live flow. Run from the product clone with `TMPDIR` set to a writable scratch directory, one module at a time, `python3 -B` and no `PYTHONPATH=.`: `tests.test_codex_worker`, `tests.test_codex_worker_sandbox`, then `tests.test_package_structure`, `tests.test_codex_sandbox`, `tests.test_codex_tester`, `tests.test_worker_launch`, `tests.test_harness`, `tests.test_command_files` and `tests.test_write_containment` (they show the neighbouring modules are unchanged and the scan accepts the new module), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. A flow that creates temporary folders or runs git needs a writable `TMPDIR` and is `environment` when the tester's `/tmp` is read-only. The live flow (`CONTROLLER_LIVE_CODEX_TESTS=1 python3 -B -m unittest tests.test_codex_worker_live -v`) needs a real `codex`, `bwrap`, a recorded `verify-codex` build and a credential file and is operator-run; its output is the capture file. The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **The composition is read from a separate process.** D2 states the window; a layer or setting that differs between the app-server and the `exec` is not seen. The guard digest and the live proof are the other lines.
- **A nested-repository refusal before the run rejects a worktree that legitimately vendors one.** Accepted for a fixture role; H4c decides how real jobs get their tree.
- **Where the job's tree comes from.** The launcher requires the tree at the layout's path and does not create it. H4c prepares it; this item proves the launch on a tree the test creates.
- **The fake Codex can drift from the real one.** The pinned `exec_argv` and `config/read` captures under `tests/harness_contract/codex/` feed the fake's answers, and the opt-in live test is the only real check.
- **Write containment.** The module writes only through `controller/runtime.py` primitives; `tests.test_write_containment` fails on a direct write or `.replace(` call. A missing primitive is added to `runtime.py`, not the new module.
- **Out of scope:** job records, usage derivation, ownership tags and reaping on a timeout (H4c); usage windows (H4d); review roles on Codex (H4e); `milestone-implement` on Codex (H4f); the remaining roles (H4g); declaring the worker role on `CODEX`, registering a real launcher, any setting, option, exit code or gate, and any change to the Claude worker launch, the reviewer or the tester.
