## Goal

Build and prove the sandbox a Codex **worker** would run in. The tester's sandbox (C10g-1) lets the model read a clone and write only a scratch area. A worker must change the job's worktree and commit there, and nothing else. This item adds the permissions profile, the `codex exec` command line, the layout and build, the boundary probes and an opt-in live proof that `codex exec` applies the profile. It launches nothing: the launcher (render, gate, run, `WorkerResult`, fixture registration) is H4b2.

## Why the issue is split

#252 asks for the sandbox policy and its live proof, and for the launcher, in at most three checkpoints, and says to split before the first review if there is more than one mechanism. There are two: the permissions profile with its measured boundary (a filesystem and process-isolation question, answered by probes on the pinned build) and the launcher (a process-supervision question, answered by fake-Codex tests). They fail for different reasons and need different evidence, so H4b1 ships the first and H4b2 ([#255](https://github.com/RodrigoFAbreu/workflow-controller/issues/255)) the second, including the composed-configuration check for the worker profile (D6).

## Decisions

Each decision states one principle.

- **D1. A new module beside the tester's, which stays as it is.** `controller/codex_worker_sandbox.py` holds `WorkerLayout`, the profile, the command line, `build` and the probes of the worker. `controller/codex_sandbox.py`, `controller/codex_tester.py` and their tests are not edited. `WorkerLayout` is `<runtime>/worker/<job id>/` (a `review.JobLayout` with `area="worker"`) and exposes `worktree`, `home`, `codex_home`, `last_message`, `scratch`, `scratch_tmp`, `fake_logs` and `bin`. Helpers of `codex_sandbox` are called when they depend only on strings and paths (`_quote`, `_string`, the `-c` spellings); a helper typed to `TesterLayout` is written again in the new module, small, and a test pins the two to the same behaviour where they overlap. The rule for the controls: the new module defines its own `check_home` and `check_launch` over `WorkerLayout` (the tester's read `layout.clone` and name "the tester's Codex home"), built from the shared pieces `review.check_outside_layers`, `review.argv`/`review.check_argv`, `review.check_mcp_list` and `review.check_features`; it never calls `codex_sandbox.check_home` or `codex_sandbox.check_launch`. Why a new module: the tester's profile name, layout and probe table are constants of that role, and changing them to take both roles would put the tester's tests in play.
- **D2. The worktree is a tree with its own `.git` directory.** `check_worktree(path)` refuses a path that is not a directory, whose `.git` is missing, is a symlink, or is a file (a linked worktree or a submodule keeps its objects and refs outside the tree, so a commit would need write access outside it). The refusal is a `ReviewLaunchRefusedError` naming the cause. How a real job's tree is made to satisfy this (a clone of the job's branch, a disposable copy) is H4b2's and H4c's decision; this item states the requirement and proves the profile for such a tree.
- **D3. The `worker` profile is the tester's with one more writable path.** `:minimal` read; the readable roots (system directories, Codex install roots, interpreter roots, the Controller package directory, `<base>/bin`); the **worktree and the scratch area `write`**; the network off. Nothing of the operator's home, the runtime root, a sibling job or the credential copy is listed. Commands see only `command_environment` (D5). Allowed, then: edit, create, rename and delete files in the worktree, and commit there (the commit writes the objects, index and refs under the worktree's `.git`). Not allowed: any write outside the worktree and scratch, any read outside the readable roots, any network connection from a command (so no push, no `gh`, no package download). Codex's own model connection is made by the Codex process, outside the command sandbox, as in the tester.
- **D4. The git directory gets a second line of defence, and it is an allowlist.** A hook, a changed `core.hooksPath`/remote URL or `core.fsmonitor`, or a redirection such as a new `.git/commondir` runs later, outside the sandbox, when the operator or the Controller next uses git in that tree (reproduced on git 2.56.0: a worker-written `.git/commondir` pointing at a folder whose `config` sets `core.fsmonitor` made the next plain `git status` run that command). The worktree is writable, so the worker can write any file under `.git`; a list of three names is not a guard. The profile lists `<worktree>/.git/hooks` and `<worktree>/.git/config` as `read` under the writable worktree, if Codex honours a narrower entry nested in a wider one; whether it does is a thing to **measure**, not assume, and it covers only those two names. The guard is `guard_digest(worktree)`, a digest of **every entry of `.git`** (relative name, type, mode, and contents for a file or the target string of a symlink, recursive; a symlink is never followed, at the root or below it) **except the content of** what a commit writes: `objects/`, `refs/`, `logs/`, `index`, `HEAD`, `ORIG_HEAD`, `COMMIT_EDITMSG`, `packed-refs`, `info/refs` and any `*.lock` file. For those excluded paths the digest records exactly three things and nothing about names, contents or modes: (a) the type of each excluded root (`objects`, `refs`, `logs`) present at the start, which must not change; (b) every symlink and every entry that is neither a regular file nor a directory (a device, fifo or socket), anywhere under `.git`, excluded paths included, by relative path, which must be empty in both the before and the after digest; (c) whether `objects/info/alternates` or `objects/info/http-alternates` exists, which must be false. The names, contents and modes of regular files and directories beneath the excluded paths, and whether an excluded top-level file (`index`, `HEAD`, `ORIG_HEAD`, `COMMIT_EDITMSG`, `packed-refs`, `info/refs`, a `*.lock`) exists at all, are **not** recorded, so a commit's new loose objects and `objects/<xx>/` directories, new `refs/` and `logs/` entries, a first `COMMIT_EDITMSG` or `ORIG_HEAD`, a `packed-refs`, `objects/pack/*` and `info/refs` after an automatic gc (reproduced on git 2.56.0: a plain `git gc` creates `.git/info/refs`, the dumb-HTTP catalogue that `update-server-info` writes, and git never runs it; `info/exclude` and every other name under `.git/info` stay recorded), and a lock file that appears and goes leave the digest unchanged. A commit creates none of (a)'s changes, (b) or (c). This closes the redirection route the exclusions would otherwise leave: replacing `.git/objects`, or a directory or file beneath `objects/`, `refs/` or `logs/`, or `COMMIT_EDITMSG`, `index` or `HEAD`, with a symlink to another repository leaves `.git` a real directory but makes the next unsandboxed `git add` or `commit` write outside the worktree through it. The digest also records the type of `.git` itself, and `check_guard(before, after)` refuses, naming `.git`, when `.git` is no longer a real directory (removed, a file such as `gitdir: evil`, or a symlink): the worktree root is writable, so a worker can swap `.git` for a `gitdir:` file or a symlink to a copy whose `config` sets `core.fsmonitor`, and the next plain `git status` runs that command (reproduced on git 2.56.0). `check_guard` also refuses any entry added, removed or changed outside that set, and, inside it, any change to (a), any member of (b) in either digest, and any (c), and names the entry, so a new `commondir`, `config.worktree`, `gitdir` or `modules/*/config` is refused as well as a hook or `config` edit. A launcher compares the two digests around the run, as the tester does for the real repository (`codex_tester._origin_breach`). The live test records which line held. Why both: a limit measured on one build is not a guarantee on the next. **Open limit, stated in the guide and blocking any launch in H4b2:** a nested repository or submodule the worker commits into the tree (a `.git` directory of its own below the worktree root, with a `config` git reads when used from inside it) is a separate later-git risk this digest does not cover; H4b2 must close it (for example by refusing a nested `.git` entry in the worktree after the run) before a worker is launched.
- **D5. The command environment carries no identity and no config.** `command_environment` is the tester's (`PATH` of `<base>/bin` then the system path, `HOME` the stand-in home, `TMPDIR` the scratch area, `LANG`/`LC_ALL`) plus `GIT_CONFIG_NOSYSTEM=1` and `GIT_TERMINAL_PROMPT=0`. Which git identity a real worker commits under is H4b2's decision; the probe commits with `git -c user.name=... -c user.email=...` so it needs none.
- **D6. The command line is the tester's, with the worker's profile, tree and last-message path.** `argv` builds `codex exec --strict-config`, the same `--disable` features, the same pinned `-c` items with `default_permissions="worker"` and `projects={<worktree>={trust_level="untrusted"}}`, `-C <worktree> --ignore-rules --color never -o <last_message>`, and the prompt on standard input (`-`). `check_argv` refuses an omitted pinned item, an extra `-c`, an equivalent spelling and every banned flag (`codex_sandbox.BANNED_FLAGS`, `-s` and `--sandbox` included). `check_home` and `check_launch` are the new module's own, over `WorkerLayout` (D1): `check_launch` runs `mcp list` and `features list` with `cwd=layout.worktree`, checks the home before each and once after both, and calls `review.check_outside_layers` first. The **composed-configuration check** (`check_composed`, `effective_policy`, `check_effective`) is tied to the tester's profile and is **not** built here: nothing launches in this item, and H4b2 adds the worker's before any launch. This is stated in the guide as an open limit of the sandbox until then.
- **D7. The probes are the tester's, turned round on the worktree.** `probe_command(targets, marker)` attempts a real action per boundary and prints `PROBE <name> <RESULT>`. Expected: `tracked`, `newfile`, `rename` and `delete` `WROTE` in the worktree (`rename` and `delete` act on files of their own that the probe creates in the worktree, with the rename inside the tree, so the tracked file keeps the `tracked` probe's edit and D8 can assert it changed); `commit` `COMMITTED` (`git add` and `git commit` in the worktree, objects and refs written); `scratch` `WROTE`; `home` `REFUSED`; `canary_file` `BLOCKED`; `canary_env` `EMPTY`; `credential` `BLOCKED`; `push` `REFUSED` (a bare origin made readable by an extra root); `gh_name` `STANDIN` (the stand-in launchers `build` writes in `<base>/bin`, `functional_review.write_launchers`); `gh_path` `FAILED`; `tcp` and `unix` `BLOCKED`. Informational (`WROTE` or `REFUSED`, as in the tester): `sibling`, `tmp`, `vartmp` (a write into an ancestor folder reports success but lands on a private layer; the live test asserts the host path stays absent), and `hooks` and `gitconfig` (D4: the live test then requires `guard_digest` to differ when the probe wrote). The `hooks` and `gitconfig` probes run **after** the `commit` probe and never use the tester's truncating `w` helper. `hooks` creates `.git/hooks/probe-<marker>`, a name no git command runs, which tests the listed `.git/hooks` entry. `gitconfig` appends a harmless comment line to `.git/config` itself (`printf '# probe-<marker>\n' >> .git/config`), which needs write access to that file, never truncates it and leaves git working; a `WROTE` result changes the content, so the live test's `guard_digest` requirement holds. Neither can change the `commit` result or leave a live hook or a truncated `config`. `judge(output)` fails closed: a missing line, a conflicting repeat, an unexpected result or an unknown probe name is a failure. `sandbox_probe_argv` is `codex sandbox -P worker -C <worktree> -c <shell policy> -- sh -c <command>`.
- **D8. The live proof is opt-in and measured.** `tests/test_codex_worker_sandbox_live.py` runs the identical probe command twice on a scratch clone, as `tests/test_codex_sandbox_live.py` does for the tester: `codex sandbox -P worker` (no model, no spend) and one short `codex exec` turn (proof that `exec` applies the profile). It is skipped by default and on CI, with the reason (`CONTROLLER_LIVE_CODEX_TESTS=1`, `codex`, `bwrap` and a credential file are needed). It asserts on the host after each run: the tracked file changed, the commit exists in the clone's `git log`, no file exists outside the worktree and scratch, the credential and canary are unread. The result lines and the hooks/config finding are recorded in `tests/harness_contract/codex/worker_sandbox.txt` and stated in `docs/guide/harnesses.md`.
- **D9. Not wired in.** The module is only registered in the package. `harness.CODEX.roles`, `worker_launch.LAUNCHERS`, routing, settings, options, exit codes, gates, `worker.py`, `review.py`, `codex_sandbox.py`, `codex_bridge.py`, `codex_tester.py` and `codex_build.py` are unchanged. No real Codex runs in the default suite: the offline tests use a fake credential file and no process; the opt-in live test is the only one that starts Codex.
- **D10. Release type.** `chore:`. The module has no caller and no operator-visible change. If review finds one, the title becomes `feat:` before the plan is approved, not after.

## Functional review

Every flow is offline and unit-level except the one live flow (no real network or `gh` in any). Run from the product clone with `TMPDIR` set to a writable scratch directory, one module at a time, `python3 -B` and no `PYTHONPATH=.`: `tests.test_codex_worker_sandbox`, then `tests.test_package_structure`, `tests.test_codex_sandbox`, `tests.test_codex_tester`, `tests.test_worker_launch`, `tests.test_harness` and `tests.test_write_containment` (they show the neighbouring modules are unchanged and the scan accepts the new one), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. A flow that creates temporary folders or runs git needs a writable `TMPDIR` and is `environment` when the tester's `/tmp` is read-only; `tests.test_codex_worker_sandbox` is such a flow and is operator-run there. The live flow (`CONTROLLER_LIVE_CODEX_TESTS=1 python3 -B -m unittest tests.test_codex_worker_sandbox_live -v`) needs a real `codex`, `bwrap` and a recorded `verify-codex` build and is operator-run; its output is the capture file. The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **A narrower `read` entry under a writable path may not be honoured.** D4 does not assume it: the guard digest is the second line, and the live test records which one held. If neither held for `.git/config`, the guide says so and H4b2 must compare the digests around every launch; this item still ships because nothing launches.
- **The profile may behave differently under `exec` than under `codex sandbox`.** D8 runs both for that reason, as the tester's proof did. A difference fails the live test and blocks acceptance, not the default suite.
- **A commit needs more of `.git` than the profile lists.** The worktree entry is writable, `.git` included, so objects, refs and the index are covered; the probe `commit` is the check. Garbage collection and `git worktree` operations are not probed.
- **The composed-configuration check is missing for the worker profile.** D6 states it: a layer outside the home or an app-server composition difference is not seen until H4b2 adds the check. Nothing launches before then.
- **Write containment.** The module writes only through `controller/runtime.py` primitives; `tests.test_write_containment` fails if a direct write or `.replace(` call appears. Primitives that do not yet exist are added to `runtime.py`, not the new module.
- **The real job's tree.** Real jobs run in the repository; D2 requires an own `.git` directory and refuses otherwise. Choosing how a real job gets such a tree is H4b2's and H4c's, and the guide says it is open.
- **Out of scope:** the launcher, the run, `WorkerResult`, fixture registration and the composed-configuration check (H4b2, #255); job records, reaping and usage for Codex workers (H4c); usage windows (H4d); review roles on Codex (H4e); `milestone-implement` on Codex (H4f); the remaining roles (H4g); any change to the Claude worker launch, the Codex reviewer or tester, settings, options, exit codes or gates.
