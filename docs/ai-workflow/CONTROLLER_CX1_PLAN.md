## Goal

Three accepted Codex worker items left open review follow-ups: [#320](https://github.com/RodrigoFAbreu/workflow-controller/issues/320) (H4e2), [#339](https://github.com/RodrigoFAbreu/workflow-controller/issues/339) (H4e3) and [#341](https://github.com/RodrigoFAbreu/workflow-controller/issues/341) (H4e3b). Each fails closed today and none hurts a run, but #320 names a real defect (a target repository's `gpg.program` can run in the recorder's commit) that the item's own text says to fix before a Codex role is routed. After this item the defect is fixed, the small code gaps are closed with tests, and the pages say what remains true. **The item adds no mechanism**: every change tightens or words something that exists (a pinned Git setting, a recorded evidence key, a narrower predicate, a dropped environment key, a comparison, a sentence). If a reviewer finds that one of them needs a new mechanism after all (a new record, command or protocol row), that finding is split out as its own item and is not fixed here.

## What exists

- **The recorder's commit.** `controller/review_recorder.py` runs the Workflow's `commit_pending_applying_review_feedback_entry` (a plain `git commit`) through `workflow_contract.run_in_private_copy(..., real_index=True)`. `controller/workflow_contract.py` `_GIT_PINNED_CONFIG` pins `core.hookspath`, `core.fsmonitor`, `core.splitindex` and `log.showsignature`, and `_git_isolation` re-reads the configuration to prove each pin is the last command-scope value. It pins no `commit.gpgsign`, so a target's own `commit.gpgsign=true` with its own `gpg.program` runs that program (F-756421cba9ce reproduced it: the program ran and the commit failed with exit 128; a hanging program meets the 120 s timeout).
- **The review role's run.** `controller/codex_review_role.py` `_run` reads `last-message.md` as bytes, then removes it with `runtime.remove_tree` and swallows `(OSError, ControllerError)`; `after_check` compares the clone with the base through a fresh index (`read-tree`, `status --porcelain=v1 -z --untracked-files=all`), the refs and `HEAD`, and walks `.ai-review` with `os.walk` against the input manifest, which records each file's `sha256` and mode.
- **The carry and the guarded regeneration.** `controller/job.py` `_guarded_regeneration` records `ownership_tag` in its `checked` and `started` blocks and writes `finished` without it; `_interrupted_publication` accepts any first reconcile whose reason is `reconcile_invalid`; `_landing_gate_before_queries` and the implementation role's gate text handle `surface_landing_touched`. `controller/workflow_contract.py` `interpreter_environment` drops `PYTHON*`, `BASH_ENV` and `ENV` from the generator's environment. `_carry_failure_fields` builds `codex_carry.not_written`.
- **The pages.** `docs/common-problems.md` (the regeneration gate list and the carry entry) and `docs/guide/harnesses.md` (the carry and "what the Controller runs after a landing") describe these behaviours.

## Decisions

- **D1. Pin the signing switch-off where the hooks' is.** `_GIT_PINNED_CONFIG` gains `commit.gpgsign=false` and `tag.gpgsign=false`, and `gpg.program` set to `false` (the program a signing request would run is then one that fails and runs nothing of the target's). It is in the shared pins, not only under `real_index`, so every Workflow query, the read-only ones included, gets the same configuration, and `_git_isolation`'s existing re-read proves each pin is in force (a Git that does not apply them is `query_git_not_isolated`, as it already is for the others). One principle: nothing in the target's Git configuration may start a program in a Workflow run. A test sets `commit.gpgsign=true` and a marker-writing `gpg.program` in the target's local configuration, runs `commit_pending`, and shows the commit is made unsigned and the marker is absent.
- **D2. Name a failed deletion; do not swallow it.** When the removal of `last-message.md` fails in `_run`, the ending's evidence names it (`last_message_removal_error`, the same shape as the existing `clone_removal_error`), attached **once**, to whatever `Ending` `_run` returns after the removal, the way `run_review` adds `clone_removal_error` once to the ending `_run` returned, so no return path (the credential refusal, `WORKER_FAILED`, `read_only_violated`, the recorded endings) can drop it; the credential path is unchanged. The ending's outcome does not change: a retained message is a leak to report, not a reason to change the verdict. A test makes the removal fail and shows the key on two different endings (a recorded ending and `WORKER_FAILED`). The two untested branches F-4b73d0cc9188 names get one test each: a `.git` path component in an input is refused as `submodule`, and a symlink replacing an input is reported `non-regular`; a mutation of either branch must fail a test.
- **D3. The after-check compares what it says it compares.** Four gaps, one comparison each, none new in kind: the manifest's recorded mode is compared with the file's (`input <path> changed mode`); a symlinked `.ai-review` (an `lstat` of the directory itself, before the walk) is a problem; ignored untracked files are listed too (the fresh-index `status` gains `--ignored`, and `.ai-review` stays the only allowed path), so a worker's `.gitignore` of `*` hides nothing; and the false refusal on an attribute-normalised file is removed by comparing each tracked path with the base tree **per `ls-tree -r` entry**, in place of the filtered `status` comparison for tracked content (`status` still lists untracked and ignored paths). The comparison is by type and mode as well as bytes, from an `lstat` of the path: a regular file (`100644`/`100755`) must be a regular file whose executable bit matches the entry's mode and whose content equals the entry's blob, read as raw bytes (`git hash-object --no-filters`, which the attributes and `core.autocrlf` cannot change) with **one accommodation for checkout conversion** (CX1-EXT-001): the file passes if its raw bytes hash to the entry's object id, **or** if its bytes and the blob's bytes (`git cat-file blob <id>`) are equal after each `\r\n` is replaced by `\n` in both. That covers the two ordinary directions: a file stored LF and checked out CRLF under `*.txt text eol=crlf` (raw bytes differ from the blob, newline-normalised bytes equal), and a file stored CRLF and checked out unchanged under a later `*.txt text` (raw bytes equal the blob). No clean filter, no attribute lookup and no program runs, so the worker's own `.gitattributes` or configuration cannot change the comparison; the cost is that an edit which changes only line endings is accepted (for a text file it changes no content; for a path the base marks `binary` or `-text` it can, and is accepted all the same, which is harmless because a read-only clone is discarded, CX1-L3-O1), and every other byte difference is still refused. **The two other conversions Git applies at checkout under the scrubbed configuration are declared a known false refusal, not computed** (CX1-L3-I1): a path under the `ident` attribute (checkout expands `$Id$` to `$Id: <blob> $`) and a path under `working-tree-encoding` (checkout writes e.g. UTF-16 for a UTF-8 blob) hold bytes that equal the blob neither raw nor newline-normalised, so such a path is refused as `input`-style `read_only_violated` even in an unchanged clone. Computing the checkout bytes (`git --attr-source=<base> cat-file --filters`) would need Git 2.40 or later and a second reading of the base's attributes, which is a mechanism this item does not add; the refusal fails closed (the verdict is discarded, nothing is accepted that should not be) and `docs/common-problems.md` names it and its remedy (route that repository's review through a role other than the Codex review role, or remove the attribute for the review). A test pins the refusal; a symlink (`120000`) must still be a symlink whose `readlink` text, hashed as a blob (`git hash-object --stdin` of the link text, never the path, because `--no-filters` on a link path follows the link and hashes its target), equals the entry's object id; a gitlink (`160000`) must still be a directory and is otherwise skipped (its content is the submodule's); a path that is missing, or whose type differs from the entry's, is a problem. Checked with Git on this machine (and by the external review's probe for the `eol=crlf` case): `chmod +x` of a tracked file leaves its raw bytes at the base blob (`status` reports it, the bytes do not), and `hash-object --no-filters` on a tracked symlink hashes the target's content, not the link text, which is why the type and mode come from `lstat` and not from the bytes. Both false-refusal fixtures must pass as unchanged clones: F-a40ae7e802a5's (a file committed CRLF under a later `*.txt text`) and CX1-EXT-001's (a file stored LF and checked out CRLF under `*.txt text eol=crlf`); the two worker attacks of F-a02f340ed752 must be refused, so must a worker's one-byte edit of the `eol=crlf` file, and so must a mode change and a symlink swap of a tracked file; an unchanged clone holding a tracked symlink must pass.
- **D4. `finished` keeps the run's tag; the publication check names its two states.** `_guarded_regeneration`'s `finished` block carries `ownership_tag` (so `_scan_record_owned` scans the run's tag after a kill past `regeneration_finished`). `_interrupted_publication` is narrowed **for the plan role only** (`apply-plan-review`), the one role whose stale-bundle check (`_is_expected_stale_bundle`) reads a carried revision: there it accepts only the two torn-manifest shapes its docstring names (a missing manifest, or `current/MANIFEST.md` already at the carried-out entry's `plan_revision`), judged by the same two reads `_is_expected_stale_bundle` makes (`_manifest_plan_revision`, `_carried_out_entry`), and not a `REJECTED` bundle (its `lstat` stays); any other `reconcile_invalid` reason ends the record without the extra generator run, which was the outcome already. The two implementation-stage roles that share `_guarded_regeneration` (`apply-implementation-review`, stage `post-fix`, and the self-review role, stage `implementation`) **keep today's check unchanged** (an in-flight `regeneration` stage with a `reconcile_invalid` first reconcile reruns the generator under the guard), because the implementation stage has no carried plan revision to compare and inventing one would be a new mechanism; narrowing those roles, if an owner wants it, is its own item. The dispatch therefore passes the record's role to the predicate; the behaviour change is declared: only the plan role loses the rerun for an unrelated reason.
- **D5. Drop `BASH_FUNC_*`, `SHELLOPTS` and `BASHOPTS` from the generator's environment.** `interpreter_environment` also removes every key that starts with `BASH_FUNC_`, and the keys `SHELLOPTS` and `BASHOPTS`, so an exported `python3` or `git` function cannot override the private `bin/python3` pin and a bash generator cannot be started with `xtrace` and a `PS4` holding a command substitution (the same inherited-bash-configuration class as `BASH_ENV`; the plan review, CX1-L1-O2, found it outside #341, and it is two more names in the same drop, not a mechanism). The test exports a function named `python3` and `SHELLOPTS=xtrace` with a marker-writing `PS4` through the environment of the Controller process and shows both are absent from the mapping and, in a run of a real bash generator, that neither ran.
- **D6. Words, not mechanisms, for the three findings that ask for a choice.** For each, the plan takes the documentation option the finding offers, because the code options add a mechanism (a planned-writes record, a read of the managed artifacts file into the carry's named set, a stored gate):
  - **#339 item 1** (`not_written` at the check): the pages say that a refusal at the check writes nothing and `codex_carry.not_written` then names only the state file when it caused the refusal; the sentence "A change found at the check, or when `resume` finishes an interrupted carry out ..., writes nothing more, or a write failed part-way" is reworded to say the same. `docs/guide/harnesses.md` says it too.
  - **#339 item 2** (extra `plan_stage.protected_paths`): `docs/guide/harnesses.md` and `docs/common-problems.md` say that an item whose artifacts file declares more plan-stage protected paths than the five named files is refused (`carry_foreign_dirt` in, `carry_out_of_set` out), and that the operator applies such an item's plan or review change by hand. Reading the paths from the managed artifacts file would be a new trust decision and is left to its own item if an owner needs it.
  - **#339 item 3** (a run past `carry_bundle_regeneration_pending`): `docs/common-problems.md` says that the gate holds only for the `run` that ended on it, that running again without regenerating gives a `FAILED` review job and not the gate (the recorder's own checks refuse), and what to do. One test runs the next review without regenerating and shows the refusal ends the job `FAILED` and records nothing, which pins the fail-closed claim the page now makes.
- **D7. The landing gate says what else runs the landed `scripts/`.** For a `surface_landing_touched` refusal the implementation role's gate text, and the `docs/common-problems.md` entry, add that `explain` and every later Controller step also run the Workflow's queries over the landed `scripts/`, checked only against the committed `.workflow-manager/installation.json` (which the landing can edit with a script), so the operator restores or verifies `scripts/` and `.workflow-manager/` before running any Controller step, `explain` included. The check in `_landing_gate_before_queries` is unchanged.
- **D8. Test what the repository's guards require.** Every test is hermetic (a scratch repository, a fake `codex`, a marker file, no network), so each new test passes the repository-wide guards (leftover processes, write containment, no bare `.replace()` outside `runtime.py`).
