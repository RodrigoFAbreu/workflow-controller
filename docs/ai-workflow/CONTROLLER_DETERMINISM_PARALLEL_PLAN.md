## Goal

Since C2b the whole-catalogue determinism check runs after the merge and the release waits for it. On the first `main` run (37c80b6) `after-merge-determinism` took **32.1 minutes** against 17.3 for `after-merge-mutations`, so every release publishes about 32 minutes after its merge and the next merge's run waits behind the `main-release` slot for that long ([#126](https://github.com/RodrigoFAbreu/workflow-controller/issues/126)).

The job is slow because `tests.test_catalogue_determinism` runs the whole scenario catalogue twice, one complete run after the other, inside one test. The two passes are independent of each other, so they can run at the same time. The target is a determinism job about as long as the mutations job (17 to 18 minutes), which makes the longest after-merge job roughly half of what it is.

## Decisions

Each decision states one principle.

- **D1. The two passes run at the same time, in one test, on two clones.** `CatalogueDeterminismTest` runs pass A in the class's clone and pass B in a second clone made from the first (`git clone -q --no-hardlinks <clone> <second>`, so it has the same `HEAD`, the same committed code and the same work-item state), each into its own output folder, in two threads that wait on their own `run_scenarios.py run` child. The passes never share a checkout, because a scenario run reads the checkout's Git state and two runs would contend for its index. The comparison, the ingestion check of the first pass's records and the size and `selftest` assertions stay exactly as they are. The test keeps its name and its module, so `CI_PLACEMENT`, `ci_workflows.py`, `main.yml` and the job names do not change.
- **D2. A failed or hung pass fails the test, within a finite time, and never leaves anything behind.** Each pass runs its `run_scenarios.py run` child through a bounded runner: the child starts in its own session (`start_new_session=True`) as a **reaping subreaper**: the runner launches `python3 -I -c <reaper> -- <argv>`, whose first act is `prctl(PR_SET_CHILD_SUBREAPER, 1)` (through `ctypes`, as `tests/process_fixtures.py` does at line 687), and which then runs the real command as its child and waits for it. The scenario kit deliberately puts its heavy descendants in sessions of their own, so a process-group signal does not reach them: `kit._launch` starts every sandbox chain with `start_new_session=True` behind `timeout -s KILL` (`tests/scenarios/kit.py:330-331`) and the scenario's Controller children start through `process_fixtures.popen_bounded(..., start_new_session=True)` (`tests/scenarios/kit.py:914-916`), each living up to `LEFTOVER_LIFETIME_SECONDS` (600 s, `tests/process_fixtures.py:54`), and `tools/run_scenarios.py` installs no signal handler, so no `Scenario.close()` runs when the group is signalled. The subreaper is what reaches them: when the real command exits or is killed, every descendant that survives it, in any session, is re-parented to the reaper (the sandbox `unshare` has no `--pid`, so orphans are not captured by a namespace init). The pass has a deadline of 2700 seconds (45 minutes, against about 16 minutes for one sequential pass on the base commit). At the deadline the runner sends `SIGTERM` to the group and to the reaper; the reaper's handler signals its real child's group, then repeatedly lists its own children (`/proc/<pid>/task/*/children`), sends `SIGKILL` to each adopted descendant's session and process group and to the process itself, and `waitpid`s every one until none remains, then exits. If the reaper has not exited within a 10-second grace period the runner sends `SIGKILL` to the group and then sweeps backstop-style: it kills and waits out every process still carrying the pass's tag in its command line or environment (`kit.tagged_pids` / `kit.wait_no_tagged`, `tests/scenarios/kit.py:463-495`). The tag is a **pass-owned temporary root**: the runner creates one directory per pass (`tempfile.mkdtemp(prefix="det-pass-")`, removed by the test's cleanup) and starts the child with `TMPDIR` set to it, so the scenario kit's own scratch directory, which `kit.run_scenario` makes with `tempfile.mkdtemp(prefix=f"scn-{flow_id}-")` (`tests/scenarios/kit.py:575`) and which therefore lives under that root, is the one place every sandbox descendant's environment is rebuilt from: `kit.build_env(scratch)` (`tests/scenarios/kit.py:668-680`) sets `PATH`, `HOME`, `TMPDIR`, the `XDG_*` variables and `SCENARIO_SCRATCH` to paths under the scratch directory and carries neither the clone path nor the output folder, so a tag made of those would miss an ordinary descendant such as `sleep`, but a tag made of the pass's temporary root is a prefix of every one of those values. The sweep tags by that root (and also by the clone path and the output folder, which still catch the pass's own `run_scenarios.py` processes), repeats until no tagged process is left or a bound of 10 seconds passes, `SIGKILL`s each survivor, and reaps those that are children of the runner with `waitpid`; a survivor that is not the runner's child is waited out until it is gone (the subreaper has already adopted and reaped every descendant on the normal path, so the sweep is a backstop and finds nothing there). A tag that is still matched after the bound fails the call with a named leak, never silently, and it reaps the reaper with `wait()`. So no descendant, in the group or in another session, outlives the call; the runner then raises a timeout failure naming the pass, the deadline and the output captured so far. The helper that runs the two passes waits for both callables to return (each is bounded by its own deadline, so the wait is finite: at most the deadline plus the grace period), then raises the failure of the first pass that failed (its return code, stdout and stderr, or the timeout), so a failing pass is never masked by the other's success. It returns the two results in pass order. The second clone and both output folders are removed by the class's and the test's cleanups, which run only after the helper has returned or raised, that is, after every child has been reaped. A failure or a timeout of either pass fails the test; there is no retry and no tolerance.
- **D3. The fail-closed rules of `main-check` are untouched.** An empty or short selection, a skip and a failure still fail the job; the module's test ids are unchanged except for the helper's own unit tests (D4), which are ordinary tests of the same module and run in the same job.
- **D4. The concurrency and lifecycle helpers have tests of their own.** Whether the passes really overlap, that the results come back in pass order, and that a failure of either pass (the first, the second, and both) is raised only after both have finished are tested on stand-in callables, not on the catalogue. The bounded runner is tested on a real subprocess: a deliberately stalled stand-in command that itself starts two sleeping descendants, one in the same group and one that leaves it the way the scenario kit's do (`start_new_session=True`, behind `timeout -s KILL` like `kit._launch`), each recording its pid in a file, run with a deadline of a few seconds and with the stand-in's environment rebuilt the way the kit rebuilds it (a scratch directory made by `tempfile.mkdtemp` under the pass's temporary root, then `kit.build_env(scratch)`), so the descendants carry the scenario scratch path and neither the clone path nor the output folder, must fail within the deadline plus the grace period, with the child and **both** descendants gone before the runner returns (reaped, `os.kill(pid, 0)` raises `ProcessLookupError`, and no process tagged with the test's scratch path remains); a variant whose reaper is made unresponsive (it ignores `SIGTERM`) shows that the grace expiry, the group `SIGKILL` and the tagged sweep by the pass's temporary root still remove the other-session descendant, which matches neither the clone nor the output tag (an inherited pass tag would conceal the defect), and asserts that it is terminated and reaped before the failure returns; a second case runs the stalled command as one pass and a terminating command as the other through the helper, and asserts that the sibling completes, that the failure is raised only after the stalled one is reaped, and that the clone and output folders still exist until the helper has returned and are removed by the cleanups afterwards. All of these are ordinary tests of the same module, next to `IsolationGateTest`.
- **D5. The speed-up is measured, and a shortfall amends the plan.** The pass-two clone and the concurrency add CPU contention on a 4-vCPU runner. CP2 measures the module locally on four CPUs (`taskset -c 0-3`), before and after, three runs each, and records every wall time. "At least 30% faster" means the concurrent median is at most 0.70 of the sequential median. If it is not, on four CPUs, or any scenario fails under the contention, the milestone stops and is amended (`/request-plan-amendment`) to the form the issue also names: two jobs that upload their normalised summaries and a short third job that compares them. It does not ship a form that is not faster, and it does not weaken a scenario's timing to pass.
- **D6. The documentation changes with the behaviour, in place.** `docs/guide/ci-and-releases.md` says that the two passes run at the same time and gives the new expected wait; the stale "(#126 tracks making it faster)" wording and the 32-minute figure become a statement of the current behaviour with the old figure kept as the measured baseline. `docs/ROADMAP.md` marks #126 done and drops it from "Next, in order"; `docs/ACTIVE_MILESTONE.md` records the milestone. The first `main` run's measured job time is recorded in the documentation pull request that follows the merge, because it exists only after the merge.
