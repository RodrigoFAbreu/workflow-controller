Work item: `workflow-controller-gate-policy`
Work item type: `product`
Governing workflow version: `2.2` (this repository's `docs/ai-workflow/WORKFLOW_CONFIG.json` default at creation)
Base commit: `07d0d6d8c572c7495d945568ec1a3461a9fb523a` ("docs: 1.13.1 release notes (#80)"), the tip of `main`, passed explicitly as `/milestone-plan 07d0d6d…`.
Lifecycle authority: this repository's installed Workflow **2.12.0**, automatic gates.
Roadmap slot: `docs/ROADMAP.md` step **C10a**, the first third of C10 (decision D1), first of "Next, in order".
Released baseline: `workflow-controller 1.13.1`. The change adds a routing role (`satisfy-gate`), so the squash commit is a `feat:` and releases the minor release **1.14.0**.
Pull request title: `feat: launch the Workflow's gate-policy validations so a satisfied gate passes without a person`

## Goal

Today a gate the owner set to `automatic` still stops the Controller. The Workflow answers `next-action` with the disposition `validation` and an action `plan.satisfy`, `implementation.satisfy` or `acceptance.satisfy` (rows 14a, 28a and 38h), and the Controller blocks any disposition it does not know, so a person or an orchestrating session has to run `/satisfy-gate` by hand (as every milestone since C9d has done). This milestone makes the Controller launch that command itself, as a worker, exactly as it launches `/review-plan`. After it a run passes plan approval, technical approval and acceptance on its own when the Workflow says the policy is satisfied, and stops where the Workflow says a person is needed.

Two smaller changes of the same step ride with it, both already decided and both about "what is a stop" (the second is completed only in part here, see D7): a value that a protocol 1.x minor release adds to a closed enum is advisory or blocked, never a refusal of the whole answer (follow-up 17), and a notification asks for the owner only when the owner is needed (follow-up 26).

## Decisions

Each decision states one principle.

- **D1. C10 is three steps, because one milestone of its size cannot be reviewed in few rounds.** `docs/ROADMAP.md` step C10 holds three separable pieces: this one (C10a, the gate-policy validations and the two follow-ups), the pull request defect loop (C10b, `pr.apply_review` and its place in the merge flow of C4) and the automated functional review (C10c, section 11.9). Each is released on its own. The order stays: C10a, C10b, C10c, then C12, C11 and O1-O7. CP5 rewrites the roadmap row and the "Next, in order" list; no part of C10 is dropped.
- **D2. The Workflow decides and the Controller only launches.** A `validation` answer is launched only when its action id is one of the three `.satisfy` ids in the action table, the worker is not `user_only`, and its role is `validator`. The table pairs each action id with the disposition the Workflow gives it (`plan.satisfy` with `validation`, `plan.review.local` with `automatic`); an id answered under another disposition, an unknown id, a `user_only` worker or any other role is blocked exactly as an unknown value is today (`workflow_unknown_action`, `workflow_unknown_worker_role`). The Controller reads no `GATE_POLICY.json` and evaluates no requirement: that is `/satisfy-gate`'s own `evaluate_gate`. A human gate (`human_gate`, or a policy with `human_approval: true`) is answered by the Workflow as `human_gate` and stops, as before.
- **D3. The stage word is part of the table, and the worker's command is rendered here, not read from the answer.** `PROTOCOL_ACTIONS` entries gain a fixed tuple of leading arguments, so `plan.satisfy` renders `/satisfy-gate plan <id>`, `implementation.satisfy` renders `/satisfy-gate implementation <id>` and `acceptance.satisfy` renders `/satisfy-gate acceptance <id>`. The existing invocation check compares the answer's text with the rendering and blocks a difference (`workflow_invocation_mismatch`); no other action id changes its rendering.
- **D4. The validator is a role of its own, because it records a decision.** A routing role `satisfy-gate` is added: Opus at `xhigh`, single-agent (the `Skill`, `Agent` and `Workflow` tools disallowed), as `review-plan` is, because it runs a transaction that commits and must not delegate it. It is overridable like every role (`--role-model`, the routing file) and joins the settings file's role names, which raises the settings table generation to 9. `pr.apply_review` stays in `UNLAUNCHED_AUTOMATIC_ACTION_IDS` for C10b; the other three leave it.
- **D5. A refused validation is a stop, not a retry, and it is not an approval.** When `/satisfy-gate` finds a requirement unmet it writes nothing and the phase is unchanged. The step is recorded as the Workflow's `reconcile` classifies it (no progress or a gate reached); `_protocol_resolution` finishes such a job with `progress: "none"`. The existing round counting and the loop guard (`no_progress_repeated`) let two refused validations run and block the third launch (`_no_progress_gate`), and `explain` shows the unmet requirement from the worker's report. No new stop code and no new exit code. Because `derive_job_event` sends `approval_recorded` for every finished `/satisfy-gate` job, CP2 changes it to send `approval_recorded` (and, for the acceptance stage, `milestone_accepted`, which already keys on the post phase) only when the phase moved, read from the job record (`observed_phase_before != observed_phase_after`), and not from the reconcile class: in 2.12.0 `reconcile` classes a step `gate_reached` even when the phase moved, whenever the next answer is a `human_gate` or `external_gate` (for example `/satisfy-gate implementation` moving to `AWAITING_FUNCTIONAL_REVIEW` with a matching checklist already committed, next answer row 38e or 39), so keying on `progress` would drop a real approval's notification. A refused validation leaves the phase unchanged and sends `step_done` only.
- **D6. A closed enum in a 1.x answer is open, with a rule per field, and the rule is held by a test over the whole schema (follow-up 17).** The vendored schema has twenty enum locations (round 3, I2): seven are already open in `OPEN_ENUMS` (the error code, the action id in `action` and in `nullable_action`, the decision disposition and `satisfied_by`, the worker role and the verify check id) and thirteen are closed (the protocol name, and twelve a minor release could extend). One table, `protocol_schema.ENUM_RULES`, classifies **all twenty** as `identity` (the protocol name: only a major change refuses), `advisory` (shown, never gates, never changes what the Workflow said), `blocked` (a decision depends on it, so the step ends in a gate that names the value, launching nothing) or `ignored` (the Controller reads no decision from it). The seven existing locations keep exactly the behaviour they have (an unknown action id, worker role or disposition is already a semantic block before any launch: `workflow_unknown_action`, `workflow_unknown_worker_role`, `workflow_unknown_disposition`) and are listed with the rule that describes it. `OPEN_ENUMS` is derived from the table as every location but `identity`, so the seven stay open and the thirteen join them minus the protocol name; a test pins the seven by name so the derivation can never close one. The classification of the thirteen newly opened fields, from the measured use of each in `controller/`: a `verify` check status other than `pass`/`warn`/`fail`/`skip` is `advisory` (shown with the `warn` lines; `healthy` stays the Workflow's boolean); a `reconcile` class, a `record-external-result` stage or verdict, and a functional-evidence status the Controller must act on are `blocked`; `allowed_results` items, the policy gate and mode, the forge source, the resolve-artifact kind and the `pr_reported` slot are `ignored` or `advisory` where the Controller only displays them. CP3 first lists the use of each field and amends this sentence if the measurement differs, and a test fails when the schema holds an enum location that `ENUM_RULES` does not name, so a later vendored schema cannot add one unclassified.
- **D7. A stop that needs no person does not ask for one (follow-up 26), as far as this step can know.** A job that ends `GATE_BLOCKED` sends `user_gate` (the owner is needed) unless the Workflow's own disposition recorded in the job's `protocol.decision` is `blocked`, which sends `lane_blocked` ("Blocked: …", the blocker kind) with the same identity rules. D2 removes the stop for plan approval and technical approval and for acceptance when its requirements are met, but not every stop under an automatic gate: the Workflow still answers `external_gate` at rows 38e (`functional_evidence_needed`), 38f (`pr_evidence_needed`, for example while the pull request's checks are still running) and 38g (`pr_approval_needed`), and the Controller cannot satisfy them until C10b (38f, 38g: the `pr_review_result` reporter and `pr.apply_review`) and C10c (38e: the automated functional review) land. Those stops keep `user_gate`. Row 38e needs functional evidence, which the automated functional review of C10c produces; rows 38f and 38g belong to C10b (round 3, O1). **The 38f stop does not clear itself (round 2, I1):** once a refused `/satisfy-gate acceptance` has stored a pull-request fact whose checks are `pending`, the Workflow queries GitHub again only when no fact is stored or a reported `pr_review_result` is newer than the stored fact (`pr_query_trigger`); `next-action` never runs `gh`. So when the checks turn green the answer stays 38f (`pr_evidence_needed`) until a person runs `/satisfy-gate acceptance <id>` by hand. **Reporting a fresh `pr_review_result` is not a recovery in this step (round 3, I3):** it makes `pr_query_trigger` true, and under the default enabled pull-request review policy Workflow 2.12.0 then answers row 38d, the automatic `pr.apply_review`, which precedes row 38h; C10a leaves that action unlaunchable (D4), so the Controller stops again with the unlaunchable-action block. The manual `/satisfy-gate acceptance <id>` is the only remedy until C10b launches `pr.apply_review`; the runtime guide (D9) says so. CP5 marks follow-up 26 **partly done**: it names this remaining case and C10b as the step that owns it, rather than claiming a gate in automatic mode never stops. The Controller's own gates (the round cap, a merge permission, a usage pause) keep `user_gate`.
- **D8. Every behaviour change is shown on a real Workflow answer.** The tests use the vendored Workflow 2.12.0 tree's `next-action` answers for rows 14a, 28a and 38h (`tests/workflow_releases/2.12.0`), not only hand-made documents, and one lifecycle scenario with fake workers runs a plan to acceptance under automatic gates.
- **D9. The documents are changed in place.** The commands guide (the role table), the runtime guide (routing, automatic gates, the stop reasons, and the 38f stop of D7 with its one remedy until C10b: run `/satisfy-gate acceptance <id>` by hand; reporting a `pr_review_result` leads to the unlaunchable `pr.apply_review` of row 38d), the automation guide, the compatibility page (what a minor release may add), the common-problems page and `docs/ROADMAP.md` say what the Controller does now; none keeps a "until C10" sentence. An ADR records D2 and D6.

### CP2 -- A satisfied gate passes in a run; a refused one stops (D5, D8)

- The validation is an ordinary protocol job reconciled by `reconcile`, so `controller/cli.py` needs no new path. `controller/job.py:derive_job_event` does change (I1): it sends `approval_recorded` for `/satisfy-gate` only when the job record's phase moved (`observed_phase_before != observed_phase_after`; not the reconcile class, see D5), and `milestone_accepted` only on the post phase `MILESTONE_COMPLETE` as today. A refused validation finishes with `progress: "none"`, leaves the phase unchanged and sends `step_done` only. Tests pin `approval_recorded` for the three stages when the phase moves, `milestone_accepted` for the acceptance stage, that a refused `/satisfy-gate` sends `step_done` and no `approval_recorded`, and that a `/satisfy-gate` whose phase moved but which `reconcile` classes `gate_reached` (a real 2.12.0 answer: `implementation` moving to `AWAITING_FUNCTIONAL_REVIEW` with a matching checklist committed) still sends `approval_recorded`.
- One lifecycle scenario (`tests/test_protocol_lifecycle.py`, with the existing fake workers and the vendored 2.12.0 Workflow): under automatic gates `run` goes from the plan review to `IMPLEMENTING` through a `/satisfy-gate plan` worker with no stop, and from the functional evidence to `MILESTONE_COMPLETE` through `/satisfy-gate acceptance`. **The acceptance gate's requirements (I3):** the default policy requires `ci_green` and a current pull-request fact, and `/satisfy-gate acceptance` queries GitHub itself through `workflow_forge` (`resolve_gh`, then a `gh` subprocess started by Python). The fixture therefore puts a fake `gh` on the worker's `PATH` and sets a scratch bare origin (the functional-tester isolation rule), with a pull request at the head and green checks, so the answer is row 38h and never reaches the real GitHub; the scenario says so in its docstring. A second scenario has the fake validator refuse (an unmet requirement): the phase is unchanged, the run stops after two refused validations, before a third launch, with `no_progress_repeated`, `explain` names the stop, and no further worker is launched. A third case runs the acceptance stage with the fake `gh` reporting checks still pending, then green: the pending query is refused, the next answer is the real row 38f `external_gate` (`pr_evidence_needed`), the run stops with a `GATE_BLOCKED` job, and the notification is `user_gate` (the case D7 leaves to C10b). **The case ends at that 38f stop (round 2, I1):** the refused validation stored the pending fact, so turning the fake's checks green changes nothing, because `next-action` never re-queries; the test asserts the answer is still 38f after the checks turn green. It continues only through the stated outside act, which the test performs as the person (round 4, I1): it calls the vendored `workflow_state.satisfy_acceptance_gate(repo_root, <id>, now=...)` once, with the fixture's fake `gh` (checks now green) on `PATH` and the scratch bare origin set, outside `run` and launching no Controller worker. That call is the acceptance itself: in the same `state_transaction` it queries `gh`, stores the fresh fact, evaluates the gate and, being satisfiable, calls `apply_acceptance_satisfaction`. The test therefore asserts the item is `MILESTONE_COMPLETE` with an `acceptance_satisfaction` record (the real command's roadmap, narrative and completion-commit writes are not reproduced, and the test says so), never a further 38h answer, which the Workflow does not give after this act; and that the Controller's next `run` launches nothing for the item. A fourth case pins the non-recovery (round 3, I3): after the pending fact, the test records a green `pr_review_result` through the Workflow's `record-external-result` with the default enabled pull-request review policy, and asserts the next answer is the real row 38d `pr.apply_review`, that the Controller blocks it as an unlaunchable action, launches no worker and sends `user_gate`.
- `explain` and `inspect`: the three ids are no longer advised as unlaunchable; the `inspect` text and its golden follow.

## Risks

- **The validator commits (CP1, CP2).** `/satisfy-gate plan` makes the plan-approval commit. A Controller-launched worker with a milestone-branch binding has `git push` and `gh` disallowed, not `git commit`, and the post-step branch check runs after it, as for `/milestone-implement`. CP2's scenario runs with a binding to prove it; a break stops the checkpoint and amends the plan.
- **The validator reaches GitHub from inside the worker (CP2).** `/satisfy-gate acceptance` queries the forge itself (`workflow_forge.resolve_gh`, `subprocess.run([gh, ...])`). The binding's `Bash(gh:*)` and `Bash(git push:*)` rules disallow the worker's *tool* calls only; they do not stop a `gh` that a Python subprocess starts, so the query succeeds in a real run. This is intended: it is a read-only query the Workflow makes to record the pull-request fact, and the Controller adds no second GitHub path. Tests never reach it, because the fixture supplies a fake `gh` and a scratch origin.
- **Deciding the unknown enums (CP3).** The rule per field is a judgement on how each value is used. The measurement comes first and the test over the schema keeps a later release from adding one unclassified; a field whose use cannot be settled is `blocked`, the safe side.
- **Size.** Four code checkpoints and one for documents. If CP3 grows past one session it is split by amending the plan, not by dropping a field.
- **Open decisions.** `docs/TECHNICAL_DECISIONS.md` does not exist in this repository; no open decision is finalized here. D1 splits a roadmap step on the strength of the workflow's size rule, and the owner can reorder C10b and C10c at the acceptance gate or before.
