## Goal

One mechanism: **the carry**. The two apply roles change work that is not committed (`apply-plan-review`: the plan, the registry, the mapping, the artifacts declaration and the state file, intent-to-add or uncommitted until the plan approval commit) or that needs files a clone does not have (`apply-implementation-review`: the ignored `.ai-review/<work item>/` tree holding the feedback and the bundle's author-written inputs). A Codex worker runs in a private clone that sees committed state only (H4e). The carry is the Controller's own act of putting a bounded, named set of working-set paths into the clone before the worker starts and bringing exactly the changed members of that set back when it ends, with every check made before any write to the managed repository, and recovering it after a kill. It adds no new way to run Codex, no new sandbox rule and no new setting: the worker, the clone, the usage record and the fast-forward landing are H4c to H4e, used unchanged, and the routing is the existing `harness` field of a role's route.

## What the Controller does not do after a landing

Stated once, here, and repeated on the pages (D12). After the implementation role's commits land and after either role's members are carried out, the Controller:

- **does not run `scripts/prepare-ai-review.sh`**, or any other script, module, generator, hook or test of the managed repository's working tree, from `scripts/` or anywhere else;
- **does not regenerate, repair, withdraw or bind the review bundle** under `.ai-review/<work item>/current/`: it writes no generated file there (no `MANIFEST.md`, `files/`, `.pin/`, `CHANGES_SINCE_REVIEW.md` or archive), only the role's carried-out author-written inputs (D3);
- **does not commit, amend or write a generation record** in the managed repository, beyond landing the worker's own commits (H4e) and D4's commit, which runs before the clone is made;
- **does not run the next stage** (`/review-plan`, `/review-implementation`, an approval).

The only Workflow code it runs after a landing is what it already runs on every step: the Workflow's queries, `reconcile` and the recorder driver through `workflow_contract.run_in_private_copy`, which copies the installed release's verified bytes into a private directory and runs them with `-B -E -s` from there, never the managed tree's copies; and Git only through `gitrepo`'s hardened option set. Regenerating the bundle is left to the operator, or to a Claude session the operator starts, through the steps of the existing bundle gate the next decision stops at (D8). Running the generator safely after a landing is H4e3b.

## What exists

- `harness` declares adapter roles; `routing.ADAPTER_ROLE` maps a routing role to one; the two apply roles run as `worker`, which the `codex` adapter does not declare, so `codex` for them is refused at configuration time. H4e2b added the adapter role `local-reviewer`, its `(adapter, role)` launcher registry (`worker_launch.LAUNCHERS`) and `review_mode.worker_families`.
- `codex_worker.CodexLauncher` is the real launcher of a Codex worker, registered under no role. `job._run_codex_worker` prepares a clone through `codex_worker_tree.prepare`, launches, and lands the clone's commits fast-forward through `codex_worker_landing.land`, which refuses with `managed_tree_not_clean` unless the managed tree is clean. `prepare(read_only=True)` makes the clone from the commit whatever the managed tree holds.
- `codex_review_role` (H4e2) copies a review's inputs into a clone and refuses a credential-named input, a symlink or special file, a `.git` component, a gitlink, an escaping path, an over-bound input and key armour (`ARMOUR`). `review_recorder` runs the Workflow's own writers through a driver in `run_in_private_copy`; its interface already names `state_transaction` and `commit_pending_applying_review_feedback_entry`.
- `/apply-plan-review` makes no commit and ends at `AWAITING_LOCAL_PLAN_REVIEW` with a bundle it regenerated and bound. `/apply-implementation-review` commits one fix per commit, then a generation-record commit that moves the phase to `AWAITING_LOCAL_IMPLEMENTATION_REVIEW`, and regenerates the (ignored) bundle.
- When the managed bundle does not belong to the state, the next decision already stops at a human gate that names the regeneration steps: at a ready plan phase, Workflow's publication status row 4b (`BUNDLE_UNVERIFIED`: the bound content equals the fresh content, the bundle does not verify) gives `evidence._published_stale_plan_bundle_gate`; at an implementation-bundle phase, `evidence._implementation_bundle_gate` gives the regeneration gate. This item adds no gate; it reaches these.

<!-- CP2 -->
- **D3. The carry set of a role is derived from the managed state, closed and named before any spend.** `controller/codex_carry.py` computes, for a managed repository, a work item and a role, a `CarrySet`: the exact paths that go into the clone and the subset that may come back, each with its kind and SHA-256. The paths come from `WORKFLOW_STATE.json`'s record of the item, read in the managed repository, never from the worker. Every path of the managed repository is judged by exactly one of these rules:
  - **Named files.** `apply-plan-review`: the item's `plan_path`, `registry_path`, `mapping_path`, its `<work item>-artifacts.json` and `docs/ai-workflow/WORKFLOW_STATE.json`, carried in and out. `apply-implementation-review`: none (its tracked tree is made clean first, D4, and its commits land under H4e's rules).
  - **Every other tracked or untracked non-ignored path** (as `git status --porcelain` reports with the default ignore rules): dirty at carry in is `carry_foreign_dirt`, naming the paths, before any clone is made; changed in the clone at carry out is `carry_out_of_set`. The Controller never decides what to do with an unrelated working-tree change.
  - **Carried in from `.ai-review/<work item>/`** (regular files, read without following a link): `feedback/`, `plan-inputs/` and `current/`. Not `.pin/`, `CHANGES_SINCE_REVIEW.md` or `review-bundle.tar.gz`: they are derived, and the worker's own generation in the clone writes its own. Never `.ai-review/runtime/` (the locks).
  - **Carried out from `.ai-review/<work item>/`, the author-written inputs of the role's next regeneration and nothing else:** for `apply-plan-review`, `plan-inputs/REVIEW_REQUEST.md`, `plan-inputs/TEST_RESULTS.md` and `plan-inputs/CONTEXT_FILES.txt`; for `apply-implementation-review`, `current/REVIEW_REQUEST.md`, `current/IMPLEMENTATION_SUMMARY.md`, `current/TEST_RESULTS.md`, `current/CONTEXT_FILES.txt` and `current/PLAN.md`. They are carried out so that the operator's regeneration reads this round's inputs: the managed `IMPLEMENTATION_SUMMARY.md` and `REVIEW_REQUEST.md` otherwise still hold the previous round's revision and `review_content_id`, and the generator's completeness check would withdraw the bundle. A member absent at carry in that the worker creates is a changed member (managed digest "absent").
  - **Derived, written by the worker's generation in the clone, discarded and never judged:** every generated file of `current/` (`MANIFEST.md`, `CHANGED_FILES.txt`, `DIFF.patch`, `COMMITS.txt`, `files/`; for the plan role all of `current/`), `.pin/`, `AMENDMENT_DIFF.patch`, `CHANGES_SINCE_REVIEW.md`, `review-bundle.tar.gz`, `review-bundle.tar.gz.tmp`, the leftovers of an interrupted promotion and the failure artefacts `REJECTED` and `current.rejected-*`. The list is read from the Workflow's own names (`workflow_fingerprint._LEFTOVER_STAGING_PREFIXES`, `workflow_fingerprint.CHANGES_SINCE_REVIEW_FILE`, and the names the generator's promotion and `prepare-ai-review.sh` write) through one `codex_carry` helper, and a test fails when a name the generators write under `.ai-review/<work item>/` is neither a carried-out member nor derived.
  - **Any other path under `.ai-review/<work item>/`**, a change to `feedback/` included, is `carry_out_of_set`. Every other ignored path (`__pycache__/`, `.ai-review/runtime/`, other items' trees) is neither carried nor judged.
  - **A carried-out member present at carry in and absent from the clone at carry out** is `carry_member_refused` (detail `absent`), never skipped: a skip would leave the previous round's inputs for the next regeneration. This covers a worker that deletes one and an implementation-role worker whose own generation in the clone withdrew `current/` into `current.rejected-*`.
- **D4. The implementation role starts from a clean tracked tree, made by the Workflow's own writer.** After a Controller-recorded implementation `REVISE`, `review_recorder` has already committed the pending `APPLYING_REVIEW_FEEDBACK` entry and D4 commits nothing. In the two cases the entry is still pending (a manual-ingest `REVISE`, and a recorder commit that failed), the new driver operation `review_recorder.commit_pending` calls the Workflow's `commit_pending_applying_review_feedback_entry`, before the clone is made. Its failure is `carry_commit_pending_failed`, nothing launched; a managed tree still not clean after it is `carry_foreign_dirt`.
  - *D4a. D4's commit becomes the carry base.* The job captures the pre-step head before the branch (as it does today) and keeps it as `codex_carry.pre_step_head`. `commit_pending` returns the commit it made, or none. When it made one, the Controller checks that the commit's only parent is the pre-step head and that the managed branch is at it (any other movement is `carry_commit_pending_failed`, detail `branch_moved`), and that commit is the **carry base**: it is recorded as `codex_carry.base_commit`, in the record, before the clone is made, and it is the `base` that `codex_worker_tree.prepare` (so `check_managed`'s `managed_branch_moved` comparison), the clone, the landing's `Prepared.base` and every recovery of D7 use. When it made none, the carry base is the pre-step head, and `check_managed` still refuses any other branch movement with `managed_branch_moved`, unchanged. The pre-step head stays in the record beside the carry base. **The job's "moved nothing" baseline is re-captured at the carry base.** Immediately after D4, before the clone is made, the job re-captures the record's `pre_state` (`target_head` and `tracked_changes`) from the managed repository, so `target_head` is the carry base and `tracked_changes` is what remains after D4's commit; the earlier values are kept only as `codex_carry.pre_step_head`. Every "moved nothing" judgement of a carry record reads that re-captured `pre_state` unchanged: `job._limit_moved_nothing` (`HEAD` equals the carry base and the tracked tree equals the re-captured baseline) and `_reconcile_launched`'s interrupted ending (`observed_head` equals the carry base, the phase unchanged). A usage-limited worker or a worker killed before its end is recorded, having changed nothing, is therefore `INTERRUPTED` after D4's commit exactly as it is without one. The carry out is not run for a limited worker, so the managed tree is as D4 left it. A recovery never recomputes D4 (see D7's first stage).
- **D5. The carry in copies bytes the Controller read itself, into a clone made from a commit.** The clone is made by `codex_worker_tree.prepare` at the carry base (D4a: D4's commit when it made one, the pre-step head otherwise), with the dirty-tree refusal skipped only when D3's set accounts for every dirty path (`allow_dirty`, a keyword beside `read_only`). Each member is read in the managed repository without following a link and refused, with cause `carry_member_refused` and a detail naming the check, when it has a credential-shaped name, is a symlink or special file, has a `.git` component, is a gitlink, escapes the root, is over the per-file bound, or holds key armour; it is written at its relative path in the clone with `O_NOFOLLOW`, and its digest is recorded in the record's `codex_carry` block. The members that are intent-to-add in the managed index are made intent-to-add in the clone (`git add -N` through `gitrepo`'s hardened option set, for exactly those paths), because the plan-stage resolver refuses an untracked plan path and the plan-stage id reads the index; the carried-in intent-to-add set is recorded beside the digests.
- **D6. The carry out brings back only changed members of the set, after every check, and nothing else.** When the worker has ended, before any write to the managed repository, the Controller checks, in this order, each with one cause: the plan role's clone `HEAD` and refs are unchanged (`carry_unexpected_commit`); the clone's `.git` is what `Prepared.guard` recorded, apart from its index (`clone_git_changed`); the clone's intent-to-add set is the carried-in one (`carry_index_changed`); no path outside the set differs from the carried-in state, by D3's rules (`carry_out_of_set`); every changed member is a regular file, within the bound, without armour, and no present carried-out member went absent (`carry_member_refused`, detail `absent`, `kind`, `bound` or `armour`); the managed members and the managed intent-to-add set still have what was recorded at carry in (`carry_managed_changed`). For the implementation role the commits then land through `codex_worker_landing.land`, unchanged; a refused landing carries nothing out. Then the writes, state file last: each changed non-state member through a temporary file in its own directory and an atomic rename (which leaves the managed index as it was), then the state file as D6a says.
  - *D6a. The state file is carried out through the Workflow's state lock, and only this item's entry is taken from the worker.* The Controller parses the worker's copy and refuses with `carry_state_foreign` unless the worker's document with this item's `work_items` entry removed is exactly equal to the carried-in document with that entry removed (same key sets at both levels, so a new top-level key, a new or changed entry of another item, or a moved `active_work_item_id` fails closed). The write is the new recorder driver operation `review_recorder.carry_state`, run through `run_in_private_copy` as `record` is: inside the Workflow's `state_transaction`, its mutator refuses with `carry_managed_changed` when this item's freshly read entry is not the carried-in entry, and otherwise returns the fresh state with only this item's entry replaced by the worker's. Another lane writing its own item while Codex runs is therefore kept and does not fail the job.
- **D7. The carry is recoverable from what is on disk, and the Workflow's state is the truth.** The `codex_carry` block holds the pre-step head and the carry base (D4a), the stage (`preparing`, `carried_in`, `worker_ran`, `out`, `done`), the members with their carried-in digests, the carried-in intent-to-add set and the digests to write; the clone is kept until `done`. Recovery by stage, one test each:
  - `preparing`, or `carried_in` with no `worker_process`: nothing ran; the clone is removed, nothing is written beyond D4's commit (the Workflow's own committed entry, which stays), and the record ends as H4e's not-started worker does. The recovery does not continue the record and does not recompute D4: D4's commit stays, and the re-run is a new job whose pre-step head is that commit, so `commit_pending` is a no-op (the entry is already committed), the carry base equals the pre-step head, and there is no second commit and no `managed_branch_moved`.
  - `carried_in` with a `worker_process`, or `worker_ran`: once the worker's process is gone, the carry out (D6) runs from the kept clone exactly as at the end of a run, and the record ends as D8 says; with the worker's end never recorded, a move of nothing, judged against the re-captured baseline of D4a, is the existing interrupted ending.
  - `out`: the carry out is re-run: a member already at its target digest is skipped, one at its carried-in digest is written, any other digest is `carry_managed_changed`; the state is re-run through D6a's mutator, a no-op when this item's entry already equals the worker's.
  - `done`: nothing is written; the ending of D8 is evaluated again.
  - The clone gone before `done`: `carry_clone_gone`, nothing further written, the evidence naming the members not yet written.

- **D8. A routed apply runs the carry around the existing Codex worker launch, inside the job's own record, stops after the landing, and the job status is a function of the ending.** After the route and the usage admission, `execute_step` takes the apply branch when the route's role is one of the two and its harness is `codex` (taken before the Codex worker's and the review branch, with a test of the order). The branch computes D3, runs D4 for the implementation role (recording the carry base, D4a, before anything else is made), prepares the clone at the carry base and carries in (D5), launches with the eight options of H4d (`codex_worker_job.launch_options`), records `usage` and `usage_record` from the rollouts, and carries out (D6), landing first for the implementation role.   | ending | job status and what the record says |

  | carried out, implementation role: the resolution answers `FINISHED` | `GATE_BLOCKED`, `human_gate_pending` the gate `evidence.decide` returns for the managed repository, which is the existing implementation-bundle regeneration gate (the landed generation-record commit is newer than the managed `MANIFEST.md`'s `generation_head`); `codex_carry` at `done`, the landed range named; the clone removed. One test per site and per stage.

## Risks

- **The carry writes into the managed working tree, which no Codex path has done before.** D3 closes the set, D6 checks before any write and writes atomically with the state file last, and D7 makes the carry re-runnable; the safety tests prove the worker cannot widen the set, not that its edits are right: the review stages still judge the content.
- **A worker that rewrites the state file.** D6a compares everything outside this item's entry with the carried-in copy (exact equality, fail closed) and replaces only this item's entry under the Workflow's state lock. A Workflow release that changes the state file's shape is caught by the same comparison failing closed.
- **The regeneration the operator runs.** After an implementation-role landing, the managed generator runs code the worker may have changed or added. The Controller runs none of it, the lane stops at a human gate, and the pages tell the operator to read the landed range before regenerating; making that run safe without a human is H4e3b.
- **The implementation role's generation-record commit.** It is made in the clone; the hand-off test of D10 proves the operator's regeneration accepts it in the managed repository. If it records anything specific to the clone's root, the implementation role is split off as its own item (the plan role first), not widened here.
- **Sizing.** One mechanism (the carry); the clone, the launcher, the landing, the reconcile and the gates are reused unchanged.
- **Out of scope:** running the managed repository's generator after a landing (H4e3b), `milestone-implement` (H4f), a default harness for these roles, the options UI and the Manager's use.

## Open decisions

This repository has no `docs/TECHNICAL_DECISIONS.md`, so no open decision row there is touched. Four choices are the plan's own and are stated so the reviewers can overrule them: the adapter role is a new name (`local-applier`) rather than a second meaning of `worker`; a pending feedback entry is committed by the Controller through the Workflow's writer before the implementation clone is made, rather than carried; any dirty path outside the set refuses the job rather than being left alone or carried; and a carried-out apply ends `GATE_BLOCKED` at the existing bundle gate (for the plan role, on the Workflow's own `plan_review_not_bound` answer at row 4b) rather than `FINISHED`, because the step's bundle is left for the operator to regenerate.
