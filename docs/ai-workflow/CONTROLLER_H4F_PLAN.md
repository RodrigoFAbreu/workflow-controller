## Goal

One mechanism: **the implementer route**. `milestone-implement` runs one checkpoint per invocation (claim, implement, run the narrow check, commit with the Workflow's trailers, complete the checkpoint in the state file in the same commit, release the claim), so everything it keeps is **committed**. That is the shape H4e already handles: a Codex worker in a private clone, whose linear commits the Controller fast-forwards onto the managed branch. This item makes that path reachable for this one role and adds the one thing the path lacks for a role that writes code: a check, made **before** the fast-forward, of what the landed commits touch. No new setting, no new gate, no new way to run Codex: the clone, the landing, the job record, the usage record, the ownership and the recovery are H4c to H4e's, used unchanged.

What this item leaves out, stated once: `milestone-implement-self-review` (the invocation that writes the implementation bundle's author-written, ignored files and runs the generator) stays on the `worker` adapter role, so it still runs on Claude Code only. It needs the carry out of ignored files and the generator's `implementation` stage, which is a second mechanism; see "Open decisions".

## What exists

- `harness.WORKER` is the adapter role of every routing role not named otherwise (`routing.ADAPTER_ROLE`); `harness.CODEX` declares `local-reviewer`, `local-applier`, `reviewer` and `functional-tester`, not `worker`, and `worker_launch.LAUNCHERS` has no `(codex, worker)` entry, so `routing.check_role_harness` refuses `milestone-implement=codex` today. H4e3 did the same for the two apply roles with the adapter role `local-applier` (`harness.LOCAL_APPLIER`, `routing.LOCAL_APPLY_ROLES`).
- `job._run_codex_worker` is the call-and-wait block of a Codex worker (tree, Codex home, the eight launch options, the two stream files) and `_land_codex_worker` lands its commits through `codex_worker_landing.land` (`job.CODEX_LANDER`); the ordinary body of `execute_step` already runs both for a launcher that is a `codex_worker.CodexLauncher` (`job._is_codex_launcher`), then the Workflow's `reconcile`. `job.CODEX_WORKTREE_PREPARER` is the seam for the tree and is `None` by default, so a Codex worker launch that is not an apply role is refused with `WorkerLaunchError` before anything starts. The H4c to H4e live proofs set it to `codex_worker_tree.prepare` themselves.
- `codex_worker_landing.land` refuses a landing with the causes in `codex_worker_landing.CAUSES` (a moved branch, a non-descendant, a merge commit, more than `MAX_LANDED_COMMITS` commits, a submodule, extra refs, hooks or config in the clone, a tip that moved, a sandbox breach, and the rest). It does **not** look at which paths the commits changed: for the two apply roles that was acceptable because `generator_run.check_landing` and the carry's own checks run after the landing and before anything of the managed tree is executed (H4e3b, D2). A role that writes code lands arbitrary paths.
- The Workflow's `milestone-implement` writes `docs/ai-workflow/WORKFLOW_STATE.json` only through `state_transaction` and commits it with the checkpoint (`complete_checkpoint`, step 1f), which is why the landing is the whole of its durable effect. Its claim does **not** live in the state file: `claim_checkpoint` and `release_checkpoint` (`scripts/workflow_state.py:6266`, `:6325`) write a claim file under `<git-common-dir>/ai-workflow/checkpoint-claims/` (`claims_dir`, `:5868`), and the amendment witness and the lifecycle lock are under the same common dir (`amendment_witness_path`, `lifecycle_lock_path`, `:7824`, `:7819`). The state file's own writers in a checkpoint invocation are `transition_checkpoint_in_progress` (`:5224`) and `complete_checkpoint` (`:5255`), through `state_transaction`. So a claim an earlier invocation left (`CONTINUE_CLAIM`, published with the state write never made and the tree clean), or an open amendment, is invisible to the managed tree's dirty check, and a private clone has its own empty common dir; D5 therefore checks the managed common dir itself. Uncommitted work an earlier invocation left (a dirty-resume) is caught by the dirty check.
- The `.git` guard (`codex_worker_sandbox.guard_digest`, `check_guard`; `GUARD_EXCLUDED_ROOTS` is `objects`, `refs`, `logs`; `GUARD_EXCLUDED_FILES` and `*.lock` are the regular files a commit writes) records the type, mode and content of every other entry of the clone's `.git` and is compared before and after the run by the launcher (`controller/codex_worker.py:145`, `:187`) and again by the landing's clone check (`controller/codex_worker_landing.py:166`). A checkpoint invocation legitimately writes under the clone's own common dir: `claim_checkpoint`, `release_checkpoint` and `owner_mutation` leave `.git/ai-workflow/checkpoint-claims/` directories and `<sha256>.guardlock` files (`scripts/workflow_state.py:5900`), which are deliberately never unlinked; the guard today records each as a new entry.
- The ending of a `landed` or `nothing` landing removes the clone (`job._settle_codex_worker_dir(..., keep_tree=False)`, `controller/job.py:10366`, and the recovery's twin at `:9110`); a clone that could not be removed is named by `tree_left` and `_name_kept_clone` (`:3394`, `:9119`, `:10369`). The landing judges commits only: it does not look at uncommitted files in the clone. `milestone-implement` may stop **before** committing (`.claude/commands/milestone-implement.md`, step 1e's stop conditions), leaving implementation files and the `IN_PROGRESS` state write uncommitted in the clone.
- `routing.role_for` returns `milestone-implement-self-review` from `SELF_REVIEWING_IMPLEMENTATION`, and from `IMPLEMENTING` once the registry is complete, so the checkpoint role and the wrap-up role are already two routing roles with separate routes.

## The risk this item closes

A Codex worker is a model working in a clone with commit authority over the managed branch once its commits land. Three things reach the Controller's own authority through a landed commit, and the landing must refuse each before the fast-forward:

- **IMPL-R1.** A landed edit of what the Controller executes next: `scripts/` or `.workflow-manager/` (the protocol queries run the managed repository's Workflow scripts from verified bytes, but the verification record is itself a committed file, and H4e3b's guarded generator run trusts `scripts/` to be the installed release's; a commit that edits a script and the record's digest together passes any check that trusts the record alone), and `.claude/` (Claude workers are launched without `--setting-sources ""`: `controller/worker.py` passes only `--append-system-prompt`, `--effort`, `--input-format`, `--model`, `--output-format`, `--permission-mode` and `--verbose`, and only `controller/review.py:1653` empties the setting sources, so the managed `.claude/settings.json` hooks and permissions and `.claude/commands/*.md` are loaded by every later Claude worker on the tree, including `milestone-implement-self-review`, which runs right after the last Codex checkpoint lands). After the fast-forward the bad commit is already on the managed branch; before it, nothing is.
- **IMPL-R2.** A landed edit of the Workflow's state file outside what a checkpoint writes: the plan and technical approvals, the review stages, the binding records and the gate policy fields live there, and a worker that sets them by hand would make the Workflow believe a gate was passed. The Workflow's own commands refuse such a write; a model that bypasses the commands is the case the check is for.
- **IMPL-R3.** A landed symlink, submodule or file mode change that the managed tree then follows (`.gitmodules`, a link in `docs/` that a later generator copies). The landing already refuses a submodule; a symlink, and a type or executable-bit change, is refused here for a path anywhere in the range (D3), a deliberately blunt rule a managed repository that needs such a change takes up with the operator by routing the role to `claude-code`.

## Decisions

Each decision states one principle.

<!-- CP1 -->
- **D1. A role is routable to a harness when the harness declares the adapter role the role runs as, and the checkpoint role gets its own adapter role.** `harness` gains the adapter role `implementer`; `routing.ADAPTER_ROLE` maps exactly `milestone-implement` to it (`routing.IMPLEMENT_ROLES`, a one-element tuple that H4g can widen) and every other routing role keeps its adapter role; both adapters declare it. `worker_launch.LAUNCHERS` gains `(claude-code, implementer)`, the Claude launcher as today, and `(codex, implementer)`, `codex_worker.CodexLauncher`. `(codex, worker)` stays unregistered, so `codex` still cannot be routed to any other worker role, `milestone-implement-self-review` included. `review_mode.worker_families` counts `implementer` with `worker`, `local-reviewer` and `local-applier`, so the independence check sees the role as it saw it when it ran as `worker`. `python3 tools/harness_table.py --write` regenerates the two tables. Admission is the Codex provider's, as for any route whose launcher is a `CodexLauncher`, on the single-route and the chain path alike.
- **D2. Routing is opt-in and changes nothing by default.** With no routing config, setting or `--role-harness`, the role resolves to `claude-code` and every Claude job record is byte-identical to today's. Selecting `codex` takes a model and an effort the adapter lists; anything else is refused by the existing `check_route_values`. No setting, flag, exit code or gate is added.

<!-- CP2 -->
- **D3. The landing refuses, before the fast-forward, a commit range that touches the execution surface, and the check is the landing's own so no caller can skip it.** `codex_worker_landing.land` gains a keyword `surface`, a `LandingSurface` value (default `None`: unchanged behaviour for every existing caller and test). When given, the check runs inside `_check_range`, so it runs in both passes the landing already makes (the clone-side pass before `on_intent`, and the managed-side pass after the fetch and before the merge, where the object ids are authentic and which is the pass that decides). It reads the net change `git diff-tree -r -z --raw --no-renames --no-textconv --no-ext-diff --ignore-submodules=none <base> <tip> --` through `gitrepo`'s hardened option set (the raw form carries the modes that `--name-status` does not; CP2 adds one helper beside `commit_touches_submodule`, `controller/gitrepo.py:964`, built on the same pattern and returning old mode, new mode, status and path, and leaves `diff_name_status`, `:904`, as it is). The check is on the **net** `base..tip` change: a path an intermediate commit adds and a later one removes is not in the tree that lands and is not judged (a test names this). It refuses with the new cause `surface_touched` (naming each path and its status letter): any path under `scripts/`, `.workflow-manager/` or `.claude/` (`settings.json`, `settings.local.json`, `commands/`, `agents/`, `skills/` and anything else there) or `.codex/`, whatever the status; and any changed path whose new mode is `120000` (a link) or whose mode differs from its base mode where both exist (a type or executable-bit change). A newly added `100755` file outside the listed directories is **not** refused, intended: a new script outside the surface is code the implementation review judges, as for a Claude worker. `AGENTS.md`, `CLAUDE.md` and the like are not refused either: they steer a model and execute nothing, so they are the implementation review's to judge; `.claude/` and `.codex/` are refused because the Controller's own next worker loads them as configuration, hooks and command prompts. A range the diff cannot read refuses with the same cause. The managed branch is untouched on a refusal; the clone is kept, as for every landing refusal, and the job ends `FAILED` with the existing landing-refusal evidence naming the cause. The job passes `surface=LandingSurface.IMPLEMENTER` for the implementer route only.
- **D4. The state file may change only in the fields a checkpoint writes, and the check runs in the same pass.** When the range touches `docs/ai-workflow/WORKFLOW_STATE.json`, the landing reads the file at the base and at the tip through `git show` (bounded, parsed as data, never by the Workflow's code) and refuses with `state_touched` unless: the top-level keys other than the work-item table are equal; every work-item entry except this item's is equal; and, in this item's entry, every field outside `CHECKPOINT_WRITTEN_FIELDS` is equal. `CHECKPOINT_WRITTEN_FIELDS` is derived, not guessed, from the Workflow's own **state** writers (not the claim-file writers): a test runs `transition_checkpoint_in_progress` and then `complete_checkpoint`, each through `state_transaction` on a fixture entry, for a middle checkpoint and for the last one (where `complete_checkpoint` also moves `phase` to `SELF_REVIEWING_IMPLEMENTATION`), and asserts the changed fields are exactly the constant's members, across **successive** completions (so a field that only changes from a later checkpoint on is seen): `checkpoints` (the `checkpoints.<id>` sub-object, whose shape is `{status, start_commit}`, then `COMPLETE`), `current_checkpoint_id`, `last_completed_checkpoint_id` (assigned by `complete_checkpoint`, `scripts/workflow_state.py:5322`), `phase`, and what `state_transaction` stamps (`state_revision`, `last_transition`). `clear_amendment_resolution` is **out** of the set: it rewrites the amendment witness under the git common dir, never the state file, and a checkpoint invocation cannot run at an open amendment (D5). A Workflow release that adds a written field fails the test, not a live job. The plan and technical approvals, the review stages and bindings, `governing_workflow_version`, the paths, `base_commit` and every gate policy field are outside the set. A state file that is absent at the base or unparseable at the tip refuses with the same cause. The list above states what the derivation finds today and is not a second source: the test's derived set is the authority, and the constant is whatever the test requires it to equal.
- **D4b. The git guard accepts the Workflow's own checkpoint bookkeeping under the clone's common dir and nothing else new, for the implementer route only.** `guard_digest` gains the keyword `workflow_metadata` (default `False`: every existing caller and digest unchanged). When true, the single root `ai-workflow` under the clone's `.git` is treated as the guard treats `objects`, `refs` and `logs`: only its type is recorded, and a regular file or directory anywhere under it may be added, changed or removed unrecorded. Everything else the guard does is kept, inside that root too: a symlink or special file anywhere under it is still recorded by path and refused; `config`, `hooks`, `info`, the alternates files and every other entry are still compared; `.git` itself must still be a directory. The digest records the flag and `check_guard` refuses a before/after pair taken with different settings, so a caller cannot weaken a comparison by re-taking one side; the launcher holds no `Prepared` (`launch_codex_worker` takes its own baseline, `controller/codex_worker.py:187`, and compares after the run, `:145`, from the eight options of `codex_worker_job.launch_options`), so the setting reaches it as a **ninth launch option**, `workflow_metadata`: `launch_options` gains the keyword (default `False`) and includes the key **only when true**, which the job does for the implementer route only, so every other route passes exactly the eight options and stays byte-identical; `launch_codex_worker` gains the keyword (default `False`) and takes **both** its digests (the baseline and `_breach`'s post-run one) with it. The landing's clone check (`controller/codex_worker_landing.py:166`) and the carry's (`controller/codex_carry.py:646`, which the implementer route never reaches; named so a later route that both carries and sets the flag finds the rule already applied) hold a `Prepared`, and take their digest with the flag `prepared.guard` recorded, through one helper beside `guard_digest`. `tests/test_codex_worker_job.py:44` (`test_exactly_the_eight_keys_of_the_plan`) is updated on purpose: the default set stays exactly the eight, and a second case pins the nine keys for the flag set. `codex_worker_tree.prepare` takes `workflow_metadata=` from the job, true for the implementer route only; the apply and review routes pass nothing and stay byte-identical. Nothing the Controller executes reads what the Workflow writes there: it is the clone's own common dir, discarded with the clone, and the managed common dir is never touched by the worker (D5).

- **D5. The tree is the real preparer, and an uncommitted managed tree refuses the launch.** `job.CODEX_WORKTREE_PREPARER` defaults to `codex_worker_tree.prepare` (the seam stays, and `None` still refuses with `WorkerLaunchError`, which the existing test keeps). The clone is made at the pre-step head, which the apply roles' carry does for them with a bounded carry set; this role has none, because every file a checkpoint needs is committed (the plan, the registry, the mapping and the approvals are in the plan approval commit). `codex_worker_tree.prepare` refuses a dirty managed tree already (`managed_tree_not_clean`); the job maps that refusal for the implementer route to `WorkerNotStarted` with the cause named and the remedy "commit, or reset, the managed tree's own uncommitted work, or route the role to `claude-code`", so a dirty-resume an earlier Claude run left is never silently run on a clone that cannot see it. The dirty check cannot see the common dir, so a second pre-launch check, before the clone is made, refuses with `WorkerNotStarted` naming `managed_claim_present` when the managed repository's common dir holds a checkpoint claim for the item (a `CONTINUE_CLAIM` crash: claim published, state write never made, tree clean), and `managed_amendment_open` when the item's amendment witness is `OPEN` or `RESOLVING` (the clone's empty common dir would bypass `claim_checkpoint`'s witness refusal), and, for a `RESOLVED` witness, the Workflow's own stale and conflicting resolution refusals (`StaleLifecycleStateError`, `AmendmentResolutionConflictError`, `scripts/workflow_state.py:8853`) as `managed_amendment_stale` and `managed_amendment_conflict`: a `RESOLVED` witness is clean only when the managed branch's committed state already carries the very resolution it records, so a branch that has not merged an amendment approved on another linked branch never launches a worker whose private clone cannot see the repository-wide witness. **The mechanism is a Controller-side literal of the layout, not Workflow code**: the Controller never imports `scripts/workflow_state.py` (`controller/errors.py:231`) and its only route to Workflow code is `workflow_contract`'s verified-bytes query (invariant I6), which offers no claim or witness query and which this item cannot extend. A new module `controller/checkpoint_claims.py` resolves the managed common dir through `gitrepo`'s hardened read runner (`git rev-parse --git-common-dir`) and reads `<common-dir>/ai-workflow/checkpoint-claims/<sha256(work_item_id)>.json` (the claim) and `<sha256(work_item_id)>.amendment.json` (the witness) with `lstat` and no symlink following (`O_NOFOLLOW` for the read of the witness), bounded in size. A claim file that exists is `managed_claim_present` whatever it holds; a claim path that is a symlink, a non-regular file or an `lstat` error other than "absent" refuses with `managed_claim_unreadable`. An absent witness is clean; a witness that parses as the Workflow's schema (`schema_version`, `work_item_id` equal to the item's, `status` one of the Workflow's `AMENDMENT_WITNESS_STATUSES`) and whose status is `NONE` is clean, and one whose status is `RESOLVED` is clean only after the resolution comparison below; `OPEN` and `RESOLVING` are `managed_amendment_open`; **the resolution comparison** for `RESOLVED` reads the witness's `amendment_seq` and `resolution_projection_sha256` and the managed `HEAD`'s committed state file through `git show HEAD:docs/ai-workflow/WORKFLOW_STATE.json` (hardened read runner, bounded, parsed as data; the managed tree is clean, so `HEAD` is what the clone is made from), takes `work_items[<id>].amendment_history[seq - 1]`, and refuses `managed_amendment_stale` when that entry is absent or has no `resolved_at_plan_revision`, and `managed_amendment_conflict` when the Controller-side literal of the Workflow's resolution projection (the SHA-256 of the canonical JSON, `sort_keys`, `(",", ":")` separators, `ensure_ascii=False`, of `{request_projection_sha256, resolved_at_plan_revision, reconciliation_outcome, resolved_review_content_id}`, an absent key `null`, the request projection being the same hash of the entry without those three keys; `amendment_request_projection_sha256` and `amendment_resolution_projection_sha256`, `:7882`, `:7896`) differs from the recorded one; an unreadable or malformed committed state, or a witness `amendment_seq` that is not a positive integer, is `managed_amendment_unreadable`; a witness that is a symlink, is not a regular file, is torn or unparseable, has another schema, another item's id or an unknown status refuses with `managed_amendment_unreadable`, the safe direction (the Workflow's own `read_amendment_witness` refuses the same shapes, `scripts/workflow_state.py:8185`). The literal is kept honest by a pin test that, in a subprocess against the installed release's `scripts/workflow_state.py` as `tests/test_target_state.py` does, asks the installed `claim_path` and `amendment_witness_path` (and `AMENDMENT_WITNESS_STATUSES`) for a fixture repository and item ids (an ordinary one and one with a path-like id) and requires the Controller module's paths, its open-status set and its resolution projection (on a resolved fixture entry, one with absent keys and one with non-ASCII text) to equal them, as `controller/decision.py:129` copies `KNOWN_PHASES`; the remedy is "resume or release the claim with the Workflow's commands on the managed tree, or finish the amendment, or merge the resolved amendment into this branch (`managed_amendment_stale`) or discard the divergent approval on it (`managed_amendment_conflict`), or route the role to `claude-code`". After a Codex-landed checkpoint the managed common dir holds no claim (the worker's claim and its release lived in the clone's own common dir, which is discarded with the clone), so the next Claude invocation on the managed tree finds none. Nothing is carried.
- **D6. The existing Codex worker body runs the role, with the surface check passed in, and the rest of the ending is unchanged.** `execute_step` already runs `_run_codex_worker`, `_land_codex_worker` and the Workflow's `reconcile` for a Codex launcher; the change is the `surface=` argument of D3 on the landing call of the implementer route, and the dispatch test that a `milestone-implement` route with harness `codex` reaches the plain body (not the apply branch, not the review branch) while `milestone-implement-self-review` cannot be routed to `codex` at all. A landing refusal is the existing `CodexLandingRefused` ending with the clone kept; a `landed` or `nothing` landing is followed by `reconcile`, which finds the checkpoint complete (or `no_progress` for a worker that landed nothing, as today). The recovery of a killed run (`resume`, `abandon`, the drifted release, the landing's own `recover`) is H4c2's and H4e's and **unchanged**: `codex_worker_landing.decide` (`controller/codex_worker_landing.py:365`) re-runs no check, it reads the branch against the base and the intent block. The endings that follow are therefore stated, not promised equal to the uninterrupted run's: a kill at any point before the managed branch moves (during the clone-side check, after a passing check and before `on_intent`, after `on_intent`, during the surface or state check of the managed-side pass, or before the merge) recovers as the refused `landing_interrupted`, the clone kept and the managed branch, tree and index untouched, the safe direction, **whatever the checks would have said** (a range the uninterrupted run would have refused as `surface_touched`, or landed, both end `landing_interrupted`); a kill after the branch moved recovers as `landed` through `verify_move` (case b), exactly as for H4e. Re-checking and landing on recovery is a new mechanism and out of scope. A test proves each window's actual ending.
- **D6b. A clone that holds unfinished work is kept and named, never removed with the successful-landing cleanup.** For the implementer route only, before the removal of a `landed` or `nothing` landing's clone (the uninterrupted ending and the recovery's twin alike), the job probes the clone with one bounded, hardened read (`git status --porcelain=v1 -z --untracked-files=all --no-renames`, ignored files not listed, through `gitrepo`'s read runner with `gitrepo.LANDING_CONFIG` (hooks, fsmonitor and maintenance off; it has no filter overrides) **plus a filter-disabling set** built the way `workflow_contract._git_named_overrides` builds it (`controller/workflow_contract.py:963`: the clone's configured filter names read with `git config --local --name-only --list`, each filter's `process`, `clean` and `smudge` set empty; CP3 adds one small helper to `gitrepo` for it, never imported from `workflow_contract`) and `no_optional_locks`, so the probe does not depend on the clone's `config` having been guard-checked first, which the recovery path does not re-run) in a helper beside `land`, `codex_worker_landing.unfinished_work`. A tracked change, a staged change, an untracked file, or a probe that cannot read, is **unfinished work**: the job removes everything of the job directory except the tree (`_settle_codex_worker_dir(keep_tree=True)`), records `tree_left = {reason: "unfinished_work", path, tracked, untracked}` (counts, never file contents) in the landing block, and names the clone in the terminal `reconciliation_evidence` through the existing `_name_kept_clone`, so the path is recorded by the uninterrupted ending and again by the recovery's own record. The managed tree is never written from the clone: nothing is carried, and the operator reads the clone and re-runs the checkpoint or applies the work by hand. A landing with commits **and** a dirty clone lands the commits (they were checked) and keeps the clone; a `nothing` landing with a dirty clone keeps it, and the Workflow's `reconcile` judges the unchanged checkpoint as today. A clean clone is removed exactly as before; a kept clone is removed only by the recovery commands that already remove one.

- **D7. The route is proved adversarially through the job, with a case for every new cause.** The tests drive `execute_step` with the real clone, the real landing and the fake `codex` of `tests/fake_codex.py` on fixture repositories whose Workflow state is a real one at `IMPLEMENTING`, as `tests/test_job_codex_worker_landing.py` does. ## Risks

- **A checkpoint needs a toolchain in the sandbox.** The worker runs the narrow test of its checkpoint inside the H4b1 sandbox profile; whether that works for a given managed repository is not provable offline. The live proof records it, and the route stays opt-in; a repository whose tests cannot run there keeps `claude-code`.
- **The surface list is a floor.** The check keeps the worker from changing what the Controller executes (`scripts/`, `.workflow-manager/`) and the Workflow's own approvals. It does not review the code the worker writes; the implementation review does, as for a Claude worker. A managed repository that wants more paths refused (`.github/`) names them in a later item; the list is one constant.
- **The state field set follows the Workflow.** A Workflow release that changes what a checkpoint writes fails the pinning test on the Controller's side, before a job meets it; until then the landing refuses (`state_touched`), the safe direction.
- **A dirty managed tree is refused, not carried.** Carrying a dirty-resume (an earlier invocation's uncommitted work) is the apply roles' mechanism applied to a role with an open-ended file set; this item does not do it. The operator commits or resets, or keeps the role on `claude-code`.
- **Unfinished work stays in the clone.** A stopped checkpoint's uncommitted work is kept, named and never carried (D6b); recovering it is the operator's, by reading the clone. Carrying it back is the open-ended carry this item does not do.
- **The guard's metadata root is a deliberate, narrow widening** (D4b): one root, type-only, implementer route only, with symlinks, special files, `config`, hooks and alternates still refused.
- **Sizing.** One mechanism, the implementer route and its landing policy; the clone, the landing, the usage record and the recovery are reused. If the plan review finds the surface check and the state check to be two mechanisms, the split is CP2 as its own item with CP1 and CP3 following; CP2 now also carries the guard flag (complexity 4).
- **Out of scope:** `milestone-implement-self-review` and every other worker role (H4g), the carry of ignored or uncommitted files for this role, the generator's `implementation` stage, and a setting for the surface list.
