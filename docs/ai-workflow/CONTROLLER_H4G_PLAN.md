## Goal

One mechanism: **the self-review route**. It is the first thing the item page says H4g inherits from H4f, and it is built only from parts that exist: H4f's implementer landing (a Codex worker in a private clone, whose linear commits are fast-forwarded after the surface and state checks), H4e3's carry of the implementation stage's author-written, ignored bundle files, and H4e3b's guarded generator run, which today knows the stages `plan` and `post-fix`. The new thing is the combination, plus the one decision each part needs for this role: which state fields its commits may change (D3), and which generator stage runs after the landing (D5).

**Scope decision (the sizing rule, `docs/planning-rules.md`).** The backlog row for H4g names every remaining role: `milestone-plan`, `apply-functional-review`, `apply-pr-review`, `satisfy-gate`, `prepare-functional-review`, `record-manual-*` and the documentation. Those roles write five different shapes of effect: new files in the plan stage plus the plan-stage generator (`milestone-plan`), state-only commits with approval fields (`satisfy-gate`, `record-manual-*`), a child work item and a checklist (`apply-functional-review`, `prepare-functional-review`), and a reopened item with a forge fact (`apply-pr-review`). Each needs its own state profile and its own carry, so they are more than one mechanism and are **not** in this item (see "Open decisions"). This item makes the implementation lane complete: `milestone-implement`, `milestone-implement-self-review`, `review-implementation` and `apply-implementation-review` can all run on Codex.

## What exists

- `routing.IMPLEMENT_ROLES` is `(MILESTONE_IMPLEMENT,)`, a one-element tuple H4f left to widen; `routing.ADAPTER_ROLE` maps its members to `harness.IMPLEMENTER`; both adapters declare it, and `worker_launch.LAUNCHERS` holds `(claude-code, implementer)` and `(codex, implementer)` (`codex_worker.CodexLauncher`). `milestone-implement-self-review` keeps the adapter role `worker`, for which `(codex, worker)` stays unregistered, so `routing.check_role_harness` refuses `codex` for it today.
- `job._is_codex_implement_route` is keyed on `route.role in routing.IMPLEMENT_ROLES` and the Codex adapter; such a route takes the plain Codex worker body (`_run_codex_worker`, `_land_codex_worker`) with `surface=LandingSurface.IMPLEMENTER` and the item id, then the Workflow's `reconcile`. `codex_worker_landing.CHECKPOINT_WRITTEN_FIELDS` is the set of fields of this item's state entry a landed commit may change, pinned by a test to `transition_checkpoint_in_progress` and `complete_checkpoint`.
- The apply roles' carry (`controller/codex_carry.py`): `CarrySet` for the stage `implementation` has no named repository paths and the out members `current/REVIEW_REQUEST.md`, `current/IMPLEMENTATION_SUMMARY.md`, `current/TEST_RESULTS.md`, `current/CONTEXT_FILES.txt` and `current/PLAN.md` under `.ai-review/<work item>/` (`OUT_MEMBERS`); `carry_in`, `check_out`, `write_out` and `recover` judge and move them. `generator_run.run` runs the managed generator after a landing under the interpreter pins and the tree checks (`generator_run.STAGES` is `("plan", "post-fix")`), and `job._guarded_regeneration` and `_carry_resolution` are the apply branch's call sites.
- The role's own steps (`.claude/commands/milestone-implement.md`, step 2): one state commit when the phase actually moves to `SELF_REVIEWING_IMPLEMENTATION`; review and fix the diff (code and test commits); the full verification; then, for a state entry, `record_bundle_generation` with `stage="implementation"` committed alone with the `Workflow-Bundle-Generation-Record` and `Workflow-Work-Item` trailers **before** the bundle is generated, the four author-written files and `PLAN.md`'s source, and the generator run. Everything durable is either a commit in the clone or an ignored file under `.ai-review/<work item>/current/`.

## The risk this item closes

- **SR-1.** The role's commits may change two things the implementer's may not: the phase (`enter_self_reviewing_implementation`) and the generation record (`record_bundle_generation`). The implementer's field set refuses both, so reusing it unchanged would make every self-review end `state_touched`; widening it for both roles would let a checkpoint worker write a generation record. The set must be per role, and derived from the Workflow's own writers.
- **SR-2.** The ignored bundle files are written by the worker, and the generator that reads them runs in the managed tree. H4e3b closed that for two stages; a third stage must be named, and the guard must judge the lists it reads. The `implementation` stage reads the same lists as `post-fix` (`scripts/prepare-ai-review.sh` treats the two identically, and `generator_run._context_lists` already returns the live `current/CONTEXT_FILES.txt` for every stage that is not `plan`); `PLAN.md` is an author file that is stubbed when absent, and no plan source is read, so CP4 adds no check of one.
- **SR-3.** The worker's own generator run happens in the clone and leaves a bundle there; it is derived output and must never be carried out or trusted (the carry's derived names already say so), so the managed bundle is only ever the Controller's regeneration.

- **D2. The landing's state profile is a named argument of the landing, one per role, and an unnamed profile is the implementer's.** `codex_worker_landing.land` gains `state_profile`, a `StateProfile` value (default the checkpoint profile: every existing caller and test unchanged). - **D3. The self-review profile is the union of the fields the Workflow's two self-review writers change, derived from them by a test, and nothing else.** `SELF_REVIEW_WRITTEN_FIELDS` is the fields changed by `enter_self_reviewing_implementation` (the phase) and `record_bundle_generation` with `stage="implementation"` (`implementation_revision`, `reviewed_implementation_head`, `state_revision`, `last_transition` and the target `phase`; the generation record is the trailer commit, not a field), each run through `state_transaction` on a fixture entry, for the governing versions `2.1` and `2.2`, whose target phases differ, and `record_bundle_generation` over **both** outcomes the role can write, `outcome="ordinary"` (advances `implementation_revision`, sets `reviewed_implementation_head`) and `outcome="same_content"` (the recovered record after a plan-only re-approval: changes only the phase, `state_revision` and `last_transition`), so the derivation test names both; the union is unchanged, because the recovered field set is a subset of the ordinary one. A test fails when the profile and the derived set differ in either direction, and a second test fails when a checkpoint-profile landing accepts a generation record. The profile never includes the plan or technical approval, the review stages, the binding records or the gate policy fields; the surface check of H4f (`scripts/`, `.workflow-manager/`, `.claude/`, `.codex/`, links, modes) applies unchanged.

- **D5. After the landing and the carry out, the Controller regenerates the bundle itself, with the stage `implementation`, and the worker's own bundle is discarded.** `generator_run.STAGES` gains `implementation`; `check_copy_sources` reads the live `current/CONTEXT_FILES.txt` for that stage, as `generator_run._context_lists` already returns it for every stage that is not `plan` (the `post-fix` lists; no plan source is read and CP4 adds no check of one), and every other check (landing, tree, interpreter pins) is the existing guard's. The generator is `scripts/prepare-ai-review.sh <base_commit> implementation <work item>` with the milestone's base commit. The route reuses the order of `job._carry_resolution` (`controller/job.py`), it does not invent one: the first `reconcile` runs **before** the generator and decides; only an answer that finished with progress and satisfies this role's hand-over predicate is handed to `_guarded_regeneration`, whose guarded `implementation` run is followed by a second `reconcile` that is the ending. **The hand-over predicate** (added before `_guarded_regeneration` for this role only): the first answer's `observed_phase_after` equals `workflow_state.bundle_generation_target_phase("implementation", version)` and the landed range holds the generation record, in the Workflow's own terms: a commit that `workflow_state.validate_bundle_generation_record_commit(repo_root, <commit>, work_item_id)` accepts (it touches only the state file and carries one of the **two legal trailer sets** that `_bundle_generation_record_role` classes, `scripts/workflow_state.py:15371-15381`), and then **either** it is the *ordinary* role (`Workflow-Bundle-Generation-Record` and `Workflow-Work-Item`) with `implementation_revision` advanced over the carry base, **or** it is the *recovered* role (those two plus `Workflow-Supersedes`), whose `Workflow-Supersedes` names the item's current generation record at the carry base and whose `implementation_revision` is unchanged. The recovered role is the ordinary outcome after a plan-only re-approval (`resolve_bundle_generation_outcome` answers `same_content`, `.claude/commands/milestone-implement.md` step 2; `record_bundle_generation` then changes only the phase, `state_revision` and `last_transition`), the case of an `IMPLEMENTING` item with every checkpoint `COMPLETE`, so a predicate that required an advanced revision would refuse a correct, complete self-review and leave the item at the review phase with the stale plan-stage bundle. The predicate defers to the Workflow's own role classification and supersession chain and does not re-derive which commits count. The record is never compared with the landed head: `record_bundle_generation` stores the head the role passed, `.claude/commands/milestone-implement.md:375-376` passes HEAD before the record commit, so for the ordinary role the record's `reviewed_implementation_head` is that commit's parent (the recovered role leaves it unchanged) and the landed tip is the record commit itself; a clean landing whose tip is the record commit therefore meets the predicate. Any other `FINISHED` answer is the resolution's own ending, and the next step re-decides and continues the self-review. The predicate is needed because the Workflow's action `implementation.self_review` lists `IMPLEMENTING -> SELF_REVIEWING_IMPLEMENTATION` as a legal edge (`scripts/workflow_protocol.py:2118-2124`) and `reconcile` classes any legal edge whose target differs from its source as `progress` (`scripts/workflow_protocol.py:2627-2628`), so a partial self-review answers `FINISHED` with progress and `_carry_resolution` (`controller/job.py:9625-9630`) would otherwise start the generator at `SELF_REVIEWING_IMPLEMENTATION`. `_REGENERATION_STAGE` gains `milestone-implement-self-review` at `implementation`, and the landing-ownership arguments of the run (`carry_base`, `landed_head`) are passed for this role as for `apply-implementation-review`. A refusal ends at the Controller's own gate `carry_bundle_regeneration_pending` with the cause, as for the apply roles; a success is followed by the second `reconcile`, which must find the version's target phase (`AWAITING_LOCAL_IMPLEMENTATION_REVIEW` for `2.2`) and a verifying bundle. The stale-bundle answer needs no second narrow check: the existing implementation apply role ends `FINISHED` at `AWAITING_LOCAL_IMPLEMENTATION_REVIEW` with a stale bundle (`tests/test_job_codex_apply.py`, the stale-bundle test around line 490), a complete self-review is expected to give the same answer, and CP4 pins that by a test.
