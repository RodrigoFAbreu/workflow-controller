Pull request title: `fix: review and functional-review waits send review_wait, an info event, not user_gate (#149)`

## Goal

Close [#149](https://github.com/RodrigoFAbreu/workflow-controller/issues/149) as the owner decided it on 2026-10-24 (the owner's comment replaces the issue's own proposal where they differ). A `user_gate` (ACTION_REQUIRED, HIGH) must mean "a person decides something". Today `derive_job_event` sends it for every `GATE_BLOCKED` lifecycle gate, including the stops that only wait for a reviewer or a tester the operator is already running: 20 of the 24 HIGH or CRITICAL events one lane sent on 2026-10-24 were of this kind, and the owner learns to ignore the severities that matter.

One concern only: **which stop sends which event type**. No new setting, no change to an exit code, a job record, a step count, the lifecycle gate identity or the pending-checks wait.

## Decisions

Each decision states one principle.

- **D1. A wait for a reviewer or a tester is its own low event.** `controller/notify.py` gains the event type `review_wait` in `EVENT_TABLE`, of kind `state` (INFO, LOW), on by default. The `events` section of the settings file already accepts any type in the table, so an operator can still raise, lower or switch it off; nothing else in the settings changes.
- **D2. The mapping is by what the record says the stop is, in a fixed order.** In `derive_job_event`, a `GATE_BLOCKED` lifecycle gate is mapped in this order, the first rule that applies wins:
  1. as today, a pending-checks stop that waited, a stop the Workflow disposed as `blocked`, and `functional_unchanged` send `lane_blocked`; a pending-checks stop that did not wait sends nothing. The existing branches are kept as they are, so none of them changes;
  2. a record that carries the **`protocol_gate`** block (D7: written for the Workflow's own protocol gate, `{row, disposition, action_id}`) whose `disposition` is `external_gate`, whose `action_id` is `plan.review.external` or `implementation.review.external`, and whose gate `phase` is `AWAITING_MANUAL_EXTERNAL_PLAN_REVIEW` or `AWAITING_MANUAL_EXTERNAL_IMPLEMENTATION_REVIEW` (the wait for the manual external reviewer's verdict: rows 14 and 28 of the vendored protocol, whose resume command is `/record-manual-*-review`) sends `review_wait`; the two phase names are one module constant, so a phase added later is a one-line change. All three keys are required, because none alone says what the stop is. The phase does not: the manual-external phases also host the BLOCK-resolution gate (rows 11 and 25, disposition `human_gate`, action `review.resolve_block`, "a current BLOCK verdict: explicit user resolution required"), and the single-stage `AWAITING_EXTERNAL_PLAN_REVIEW` and `AWAITING_EXTERNAL_IMPLEMENTATION_REVIEW` host an approval gate (at a `"2.2"` item `AWAITING_EXTERNAL_IMPLEMENTATION_REVIEW` is the terminal "ready for approval" phase where `/approve-review implementation` is the gate; for a legacy item both single-stage phases host `/approve-review ...` once an `APPROVE` is on file), so those two single-stage phases are not in the constant at all. The disposition does not either: it is also `external_gate` at other phases (the pull-request report and the functional review, which are not the wait for a verdict), and the action id pins the two review actions apart from those. A `human_gate` at a manual-external phase therefore stays `user_gate` (rule 4): the owner resolves every BLOCK themselves, and a BLOCK arriving as INFO/LOW would be the owner learning to ignore the severities that matter, in reverse. A **legacy** record (no `protocol_gate` block: every record written before this change, every Controller-coded gate, and every record of a legacy target) carries only the phase and a gate whose text the phase cannot tell apart (the plain wait for a verdict, the admissible-`BLOCK` gate "a human resolves it before anything else runs", the inadmissible-verdict gate and the ledger-incoherent gate, all at the same manual-external phase and all with a `/record-manual-*-review` or withdraw resume), so **every legacy gate stays `user_gate`**: a missed downgrade costs one HIGH that should have been LOW, the safe direction. The principle: `review_wait` is sent only where the record itself says the stop is a wait for a reviewer's verdict;
  3. a gate the tester step wrote, that is a record with a `functional` block, sends `review_wait` for every stop in `functional_review.FAULT_GATES` **except** `isolation_breach`, which stays `user_gate`. One principle: a stop stays a gate only when its own `functional_review.gate_text` says a person must act, and the owner's decision on #149 keeps `user_gate` only for approvals, acceptance and merges that need the owner. Only `isolation_breach` says so ("A person must look at what changed before anything is tested again"). Every other member offers a remedy that an orchestrator does: "Run again" (`results_invalid`, `tested_bytes_unbound`, `recording_refused`), change the checklist (`checklist_unrecognised`), or `MANUAL_REMEDY`, the hand test, which the issue's table (the "who really handles it" column of #149's body: "the orchestrator fixes the checklist or runs the flows") and the owner's guidance comment (the tester stops are a new `state` event) assign to the orchestrator: `flows_not_runnable`, `functional_tester_unavailable` and `functional_rounds_exhausted`. `functional_rounds_exhausted` is therefore a `review_wait` like `flows_not_runnable`, which has the same remedy; that no further tester run is started changes what the orchestrator does, not who does it;
  4. everything else sends `user_gate`, as today: approvals (`AWAITING_PLAN_APPROVAL`, the technical approval, and any gate at the single-stage `AWAITING_EXTERNAL_PLAN_REVIEW` or `AWAITING_EXTERNAL_IMPLEMENTATION_REVIEW`, where the approval is the gate), a BLOCK-resolution gate (`review.resolve_block`) at a manual-external phase, every gate of a legacy record at a manual-external phase, acceptance, and a functional-review gate with no `functional` block (that is `functional.automated` false: the owner chose to keep the stop for a person, as the roadmap's follow-up 26 already says).

  Rule 2 reads the Workflow's decision from the record (`protocol_gate`, through one new reader next to `_protocol_disposition`) together with the phase, never the phase alone: this is the round-5 and round-6 root cause (a phase hosts more than one kind of stop), and where a protocol decision exists its disposition names the stop. The phase stays the second key because `external_gate` is not specific to review waits. Tests pin the three sides: a protocol record at each manual-external phase with disposition `external_gate` derives `review_wait`; the same record with disposition `human_gate` and action `review.resolve_block` derives `user_gate`; a legacy record (no `protocol_gate` block) at a manual-external phase derives `user_gate` for the plain wait and for the BLOCK gate alike, pinned explicitly. **The tests produce their records through the production writer** (the step's `_no_launch_record` path for the Workflow's own row 14, 28, 11 and 25 gates), never by hand-building a record with the field in it, because a hand-built record is how round 7 missed that the field was not written.

  The phase and the `functional` block are read from the record only, like the rest of `derive_job_event`, never from the live state.
- **D3. The identity is the gate's, so a re-derived event cannot duplicate.** `review_wait` uses the same `notify.lifecycle_gate_identity(work item, phase, state revision, code)` as `user_gate` does today, and the same body (the gate's text and its next command). The title names the stop, not a review, because the tester's fault stops are not reviews, and it never holds the identity digest (the `code` passed to `lifecycle_gate_identity` is a 16-hex-digit hash of the gate's text and command, not a readable name). Two forms, one per source: for a tester stop (rule 3) it is `Waiting: <functional gate> (<work item>)`, where `<functional gate>` is the `functional_review.FAULT_GATES` member in `record["functional"]["gate"]` (for example `Waiting: flows_not_runnable (<work item>)`); for a protocol external-review wait (rule 2), which has no readable gate code, it is the fixed phrase `Waiting for the external review: <work item>`. A record without a `work_item` omits the parenthesis or the suffix, as the other titles do. The idempotency key includes the event type, so the key of a wait differs from the key the same stop got before this change; a record re-derived by the command-entry recovery after the upgrade sends one `review_wait` and never a `user_gate`, because the derivation is the only place that decides. **Recovery across the reclassification (round 8, I2):** the key changes with the type, so `_recoverable` (the D13 check that the run's `notifications.jsonl` holds no handled outcome for the derived key) would send a second notification for a stop whose old `user_gate` was already delivered. `DerivedEvent` therefore gains one optional field, `supersedes`, the event type the same stop sent before this change (`user_gate` on every `review_wait` the derivation produces, `None` on all others), and `_recoverable` treats a handled outcome under the key of the **superseded** type (the same repository and identity) as handled too. A stop whose old `user_gate` was never sent (no handled outcome under either key) is delivered once as `review_wait`, and a second recovery then finds the `review_wait` outcome handled, so a repeated recovery sends nothing more. Nothing else of `_recoverable` changes (a run whose notifier was not active, a disabled type and the window stay as they are).
  **Live delivery across the reclassification (round 9, I3):** recovery is not the only path to a second notification. After an upgrade, an ordinary `step` that meets the same unchanged gate writes a new record (a new job id, the same occurrence identity, now carrying `protocol_gate`) and `_no_launch_record` hands it to `_run_job_ended`, `_notify_job_record` and `_send_derived`, which call `notify.send` without `_recoverable`; and the earlier delivery sits in an **earlier run's** `notifications.jsonl`, not in the new run's. The protection is therefore in the one function every send passes through, not in recovery: `_send_derived` drops an event whose `supersedes` is set when a **delivered** outcome (round 10, I4: `sent` or `conflict`, or a server-side `duplicate`, the states that prove the server holds the key; not `failed` or `rejected`, which only say attempts were spent) exists under the key of the superseded type, same repository and identity, in the notification log of **any recent run**. "Recent" is the `RECOVERY_RECORD_LIMIT` newest `runs/<run_id>/` directories of the runtime root (the root is the open run's `RunRecord.runtime_root` on the live path and the one `resume` already holds on the recovery path); a directory with no log, an unreadable log or a log over the existing size cap is skipped, and when the runtime root cannot be resolved the event is sent (a duplicate INFO is the safe direction; a lost stop is not). One helper, `_superseded_handled(event, repository, runtime_root, spent)`, is the only place that reads the old key, and it reads each examined log once per call. **Two questions, one helper (round 10, I4):** the live path asks "does the server hold the old key?" (`spent=False`: delivered outcomes only), so an old `user_gate` that failed through an outage or was rejected on a bad key never vetoes a fresh send, and the owner still gets the stop once service or credentials are restored. Recovery asks "were attempts already spent?" (`spent=True`: the existing `_HANDLED_OUTCOMES`, `failed` and `rejected` included), which is the policy recovery has today of not replaying spent attempts, unchanged and with no persistent retry added. **Containment (round 10, O1):** the helper resolves each candidate `runs/<run_id>/notifications.jsonl` and the runtime root and skips a log whose resolved path is not inside the resolved `runs` directory (a symlinked run directory or log is skipped, not followed), because `_outcome_lines` itself follows symlinks; the skip is the safe direction (the event is sent). A stop whose old `user_gate` was never handled is sent once as `review_wait`; the next step against the same gate finds the `review_wait` outcome in the log of the run that sent it and the in-process and server duplicate rules apply as they do today. Nothing else of `_send_derived` changes (the arguments, the `recovered` flag and the run id are passed on as now).
- **D4. A normal merge is already an info event; the plan pins it and changes no code.** Checked at the base commit: `pr_merged` is a member of the `info` kind (INFO, NORMAL) in `EVENT_TABLE`, and `derive_pr_merged` sends it when a binding record observed a merge. The branch gates that ask for the owner (`merge_pull_request`, `merge_held`) stay `user_gate` through `milestone_branch.USER_GATES`. A test pins both facts so a later change cannot move them silently.
- **D5. The pending-checks wait is untouched (owner decision).** `checks_pending` keeps its current mapping in both `derive_job_event` (the reporter record) and `derive_branch_gate_event`; a test pins that a spent wait still sends `lane_blocked`.
- **D6. The documentation names the new type and the rule.** `docs/guide/commands.md` (the event table of `notifications`), `docs/guide/automation.md` (the notification paragraph and the functional-review stops sentence) and `docs/ROADMAP.md` (NF1 done; follow-up 26 states that it is finished) change. The release note, the release history row and the compatibility line belong to the docs pull request after the 1.19.3 release, as for every earlier release. The pull request closes #149.

- **D7. Rule 2 reads a field the production writer writes (round 8, I1).** The Workflow's own protocol gates reach `_no_launch_record` (`controller/job.py`, the fall-through return of `run_job`) and `_no_launch_record` persists no `protocol` block, so `_protocol_disposition(record)` is `None` for them (probed through the real writer: rows 14 and 28, disposition `external_gate`, both records without `protocol`). The `protocol` block is **not** added to these records: the existing `blocked` branch of `derive_job_event` keys on `_protocol_disposition(record) == "blocked"`, so exposing a disposition that is absent today could turn a gate that sends `user_gate` now into `lane_blocked` (the reviewer's warning), and `resume`'s reconcile reads that block as the mark of a launched protocol job. Instead `run_job` passes `extra={"protocol_gate": {"row", "disposition", "action_id"}}` to `_no_launch_record` at that one call site, taken from `decision.protocol` (the Workflow's decision as received); it is an additive optional field, absent otherwise, and no reader but the new one in rule 2 looks at it. The other `_no_launch_record` callers (the Controller-coded gates built by `protocol_decision.gate_for` for the review-mode refusal and the round cap, the declined and handoff records, the tester step's own records) pass no such field, so each of them stays `user_gate` or its current event. The `blocked` branch, the pending-checks branch and `lane_blocked` for a `blocked` disposition are unchanged, and tests pin them on the production path: a gate whose protocol disposition is `blocked` and one for a Controller-coded gate over a row-14 decision derive what they derive at the base commit.
