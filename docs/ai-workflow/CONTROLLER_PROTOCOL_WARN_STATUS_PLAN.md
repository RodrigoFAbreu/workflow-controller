## Goal

Controller 1.7.0 refuses `explain`, `step` and `run` with exit 20 ("protocol verify gave an answer outside the protocol ... 'warn'") whenever a Workflow 2.8.0 or later repository's `verify` reports a check as `warn`. Orchestration Protocol 1.1 added that status; `controller/protocol_schema.json` (Workflow 2.7.0's schema) allows only `pass`, `fail` and `skip`. This blocks moving this repository to Workflow 2.9.0 with automatic gates, so it comes first.

After this milestone:

1. A `warn` check is **advisory**: it never makes the repository unhealthy, never blocks a step, and its detail is shown.
2. The vendored schema is Workflow 2.9.0's (protocol 1.2). The delta from the vendored 2.7.0 file (protocol 1.0) is **two protocol minors**: eight new action ids (`acceptance.satisfy`, `functional.evidence.external`, `implementation.resume`, `implementation.satisfy`, `legacy.retire`, `plan.satisfy`, `pr.apply_review`, `pr.review.external`); the worker role `validator` and the check id `gate_policy` (both open enums); `record-external-result` loses all but `stage` and `basis` as required fields, gains the stages `functional` and `pr_review` and the fields `identity`, `fact_id`, `slot` and `flow_id`; and new `$defs` `policy`, `forge` and `inputs`, `decision.policy` and two new `satisfied_by` values. D5 classifies each new action id; the `inspect` advisory keeps naming the ones this Controller cannot launch.
3. The pages that document the refusal say it is gone, and `docs/compatibility.md` lists 2.9.0.

Out of scope: Workflow-side policy logic, moving this repository to 2.9.0, any change to a gate's meaning, vendoring a full 2.9.0 release tree (Workflow Manager's checkout has no `distribution/workflow` for it, and capability admission needs none).

## Decisions

- **D1. `warn` is advisory, not a gate.** The Workflow owns the meaning of `healthy`. `Verify.healthy` stays the Workflow's boolean; the Controller never recomputes it from the statuses. A `warn` beside `healthy: true` is shown and ignored. A `warn` beside `healthy: false` changes nothing: the existing `workflow_unhealthy` gate names the `fail` checks, and the gate text additionally lists the `warn` checks so the operator sees every check the Workflow reported. (Principle 7: the Workflow owns lifecycle meaning.)
- **D2. The `status` enum stays strict.** It is not added to `OPEN_ENUMS`. A status a later protocol minor invents is unknown meaning, so it keeps failing closed with the same exit 20 until a Controller release learns it. `warn` is accepted because the vendored schema now lists it, not because the enum was loosened. A test pins that an invented status is still refused.
- **D3. Vendor the schema byte for byte.** (Protocol 1.0 to 1.2; the delta is stated in Goal item 2.) `controller/protocol_schema.json` becomes the schema Workflow 2.9.0 publishes (`payload/docs/ai-workflow/orchestration-protocol-v1.schema.json` in the Workflow repository, tag `v2.9.0`), sha256 `c203f2b263a3060be1e1f41d478bebd60c1a40302de9daecf7fe7cc97d5af52c`, pinned by a test. It loads under the existing keyword subset (checked 2026-10-09 by constructing `Schema` from it, and re-checked by the plan review: with the file swapped into a scratch copy of the base, 234 tests in the protocol modules and `tests.test_cli` pass except the sha pin), so `protocol_schema.py` needs no new keyword. The relaxed `record-external-result` shape is unused: no `controller/` module sends or parses that operation (`grep -rn record-external-result controller` finds only the schema), so nothing needs handling and a test pins that no module names it. The published copy is kept at `tests/protocol_schemas/workflow-2.9.0.schema.json` (the existing `tests/workflow_releases/2.7.0/` tree must stay: the lifecycle tests install its scripts, and its own schema copy is part of its pinned `RELEASE.json`).
- **D4. Where the advisory is shown.** `protocol.verify` returns `Verify` with the checks as before plus a `warnings` property (the `warn` checks). A new `protocol_decision.preflight(...)` returns `(gate_or_None, advisories)` where `advisories` is a tuple of `verify <id>: warn: <detail>` lines; `health_gate(...)` stays as a thin wrapper returning only the gate (its callers `controller/job.py:4962`, `controller/cli.py:920` and `tests/test_protocol_job.py:289` keep working). One shared helper, `protocol_decision.decide_after_preflight(managed_repo, work_item, *, base)`, returns `(decision, advisories)`: the unhealthy gate when `preflight` gives one, else `decide(..., advisories=advisories)`. Both `explain` (`controller/cli.py`) and `job._decide_protocol_current` call it, so the two sites cannot drift (the same reason `explain` already mirrors `step`'s job-history read); the loop guard and the instability guard stay at their sites but receive the advisories.

  **Every constructor of a standing decision on the protocol path** gets the advisories, through one mechanism: an `advisories: tuple[str, ...] = ()` keyword that `_Context` stores and `_Context.evidence()` appends (so every `context.gate`, `context.blocked`, `complete` and automatic decision carries them): on `decide`, `from_answer` and `gate_for`. The constructors are: (1) `from_answer`, reached through `decide`; (2) `health_gate`/`preflight`'s `workflow_unhealthy` gate, which lists the `warn` checks after the failing ones; (3) `gate_for`, called by `job._unstable_gate` (`decision_unstable`) and `job._no_progress_gate` (`no_progress_repeated`), both of which gain an `advisories` keyword that `execute_step` passes and `explain` passes to `_no_progress_gate`. `from_answer` raising `WorkflowProtocolFailedError` produces no decision (a refusal, exit 20) and carries none. No standing decision omits them. Do **not** use `dataclasses.replace` or any `.replace(` call (`test_write_containment` flags any `.replace()` call in `controller/`).
- **D5. The eight new action ids, classified (Workflow 2.9.0 `ACTIONS`, `payload/scripts/workflow_protocol.py`; `ORCHESTRATION_PROTOCOL.md` rows 14a, 28a, 38d-38h).** `PROTOCOL_ACTIONS` is unchanged; the twelve automatic ids are unchanged.
  - **user-only** (`legacy.retire`, `implementation.resume`): `_automatic` blocks them (`workflow_user_only_action`) if one ever became the next action; they are gates the Controller never launches by design.
  - **external gates** (`functional.evidence.external`, `pr.review.external`, role `external`): rows 38e-38g are `external_gate`, which `from_answer` turns into a gate; never launched, like `plan.review.external` already in the 2.7.0 catalogue.
  - **automatic or validation, no command here** (`plan.satisfy`, `implementation.satisfy`, `acceptance.satisfy`, role `validator`, disposition `validation`; `pr.apply_review`, role `applier`, disposition `automatic`, rows 38d, also matching `MILESTONE_COMPLETE` items): the Controller has no `PROTOCOL_ACTIONS` entry for them. At runtime they are still stopped safely (`workflow_unknown_disposition` for `validation`, `workflow_unknown_action` for `pr.apply_review`).
  - **Advisory decision (option (a) of review LPR-1-001).** The schema's catalogue cannot say which ids are user-only (that flag is in `worker`, not in the catalogue), so `protocol_decision` gains an explicit `UNLAUNCHED_AUTOMATIC_ACTION_IDS` frozenset of exactly the four ids of the third bullet, and `unknown_action_ids` becomes `listed - PROTOCOL_ACTIONS - (protocol.KNOWN_ACTION_IDS - UNLAUNCHED_AUTOMATIC_ACTION_IDS)`. So `inspect` keeps warning, for a 2.8.0/2.9.0 repository, about the four ids this Controller cannot launch, and stays silent for the four gates it never launches. The `unknown_action_ids` docstring and `docs/compatibility.md` (line 20, "an advisory about action ids it does not know") are corrected to say so; a test pins `unknown_action_ids` for a 2.9.0 `describe` listing (exactly the four, `pr.apply_review` among them) and for an invented id.
- **D6. Release.** `fix:` PR title, squash merge, 1.7.1. Release notes (`docs/releases/1.7.1.md`) come in the docs pull request that follows the release, as for earlier patches. No change to `pyproject.toml`, `setup.py` or the CI workflows.

No "Open decision" row in `docs/TECHNICAL_DECISIONS.md` is touched: that document describes the Android application's prototype, not the Controller.

## Risks

- **Unknown future statuses.** Kept strict on purpose (D2); the cost is another patch if protocol 1.3 adds a status.
- **Advisory noise in `run`.** Each step prints no new line; the advisory is in `explain` output and the job record only, so a long run is not flooded.
- **Golden and equivalence tests.** CP2 changes call sites in `job.execute_step`; the equivalence suites are the guard, and `health_gate`'s signature is unchanged.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/` or the `docs/*.md` pages (known follow-up 10). The declaration here is therefore D1's reviewed classification with this item's ids, and the review of revision 1 confirmed that every path the checkpoints name is classified at both stages. Revision 2 rewrites only its reason strings so they describe this item (the Controller source, `tests/` and the pages are changed by CP1-CP3; `README.md`, `tools/` and `pyproject.toml` are not); the declaration is protected at the implementation stage, so it is final once approved.
