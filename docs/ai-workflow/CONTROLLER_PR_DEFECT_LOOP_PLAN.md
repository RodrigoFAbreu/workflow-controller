# Close the pull request defect loop: report the pull request's state and apply its review result (Revision 5)

Work item: `workflow-controller-pr-defect-loop`
Work item type: `product`
Governing workflow version: `2.2` (this repository's `docs/ai-workflow/WORKFLOW_CONFIG.json` default at creation)
Base commit: `164d813810d0c17805320fd661c51d82d00fcc70` ("docs: 1.14.0 release notes (#90)"), the tip of `main`, passed explicitly as `/milestone-plan 164d813…`.
Lifecycle authority: this repository's installed Workflow **2.13.0**, automatic gates.
Roadmap slot: `docs/ROADMAP.md` step **C10b**, the second third of C10 (C10a is released as 1.14.0), first of "Next, in order".
Released baseline: `workflow-controller 1.14.0`. The change adds a routing role (`apply-pr-review`) and a Controller-run report step, so the squash commit is a `feat:` and releases the minor release **1.15.0**.
Pull request title: `feat: report the pull request's state to the Workflow and apply its review result so acceptance clears itself`

## Goal

Under an automatic acceptance gate the Controller still stops where the Workflow needs a pull-request fact or a pull-request defect applied. Three rows cause it, and each is a stop that a person or an orchestrating session clears by hand today:

- **Row 38f** (`pr_evidence_needed`, action `pr.review.external`). A refused `/satisfy-gate acceptance` stored a fact whose checks were `pending`. The Workflow queries GitHub again only when no fact is stored or a reported `pr_review_result` is newer than the stored one, and `next-action` never runs `gh`, so the answer stays 38f after the checks turn green until someone acts.
- **Row 38g** (`pr_approval_needed`), the same action, when the gate requires an approved pull request.
- **Row 38d** (`pr_query_due` or `pr_review_actionable`, action `pr.apply_review`). A reported fact arms the query trigger, or a stored fact carries an unapplied cause (`changes_requested`, `checks_failed`, `content_changed`); the Controller blocks the action as unlaunchable since C10a.

After this milestone the Controller reports the pull request's state to the Workflow itself (the `pr_review_result` reporter) and launches `/apply-pr-review` (`pr.apply_review`) like any other automatic action, so a run whose checks were pending carries on once they are green, and a pull request found red **before acceptance** (at `AWAITING_FUNCTIONAL_REVIEW`, the only phase where rows 38f and 38g answer) reopens the same work item into remediation and returns to acceptance, with no person in the loop. A person is asked only where one is needed: an approval that only a person can give (row 38g), a functional-evidence gap (row 38e, C10c) or a defect the Workflow calls blocked.

**Out of scope, deferred (revision 3).** A red pull request found **after** acceptance, in C4's merge flow, is not delivered here. `job._execute_step_locked` runs `milestone_branch.waiting_preflight` before `_decide_protocol_current`, so for a `MILESTONE_COMPLETE` item with failing checks `_checks_gate` stops at `checks_failing` before `next-action` is asked, and rows 38f and 38g answer only at `AWAITING_FUNCTIONAL_REVIEW`, so nothing arms the query there. Making it reachable needs the merge flow to report the fixed query's output at its own stop (or at a `CHANGES_REQUESTED` review decision) so that row 38d arms, plus a lifecycle scenario (accepted, red, reopened, accepted again, merged). CP4 adds that as a named ROADMAP follow-up, **C10d**; until then that case ends at the merge flow's own stop, with a person, and CP3 pins it (scenario 9).

## Decisions

Each decision states one principle.

- **D1. The Workflow decides and the Controller only launches or reports.** `pr.apply_review` becomes a launchable automatic action: the table entry renders `/apply-pr-review <id>`, the answer's worker must be role `applier` and not `user_only`, and every other pairing is blocked as for the other twelve automatic ids. The Controller never reads the pull-request fact, evaluates no cause and chooses no branch (no code change, bounded fix, broad fix): that is the command's own cause table. A finished `pr.apply_review` job is reconciled like every protocol job; the classes the Workflow gives it (`progress` for a reopen or a changed phase, `no_progress` for a refreshed fact) feed the existing loop guard unchanged.
- **D2. A reopened item is surfaced by naming it, so the table entry always carries the work item.** `/apply-pr-review` requires the id and refuses a bare call; the command itself can reopen a completed item, but in this milestone the Controller reaches it only at `AWAITING_FUNCTIONAL_REVIEW` (see the deferral in the Goal). The Controller's `next-action` call already names the item. For any non-`plan.start` action `_automatic` already raises `WorkflowProtocolFailedError` (`protocol_decision_invalid`) when the answer's `work_item_id` argument is absent; CP1 pins that existing refusal for `pr.apply_review` and adds no new blocked code.
- **D3. The apply worker is a role of its own: Opus at `xhigh`, not single-agent.** `apply-pr-review` fixes code on the bounded branch and delegates like `apply-functional-review` and `apply-implementation-review` do, so its route is `_OPUS`. It is overridable like every role and joins the settings file's role names, which raises the settings table generation to 10. `UNLAUNCHED_AUTOMATIC_ACTION_IDS` becomes empty.
- **D4. The reporter is a Controller step, not a worker, and it reports only what GitHub says.** At an `external_gate` whose action id is `pr.review.external` and whose `satisfied_by` is `pr_review_result` (rows 38f and 38g), and only for a target that has a milestone-branch binding with a pull request, the step runs the Workflow's one fixed query (the vendored `pr-list-v1` argv: `gh pr list --repo R --state all --search C --limit 200 --json number,url,state,headRefOid,reviewDecision,reviews,statusCheckRollup`) for the item's **anchor** commit `C` (the commit the Workflow's own `query_and_store_pr_fact` queries via `workflow_gate_policy.anchor_of`, already local so no fetch is needed). The Controller does not import the Workflow's scripts, so it reads the same two state fields itself: `technical_approval.reviewed_content_commit` when the approval carries it together with `approved_review_content_id`, else `reviewed_implementation_head`, and no anchor (nothing to report) when neither exists; a CP2 agreement test runs the vendored `anchor_of` over the same work-item fixtures, fallback included, and asserts the commits agree. The repository `R` is the milestone-branch binding record's `record["repository"]["forge_repository"]` (the accessor `milestone_branch` already uses at its other `ctx.forge(...)` calls; `_forge_repository_of` parses a remote URL and is not the accessor), and `GhForge` is constructed with that value. A binding repository that differs from `origin`'s is the Workflow's own `ForgeRepositoryMismatchError` refusal at `record-external-result`, which ends the step in a gate naming it. The step hands the verbatim output to the Workflow through `record-external-result --kind pr_review_result`. The input is the `forge` block (`source`, `query`, `repository`, `queried_commit`, `fetched_at`, `fetched_by`, `raw`, `raw_sha256`) and a `run_ref` naming the Controller job. The Controller parses nothing and derives nothing: the Workflow parses `raw` itself, and a reported fact "only arms the query, never decides". This is the courier the code review and the functional evidence already use: Controller-run, recorded as a job, handed to the Workflow. The reporter acts only when the decision's policy object names an **automatic** acceptance gate. Row 38g also answers under a **human** acceptance gate (`pr_approval_needed`, `satisfied_by: pr_review_result`, remedy `/accept-milestone`); there the reporter does nothing, so the reporter never arms row 38d under a human gate: the stop stays `user_gate` with the Workflow's `/accept-milestone` remedy. (Row 38d has no gate-mode condition: a red fact that `/accept-milestone` itself stores under a human gate answers `pr_review_actionable`, and the Controller then launches `/apply-pr-review` under D1. That launch is wanted: it is the Workflow's own defect path, and it is not something the reporter causes.) A report the Workflow refuses (for example `forge_unavailable` for an `origin` that is not a `github.com` URL) ends in a gate naming the refusal and writes nothing.
- **D5. A report changes the answer, or it is not made.** A report is useful only if it differs from what the Workflow holds. The step reports when the fresh query's `raw_sha256` differs from the one the last `pr_report` job for this item sent; if it is the same, nothing changed since the last report, so the step does not report again and the stop stays (`pr_report_unchanged`), which makes the report/apply cycle finite. The comparison is against the last report's `raw_sha256`, not the stored fact's signature, so a raw change that leaves the signature unchanged (a re-run check, a COMMENTED review under an APPROVED decision) is reported once more. **That report is not free (revision 5):** `ingest_pr_facts` always stores a reported fact in `pr_reported` with the next `ingest_seq`, whatever its signature, so the stored `pr` fact is now older. `pr_query_trigger` is false (equal signatures), so row 38d does not answer; `_acceptance_pr` sets `pending_query`, so row 38f and row 38g return nothing; `satisfiable_after_query` is true, so the answer is **row 38h** (`acceptance.satisfy`, "the act queries GitHub itself first"). The Controller launches `/satisfy-gate acceptance` (C10a), which queries GitHub, is refused and stores a newer `pr` fact; the answer returns to 38f or 38g and the next step stops `pr_report_unchanged`. This is the common path at row 38g, whose stop usually follows a refused `/satisfy-gate acceptance` that has just stored the same pull request's state. The plan **accepts that one launch** per unchanged-signature report rather than adding a Controller rule that parses the fact: the cost is one worker, it is bounded, and the Workflow's own answers choose it. The cycle is finite for two reasons the tests name: D5's raw comparison stops the next report, and the refused `/satisfy-gate` query stores a newer `pr` fact, which returns the answer from 38h to 38f/38g (and changes the state identity, so the loop guard's streak resets rather than counting it). `explain` words the stop after it as "reported; the report changed nothing", never as "not reported", and the notifications guide says that an operator waiting on a person's approval sees one refused `/satisfy-gate` worker after a report whose fact is unchanged; `explain` words that stop as "reported; the report changed nothing", never as "not reported". A query whose checks are `pending` is not reported only when D6's three conditions hold; the step then waits (D6). Rows 38g and 38f share the rule, so a pull request still unapproved after a report stops at 38g with the approval named (the person who approves on GitHub makes the next fact differ).
- **D6. Pending checks wait only when they are the one thing the Workflow is waiting for; they never hide an approval or an objection, and "pending" is the Workflow's own test.** The step waits instead of reporting only when **all three** hold: (a) the decision is row 38f (`pr_evidence_needed`), never row 38g (`pr_approval_needed`), because at 38g the Workflow awaits an approval and a rollup that stays empty or pending in a repository without CI (`require_ci: false`) would otherwise hide the approval for ever; (b) that row's own stop text names the unmet `ci_green` requirement (the Workflow's words: 38f lists `ci_green` only when `require_ci` is effective, so the Controller reads no policy value itself; CP2 pins this against the vendored answers and, if the text does not carry it, amends this decision); and (c) the fresh record carries no standing objection by the Workflow's own rule, that is no `reviewDecision` of `CHANGES_REQUESTED` and no failing check (`failure` already takes precedence over `pending`). When (a), (b) and (c) do not all hold, pending checks are reported like any other result, and the Workflow's own query decides acceptance and reopening: a current-head `CHANGES_REQUESTED` reaches row 38d and `/apply-pr-review` while checks are still pending, and an approval given in a repository without CI reaches the stored fact. The wait predicate, when it applies, is "the record the Workflow would select has check state `pending` by the Workflow's own rule" (`workflow_forge.parse_forge_raw` and `_checks`): the selected record is the single `OPEN` one, else the newest (highest `number`) closed or merged one, older records being ignored; its checks are `pending` when its `statusCheckRollup` is **empty** (checks not registered yet just after a push, or no CI: fail closed) or any entry is unfinished (`status` other than `COMPLETED`, no conclusion, or a StatusContext `state` of `PENDING` or `EXPECTED`), and `failure` takes precedence over `pending`. The Controller keeps this one small hand-written predicate (it derives no other fact) and a CP2 test ties it to the vendored parser. A query with **no** record at the anchor commit (the Workflow's `NO_PULL_REQUEST` fact, whose checks are `pending`) does not wait: it is the missing-pull-request stop of CP2, since no push registers checks for a pull request that does not exist. An empty rollup waits rather than reports, so the window right after a push cannot produce a pending report whose signature equals the stored one. When the fresh query shows pending checks by this predicate the step ends in a waitable gate (`pr_checks_pending`) that the existing `--wait` budget of `run` polls, as C4 waits for readiness; without `--wait` the gate is a stop that names the pending checks, as today. The stop text says "no checks reported" when the rollup is empty (as `_checks_gate` does), so a repository without CI is told why the wait ends. CP2 first reads the wait code in `controller/cli.py` and `controller/milestone_branch.py` and reuses it; if it cannot be reused, CP2 adds the smallest bounded poll to the step and amends this decision. The wait is the shared bounded polling machinery, not a second one (O1): `milestone_branch.waiting_preflight` polls only `repository_preflight`, before the reporter's decision exists, so CP2 factors that loop into one helper that both call, keeping one deadline from the first waitable gate across gate changes, the `clock`/`sleep`/`monotonic` seams, `on_wait` and `WaitInterrupted`; the reporter's step re-runs the query on each poll. Nothing about the wait reports a pending fact when D6's conditions hold.
- **D7. The sequence is the Workflow's, and the tests show it on real answers.** A reported fact arms row 38d (`pr_query_due`); `/apply-pr-review` runs the Workflow's own query, stores the fresh fact and (for a fact needing nothing) classes `no_progress` (`pr_fact_refreshed`, `nothing_to_apply`); then the answer is row 38h and `/satisfy-gate acceptance` passes. After a report whose fact has the **same signature** as the stored one the answer is also row 38h, not a stop (D5): the one `/satisfy-gate acceptance` it launches is refused and stores a newer `pr` fact, and only then does the answer return to 38f/38g. For a red fact the same command reopens the item: `progress`, then the ordinary review, functional and acceptance rows. The loop guard counts two `no_progress` jobs per `(item, action)` and blocks the third; a report/apply/satisfy cycle runs one apply, so it stays clear, and a cycle that would repeat is stopped by D5 before the guard. The review round cap (`review.round_cap`) already caps the implementation review rounds a bounded fix opens; `pr.apply_review` itself is not a capped action.
- **D8. A stop asks for a person only when one is needed (the rest of follow-up 26).** After this milestone a `GATE_BLOCKED` stop at row 38f or 38d is no longer reachable by design: 38f is cleared by the reporter or waits (D6), 38d is launched. A red pull request after acceptance still ends at the merge flow's own `checks_failing` stop (the deferral in the Goal, C10d). The remaining `external_gate` stops under an automatic acceptance gate are row 38g with the approval still missing (a person must approve on GitHub: `user_gate`, correct), row 38g under a human acceptance gate (`/accept-milestone`, D4) and row 38e (C10c). CP4 states this in the notifications guide and marks follow-up 26 done except row 38e, which C10c owns.
- **D9. Every behaviour change is shown on a real Workflow answer.** The tests use the vendored 2.12.0 tree's `next-action` answers for rows 38d, 38f, 38g and 38h (`tests/workflow_releases/2.12.0`), and lifecycle scenarios with fake workers, an injected `gh` runner for the Controller's query and the vendored functions' seams for the Workflow's (CP3 names the fixture; the functional-tester isolation rule: a clone's origin is the real repository). No test reaches GitHub.
- **D10. The documents are changed in place.** The runtime guide (the 38f/38d stops and their old manual remedy are removed), the commands guide (the role table), the automation and notifications guides, the compatibility page (what the Controller reports), the common-problems page and `docs/ROADMAP.md` say what the Controller does now; none keeps a "until C10b" sentence. An ADR records D4 and D5.

### CP3 -- The loop end to end on real answers (D7, D9)

- `tests/test_protocol_lifecycle.py`, with the existing fake workers and the vendored 2.12.0 Workflow. **Fixture (the C10a `GateLifecycle` pattern):** `origin` is set to `https://github.com/owner/repo.git` and nothing is pushed to or fetched from it, so the Workflow's `origin_repository`, `ingest_pr_facts` and `query_forge_pr_facts` accept it with no network access; any push or fetch the scenario needs uses a separate scratch bare remote. The Controller's own query uses an injected `GhForge` runner (no `PATH` lookup). The fake workers call the vendored functions (`ingest_pr_facts`, `query_forge_pr_facts`, `workflow_state.begin_pr_review`) with their `run`/`resolve` seams, as C10a's `_SATISFY_ACCEPTANCE` and `_REPORT_PR` do, because the Workflow's `resolve_gh` refuses a `gh` under `/tmp`, in the repository or in a world-writable directory, so a fake `gh` on the `PATH` cannot answer the Workflow's own query:
  1. **Pending clears itself.** Acceptance with the pull request's checks pending: `/satisfy-gate acceptance` is refused and stores the pending fact, the answer is row 38f; the step waits (D6); the fake's checks turn green; the step reports the green query; the answer is row 38d (`pr_query_due`); `/apply-pr-review` runs the Workflow's own query, stores the fresh fact and classes `no_progress`; the answer is row 38h and `/satisfy-gate acceptance` completes the milestone. The run ends `MILESTONE_COMPLETE` with no stop and no `user_gate`.
  2. **A red pull request reopens the item.** The fake reports `CHANGES_REQUESTED` (or failing checks) at the head: the reported fact arms 38d, the apply worker reopens the item (a fake that performs the Workflow's reopen by calling the vendored `workflow_state.begin_pr_review`), the run continues through the ordinary rows to acceptance again, and the item completes. The loop guard did not trip.
  3. **An unchanged fact does not loop.** The step reports once, the apply refreshes with `no_progress`, and a still-unsatisfied gate stops with the Workflow's own reason, never a third `pr.apply_review` launch and never a second report of the same output. A second variant reports an output whose signature equals the stored fact's (scenario 4's sequence), with the same bounds.
  4. **Row 38g needs a person.** Under `requires_pr_approved` with the pull request unapproved, a refused `/satisfy-gate acceptance` has stored the unapproved fact (row 38g). The step reports the query, whose signature equals that stored fact's; the answer is then **row 38h** (the vendored 2.12.0 answer is asserted, not assumed); the Controller launches one `/satisfy-gate acceptance`, which is refused and stores a newer `pr` fact; the answer returns to 38g and the next step stops `pr_report_unchanged` with `user_gate` naming the approval. Exactly one refused launch, no second report of the same output, no `/apply-pr-review`, and the loop guard did not trip; after the fake's decision becomes `APPROVED` the next step reports the new output and the run carries on.
  5. **Approval without CI.** `require_ci: false`, `requires_pr_approved: true`, the rollup stays empty. A refused `/satisfy-gate acceptance` stores the unapproved fact (row 38g); the step reports once, the answer is row 38h, one refused `/satisfy-gate acceptance` follows and the run stops at 38g with the approval named (the sequence of scenario 4); the fake's decision becomes `APPROVED`; the next step reports the new output (not held back by the empty rollup), the answer is row 38d, `/apply-pr-review` refreshes the fact, `/satisfy-gate acceptance` completes the milestone.
  6. **An objection is not hidden by pending checks.** A current-head `CHANGES_REQUESTED` review with checks still `pending` is reported at once (no wait), arms row 38d and `/apply-pr-review` launches and reopens the item, as in scenario 2.
  7. **A target without a binding** keeps the old stop at 38f.
  8. **A human acceptance gate** at row 38g: the step reports nothing, the reporter arms no row 38d and the stop stays `user_gate` with the `/accept-milestone` remedy.
  9. **A red pull request after acceptance is not looped (deferral, C10d).** A `MILESTONE_COMPLETE` item whose pull request has failing checks ends at the merge flow's own `checks_failing` stop; no `pr_report` job is created and no `/apply-pr-review` is launched.
- `explain`/`inspect`: the 38f and 38d stops are described by what the next step does (report, wait, apply), not as a manual remedy; their goldens follow.

Done when the scenarios pass and `tests/test_protocol_lifecycle.py` and the explain/inspect tests pass.

## Risks

- **A report whose head the Workflow refuses (CP2).** The Workflow checks the reported head against the repository (`pr_head_unknown`, `pr_head_not_in_branch`). The step queries the item's anchor commit, already local (no fetch); a refusal ends in a gate that names it and writes nothing.
- **A loop between report and apply (CP2, CP3).** D5 stops a repeated identical report, the loop guard stops a third unproductive `pr.apply_review`, and a report with an unchanged signature costs one refused `/satisfy-gate acceptance` (row 38h) before the stop, which D5 accepts. Scenarios 3 to 5 pin each.
- **Reaching GitHub (CP2).** The reporter's `gh` call is read-only and goes through the existing resolver; `/apply-pr-review` and `/satisfy-gate` query GitHub themselves from the worker. Tests never reach GitHub because the fixture supplies an injected runner and a `github.com` origin URL that nothing is pushed to.
- **A Workflow release that changes rows 38d-38g.** The tests run on the vendored 2.12.0 answers; this repository runs 2.13.0. CP3 runs the same scenarios against the installed 2.13.0 scripts when they are importable as a fixture, and records the difference if any in the checklist.
- **Size.** Four checkpoints, two with fakes of GitHub. If CP2 outgrows a session it is split by amending the plan, not by dropping the wait.
- **Open decisions.** `docs/TECHNICAL_DECISIONS.md` does not exist in this repository; no open decision is finalized here. D4's courier is a Controller step rather than a worker because a worker adds a model and a cost to a call that is a single read-only query; the owner can ask for a worker at plan approval.
