## Goal

Review loops took about 65% of worker usage over six milestones (local plan review 30%, local implementation review 18%, applying plan reviews 10%, applying implementation reviews 7%); plans took 11 to 16 local review rounds each. Workflow 2.12.0 (W8) shipped its half of the fix: from round 2 a reviewer may review only the changes since the last round, a verdict's shape is checked, and protocol 1.4 adds `review_round` to an item's `next-action` snapshot. The Controller still dispatches review and apply workers for as long as the Workflow says `automatic`, however many rounds that is.

After this milestone:
- a protocol target's review loop stops at a **round cap** per review stage (`review.round_cap`, default 4). At the cap the Controller launches no review or apply worker and returns a gate that says which stage, which round and what the owner can do; the Controller never accepts at the cap itself;
- the owner continues by raising the cap for one command (`--review-round-cap N`) or for good (the setting), accepts at the cap through the Workflow's existing user-only paths, or withdraws and re-scopes the plan;
- `telemetry` shows each worker job's **activity** (the protocol action), **stage** and **round**, and can group usage by them, so a before and after comparison of the review loop is one command over the recorded jobs.

## Decisions

Each decision states one principle.

- **D1. A round is the Workflow's number, else the Controller's own count, never a guess.** The round of a stage is `snapshot.review_round[<stage>]` when it is an integer (protocol 1.4, Workflow 2.12.0 and later). When it is `null` or absent (an older Workflow, or a history the Workflow cannot show complete) the Controller derives the round from **persisted revision evidence, never from a reconcile class**: an **observation** is the (`phase`, revision) pair of a stored `pre_state` of this repository's and work item's protocol job records read oldest first (excluding `GATE_BLOCKED` records), followed by the current snapshot as the last observation. For `implementation` the count is **1 plus the number of times `implementation_revision` rose** across the observations. For `plan` it is **the number of distinct integer `plan_revision` values observed at a plan-review ready phase** (`workflow_state.PLAN_REVIEW_READY_PHASES`: `AWAITING_LOCAL_PLAN_REVIEW`, `AWAITING_MANUAL_EXTERNAL_PLAN_REVIEW`, `AWAITING_PLAN_APPROVAL`), and never less than 1. A revision seen at a ready phase was published and bound, which is publication evidence; a revision seen only at `PLANNING`, `REVISING_PLAN` or `AMENDING_PLAN` is authoring and is not a round. The difference matters: `create_remediation_child_work_item` creates an unpublished `PLANNING` child at `plan_revision` 1 (`scripts/workflow_state.py:13022`) and `/milestone-plan` advances it before its first publication (`:10407`), so that child's first publication is at revision 2, the Workflow's `review_round.plan` is 1, and a count of every rise would say 2 and stop its first local review at cap 1; interrupted authoring can add further unpublished rises. The plan count agrees with the Workflow's own rule (consumed contents plus one while published or bound): each distinct ready revision is one consumed or current content. The two stages differ in how well that revision tracks the Workflow's own number. For `implementation` it is the same field `review_round.implementation` is taken from (`scripts/workflow_protocol.py:2283`), so the fallback agrees with the Workflow. For `plan` it is **not**: `review_round.plan` is the number of consumed plan contents plus one while the binding is `PUBLISHED` or `BOUND` (`_plan_review_round`, `scripts/workflow_protocol.py:2228-2258`; protocol section 5.4), and it never reads `plan_revision`. `/apply-plan-review` step 5 publishes new content on every round whether or not the author advanced `plan_revision`, so a plan round can open with `plan_revision` unchanged. This repository's `workflow-controller-automated-lifecycle-scenarios` has 10 consumed plan contents and a `BOUND` binding, so the Workflow's plan round is 11 while its `plan_revision` is 10. The Controller's job records store no per-content plan evidence (`PRE_STATE_FIELDS` has `plan_revision` and `bundle_id` only, and D7 adds no schema), so the plan-stage fallback is **a lower bound**: it undercounts exactly when a plan round published new content without advancing `plan_revision`, and the undercount can grow with the item's history. It is never an overcount, because each counted revision was observed at a ready phase, so it is a published content. An `implementation_revision` rise is a strict increase between two consecutive integer observations; `null`, a missing key and a decrease are skipped without counting, and for `plan` a `null`, missing or non-integer revision, or a missing or unknown phase, is not counted. The reconcile class is deliberately not the evidence: the Workflow assigns `gate_reached` whenever the next decision is a human or external gate, before it looks at the phase or the revision (`scripts/workflow_protocol.py:2612`), so a `2.1` apply that publishes revision 3 to 4 and ends `gate_reached` is a new round that a `progress`-only count would miss; and `record_bundle_generation(..., outcome="same_content")` leaves `implementation_revision` unchanged (`scripts/workflow_state.py:14417-14423`), so a `2.2` implementation apply or a bounded functional apply can end `progress` with the revision 3 to 3, a republication that is not a new round and that a class-based count would add. A revision published by an apply done by hand between two jobs is observed when a later job's `pre_state` or the snapshot shows it at a ready phase. This one rule serves the cap (CP2) and telemetry (CP3). `null` is never read as 0 or as any number (protocol section 8.1). The count is also a lower bound for an item whose first recorded job was already past revision 1 (the revisions before it were not observed). A count from `jobs` is advisory: `current_round` returns `source` `jobs`, the gate text states that source and, for the plan stage, that the round may be higher than shown (the Workflow counts published contents), and the cap then fires later than the Workflow's own number would, never earlier.
- **D2. The cap guards the two actions that spend a round.** `<stage>.apply_review` is stopped when the round is **at or above** the cap (the reviewer already returned `REVISE` on round `cap`, and applying it would open round `cap + 1`). `<stage>.review.local` is stopped when the round is **above** the cap (a content past the cap that nobody approved the loop to continue into). Stages are `plan` (`plan.review.local`, `plan.apply_review`) and `implementation` (`implementation.review.local`, `implementation.apply_review`). **Functional-fix republications count toward the implementation round.** The Workflow's `review_round.implementation` is `implementation_revision` (protocol section 5.4), which `record_bundle_generation` increments on every ordinary bundle generation, including each bounded functional-fix republication, so an item approved at revision 3 that then takes two functional fixes reaches `implementation.review.local` at round 5. The Controller keeps that number as the Workflow states it: each republication is a new content a reviewer must read, and one number is the same for the cap and for telemetry. The fallback count follows the same revision (D1 counts rises of `implementation_revision`, whichever action published them), so the two sources agree in an ordinary lifecycle, and a `same_content` republication that leaves the revision unchanged is a round in neither. The owner who finds the cap early after functional fixes raises it for that command (D4). Authoring, implementing, self-review, the manual-record actions and the Controller's own external-review courier are never stopped by the cap: a new content only arises through an apply, so an external review of content already in review is not a new round.
- **D3. The stop is a gate, decided after the decision that stands.** `job._review_cap_gate` runs after the currency check and the loop guard in `_decide_protocol_current`, and in `explain` beside `_no_progress_gate`, so `explain` and a step show the same stop. It returns `protocol_decision.gate_for(…, "review_round_cap_reached", text)`: no worker is launched, nothing is written to the Workflow's state, and the exit status is that of any gate. Like every gate that is not couriered, a step records it through `_no_launch_record` as one `GATE_BLOCKED` job record; that record is not `FINISHED`, so D1's count, the loop guard and `telemetry` (it has no worker) never count it.
- **D4. Continuing is a visible, owner-made act.** The cap is the setting `review.round_cap` (integer 1-100, default 4, settings generation 7) with the flag `--review-round-cap N` on `run` and `step`, which wins for that command. Raising it is the "continue" option; there is no "off" value, an owner who wants a long loop sets 100. The cap applies to one command: the next plain `run` stops again at the next capped action of the same item, and the gate text says so. The gate text lists, in this order: raise the cap and re-run; accept at the cap with `/approve-review` and its confirmation guard where the Workflow's gate is reachable (`USER_OVERRIDE` after a `REVISE`); withdraw and re-scope with `/milestone-plan <id>`. The Controller runs none of them.
- **D5. The Controller stops at the cap on any `REVISE`, not only when minor findings remain.** The roadmap asks to stop "at the cap with only minor findings left". After W8 a `REVISE` must name at least one Blocking or Important finding and a verdict of minor findings alone is an `APPROVE`, so no `REVISE` with only minor findings exists, and the Controller does not read verdicts. This is a deviation from the roadmap's wording, flagged for the owner (Risks).
- **D6. Legacy targets are not capped.** The legacy (non-protocol) decision path reads no snapshot and Workflow 2.5.1 and 2.6.0 targets are being retired; the cap applies to protocol targets only, which the docs state.
- **D7. Rounds and usage are derived from the job records, with no schema change.** A job record already stores the whole `next-action` decision (`protocol.decision`) and its action id. `telemetry` derives per job: `action` (the protocol action id, the record's stored real id `plan.review.external` / `implementation.review.external` for a Controller review job, `none` for a legacy job), `stage` (`plan`, `implementation`, `functional`, `none`) and `round` (the stored `review_round[stage]` when an integer, else D1's count over the **full, unfiltered, oldest-first record list** of the same repository and work item that precede the job, computed before `--work-item`, `--run`, `--since` and `--repo` filter the rows, so a job's round is the same with and without `--since`) and `round_source` (`workflow` or `jobs`, D1). **Before and after are not the same measure for the plan stage:** a job recorded before this release has no `review_round`, so its plan round is the fallback's lower bound, while a job recorded after it carries the Workflow's content count. The `stage,round` grouping therefore keeps the two apart: a derived round is labelled with a `~` suffix (`plan/4~`) and never merged into the Workflow's `plan/4` row, the JSON rows carry `round_source`, and `docs/guide/runtime.md` states that a `~` plan round is a lower bound, so the owner does not read a before and after difference as a change of the loop alone. **One rule for both stages:** every round with `round_source` `jobs` carries the `~` suffix (`plan/4~`, `implementation/3~`), every round with `round_source` `workflow` carries none, and the label depends on nothing but that source, which `review_rounds` already returns, so no exception and no extra output exist. The implementation stage's derived round usually equals the Workflow's, but the mixed label stays honest and the owner never has to remember an exception. A past job's derived round applies D1's count over the records before it, **ending with the job's own `pre_state`** (its decision-time snapshot) as the last observation, so a review job that follows an apply is not one round low. Because it is derived, the same query reads the jobs from before this release, which is the "before". Groupings added to `--by` (the `~` label is described above): `action`, `stage`, `stage,round`, `work_item,action`. Nothing is added to a job record.

## Risks

- **The roadmap's "only minor findings left" cannot be tested.** W8 makes a `REVISE` name a Blocking or Important finding, so D5 stops on any `REVISE` at the cap. The owner should confirm that reading; the alternative (reading the verdict) would put verdict parsing in the Controller and is not proposed.
- **Count versus the Workflow's number.** The two can differ for an item whose applies were done by hand or that predates Workflow 2.7.0 (protocol section 5.4). D1 prefers the Workflow's integer and names its source; a hard cap on such an item is advisory, as the protocol says. For the plan stage the divergence is structural, not only historical (D1): the fallback undercounts whenever a plan round publishes content without a `plan_revision` rise, so the cap on a Workflow older than 2.12.0 fires late, and D7's before column is a labelled lower bound.
- **A cap of 4 is the owner's proposal, not measured.** Plans took 11 to 16 rounds. The default is a setting and `--review-round-cap` is the per-command escape; the before and after table (D7) is how the owner judges it.
- **The gate has no exit code of its own.** It uses the existing gate status; the problems page names the reason code. A distinct code is not added in a minor release without a use for it.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10). The declaration is the previous milestone's reviewed classification with this item's ids; every path the checkpoints name is classified at both stages, and `docs/ROADMAP.md` and `docs/ACTIVE_MILESTONE.md` are excluded by exact path at both stages.
