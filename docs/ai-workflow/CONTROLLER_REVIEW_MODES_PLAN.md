## Goal

Today the two external review gates (`plan.review.external`, `implementation.review.external`, rows 14 and 28) stop and wait for a person, unless the owner set `reviewer.harness` to `codex`. A user with one provider is blocked at every milestone: there is no distinct provider to ask.

After this milestone the owner picks how the external review runs with the setting `review.mode` (and `--review-mode` for one command):

| Mode | The external review |
|---|---|
| `auto` (default) | the cross-model reviewer when the owner turned it on (`reviewer.harness` set); else a same-provider reviewer where the Workflow reports a lowered `distinct_reviewer_models` policy; else the gate stops, exactly as today |
| `cross-model` | the cross-model reviewer; a stop that says why when `reviewer.harness` is unset or names the workers' own provider |
| `single-provider` | a fresh Claude session as the reviewer, at a stronger model, on C7's review seam; its approvals are labelled lowered; it runs only while the Workflow's policy signal names the stage's `require` as lowered, else it is refused before launch (D3) |
| `manual` | the gate waits for a person, whatever else is configured |

Two independent review stages stay mandatory in every mode. A repository that sets nothing behaves byte for byte as it does today (`auto` with no `reviewer.harness` and no lowered policy is the gate). One difference is intended and named in the release note: a repository whose newest gate adoption lowered the stage's `require` now gets a paid same-provider review from `auto` where 1.12.0 stopped at the gate (D3).

## Decisions

Each decision states one principle.

- **D1. The mode picks the reviewer; the Workflow still decides admissibility.** `review.mode` is a closed choice (`auto`, `cross-model`, `single-provider`, `manual`, default `auto`), a settings row at table generation 8 with `--review-mode` on `step` and `run`, the flag winning for one command. The Controller's choice happens only at an `external_gate` of row 14 or 28, after the Workflow's own answer (`job._review_gate`); no other action changes. The Controller never decides whether a verdict is acceptable: `record-external-result` runs every guard, `distinct_reviewer_models` included (protocol 8.2, unchanged). Which `reviewer.*` rows each harness reads: `codex` reads `reviewer.harness`, `reviewer.model`, `reviewer.effort`, `reviewer.binary` and the timeouts as today; `claude` reads only `reviewer.same_provider_model`, `reviewer.same_provider_effort` and the shared timeouts, never the Codex rows.
- **D2. `auto` is opt-in, never inferred from a login.** Cross-model in `auto` means `reviewer.harness` is set. A distinct provider that is merely installed or logged in is never used. `auto` counts as cross-model only when the family of `reviewer.harness` differs from the workers' family (`anthropic`); a `reviewer.harness` that names a same-family harness (`claude`) is treated in `auto` as unset for the cross-model branch, so a Claude review runs there only through the lowered-policy branch of D3, with its condition and its `review.lowered` label. `reviewer.harness` never selects the same-provider reviewer by itself. With `reviewer.harness` unset and no lowered policy, `auto` is the gate, so nothing changes for an existing setup.
- **D3. Same-provider review is admissible only under a lowered policy, and the Controller reads that from the Workflow.** The Workflow adds no marker. The signal is the advisory `gate_policy` check of `verify` (`ORCHESTRATION_PROTOCOL.md` section 5.2, check 8), which is `warn` and names each lowered field of the newest gate-lowering adoption (`plan_approval.require`, `technical_approval.require`). `auto` falls back to `single-provider` only when the signal holds, and the read is an **allow-list**: the check's status is `warn` and the detail names the field of the stage's gate in the lowering clause, and every clause of the detail is one D3 knows to be harmless -- the lowering clause (and the label-disagreement clause that follows it) and the `unreferenced_runs` clause. Any other clause cancels the signal for both stages: the `file_tightened` clause, the `floor` clause, the pending-floor clause, the loosening-ignored clause, an invalid-file or provenance clause, and a clause a later Workflow adds. So does a status of `fail` (an invalid file still carries the lowering clause, `scripts/workflow_gate_policy.py:1120-1121`). The reason is that `effective_policy` can restore `distinct_reviewer_models` under sources that emit none of the two named clauses: `file_loosening_ignored` (a file that tightens one field and loosens another, or a floor holding a tightening with the file reverted to the adopted body, `:986-989`) and `invalid` (`stricter(base, floor)` stays in effect). The lowering clause comes from the adoption commit history and never from the working `GATE_POLICY.json` (`gate_lowering_event`), so an unadopted file that tightens a field leaves it in place; D3 therefore fails closed: a cancelled signal holds for both stages, because the Workflow may have restored `distinct_reviewer_models` and the clause does not say for which field (a file that turns the gate human is such a tightening). This signal exists only while that adoption is the newest, so a later adoption that lowers nothing returns `auto` to the gate: fail-closed, never wrong. An explicit `single-provider` needs the same signal: `distinct_reviewer_models` is enforced only on an `APPROVE` (`assert_ingest_reviewer_model_admissible` returns at once for a `REVISE` or `BLOCK`), so an unchecked `single-provider` would pay for every `REVISE` round and be refused only at the final `APPROVE`. Without the signal naming the stage's field, `single-provider` is refused before launch with `review_mode_unavailable` (D6), naming the three `GATE_POLICY.md` paths. The signal is read from text and can be stale (a tightening the Workflow has not yet observed, so no clause outside the allow-list shows yet); that costs at most one review before the Workflow's refusal at `APPROVE` is caught by D6, and D3 says so rather than claiming the read is exact. CP1 starts by capturing real `verify` answers in a scratch repository: one for a lowering adoption alone, one for a lowering adoption plus an unadopted `GATE_POLICY.json` that turns the stage's gate human (it must show both the lowering clause and `file_tightened`), one for a lowering adoption plus a floor holding a tightening with the file reverted to the adopted body (the `file_loosening_ignored` source), and one for a lowering adoption plus an invalid file (status `fail`); if the check's detail cannot be read reliably, neither the `auto` fallback nor `single-provider` ships (both would run unchecked), the plan is amended before CP2, and `cross-model` and `manual` ship alone.
- **D4. `cross-model` is refused without a distinct provider, with a reason.** It needs `reviewer.harness` set to a registered harness whose verdict family differs from the family of the Controller's workers (`anthropic`, Claude being the only worker harness). With none, or with `reviewer.harness = "claude"` (a same-family harness), the step stops with the gate `review_mode_unavailable`, naming the mode, the missing piece and the two settings that fix it. No worker or reviewer is started and one `GATE_BLOCKED` record is written.
- **D5. A same-provider reviewer is a fresh, stronger Claude session on the existing seam.** A second `ReviewHarness`, `claude` (verdict family `anthropic`), registered beside `codex`: a new session with no resume and no inherited conversation, a disposable copy of the worktree (the existing `build_copy`, never `.git`), read-only tools, no MCP, no hooks, no user configuration and no project-level configuration (the copy's `.claude/` -- `settings*.json` with hooks and permissions, `commands/`, `agents/`, `skills/` -- and `.mcp.json` are removed by a per-harness strip list, `CLAUDE.md` is kept as ordinary repository content the reviewer may read but which the harness's settings-source control keeps from acting as instructions beyond the review prompt, if the pre-step shows that control exists, else it is stripped too), and the credential handled as Codex's is (copied in, copied back and checked). Its model is `reviewer.same_provider_model` (default a stronger model than the worker route's default) and its effort `reviewer.same_provider_effort` (default `high`). The verdict's `Reviewer model:` line is `anthropic/<model>` (`expected_headers` takes the harness's family instead of the fixed `openai/`). Each of these controls is pinned in the D9 captures and in a CP2 test, as C7 did for Codex control (e). The boundary is taken from a real operator pre-step on the installed Claude Code (D9), never from documentation.
- **D6. A refusal for the distinct-model rule is final for that state and that policy, and each way out is named.** Two refusals share one stop: the pre-launch refusal of D3/D4 and a `DistinctReviewerModelsRequiredError` from `record-external-result` (a stale signal). The latter ends the job `INCOMPLETE`. The next step stops at the gate `review_mode_unavailable` without launching (the Controller reads its own last review job) while the state identity and the effective gate-policy signal equal those recorded **and** this step's `choose` again selects a same-family reviewer. The stop never overrides `choose`: a step whose `choose` selects the gate (`manual`, or `auto` with neither a signal nor a cross-model `reviewer.harness`) or a distinct-family harness (`reviewer.harness = "codex"` under `auto`, or `--review-mode cross-model`) goes ahead, at an unchanged state identity and signal, because only a pre-launch refusal is safe to repeat and `choose` runs on every step. The signal key is the `gate_policy` check's status plus the allow-listed parts D3 reads (the lowering clause for the stage's field and the label-disagreement clause) plus a flag "some other clause present", from the same `verify` answer, not the whole detail, so an unrelated `unreferenced_runs` warning does not release the stop; a change to the key ends it. The message names each path with what the Controller does after it, filtered by the mode and by the signal as well as by the phase: (1) lower the stage's `require` by adopting a policy: the signal changes, `auto` and `single-provider` run the next step; (2) turn the stage's gate human (an uncommitted `GATE_POLICY.json` edit that writes no state): the file adds a `file_tightened` clause, which by D3 sets the "other clause present" flag and cancels the signal, so the signal changes and the stop is released for `auto` and `manual`, whose next step reaches the gate. Path 2 does not release an explicit `single-provider`: its next step evaluates D3 again, finds the signal cancelled and refuses with `review_mode_unavailable`. D3's strictness is a choice of this plan, not a Workflow rule (a human gate admits a same-provider `APPROVE`), kept because the smaller change is to say so. So when the mode is `single-provider` the message leaves path 2 out and names `--review-mode manual` (or `review.mode`) instead; a distinct provider is named too (`reviewer.harness`, or `--review-mode cross-model`), since those also act at once (see the rule above); (3) record a verdict from a distinct model by hand (`record-external-result`, or `--review-mode manual`): the next step sees the new state; or turn on a distinct provider (`reviewer.harness`, or `--review-mode cross-model`), which runs that review. Path 1 stales an open bundle (`GATE_POLICY.md`) and rows 14 and 28 are always open review phases, so there it takes effect only after the bundle is withdrawn and generated again; the message says that rather than "does not apply", and names paths 2 (for `auto`) and 3 as the ones that act at once. A change to a keyed part may cost one more review before the next refusal. No review is paid for twice.
- **D7. A lowered approval is labelled everywhere it is shown.** The review job record gains `review.mode`, `review.mode_source` (cli, file, default) and, for a same-provider review, `review.lowered: true`. `explain` and `telemetry` show the mode and the label; the Workflow's own `gate_lowering` report is unchanged and not restated. The ledger reference follows the harness that ran (`<harness.name>:<job id>`, not a fixed `codex:`), so a Claude review is never recorded as a Codex one. Records written before this milestone have none of these keys and read as cross-model everywhere, `telemetry --by review_mode` included (bucketed `cross-model`, never `null`).
- **D8. Usage is counted for the provider that ran.** The same-provider review is admitted against the **Claude** budget (`usage.*`, not `usage.codex_*`), counted as a review job, and its end figures come from the job's own session. The round cap (C13) and the loop guard apply to it as to any review loop; no new severity or round rule.
- **D9. The pre-step comes first.** CP2 opens with an operator pre-step in the style of C7's D12: real `claude -p` runs on the installed version under a scratch home, capturing the invocation, the configuration layers, the tools offered, the credential file, the session files and the usage figure. The captures are stored under `tests/harness_contract/claude/` and pinned by a test; a Claude upgrade that changes one fails closed, naming it. The harness is not registered until the captures exist.
- **D10. Out of scope** (unchanged from the roadmap): the automated functional review (C10), and lowering a gate policy on the owner's behalf. The Controller never edits `GATE_POLICY.json` and never runs `/adopt-gate-policy`.

## Risks

- **The lowered-policy signal is partial (D3).** It exists only while the lowering adoption is the newest, and the check's detail is text. The fall-back is safe: without a readable signal `auto` returns to the gate and an explicit `single-provider` is refused before launch (D3), so neither runs unchecked. A structured `requires_distinct` field in a later Workflow release is the real fix; it is filed as a Workflow issue at acceptance, not waited for.
- **The Claude boundary is unmeasured until CP2's pre-step.** If the installed Claude Code cannot be made read-only and tool-limited with a fresh session, CP2 stops and the plan is amended before CP3; `manual`, `cross-model` and `auto`'s cross-model and gate branches (CP1) would still ship; `auto`'s lowered-policy branch and `single-provider` run the Claude harness and would not.
- **"Stronger model" is a default, not a guarantee.** The defaults are settings; a worker route and a reviewer on the same model still give an independent session, which is the requirement.
- **A same-provider review spends the Claude budget.** It is counted (D8) and the round cap applies; the owner sees the cost in `telemetry --by review_mode`.
- **No `docs/TECHNICAL_DECISIONS.md` "Open decision" row is touched** (the file does not exist in this repository); the roadmap's C14 decisions of 2026-10-16 are the owner's and are followed, not re-decided.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10). The declaration is the previous milestone's reviewed classification with this item's ids and wording; every path the checkpoints name is classified at both stages, and `docs/ROADMAP.md` and `docs/ACTIVE_MILESTONE.md` are excluded by exact path at both stages.
