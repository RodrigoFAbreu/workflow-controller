## Goal

`workflow-controller verify-claude` (1.19.0) refuses every Claude Code build from 2.1.304 on with `boundary: writable: REFUSED` ([#129](https://github.com/RodrigoFAbreu/workflow-controller/issues/129)). The tester's settings deny writes on the whole clone (`denyWrite` on the clone root and its `.git`) and allow writes on derived locations *below* it: the output folder is outside the clone, but the repository's own ignored directories (`build/`, `.venv/`, derived from the root `.gitignore`) are `<clone>/build`, `<clone>/.venv`. Claude Code 2.1.303 lets the more specific allow win over the deny on its parent. From 2.1.304 the deny on the parent wins, so a build cannot write its `build/` and the live boundary probe fails. The automated functional review is therefore off on every host that has updated past 2.1.303 (this machine runs 2.1.309), and falls back to a person's manual review.

The newer behaviour is stricter, not weaker, so the answer is not to weaken the deny. The fix is a layout in which **no allowed write location lies below a denied path**, with the isolation the tester has today unchanged: every tracked path, every new file, the checklist and `.git` stay unwritable, and the ignored build directories stay writable.

## Decisions

Each decision states one principle.

- **D1. No allowed write location lies below a denied one, and the code says so.** `functional_review.tester_settings` derives the settings and refuses (a `ValueError`-class programming error, never a runtime fallback) a document in which any `allowWrite` entry equals or lies below any `denyWrite` entry. The same invariant is checked on the settings document on disk by `review.check_functional_settings` at every launch, in place of its present rule that a writable root may be "a derived writable location below the clone". The rule holds under both precedences (the old build's "most specific wins" and the new build's "a deny above wins"), so the layout does not depend on which one a build implements.
- **D2. The writable locations move out of the clone; the clone keeps a link to each.** `build_sandbox` creates `<sandbox>/writable/<name>/` for each name `derive_writable_locations` admits and, in the fresh clone, a symlink `<clone>/<name>` to that folder (an absolute target). The allow list names the external folders, never `<clone>/<name>`. The product's paths are unchanged: a flow still writes `build/x` and `.venv/y` relative to the clone, and the write lands outside the denied clone. The deny list stays exactly the clone root and its `.git`, so every refusal the tester has today stays. `build_sandbox` also writes one `/<name>` line (no trailing slash, so a link matches; a `name/` line matches only a directory) per link into the clone's `.git/info/exclude` **before** `_git_dir_state` records `.git`, so `git status --porcelain` is empty in a fresh sandbox clone exactly as it is today with empty directories, and a `cp -a` copy inherits the file. Each link is *per checkout*, not shared: the prompt's copy rule tells the tester that right after `cp -a <clone> <copy>` it replaces each Controller link in the copy with an empty directory (`rm <copy>/<name> && mkdir <copy>/<name> && cp -a <clone>/<name>/. <copy>/<name>/`, the copy being under the writable `TMPDIR`), so a copy holds its own directory for `build/`, `.controller/`, `.ai-review/` and the rest with what the clone's folder held when it was copied, exactly what `cp -a` carried before, and two copies never meet in one folder. This one step edits the copy, so CP1 rewrites the prompt's present sentence "A copy that is edited is a tester fault" to allow it and nothing else. The shared external folder is therefore the clone's alone. `tester_prompt` changes its "Writable locations below the clone root" wording to say that they are links to folders outside the clone, and `SANDBOX_LIMITS` gains one sentence: a tool that deletes and recreates a linked output folder (`shutil.rmtree('build')`, `rm -rf build`) is refused on the link, a sandbox limit (`environment`), not a product `defect`.
- **D3. The post-run walk knows the Controller's own links and nothing else.** `walk_differences` accepts a symlink at `<name>` exactly when `<name>` is a derived writable location and the link's target is that location's external folder. A link that is missing, retargeted, replaced by a directory or file, or any other symlink the manifest does not hold is a difference (a symlink inside a writable folder is not walked: nothing in a writable folder is). The clone's own `.gitignore` still ignores nothing the manifest holds; the link is accounted for by this rule, not by an ignore pattern (a `build/` ignore line matches a directory, not a link). Tampering with the link is also refused in the sandbox (the clone is denied), and the walk is the second layer.
- **D4. The probe proves the link works and cannot be moved, on the real CLI.** `PROBE_EXPECTED` keeps `writable: WROTE`, which now writes through the link, and gains `link: REFUSED` (the probe tries to replace the link: remove it and make a directory of the same name). `verify_build` records a build only when both hold, plus every other line as today; the host-side checks add that the probe file exists in the external folder and that the link is unchanged. The live tests and `verify-claude` run the one shared implementation (`controller/claude_build.py`), so the command and the release check cannot drift. The working-directory test of the previous milestone, which pins why the output folder is the working directory, stays release-side only.
- **D5. The fake tester emulates the stricter precedence.** `tests/fake_functional_tester.py` resolves a path through symlinks (as a sandbox mount does; for an unlink, a rename or a `mkdir` over a link it resolves only the parent and not the last component, as the kernel does, so `clone/build` is not taken for the allowed external folder and the link cannot be removed) and refuses it when any `denyWrite` entry is the path or an ancestor of the resolved path, unless the resolved path lies in an `allowWrite` entry that is not below a deny; a resolved path in no `allowWrite` entry is refused, as the fake's docstring says today, so the emulation is never allow-by-default outside the denied paths. The previous layout then fails in the fake suite as it does on the real builds, which keeps the suite from passing a layout the real CLI refuses. The resolution half of this (the symlink-following path and the parent-only rule) lands in CP1, because CP1's links make an unresolved `<clone>/build/out.o` look denied to the fake and would turn the sandbox suite red; the stricter precedence and the refusal of a path in no `allowWrite` entry land in CP2. The real CLI stays the only judge of enforcement (live tests).
- **D6. No isolation is traded for capability.** If the live measurement of CP3 shows a current build refusing a write through the link into the external folder, the milestone stops there and is amended by a new decision (`/request-plan-amendment`); it does not fall back to a deny that leaves the clone root creatable. The plan states this now because the one thing CP1-CP2 cannot prove is the real CLI's treatment of a write through a symlink.
- **D7. Documentation changes with the behaviour, in place.** `docs/compatibility.md`, `docs/common-problems.md`, `docs/install.md`, `docs/guide/automation.md` and `docs/guide/development.md` say that the layout no longer depends on the build's precedence rule, where the writable locations live, and that Claude Code 2.1.304 and later can be verified; the closing records of `docs/ROADMAP.md` (C10f complete, #129 done) and `docs/ACTIVE_MILESTONE.md` are written by CP4, in the implementation, so the acceptance gate only confirms them.

## Out of scope

The credential-read denial and `file://` origin detection ([#115](https://github.com/RodrigoFAbreu/workflow-controller/issues/115)), probes in CI, the sandbox-start check of `verify-claude` (#132), and the Codex tester (C10g, [#131](https://github.com/RodrigoFAbreu/workflow-controller/issues/131)).
