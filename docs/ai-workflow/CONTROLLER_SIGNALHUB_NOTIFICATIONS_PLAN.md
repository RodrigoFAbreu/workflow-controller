## Goal

Once runs are unattended the operator must learn what is happening, and when something is blocked, without watching a terminal. Today the lanes do it by hand: `~/.local/share/claude-lanes/notify.py` is called by the orchestrator sessions, reads `~/.config/signalhub/events.json`, and sends to SignalHub (`POST <url>/api/v1/events`, `Authorization: Bearer <key>`, optional `Idempotency-Key`). After this milestone the Controller is itself a SignalHub producer:

1. **It derives events from what it already records.** Run-log lines, job records, the branch-binding events a step's preflight writes, and the lines of `usage-events.jsonl` map to a closed table of notification event types (D2).
2. **Each event is configurable per event type** in the settings file (the user's requirement of 2026-09-30): on or off, category, severity, with a per-kind layer under it. The defaults are the mapping the lanes use by hand today (D3).
3. **Delivery never steers the lifecycle.** Sending is asynchronous, bounded, retried a bounded number of times, recorded, and can never block, fail, delay or change a step (D5, D6).
4. **A retry or a `resume` never notifies twice**, because each event carries an `Idempotency-Key` derived from its run, job or event identity (D4).
5. **Standard library only**; the API key comes from the environment or a file, never from the repository or the settings file (D7).

Out of scope: any change to SignalHub; the lanes' own scripts and `events.json` (they stop sending the events the Controller now sends, as a coordination step after release, D9); a persistent outbox that survives the process (D6 names why); notifications for the Manager or Workflow repositories; C7, C8b, C8c.

## Decisions

- **D1. One new leaf module, `controller/notify.py`, placed after `routing` and before `settings` in `DEPENDENCY_ORDER`.** It imports `runtime`, `errors` and the standard library, never `settings` (which imports it, to validate the `notifications.events` row and its defaults), `usage`, `job`, `observe` or `cli`; the effective values arrive as parameters. `usage.py` (which writes the usage events) and `job.py` (which owns `RunRecord`) call it; `milestone_branch.py` (early in the order) cannot, so the step passes it the preflight's event names (D2). Every path, clock and transport is a parameter, so no test touches the real home, the network or the real SignalHub. A process-wide *installed* notifier (set once in `cli.main` beside `settings.apply_process_defaults`) lets deep callers emit without threading an argument through twenty signatures; with none installed (every test that does not install one) `emit` is a no-op.
- **D2. The closed event table.** Each Controller event type has a kind (`state`, `info`, `gate`, `blocker`), a source and a derivation. The names reuse the lanes' own where one exists, so `events.json` entries port unchanged.

  | `usage_paused`, `usage_resumed` | state | the `usage-events.jsonl` line of that name (D8) |

  The branch gates are classified **exhaustively**: `checks_failing`, `checks_cancelled`, `release_failed`, `merge_method_rewrote_history`, `pr_closed_unmerged`, `merged_before_acceptance`, `post_acceptance_commits`, `unmerged_commits`, `integration_required`, `pr_title_invalid`, `release_notes_invalid`, `dirty_tree`, `bound_item_missing`, `switch_to_trunk`, `fast_forward_trunk` are blockers; `merge_pull_request` and `merge_held` are user gates; `checks_pending`, `merge_pending`, `release_pending` and `pr_head_not_accepted` (the transient "GitHub does not show the pushed head yet", `milestone_branch.py:1025`, `waitable=True`; O1 of round 11) are waits **only when the outcome is `waitable`**, and notify only when a run that **waited** (`merge.wait_seconds` > 0) ends on one when the wait is spent (a stuck release or merge), as `lane_blocked`. Under `merge.wait_seconds` 0 (`settings.py:125`), `waiting_preflight` returns the first gate without waiting (`milestone_branch.py:2773`), so an ordinary `checks_pending` step sends **nothing**: a wait gate is a normal end there, not a stall (O1). **Preflight events and the exits that forward them.** A step's preflight writes its events before the outcome is known, and they reach the end of a step on paths that write no job: a usage hold (`job.UsageHold.preflight_events`, `cli._usage_paused`), `_refuse_changed_release` (`preflight_events` in its error evidence, `job.py:2006`), and a branch gate that ends the step. The step therefore derives `pr_merged` **when the preflight leaves `waiting_preflight`, by return or by raise** (`job.py:5680-5693`), from the preflight's events and the binding record, and hands the derived events to `notify`; it does not wait for the job record that those exits never write. Two exits leave by raising after a `merged`/`merged_squashed` event is already written (F1): `WaitInterrupted` (`milestone_branch.py:2797-2800`; one wait poll writes `merged_squashed`, lines 1251-1253, and a Ctrl-C during the next `release_pending` sleep raises), and a `BranchBindingError` from `_close_trunk_step3` after `_merged_handling` (the `_trunk_merged` refusals, lines 2275-2283 and 2312-2339, exit 20). On the next step the binding is already `MERGED`/`MERGED_SQUASHED`, `_merged_handling` does not run again and nothing would be written, so the derivation runs in a `try/finally` around the `waiting_preflight` call; it reads `preflight_events` and the binding record, only enqueues (never raises, never hides or replaces the original exception) and runs on the raise path too. A contract test drives each exit (job written, usage hold, changed-release refusal, branch gate, `WaitInterrupted`, `_close_trunk_step3` refusal) and shows the merge observed on that step sent exactly once. **A wait code is a wait by the outcome, not by the code alone (F2 of round 10):** `_merge_step` returns `merge_pending` with `waitable=False` when GitHub reports `DIRTY` (`milestone_branch.py:1039-1043`), which needs a person to resolve the conflict and ends the step at once, so no wait ever spends and the wait rule would send no `lane_blocked`; the classification is a function `classify(gate)` in the constant next to `GATE_CODES`, reading `gate.waitable`, and a non-waitable outcome of a wait code is a **blocker** (`lane_blocked`, identity as for the other branch gates in D4). A contract test fails if a member of `milestone_branch.GATE_CODES` is in none of the three classes, so a future gate cannot go silent, and a second one drives the `DIRTY` conflict and shows one `lane_blocked`.
- **D3. Configuration lives in the settings file, in the lanes' shape.** New `notifications.*` rows in `settings.TABLE` (generation 5; `TABLE_GENERATION` 4 → 5): `notifications.enabled` (bool, true), `notifications.url` (optional string, an `http(s)` URL of 1-2048 characters), `notifications.api_key_file` (optional string, a *path* of 1-1024 characters, never the key: F2), `notifications.timeout_seconds` (int 1-60, 5), `notifications.attempts` (int 1-10, 3), `notifications.retry_seconds` (int 1-60, 2) and a mapping row `notifications.events` of the form `{"kinds": {<kind>: {enabled, category, severity}}, "events": {<event type>: {…}}}` (the `routing` precedent: a new `TYPE_NOTIFICATIONS` validated by `notify.validate_events_mapping`). Fields whose name starts with `_` (the lanes' `_help`, `_kind`, `_what` in `events.json`) are ignored silently, so a copied `events.json` object does not warn (O4). Resolution is the lanes': built-in kind default, then the file's kind entry, then the file's event entry, field by field. Categories are `ACTION_REQUIRED`, `BLOCKED`, `COMPLETED`, `INFO`; severities `LOW`, `NORMAL`, `HIGH`, `CRITICAL`. A known field with a bad value is `SettingsError` (exit 20, the file is never rewritten); an unknown event name or field is ignored with the one warning per invocation unknown keys already get. The built-in defaults equal the roadmap's mapping: `state` INFO/LOW, `info` INFO/NORMAL, `gate` ACTION_REQUIRED/HIGH, `blocker` BLOCKED/CRITICAL. `usage_released` and `usage_reservation_expired` default to `enabled: false` (O7). The fill (`settings.fill`) writes the new rows with their defaults like every other row. The Controller does **not** read `~/.config/signalhub/events.json` (D9).
- **D4. Idempotency.** `Idempotency-Key` = `wc-<event type>-<identity>`. SignalHub's contract (`~/Workspace/SignalHub/docs/architecture.md`, "Idempotent publishing") has two rules this design is built on (F1): a key is kept **as long as its event exists**, with no expiry; and reuse of a key answers `200` with no push **only when** the stored fields (`context`, `category`, `severity`, `title`, `message`, `metadata`, `link`, `occurredAt`) are identical, while a *different* body under a used key is `422` and stores nothing. Two requirements follow. **(a) The identity is the occurrence** of the thing notified, never the invocation that observed it, and it must **change when the thing recurs**, because a key is permanent: a recurrence under the old key is a lost notice. **(b) The body is a deterministic function of the identity**: `title`, `message`, `metadata` and `link` carry no `job_id`, `run_id`, clock, wait deadline or other per-invocation value, and `occurredAt` is not sent or, where sent, is taken from the occurrence (the job's, event's or gate's own recorded time), so a re-derived event repeats the stored body byte-for-byte and gets `200`, not `422`. A test builds each event twice from two different invocations and asserts equal bodies. **Repository namespace (F3 of round 10).** D7 lets one Controller key drive several repositories and SignalHub keys are per producer, so an identity that is unique only inside one repository (a release tag, a work item id, a pull request number, a gate's `binding_generation`) would collide across repositories, while D12 gives the two bodies different contexts: a `422` and a lost notice. Every key is therefore `wc-<event type>-<repository>-<identity>`, `<repository>` being the repository directory name as D12 sanitises it (the same value the body's `context` and `metadata.repository` carry, so the key and the body differ together); a test builds `release_published` for `v1.9.0` in two repositories and gets two keys. The directory name is not a repository identity (O3 of round 14): two checkouts with the same directory name, or names that sanitise identically (`my repo`, `my_repo`), share keys and contexts. That is a named limitation of the namespace, stated in the ADR; the bodies of two such repositories' events are only affected when their identities also coincide, and no wider repository identity (a path hash) is added because it would make keys and contexts differ between checkouts of one repository. Identities: `step_done`, `milestone_planned`, `approval_recorded`: the `job_id` (a job is one occurrence; one rule for the `milestone_*` family: `milestone_planned` is per job because it recurs on every plan revision, `milestone_started` and `milestone_accepted` are per work item, O2 of round 10). `user_gate`/`lane_blocked` from a lifecycle gate: work item + phase + `state_revision` + gate code, hashed (a `step` that meets the same unchanged gate again mints a new `job_id` in `_no_launch_record` but the same key and the same body; a changed gate or state sends a new notice). **A branch gate** (F1 of rounds 3 and 4; F3 of round 14): **work item** + `binding_generation` + gate code + an **occurrence component** that changes on **each gate's own named retry exit**, chosen per gate and kept in the classification constant next to `GATE_CODES` (`milestone_branch.py:160-166`):
  - `release_failed`: the `at` of this binding generation's latest `release_failed` binding event (F1 of round 5). `_release_failed_shown` (`milestone_branch.py:1547-1561`) writes that event exactly once per distinct detail, and compares only with the **last** detail, so an A → B → A sequence writes three events. Several `release_failed` outcomes have **no failed runs** (the classification failures `f"{found.state}: {found.detail}"` at `1504`/`1506-1507`, `classifying {m} refused: …` at `1593`, and the published-nothing outcome at `1469-1471`/`1543-1544`), so a key built from the failed runs alone would be constant across them while their details, and so their messages, differ: a `422` recorded as `duplicate` and a lost CRITICAL notice. The event's `at` changes for every distinct detail, is stable while an unchanged gate is seen on several `step`s (no event is written), and the body, which carries the detail, is then a function of the key. A GitHub re-run of the failed jobs keeps the run id and URL and raises only `attempt`, and `_runs_text` (`milestone_branch.py:1426-1428`) prints no `attempt`, so the detail was byte-identical and the event suppressed. CP3 adds `attempt` to `_runs_text` (a small `milestone_branch` change, in CP3): a new attempt is then a distinct detail, a new event and a new key. The one component covers the re-run, the no-runs failures and A → B → A. The `at` has second resolution (`ctx.clock()`, `%Y-%m-%dT%H:%M:%SZ`): in production two distinct details in one second need two `step`s within one second (`merge.wait_seconds` polls are at least 10 s apart, `settings.py:126`), which cannot happen; the CP1/CP3 tests that write several `release_failed` events (the A → B → A case) **advance the injected clock for each event**, so they do not share a key by construction (O1 of round 6).
  - `checks_failing` and `checks_cancelled`: `pr_checks` exposes only `name`, `state`, `bucket` (`forge.py:45`, `CHECK_FIELDS`), no run or attempt id, and a re-run changes neither the head nor any binding event (`_checks_gate` writes nothing). So these use a **streak occurrence**: a counter stored in the `last_observation` record as an additive field `gate: {code, streak}` (no new event). That field is **not computed** by the existing per-step write in `_observe_branch` (`milestone_branch.py:803-806`), which runs before any gate is known; it has its own record write where `repository_preflight` returns its outcome, including the Proceed outcome (counted as "no gate") and each poll of `waiting_preflight` (O1 of round 5). **The write lives in `milestone_branch` (F1 of round 7):** `repository_preflight` and `waiting_preflight` are both in that module (`2726`, `2754`), `job.py` sees only `waiting_preflight`'s final outcome (`job.py:5684-5685`; the polls at `2772-2794` are internal, and `on_wait` fires once per waitable code, before the first sleep, so it sees neither a Proceed nor a later poll), and a record write needs `_write` and the key `preflight` resolves. CP3 adds a small helper there, called by `repository_preflight` on each outcome. It writes with `_write` and **no event name**, so the binding's latest-event `at` (a key component for the other branch gates) does not move on every step, and it writes nothing when there is no bound, non-terminal record (`found.inactive`, terminal and close-out states), **and nothing while the record's `last_observation` is `None`** (F1 of round 8): both new-binding paths (`milestone_branch.py:2456`, `2565`) leave it `None` until the first `_observe_branch`, so `dict(None, …)` would raise `TypeError` on the first step of every milestone that binds a branch, and the `record.get("last_observation") or {}` form of `_push` (line 813) would store `{"gate": …}`, which `_binding_view` (`2833`, `record.get("last_observation") or None`) treats as an observation and prints as `behind (None behind the trunk), observed None` instead of `not observed yet` (`cli.py:967-970`). Skipping loses nothing: a new binding is a new `binding_generation` (already a key component), and the checks gates exist only in `PR_OPEN`/`READY`, after `_branch_cells` has observed. Once an observation exists the write builds on it with `dict(record["last_observation"], gate=…)` (as `_push` does at line 821, where `814` has just written a dict). **`_observe_branch` must carry the field across its rewrite (F1 of round 6, choice (a)):** it builds a **new** `observation` dict on every preflight of a bound, non-terminal item (`observation = {} if push is None else {"push": push}`, then `update(...)`) and writes it whole, so without a change the stored `gate` is erased before every gate is computed, the streak restarts from nothing and never advances, and a checks re-run on the same head reuses its key. CP3 therefore adds one line to `_observe_branch`: the previous `last_observation.get("gate")`, when present, is copied into the new observation. The new-binding paths (`milestone_branch.py:2456`, `2565`) set `last_observation` to `None`, which is correct: a new `binding_generation` is part of the key. The field is additive, so `_binding_view` (`2831-2846`, a fixed key list) keeps it out of `status`. Every branch-gate observation, including `checks_pending`, compares its code with the stored `gate.code`; a different code (or no gate) increments `streak`, an equal code leaves it. The key component is the `streak` at the observation. `checks_failing` is not waitable (`waitable` is only the pending flag, `milestone_branch.py:1037`; the wait loop runs only while `outcome.waitable`, `2773`), so one wait cannot contain the whole failing → pending → failing sequence: step N ends on `checks_failing`, and step N+1 sees `checks_pending` while it waits and ends on `checks_failing`. So a flaky check that fails, is re-run (the next observation sees `checks_pending`, in the next `step`'s wait) and fails again on the same head is two keys; the same unchanged `checks_failing` seen on two `step`s with no observation between is one. A re-run that finishes failing before any observation intervenes is indistinguishable from the first failure and sends one notice (a stated limit, not a defect: nothing recorded tells them apart).
  - Every other branch gate: the pull request's head SHA (`head_oid`, read from the binding record's `pr` field, `milestone_branch.py:899-900`, the value the record holds, refreshed only at some transitions, `734`, `939`, `1713`, `1741`, `2043`) and the `at` of the binding record's latest event (`milestone_branch.py:420`, written with each binding event, so a push moves it between refreshes (O2 of round 4)), and for a gate with neither (`dirty_tree`, `switch_to_trunk`), the work item's `state_revision`; **and, for each of these gates, the stored `gate.streak` (F5 of round 10)**. A person can convert the pull request to a draft after it was marked ready (`merge_held`), mark it ready (`checks_failing`) and convert it back (`merge_held`, `milestone_branch.py:1024-1037`) without a push and without a binding event, so the head and the event `at` are unchanged and the second `merge_held` would reuse the first's key and be suppressed, a lost human gate. The streak helper above already increments on every observation whose code differs from the stored one (or that is no gate), adds no binding event, and so separates the recurrence; the component is `0` where no `gate` field is stored (a gate met before the first observation, such as `dirty_tree`, `switch_to_trunk`, `bound_item_missing`, which keep `state_revision`). A recurrence with no observation between its two occurrences is indistinguishable from the first and sends one notice (the same stated limit as for the checks gates).
  **The work item is part of every branch-gate key (F3 of round 14).** `binding_generation` is counted per work item (`milestone_branch.py:2454`, `2564`), and `streak` and a PR head or event `at` can coincide across two work items in one repository, so two ordinary milestones can both reach generation 1, `checks_failing` and streak 1 under one repository and producer; without the work item their keys would coincide with different bodies (SignalHub `422`, a lost blocker). The lifecycle-gate and `lane_blocked` identities already carry the work item; this makes the branch-gate identities do the same (usage identities carry no work item: they name provider, window, repository and run or occurrence, so they need no such component). A test builds `checks_failing` (and `merge_held`) for two work items with equal generation, code and streak and gets two keys.
  So `checks_failing` on head A, a pushed fix, `checks_failing` on head B are two keys; `release_failed`, a GitHub re-run of the failed jobs of the same run id that fails again (`attempt` 2), `release_failed` are two keys; `checks_failing`, a checks re-run, `checks_failing` on the same head are two keys; the same unchanged gate seen on two `step`s is one. A `FAILED`/`INCOMPLETE` job: the `job_id`. `run_finished`: the `run_id`. `pr_merged`: work item and pull request number; for the PR-less close-out, work item and `binding_generation` (O4). A fail-closed refusal (exit 20) writes no job record, so `lane_blocked` takes an occurrence identity from the SHA-256 of the error class plus its stable evidence (work item id, branch, binding state, `binding_generation` where present, the work item's `state_revision`), never the invocation (F2 of round 2). `milestone_started`/`milestone_accepted`: the work item id (the second rule above is the only one, there is no job identity for them). `release_published`: the release tag, else work item + `binding_generation` (O1 of round 1). **Usage events** (F2): the SHA-256 of `event|at|provider|token|run_id|repository` (the line's own fields), except `usage_paused`, which is written on every pass of `usage --wait` (`cli.py:1557`) with a new `at` and a `reason` that is free text holding live percentages (`usage.py:872-874`, `Hold.reason`), so neither may enter its key or body. `usage_paused` is keyed on the **stable `window`** field (`five_hour`, `weekly`, `run_cap`, `repository_cap`): a timed hold on `provider|window|repository|resume_at` (the pause is account-wide, but the notice names a repository, D12, so each repository paused by the same window sends its own, F3 of round 10), where `resume_at` is the **first** `resume_at` of the run of holds whose readings lie within `WINDOW_JITTER_SECONDS` of each other (`usage.py:54-56`, `merge_reading` keeps the larger `resets_at` of two such readings, so it can drift by a second or two inside one window). **The chain's first value is carried forward in the line itself (F4 of round 14).** `usage.append_event`, just before it writes a `usage_paused` line, reads the tail of `usage-events.jsonl` (at most the 50 most recent lines; a bounded local read, no network) for the **most recent** earlier `usage_paused` line of the same provider, window and repository; when that line's value lies within the jitter of this line's, this line copies that line's `occurrence` field, otherwise it records its own value. The line therefore carries an additive `occurrence` field (the chain's first `resume_at`, or for a cap hold the value defined below) and the key uses it. Only the **immediately preceding** matching line is ever needed, so a chain that creeps for hours keeps one key past the 50-line boundary (the first line need not stay in the scan). The one residual: when more than 50 lines of other repositories' usage events fall between two consecutive pauses of one hold, the earlier line is out of reach and the hold starts a new chain, **one extra notice**; that residual is accepted, named in the ADR and tested (O1 of round 4, O2 of round 5); a cap hold (`run_cap`, `repository_cap`, always `resume_at` `None`, `usage.py:840-856`) on `provider|window|repository|run_id` for `run_cap` (a run's spend only grows, so a `run_cap` pause recurs only in another run) and, for `repository_cap`, on `provider|window|repository|<reset window>` (F4 of round 10): the five-hour window the cap is measured in resets and work resumes, and the same repository can hit its cap again, so a key on the repository alone would silence the second pause for ever. `Hold.resets_at` (`usage.py:850-854`) holds that window's identity when a five-hour reading exists; `_usage_event_fields` (`cli.py:1212`) does not record it, and CP3 adds it as the additive field `window_resets_at`. **With no five-hour reading the repository still has an accounting window (F2 of round 14):** `_charge_repository` places a charge it cannot place in the window `now + WINDOW_SECONDS[FIVE_HOUR]` (`usage.py:617-640`) and `repository_spent` stops counting it once that reset has passed (`752-759`), while `evaluate` returns `Hold.resets_at=None` (`854`). CP3 therefore makes the cap `Hold` carry the repository spend window's `window_resets_at` (read from `record["spend"]["repository"][provider][repository]` where `repository_spent` already reads it) when the reading is absent, so `window_resets_at` is the five-hour reading's reset, else the accounting window's reset. That identity advances on the real path the review traced: a cap is non-waitable, ends the invocation (`cli.py:1308-1323`), and work resumes only after the accounting window has rolled, so the next cap hold carries a later accounting window. The `occurrence` of a cap line is the first value of the chain of its consecutive `usage_paused` lines for this provider and repository whose `window_resets_at` values lie within `WINDOW_JITTER_SECONDS` (the rule above); a later accounting window, which differs by hours, is a new occurrence. A charge that re-places the window on a later charge (`now + 5 h` each time with no reading) can move the identity by more than the jitter inside one hold; that costs **one extra notice** per move, accepted and named in the ADR. When the cap trips on outstanding reservations and the forecast alone (`repository_spent` 0, so no accounting window exists, `window_resets_at` `None`), the line's `occurrence` is the previous matching line's `occurrence` unless a `usage_resumed` line for this provider and repository lies after it in the same scan **or that previous line's `at` is more than `WINDOW_SECONDS[FIVE_HOUR]` before this line's** (F1 of round 15: a non-waitable cap path writes no `usage_resumed`, `cli.py:1319-1323`, `1550-1552`, and the spend window that separated two occurrences lasts at most five hours, so a gap longer than that is a new occurrence), otherwise the line's own `at`. **Named residual (F1 of round 15):** a reservations-only cap pause that follows a matching pause by **less** than five hours with no `usage_resumed` and no spend-window entry between them (workers completed, their spend window rolled, another pair reserved, all inside five hours of the first pause) reuses the first occurrence, and that one notice is **lost**; it is accepted, bounded to one notice per such sequence, named in the ADR and tested, and the promise below is qualified accordingly. **Legacy and unreadable history (F1 of round 15):** an earlier matching `usage_paused` line written before 1.9.0 carries no `occurrence` and no `window_resets_at`; it is read as `occurrence` = its `resume_at` for a timed hold, its `window_resets_at` for a cap hold that has one, else its own `at`. A tail that is missing, unreadable or holds a malformed line is treated as having no earlier matching line (this line records its own value); the read is wrapped so that no error escapes, and `occurrence`/`window_resets_at` are written to the usage-events log only: `evaluate`, the spend record and every admission decision read neither, so notification history can never change a usage decision or interrupt a step (test below). A cap pause on each of two successive accounting windows sends two notices; a reservations-only cap pause on a successive occurrence sends a notice unless it falls under the named residual. Its body states the window and `resume_at` only, never the percentages. One hold is therefore one window and one `resume_at`: when `resume_at` has passed and the next pass reads a new `resets_at`, or a stale reading makes it non-waitable (`resume_at` `None`, `usage.py:868-871`), that is a **new** hold and a new notice is correct. Keys are limited to `[A-Za-z0-9._:-]` (the repository component is sanitised the same way), at most 128 characters (a longer identity is replaced by its SHA-256). The Controller never enqueues a key twice in one process. Outside the process the server de-duplicates an identical body (`200`). A `422` on a key this process derived is classified `conflict` (D5): a different body was discarded and nothing was delivered, which is a lost notice that diagnosis must see, so it is neither `duplicate` nor `rejected` (O3 of round 10). `duplicate` is reserved for the in-process rule above (a key already enqueued in this process is dropped before sending and recorded as such, with `source: "process"`) and for a recovered event's `422` (`source: "server"`, D13); D13 (iii) counts only the second as handled. Periodic reminders of an unchanged gate are not sent; if wanted they are a separate, explicit, configurable choice, out of this milestone.
- **D5. Delivery is off the lifecycle's thread.** `emit()` builds the request body and puts it on a bounded queue (256; a full queue drops the new event and writes one `dropped` line for it, the only per-event line the queue ever writes for an event that never left the process) and returns. One daemon thread sends, one event at a time, with `urllib.request` and `notifications.timeout_seconds` per attempt, up to `notifications.attempts` attempts, waiting `retry_seconds × 2^n` between them. Network errors, timeouts, HTTP 429 and 5xx are retried; `422` is a `conflict` (the key was already used for a different body: nothing is stored, nothing is retried, and it is recorded as `conflict`, neither a rejection nor a `duplicate`, F1, O3 of round 10); any other 4xx is a rejection, recorded and not retried; an unconfigured URL or key makes the whole notifier inert after one recorded `not_configured` line. A circuit breaker stops attempting for 300 s after three events in a row exhaust their attempts (the rest are recorded as skipped). `notify.flush(timeout)` runs as the last act of the run's close (`RunRecord.close` enqueues `run_finished`, flushes, and only then writes `notifications_summary`, so `run_finished` is never enqueued after the last flush and lost with the daemon thread; `_close_open_run` runs in `main`'s `finally`, `cli.py:2304-2307`), and once more in `main`'s `finally`, **after** `_close_open_run`, for an interrupted run (which ends through `RunRecord.interrupt`, not `close`, `job.py:4773-4778`, `cli.py:2307-2308`) and for a command that opens no run; a normally closed `step` therefore flushes twice, and the second is an empty-queue no-op. A flush waits at most `timeout_seconds + 5` s for the queue to drain and writes **no per-event line** for what it did not drain: an undrained event is counted only as `pending` in the `notifications_summary` (so `dropped` has one meaning, a full queue). After `KeyboardInterrupt` or `WaitInterrupted` the flush waits at most **2 s** and a second Ctrl-C abandons it at once (the daemon sender thread cannot keep the interpreter open), so Ctrl-C never costs up to 65 s (O3); the existing Ctrl-C tests are the check. **The two flushes share one deadline (O2 of round 14):** the first flush of a process (in `RunRecord.close` or `main`'s `finally`) fixes a process-wide flush deadline of `timeout_seconds + 5` s from its start, and a later flush in the same process waits only for what remains of it (0 once spent), so the aggregate shutdown wait is at most `timeout_seconds + 5` s, not twice that; a test times a timed-out close flush followed by `main`'s final flush against that bound. **No lifecycle lock, record write or exit code depends on any of it**, and the sender thread never touches `RunRecord`, the state file or a job record.
- **D6. Where outcomes are recorded.** The sender appends one line per event outcome (`sent`, `duplicate`, `conflict`, `rejected`, `failed`, `skipped`, `dropped`, `not_configured`, `disabled`; `dropped` means the queue was full and nothing else, and an event still undrained at a flush timeout has no line) to `runs/<run_id>/notifications.jsonl`, preceded, once **per run**, by a `notifier_active` line that `open_run`/`RunRecord.__init__` writes into `runs/<run_id>/notifications.jsonl` when the run is opened, if the installed notifier is configured with both a URL and a key **and `notifications.enabled` is not `false`** (the master switch off makes the notifier inert exactly like the kill switch: no `notifier_active`, and the one inert line is `disabled`, D10; the install in `cli.main` precedes any run and has no `run_id`, so the line is written at run open, before any job starts, never at install; D13 reads it; an inert notifier writes `not_configured` or `disabled` and no `notifier_active`) (events outside a run: `<runtime root>/notifications.jsonl`; the outcome line of an event **recovered** by `resume`, which opens no run, is appended to the log of the record's own `run_id`, so D13 (iii) reads one place); **every outcome line records the event's Idempotency-Key** (not a secret: it is `wc-<event type>-<identity>`, D4), which is what D13 (iii) matches, best effort, through `runtime.append_jsonl_best_effort`, by the sender thread (the outcome-log append stays off the lifecycle thread. D4's `occurrence` read of the last 50 lines of `usage-events.jsonl` runs in `usage.append_event` before the write, a bounded local read that waits on no network and takes no lock (`append_event` holds none, `usage.py:533-542`; two processes appending at once may both read the tail before either writes and each record its own value, one extra notice, accepted and named in the ADR), and D13's notification-log reads under the lifecycle lock are bounded the same way: at most the 50 most recent terminal records are examined, each by reading one run's `notifications.jsonl` once, so none of them can add an unbounded or network-dependent wait, F-architecture of round 14); `RunRecord.close` adds one `notifications_summary` event (the counts at close, after the final flush, which waits at most the shortened flush time, so an event still in flight is counted `pending`) to the run's own `events.jsonl` from the main thread, which keeps that log single-writer. No line ever holds the **API key**, the `Authorization` header or URL user-info (the Idempotency-Key is recorded, see above). There is **no persistent outbox**: an event that exhausted its attempts is recorded and not replayed by a later process (recovery re-derives an event from the authoritative record, D13; it never replays the spool), because a late "step done" is worse than none, and a blocker that matters is not lost: it is still the gate the run is stopped at, and the next `status`/`explain` shows it. A resumed run that meets the *same* gate sends nothing new (D4: same key and identical body, answered `200` and never pushed twice, and recorded `sent`, not `rejected`); a gate that changes or recurs sends a new notice.
- **D7. Credentials.** URL: `$SIGNALHUB_URL`, else `notifications.url`, else the first line of `<signalhub config dir>/url`. Key, in this precedence: `$SIGNALHUB_API_KEY`, else the first line of the file named by `$SIGNALHUB_API_KEY_FILE`, else the file named by `notifications.api_key_file` (a path, never the key), else `<signalhub config dir>/api-key`, where the **signalhub config dir** is `$SIGNALHUB_CONFIG_DIR` if set, else `~/.config/signalhub` (the override exists so the test suite can redirect it, F3 of round 11). `~/.config/signalhub/` holds `url`, `events.json` and a key **per lane** (`workflow-controller.key`, `workflow-manager.key`, `repflow.key`, `signalhub-orchestrator.key`), and no `api-key`: only the lane's `controller-watchdog.sh` exports a per-lane `SIGNALHUB_API_KEY_FILE` (defaulting to `workflow-controller.key`), so only the runs the watchdog starts inherit it; `start-run.sh` starts the first Controller run **before** it launches the watchdog and exports nothing, so that first step finds no key and records `not_configured` (F3). Every launch path works only when `notifications.api_key_file` names the key once in the settings file, or `start-run.sh` exports the variable (D9). SignalHub identifies a producer by its key; a Controller uses **one** key per process, the one the precedence above resolves, whichever repository it drives. When it drives the Manager's repository from the Controller lane it still sends as the Controller (the `lane`/`context` value names the repository, D12); no per-repository key rule is added. The lanes' kill switch `<signalhub config dir>/disabled` is **honoured**: when it exists the notifier is inert (one recorded `disabled` line), so one switch silences every producer. Absent a URL or key the notifier goes inert after one `not_configured` line that **names** the paths and variables it looked in (never a key), and `notifications` (D10) prints the same. A world- or group-readable key file is used but warned about once. The key is read once per process, held in memory only, and sent as `Authorization: Bearer <key>`. The settings file has no key row, and the repository never holds one.
- **D8. Usage events.** `usage.append_event` is the single choke point for every `usage-events.jsonl` line (the four ADR 0011 events and a few diagnostic ones: `usage_renew_failed`, `usage_accounting_orphan`, `usage_record_unreadable`, `usage_complete_unknown_token`, `usage_complete_already_settled`), so the hook is one call there, after the line is written, and **maps only the D2 table's four names and ignores every other line** (O1: the diagnostic names are not notifications in this milestone): `usage_paused` and `usage_resumed` are therefore sent once whether the run log also got the event or not, and a manually started worker's `usage --wait` pause is covered. The run-log copies of those two events are not subscribed to (they would double-send).
- **D9. The lanes.** After release the lane orchestrators stop hand-sending `step_done`, `usage_*`, `pr_merged`, `release_published`, `milestone_*`, `user_gate` and `lane_blocked` for a Controller-driven repository and keep sending only what no Controller observes (Codex review rounds, their own approvals). That is a message to the two orchestrator sessions after the release (by exact name, never a broadcast), not a repository change. It also asks the lanes' restart path to run `resume` before `run --max-steps 1` after a killed Controller process, which is what repairs a notice lost between `_persist` and the enqueue (D13). The handover also names the step that makes every launch path find a key (F3): set `notifications.api_key_file` to `~/.config/signalhub/workflow-controller.key` in the settings file once, or have the lane's `start-run.sh` export `SIGNALHUB_API_KEY_FILE`. That is a lane change outside this repository, named and not done here. A user who wants today's `events.json` values copies its `kinds`/`events` objects into `notifications.events` of the settings file; the `_help`/`_kind`/`_what` fields may stay (ignored, O4).
- **D10. A `notifications` command.** `workflow-controller notifications` prints the effective table (event type, kind, enabled, category, severity, source of each) and whether a URL and a key were found, **naming the key file and the URL source** it used (never the key); `notifications --test` sends one `info` test event through the real transport and exits 0 on `sent` or `duplicate`, 1 on `rejected` or `conflict` (a `422`), 3 on `failed` (the lanes' codes), 2 on `not_configured`, `disabled` (the kill switch file or `notifications.enabled: false`) or the test event's type disabled by `notifications.events` (nothing was sent; O4 of round 11). It is read-only and takes no repository. It is the operator's check that the wiring works.
- **D12. The Controller's context and lane name (O6).** Every body carries `context` = `<repository directory name>/<work item id>` (or the repository name alone outside a work item), after the character limits of CP1, and `metadata.lane` = `workflow-controller`, with `metadata.repository`, `metadata.kind` and `metadata.event_type`. The lanes group their notices by `context`, so the Controller's group with theirs for the same work item.
- **D11. What is not a notification.** A held lock (exit 45), a pending handoff (50), `--max-steps` (16) and a declined action (15) are the run's normal ends; `run_finished` is **not** sent for exit 16, so the lanes' `--max-steps 1` steps send `step_done` alone, one notice and not two (O3). The others are covered by `run_finished`. No event is emitted from `explain`, `follow`, `status` or any other read-only command.
- **D13. Recovery from authoritative records (F1 of round 10; bounded by F1 and F2 of round 11).** The excluded outbox (D6) replays what failed to send. A different loss is an event whose authoritative record outlived the process that was to enqueue it, and it is recovered by re-deriving from the record, never from a spool. Three paths lose it today: (a) `resume` opens no run, and reconciliation persists a re-attached job's terminal outcome directly through `_persist` (`job.py:2935`, `3172`), so a job that becomes `FINISHED` or `FAILED` there misses its `step_done` or `lane_blocked`; (b) an already-terminal record is returned unchanged (`job.py:3237-3238`), so a crash after `_persist` and before the enqueue loses the notice for good; (c) the preflight `finally` of D2 cannot run after process death, so a `merged`/`merged_squashed` event already written in the binding record misses its `pr_merged`. **A named, bounded residual (F1 of round 14):** one preflight can observe the merge and then persist `CLOSED` before returning (`_close_out_on_branch`, `milestone_branch.py:1371`; `_close_trunk_step3`, `2338`). A process death after that write and before D2's `finally` enqueues the notice leaves a `CLOSED` binding, which command-entry recovery (state `MERGED`/`MERGED_SQUASHED` only) does not read, and no job record, so that one `pr_merged` is **lost**. The window is the remainder of the close-out preflight after the `CLOSED` write: `_after_close` runs Git operations and the trunk processing (`milestone_branch.py:1375-1385`) before the `finally` enqueues, so it is as long as those take, not a few statements, and the bound is unchanged: one `pr_merged` per binding, in one process; no retained merge evidence is added (a post-close lookup would need a new record or a forge query on every entry), and the loss is accepted, named in the ADR and in the guide, and bounded to one `pr_merged` per binding. The ordering inside the step is made as tight as possible: the `finally` enqueues from the preflight's own events and the binding record the step already holds, before any later write.
  **Scope and bound (F1 of round 11).** `_resume_records` returns every terminal record of the repository (about 700 in this runtime root), so recovery must be bounded to records *this Controller generation could have failed to enqueue*. A job record is recovered only when **all** of these hold: (i) it is one `resume` **reconciled to terminal in this call** (this process is the first that could notify it, so no bound beyond (ii)-(iv) is needed), **or** it is already terminal, its `updated_at` is within `RECOVERY_WINDOW_SECONDS` (1800) of now and (ii)-(iv) hold; (ii) the log of the run that wrote it (`runs/<run_id>/notifications.jsonl`, `run_id` being the record's own) exists and holds the `notifier_active` line `open_run` writes when the run is opened with a configured notifier (D6, per run), so a record written by a pre-1.9.0 Controller (no such log), by a process with notifications `not_configured` or `disabled` (the kill switch writes no `notifier_active`), or on a repository that never had one, is **never** recovered, and the first `resume` after installing 1.9.0 sends nothing for the existing terminal records; (iii) that log holds **no outcome line recording the derived Idempotency-Key** in the states `sent`, `conflict`, `rejected`, `failed` or `duplicate` **with `source: "server"`** (the server's `422` answer to a recovered event). The rule is one sentence: **an event that never left the process is recovered, an event whose attempts were spent or whose key the server holds is not.** So a `skipped` line (the breaker), a `dropped` line (a full queue), an in-process `duplicate` line (`source: "process"`, the second enqueue of a key in one process, which says nothing about the first copy) and an event undrained at a flush timeout (no line, counted `pending` in the summary, D5) all **are** recovered by the next `resume` inside the window: the notice never left, which is the intended asymmetry with `failed`, whose attempts were spent: a key the first process already handled is not re-sent, so a `notifications.events` severity or category override changed between two `resume`s cannot turn an already-delivered event into a `422` (D4 b makes the stored body depend on category and severity, so re-sending under a changed override *would* conflict; skipping on the log is what prevents it); (iv) the event type is enabled **now**. A `failed` line is not retried (the excluded outbox, D6). A recovered event's outcome line goes to the record's own run log (D6), so a second `resume` inside the window finds it by (iii) and sends nothing. The residual case is a crash *after* a successful send and *before* the outcome line, followed by a configuration change within the window: the server answers `422`, and a **recovered** event records `422` as `duplicate` (the server already holds the key, so the notice was delivered), never `conflict`; `conflict` stays reserved for a first-time send, where it is a real lost notice. A record written while the kill switch or `notifications.enabled: false` was set has no `notifier_active` line (the notifier was inert), so it is outside (ii) and enabling later sends nothing for it. **A record whose event type alone was disabled is different (O1 of round 14):** the run's notifier was active, so (ii) holds, `disabled` is not a handled outcome in (iii), and (iv) reads enablement now; enabling the type within `RECOVERY_WINDOW_SECONDS` of the record therefore sends **one late notice**, and after the window none. That bounded case is accepted and stated rather than prevented (no historical enablement is stored), and the test asserts exactly it. The one exception is `pr_merged` recovery, which is outside the (ii)-(iv) bound: the first `step` under 1.9.0 can send one `pr_merged` for a binding already at `MERGED`/`MERGED_SQUASHED` that 1.8.0 observed, or for a merge seen while the switch was set; that is at most one late notice per binding and is accepted.
  **Recovery.** `resume` (in `_resume_records`, after reconciliation, under the lifecycle lock) hands the records that pass the bound to `derive_job_event`, which reads only the record and the states it records (`pre_state` carries `state_revision`, `job.py:371`, `403`; reconciled records carry `observed_phase_after`), never the live state, so the re-derived key and body equal the original (D4 b). **Job recovery runs on `resume` only** (O2 of round 11): a crash between `_persist` and the enqueue in a normal `step`/`run` is repaired by the next `resume`, and a new `run` does not repair it. The lane watchdog (`controller-watchdog.sh`) restarts with `run --max-steps 1` after a finished step (rc 16) and a usage hold (rc 17) and runs `resume` only after rc 30, handing back without `resume` for a killed process, so D9's handover asks the lanes to run `resume` first before restarting `run`; the limit is stated in the guide. **Branch-gate records are excluded** (F2 of round 11): `_branch_gate_record` stores a `GATE_BLOCKED` record whose gate is `branch_human_gate`'s `HumanGate`, and `_human_gate_dict` (`job.py:4511-4519`) holds only `repository`, `work_item_id`, `phase`, `what_is_required`, `artifact_path` and `safe_resume_command`, not the `binding_generation`, PR head, binding-event `at`, `gate.streak`, `release_failed` `at`, `Gate.waitable` or `merge.wait_seconds` that D4's keys and D2's `classify` read. A branch-gate record cannot be re-derived to its original key or class from the record alone, and the gate is still current: the next `step` re-observes it and sends it under its own key (D4), so recovery has nothing to add. `derive_job_event` returns `None` for a record whose gate phase is `MILESTONE_BRANCH` (**for recovery only**: the normal path sends branch gates through `derive_branch_gate_event`, CP3), and no field is added to the job record. **`pr_merged` recovery** (O3 of round 11): `resume`, `step` and `run` hand the bound branch record, when its state is `MERGED` or `MERGED_SQUASHED`, to the `pr_merged` derivation **at command entry, before `waiting_preflight`** runs (the preflight's close-out moves a binding past `MERGED`/`MERGED_SQUASHED`, after which recovery would find nothing); its key is the pull request or work-item/`binding_generation` identity of D4, which the binding record holds, and the same (ii)-(iv) bound does not apply because the binding is authoritative and the key is stable (a `200` answer pushes nothing). Recovered events enter the same queue under the same keys: an event already stored answers `200` and pushes nothing, an event the first process never sent is delivered, and a key already enqueued in this process is dropped as `duplicate`. `run_finished` and the usage events are **not** recovered: they describe a moment, and a late one is noise. A recovery failure never raises into the command (D5).

## Risks

- **A blocked network or a hung server.** The sender thread is the only code that waits on it; the lifecycle thread only enqueues. The wiring test with a hung server compares step counts, exit codes and job-record bytes with a run that has notifications off.
- **The sender thread in a Controller that is a subreaper.** A thread adds no child process; `flush` joins it before `main` returns so no daemon thread holds the interpreter open. The existing orphan-reap and Ctrl-C tests are the check; CP3 runs them serially.
- **Double notices from the two usage paths.** D8 subscribes at `usage.append_event` only; the wiring test asserts one `usage_paused` per pause for both a `run` and a manual `usage --wait`.
- **A new gate code that is never classified.** The completeness test over `GATE_CODES` fails the build.
- **Hand merge and exits without a job.** `pr_merged` derives from the preflight at its return, so a merge seen on a step that ends in a usage hold or a refusal is still sent (F1); the wiring test drives each exit.
- **Lanes and Controller both sending.** D9 is a post-release coordination step; until it happens a user sees a duplicate for each event the lane also hand-sends. Idempotency keys differ between the two producers, so the server cannot merge them. This is annoying and harmless.
- **Settings table growth.** One mapping row holds all per-event overrides, so the closed table gains seven rows, not thirty; the compatibility rule needs no change.
- **Artifact declaration.** The declaration is the previous milestone's reviewed classification with this item's ids (the default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages, known follow-up 10): `controller/`, `tests/`, `tools/`, `docs/adr/`, `docs/guide/` and the listed `docs/*.md` pages are protected at the implementation stage, and `docs/ai-workflow/` stays excluded at both stages.
- **Open decisions in `docs/TECHNICAL_DECISIONS.md`.** None is touched; this is a Controller feature with no application data or UI.

## Questions for the user

1. **Default severities that differ from your `events.json`.** The roadmap's mapping makes `usage_paused`/`usage_resumed` INFO/LOW, but your current `~/.config/signalhub/events.json` raises both to INFO/HIGH. D3 ships the roadmap defaults (a fresh install stays quiet) and D9 tells you to copy your overrides across. Say if you prefer HIGH as the built-in default.
2. **No outbox (D6).** A notification that exhausts its attempts is recorded and dropped. If you want blockers retried by a later Controller process, that is a separate small milestone with its own spool file.
