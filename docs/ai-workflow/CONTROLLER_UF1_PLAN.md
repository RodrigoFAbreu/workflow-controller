## Goal

After the Codex weekly reset the Controller kept the stored 99% reading until a new Codex session was recorded, and the lane stopped twice on "codex weekly usage 99% ... reaches the 99% threshold" although the limit had reset. A tiny `codex exec` call refreshed it by hand.

One mechanism: **`workflow-controller usage --refresh` runs one cheap probe per provider, records what each probe read into the shared usage record, and shows what it read and when.** A caller (the lane's watchdog, a restart script, an operator) runs it before it decides that a hold still applies.

## What exists

- `usage` (`controller/cli.py`, `_usage_show`) already merges `usage.read_codex_home(_codex_home())` into the shared record `usage.json` through `usage.record_reading` and prints each window's percent, reset time and reading age. It reads Claude's windows only from the record, which fills from worker streams; `_usage_fresh_readings` returns nothing for Claude.
- `usage.window_percent` already reads a stored reading as `0.0` once its `resets_at` has passed, so a reading older than its own reset cannot hold a window. What it cannot know is a reset that came **before** the stored `resets_at`, and a window nobody has used since: nothing new is recorded until a session runs.
- `usage.merge_reading` keeps the greater percent inside one window (usage within a window never falls) and lets the later window win. A refresh therefore lowers a reading only by reading a window that ends later; it never overwrites a higher percent of the same window.
- `usage.read_claude_stream` reads the `rate_limit_event`s of a `stream-json` output; `usage.read_codex_home` reads the `rate_limits` of the newest rollout files under `<home>/sessions`.
- `review.run_bounded` starts a child in its own process group under a hard deadline, kills it and every descendant on the deadline or on an exception, and returns a `RunResult`; `codex_verify.verify_build` takes it as an injectable `run`.

## Decisions

- **D1. One option, no new command.** `usage --refresh` is an option of the existing `usage` subcommand. It takes `--provider claude|codex|all` (default `all`) and `--json`. It is a usage error (exit `2`, before anything runs) with `--check`, `--wait`, `--reserve`, `--renew`, `--release`, `--stream` or `--outcome`. Without `--refresh`, `usage` behaves exactly as today.
- **D2. One probe per provider, a tiny prompt, a pinned command line.** The Codex probe runs `codex exec` and the Claude probe runs `claude -p`, each with a fixed one-word prompt, a throwaway working directory, a cheap model each probe names itself (`haiku` for Claude Code, `gpt-6.1-sol` for Codex: `controller/harness.py` declares its models with no cost order, so "cheapest" cannot be derived from the table), and the lowest reasoning effort the adapter declares for it, `efforts[0]` (`low` for Claude Code, `high` for Codex, whose table declares only `high` and `xhigh`, so "cheap" there means a one-word prompt, not a low effort). `usage_probe.py` asserts at import that each named model is in its adapter's `models` and takes the effort from its `efforts`, and a test of that assertion fails when the table drops the name, and a fixed 120-second timeout. The probes live in a new module `controller/usage_probe.py` that imports `controller.usage`, `controller.harness` and `controller.review` (for `review.run_bounded`, the bounded process runner `codex_verify` also takes as an injectable `run`, and for the hardened launch pieces below), and is imported by `controller.cli` only. Binaries are `codex` and `claude` from `PATH`; tests inject both. There is no new setting: a setting would be a second mechanism, and no third, looser command line is built: each probe's argv is pinned in `controller/usage_probe.py` and checked there by its own `check_probe_argv`. `controller/review.py` is **not** changed: `claude_argv`, `argv` and their `check_*` functions stay exactly as they are, because the probe's argvs differ from the review launches' (below), so neither can be called for a probe. The probe only imports `review`'s existing public names (`DISABLED_FEATURES`, `HOME_CONFIG_TOML`, `CLAUDE_FIXED_ENV`, `ENV_ALLOWLIST`, the home and environment builders, `copy_back_credentials`, `run_bounded`) and reads them; nothing is shared by editing them.
  - **Claude argv:** `claude -p --output-format stream-json --verbose --no-session-persistence --setting-sources "" --strict-mcp-config --mcp-config '{"mcpServers":{}}' --tools "" --max-turns 1 --disable-slash-commands --model haiku --effort <lowest declared>`, the prompt on stdin. `--setting-sources ""` and the empty MCP config keep the operator's hooks, MCP servers and plugins out; `--no-session-persistence` writes no transcript under `~/.claude/projects`; `--verbose` is what `stream-json` needs under `-p`, without it no `rate_limit_event` is emitted. These flags differ from `review.claude_argv`'s, which is why the probe pins its own: `--tools ""` where `claude_argv` passes `--tools Read,Grep,Glob` (`CLAUDE_TOOLS`); `--max-turns 1` is added; `--permission-mode dontAsk --permission-prompts none` are dropped (no tool exists to prompt for); and the model is the alias `haiku`, which `claude_argv` refuses (`CLAUDE_MODEL_ID_RE` requires a full `claude-...` id). The flags both lines carry (`-p`, `--output-format stream-json`, `--verbose`, `--no-session-persistence`, `--setting-sources ""`, `--strict-mcp-config`, `--mcp-config`, `--disable-slash-commands`) are written out in `usage_probe.py`, and a test compares the **complete** flag sets of the two argvs (every `--flag` and `-p`, values aside): the flags only the probe carries (`--tools ""`'s value apart, `--max-turns`) and the flags only `review.claude_argv` carries (`--permission-mode`, `--permission-prompts`, and whatever the model, effort and tool arguments add) are each listed in the test as intentional differences, so a hardening flag added to the review argv later fails the test until the probe takes it or the test lists it with a reason. The live check (end of CP1, recorded in CP3) confirms the installed `claude` accepts `--tools ""` and `--max-turns 1` under this set and emits a `rate_limit_event`; if a flag is not accepted, its nearest equivalent is used and the page records it.
  - **Codex argv:** `codex exec --strict-config` + one `--disable <f>` per `review.DISABLED_FEATURES` + `-c model_provider="openai" -c notify=[] -c web_search="disabled" -c model="<model>" -c model_reasoning_effort="<lowest declared>" -c approval_policy="never"` + `-s read-only --skip-git-repo-check --ignore-rules --color never -C <throwaway dir>`, the prompt as the last argument. It differs from `review.argv("exec")` in `-s read-only`, `--skip-git-repo-check` and no `-o` (no verdict file is written), and it does not carry `_overrides("exec")`'s sandbox table, `service_tier` or trust table: the probe is read-only with no tools to run, and the pinned `-c` list above is the whole override set. The `--disable` list is read from `review.DISABLED_FEATURES` so it stays in step. `--skip-git-repo-check` is required because the throwaway directory is not a git repository and `codex exec` refuses to run outside one without it. `--ephemeral` is never passed, because it stops the session file the reading comes from.
  - **Private homes and environment (both probes):** each probe runs under its own `review.JobLayout` under the runtime root, with its own `area` (`usage-probe`) and a fresh job id, removed in every case; `layout.tree` is the throwaway working directory (`-C` for Codex, the child's cwd for Claude). Both probes are built on `review.ReviewHarness` (`review.CODEX`, `review.CLAUDE`), so each takes its home builder, credential file and credential lock from the same record the review launches use and the two stay in step with them; no per-provider copy of those pieces is written.
    - **Codex:** the home is built as `review.build_home` builds a review's (`layout.codex_home`: a `config.toml` that is `review.HOME_CONFIG_TOML`, with no `mcp_servers`, `hooks`, `notify`, `profiles` or `plugins`, and a 0600 copy of the operator's `auth.json`; an operator home without one is the `failed` outcome, cause named). MCP servers run outside the command sandbox, so only a home with none contains the probe; the operator home's config layer is never composed. The environment is `review.child_environment(layout, binary, <tag>)`: exactly `ENV_ALLOWLIST`, a `PATH` of the binary's directory and the system directories, private `HOME`, `TMPDIR` and `CODEX_HOME`, and the ownership tag (`OWNERSHIP_VAR`) that `review.run_bounded` uses to kill descendants that leave the process group. It is passed to `run_bounded` exactly as built.
    - **Claude:** the home is built as `review.build_claude_home` builds one: a private `CLAUDE_CONFIG_DIR` (`layout.claude_home`) holding a 0600 copy of the operator's `.credentials.json` and nothing else, plus the empty private `HOME` and `TMPDIR`. The environment is `review.claude_environment(layout, binary, <tag>)`: the private `CLAUDE_CONFIG_DIR`, `HOME`, `TMPDIR` and XDG directories, `review.CLAUDE_FIXED_ENV` (`DISABLE_AUTOUPDATER=1`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `ENABLE_CLAUDEAI_MCP_SERVERS=false`) and the ownership tag. So the account's claude.ai connectors are not fetched, auto-memory writes nothing, and every file Claude Code writes on a run (`.claude.json`, `backups/`, `sessions/`, `session-env/`, `projects/<slug>/memory/`, the `~/.cache` MCP logs) lands inside the probe's own layout. The boundary checks before the launch are the next bullet. An operator home without a credential file is the `failed` outcome, cause named.
    - **Boundary checks before each launch (both probes):** the checks a review runs, in the order the review launches run them, because the pinned flags and private homes alone do not keep a managed layer out (`review.py:1627`: managed policy files apply whatever `--setting-sources` says, and a `/etc/codex/config.toml` or `managed_config.toml` layer composes into a Codex run). Claude: `review.check_claude_home(layout)` and `review.check_claude_outside_layers(review.CLAUDE.system_dir)`. Codex: `review.check_home(layout)` and `review.check_outside_layers(review.CODEX.system_dir)`. `usage_probe.py` takes the `system_dir` as an injectable parameter the way `review.launch_review` takes it, defaulting to the harness's own. A refusal (`ReviewLaunchRefusedError`) is the `failed` outcome with its cause named: the binary is not started, the stored readings are unchanged, and the layout is removed and the credential handled as in every other case. **Codex's composed-configuration check (revision 6, review finding I1):** `check_home` and `check_outside_layers` see only file-backed layers. `review.CONFIG_SOURCES` also lists `mdm`, `enterpriseManaged` and `legacyManagedConfigTomlFromMdm` layers (disposition `managed`), which Codex composes from the operating system or the account whatever the private home and an empty `/etc/codex` hold, and which can supply an MCP server that runs outside the command sandbox. So before the inference launch the Codex probe also composes the configuration under its **own** command line and checks it. It runs `codex app-server` with the same pinned `--strict-config`, `--disable` and `-c` set as the exec argv above (`check_probe_argv` pins this third argv too, `-s`, `--skip-git-repo-check`, `--ignore-rules`, `--color` and the prompt excluded), the same private environment and `cwd` the throwaway directory, sends the `initialize`, `initialized` and `config/read` (`includeLayers: true`) requests as `review.compose_config` does, and judges the answer with `usage_probe.check_probe_composed`. `review.compose_config` itself is not called, because it builds `review.argv("app-server")` with the review's sandbox, tier and trust overrides; `usage_probe.py` carries a small compose function of its own over `review.run_bounded` and the public `review.CONFIG_SOURCES`, `review.MANAGED_APPROVED_LEAVES`, `review.ORIGIN_ALLOWED`, `review.flatten` and `review.ReviewLaunchRefusedError`. `check_probe_composed` refuses (`ReviewLaunchRefusedError`, the `failed` outcome with its cause named) when: a layer has a type not in `CONFIG_SOURCES`; a `managed` or `absent` layer carries any leaf (`MANAGED_APPROVED_LEAVES` is empty, so none is approved); a `project` layer is enabled; the `user` layer is not the private home's `config.toml`; the composed `mcp_servers`, `hooks` or `notify` is not empty; or any leaf of the composed configuration has an origin whose type is not in `ORIGIN_ALLOWED` (the packaged defaults and the probe's own `-c` layer and home). It does not compare the sandbox, tier or trust values the review pins (the probe's `-s read-only` and its pinned `-c` list are checked by `check_probe_argv`). A compose command that does not run, times out or prints no `config/read` answer is the same `failed` outcome, with the binary of the inference launch never started. The launch costs no tokens (the app-server needs no credential and starts no inference, as `review.compose_config`'s docstring records) and runs under the same 120-second deadline. The Claude probe has no equivalent gap: `check_claude_outside_layers` reads the managed policy files, which are the only layers Claude Code applies whatever `--setting-sources` says, and the empty MCP config with `--strict-mcp-config` keeps every other MCP source out. The rest of the Codex review's `_preflight` (`mcp list`, `features list`) is left out: with the composed check above, the empty working tree and the read-only sandbox, nothing remains for it to find.
    - **Credential copy-back:** after each probe, whatever its outcome, a refreshed credential is copied back by `review.copy_back_credentials(layout, <operator home>, <captured digest>, review.CODEX | review.CLAUDE)` under that harness's credential lock (`reviews/codex-auth.lock`, `reviews/claude-auth.lock`): only when changed, still valid, and the operator's file unchanged since captured. The operator homes are `$CODEX_HOME` (else `~/.codex`) and `$CLAUDE_CONFIG_DIR` (else `~/.claude`), resolved as the review launches resolve them. Each helper named in this decision takes a `JobLayout`, which the probe builds, so none needs extracting or changing.
  - **Killed probes:** a SIGKILL or a power loss during a probe leaves its layout, with a 0600 credential copy, under `<runtime>/usage-probe/`. At the start of each `refresh`, any `usage-probe/<job id>/` layout whose modification time is older than 300 seconds (more than twice the 120-second probe timeout, so a running probe's layout is never taken) is removed. The operator page says so.
- **D3. The reading comes from the probe's own record, and only from it.** Codex: the probe's private home (D2) holds exactly the session file the probe wrote, so `usage.read_codex_home(<private home>)` reads the probe's own reading, never an earlier session's; a probe that exits `0` but wrote no `rate_limits` (a refused turn, a changed rollout shape) finds no rollout reading there and is `no_reading`. The operator home (`$CODEX_HOME`, else `~/.codex`) is not read for the refresh: `usage`'s own merge of it is unchanged and shows the operator's sessions as before. Claude: the `stream-json` output of the probe is parsed with `usage.read_claude_stream`. A probe never parses prose.
- **D4. A probe that fails changes nothing.** A missing binary, a non-zero exit, a timeout, or output with no reading of the probe's own (D3) leaves the stored readings untouched and is reported per provider with its cause (`not_found`, `failed`, `timed_out`, `no_reading`). One provider failing never skips the other. The exit status is `0` when every probed provider yielded a reading, and `1` when at least one did not (the existing code `1`, which `EXIT_TOKEN_UNKNOWN` already names; the refresh path returns it through a private `_USAGE_EXIT_PROBE_FAILED = 1`, not a second module-level `EXIT_*` constant, because `tests.test_plan_document_consistency`'s ADR exit-code check refuses two `EXIT_*` constants sharing a code; `docs/exit-codes.md` row 1 gains the case). The view still prints, from the record as it stands.
- **D5. It shows what it read and when.** After the probes, `usage --refresh` prints the usual view and a `refresh` block per provider: the probe outcome, and for each window the percent, `resets_at` (epoch and local time), `observed_at` and the source, marking a stored reading whose `resets_at` has passed as reset. `--json` adds the same block under `providers.<name>.refresh`.
- **D6. Read-only apart from the refresh.** The only writes are the merged readings in `usage.json` (as `usage` already writes Codex readings), the probe's own layout under the runtime root (D2: its private homes, the Codex session file, Claude Code's own state), which is removed in every case (a layout a killed probe left, older than 300 seconds, is removed at the next refresh, D2), and a credential file copied back into an operator home when it changed (D2). Nothing else is written in `~/.claude`, `~/.cache`, `~/.codex` or `HOME`. Under the pinned command lines, environments and boundary checks (D2) the probe loads no operator hooks, MCP servers (the claude.ai connectors included), plugins or notify command, writes no Claude session transcript and no auto-memory. A probe reserves nothing, charges no run or repository, and writes no event.
- **D7. Callers, not callees.** The Controller's own `run` and `step` admission is unchanged. The pages show the call a watchdog or restart script makes before it acts on a hold (`workflow-controller usage --refresh --provider all`, then `usage --check`). Changing the operator's own scripts outside this repository is not part of this item.
