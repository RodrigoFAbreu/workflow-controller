## Goal

The kanban loop (C11) and the lanes share one Claude plan window (5 hours, and a weekly one) and one Codex allowance. Today the lane scripts (`usage-lib.sh`, `usage-gate.sh`) read the percentage out of the newest `worker.stdout` files and pause at a fixed 85% between steps. They have no forecast, no per-lane share, no Codex budget, and they live outside the Controller. After this milestone the Controller does it itself:

1. **It reads usage.** The Claude five-hour and seven-day windows from the `rate_limit_event`s in its own worker streams, and the Codex primary (5 h) and secondary (weekly) windows from Codex's session files. One account-wide record under the runtime root is shared by every lane and repository, because they share one runtime root.
2. **It forecasts a job**, for both windows, from earlier jobs of the same `(role, model)`.
3. **It admits a job atomically.** Admission checks the forecast against the readings *and against the forecasts other lanes have already reserved*, and reserves its own, under one lock, so two lanes cannot both pass on the same headroom.
4. **It pauses before a job that would not fit**, at a safe boundary (before the job record exists, so nothing is half finished), waits until the window resets plus a grace period, and resumes through the full orchestration boundary. Every pause and resume is an event.
5. **Budgets are settings** (settings generation 4): an account threshold per window, and a per-repository and an optional per-run cap, each for Claude and Codex separately. The strictest limit wins.
6. **`workflow-controller usage`** prints the readings and, with `--check` or `--wait`, admits a worker started outside the Controller (cross-model reviews, functional testers, gate workers) against the same rules, and `--release` closes its reservation, replacing `usage-gate.sh`.

Out of scope, and why (every deferral has a named roadmap owner that CP5 adds; see D13):
- **Notifications** for a pause and a resume: C5 (SignalHub) comes next in the user's order and owns delivery and per-event configuration. C8 writes the events C5 subscribes to (D9); C5's ROADMAP 11.4 entry already lists "a usage pause and its resume (C8)".
- **Recognising a usage-limit `result` in a worker stream** and waiting then restarting: roadmap step **C8b** (D13). Real samples exist: `~/.local/state/workflow-controller/jobs/20260924T213209Z-148c63ed/worker.stdout` and `.../20260924T211904Z-73845184/worker.stdout`, each ending in a `rate_limit_event` with `status: "rejected"`, an `assistant` message with `error: "rate_limit"` and a `result` with `is_error: true`, `api_error_status: 429`; both jobs are `FAILED` with `TransitionNotObservedError`, so today a limit hit mid-job stops the run with exit 30. Deferred on its merits: classifying the job distinctly, waiting for the stream's `resetsAt` and having `resume`/reconciliation accept a job that ended that way changes `controller/job.py` supervision and the reconciliation contract, which this milestone otherwise leaves alone. What this milestone does take from the samples: the reader treats `rejected` as at or over the limit (D2), and a sanitised copy of one stream is a golden for that reading (CP1).
- **A per-repository cap that differs by repository** (a map setting needing its own validator like `routing`'s): roadmap step **C8c** (D13). Here the repository cap is one number applied to the repository the Controller is driving, set in that repository's settings file (`--settings`), which is how lanes already differ.
- **Codex workers** (C7) calling the gate from inside the Controller: roadmap step **C7** gains that requirement (D13). Until then Codex is enforced only through `usage`, whose Codex budget is complete (D4, D8).
- Hosted per-user budgets (11.12), changing `controller/worker.py` or the spawn.

## Decisions

- **D1. One new module, `controller/usage.py`, a leaf.** It imports `runtime`, `worker_stream` (only for line/event iteration if it exposes it; otherwise it parses the JSON lines itself) and the standard library. It never imports `job`, `observe`, `cli` or `telemetry`. (Revision 2 claimed importing `telemetry` or `worker_stream` would cycle; it would not, since `telemetry` imports only `worker_stream` -- the rule is simply that `usage` stays below `job`, `observe` and `cli`, which import it.) It holds: the readers, the shared record, the window arithmetic, the forecast, admission and the pure decision `evaluate(...)`. Every path (runtime root, Codex home) is a parameter; nothing reads `~/.codex` or the real runtime root unless the caller passes it, and tests never do. The I5 guard in `tests/__init__.py` redirects `XDG_CONFIG_HOME` only, and the `usage` subcommand defaults to `$CODEX_HOME`, else `~/.codex`; CP3 therefore adds a `CODEX_HOME` redirection beside the XDG one in `tests/__init__.py` and a guard test.
- **D2. Readings, and one freshness rule.** A reading is `{provider, window, percent, resets_at, observed_at, source}`. Claude: `percent` is `100 * utilization` (the stream gives a 0-1 fraction); the reader scans the `rate_limit_event`s of a worker stream and keeps the last `unifiedWindows.five_hour` and `seven_day`; `rate_limit_info.status: "rejected"` counts as 100% whatever `utilization` says, **for the window the event names** in `rateLimitType` (`five_hour` or `seven_day`; the real sample carries `five_hour`) and for no other, so a weekly rejection holds the weekly window with the weekly resume time and does not manufacture a five-hour hold (revision 4, review Optional 1); an event naming neither leaves both windows to their `utilization`. `observed_at` is the stream's mtime when read from a file, else the job record's `updated_at`; for Codex it is the `timestamp` of the `event_msg` line holding the reading. A reading whose `resets_at` is in the past is 0%: that window has reset.
  The shared record `<runtime_root>/usage.json` (schema `{version: 2, readings: {...}, reservations: {...}, lapsed: {...}, ledger: [...], settled: {...}, spend: {...}}`; D6) is written by `usage.record_reading` under a new `runtime.usage_lock`, with `runtime.write_json`. **Merge rule (deterministic, revision 3, review Important 4).** Two readings of one provider and window are *the same window* when their `resets_at` differ by at most `WINDOW_JITTER_SECONDS = 120` (the real Codex samples show the weekly `resets_at` ending `4075` then `4074` inside one window; a Claude stream's `resetsAt` is likewise quantised). For the same window the stored reading is replaced only if the incoming `percent` is greater (usage in a window never falls), or equal with a newer `observed_at`; the stored `resets_at` becomes the larger of the two so jitter cannot make the window look older. Otherwise the reading with the greater `resets_at` (the later window) wins, whatever either `observed_at`; so a delayed writer holding an older window can never replace a newer one, and a delayed writer holding the same window with a lower percent can never replace a higher one. The merge is a pure function (`usage.merge_reading(stored, incoming)`), tested over the Codex jitter pair, a delayed Claude stream and a window rollover. Because Claude's `utilization` is account-wide, a reading from any Controller job reflects work done outside the Controller too, up to its age; `usage` prints the age.
- **D3. Codex reading.** From `<codex_home>/sessions/YYYY/MM/DD/rollout-*.jsonl` (default `$CODEX_HOME` else `~/.codex`; a parameter), the last `rate_limits` object of the newest files, taking `primary` (`window_minutes` 300) as the five-hour window and `secondary` (10080) as the weekly one, chosen by `window_minutes`, not by the names. `used_percent` is already 0-100; `resets_at` is an epoch. The reader tolerates the field being absent (no reading, not an error) and a partial last line (skipped). Files are ordered by mtime; only the newest three are scanned to bound the cost, and the reading with the latest `timestamp` across them wins within the D2 merge rule.

  `TABLE_GENERATION` becomes 4; `fill` adds the rows and moves nothing already in a file. Two new CLI flags, each the `cli_flag` of exactly one row and accepted by the subcommands that evaluate that row (revision 4, review Optional 3): `--usage-cap` (row `usage.run_cap_percent`) on `run`, `step` and `usage`; `--usage-codex-cap` (row `usage.codex_run_cap_percent`) on `usage` only, because until C7 the Controller launches no Codex worker. Every other new row has `cli_flag = None`. A flag overrides the setting for that invocation, like the existing flags. The Claude settings govern Claude jobs and the Claude windows; the `codex_*` settings govern the Codex windows and Codex workers. A Claude cap never counts Codex spend and the reverse (the ledger is keyed by provider, D6).
- **D5. The decision: pure, strictest-wins, with a stated precedence.** `evaluate(provider, readings, reservations, settings, forecast, run_spent, run_outstanding, repository_spent, repository_outstanding, now)` returns `go` or a `Hold(provider, window, resume_at | None, reason, waitable)`. `forecast` is `(five_hour_percent, weekly_percent)`; `reservations` are the live reservations of that provider from other admissions (D6), summed per window component; `run_outstanding`/`repository_outstanding` are the outstanding liabilities of D6 (live and lapsed reservations), which the caps count beside completed spend. A job is held when any of these holds:
  - five-hour: `percent + reserved_five_hour + forecast_five_hour >= pause_at_percent` (each reservation's `five_hour` component, rolled over into the current window by D6);
  - weekly: `percent_weekly + reserved_weekly + forecast_weekly >= weekly_pause_at_percent` (revision 3, review Important 2: the weekly window has its own forecast, from the job's seven-day delta, and its own default, because five-hour points are not weekly points; the weekly window's capacity differs, so the two are never mixed);
  - run cap: `run_spent + run_outstanding + forecast_five_hour > run_cap_percent`;
  - repository cap: `repository_spent + repository_outstanding + forecast_five_hour > repository_cap_percent` (revision 6, review Important 1: two workers cannot each pass on the same cap headroom, and a lapsed holder keeps its liability).
  **Precedence.** A cap hold is never waitable (it has no reset) and dominates every timed hold: if any cap holds, the result is the cap, with `waitable=False`, so a run is never left sleeping on a window while a cap would stop it afterwards. Among timed holds the one with the latest `resume_at` is reported. A *missing* reading disables only the account check for that provider and window (reason `no reading`, recorded), never a cap or the other window: fail-open on missing *data* is deliberate (a fresh machine must run) and is stated in the guide. A reading older than its own `resets_at` is 0%.
- **D6. Admission, reservations, outstanding liabilities, the ledger and the spend totals (revision 3, review Important 1 and 3; reworked in revision 6, review Important 1-4).** The shared record has seven sections, all under `usage_lock` and all published by one `runtime.write_json`, so each change below is all-or-nothing:
  - `readings` (D2);
  - `reservations`: `{token: {provider, role, model, repository, run_id, job_id | None, created_at, renewed_at, expires_at, five_hour: {amount, start, window_resets_at}, weekly: {amount, start, window_resets_at}}}`. **The two windows are independent components** (revision 6, review Important 2), each with its own reserved `amount` (the forecast), its own `start` reading and its own window. `usage.admit(...)` takes the lock, first **rolls over** every live component whose window has reset (below), then moves the reservations whose lease has expired (`expires_at`) to `lapsed`, evaluates D5 with the per-window sums of the live components of that provider and the outstanding liabilities (below), and, on `go`, writes the reservation in the same critical section and returns its token; on a hold it writes nothing. So two lanes with 70% used, an 85% threshold and forecasts of 8% each: the first is admitted and reserves 8; the second sees 78 + 8 = 86 and is held. `start` is the reading at admission (or, when the job's own stream carries an earlier-or-equal reading of the same window, the lower of the two, which only enlarges the measured delta and so errs on the safe side, review Optional 4). The *original* baseline (both `start`s and their windows) is kept durably in the reservation **and copied into the job record's `usage` block when the record is created** (below), so a recovered job still has its accounting baseline even if the reservation has gone; deltas always use this original baseline, never a rolled-over `start`.
  **Rollover, not release (revision 6, review Important 2).** A window reset never releases the reservation of work that may still be running. When a component's `window_resets_at` is in the past (D2) and the lease is live, that component alone is *re-based* into the new window: `amount` is unchanged (the full forecast is held again in the new window, conservatively, because a continuing job consumes there too), `start` becomes the new window's current reading (0 when none), `window_resets_at` becomes the new window's and a `rolled_over` count increments. The other component is untouched: a five-hour reset leaves the weekly component exactly as it was. So with weekly usage at 90%, a 95% weekly threshold and an active worker holding 4% weekly, a second 4% worker is still held after a five-hour reset (90 + 4 + 4 = 98 >= 95), and the active worker holds its five-hour forecast in the new five-hour window as well. A rollover is not a lapse: the job completes through the normal path, as an `after_reset` delta.
  **Renewal and lapse (revision 4, review Important 1; mechanism replaced in revision 5, review Important 1).** `expires_at` is a liveness lease, not a fixed deadline: `usage.renew(token, now)` sets `renewed_at = now` and `expires_at = now + usage.reservation_seconds`. The worker-state flush (`on_state_change`) is **not** a renewal hook: it fires only when the published worker signature changes (`controller/worker.py` `_publish`), so a long `RUNNING` turn with stable processes produces none (the operator's runtime root holds jobs of 58 and 72 minutes with no event between spawn and end). Renewal is therefore **owned by `job.py` on a timer of its own**, option (a) of the review, with `controller/worker.py` untouched (it stays out of scope): `usage.RenewalTicker(renew, interval_seconds, wait)` is a small leaf class in `usage.py` that runs a daemon thread calling `renew` every `interval_seconds` (`min(60, reservation_seconds / 4)`), where `wait` is an injectable `Event.wait`-shaped callable so tests step it without sleeping; `start()` is idempotent and `stop()` joins the thread and is safe to call twice. `job.execute_step` starts it immediately after the `on_spawn` flush (the process exists and is recorded) and stops it in the same `finally` that closes the launch, whatever the outcome; `_reattach` starts it for a job it finds still alive and stops it in its own `finally`. The ticker is stopped and joined outside `usage_lock` and is independent of lifecycle-lock acquisition (it takes only `usage_lock`, briefly). A renewal that raises is logged as the event `usage_renew_failed` and the ticker keeps running; it never fails the job. So a job that runs for 48 h keeps its reservation however few state changes it publishes, and no other lane is admitted on its headroom; `reservation_seconds` bounds only how long a *crashed* holder's reservation survives (the ticker dies with the Controller). A job whose supervisor has detached (`worker_drain_detached`) is no longer renewed, so its reservation lapses while owned processes may still run; that is accepted for the *account* windows (the worker has exited and most consumption is done) and its cap liability is retained anyway (below); the guide says so. A manual token has no supervisor: `usage --renew TOKEN` extends it, and the lane script calls it with the worker (a script that does not has the original lease).
  **Lapsed, and renewing a lapsed reservation.** A reservation whose lease expired moves to `lapsed` with `reason: "expired"` (the only reason: a window reset is a rollover, above) and an event `usage_reservation_expired`. It no longer counts towards the *account* windows (its holder is presumed dead) but **still counts as a cap liability** (below) until it is settled or abandoned. `usage.renew` on a `lapsed` reservation **revives** it, because the holder is demonstrably alive and the lapse was the clock's, not the job's: it moves back to `reservations` with a fresh lease and both components re-based to the current windows by the rollover rule; this is the normal case for `_reattach` after a Controller crash longer than `reservation_seconds`. The revival does not re-run D5 (the job already runs; refusing would not stop it, only hide its use), so the live sum may then exceed headroom until it completes, which errs towards pausing the next admission. On an unknown or already settled token, `renew` revives nothing and returns `unknown`: `usage --renew` then exits 1 with a message that the token is unknown or already accounted and that `usage --release` cannot account an unknown manual token or further work behind an already-settled token; `_reattach` and the ticker ignore that result (`complete` follows the single charging authority above).
  - `lapsed`: `{token: reservation + {reason: "expired", lapsed_at}}`. **Abandonment (revision 6, review Important 1).** A lapsed reservation never settled within 7 days is not deleted: in one write it is *abandoned*, i.e. charged at its `five_hour.amount` to `spend.run`, and to `spend.repository` when its window is the current one, with a `settled` entry and a `ledger` entry of `delta: "abandoned"` (figures `None`, so it never enters a forecast). An abandoned holder therefore costs its forecast, never nothing.
  **Outstanding liability (revision 6, review Important 1).** The cap checks of D5 count completed spend *plus outstanding work*. `run_outstanding` is the sum of `five_hour.amount` of every live **and lapsed** reservation of this provider with this `run_id`; `repository_outstanding` is the same for this `repository`, restricted to those whose `five_hour.window_resets_at` is the current window (within `WINDOW_JITTER_SECONDS`), because repository spend is window-scoped (a lapsed holder from an earlier window no longer weighs on this one; it still weighs on its run). A reservation leaves outstanding only by `complete` or abandonment, each of which replaces the liability with the charge in one write, so there is never an instant at which a cap sees neither or both. Two manual workers each forecasting 8 against repository spend 10 and a cap 20: the first is admitted (10 + 0 + 8 = 18), the second is held (10 + 8 + 8 = 26 > 20), and the token of a worker that never returns keeps weighing on the cap after its lease lapses.
  - `ledger`: the completed-job accounting kept **for forecasts and audit only**, at most 1000 entries and 30 days. It is not authoritative for any cap, so other lanes or manual workers evicting entries can never reopen a cap (revision 6, review Important 3). **Entry schema (complete, revision 4, review Important 3):** `{id, provider, role, model, repository, run_id, started_at, finished_at, start_window_resets_at, end_window_resets_at, five_hour, weekly, five_hour_after_reset, weekly_after_reset, reserved_five_hour, reserved_weekly, charged, delta}` where `delta` is `"measured"` (start and end are readings of the same window, newer end), `"after_reset"` (a reset lies between them), `"unknown"` (no usable end reading) or `"abandoned"` (above). `five_hour`/`weekly` hold `end - start` (floored at 0) only for `"measured"` and are `None` otherwise; `five_hour_after_reset`/`weekly_after_reset` hold the end reading's percent for `"after_reset"` and are `None` otherwise. `start_window_resets_at` is the window of the start reading and `end_window_resets_at` that of the end reading (`None` for `"unknown"`). `reserved_*` are the forecast the reservation held. Any future field addition bumps `usage.json`'s `version`.
  - `settled`: `{token: settled_at}` for every token already accounted (tokens only, no entry-count limit, kept 90 days): the idempotency key of `complete` and of replay, independent of the ledger's eviction.
  - `spend`: the authoritative totals. `run: {provider: {run_id: {charged, updated_at}}}` is kept until `updated_at` is 90 days old, where **activity** is any charge, admission or renewal for that run (each refreshes `updated_at`), and a total is never pruned while a live or lapsed reservation with that `run_id` is outstanding, so work that outlives 90 days (worker execution has no default timeout, `controller/job.py:228`) never reopens its cap. A run with no activity and nothing outstanding for 90 days is over; reusing its `--run-id` afterwards intentionally starts fresh accounting at zero, and the guide says so. `repository: {provider: {repository: {window_resets_at, charged}}}` is the current five-hour window's total: a completion in a newer window replaces it, one in the same window (within jitter) adds to it, and one for an older window (a delayed writer) is ignored for this window.
  A reservation is released exactly once, by `usage.complete(token, end_readings, outcome, usage_block=None)`: it resolves the baseline from the live reservation, else the `lapsed` one, and from nothing else. **Single charging authority (revision 11, round 10, Important 1): a charge is made only against a reservation or lapsed entry that is still in the shared record; `complete`, the sweep, `_reattach` and the `resume` dispatch never charge from a `usage_block` alone, and there is no unknown-token fallback anywhere.** The `usage_block` the caller passes (the job record's) supplies only the end figures (`five_hour_end`, `weekly_end`, `end_window_resets_at`) of a job whose reservation is present, never a baseline and never the right to charge. With neither a reservation nor a lapsed entry the call is a no-op, silent if the id is already in `settled` (event `usage_complete_already_settled`) and otherwise recorded (event `usage_complete_unknown_token`; nothing is invented, and the same holds for a manual token). Because abandonment writes `settled` and charges the forecast, and a pruned `settled` entry (90 days) falls to the same no-op, no path can charge a token twice; a lapsed reservation is retained until `complete` or abandonment, so any permitted charge always has its durable identity. In **one write** it computes the job's deltas (below), appends the ledger entry, adds the charge to `spend.run` and `spend.repository` (Spend, below), records `settled[id]`, removes the reservation or lapsed entry and records the end readings. An expired, lapsed or missing reservation therefore never loses accounting: a manual worker that spans a five-hour reset (`usage --wait --reserve` ... `usage --release TOKEN`) is rolled over while it renews and is recorded as an `after_reset` delta charged at least the forecast. It is called (a) by the completion path in `job.py` once the record is terminal, (b) by the replay sweep below and by `_reattach` (which gets the token **and the whole `usage` block** from the job record: `_reattach` runs at `resume`, often hours after the Controller died, when the reservation has typically lapsed, so this path is served by the lapsed reservation, with the block supplying the end figures; if the reservation is gone, the settled or orphan rules above apply and nothing is charged), (c) with `outcome="not_started"` when launch fails after admission (the gate's caller releases in a `finally`; a `not_started` release writes no ledger entry, spend or `settled` entry), and (d) by expiry and abandonment, the backstop for a crashed process.
  **Crash-safe replay (revision 6, review Important 4; reworked in revision 7, review Important 1 and 2; `never_launched` and `_reattach` corrected in revision 8, round 7; `never_launched` (i) made structural in revision 9, round 8; its real-predicate test placed in CP3 in revision 10, round 9).** Three durable facts make completion replayable. (1) The job record's `usage` block holds the baseline from creation. (2) **The end figures and `accounting: "pending"` are written in the write that reads the stream, i.e. the `COMPLETED` write** (`controller/job.py` `execute_step`, where `_telemetry_block` runs, and `_reattach`'s own `COMPLETED` write): `COMPLETED` is a non-terminal status (`NON_TERMINAL_STATUSES`), and every later write of that record spreads `**record`, so the figures carry through to whichever terminal write follows, whether `execute_step`'s own step 8/9 or protocol write or one of `resume` phase 2's reconcilers (`_reconcile_completed`, `_reconcile_launched`, `_reconcile_planned`, the drift and protocol reconcilers). No terminal write needs to name them. (3) The reservation stays in the shared record, carrying its `job_id`, until `complete` removes it. **Binding order:** `usage.bind_job(token, job_id)` writes the `job_id` into the reservation durably *before* `execute_step` publishes the job record, so the sweep, which finds jobs through the reservation's `job_id`, can always reach a record that exists; a crash between the bind and the record publication leaves a reservation bound to a job with no record, which the sweep releases `not_started` once the reservation has lapsed (a live one is left to its lease, never raced against a record being created).
  **Which id.** `complete`, `settled`, abandonment, `settle_pending` and the `resume` dispatch all key on the **token**: every admitted unit has one, a Controller job's token is in its `usage` block and in its reservation (which also carries the `job_id` for the walk), and a manual worker has only the token. The job id is never a key.
  **What the sweep settles.** `usage.settle_pending(runtime_root, load_job, never_launched)` (`load_job(job_id)` and the predicate `never_launched(record)` are injected, so `usage` stays a leaf) walks the reservations and lapsed entries that carry a `job_id`, loads each record and acts only on a **terminal** one (a non-terminal record is left to supervision and `_reattach`):
  - `accounting: "pending"` (end figures present): `complete(token, ..., usage_block=block)`, i.e. `measured`, `after_reset` or `unknown` from the figures it carries;
  - `accounting: "open"` (no end figures) and `never_launched(record)`: `complete(token, outcome="not_started")`, released with no charge. `never_launched` is defined on what the code actually writes, and is true for (i) a record with `status == STATUS_INTERRUPTED` **and no `expected_transition` key** -- the record a `PLANNED` one becomes under `_reconcile_planned` (its docstring: nothing can have happened, the record was flushed before the launch was prepared, and "no `expected_transition` was ever written for this record"). The test is structural because the sweep reads the terminal record, not its history, and `_reconcile_planned` (`job.py:2627`), `_reconcile_launched` row 3 (`:2698`) and the protocol reconciler (`:2912`) all write the same `INTERRUPTED` status without recording what they reconciled from. `expected_transition` is the one key that tells them apart: `_execute_launched` adds it (with `ownership_tag` and `worker_state`) in the `LAUNCHED` write (`:5541-5552`) and every later write spreads `**record`, so a record that was ever `LAUNCHED` always carries it, and a `PLANNED` record never does. The status guard is part of (i), as it is of (ii): a future reconciler writing another terminal status on a never-launched record falls through to the conservative `unknown` charge instead of being silently released. And (ii) a `FAILED` record whose `reconciliation_evidence["code"]` is `WORKER_NOT_STARTED_CODE` (`"WorkerNotStarted"`, `job.py:3264`; written by `worker_not_started()` for a stream-creation failure, a protocol currency-check error or a launch error before `on_spawn`) or `protocol_decision.DECISION_STALE_AT_LAUNCH` (`"decision_stale_at_launch"`, `protocol_decision.py:443`; the stale-answer path), both through `not_started()` (`job.py:5554`). `"worker_not_started"` is only the *event name* that `not_started()` passes to `_persist`; the record carries no `worker_outcome`, which only the `COMPLETED` write sets (`validate_record` even rejects it on `PLANNED`/`LAUNCHED`), so the predicate never reads it. Either record can be followed by a crash before the in-process `not_started` release;
  - `accounting: "open"` otherwise (a `LAUNCHED` record `_reconcile_launched` made terminal: the worker may have run and no stream was read): `complete` with no end reading, an `unknown` delta charged at the forecast, as a launched worker must not be free; this includes a `LAUNCHED` record `_reconcile_launched` row 3 made `INTERRUPTED` (it carries `expected_transition`, so (i) does not match it);
  - `accounting: "done"`: nothing.
  After each `complete`, `job.py` sets `accounting: "done"` on the record with the existing record write. That write is **idempotent and made only to a terminal record, or to the `COMPLETED` record `_reattach` itself holds under that job's supervisor lock** (`_reattach` calls `complete` from the block and the end figures its own `COMPLETED` write carried, then sets `"done"` on that record; later writes spread `**record`, so the flag carries through to the terminal write, and a crash before it is covered by the dispatch's `settled` check). The sweep also reaches records of other target repositories sharing the runtime root, without the owning repository's lifecycle lock or the job's supervisor lock; a racing owner writes the same content, so the race is benign), and CP3 confirms that `validate_record` accepts the `usage` block and the `accounting` key on a terminal record, because `resume` reports a record that fails validation as `malformed`.
  **Where it runs.** At the start of `_execute_step_locked` before the gate (so a missing charge is settled before the next admission relies on it), on a `usage` read, and in `resume` **twice: at its start, and again after phase 2's reconciliation** so the records that very call made terminal are settled before they are reported. The sweep is idempotent because `complete` is a no-op for a token in `settled`: a crash after the terminal write and before accounting, a crash between the `COMPLETED` write and the terminal write, a crash between the shared-record write and the `"done"` flag, a crash during the sweep, and a second sweep each charge exactly once.
  **Dispatch, with no re-charging fallback.** `resume`'s dispatch over a terminal record whose `accounting` is not `"done"` does the following. If its token is in `settled`, it sets `accounting: "done"` and charges nothing. If its reservation or lapsed entry is still present, the sweep above settles it. If it has **neither** a reservation **nor** a `settled` entry, it is a recorded no-op (event `usage_accounting_orphan`, record untouched apart from `accounting: "done"`): that state arises when `usage.json` was lost, or after a `not_started` release (which deliberately writes no `settled` marker, so an orphan does not imply a lost `usage.json`), since every other way a reservation leaves the shared record writes `settled`; and if the `settled` entry has since been pruned (90 days) the record is not charged either: it takes this same no-op, though nothing guarantees an earlier dispatch marked it `"done"` (`settle_pending` walks reservations, and the `complete` that preceded the crash removed it). Nothing is ever charged from a record's block alone, so a pruned `settled` entry can never produce a second charge.
  **Deltas.** `delta = "measured"` when the start and end readings are the same window (D2) and the end reading is *newer*: `observed_at` strictly after the reservation's `created_at` (revision 4, review Important 2); then `five_hour = max(0, end - start)` and `weekly` likewise, and `charged = five_hour`. **A missing end reading, or one no newer than the start, is an unknown delta, not a zero**: `delta = "unknown"`, `five_hour`/`weekly = None`, and `charged = reserved_five_hour`, i.e. at least the forecast. This covers a manual Claude worker (nothing has refreshed the Claude reading when `usage --release` runs) and a Controller job whose stream carries no `rate_limit_event`; it keeps manual Claude work from being free under every cap. When a reset lies between start and end, `delta = "after_reset"`, `five_hour_after_reset = end` (consumption since the reset, a lower bound) and `charged = max(five_hour_after_reset, reserved_five_hour)`. Never zero for an unmeasured job. An `unknown`, `after_reset` or `abandoned` entry is **excluded from the forecast mean** (its figures are `None`), so manual roles keep the provider default until a measured entry exists. For a `stream-json` manual worker the operator can supply the reading: `usage --release TOKEN --stream PATH` reads the worker's stream with the Claude reader (first event for the start comparison, last for the end), which makes the delta measured. The job record's `usage` block is **written at record creation** with the start figures, so the baseline survives without the token: `{token, provider, role, model, repository, run_id, started_at, window_resets_at, five_hour_start, weekly_start, reserved_five_hour, reserved_weekly, accounting: "open"}`, and extended in the terminal write with `{five_hour_end, weekly_end, end_window_resets_at, five_hour, weekly, five_hour_after_reset, weekly_after_reset, charged, delta, accounting: "pending"}` (the same names and meanings as the ledger entry), then `accounting: "done"`.
  **Spend.** A completion adds one *run charge*, `charged`, to `spend.run[provider][run_id]` (never window-scoped, so a run cap survives resets and ledger eviction), and one *repository charge* to the total of the window it ended in: `charged` when `start_window_resets_at` is that window (same window within `WINDOW_JITTER_SECONDS`); otherwise (the job began in an earlier window) its `five_hour_after_reset`, **not floored at the forecast** (what the job is known to have consumed inside this window; deliberately a lower bound: a live reservation rolled into the current window counts its full `five_hour.amount` in `repository_outstanding`, so the repository cap's view can fall when it completes and is charged only that unfloored figure; this is the documented lower bound and must not be "fixed" into a floor), or `reserved_five_hour` when that is `None` (an `unknown` delta that began earlier cannot be placed, so the forecast stands in). A job spanning the boundary is thus neither dropped nor double counted. Repository spend read at time `now` is the stored `charged` when its `window_resets_at` is in the future, else 0. **Forecast** for `(provider, role, model)` is the mean of `five_hour` (and, separately, `weekly`) of the last 20 `ledger` entries, ignoring `None` (so `unknown`, `after_reset` and `abandoned` entries never enter it), else the provider's default setting. Both providers get history from the ledger; Codex entries exist only where a manual worker released a token (`usage --release`), so until C7 a Codex forecast is the default plus whatever manual releases recorded. Concurrent lanes inflate a measured delta, which errs on the safe side.
- **D7. Where the gate runs; a pause re-decides through the full boundary (revision 3, review Important 7).** `job.execute_step` gets a `usage_gate=None` argument, a callable `(route) -> UsageHold | token | None`, called in `_execute_step_locked` after the route is resolved and the decision made, **before** the job record is created, so a hold leaves no `PLANNED` record and nothing for `resume` to reconcile. On `go` the gate returns the reservation token, which `execute_step` writes into the job record's `usage` block when it creates the record; if the record is never created (a refusal after admission) `execute_step` releases the token with `not_started`. A hold **never waits inside `execute_step`**: the decision and `pre_state` were taken before the gate, and hours later the operator, a merged PR or a moved origin may have changed the repository. `execute_step` returns a new frozen dataclass `UsageHold` (`provider`, `window`, `percent`, `forecast`, `resume_at`, `reason`, `waitable`) as a third member of its return union (`JobRecord | Decision | UsageHold`), and its `with` block releases the lifecycle lock on the way out.
  The wait is `cli._run_steps`'s. `_run_one_step` returns `(EXIT_USAGE_PAUSED, hold)` for a `UsageHold`. In `_run_steps`, when `hold.waitable` and the cumulative wait for this step is within `usage.max_wait_seconds`: emit the run event `usage_paused`, sleep in short interruptible slices (Ctrl-C works, as the merge wait does) with **no lock held**, and **`continue` the loop without incrementing `steps_run`**. `usage_resumed` is **not** emitted at wake-up (revision 6, review Optional 2): the gate builder in `cli.py` emits it only when the re-entered boundary's fresh admission returns `go` after an earlier hold in this run, so a wake-up followed by another hold, a handoff exit or a changed decision never announces resumed execution. The next iteration therefore runs the whole boundary again: `_await_pause_file`, then `_run_one_step`, whose `handoff.detect` check runs first (a generation installed during the wait is detected and exits 50 instead of starting a job), then the lock, the fresh state and a fresh decision, then a fresh admission against fresh readings. A held attempt consumes no step allowance, so `run --max-steps 1` that pauses once still performs its one step after the wait; a second hold on the same step accumulates against the same `max_wait_seconds` budget and stops with exit 17 when it is exhausted. On a longer wait, on a cap (`waitable=False`), or for the single `step` command, `_run_one_step`'s exit 17 stands, with the `usage_paused` event and a one-line stderr message naming the resume time in local time as well as the epoch (and, for a cap, the cap-specific guidance of D10); nothing is started. Branch preflight (close-out, branch switch, merge wait) runs before the gate; so a hold after a preflight action is not silent, the `usage_paused` run event carries `preflight_events` (the preflight's own events for that attempt). `usage.enabled=false` makes the gate a no-op. The settings values are recorded in the job's `controller_settings` block like the others.
- **D8. `usage` subcommand and the manual-worker gate (revision 3, review Important 5 and 6).** `workflow-controller usage [--provider claude|codex|all] [--json] [--check | --wait] [--reserve] [--role R] [--model M] [--repo PATH] [--run-id ID] [--renew TOKEN] [--release TOKEN [--outcome ok|not_started] [--stream PATH]]`. This line is the single source for the argparse and `--json` pins in CP4. Without flags it prints each window's percent, reset time, reading age, live reservations and the forecast per `(provider, role, model)` in the ledger. The manual gate has the context it needs from arguments: `--provider` (default `claude`), `--role`/`--model` select the forecast (else the provider default), `--repo` selects the repository cap and spend (`--repo` absent: the repository cap is not evaluated and the output says so), `--run-id` selects run spend (absent: the run cap is not evaluated). The account windows and both reservations are always evaluated. Claude and Codex use their own caps (D4).
  `--check` evaluates D5 once and exits 17 on a hold, else 0; it reserves nothing unless `--reserve` is given. `--wait` is a loop (revision 3, Important 6): on a waitable hold it emits `usage_paused` to the usage event log, sleeps in slices to the resume time plus `usage.resume_grace_seconds`, re-reads the readings and **re-evaluates**; it exits 0 only when the re-evaluation is `go` (and, with `--reserve`, only after the reservation is written in the same critical section, printing the token on stdout), and otherwise waits again, the whole loop bounded by `usage.max_wait_seconds` counted from the start, after which it exits 17. A cap exits 17 immediately and says so. On success, after the final admission or evaluation returns `go`, it emits `usage_resumed` (never before: a wake-up that is held again emits only another `usage_paused`). `--release TOKEN [--stream PATH]` calls `usage.complete` with the readings at that moment (or, with `--stream`, the worker stream's readings), recording the manual worker's delta and spend in the ledger as D6 defines (a Claude release with no newer reading is an `unknown` delta, charged at least the forecast), emits `usage_released`, and is idempotent and works on an expired token while it is `lapsed`; `--renew TOKEN` extends a live reservation, revives a `lapsed` one (re-basing its windows, D6), and otherwise exits 1 with the message D6 names for an unknown or settled token; a token never released lapses (D6). The lane scripts that replace `usage-gate.sh` call `usage --wait --reserve`, run the worker, then `usage --release`. `usage` is read-only apart from the shared record. Output gives every resume time in local time as well as the epoch.
  **Durable events for manual waits.** `usage_paused`, `usage_resumed`, `usage_released` and `usage_reservation_expired` are appended as JSON lines (`{event, at, provider, window, percent, forecast, resume_at, reason, token, repository, run_id}`) to `<runtime_root>/usage-events.jsonl` through a `runtime` append primitive, so a manual-worker wait leaves an auditable record C5 can subscribe to without a run. Run waits write the same events into the run's own log (D7) and to the same file.

## Risks

- **Reading freshness.** A Claude reading comes from the newest Controller job's stream; with no recent Controller job the figure is a lower bound (outside work is unseen) until the next job. `usage` prints the age, and the guide says so. This is the same limit `usage-lib.sh` had; it is not made worse.
- **Delta inflated by concurrency.** A measured `five_hour` includes other lanes' use during the job. It errs towards pausing earlier, the safe direction, and the defaults and caps are settings.
- **Reservations leak on a crash.** An abandoned reservation holds account headroom until `usage.reservation_seconds` (default 2 h) passes without a renewal; it lapses on the next read, with an event, and keeps weighing on its run and repository caps until settled or, after 7 days, abandoned at its forecast. A live job renews its lease on a timer of `job.py`'s own (D6), so a long job is no longer at risk from a short value, but a job drained after its supervisor detached is not renewed and lapses (accepted, D6); the value now only sets how fast a crashed holder's headroom is freed.
- **Fail-open on missing data.** No reading means no account pause (caps still apply). A fresh machine runs; the first job's stream produces the first reading.
- **Lock released across a wait.** A paused `run` holds no lifecycle lock during the wait (up to `max_wait_seconds`, 6 h), so that the step can re-read and decide again; another `run` or the operator may act meanwhile, and the re-entered step, passing through the handoff check and a fresh decision, sees the result. The merge wait differs only in holding the lock because it polls inside the preflight.
- **Codex file format.** Read from a format Codex does not promise. Every missing or odd field is "no reading", never an error, and the reader is tested on synthetic files so a format change cannot fail CI; it only degrades to no Codex account check (Codex caps, fed by manual releases, still hold).
- **Settings generation 4 on a shared file.** The shared pipx install is 1.7.1 until the Manager gap; it ignores the new rows with the existing warning once, which is the designed behaviour.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10). The declaration is C9d's reviewed classification with this item's ids; every path the checkpoints name is classified at both stages: `controller/`, `tests/`, `tools/`, `docs/guide/`, `docs/adr/` are protected prefixes and `docs/exit-codes.md` and `docs/common-problems.md` are protected by exact path. `docs/ROADMAP.md` is explicitly excluded at both stages, and CP5 edits it.
