## Goal

The usage budget (C8, 1.8.0) forecasts a job's cost and refuses to start one that would not fit. A forecast can be wrong, and other workers share the account, so a job can still reach the limit while it runs. Today such a job ends `FAILED` with a `TransitionNotObservedError` and the run stops with exit 30. Two real streams from 2026-09-24 show it: a plan-review job (phase unchanged, `AWAITING_LOCAL_PLAN_REVIEW`) and a sixteen-minute implementation job (phase unchanged, `IMPLEMENTING`) each end in a `rate_limit_event` with `status: "rejected"`, a synthetic `assistant` message with `error: "rate_limit"` and a `result` with `is_error: true` and `api_error_status: 429`. Nothing the operator did was wrong; the right behaviour is to wait for the window to reset and repeat the step.

After this milestone:

- the worker stream shows the limit as a structured fact, with the window's reset time, never from the message text;
- a job that ended on the limit and verifiably moved nothing (no phase change, no new commit, no new tracked edit) is recorded `INTERRUPTED` with the limit named, not `FAILED`, so a fresh `step` repeats it;
- `run` waits for the reset plus `usage.resume_grace_seconds` (the pause of C8: no lock held, `usage_paused` recorded, bounded by `usage.max_wait_seconds`), then repeats the step, and `step` and `resume` report it with exit 17 and exit 40 respectively and name the reset time;
- the first job after a window reset is measured, closing the follow-up from the C8 review.

Out of scope: per-repository caps and per-lane budgets (C8c); a limit of a provider other than Claude (the Codex reviewer already ends `INCOMPLETE` at its own limit, exit 35, C7); a limit reached while a job's work is half committed (D5 keeps that `FAILED`); any change to the forecast.

## Decisions

- **D1. The fact is read from the stream's structured fields.** `controller/worker_stream.py` records a *usage limit* when the stream holds all three of: a `rate_limit_event` whose `rate_limit_info.status` is `"rejected"`, a terminal `result` with `is_error: true` and `api_error_status: 429`, and (the reset) a finite `resetsAt`, taken in the order `usage._claude_event_readings` uses: `unifiedWindows[rateLimitType].resetsAt` first, the event's own `rate_limit_info.resetsAt` only when that window is missing (C8B-R2-004). The parse reuses `usage._CLAUDE_WINDOW_KEYS` and that order, so the Controller's two stream readers cannot disagree for a mapped type; `_claude_event_readings` builds a rejected reading only when `rateLimitType` maps, so for an unmapped type `worker_stream` reads the event's own `resetsAt` itself (there is no `unifiedWindows` key to look up). The text `"You've hit your session limit"` is never matched, because it is localised and rewordable. The fact is `{"resets_at", "rate_limit_type", "window"}`, where `window` is the C8 name (`five_hour` or `weekly`: Claude's `seven_day` maps to `weekly`); an unmapped `rateLimitType` gives `window: null` and the fact still stands (the reset time is what the wait needs), and the hold then names the window as `unknown` and rides in the existing `worker.stream_diagnosis` as `usage_limit` (`null` otherwise), so a record written before this milestone has none. A stream with only some of the three (a 429 without a rejected event, an `allowed_warning` event alone, a rejected event with a successful result) has no fact: it stays an ordinary failure.
- **D2. The worker outcome does not change; the reason sits above `exit_status`.** `classify` still returns `FAILURE`; the diagnosis `reason` becomes `usage_limit`, a new member of the reason set placed **after the timeout and signal rows and before the `exit_status` row** (C8B-R1-003). The real workers of 2026-09-24 exit with status 1 (`worker.exit_code` in both records), so a row below `exit_status` would never be the primary reason; the timeout and signal rows keep their precedence because those outcomes are `INTERRUPTED`. The fact itself is independent of the reason (it is kept in the diagnosis whichever reason is primary), and every later decision keys on the fact, never on the reason. `_VERIFYING_WORKER_OUTCOMES` and `_KNOWN_WORKER_OUTCOMES` are unchanged, so no code that is closed over the four outcomes needs a fifth.
- **D3. A limited job that verifiably moved nothing is `INTERRUPTED`.** `INTERRUPTED` already means "no observed reality is verified; a fresh `step` may retry" and is not terminal for the run's purposes, so no new job status is added (the ten-member enumeration, `TERMINAL_STATUSES`, the schema checks and the observation views stay as they are). The record gains `usage_limit` (the D1 fact) and `reconciliation_evidence` with the new code `UsageLimitReached`. "Moved nothing" is the same three-part test in both modes (C8B-R1-001, -004): the observed phase equals the pre-phase, `HEAD` equals `pre_state.target_head`, and the tracked-change list equals the one captured at launch (D10). In protocol mode (`_protocol_resolution`) a `FAILURE` worker whose diagnosis carries the fact is no longer rejected before `reconcile`: `reconcile` runs, and the job is `INTERRUPTED` only when `reconcile` answers `no_progress` **and** the `HEAD` and tracked-change clauses hold. `reconcile`'s `no_progress` does not look at `HEAD` or the tree (`scripts/workflow_protocol.py` `reconcile` answers it whenever the phase is unchanged and there is no same-phase proof), so the Controller adds those two clauses itself; a `no_progress` with a moved `HEAD` or a changed tree is D5's `FAILED`. Any other `reconcile` answer resolves exactly as a failed worker does today. The same rule applies in `resume` (`_reconcile_protocol`). In legacy mode (Workflow 2.5.1 and 2.6.0: `execute_step` step 8 and `_reconcile_completed`) the helper applies when verification failed and the three clauses hold, which is `_reconcile_launched`'s existing phase-and-`HEAD` test plus the tree clause.
- **D4. A limited `FAILURE` worker is never `FINISHED`; this is chosen, not inherited** (C8B-R1-002). Today `_verify_transition` and `_protocol_resolution` return `worker_outcome` for any outcome outside `_VERIFYING_WORKER_OUTCOMES = {SUCCESS, INTERRUPTED}` before they look at the transition, and D2 keeps that set unchanged, so a worker that wrote the state transition and then hit the limit in its closing summary turn is `FAILED` with `usage_limit` in the evidence (D5), not `FINISHED`. Admitting a limited `FAILURE` worker to verification (option (a) of the review) would widen a set the rest of the Controller is closed over; the case is rare, and recovering it is C12's (self-recovery). The fact stays in the diagnosis, and the next admission sees the limit through the usage reading, as in C8.
- **D5. Everything but a verified no-op stays `FAILED`, with the limit named.** A limited job that is not D3's no-op (the phase changed, `HEAD` moved, a tracked file differs from the launch baseline, or the worker outcome is outside the verifying set with a transition possibly written, D4) is `FAILED` as today, and its `reconciliation_evidence` gains `usage_limit` so `explain` and the exit-30 message can say the worker stopped at the usage limit. Repeating a step over unverified commits or half-edited files is the Workflow's judgement and C12's, not this milestone's. The honest consequence is that C8b recovers the cases where the limit hit before the worker changed anything durable, which the plan-review sample and most limit hits at a step's start are; the sixteen-minute implementation sample most likely left uncommitted edits (`workflow-manager` has no commit in that window) and would stay `FAILED` under the tree clause.
- **D6. The wait reuses C8's pause.** After an `INTERRUPTED` job with the fact, `run` builds a `UsageHold` (provider `claude`, `window` the rate-limit type, `percent` 100, `forecast` 0.0, `resume_at` the fact's `resets_at`, `waitable` true, a `reason` naming the job; `window` is D1's, `unknown` when unmapped) and calls `_usage_wait`, whatever `usage.enabled` says, because the wait must hold when the budget is off. The wait is the reset plus `usage.resume_grace_seconds`, bounded by `usage.max_wait_seconds`. `_usage_wait` today prints `usage_hold_message` itself in its over-bound and non-waitable branches (C8B-R2-003), a text that says "nothing was started", which is false for a job that ran; CP3 therefore adds a `UsageHold` field `mid_job` (default false, set by `_run_steps` here) that `_usage_wait` reads to print the D7a bound line instead, and `usage_hold_message` is unchanged for every hold that has it false. `_usage_paused` records `usage_paused` in the run's log and `usage-events.jsonl` and the notification fires as for C8. The step is repeated through the whole orchestration boundary (pause file, handoff check, lock, fresh state, a fresh decision and a fresh admission), and the interrupted attempt consumes no step of `run.max_steps`.
- **D7. A limit that keeps repeating stops the run.** Three consecutive limit-interrupted jobs of one `run` with no finished step between stop it with exit 17, so a stale `resetsAt` (a clock that is ahead, a reading the provider never advances) cannot spin. The counter is reset by any finished step.
- **D7a. The two stop lines** (C8B-R1-006), both starting `workflow-controller: stopped at the usage limit reached mid-job: the worker ran and changed nothing, so the step can be repeated` and then: for the over-bound wait, ` -- the reset is at <local time> and waiting for it would exceed usage.max_wait_seconds (<n> s); run again after it`; for the third attempt, ` -- the last three attempts all reached the limit, so the reset time the provider reports is not trusted; check the clock and the usage reading, then run again`. `usage_hold_message` is unchanged for jobs that never started.
- **D8. Exit codes: no new code.** `step` returns 17 for an `INTERRUPTED` job with the fact and prints one line (never "nothing was started"): the job reached the usage limit, the step changed nothing, the reset time, and that a new `step` or `run` repeats it. An `INTERRUPTED` job **without** the fact (a timed-out or signalled worker that `reconcile` calls `no_progress`, which `execute_step` can already return in protocol mode and `_run_one_step`'s table has no entry for, C8B-R1-008) maps to exit 40, the code `resume` uses for the same status, with a line naming the job and that a new `step` repeats it. The 17 row of `docs/exit-codes.md` is widened from "nothing was started" to also cover a limit reached mid-job, with its fix, the 40 row (which names only `resume` today) is widened to name `step` and its remedy, a new `step`, and the `EXIT_USAGE_PAUSED` comment in `controller/cli.py` ("Nothing was started") is widened the same way (C8B-R2-005). `resume` keeps exit 40 for a record it reconciled to `INTERRUPTED` and its message names the reset when the record carries the fact. Open to the reviewers: a distinct code (18) was considered and rejected because every script that already handles 17 ("wait, then run again") is right for this case too.
- **D9. The first job after a reset is measured (the C8 review follow-up).** `usage._component` stores an expired stored reading with `start` 0.0 (`window_percent` returns 0 after a reset) but the **old** `window_resets_at`. A job admitted after the reset, whose end reading is from the new window, therefore has `end_resets > start_resets` and is not the same window, so `_window_delta` returns `after_reset`, not `unknown`, and the charge is `max(after, reserved_five)`, not the bare forecast (C8B-R1-005). CP4 reproduces exactly that on the unchanged code (`after_reset`, charged `max(after, reserved_five)`, no forecast sample), then baselines the new window from the first reading the job's stream shows (`stream_start`, already passed to `complete`). In `complete` that reading is used as `lower_start` only when it is in the same window as the baseline, so the fix replaces **both** `start` and `start_resets` (the baseline's stored `window_resets_at`) with the first reading's `percent` and `resets_at` when that reading is in a later window than the baseline **and the baseline had already expired when the reservation was created** (`baseline[window]["window_resets_at"] <= reservation["created_at"]`, C8B-R3-002), and the delta is then `measured` from it (C8B-R2-002). The guard is the admission-time distinction: a job admitted **before** the reset (baseline still live at `created_at`) whose first stream reading arrives after it is a job that spanned the reset, and it keeps today's accounting unchanged (`after_reset`, charged `max(after, reserved_five)`, no forecast sample), because its pre-reset consumption is unobserved and a rebase to the first new-window reading would charge it 0 for an 8% reservation; the existing scenario `test_a_five_hour_reset_while_the_worker_runs_rolls_over_and_completes_after_reset` (`tests/test_usage_gate.py`) stays green unchanged. The required measured result: for a stream whose first new-window reading is p0 and last is p1, the delta is `p1 - p0`. If the fix needs a change to the ledger or reservation schema, it is not made here: the follow-up stays on the roadmap with the finding recorded, and CP4 ships its reproducing test as an expected-failure note instead.
- **D10. One additive pre-state field: a content-sensitive tracked-change baseline** (C8B-R2-001). The tree clause of D3 needs the state of the tracked tree at launch, because a dirty tree is the normal case (the plan stage never commits: `WORKFLOW_STATE.json` is ` M` for the whole stage, and the plan files are ` M` or ` A` while unstaged or intent-to-add). A list of `git status` entries cannot see a second edit of a file that is already dirty, and neither can worktree bytes see a change of the **index** (partial staging leaves status `AM` and the worktree bytes identical while the staged blob changes, C8B-R3-001), and a `chmod` changes neither the status entry, the bytes nor the index while Git reports a mode change (EXT-C8B-003), so the baseline is a mapping `{path: record}` over `gitrepo.tracked_changes` (`--untracked-files=no`): for each changed tracked path, the status entry, the sha256 of the worktree bytes (a deleted path, a fixed marker string), the worktree executable bit (`lstat` `st_mode & S_IXUSR`, the one mode bit Git tracks for a regular file; a deleted path, a fixed marker) and the path's staged identity, its index mode and blob id as `git ls-files --stage -z` reports them (an intent-to-add entry reports the empty blob, so a later real staging differs). The digests and index state are computed by a new `gitrepo.tracked_change_digests(repo_root)` that reads the worktree files itself (no `git hash-object`) and makes one additional read-only `git ls-files --stage -z` call (no hook, filter or textconv runs and nothing under `.git` is written). A changed tracked path the baseline cannot distinguish (a symlink, a path whose `lstat` fails, a submodule or a directory in the worktree, or a path with an unmerged index stage) makes the baseline not comparable, so the clause fails closed for it. `_capture_pre_state` records it as the new member `tracked_changes` of `PRE_STATE_FIELDS`, the single declaration the record-completeness property reads, and the clause holds only when the path set, every status entry, every worktree digest, every worktree executable bit **and** every staged identity match at the end. A record without the member (written before this milestone) or with one that is not a mapping is not comparable, so the clause fails closed: such a job is `FAILED` with the limit named, never `INTERRUPTED`. No other schema changes.
- **D11. Nothing about the settings file changes.** `usage.resume_grace_seconds` and `usage.max_wait_seconds` already exist; no setting is added, so `TABLE_GENERATION` stays.

## Risks

- **A wrong `resetsAt`.** The reset comes from the provider's own event; D7 bounds the repeats and `usage.max_wait_seconds` bounds each wait, so a bad value costs at most three waits and then exits 17.
- **Repeating a step the worker half did.** D3 and D5 repeat only a job that verifiably changed nothing: `reconcile`'s `no_progress` is necessary but, as it ignores `HEAD` and the tree, not sufficient, so the Controller adds the `HEAD` and content-sensitive tracked-change clauses (D10) itself in both modes, which also protects the plan stage, where the files are dirty throughout. Changing `reconcile` is not this milestone's.
- **The plan-review and implementation samples differ.** The plan-review sample is the clean case; the implementation sample is the case D5 leaves `FAILED` when it committed or left tracked edits (most likely). The roadmap's own text promised both; this plan states the narrower claim and why, for the owner to confirm.
- **`classify` has many callers.** Only the diagnosis and the reason change, and the golden comparison tests for the other stream goldens run in CP1.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10). The declaration is the previous milestone's reviewed classification with this item's ids, adjusted for the pages this milestone edits (`docs/exit-codes.md`, `docs/common-problems.md`, `docs/run.md`); every path the checkpoints name is classified at both stages, and `docs/ROADMAP.md` and `docs/ACTIVE_MILESTONE.md` are excluded by exact path at both stages for the reason recorded in the C12a plan's Risks (review R3-O2).
