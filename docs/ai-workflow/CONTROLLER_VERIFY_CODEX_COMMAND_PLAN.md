## Goal

C10g-3 will launch a Codex tester only on a build somebody verified. C10g-2a built the digest and the record; C10g-1 built the sandbox and its boundary probes but only as opt-in tests. This item adds the operator command that joins them: `workflow-controller verify-codex` runs the C10g-1 probes against the Codex build a launch would run and, only when every probe holds and the build did not change meanwhile, records its digest. Nothing launches on the record yet: no role is declared, `HarnessAdapter.build_verification` for `codex` stays `None`, the Codex reviewer never consults the record, and `verify-claude`, its record and its tests are unchanged.

## What exists

- `controller/codex_build.py` (C10g-2a): `build_digest(binary)`, `read_verified`, `record_verified`, `is_verified(runtime_root, binary)` returning `Verified(ok, digest, reason)`, and the record `verified-codex-builds.json`.
- `controller/codex_sandbox.py` (C10g-1): `build(...)` writes one tester job (home with the credential copy, `config.toml`, scratch, stand-in launchers) and returns `Built(layout, config_text, roots, argv, environment)`; `check_launch` runs the pre-launch controls; `probe_command`, `probe_prompt`, `judge` and `sandbox_probe_argv` are the probes. `tests/test_codex_sandbox_live.py` runs them opt-in (`CONTROLLER_LIVE_CODEX_TESTS=1`), with its own host fixtures.
- `cmd_verify_claude` in `controller/cli.py` and `controller/claude_build.py`: the shape this command mirrors (resolve, digest, "already admitted" unless `--force`, probe, record, exit 20 on a refusal).

## Decisions

Each decision states one principle.

- **D1. The command verifies the build a launch would run, and says when that is not the one named.** `verify-codex [--force] [--codex-binary PATH]`. The binary is `review.resolve_binary(PATH or "codex")` (a launcher symlink is kept, because its directory holds the interpreter); `--codex-binary` is local to this subcommand, so the global options are unchanged. As `verify-claude` does, it prints the path and the digest, and a note when the `codex` on `PATH` (what a launch finds) differs from the one named or is absent. "Differs" compares the launcher paths lexically, as `review.resolve_binary` returns them (a kept symlink is not resolved for this comparison); the digests of both are not compared, because the digest is of the named build only. A binary whose layout `codex_build.build_digest` cannot bind is a refusal that says so and records nothing.
- **D2. A digest already recorded is not probed again.** The command asks `codex_build.is_verified(runtime_root, binary)` once. A recorded digest prints "already verified ... not probed (--force probes again)" and exits 0; a record that was ignored prints the reason as a note and the build is probed. Verify-on-first-use is this cache and nothing else: no launch calls it (C10g-3).
- **D3. The digest is taken before the first run and after the last, and a change records nothing.** Every probe executes the launcher path the launch would, not a resolved copy. The digest is recomputed from that path after the last probe; a different value is the refusal `build_changed`, which catches a re-pointed symlink and a rewritten file alike. The digest recorded is the one taken before.
- **D4. There are two probes, they are C10g-1's, and they are run in the order of cost.** `sandbox` runs `codex sandbox -P tester` (no model, no spend) through `codex_sandbox.sandbox_probe_argv`; `exec` runs `codex exec` under the same profile for one short turn (a model, the operator's Codex credentials) with `Built.argv`. Each runs in its own fresh job (D5) and both run the one `probe_command` and are judged by `codex_sandbox.judge`; `check_launch` runs before each. `exec` runs only when `sandbox` held. The command redefines no probe and no judgement. Its help states the cost, and that the usage budget is not consulted.
- **D5. A boundary can be proved held only if the host could have been reached, so the host fixtures sit where the sandbox could otherwise see them, and each probe stands on evidence of its own.** Each probe runs in its own fresh job (`codex_sandbox.build` with its own job id: its own clone with one commit, scratch area, stand-in launchers and logs, and a fresh snapshot of its own bare origin), as the C10g-1 live test does (`sandbox1`, `exec1`); no positive check of D6 reads evidence a previous probe left. One short private folder (from `functional_review.short_tmp_roots()`, first root where `s.sock` is at most `SOCKET_PATH_LIMIT` bytes) holds the host Unix listener's socket and the bare push origins, and is passed as the single `extra_readable` root. A TCP listener on 127.0.0.1 and the Unix listener count connections; one connection is a failure. The canary file, the stand-in home and the sibling path live in the job folder, outside the clone, the scratch area and every readable root; the canary environment variable is set in the inherited environment and is not in the allowlist.
- **D6. The host checks read bytes and listings and run no git on a tree the sandboxed run could have written.** Git is used only before the run, with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` at `/dev/null`, to make the clone (one commit) and the bare origin. After each run the command compares a snapshot of the clone and of the origin with the one taken before. The snapshot lists every entry, directories included, as relative path to its type and, for a regular file, its SHA-256 and, for a symlink, its target text; it never follows a symlink and never opens a FIFO, socket or device, so it terminates on a tree the run planted anything in, and a created empty directory is a difference. It also checks that the probe's new-file, sibling, stand-in-home and `/tmp` and `/var/tmp` marker paths do not exist, that the scratch write happened, that the stand-in `gh` logged its call, and that no listener saw a connection. Any difference is a failure naming the path.
- **D7. Every way the probes cannot decide is its own named refusal, and none is a recorded pass.** All are `ControllerError`s (exit 20) carrying the probe name: `identity` (no digest), `host` (no `codex` or `bwrap`, no short folder, a fixture that cannot be prepared), `credentials` (no `auth.json` in the operator's Codex home, `$CODEX_HOME` else `~/.codex`), `launch_controls` (a `check_launch` refusal, with its text), `sandbox` or `exec` (a judged failure, naming each failing probe line), `model_unreachable` (the `exec` turn failed with a login, credit, limit or timeout cause, or returned no output: the build is neither verified nor shown broken, run again), `exec_failed` (the `exec` turn exited non-zero for any other cause: the message says it is an `exec` failure and carries the exit code and the tail of stderr; the cause is read from the exit code and the stderr text by one private function of the module, which reuses the reviewer's limit markers, `review.LIMIT_ERRORS`, rather than a second list), and `build_changed`. Nothing is recorded for any of them.
- **D8. The credential copy is returned and removed.** `codex_sandbox.build` writes a private writable copy of the operator's `auth.json` through `review.build_home` and discards its digest, so the run hashes that copy right after `build` returns. After each probe's run, also after a failed or timed-out one, it calls `review.copy_back_credentials(layout.job, operator_home, digest)` under the reviewer's lock (`<runtime>/reviews/codex-auth.lock`), so a token refreshed during the `exec` turn is not lost; an operator file that changed meanwhile is never overwritten (the call's `operator-changed` result). The outcome is printed. The job folder holding the credential copy is then removed, also after a refusal, and no credential copy remains under the runtime root.
- **D9. The record entry is the same shape as `verify-claude`'s.** `{"version", "verified_at", "controller_version", "probes": {"sandbox": "pass", "exec": "pass"}}`, written with `codex_build.record_verified`; a record that cannot be written (a symlink, an `OSError`) is exit 20, never a traceback. `version` is `codex --version` run in the job environment. The settings file is never read for a digest, written, created or filled: the command joins `SETTINGS_READ_ONLY_COMMANDS`, and `ALL_COMMANDS`.
- **D10. The harness declaration does not change in this slice.** `HarnessAdapter.build_verification` for `codex` stays `None` because nothing at launch consults the record until C10g-3 declares the tester role. The comment in `controller/harness.py` that says `verify-codex` "then changes this one value" is corrected to say that C10g-3 changes it. The Codex reviewer's pinned version and its checks are untouched.

## Functional review

Every flow is offline and unit-level, run one module at a time (`tests.test_codex_verify`, `tests.test_codex_verify_command`, `tests.test_harness_table`, `tests.test_package_structure`), plus `python3 -B tools/check_docs.py`. There is at most one live flow, operator-run and marked environment-limited: `CONTROLLER_LIVE_CODEX_TESTS=1 python3 -m unittest tests.test_verify_codex_live`, which needs the real `codex`, `bwrap` and an `auth.json`, and spends one short model turn. The full suite is not a flow.

## Risks

- **The host folder under `/tmp`.** Codex refuses to create its helper binaries under `/tmp` (C10g-1). The host folder is only a readable root, and `$XDG_RUNTIME_DIR` comes first; the live flow decides, and a refusal is a `host` refusal that names the root, not a pass.
- **A snapshot difference that is benign.** The probe command runs one `git push` inside the sandbox. If the live flow shows git touching a file in the clone's `.git` on a refused push, that file is named and excluded in this item, with the reason; a boundary failure is never excluded.
- **A Codex release the C10g-1 launch controls refuse.** `check_launch` reuses the reviewer's feature and layer checks, so an unknown feature set is a `launch_controls` refusal with its text; the pinned reviewer version is not widened here.
- **The window between verification and launch.** A build replaced after the record is written runs unverified; the record defends against the sandboxed tester, which cannot write the install tree, as `verify-claude` does.
- **Out of scope:** declaring the tester role, the launch wiring, `check_effective` and the fallback (C10g-3); the Codex worker (H4a to H4g); any change to the digest, the record or the C10g-1 probes.
