## Goal

A first try at moving this repository to Workflow 2.9.0 (PR #30, a plain `workflow-manager --release-version 2.9.0 update .`, closed) failed CI in `tests/test_workflow_releases.py`, class `InstalledReleaseTest`:

- `test_the_installed_release_is_admitted` requires the installed release to be in `managed_repo.VALIDATED_WORKFLOW_RELEASES` (`{2.5.1, 2.6.0}`). A protocol-mode release (2.7.0 and later) is admitted by capability, never by that set (ADR 0010), so it can never pass.
- `test_the_installed_files_equal_the_vendored_tree` requires `tests/workflow_releases/<installed release>/`. Only 2.5.1, 2.6.0 and 2.7.0 are vendored.

After this milestone, a scratch copy of this repository updated to 2.9.0 by Workflow Manager passes the whole suite, so the update can land as an ordinary `chore:` pull request straight after this one. This milestone prepares the move; it does not perform it (D3).

1. `tests/workflow_releases/2.9.0/` holds the vendored 2.9.0 tree, with a `RELEASE.json` whose hashes equal the published release.
2. `InstalledReleaseTest` admits the installed release when it is legacy-validated **or** it is a protocol release (its vendored tree ships `scripts/workflow_protocol.py`), and `tests/test_managed_repo.py`'s live-repository admission test (`test_real_workflow_manager_admits_this_repository`) makes the same distinction. The tree-equality test is unchanged.
3. The vendored 2.9.0 tree is runnable: installed into a disposable repository, the Controller admits it in protocol mode and its `verify` is healthy.
4. A scratch rehearsal of the real update, recorded as evidence, shows the suite green on the updated copy.

Out of scope: running the update on this repository (D3), any change to `VALIDATED_WORKFLOW_RELEASES` (the two admission tests are changed to accept a protocol release, the set is not expanded), `SUPPORTED_WORKFLOW_LINES` or the admission logic in `controller/` (2.9.0 is already admitted by capability, checked in C9b), Controller handling of the gate-policy, `validation` and `pr.apply_review` features (C10), vendoring 2.8.0 (not the move target), a release.

## Decisions

- **D1. Vendor from the published archive, with two more scripts.** `python3 tools/workflow_releases.py sync 2.9.0 --from <dir> --archive-sha256 <sha>` is the existing way to vendor a release unpacked from its archive (it records `archive-sha256:<sha>` as provenance, as for 2.7.0). `sync` reads `<dir>/<release>/manifest.json`, so `<dir>` is a scratch distribution directory whose `2.9.0/` child is the unpacked release: `sha256sum` the cached archive `~/.cache/workflow-manager/releases/2.9.0/workflow-2.9.0.tar.gz` against its `SHA256SUMS` entry, `0f0af156cef3eed7e7e2422d52d09abafff8dd469fec71f6ea7e0a333004905a` (which is `<sha>`), unpack **that archive** into a new empty directory `$T`, and rename its `workflow-2.9.0/` to `$T/2.9.0/`. Syncing from the unpacked archive (not the cache's `tree/`) is what makes the recorded `archive-sha256:<sha>` provenance describe the bytes actually read. A Manager checkout no longer carries `distribution/workflow`. The sync tool's vendored subset grows by `scripts/workflow_forge.py` and `scripts/workflow_gate_policy.py`, vendored when the manifest lists them and never required of an older release (the same rule as `PROTOCOL_PATHS`): from 2.8.0, `workflow_protocol.py` imports both at module level and `workflow_state.py` imports `workflow_gate_policy` at module level (and `workflow_forge` lazily), so a 2.9.0 tree without them could not be run (a smoke install of the current subset fails `protocol.describe` with `ModuleNotFoundError: No module named 'workflow_forge'`), and the protocol-mode install helper (`fixtures.install_workflow_release`) builds its `managed` map from the vendored files. 2.9.0 ships 22 command files (2.7.0: 17: 2.8.0 added `adopt-gate-policy`, `apply-pr-review` and `satisfy-gate`, 2.9.0 added `resume-implementation` and `retire-legacy-work-item`). Tests that say "seventeen" become per-release.
- **D2. Admission by capability in the installed-release test.** `test_the_installed_release_is_admitted` accepts a release in `VALIDATED_WORKFLOW_RELEASES`, or one whose vendored `RELEASE.json` lists `scripts/workflow_protocol.py` This predicate checks **only the listing**. The Controller's own capability test is stricter: the listing plus a `describe` answering protocol major 1 (`controller/managed_repo.py`, ADR 0010). Major 1 is therefore not part of the installed-release predicate; it is pinned per vendored protocol release by CP2's runnable-tree test, which installs every vendored tree that ships `scripts/workflow_protocol.py` (2.7.0 and 2.9.0) and asserts that `protocol.describe` supports major 1 and that `managed_repo.inspect` admits it. A later release vendored with a protocol script that does not support major 1 passes the installed-release test but fails that runnable-tree test, so it cannot be vendored unnoticed. The test never reads a version literal. The live-repository test `tests/test_managed_repo.py::CleanManagedRepositoryTest.test_real_workflow_manager_admits_this_repository` (round 2, I1) asserts `result.workflow_version in managed_repo.VALIDATED_WORKFLOW_RELEASES`; on a 2.9.0 installation `inspect` admits the repository in protocol mode and that assertion fails (`'2.9.0' not found in frozenset({'2.6.0', '2.5.1'})`). It is changed to the same rule: the result is legacy-validated, or `result.target_protocol` is not `None` (the `inspect` result field that is set only in protocol mode, `controller/managed_repo.py`). The `declared` equality, `profile == "full"` and the `verify`/`status` return-code assertions stay as they are, and `VALIDATED_WORKFLOW_RELEASES` is not expanded. A new test pins the rule from the other side: every vendored tree is a legacy-validated release or a protocol release, and a synthetic tree that is neither is not admitted. `managed_repo` is not edited.
- **D3. The update is a separate `chore:` pull request after acceptance, not a checkpoint.** Updating this repository changes `.claude/commands/`, `scripts/` and `docs/ai-workflow/*` (the installed Workflow) and `.workflow-manager/installation.json`. Doing that on the milestone branch would swap the Workflow's state scripts and commands under a work item that is bound to 2.6.0 between its approvals, which the milestone gates are there to prevent, and would widen every review bundle with the update's files. After this milestone is merged, `workflow-manager --release-version 2.9.0 update .` runs on a fresh branch from `main` with no work item active (no gate applies to it, as for PR #30), and its CI is the proof that this milestone worked. CP3's rehearsal does the same update in a scratch clone first. The roadmap (CP3 edits `docs/ROADMAP.md`'s C9c row and follow-up 15 to say the update is the next action after this milestone) and `docs/ACTIVE_MILESTONE.md` (written by the lifecycle commands, not a checkpoint) name the update as the next action.
- **D4. No behaviour change in `controller/`.** The milestone changes `tools/workflow_releases.py`, `tests/` (the new tree, the tests, one fixture docstring) two documentation pages and the roadmap row. `check_docs`, the full suite and `tools/workflow_releases.py check` must be green.

No "Open decision" row in `docs/TECHNICAL_DECISIONS.md` is touched: that document describes the Android application's prototype, not the Controller.

## Risks

- **A tree that cannot run.** Vendoring only the three legacy scripts plus the protocol pair would leave `workflow_forge` and `workflow_gate_policy` unimportable; D1 and R3 close this.
- **A later release adds another module.** The subset is explicit, so the next move fails `check` or R3's test rather than silently passing; the fix is another optional path.
- **Mid-update rehearsal drift.** The rehearsal uses the cached 2.9.0 package that `workflow-manager --version` (1.5.0) pins; a newer Workflow published before the real update is a different move target (the roadmap says "latest compatible"), so the update step re-checks the newest release first.
- **Artifact declaration.** The generator's default template classifies none of `controller/`, `tests/`, `tools/` or the `docs/*.md` pages (known follow-up 10). The declaration is C9b's reviewed classification with this item's ids and reasons, so every path the checkpoints name is classified at both stages: `tools/` and `tests/` and `docs/guide/` are protected prefixes here, `docs/compatibility.md` is protected by exact path.
