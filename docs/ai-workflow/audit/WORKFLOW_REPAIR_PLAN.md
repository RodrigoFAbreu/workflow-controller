# Workflow v2.x — Repair Plan

Repairs are clustered by **root cause**, not by symptom. Each repair
names the ledger rows it closes, the exact change, why it is bounded, and
what would make it a regression rather than a fix.

Non-goals, restated: no speculative hardening, no redesign, no weakening
of an invariant or gate to make a test pass, no change to RepFlow
application/domain/UI code, no Workflow Manager/Controller work.

---

## R1 — key round identity on the reviewed round, not on the generation head

**Closes** `B1`, `B2`, `B3`. **Cluster** `C1`.

`scripts/prepare-ai-review.sh`'s round-identity preflight currently
reasons:

```
prev_head  = previous MANIFEST.md's `reviewed_implementation_head:`   (= its generation head)
if prev_head == head_sha:  live_revision must equal prev_revision
else:                      live_revision must equal prev_revision + 1
```

The `else` branch's premise — "a new generation head means a new
reviewed round" — is false for both non-ordinary generation modes, which
exist precisely to move the generation head while pinning the round.

**Change.**

1. Read `prev_head` from the previous manifest's `generation_head:` line
   (unambiguous; it means the generation head under both the old and the
   repaired manifest semantics — see `R2`), not from
   `reviewed_implementation_head:`.
2. Replace the `else` branch with revision **monotonicity**:
   `live_revision` must be `prev_revision` or `prev_revision + 1`.
3. Admit the `live_revision == prev_revision` case at a new head **only**
   when this same preflight's provenance-interval half actually ran and
   verified the interval — i.e. only when
   `workflow_state.verify_implementation_provenance_interval` proved that
   live HEAD is exactly the current `Workflow-Bundle-Generation-Record`
   commit for the live `implementation_revision`, that
   `reviewed_implementation_head` is first-parent-reachable from it, that
   every non-record commit between them classifies implementation-stage
   `excluded`, and that the supersession chain is continuous.

**Why this is not a weakening.** The provenance-interval half is a
strictly stronger statement of round identity than the revision-delta
heuristic: it proves the state's own round pointer, the Git history, and
the classification all agree. Every failure the old rule caught is still
caught:

| Attack / mistake | Caught by |
|---|---|
| regenerate at a new head without calling `record_bundle_generation` | interval half — `HeadPastBundleGenerationRecordError` |
| call `record_bundle_generation` but never commit it | interval half — `BundleGenerationRecordNotFoundError` |
| a further commit lands after the durability commit | interval half — `HeadPastBundleGenerationRecordError` |
| protected content changed but the revision was left alone | interval half — `ProtectedPathInProvenanceIntervalError` (a protected path inside `P..T`) |
| revision bumped twice before generating (`prev + 2`) | monotonicity rule |
| revision moved backwards | monotonicity rule |
| same-head regeneration with the revision bumped anyway | idempotence branch, unchanged |

**Regression risk.** A bundle generated by the pre-repair tool records
`generation_head:` already (both writers emit it), so the new `sed` finds
the same value the old one did. No migration step is required.

## R2 — one meaning per identity name

**Closes** `I1`. **Cluster** `C2`.

`render_manifest_md_implementation_stage` writes the generation head
under the name `reviewed_implementation_head`, colliding with
`WORKFLOW_STATE.json`'s field of the same name, which means the reviewed
round's head. The duplicate is redundant as well as wrong:
`generation_head:` already carries that value.

**Change.** `write_manifest_with_verified_identifiers_implementation_stage`
takes the state's `reviewed_implementation_head` as an explicit argument
(alongside the `implementation_revision` it already takes) and renders it
under that name; `generation_head:` keeps meaning "the commit
`review_content_id` was measured at, and HEAD at generation time".
`write_manifest_with_verified_identifiers_implementation_stage_for_work_item`
supplies it from the same `work_items[<id>]` entry it already reads
`implementation_revision` from. When the state has no value yet (a first
round generated before `record_bundle_generation`, only reachable in
tests), the line is omitted rather than guessed.

**Why bounded.** One rendered line's source value. `review_content_id` is
still measured at `head_full`; `bundle_id` still hashes whatever the
manifest says. No consumer parses the field except
`prepare-ai-review.sh`, which `R1` repoints at `generation_head:`.

## R3 — generated declarations must be usable at both stages

**Closes** `B4`. **Cluster** `C3`.

`generate_artifacts_declarations(work_item_id, plan_path, registry_path,
mapping_path)` gains a required `work_item_type` and emits a
type-appropriate `implementation_stage` block:

- **Always protected**, both types: the item's own
  `<work_item_id>-artifacts.json` (unchanged self-protection).
- **`process`**: `protected_prefixes` = `scripts/`, `.claude/commands/`;
  everything the workflow itself writes, plus the product tree,
  `excluded`.
- **`product`**: `protected_prefixes` = `app/`; the workflow's own
  tooling and its own bookkeeping files `excluded`.
- **Both**: the paths the workflow's *own commands* are guaranteed to
  write are classified explicitly rather than left to fail closed —
  `docs/ai-workflow/WORKFLOW_STATE.json`,
  `docs/ai-workflow/WORKFLOW_CONFIG.json`,
  `workflow_state.FUNCTIONAL_CHECKLIST_PATH`
  (`docs/ACTIVE_MILESTONE.md`, written and committed by
  `/prepare-functional-review`), the item's own `plan_path`, and the
  `docs/ai-workflow/registry/` + `docs/ai-workflow/requirements/`
  prefixes (`/milestone-implement` writes the ledger there for a process
  item), all `excluded`.

**Fail-closed is preserved.** The default names a closed set; a path
under any directory it does not name still raises
`UnclassifiedPathError`. This widens the *named* set exactly the way
`PLAN_STAGE_EXCLUDED_PREFIXES`' own `OPUS-R18-004` widening did, and the
plan text's existing instruction stands: `SELF_REVIEWING_PLAN` must still
confirm the inherited set fits the item's real footprint.

`/milestone-plan` step 3's call gains the `work_item_type` argument it
already has in hand.

## R8 — state the plan stage's load-bearing staging step

**Closes** `B6`. **Cluster** `C9`.

`resolve_plan_stage_metadata` requires each declared
`plan_path`/`registry_path`/`mapping_path` to be in the Git index. A
fresh work item's four plan-stage files are untracked when
`/milestone-plan` finishes, and the plan-approval commit is what commits
them, so nothing bridged the gap. `workflow_state.py` twice names
"`/milestone-plan`'s own staging step" for a step that did not exist.

**Change.** `/milestone-plan` step 3 marks the four files intent-to-add
(`git add -N`) and leaves them that way; `/apply-plan-review` step 5
points at the same step for a revision that creates one of them for the
first time.

**Why not the other direction.** Relaxing the resolver's tracked-path
requirement would let an untracked file dropped anywhere in the worktree
become authoritative metadata — the exact hazard `GPT-R32-001` closed.
Moving `prepare-ai-review.sh`'s own internal `git add -N` earlier would
not help either: its exit trap resets every path it marked, so
`/approve-review plan`'s own later `resolve_plan_stage_metadata` call
would refuse again.

**Why intent-to-add specifically.** It satisfies the resolver without
staging content, and `git diff --name-only --cached HEAD` does not report
an unstaged intent-to-add marker (verified empirically), so
`stage_plan_approval_commit_paths`' pre-staging index-isolation check
still starts from a clean index — which is exactly what that function's
own docstring already promised.

## R9 — retire the last live `DEFAULT_ARTIFACTS_PATH` defaults

**Closes** `I6`. **Cluster** `C7`.

`load_implementation_stage_classification`'s and
`promote_legacy_work_item`'s `artifacts_path` parameters become required.

**Why this is a correctness fix, not tidying.** With the default in
place, `promote_legacy_work_item` evaluated a legacy *product* item's
`technical_approval` freshness against `workflow-v2-1-core`'s *process*
classification, in which `app/` is `excluded` — so a real product change
since the reviewed commit read as "not stale" and adoption proceeded with
a `CURRENT` approval. Reproduced by execution. This is the same
`GPT-R30-005` reasoning that already retired the `PLAN_STAGE_*` defaults,
applied to the two places it had not reached.

`DEFAULT_ARTIFACTS_PATH` stays a named constant; it is only no longer a
live default.

## R10 — a round with an unchanged checklist still needs its own evidence

**Closes** `I7`. **Cluster** `C9`.

`/prepare-functional-review` step 3a's evidence lookup is round-scoped
(`<work_item_id>/<implementation_revision>/`), but its commit shape
assumed the checklist file always moves with the round. A round that
legitimately needs no checklist change therefore had no way to create its
own evidence: `git commit -- docs/ACTIVE_MILESTONE.md` fails with
`nothing to commit`, so the round ends with nothing discoverable at all.
At the time this was written the visible consequence was
`/accept-scoped-remediation` refusing forever; that command has since been
retired (`I10`), and the consequence is now that step 4 has no identity to
report and `/review-functional` refuses for the round — the same missing
evidence, named against a surface that still exists.

**Change.** Step 3a names the branch: in exactly this case the commit is
created with `git commit --allow-empty`, because the commit's payload
*is* the round-scoped trailer, whose value differs from the previous
round's even at an identical blob.

**Why this is not a loophole.** The exception is scoped to one command
and one branch, and a conformance test asserts no other command mentions
`--allow-empty`: every other metadata-only commit in this workflow
carries a real `WORKFLOW_STATE.json` change, and an empty one there would
mean the state write never happened. The resulting commit is verified by
the same machinery as any other — `discover_current_functional_checklist_evidence`
finds it by trailer, its own committed content at the checklist path is
exactly the blob the trailer names, and the path is clean in the working
tree, all proven by execution in acceptance-matrix row `C8`. (Those last
two properties were originally asserted through
`verify_functional_checklist_evidence`, the pre-commit evidence guard;
`I10` retired that guard with its only caller, so `C8` asserts them
directly instead — the same two facts, one indirection fewer.)

## R12 — give the `IMPLEMENTING` → `SELF_REVIEWING_IMPLEMENTATION` edge a writer

**Closes** `B8`, `O9`. **Cluster** `C10` (new — see below).

`SELF_REVIEWING_IMPLEMENTATION` had exactly one writer,
`complete_checkpoint`, firing only as a side effect of a checkpoint
*transitioning* to `COMPLETE`. Both `/milestone-implement` step 2 and
`/bootstrap-workflow-v2`'s `NO_CHECKPOINT` terminal-wrap-up branch say
"enter `SELF_REVIEWING_IMPLEMENTATION`" and name no writer.

**Change.**

1. `workflow_state.enter_self_reviewing_implementation(state,
   work_item_id, registry, now)` — no-op when already there, the real
   transition from `IMPLEMENTING` when `registry_completion_status` is
   terminal, `IncompleteCheckpointsForSelfReviewError` when it is not,
   `IllegalSelfReviewEntryPhaseError` from any other phase.
2. Both commands name it, and both **commit** the state when (and only
   when) it transitioned — the same durability discipline step 1f already
   applies to `complete_checkpoint`'s own write, and load-bearing because
   the `same_content` republication that a plan-only re-approval produces
   validates the generation-record commit against its *parent's
   committed* phase.
3. `select_next_checkpoint`'s docstring clause that asserted the gap away
   is replaced by the reachable case it denied.

**Why this is bounded.** It adds one edge that the state machine already
documented as existing (`MILESTONE_WORKFLOW.md`'s
`SELF_REVIEWING_IMPLEMENTATION` entry condition is "all checkpoints
implemented", which is exactly the guard) and changes no gate, no
projection, and no approval semantics. The ordinary path's behaviour is
byte-identical: the call is a no-op there and commits nothing.

**What would make it a regression.** Accepting a non-terminal registry;
bumping `state_revision` on the no-op; or letting the transition be
reachable from any phase other than `IMPLEMENTING`. All three are
asserted against directly in `TestEnterSelfReviewingImplementation`.

## R13 — make the generated declaration's per-type halves symmetric

**Closes** `I8`. **Cluster** `C3` (the half `R3` did not reach).

`R3` gave `generate_artifacts_declarations` a `work_item_type` and a
per-type deliverable *tree*. It did not give the `product` type its
documentation and build-configuration territory, and the body kept two
one-directional `if work_item_type == "process":` blocks that excluded a
hand-listed slice of product documentation with no product-side mirror.

**Change.** `IMPLEMENTATION_STAGE_DELIVERABLE_PATHS` (the exact-path half
of the existing per-type prefix table), `docs/adr/` added to the product
prefix half, `_SHARED_REPOSITORY_PREFIXES` excluded for both types, and a
`_implementation_stage_default` body with no type-specific branch left in
it. The plan-stage template additionally excludes the product build
files. Import-time assertions extended to totality, per-type disjointness
and shared-vs-deliverable disjointness.

**Why this is bounded and conservative.** The two types are compared, not
unified: product-owned, process-owned and shared stay three distinct
categories (the table is in ledger `I8`). Self-protection is unchanged,
no whole-repository exclusion is introduced, concurrent-writer detection
is unweakened, and a genuinely novel path still fails closed. The
plan-stage half is widened in the *template* rather than in
`fingerprint.PLAN_STAGE_EXCLUDED_PATHS`, so no declaration file on disk
changes and no existing approval's identity moves — `R14`'s own rule
applied to this repair.

**What would make it a regression.** Excluding a path the owning type
should protect; protecting a shared path for one type (which would let a
concurrent item of the other type stale it); or replacing the fail-closed
default with a catch-all.

## R14 — state the real artifact-declaration identity contract

**Closes** `I9`. **Cluster** `C10`.

Two `workflow_fingerprint` docstrings asserted that editing the
declarations file never stales the plan approval, because the file's path
is plan-stage excluded. The premise is true, the conclusion is false: the
classification sets themselves are hashed into each stage's projection,
and they are read out of that file.

**Change.** Documentation and contract only — the cryptographic behaviour
is correct and deliberate, and no exemption was created. Both docstrings
corrected; `REVIEW_PROTOCOL.md` gains "Repairing an artifact declaration
after an approval" (per-edit truth table, per-stage repair procedure, the
prohibition on widening an exclusion to dodge a re-review, and the
cache-vs-recompute rule); `/milestone-plan` step 3 states the same
contract where the declaration is written.

**Why no code changed.** No implementation path was found that *relies*
on the false assumption to make a decision — it lived in prose and in
operator reasoning, and was acted on in this repository's own history
(commit `a2ac9a9`). The one place it could have leaked into behaviour is
recorded as an asserted boundary in `F4` and under ledger `I9`.

**What would make it a regression.** Adding an exemption that removes the
classification sets from either projection. That is the exact "widen an
exclusion and re-bless the digest in the same session" attack the
self-protection entry exists to prevent, and `F4` asserts against it in
both directions.

## R16 — make a remediation child selectable by the commands that drive it

**Cluster.** A mechanism designed around explicit work-item targeting,
extended to only some of the commands that need it.

**What was wrong.** `create_remediation_child_work_item` deliberately does
not repoint `active_work_item_id` — `D1`'s "resume-focus pointer, not an
execution lock" — so a `<parent-id>-remediation-<n>` child is never the
active item while its parent is open. Nine of fifteen commands already
accepted an explicit `[work-item-id]` for exactly that reason. Four on the
child's own lifecycle did not: `/milestone-plan` (its only argument was
`[base-sha]`, and its step 1 derives the target from
`docs/ACTIVE_MILESTONE.md`/`docs/ROADMAP.md`, where a child never
appears), `/apply-plan-review`, `/apply-implementation-review` and
`/accept-milestone` (which never defined how it resolved a target at
all). The child could not be planned, a `REVISE` on it could not be
applied, and it could not be accepted — and since `complete_work_item`
refuses a parent with an incomplete child, the parent was permanently
unacceptable too. Meanwhile `/apply-functional-review`'s broad branch told
the operator to run `/milestone-plan <child-id>`.

**Repair.** Extend the existing mechanism; invent nothing. Each of the
four gains the same `[work-item-id]` contract, resolved the same way
(`$ARGUMENTS`, else `active_work_item_id`, else refuse by name), stated in
each command's own step 0 so no other step's text moves.
`/milestone-plan`'s two-argument form resolves by lookup against
`work_items`, never by token shape, so its historical `<base-sha>` form is
unchanged. `/accept-milestone` additionally may not derive its target from
its own confirmation text, which would make the user-only guard
self-satisfying.

**Why not a new selection mechanism.** The alternative — a command that
repoints `active_work_item_id` — would turn the pointer into the execution
lock `D1` explicitly says it is not, and would break the concurrent-work-item
model `D14` already exercises.

**Landed.** `4866a2a`.

sixteen diagram tests and ten of the thirteen reference tests fail against
the pre-repair artifacts.

## R18 — make path resolution a resolver argument, not a caller's memory

**Cluster.** `C10` again — a contract stated in prose that no code
implements or enforces — plus `I5`'s own shape, a test standing in for a
command dependency.

**What was wrong.** `REVIEW_PROTOCOL.md` already stated the plan stage's
rule correctly ("the bundle directory is never the flat fallback ...
always resolve to `.ai-review/<work_item_id>/current/` **by
construction**"), and both generator-side path producers implemented it —
`prepare-ai-review.sh`'s `ROOT_DIR` by templating, and
`write_manifest_with_verified_identifiers_for_work_item` by templating
with a docstring that names the hazard outright ("never
`resolve_bundle_dir`'s existence-gated scoped-else-flat fallback, so the
write path can never target the wrong (flat) directory for a new item").
The one thing that never learned the rule was `resolve_bundle_dir`
itself — the function every command file names for the *authoring* half.
So a work item's first plan bundle authored to one directory and generated
into another, and failed (`I16`). The same existence gate then made
`current/`'s absence after a withdrawal mean "this item is on the flat
layout", which broke the round after every withdrawal at the
implementation stage too (`I18`) and left the withdrawal's own `REJECTED`
marker unreachable inside its crash window (`O25`).

The acceptance matrix could not see any of it: `Item.bundle_dir`
hardcoded the scoped path and created it before authoring (`I17`).

**Repair.** Push the rule into the resolver, where a caller cannot forget
it:

- `resolve_bundle_dir(repo_root, work_item_id, *, stage=None)`.
  `stage="plan"` is scoped by construction. Every other stage keeps the
  flat fallback, because omitting `prepare-ai-review.sh`'s optional
  `[work-item-id]` really does generate `.ai-review/current/` and making
  every stage scoped would break that documented invocation the
  mirror-image way. An unrecognized stage raises `InvalidBundleStageError`
  rather than silently taking the compatibility branch.
- For the stages that keep the fallback, decide the layout from the work
  item's own root directory rather than from `current/`, which a
  withdrawal is defined to remove. `resolve_rejected_marker_path` stays a
  one-line derivation from `resolve_bundle_dir` and inherits it.
- `resolve_feedback_dir` untouched: `feedback/` is stage-agnostic by
  contract.
- The same shape for `/approve-review`'s takeover, which had a
  repository-wide journal and no target check: `work_item_id` becomes a
  **required** argument of `take_over_plan_approval_transaction`, refused
  on mismatch, rather than a rule step 4b is trusted to remember (`O24`).
- And a fifth acceptance-matrix fidelity rule: no row resolves a bundle or
  feedback path by hand.

**Landed.** `7ae9a48`, `ff363e4`.

## New root-cause cluster found in convergence pass 7

**C10 — a contract stated in prose that no code implements or enforces.**
`B8` and `I9` are the same shape one level apart. In `B8`, two commands
and a docstring asserted a state transition that no writer performed; in
`I9`, two docstrings asserted a freshness property that the projection
contradicts. Neither was a logic error in a function — both were English
sentences that nothing checked, in a system where the command Markdown
*is* the executable specification. `C4` (commands not naming the
generator's required inputs) and `C9` (a precondition assumed by code and
never stated by a command) are the same cluster read in the other two
directions: prose and code disagreeing, with no mechanism that would
notice. The three mechanical conformance checks this campaign already
runs — symbol/keyword existence, the state-writer census, the phase-
assignment census — check that a named symbol exists, not that a *claimed
behaviour* is implemented. That gap is what the acceptance matrix's
fidelity rules exist to cover, and pass 7 added a fourth rule (no
hand-written `phase`) for exactly that reason.

## R19 — the generation contract belongs to every command that drives one

**Closes** `I19`, `O26`, `O27`. **Cluster** `C4` + `C5` (the same cluster
`R5` addressed, reopened by its own miscount).

`R5` corrected "the four generation-driving commands". The population is
**eight**: `/milestone-plan`, `/apply-plan-review`, `/milestone-implement`,
`/apply-implementation-review`, `/apply-functional-review`,
`/recover-implementation-provenance`, `/prepare-review` and
`/bootstrap-workflow-v2` each instruct their own run of
`scripts/prepare-ai-review.sh`. A hand-written census cannot notice its
own omissions, and this one omitted the single command whose contract was
actually incomplete.

**Command text.** `/apply-functional-review` resolves `<bundle_dir>`
through the production resolver (the compatibility form — its only
generation is a `post-fix` round), and its bounded-code-change branch
states the same generation-authoring contract `/apply-implementation-review`
step 7 already carries: refresh `IMPLEMENTATION_SUMMARY.md`'s
`implementation_revision: <N>` (advanced for `"ordinary"`, unchanged for
`"same_content"`) and `REVIEW_REQUEST.md`'s `review_content_id: <hex>`,
each naming its enforcing assertion and its consequence — a withdrawal
for the first, an outright refusal for the second. The established
contract is reused, not re-invented, and nothing else in the command
changes.

**Census, mechanised.** `workflow_integration_test.py` discovers the
driver set from the command corpus and compares it against a declared
roster; every command that so much as *mentions* the generator must be
classified as a driver or as mention-only, with the reason. A ninth
driver, a rename, or a deleted run instruction fails the suite instead of
falling outside it. Per-driver obligations run through one pure checker,
`_generation_authoring_violations`, so the identical logic can be pointed
at a deliberately reverted copy of a command — which is what the
mutation regression does.

**The other two drivers, verified rather than assumed.**
`/recover-implementation-provenance`'s round is pinned by contract (no
revision advance, excluded-only interval, so the digest recomputes
unchanged) — confirmed by driving its step 6 with the previous round's
inputs untouched, which publishes. `/prepare-review` and
`/bootstrap-workflow-v2` route authoring through
`REVIEW_PROTOCOL.md`'s "Author-written files" section, which states both
marker-line requirements.

**Matrix.** Rows `C9`/`C10` are the behavioural halves of the contract;
row `I6` executes the flat compatibility path's first successful
generation (`O27`). `Item.write_bundle_inputs` now documents that every
line it writes is one the owning command's own step names — the property
whose absence let rows `C2`/`C3`/`C8` pass over the gap. The execution
record's control-arm figures are re-measured and given a stated counting
rule (`O26`).

**Why bounded.** Two hunks of one command file, one test-suite section,
three matrix rows, and documentation. No Python, no shell, no lifecycle
semantics.

## New root-cause cluster confirmed in convergence pass 12

**C11 — a check that exists, is documented, is tested, and is never
called.** `OPUS-R133-003` named this once (`assert_stage_completeness`'s
implementation branch, whose first live caller arrived only with that
repair). Pass 12 found it again, one approval stage over:
`validate_technical_approval_commit` had **zero** production call sites
while its own docstring positioned it as the live sibling of
`validate_bundle_generation_record_commit`. The failure mode is
distinctive — a suite can be green, a unit test can prove the check
works, and the behaviour it guards can still be entirely unguarded in
production. It is detectable mechanically (a validator's call graph), and
this pass's helper audit is the general form of that detection.

**C12 — a test helper that stands in for a command and does more, or
less, than the command says.** Ledger `I19` was the first instance; pass
12 found three more in one mechanical sweep (`I21`, `I22`, `O35`). Two
directions, both harmful: a helper that does *more* than its command
makes an incomplete command look complete (`I19`, `I22`); a helper that
does *more strictly* than its command makes a supported branch of the
command unreachable in the suite (`O35`). The detection is the same in
both directions — extract every production entry point a helper calls and
require the owning command's own text to name it, or the discrepancy to
be a recorded, reasoned decision.

## R20 — the producer, not the filesystem, decides whether to finalize

**Closes** `I20`; records `O30`. **Cluster** `C11`-adjacent: a check
firing where it has no standing rather than not firing where it does.

`prepare-ai-review.sh`'s closing check was gated on a `MANIFEST.md`
*file* existing. Two of its four stages write none, and `$BUNDLE_DIR` is
reused across stages, so a `functional-review` generation inherited the
previous round's manifest and ran a three-way identity check it could
only fail — withdrawing and quarantining a valid, published,
already-approved bundle it had never claimed an identity in, while
`WORKFLOW_STATE.json` (which this script never writes) went on saying the
approval was `CURRENT`.

**Production.** An invocation-local `MANIFEST_WRITTEN` flag, set only on
the far side of a `--write-manifest` call that returned 0, gates the
closing check. It cannot drift from the write it describes because the
same `if/elif` sets it. The inherited manifest is neither deleted nor
rewritten — deleting it would be the identical filesystem-state reasoning
inverted, and would destroy the published round's own identity record —
and the run reports that what it inherited no longer describes the
directory or the archive.

**Why the residual is non-gating, and how that is known.** Every live
consumer recomputes `bundle_id` rather than reading the declared value,
so an approval over an inherited manifest fails closed. That is executed
(matrix rows `J7`, `J8`), not argued.

## R21 — every generation driver's obligations are derived, not listed

**Closes** `O29`, `O31`. **Cluster** `C4` (the cluster `R5` and `R19`
addressed), reopened one level down.

`R19` made the *population* of generation drivers mechanical and left the
*obligations* as a second hand-maintained command-name list. A driver
absent from that second list owed no marker line at all — reproduced with
a synthetic `post-fix` driver, for which the checker returned no
violations before *and* after it was added to the main census. The same
hole existed on the plan side, where two hand-written tests naming two
files stood in for a rule.

**Conformance.** The stage each driver runs at is captured from its own
invocation line. Every driver owes a declared discipline and silence is a
violation, not an exemption; the declared discipline is checked against
the derived stage, so a `post-fix` driver cannot conform by satisfying
the plan stage's different contract; and both exemption forms carry
evidence checks against the command text.

**Command text.** Separately (`O31`), no driver named any computation for
the `review_content_id` it required the author to state — while
`assert_review_request_states_review_content_id` *refuses* the whole
generation on a wrong one. `REVIEW_PROTOCOL.md` gains one "Computing
`review_content_id`" section naming exactly one existing entry point per
stage; every command references it and none restates the algorithm.
Naming it is now itself a conformance obligation, and the recipes are
executed against the generator's own recorded values rather than asserted
as text.

## R22 — the implementation stage gets the post-commit verification the plan stage has

**Closes** `I21`. **Cluster** `C11`.

`validate_technical_approval_commit` — implemented, documented,
unit-tested — had no production caller. The plan stage has step 6a's
post-commit verification set; the implementation stage had none, so a
technical-approval commit that also mutated another work item's entry or
a top-level routing field, or recorded the approval without transitioning
`phase`, was accepted by every live consumer.

**Command text.** `/approve-review` step 6's implementation-stage
paragraph names both checks, with the failure disposition stated.
Deliberately **forward-only**, applied to the commit the invocation just
created: two commits already in this repository do not satisfy the
contract, history rewriting is not available, and both SHAs are named in
the command text and asserted by conformance so the scope is recorded
rather than assumed.

## R23 — the plan document's generated table is regenerated wherever the registry is

**Closes** `I22`. **Cluster** `C12` + `C4`.

`/milestone-plan` calls the plan document's checkpoint table "never
hand-edited"; `/apply-plan-review` regenerated the registry behind it and
never said to refresh it, so a revision published a document the registry
contradicts, with nothing detecting it. The acceptance matrix's own
helper performed the re-embed all along, which is exactly why every
plan-revision row stayed green.

**Command text.** Step 5 names the re-embed, unconditionally — the render
is a pure function of the checkpoint set, so it is a no-op when nothing
moved, and a conditional step only reinvites the judgement call that
produced the staleness. Conformance: a plan-marker-step driver naming
`generate_registry` without `render_registry_markdown` is a violation,
with a live-file mutation control arm.
