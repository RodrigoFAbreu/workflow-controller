## Goal

Close [#294](https://github.com/RodrigoFAbreu/workflow-controller/issues/294). The installed Workflow already ships the backlog parser, validator, selector and page generator (`scripts/workflow_backlog.py`, described in `docs/ai-workflow/BACKLOG_FILE.md`). This repository does not use it: `WORKFLOW_CONFIG.json` has no `backlog` key, so `/milestone-plan` reads a 2279-line hand-written `docs/ROADMAP.md` and acceptance asks a person to edit its rows. After this item the roadmap is data: `docs/backlog.yaml` lists every item, `/milestone-plan` takes the next ready one from it, acceptance sets it `done` and regenerates `docs/ROADMAP.md` inside the completion commit, and CI fails when the page is stale. The prose of the old page is kept, unchanged, in one archive page until A2b splits it into one page per item.

## Decisions

Each decision states one principle.

- **D1. The built-in generator, not a declared one.** The declaration is `"backlog": {"file": "docs/backlog.yaml", "roadmap": "docs/ROADMAP.md"}` with no `generator`. A declared generator would be a second mechanism to own and test; the built-in page (a table sorted by `order`) is what the roadmap needs, and A2b can declare one later if it wants prose in the page. `docs/ROADMAP.md` and `docs/backlog.yaml` are never protected paths, so acceptance's edit never stales an approval.
- **D2. Nothing is deleted: the old page moves, byte for byte, to `docs/roadmap-archive.md`.** The generator replaces `docs/ROADMAP.md` (`generate --replace`, once), which would lose the rows' prose, their decisions and the numbered sections. The archive is the old page with only a banner line added above its title saying it is frozen and where the live roadmap is. A2b moves its rows into `docs/items/<id>.md` pages and then retires the archive. The archive is exempt from the link check exactly as the old page was (`LINK_EXCLUDED`), because it is a historical record whose links are not rewritten. One existing test reads the old page's prose: `tests/test_functional_sandbox.py::test_the_guide_and_the_roadmap_name_the_runtime_root_remainder` asserts the text of follow-up 86 in `docs/ROADMAP.md`, which after `generate --replace` exists only in the archive. CP2 repoints that test at `docs/roadmap-archive.md` and renames it to `test_the_guide_and_the_roadmap_archive_name_the_runtime_root_remainder`; a repository-wide search of `tests/`, `tools/` and `controller/` finds no other reader of the old page's prose.
- **D3. One backlog item per row of this repository's two roadmap tables.** An item is a row of the Controller lane table or of the orchestrator series table (O1 to O7). The Manager and Workflow lane table lists other repositories' items (they stay in the archive, where the dependencies on them are explained); a row that is dropped or replaced (A2c, A5) is not an item either, and the archive keeps it. A dependency on an item of another repository, or on text that is not an item, is not written in `depends_on` (the `Needs` column's prose stays in the archive). A group id that is not a row (`C10`, `C12`, `A2`, `CU3`) is expanded to the open items it stands for where the intent is clear: the group's open members are written in `depends_on` (`C10` in C12b becomes C10d-a and C10d-b; `C12` in C11 becomes C12b to C12d; `A2` in A3 and A4 becomes A2a and A2b; `CU3` in CL1a is a done group and is dropped). Any group id this expansion cannot settle is listed under "Open points" so the archive's retirement by A2b loses nothing. The consistency test names the row exclusions.
- **D4. Item id, title, status, order.**
  - `id` is `workflow-controller-` followed by the row's lower-case step id (`workflow-controller-c10d-a`), so the work item an open item starts has the id the file gives it. The id is the work item id (BACKLOG_FILE.md, "The schema"), which is why this plan's work item is `workflow-controller-a2a`. A `done` item's id is not the id of its historical work item: of the 83 work items in `WORKFLOW_STATE.json` only this one has the `workflow-controller-<step>` form (C10e's is `workflow-controller-claude-build-verify`, CU3c's is `workflow-controller-cleanup-3c`). Nothing reads a `done` item's id as a live work item, so this is harmless, and it is said here because the schema's claim holds only for items started from the file.
  - `title` is the row's step name in one line of at most 200 characters, taken from the row's first clause (the leading `Complexity: …` label and `**Done**` marker removed), quoted wherever the file format asks for it.
  - `status` is `done` for a row the archive marks complete: a leading `**Done**`, or the word `done` or `complete` in lower case in the row's parenthesis wherever it falls (so NF1, "(done, accepted 2026-10-25 …", RB1, "(done, accepted …", RB2, "… both checkpoints complete)" and C10g-2a, whose marker follows a nested link parenthesis, are all `done`); `in-progress` for A2a (acceptance sets it `done`), `next` for a sized row not done, and `idea` for a row that says it is not yet sized and must be split before it is planned (C11, A3, A4, O1 to O7), which `next` never picks.
  - `order` is unique across all items. Done items take 1, 2, 3 … in the order of the Controller table; the open items follow in this sequence: A2a, A2b, H4e, H4f, H4g, C10d-a, C10d-b, CL1a to CL1e, C12b to C12d, C8c, then the ideas (C11, A3, A4, O1 to O7). This is the roadmap's "Next, in order" list with the harness epic's remaining steps kept ahead of C10d, as that list has them, and with C8c (which that list does not name) placed after C12d; it is an owner-editable value, and the placement of H4e to H4g and of C8c is listed under "Open points" below. The open list is exactly the items above; every other row of the two tables is `done`, and the test asserts that complement.
  - `release`, `size` and `detail` are left out: A2b adds `detail`, and a release is added by hand where wanted.
- **D5. The file is built once by a script that is not committed, then pinned by a test.** A throwaway script reads the archive's two tables and writes the file; it is run once, its output is reviewed, and it is not kept (the file is the source from then on). `tests/test_backlog.py` pins what a later edit must not break, and only what survives ordinary use of the backlog: the file parses and validates; every archive row, less D3's named exclusions, is an item (one direction only: the archive is frozen, so a new item absent from it stays valid); `order` is unique; every row the archive marks `done` (D4's rule) is `done` in the file (one direction only: acceptance legitimately sets A2a `done`, so rows outside D4's open list are asserted `done` in the archive, and open rows are not asserted at all); and every archive row outside D4's open list and D3's exclusions is `done`, which would catch a row the done rule missed. Selection on the live file is pinned by a computed expectation and nothing else, never a named item: the test works out from the file's own data "the ready `in-progress` item with the lowest `order`, else the ready `next` item with the lowest `order`" (the rule of `select_next`, `scripts/workflow_backlog.py`) and compares it with `select_next`'s answer; when nothing is ready (only `idea` and `done` items remain) the expectation is the refusal `no_ready_item`, and the test expects `select_next` to raise it rather than error. The test names no item of the live file, so acceptance (A2a, then A2b, then every later item `done`) and an owner's `order` edit among open items break nothing. The delivered behaviour (A2a `in-progress` is selected; with A2a `done` the selection is A2b) is stated in two places that cannot go stale: a small inline fixture backlog the test owns (an `in-progress` item, two `next` items with a dependency, an `idea`, a `done` item) whose answers are asserted, and a one-time check in CP1's and CP2's "Done when" that is run at delivery and is not committed as a test. Tests also pin that swapping two open items' `order` in an in-memory copy of the live file, and setting A2b `done` in one, keep the computed-expectation test green.
- **D6. The CI check is a test, not a new workflow step.** CI runs the repository's tests on every pull request; the workflow files are generated from a model (`tools/ci_workflows.py`), so a new step would change that model and the committed workflows for one command. `tests/test_backlog.py` runs the same check the Workflow's `check` command runs, through its library function, so a stale page fails the existing test jobs with the first differing line.
- **D7. The in-flight declaration is classified now.** This work item's artifact declaration is written before the repository declares a backlog, which is the case BACKLOG_FILE.md calls "items in flight at adoption": without the file, the roadmap and `docs/items/` classified, acceptance's edit would stop with `UnclassifiedPathError`. Before the plan is first published, `docs/backlog.yaml` and the prefix `docs/items/` are added as excluded entries at both stages (the roadmap is excluded already). Before any approval exists this costs nothing; after one it would stale it.
- **D8. The pages say what changed.** `docs/guide/development.md` explains the backlog (where it is, how to add or reorder an item, that acceptance sets `done` and regenerates the page, that `docs/ROADMAP.md` is never edited by hand), `docs/README.md` lists the archive, and the six links that pointed into the old page's anchors point into the archive (`docs/releases/1.18.0.md`, `1.19.0.md`, `1.19.1.md`, `1.27.6.md`, `docs/guide/automation.md`, `docs/milestones/optional-findings-sweep-2026-10-16.md`; `tools/check_docs.py` scans five of them, the sweep page is under `docs/milestones/`, which it skips). The sentence in `docs/guide/development.md` that lists the pages the link check skips (`docs/ROADMAP.md` and `docs/ACTIVE_MILESTONE.md`) also names the archive. The registry record of a finished work item that names the old URL is a historical record and stays.

## Open points (not decided silently)

- **Order of H4e, H4f, H4g.** The roadmap's "Next, in order" list places the harness epic (item 2) before A2a, yet the owner set A2a next on 2026-11-05. D4 puts the three remaining Codex-worker steps right after A2b. The values are plain `order` numbers; the owner can reorder them with a one-line edit and `generate`, and the plan does not depend on the choice.
- **Place of C8c.** C8c is not on the roadmap's "Next, in order" list; D4 puts it after C12d, before the ideas. The owner can move it with one `order` edit.
- **Group-id dependencies.** D3 expands `C10`, `C12` and `A2` to their open members and drops the done group `CU3`; if the owner wants a different meaning for any (for example C11 waiting for the whole of C12 rather than its open steps), the `depends_on` line is one edit.
- **Titles.** The title is a short name; the long row text remains in the archive until A2b. A reviewer who wants a different wording for a title changes one line.

## Out of scope

The prose migration to `docs/items/` pages and the `detail` field (A2b); a declared generator; the Manager and Workflow lane rows; setting a `release` on done items; changing the Workflow's scripts (they are the installed Workflow's, not this repository's); a CI workflow step.
