## Goal

Close [#298](https://github.com/RodrigoFAbreu/workflow-controller/issues/298). After A2a the backlog is data and `docs/ROADMAP.md` is generated, but the prose of every row (decisions, complexity, issue links) and the rules sections (direction, the clean-up limit, the sizing rule, "Next, in order") still live only in the frozen `docs/roadmap-archive.md`. `/milestone-plan` reads an item's `detail` page as the milestone's description and falls back to the title alone when there is none, and planners cannot read a frozen archive for the rules. After this item every item whose archive row has prose beyond its title has a page `docs/items/<id>.md` named by `detail`, the rules live on one page the documentation map links, every title is a complete phrase, and the five small repairs A2a left are done. One mechanism (move text), no behaviour change.

## Decisions

Each decision states one principle.

- **D1. Text is moved, never rewritten.** A page holds its archive row's text verbatim under a short heading, and the rules page holds the archive's rules sections unchanged. The measure is mechanical: a one-off script (not committed) checks that each row's text, less exactly the two permitted changes in D3, occurs in its page, and the result goes in the report. Rewording would make the check meaningless and the move unreviewable.
- **D2. The pages are generated once by a throwaway script, then reviewed.** As A2a built `docs/backlog.yaml`, a script reads the archive's two tables (the Controller lane table and the orchestrator series table), pairs each row with its item through the step id in the row's first cell (a plain id such as `C1`, not backticked; all 97 items pair, and only `A2c` and `A5`, which have no item, are left over, as `tests/test_backlog.py` excludes them), and writes the pages. A2b's own page already exists and is hand-written (D4): the script never replaces an existing page; it appends A2b's row text under its own heading `## Roadmap row (moved verbatim)`. The script is not committed; its output is the source from then on. A row whose text is its title alone gets no page and no `detail` line.
- **D3. No status in a page; every other cell moves.** Status, order and `depends_on` live in `docs/backlog.yaml`, and a page that repeated the status would go stale at acceptance, which edits only the backlog. The Controller table's columns are `# | Step | Needs | Section`; it has no status cell, the status sits inside the Step text. **The marker, defined for every form** (a trial parse finds 71 marked rows: 16 start with `**Done**`; 11 are a parenthesis that is only `complete`/`done`; 44 hold the word inside a longer parenthesis whose other text is real prose, for example C8b's `(complete, released as 1.11.0, PR #52, ...; accepted ...)`, C10g-1's `(complete: <what was built>)`, NF2's `(a `fix:` patch; complete, [#170](...) closed by its pull request)`): the marker is **the one word and its adjoining separator, never the parenthesis**. The word is the first standalone `done` or `complete` of the Step that is outside inline code (backticks) and inside a top-level parenthesis, or the leading `**Done** `. Removal: `**Done** ` is dropped; the word is dropped together with the one `, `, `; ` or `: ` that follows it (`(complete, released ...)` becomes `(released ...)`, `(complete: x)` becomes `(x)`); a word at the end of its parenthesis is dropped with the one separator before it (`(a `fix:` patch; complete)` becomes `(a `fix:` patch)`); a parenthesis left empty is dropped with the one space before it. Exactly one marker is removed per marked row, so a row's other parentheses are not markers: C7's `` (`usage.admit`, `usage.complete`) `` (the word is in code) and CU3b's second parenthesis (`done` inside prose) stay. This is stricter than `archive_marks_done` in `tests/test_backlog.py`, which only decides whether a row is done and reads any lower-case `done` or `complete` in any parenthesis. The report lists every removed string with its row id (71 entries), so the removal itself is reviewed and a removal that took prose with it is visible. Per cell: the **Step** text moves with exactly one removal, its status marker; the **Needs** text moves whole under a `Needs:` line, because it holds owner decisions that `depends_on` cannot hold (H4e's separate clone and fast-forward landing decision, H4f's reuse of it, C8's "without C7", O2's "a SignalHub reply path"); the **Section** cell moves whole under a `Section:` line (C12b's "follow-ups 8, 9 and 14"). The orchestrator table's cells move the same way. The containment check in D1 compares a row's text less that one removal (applied to the check's side by the same rule), and less the link-target rewrite of D10, nothing else; it also fails if the removed strings do not number exactly the marked rows or if any removed string is longer than a word plus one separator.
- **D4. The open items' pages are checked by hand, not only generated.** The pages of A2b itself (existing, preserved, plus its appended row text, D2), H4e to H4g, C10d-a and C10d-b, CL1a to CL1e, C12b to C12d, C8c and the ideas are what the next planners read. Each is read against three questions: is the description complete, are the applicable rules (sizing rule, one mechanism, releasable alone) stated or linked from the rules page, and does the item's GitHub issue carry planning guidance that the page must name or quote. Where an issue has guidance the row lacks, the page links the issue; the row's own text is still moved verbatim and any addition sits under a separate "Planning notes" heading.
- **D5. The rules page is `docs/planning-rules.md`.** The name is the plan's choice (the item leaves it open). The moved text is enumerated by archive heading and anchor, nothing else moves: (a) under a new heading `## Next, in order and the sizing rules`, the prose of `## At a glance` from the line `**Next, in order**` (archive line 43) down to the blank line before `**Controller lane, in order.**`, which holds "Next, in order", the clean-up limit of more than 8 open `review-follow-up` issues, the sizing rule (one paragraph with them, so they share this one heading) and the owner-decision paragraphs, preceded by one new line (outside the moved text, like D4's "Planning notes") saying the order is `docs/backlog.yaml` and the list below it is a frozen record; (b) `## 11.11 The orchestrator: a person only for escalation` and `## 11.12 Direction: a hosted platform (not a step yet)`, each under its original heading; (c) `# Roadmap Principles`, as `## Roadmap Principles`; (d) the `**Deferred**` paragraph that ends `## At a glance` (concurrency and multi-worktree, other forges, hot-reloadable routing, assurance tiers, the hosted-platform direction, RepFlow), which is direction a planner needs, under a new heading `## Deferred directions`. Release notes follow the milestone (`## 11.1.2`) is a completed item's design and stays in the archive; the release notes link to it there (D8). The text of (a)-(d) is unchanged except for the link rewrite of D10, whose one rule is: on the rules page a `#` link whose heading is on that page (11.11, 11.12) stays local, every other `#` link is rewritten to the archive. The documentation map `docs/README.md` links the page. The archive stays as the frozen record (nothing is deleted) and gains a banner line pointing at the new page.
- **D6. Every reference to "the roadmap's rule" is repointed.** A search over `.claude/commands/`, the Controller's own docs and `docs/guide/development.md` lists each place that says the rule lives in the roadmap; each is repointed to `docs/planning-rules.md` (or, for the backlog mechanics, left alone where `docs/ROADMAP.md` is the generated page). The search result is part of the report. Files under `tests/workflow_releases/` and every file in `.workflow-manager/installation.json`'s `managed` set (the installed Workflow's `scripts/` and `.claude/commands/`) are vendored or the Workflow's own and are not touched: `InstalledReleaseTest` fails on a modified managed file. A search of `.claude/commands/` finds only backlog mechanics that mention `docs/ROADMAP.md` and nothing to repoint; the report shows that empty result, and if the search does find a rule reference there, the route is an issue in `RodrigoFAbreu/workflow`.
- **D7. Titles are complete phrases.** A script lists every title in `docs/backlog.yaml` whose last word is a dangling conjunction or preposition (`and`, `or`, `one`, `the`, `of`, `to`, `a`, ...), or that is cut at the 200-character limit; the list is in the report. Line 172 (C10g-3c2, "... and one") is known; each is fixed from its archive row (a fixed title may be condensed to fit the validator's 200 characters: C10g-3c2's completed phrase, which ends "... on Codex (`CONTROLLER_LIVE_CODEX_TESTS=1`) that proves it", is longer than that) and `python3 scripts/workflow_backlog.py generate` is re-run so the page matches.
- **D8. The small repairs left by A2a.** `docs/releases/1.4.1.md`, `1.4.2.md`, `1.5.0.md`, `1.6.0.md` and `1.7.0.md` say "Release notes follow the milestone" in a backticked `docs/ROADMAP.md`. That section stays in the archive (D5), so the notes name the archive section only: they become real links to `../roadmap-archive.md#1112-release-notes-follow-the-milestone` (relative to `docs/releases/`), which `tools/check_docs.py` then checks (a backticked path it does not). Mapping requirement R4 says the same. `test_selection_survives_reordering_open_items_and_accepting_one` (`tests/test_backlog.py:208`) makes the last two items of the order open in a copy and swaps their orders; it stops discriminating once A2b is accepted (the last item then depends on its neighbour and the swap changes nothing). The repair builds the discriminating case in the copy and does not depend on live statuses: in the copy every item is set `done` except two chosen items, which get `status: next`, no `depends_on`, and distinct `order` values, so exactly two ready items exist and no `in-progress` item (an `in-progress` item would be taken before any `next` whatever the order, `BACKLOG_FILE.md`, and the ideas are never selected); the test asserts the selection is the lower-order one, swaps the two orders and asserts the selection changed to the other, so a vacuous swap fails loudly and a mutant that ignores `order` must fail it. The accept-one half is kept (accept the selected item and compare with `expected_selection`). Nothing depends on how many live items are open or which are ideas.
- **D9. In-flight declaration.** The deliverable paths (`docs/items/`, `docs/backlog.yaml`, `docs/roadmap-archive.md`, `docs/planning-rules.md`) are classified at both stages before the plan is first published, as A2a's D7 did. `docs/backlog.yaml` and `docs/items/` are excluded at both stages because acceptance edits them (the Workflow's classification requires it). `docs/roadmap-archive.md` is excluded (frozen, edited only for the banner). `docs/planning-rules.md` is excluded at the plan stage, where it does not exist yet, and **protected at the implementation stage**: acceptance never edits it and its unchanged text is the deliverable, so a later edit should stale the technical approval.
- **D10. Row links keep working from their new pages.** The rows' anchors are relative to the archive (87 of the 97 item rows, 17 of the 25 open ones: C8c, C10d-a/b, H4e-g, CL1a-e, C12b-d, C11, O5, O7, whose real designs stay in the archive). The script rewrites a link target that starts with `#` to `../roadmap-archive.md#x` on an item page and, on the rules page, by D5's rule (local when the heading is on the page, else `roadmap-archive.md#x`), and nothing else; the containment check normalises exactly that rewrite. `tools/check_docs.py` gains `docs/items/*.md` in `LINK_GLOBS`, so a dead link on a page fails the docs check, and a small pin in `tests/test_docs.py` on a synthetic tree (a dead link in `docs/items/x.md` is reported) fails if the glob is removed; `docs/guide/development.md`'s "Links and anchors" list names `docs/items/` too.

## Open points (not decided silently)

- **The archive is kept.** A2a's plan said A2b "then retires the archive". This plan keeps it frozen and linked (D5), because the item's scope says move, not delete, and the dependency prose on other repositories' rows stays only there. The owner can retire it in a later chore.
- **Name of the rules page.** `docs/planning-rules.md` (D5); a rename is one move and a link edit.
- **Rows with prose in the Manager and Workflow lane table** stay in the archive (other repositories, out of scope).

## Out of scope

The Manager and Workflow lane rows, a declared generator, a tracker, and any change to the Workflow's scripts.
