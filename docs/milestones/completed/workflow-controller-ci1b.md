## Goal

The shard planner places whole `TestCase` classes and never splits one. A few multi-test classes are large enough to hold a shard up, and the committed `tools/test_timings.json` is about 1.3 times too high against the shards' real durations (profile in #317: the shards ran 925 to 1455 s against a 1810 s planner estimate). This item cuts the multi-test giants into smaller classes that assert exactly what they asserted before, refreshes the committed timings from real CI, and raises the CI shard count only if the planner's own estimate says it pays. Target for the three CI1 items together: a code pull request's CI under 20 minutes; this item's share is 3 to 6 minutes.

One mechanism: **finer bricks for the planner** (a class is split into sibling classes; nothing else about running tests changes).

## Decisions

Each decision states one principle.

- **D1. A class is split only along its test methods, and the split changes no assertion.** The six multi-test classes that the committed timings show above 200 s (the ratchet limit of D5) are split: `PrDefectLoopLifecycleTest` (9 tests, 464 s) and `SatisfyGateLifecycleTest` (8, 257 s) in `tests/test_protocol_lifecycle.py`; `OutcomesTest` (8, 270 s) and `TheFaultStopsTest` (11, 267 s) in `tests/test_protocol_job.py`; `ReportTest` (9, 262 s) and `WaitTest` (7, 220 s) in `tests/test_pr_report.py`. Each class keeps its helpers in a non-`TestCase` base (a plain mixin class, or the existing base where the class already has one such as `_TesterCase` or `ReporterCase`) and its test methods move, unchanged and in the same order, into two to four `TestCase` subclasses of that base, grouped so the groups' measured seconds are close. A test method's body is not edited, with one named exception: `ReportNotificationTest.test_notifications_follow_the_real_pending_check_records` and `test_the_real_record_carries_the_age_of_the_pending_checks_and_a_long_one_is_a_blocker` (`tests/test_pr_report.py:641`, `:653`) build `ReportTest("test_a_green_query_is_recorded_and_the_record_holds_the_workflows_result")` by name to reuse `at_38f`/`bind`/`report`, so in each of the two bodies that one class name becomes the new sibling class that holds that method; nothing else in them changes (a module-level alias `ReportTest = ...` is not used, because the loader would collect the class twice). The test counts above are the source's; the committed timings still record 9 for `TheFaultStopsTest` and 8 for `ReportTest`, which the CP2 refresh corrects. Group the methods by measured seconds only; sharing a snapshot fixture key (`tests/fixtures.py`, `(name, snapshot_inputs)`) is **not** a grouping constraint. Every method of `ReportTest` (nine) and `WaitTest` (seven) calls `self.at_38f()` with no argument (`tests/test_pr_report.py:198, 268, 395`), so all of them share one key, and keeping shared keys together would leave each of those two classes whole. Methods that share a key therefore cross sibling boundaries freely; each sibling class that uses a key builds its tree once more, which is the repeated drive D4 measures and reports. The CP1 report lists, per split class, which fixture keys each sibling builds, so the repeated drives are countable. The old class names disappear from the inventory; the new ones take their place. No test is added, removed, renamed or skipped.
- **D2. The split is proved by identity of the test bodies, then by the run.** Before the split, the checkpoint records for each split module the sorted list of `(class, method)` names and the AST dump of each test method's body at the base commit; after it, the same method names must all be present exactly once across the new classes with identical body dumps, except the two `ReportNotificationTest` bodies of D1, whose only expected AST difference is the one class name in the `ReportTest(...)` call; the report lists those two differences and any other difference fails the checkpoint. The checkpoint's report states the comparison. The permanent proof is the existing coverage check: every planned test id runs exactly once, and `tests.test_test_shards` already refuses a plan that loses or repeats one.
- **D3. Single-test atoms are not split by this item.** The other top atoms hold one test each: the conformance `acceptance_matrix`, `protocol`, `state` and `gate_policy` suites (frozen Workflow content, one atom per file), `IsolationTest`, `CycleClosesTest`/`PersonStopsTest` and the generated `Scenario_*` classes. A class of one test cannot be made smaller by moving methods; cutting one means splitting a flow function that the scenarios and their mutation checks also call, which is a separate change with its own proof. This item names them and does not touch them. On the pull-request plan the conformance `acceptance_matrix` atom (999.7 s in the committed timings, under `LANE_CONTENTION = 1.15` on its shard) is the largest atom, so it is a floor below which the longest shard cannot go; at the current numbers it is not yet the binding limit (the balanced shards are about 1884 s at 6 and 1615 s at 7), and the guide note says exactly that. `tests.test_catalogue_determinism.CatalogueDeterminismTest` (1075.4 s) is not on the pull-request shards: `tools/test_shards.py:145-148` places it as `MAIN` under `CI_PLACEMENT`, so with `--ci-placement` it is dropped from the matrix and runs in `main.yml` after the merge; it is named only as the largest `main.yml` check, outside the shard estimate. The `acceptance_matrix` suite's `shards` option belongs to the frozen Workflow content, so any upstream change is a separate step, named in the guide and not done here.
- **D4. The timings are refreshed from real CI, never invented.** The source is the `timings-ci-attempt-<a>` artifact (highest attempt) of the latest `validate` run on a code pull request or on `main` that ran the shards, merged with `python3 tools/run_tests.py timings merge --into tools/test_timings.json DIR...` as `docs/guide/development.md` describes. The merge is an EWMA (`EWMA_WEIGHT = 0.5`), so one artifact moves each surviving atom only halfway to CI; CP2 merges the artifacts of the two or three latest qualifying runs, oldest first, and states how many it merged. If no such artifact is retained, the checkpoint stops and reports; it never edits seconds by hand. Before CP1 deletes the six stale entries (see CP1), the old classes' committed seconds are recorded in a scratch file; they are only the fallback base. The merge drops the six split classes (no longer in the inventory), so `update_timings` (`tools/test_shards.py:763-793`) would never refresh them: their keys are absent from the inventory and `_mergeable_atoms` skips them. The old classes' fresh seconds are still in the artifacts, because every `validate` run before this item merges runs the old classes and each shard record's `atoms` holds their observed seconds. So the base of each old class is taken from the artifacts, not from the stale committed value: the apportioning script folds the same artifacts the merge uses, oldest first, into the old committed value with `EWMA_WEIGHT`, using only records where every test of the old class has exactly one passing entry (the `_mergeable_atoms` rule, so the base is refreshed the way every other atom is), and with the same count rule as `update_timings` (`tools/test_shards.py:780-781`): when the old class's test count in the source (11 for `TheFaultStopsTest`, 9 for `ReportTest`) differs from the committed `tests` value (9 and 8), the first folded observation is taken outright instead of folded, and later ones fold into it. A class that no artifact observed falls back to its committed value, and the report says so. The report records, for each old class, the base used and where it came from (artifacts folded, or the committed fallback). Each new class then gets seconds apportioned from that base by the local share: the checkpoint runs each new class once locally, takes its local seconds as a fraction of the sum over the classes that replaced the same old class, and writes `base × that fraction`, as an entry `{seconds, samples: 1, tests}` (the parser requires exactly those three keys and `samples` of at least 1, `tools/test_shards.py:667-672`; `tests` is the new class's method count, which the D5 ratchet reads), so the next merge treats it as one weak observation. Because the lifecycle fixtures cache a built tree once per test process (`tests/fixtures.py:910-948`), every sibling class placed on a different shard pays the expensive drive again; so each new class is measured alone in its own process (its local seconds include its own drive), the apportioned sum is stated to be a lower bound of what CI will spend, and the report gives the estimated extra CPU time (the extra drives). The apportioned entries are computed by a short script, kept outside the repository, whose inputs (the committed and artifact seconds of each old class, the base chosen, local seconds per new class) and output the report records, so they cannot be mistaken for hand edits. The derivation is stated in the report and in the guide's refresh note; the next ordinary refresh replaces it with measured numbers.
- **D5. A ratchet keeps the giants from growing back.** `tests.test_test_shards` gains a check over the committed timings: no class atom with more than one test exceeds `MAX_SPLITTABLE_ATOM_SECONDS` (200). A class that grows past it is split, as here; a single-test atom is exempt because it cannot be split by class. The value is a constant in the test, with the reason. A negative case beside the check over the committed file feeds the same check a synthetic profile with a multi-test atom above the limit and requires it to fail, so the check cannot pass without checking anything.
- **D6. The shard count rises only on the planner's own evidence, and the runner budget it implies is flagged for the owner.** `CI_MAX_SHARDS` is 6 today, and the guide's budget is 6 shards + `package` + the managed `workflow-conformance` job = 8 Linux runners per pull request, on an account that shares 20 jobs. After the refresh, the checkpoint runs the CI planner offline with the command CI itself uses, `python3 tools/run_tests.py plan --profile ci --ci-placement --max-shards N --output <scratch>/plan-N.json` for N = 6, 7 and 8 (not `--plan-only`, which always plans with the local profile and the untracked `timings-local.json`), and reports each plan's longest shard estimate read from the plan file. The rule: if 7 shards lower the longest estimate by at least 90 s compared with 6, `CI_MAX_SHARDS` becomes 7 (9 runners per pull request, still under the account limit with one pull request in flight and tight with two); otherwise it stays 6 and the report says why. 8 is not chosen in this item: 10 runners per pull request would leave no room for a second pull request. **Owner decision, explicit route:** this item's plan gate is automatic, so no person approves the plan. Raising the budget from 8 to 9 runners therefore needs a yes from the owner: before CP2 writes 7, the worker asks the owner through SignalHub (`--choice` 6 or 7, default 6) and waits with a bounded `wait-answer` (timeout 1800 s). When the timeout passes with no answer, or the answer is 6, `CI_MAX_SHARDS` stays 6 and the report and the item page only recommend 7 with the measured numbers. The tests that pin `CI_MAX_SHARDS` follow the chosen value: `tests/test_test_shards.py:926-927` (the `(180, 2, 6)` profile and the constant) and `tests/test_scenarios.py:31` (`MAX_CI_SHARDS = 6`), which `ScenarioInventoryTest.test_the_ci_plan_stays_within_six_shards` (`:172-181`) compares with `shards.CI_MAX_SHARDS`. With about 9300 s of work against a 180 s target the planner always uses the maximum, so a 7 breaks that test unless it follows. `shards` is imported only inside `ScenarioInventoryTest.setUpClass` (`tests/test_scenarios.py:148-157`), so a module-level assignment from it cannot work. CP2 therefore drops the module constant `MAX_CI_SHARDS` and compares with `self.shards.CI_MAX_SHARDS` in the test, renaming it `test_the_ci_plan_stays_within_the_shard_ceiling`; this single test rename is outside D1's "no test is renamed", which covers the split classes only. That comparison is nearly self-fulfilling, because the plan is built with `max_shards = CI_MAX_SHARDS`; the independent budget pin is `tests/test_test_shards.py:927` (`assertEqual(shards.CI_MAX_SHARDS, 6)`, updated to the chosen value), and that line, not the renamed test, is the guard. `git grep` for the numbers `six`/`6` finds no other code pin; the prose "a ceiling of six shards" at `docs/guide/development.md:173` and the shard-count sentences at `docs/guide/ci-and-releases.md:93-95` are CP3's.
- **D7. Documentation changes with the behaviour, in place.** `docs/guide/ci-and-releases.md` updates the shard count, the runner budget, the estimate sentence and the refresh date, and names the `acceptance_matrix` floor on the pull-request plan, `CatalogueDeterminismTest` as the largest `main.yml` check outside the shard estimate, and the unsplit single-test atoms; `docs/guide/development.md` states the ratchet and the apportioning rule and updates its "ceiling of six shards" sentence (`:173`). `docs/items/workflow-controller-ci1b.md` records the measurements (the item page is an ordinary, non-protected page). The closing roadmap and `docs/ACTIVE_MILESTONE.md` records go in the acceptance, as for every milestone.
- **D8. This pull request's own CI is the proof, and the milestone says so.** The change touches `tests/` and `tools/`, so the pull request runs every shard; its elapsed CI time is compared with the baseline and recorded on the item page. The elapsed time is one defined interval for both sides: from the workflow run's `run_started_at` to the `completed_at` of its `tests-result` job (public API `/actions/runs/<id>` and `/actions/runs/<id>/jobs`). The `tests-result` job's own duration is not used, because the job starts only after every shard has finished (`.github/workflows/validate.yml:111`) and so excludes the shard runtime this item reduces. The baseline is measured with the same interval on the runs behind the 24.9 to 25.8 minutes of #317 if they are still retrievable, otherwise on the two latest code pull-request or `main` runs that ran every shard before this change; the item page records each run id, both timestamps and the interval for the baseline and for this pull request, and then the saving, together with the extra CPU time of the repeated snapshot drives (D4). If the saving is below 3 minutes the page states the shortfall and CI1c is not weakened by it.

## Out of scope

Splitting single-test atoms or the flow functions behind them (D3); parallel workers inside a shard (CI1c); the docs-only skip (done, CI1a); a change to the frozen Workflow conformance content; setup or caching.
