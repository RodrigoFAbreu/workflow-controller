## Goal

A shard runs its Controller tests in one `unittest` process, one atom after another, while its conformance suites run beside it in the second lane. The tests are subprocess and git heavy, so the runner's 4 vCPUs may be idle for a good part of a shard that lasts 12.7 to 26.7 minutes between runs. This item measures whether a shard finishes sooner with its Controller atoms spread over 2 or 3 worker processes, and adopts that only if the measurements say it pays and stays reliable. The target for the three CI1 items together is a code pull request's CI under 20 minutes.

One mechanism: **parallel workers for the Controller lane of one shard** (an opt-in executor option, default 1). The item page's two other candidates are measured or decided on paper, never built here (D5).

## Decisions

Each decision states one principle.

- **D1. Measure first, in a scratch clone, and change nothing before the numbers are in.** The measurements run in a scratch clone of the base commit (a `git clone` into a directory made with `mktemp -d`, never the working tree and never a shared `/tmp` name). The inputs are the real shards: `python3 tools/run_tests.py plan --profile ci --ci-placement` and `exec-shard` for the same shard indexes CI runs, from the committed `tools/test_timings.json`. Instruments (all exist on the measuring machine; `/usr/bin/time` does not, so it is not used): shard wall time is read from the shard record; CPU use from a small wrapper kept outside the clone that runs the `exec-shard` command and prints `resource.getrusage(RUSAGE_CHILDREN)` (user plus system seconds) and the percent-of-CPU it implies. CPU pinning: a 4-vCPU hosted runner is two physical cores with their SMT siblings, so the runs are pinned to two cores and their siblings read from `/sys/devices/system/cpu/cpuN/topology/thread_siblings_list` (on the measuring machine, a Ryzen 7 9800X3D where cpu0's siblings are `0,8`: `taskset -c 0,1,8,9`); the page states the topology used. `taskset -c 0-3` is not used, because it would pin four separate cores and overstate what extra processes gain. The result is a table in the item page, with the exact commands, so any number can be reproduced.
- **D2. The workers are a variable of the executor, not a second runner; the shards measured and the run counts are fixed now.** The measuring needs a way to run the Controller lane with N workers. The scratch clone gets an experimental patch to `execute_shard` for the measurement only; it is not committed. What CP2 commits, if anything, is the same option written properly (D6).
  - **Shards measured, by a rule fixed before the numbers.** From the base-commit plan's `lane_seconds`: shard A is the shard with the longest conformance lane (shard 0 today: its conformance lane `workflow_acceptance_matrix_test.py` is about 1120 s in `tools/test_timings.json`), and shard B is, among the others, the shard with the longest Controller lane (ties broken by the lower index). The plan's shard estimates are a near-tie (1438.858-1438.859 s for all six), so "the longest shard" is not used. The item page records which indexes the rule picked.
  - **The floor.** The conformance lane does not use the workers, and the shard's wall is about `max(controller, conformance) * LANE_CONTENTION (1.15)`. Shard A's floor is therefore about 1120 x 1.15 = 1288 s (21.5 minutes), even if its Controller lane cost nothing. Workers alone can thus cut shard A by at most about 10 percent (1439 to about 1288 s) and cannot by themselves bring the pull request's CI wall under the 20-minute target. This is stated before measuring and is part of the item's answer: the gain from workers is bounded by that floor, and the rest of the target belongs to the conformance lane (out of scope here) or to D5's candidates.
  - **Run counts, one rule.** Settings 1, 2 and 3 workers, on shard A and shard B, interleaved (1, 2, 3, 1, 2, 3, ...) so runner drift hits every setting equally. Every setting gets three interleaved rounds first. A setting ends at its first D3 failure, or if after the three rounds its median misses D4's speed or CPU limit on either shard. Only a setting that still passes after three rounds is extended, interleaved with the 1-worker baseline, to 9 runs per shard for D3's flake count. The median and the range of each setting are reported, never the best run.
  - **Duration and ownership.** Three rounds are 2 shards x 3 settings x 3 = 18 shard runs of roughly 15-25 minutes each on the pinned CPUs, one after another: about 5-8 hours. Extending up to two passing settings to 9 adds at most 2 x 2 x 6 = 24 runs. The measurement runs as an owned background task with a Monitor on its log, never in the foreground, and writes each run's record and log as it goes so it can be resumed.

- **D3. Reliability is measured with the speed, and it is a veto.** One environment policy applies at every N, including the 1-worker baseline and the shipped N = 1: `HOME` stays inherited, exactly as `shard_environment` does today, so N and `HOME` are never confounded (tests that read `~/.codex`, the known `fake_codex_contract` failures, or the global git identity behave the same at every N). **Placement of the worker directories (I1, round 4).** At N = 1 the environment is exactly today's, in both entry points: a direct `exec-shard` (what CI runs, `--results-dir results` inside the checkout, `tools/ci_workflows.py:352`) inherits the runner's environment and sets no `TMPDIR` or `XDG_STATE_HOME`, and the local runner's `shard_environment` keeps its `<results>/shard-<i>/{tmp,state}` (its results directory is outside the repository by default). Nothing about the shipped N = 1 environment changes, and the 1-worker baseline of CP1 is that same environment. Only at N > 1 does each worker get its own `TMPDIR` and `XDG_STATE_HOME`: two `tempfile.mkdtemp` directories per worker, created under the inherited `TMPDIR` (the system default when it is unset), unless that parent lies inside `results_dir` or inside the repository checkout, in which case under the system default temporary directory. Worker directories are therefore never inside the git checkout (a test that makes a scratch directory and runs git there never finds the checkout above it) and never inside `results_dir`, so the `if: always()` upload of `results/` never carries a worker's `tmp` or `state`. `mkdtemp` names are unique, so shards run together by `--jobs` never share a worker directory. The executor removes a shard's worker directories when its workers have ended, on the failure and interrupt paths too, and a leftover is reported by the leak scan's existing path rather than ignored. Each worker has its own process-group session under the shard's. Over the repeated runs the record shows: shard failures, tests that passed alone and failed with workers, leaked processes the shard's scan reports, zombies, and collisions on shared names. Any failure or leak that appears only with workers, and that is not fixed by isolating the shared name, rules the setting out. Flake rate is counted over the 9 runs of D2 for a setting that reaches them, and the result must be 0 failures; one failure is the end of that setting. The zombie and shared-`/tmp` hazards named in the item page are the first things looked for.

- **D4. Adopt only what the numbers support, by a rule written before the numbers.** The criterion is on the CI wall, which is the maximum over all six shards. A setting is adopted only if (a) its median shard wall is at least 15 percent below the 1-worker median on shard A and on shard B (D2's rule), (b) with that setting the six-shard maximum falls: the setting is also run three times on each of the other four shards, interleaved with their 1-worker runs, and none of them is slower than its 1-worker median, so the maximum over the six is the proof and two shards do not stand in for all six, (c) no veto from D3, and (d) the CPU time of each measured shard rises by no more than 25 percent (the repeated start-up of Python and of the per-worker discovery is the cost). Because of the floor in D2, the 15 percent on shard A can only be met if shard A's conformance lane is not the limit; if it is not met there, the setting fails speed and the item page says the conformance lane is the bound. If no setting passes, CP2 commits no code: the result is recorded as the answer, the item is accepted as an investigation with a negative result, and the follow-up the numbers suggest (if any) goes in as an item on the backlog by the usual route. If a setting passes, CP2 writes the option properly (D6).

- **D5. The other two candidates are decided, not built.** Test selection by changed paths is not built here: replaying the last 20 pull request diffs needs the pull request history from GitHub, which the Controller reads through the git-host adapter, and a selector is a second mechanism; the item records it as the next item when the workers do not reach the target, and states the one rule it would need (never skip a test that failed in the full run; `main` always runs all). A larger runner needs the owner's billing decision, so the item page records the question and the measured gain that would justify it, and asks nothing else. Neither changes code or CI.
- **D6. The option, if adopted, is small and keeps the proof.** `--controller-workers N` on `exec-shard` and on the local runner, which is the bare `python3 tools/run_tests.py [names...]` (its subcommands `plan`, `aggregate`, `timings` and `main-check` take no such option); default 1 on both, and 1 is identical to today's records except their timing fields (`started_at`, `ended_at`, `wall_seconds`, per-atom `seconds`) and `argv`: an N = 1 record omits `controller_workers`, and an N = 1 shard runs in the same environment as today (D3). The local runner already runs several shards at once (`--jobs`), so its `--controller-workers` default stays 1 and the help text and guide say that shards x workers is what the machine must carry. The shard's Controller atoms are divided over N worker processes by the planner's own estimates (the existing assignment function, longest first); each worker runs its atoms through the same `RecordingResult` and writes its records, and the executor merges them, so the exactly-once coverage proof, the per-atom results, the leak scan and the exit status are those of today. N is clamped, never refused, above what a shard can use: a shard runs with `min(N, its Controller atom count)` workers, and the `exclusive` shard (atoms that must run alone) always with one, so a bare local run whose name selection leaves a shard one Controller atom just runs it with fewer workers; only N below 1 or not an integer is refused. The record's `controller_workers` is the number of workers actually used (absent when that is 1), so the timings exclusion below follows what ran. The plan digest does not change (a runner option, not a plan input), so a recomputed plan still matches.
  - **Timing feedback (I2).** The planner's cost model (`lane_seconds`, `assign_lanes`, `shard_count`) assumes a serial Controller lane, and a worker's per-atom `seconds` include contention from the other workers, so folding them into the EWMA would raise the committed profile with no change to the code under test. Decision: a record with N greater than 1 carries `controller_workers: N`, and `update_timings`/`_mergeable_atoms` exclude every such record from the profile, as a stated, tested rule (they are still aggregated for results, only not for timings). **Schema:** `controller_workers` is an optional key, not a schema version: `validate_shard_result` (`tools/test_shards.py:520-537`) accepts it, as an integer of at least 2, under both `_RESULT_KEYS` versions, and a record without it means one worker, so records from before the change, reused or merged, still validate and an N = 1 record is today's record. The planner is not told N, the six-shard balance is planned from 1-worker estimates and is not re-planned under workers, and `shard_count` does not change.
  - **Where 1-worker records come from under reuse, and which N `main` runs (I1).** `tools/ci_workflows.py` has one `tests` job with one `shard` step (`exec_shard`), defined in `validate_workflow()`, the reusable `validate.yml` that both `ci.yml` and `main.yml` call. On `main` that step runs whenever `tests-from-run` is empty: `CI_MAIN_REUSE` not `on`, a `workflow_dispatch` (`ci_reuse.find_candidate` refuses any event but `push`, `tools/ci_reuse.py:88-89`), `decide` refusing on a tree or digest mismatch, or the reuse job crashing. **Decision:** `validate.yml` gets a second optional `workflow_call` input, `controller-workers` (string, default `"1"`), and the shard step passes `--controller-workers ${{ inputs.controller-workers }}`. Only `ci.yml` (the pull request workflow) sets it, to the adopted N; `main.yml` does not, so every shard `main` runs itself is N = 1 and `main` always produces 1-worker records. Under reuse `main` runs no shards: `validate` re-aggregates the pull request run's `timings-ci-attempt-*` records (lines 443-475) and `tools/ci_reuse.py verify` checks only the tree and the plan digest, so records of an adopted N > 1 flow through unchanged. Reuse is **not** touched (refusing N > 1 records would make `main` run the full shards again, about 25 minutes of main CI, and undo the reuse the CI time budget relies on).
  - **The `ci` profile is refreshed from a CI-sourced N = 1 run (I2).** `tools/test_timings.json`'s `ci` profile is planned for 4-vCPU hosted runners, and CI1b refreshed it from the hosted runners' `timings-ci-attempt-*` artifacts (`docs/items/workflow-controller-ci1b.md`), never from a developer machine; local seconds would shift every atom and with it the six-shard balance. So the refresh is: run `Main` by `workflow_dispatch` (it never reuses, and its shard step is N = 1 by the wiring above), download that run's `timings-ci-attempt-*` artifact, and pass it to `timings merge`. This is done when atoms are added, renamed or split, or when the item page's checks show drift. The CP1 commands, which run on the measuring machine, are for the measurement table only and never feed the `ci` profile; a local N = 1 run may feed a local profile. `timings merge` prints, when it excluded records, how many and why ("N records with controller_workers > 1 excluded from the profile"), and its summary says so when it excluded all of its input, so a freeze is visible rather than silent. New and renamed atoms use `_mean_per_test` estimates until that refresh, the same bound as today between refreshes. The guides state this procedure. If a worker setting is not adopted, nothing changes and `main` keeps producing N = 1 records as it does now.
  - A worker dying, a worker that reports an atom not assigned to it, or two workers reporting one atom fails the shard with the executor's existing refusal path, never a silent pass. CI wiring (`tools/ci_workflows.py` generating `validate.yml`, `ci.yml` and `main.yml`) passes the adopted N only from `ci.yml` through `validate.yml`'s `controller-workers` input (above), and the generated files are regenerated, never edited by hand.
- **D7. Documentation changes with the behaviour, in place.** `docs/guide/ci-and-releases.md` (how a shard runs, the measured timings) and `docs/guide/development.md` (the option and how to measure) are updated; the item page records the measurements, the decision of D4 and the two candidates of D5. Plans and completed-milestone narratives are not edited afterwards.
- **D8. This pull request's own CI is a measurement, and the milestone says so.** If the option is adopted, the pull request's first full run and the runs after the merge are compared with the CI1b baseline (the longest shard 1439 s estimated) and recorded in the item page, with the runner-noise range (12.7 to 26.7 minutes before) stated beside them. A comparison that cannot tell the change from the noise is recorded as such, not as a gain.

## Out of scope
