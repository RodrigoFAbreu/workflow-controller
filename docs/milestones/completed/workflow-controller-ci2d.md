## Goal

Decide what runs, and when, after a merge or a push, and keep the committed timings fresh without a person. The item page lists three scope items (11, 12 and 13 of the owner's decision of 2026-11-16 on the CI2 page) and the automation of scope item 1. They are one theme (trigger policy), and each is small, so they stay in one item of five checkpoints:

| scope item | what changes | checkpoint |
| --- | --- | --- |
| 12. skip the test shards on `main` for a documentation-only push, keep the managed conformance job | `tools/ci_changes.py` decides for a `push` as it does for a pull request | CP1, CP2 |
| 13. do not run the full suite on every intermediate Draft-PR push | a Draft PR's head runs the shards from the first review-bound head (D2); a ready PR always runs them | CP1, CP2 |
| 11. split the mutation job into 2 or 3 jobs inside the six-runner cap | `after-merge-mutations` (and `release-target-mutations`) become a three-leg matrix over `main-check --shard I --of N` | CP3 |
| automate the timings refresh | a scheduled workflow merges the shard records of recent pull-request runs and opens a pull request when the file changes | CP4 |

The measured motivation is on the item page: 101 cancelled CI runs since 12 November cost about 5,500 runner-minutes, documentation-only merges to `main` run all shards (about 155 runner-min), and the after-merge determinism (12.6 to 15.7 min) and mutations (11.3 to 17.2 min) jobs delay releases. The effect is read off the planner and the first runs, never promised: CP5 records the predicted figures, and [#317](https://github.com/RodrigoFAbreu/workflow-controller/issues/317) stays open until its last slice merges.

## What exists

- **Documentation-only detection.** `tools/ci_changes.py detect` (CI1a) writes `code=false` only for a `pull_request` event whose merge ref changes paths that are all in the documentation set (`DOCS_PREFIXES`, `DOCS_TOP_LEVEL`, `DOCS_FILES`; `tests/test_ci_changes.py` keeps the set honest); every other event, and any doubt, is `code=true`. `tests.yml`'s `changes` job checks out with `fetch-depth: 0`, `plan` and `tests` need `code == 'true'`, `docs`, `docs-tests`, `package` and the `tests-result` gate (`require`) run on every event.
- **The calling workflow.** `ci.yml` is generated by `tools/ci_workflows.py` (`ci_workflow()` and `_main_check_job`): `on: pull_request` (default activity types), `push` to `main`, `workflow_dispatch`; `reuse` (main only), `validate` (calls `tests.yml`), then `after-merge-determinism` and `after-merge-mutations` (a plain job each, `python3 tools/run_tests.py main-check MODULE`), then `build-publish`. `build-publish.yml` has `release-target-determinism` and `release-target-mutations` built from the same function. `MAIN_TEST_MODULES` maps the two check names to `tests.test_catalogue_determinism` and `tests.test_scenarios_negative`.
- **`main-check`.** `cmd_main_check` in `tools/run_tests.py` plans the one module with `shards=1`, runs shard 0 and fails closed on an empty or short selection, a skip or a failure (`executed_problems`). `tests/test_scenarios_negative.py` generates one `TestCase` class per mutation (about 50), each its own planner atom with committed timings, so the module splits cleanly by atom.
- **The six-runner proof.** `tests.test_ci_workflows.RunnerLimitTest` flattens the called workflows into one job graph for every event and every `CI_MAIN_REUSE` mode and sums the heaviest set of concurrent jobs plus the runners outside the graph. On a push to `main` after `validate` that is determinism, mutations, the managed `workflow-conformance` job and `reuse-report`: four. Three mutation legs make it six, which is the limit.
- **How a Draft PR reaches `ready`.** `controller/milestone_branch.py` (`_readiness`) requires, when the binding's policy says `ready_requires_green_checks`, green checks **before** `gh pr ready`, at the acceptance commit `A` exactly (the tip must be `A`); a person can also convert a ready PR back to a draft (`merge_held`). So at `A` a Draft PR's head must have run the shards: waiting for a `ready_for_review` run would deadlock the Controller.
- **The acceptance gate's `ci_green` path.** Under the automatic acceptance gate the Controller's `pr_review_result` reporter (`controller/pr_report.py`, rows 38f/38g) queries the pull request at `anchor_commit(work_item)`: the technical approval's `reviewed_content_commit` when it carries it with `approved_review_content_id`, else `reviewed_implementation_head`. That is a draft head **before** the acceptance commit `A`. `scripts/workflow_gate_policy.py` then records `acceptance_satisfaction`, which requires `ci_green` (the checks at that commit are `success`) and `no_standing_pr_objection` (no failed check). So the checks at the anchor commit must be a real run of the shards, or acceptance would rest on a green `tests-result` that ran no test and every failure would surface only at `A`, after the acceptance commit, where readiness stops at `post_acceptance_commits`.
- **The timings merge.** `run_tests.py timings merge --into FILE DIR...` folds shard records into `tools/test_timings.json`. CI2 ran it by hand over the artifacts of three pull-request runs. Both `results-<shard>-attempt-N` and `timings-ci-attempt-N` (the `results/selected/` records, the plan and `tree.txt`) are uploaded by `tests.yml`; a run that skipped the shards uploads no `timings-ci-attempt-N`, and a reused `main` run's copy duplicates the pull-request run's records (the reason for D6's source rule).

## Decisions

- **D1. A push is classified over the pushed range.** For a `push` event `detect` reads the event payload (`GITHUB_EVENT_PATH`): `before` and `after`. It is `code=false` only when `before` is not the all-zero id, `after` equals `HEAD`, `before` resolves to a commit, and every path of `git diff --name-only --no-renames -z before HEAD` is documentation. A push of more than one commit is judged by the whole range `before..HEAD` (the squash-merge policy makes `main` pushes single-commit; the rule is the same for any range, and a range of documentation only is `false`). A force-push (an unreachable `before`), a new branch, an empty or unreadable payload or diff and any `git` failure are `code=true`. The documentation set is the pull request's, unchanged, because the pushed range is judged by what its files are, not by who pushed them. `workflow_dispatch` stays `true`.
- **D2. A Draft PR's head runs the shards from the first head the acceptance gate can read.** For a `pull_request` event whose payload has `pull_request.draft` true, `detect` is `code=false` unless the head commit (`HEAD^2` of the merge ref) holds a work item whose `phase` is in the **review-bound set** and the base (`HEAD^1`) either lacks that item or holds it at a phase **outside** the set (no phase order is used, so no order has to be defined). The partition of `workflow_state.KNOWN_PHASES` is explicit and a test asserts it covers every known phase exactly once, so a new phase cannot be silently skipped. **Review-bound set (signal, `code=true`):** `SELF_REVIEWING_IMPLEMENTATION`, `AWAITING_LOCAL_IMPLEMENTATION_REVIEW`, `AWAITING_MANUAL_EXTERNAL_IMPLEMENTATION_REVIEW`, `AWAITING_EXTERNAL_IMPLEMENTATION_REVIEW`, `APPLYING_REVIEW_FEEDBACK`, `AWAITING_FUNCTIONAL_REVIEW`, `FIXING_FUNCTIONAL_FINDINGS`, `AWAITING_USER_ACCEPTANCE`, `AWAITING_TECHNICAL_APPROVAL` and `MILESTONE_COMPLETE`. **Excluded set (no signal, `code=false`):** `PLANNING`, `SELF_REVIEWING_PLAN`, `REVISING_PLAN`, `AWAITING_LOCAL_PLAN_REVIEW`, `AWAITING_MANUAL_EXTERNAL_PLAN_REVIEW`, `AWAITING_EXTERNAL_PLAN_REVIEW`, `AWAITING_PLAN_APPROVAL`, `AMENDING_PLAN`, `IMPLEMENTING` and `LEGACY_READY`. **Which phase the anchor carries:** review-stage writes stay uncommitted, so the `WORKFLOW_STATE.json` committed at the anchor (`anchor_commit`, `controller/pr_report.py:68`, the technical approval's `reviewed_content_commit`) holds the phase at commit time, which is most often `APPLYING_REVIEW_FEEDBACK` (the accepted `workflow-controller-ci2c` anchor `f953ccf4` and `workflow-controller-ci2b` anchor `3d3ca2f6`) or `SELF_REVIEWING_IMPLEMENTATION` (`workflow-controller-ci2` anchor `0277c8e8`), not an `AWAITING_*_REVIEW` phase; both are in the set. The signal is therefore on or before the anchor commit, so the `pr_review_result` reporter's `ci_green` (rows 38f/38g) reads a real run of the shards, and so do the head at `A` (`_readiness`) and every later head. Intermediate heads while the item is `PLANNING`, `IMPLEMENTING` or any plan-stage phase have no signal and skip the shards. A payload with no `draft` key, an unreadable state file at either parent and any doubt are `code=true`. A pull request that is not a draft runs everything exactly as today. This is the literal owner scope ("run it when the pull request is ready for review") adjusted for the Controller's order (green checks, then ready): see O3.
- **D3. `ready_for_review` starts a run.** `ci.yml`'s `pull_request` trigger names its types, the three defaults plus `ready_for_review`, so a person who marks a draft ready gets the full suite on that head at once. A skipped draft run is a green `tests-result` with the reason in the job summary (`detect` already writes it); making it red would make the Controller's pull-request defect loop treat every intermediate push as a defect. The residual is stated in the pages: between a person marking a draft ready and the new run registering its checks, the draft run's green checks on the same commit are visible for a few seconds, so a merge in that window is possible. The Controller never does it (D2), and branch protection's required checks make the window the only exposure.
- **D4. The mutation job is a matrix of three legs over one plan.** `run_tests.py main-check MODULE` gains `--shard I --of N` (both or neither; `N` at least 1, `I` in `0..N-1`). It plans the module with `shards=N` (the planner balances atoms by committed timings), runs shard `I`, and its fail-closed rule (`executed_problems`) is applied to that shard's own ids: an empty slice, a short or different set, a skip or a failure fails the leg. Without the flags it is today's single run. `_main_check_job` takes a leg count; `after-merge-mutations` and `release-target-mutations` carry `strategy: {fail-fast: false, matrix: {shard: [0, 1, 2]}}` and a job name with the shard, so the job id, the `needs.<id>.result` the release gate reads and `build-publish.yml`'s inputs are unchanged: a matrix job's result is `success` only when every leg succeeded. `MAIN_CHECK_LEGS` in `tools/ci_workflows.py` holds the counts (`mutations` 3, `determinism` 1). Union coverage is proved offline, not trusted: a test plans the module for N legs and requires the legs' ids to be disjoint and to equal the module's inventory, and the generated-workflow tests pin the matrix, the flags and the legs' concurrency: `max-parallel` is left unset (three legs, within the six-runner proof of `RunnerLimitTest`).
- **D5. Determinism is not split here.** `tests.test_catalogue_determinism` runs every scenario twice, in two clones, and compares summaries inside one test (12.6 to 15.7 min). Splitting it means partitioning the catalogue and a cross-leg comparison, a different mechanism. After D4 the release wait is bounded by determinism, not by mutations, and the item records that honestly (CP5): the item page's "6 to 9 min" is reached only by the follow-up of O1.
- **D6. The timings refresh is a tool and a scheduled workflow, with a token that can start the required checks.** `tools/timings_refresh.py` (stdlib only; it calls `gh` through a runner argument so tests pass a fake) has `collect`, which lists the newest successful `ci.yml` runs with `event == pull_request` (never `main`, whose reused runs duplicate records) that carry a `timings-ci-attempt-*` artifact with shard records, downloads at most `--runs` of them (default 3) to distinct directories and drops a shard record whose `(plan_digest, shard)` was already taken; and `plan-change`, which runs `run_tests.py timings merge` into a copy, then prints the untimed share before and after and exits 0 with `changed=true|false`. The scheduled `timings-refresh.yml` (weekly, plus `workflow_dispatch`; a workflow of its own so it can never hold `ci.yml`'s `main-release` slot, like `main-reuse-report.yml`) runs both and, when the file changed, pushes the branch `ci/timings-refresh` and opens the pull request titled `ci: refresh the shard timings (automated)`. **Required checks need a real `pull_request` event.** `main`'s ruleset (no bypass) requires `validate / plan`, `validate / tests-result`, `validate / package`, `workflow-conformance` and `PR title`. A pull request opened with `GITHUB_TOKEN` starts no `pull_request` workflow, and a `workflow_dispatch` of `ci.yml` reports only the three `validate / *` contexts: `pr-title.yml` and the managed `workflow-conformance.yml` run on `pull_request` only. So the push and the pull request use a repository secret `TIMINGS_REFRESH_TOKEN` (a personal access token or GitHub App token with `contents` and `pull_requests` write), whose pull request does start every `pull_request` workflow and so collects all five checks; there is no dispatch step. Without the secret the workflow does not open a pull request: it fails the job with a message that names the secret and the setting (a refresh that could never merge is worse than none). The repository setting "Allow GitHub Actions to create and approve pull requests" is not needed with the token and is documented as such. **Re-runs are idempotent:** the branch `ci/timings-refresh` is reset to the new tip with `git push --force-with-lease` (it is a bot-owned branch), and when an open pull request from that head exists it is updated (title and body) instead of a second one being opened; a closed or merged earlier pull request is not reused. A refresh that produces a file the staleness ratchet refuses is not opened: `CommittedTimingsTest` reads the checked-out `fixtures.REPO_ROOT / shards.CI_TIMINGS` and has no parameter for a copy, so the workflow writes the merged file into the runner's checkout (on the `ci/timings-refresh` branch, uncommitted) and runs `python3 tools/run_tests.py tests.test_test_shards` there before it commits; a failure there discards the change and opens nothing. `plan-change` takes `--output` for the path it writes and the tests assert the workflow orders merge, ratchet, then commit. **Credentials are split by step.** Listing the workflow runs and downloading their artifacts in this private repository need `actions: read`, which the refresh token (`contents` and `pull_requests` write) does not grant and is not asked to. So the workflow's `permissions` are the minimum that does it, `contents: read` and `actions: read` (the same grant `REUSE_PERMISSIONS` and `VALIDATE_CALL_PERMISSIONS` give the reuse path in `tools/ci_workflows.py`), and the `collect` step runs with `GH_TOKEN: ${{ github.token }}`; only the push and the pull-request steps use `TIMINGS_REFRESH_TOKEN`, which never reaches `collect`. See O2.
- **D7. Measurement, not promises.** CP3 records the planner's three-leg estimate of the mutation module (legs, longest over mean) next to today's one-shard figure; CP5 puts it and the old measured job times on the item page. The first `main` run after the merge is the real figure and is added to the page by the next slice that edits it, not claimed here.

## Open decisions

No repository decision-record "Open decision" row is touched (this repository has no `docs/TECHNICAL_DECISIONS.md`). Four owner decisions, each provisional:

- **O1. Determinism split.** D5 leaves the determinism job whole, so the release wait falls from about 17 to the determinism job's 12 to 16 minutes, not to 6 to 9. CP5 adds a backlog item `workflow-controller-ci2h` ("CI: split the after-merge determinism check (#317)", depends on this item) for it. **Owner: say "do it in CI2d" before CP3 starts and the plan is amended; or drop the item from `docs/backlog.yaml`.**
- **O2. The refresh pull request's token.** Decided above (D6): a repository secret `TIMINGS_REFRESH_TOKEN` is required, because the default token cannot produce the required `pull_request` checks. **Owner: create the secret before the first scheduled run; the workflow fails with a named message until then.** That the automated pull request then collects all five checks is GitHub behaviour and not provable offline: the first run is the proof, and CP5 states it as unproven until then.
- **O4. After-merge checks on a documentation-only push and on a branch dispatch.** The `after-merge-*` jobs run on any non-`pull_request` event once `validate` succeeded. They still run on a documentation-only push to `main` (intended: the literal scope skips only the shards, and the release gate needs them; about 30 runner-minutes remain), and with D6 no longer dispatching `ci.yml`, no extra branch run is started by the refresh. A manual `workflow_dispatch` of `ci.yml` on a branch still runs them, as today; that is intended and documented in CP5.
- **O3. The draft rule.** Scope item 13 says to run the full suite "when the pull request is ready for review". The Controller requires green checks before it marks a pull request ready, so that would never come. D2 runs the shards on a draft from the first review-bound head (D2's set), the earliest the acceptance gate's `ci_green` anchor can be. **Owner: if you want the Controller to mark ready first and wait for checks after (a change to `controller/milestone_branch.py`, its own item), say so; D2 is then replaced by "no shards on any draft".**
