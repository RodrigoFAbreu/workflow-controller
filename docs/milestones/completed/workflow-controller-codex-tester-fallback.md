## Goal

C10g-3c1 let a route name Codex for the tester and made `job._run_functional` run the route's harness, but selection still takes the chain's first entry, a Codex tester's usage record is empty, and no real functional round has run on Codex. This item (1) chooses the tester's entry before the spawn by walking the chain as H9b does for workers, with the tester's own selection-time causes; (2) records the Codex tester's cost and its telemetry row; and (3) runs one real functional round on Codex by hand and records what it proves.

## What exists

- `route_select.select(chain, unavailable, admit)` (H9b) walks a chain: an entry whose `unavailable(entry)` returns an error is skipped (`launcher_unavailable`), a held provider is skipped with every later entry of it (`usage_held`), the first admitted entry is `chosen`; none admitted is `held` (a hold) or `unavailable` (the first error). `execute_step` uses it for a worker with `len(chain) > 1`, records `worker_route.selection` (`position`, `length`, `skipped`), and `telemetry.dimensions` already reports `chain_position` and `chain_skipped` from that block.
- `job._run_functional` takes `route_options.resolve(FUNCTIONAL_TESTER)` (entry 0), calls `_functional_launch(route.harness, functional)` (which refuses a missing option as `functional_tester_unavailable`, cause `no_binary`, before `usage_gate`), asks `usage_gate(route, provider=chosen.provider)`, and ends a refusal raised by the launch at the gate with `not_started`. `RoutingOptions.chain(role)` returns the whole chain.
- `codex_tester.launch_codex_functional` checks the role, resolves the binary (`review.resolve_binary`), requires `codex_build.is_verified` (cause `enforcement`), then builds the bridge (a missing `auth.json` is refused there). Its `_settle` reads `usage.read_codex_home` readings and `review.scan_rollouts(...).subagents`, but not the rollouts, so `job._review_usage_fields(review.CODEX, ...)` (which reads `out["usage_rollouts"]`) builds an empty Codex usage record for a tester (C10g-3c1 D7).
- `telemetry.rows` lists a record only when `is_worker_job` (a `telemetry`, `worker_streams` or `worker` block) or `is_courier_job` holds; `telemetry.dimensions` reads the route's `harness`. A launched Claude tester has a `telemetry` block (`out["telemetry"]`); a Codex tester has none, so it has no row.
- `tests/test_codex_tester_live.py` is the opt-in live module (`CONTROLLER_LIVE_CODEX_TESTS=1`): one `run_tester` turn; it does not go through the job.

## Decisions

- **D1. A chain of one is today's path; a longer chain selects.** `_run_functional` keeps its present code when `len(route_options.chain(FUNCTIONAL_TESTER)) == 1` (resolve, `_functional_launch`, `usage_gate(route, provider=...)`), so the *selection path* of a single-entry configuration is unchanged for every harness (no probe, no `selection` key, the launch called with today's keyword arguments) and a Claude-only or single-entry Claude tester's whole record is byte for byte unchanged. A launched Codex tester's record gains the `usage_rollouts` figures and the `telemetry` block whatever the chain length (D6, D7), a single-entry Codex chain included. With more than one entry it calls `route_select.select(chain, probe, admit)` once, **before** the usage gate admits anything else and before any record exists, with `admit = _chain_admit(usage_gate)` (the worker's own helper) and `probe = _tester_probe(functional, runtime_root)`. The chosen entry's route replaces `route` for everything after (the record's `worker_route`, the launch, the usage figures); `_functional_launch` is then called for the chosen harness. Nothing after the selection re-selects.
- **D2. Selection-time and after-spawn causes.** A cause is *selection-time* when it can be decided from the machine before anything is started, and it makes `route_select` skip the entry: for a Codex entry its functional options are missing (`harnesses["codex"]` has no entry with an `operator_home` and a `binary`; `no_binary`, as `_functional_launch` already refuses it), the launcher binary cannot be resolved (`review.resolve_binary` refuses; `no_binary`), for Codex the operator's Codex home has no `auth.json` (no login; cause `enforcement`, the cause the launch's own bridge build reports for it, and the text names the file), and for Codex `codex_build.is_verified` is not ok (`enforcement`, text as the launch's). Login is a selection-time cause for Codex only, deliberately: a Claude entry whose home has no `.credentials.json` is not probed for it, because the Claude tester's existing behaviour is kept (such a tester ends after the spawn like any other after-spawn cause, and the next entry is not tried). Every other `TesterUnavailable` (the role refusal, the runtime-root containment, the bridge build, the controls, a breach, anything raised inside `launch`) *happens after the selection*: the job ends at `functional_tester_unavailable` or its findings gate as today and the next chain entry is **never** tried (a started tester is never retried on another entry, and a refusal inside the launch has already admitted usage and written a record). The skipped entries use `route_select`'s existing cause `launcher_unavailable`; no cause is added to `route_select.CAUSES`, no new exit code, gate or setting. The probe's first error text is the gate text when every entry is unavailable.
- **D3. The probe reuses the launch's own primitives.** `codex_tester.selection_error(operator_home, binary_name, runtime_root, system_path=...)` returns the `TesterUnavailable` or `None` for a Codex entry, composed of `review.resolve_binary`, an `auth.json` file check and `codex_build.is_verified` -- the same calls `launch_codex_functional` makes, which still makes them itself (the build is re-verified at the launch; a build that changes between selection and launch ends at the gate as today). A Claude entry has no missing-options cause: `_functional_launch`'s Claude branch has no such check (an absent `harnesses["claude-code"]` falls back to the top-level keys, and `cli._functional_options` always supplies both), and the probe does not add one, so the single-entry Claude path stays as it is. A Claude entry's probe is `review.resolve_binary(binary_name)` alone, whose `ReviewLaunchRefusedError` the probe converts to `functional_review.unavailable(UNAVAILABLE_NO_BINARY, ...)`, as the Codex launch does, so every probe returns a `TesterUnavailable` (D4 reads the first error's `message` and `evidence["cause"]`); for a one-entry chain it is not run, so the Claude launch keeps resolving its binary where it does today.
- **D4. Outcomes of the selection.** `HELD` returns `_as_usage_hold` exactly as the worker path does (nothing recorded). `UNAVAILABLE` ends the step at `functional_tester_unavailable` with one `GATE_BLOCKED` record built as C10g-3c1 D3 builds it (gate, head, `detail` the first error's message, `cause` its cause), whose `functional` block also carries `selection` (the skipped entries), and no usage token, PLANNED or LAUNCHED record. `CHOSEN` records `worker_route.selection` (`position`, `length`, `skipped`), the shape `telemetry.dimensions` reads, so `chain_position` and `chain_skipped` appear for a functional job without a change to `telemetry.dimensions`.
- **D5. Independence is unchanged.** The tester is outside the reviewer-independence rule (C10g-3c1 D5: `review_mode.worker_families` counts adapter role `worker` only). A chosen fallback entry therefore changes no reviewer decision and no mixed-lane stop; a test pins that routing and choosing a second-entry Codex tester leaves `worker_families` and the reviewer choice as they were.
- **D6. A Codex tester's usage record is the rollouts' (C10g-3c1 D7 closed).** `codex_tester._settle` gains one guarded step that stores `scan.rollouts` of the same end-of-job scan the `subagents` step makes as `result["usage_rollouts"]` (the scan runs once; the two keys come from it), and `launch_codex_functional`'s initial result dict gains `usage_rollouts: []`. `job._review_usage_fields(review.CODEX, ...)` then builds the record from them with no change; `_codex_end_block` already takes the readings. The usage budget and the `usage` command read the same record they read for a Codex review. A Claude tester's fields are untouched.
- **D7. A launched Codex tester has a telemetry row.** When the tester was launched (`launched` true, not `not_started`), `finish` writes `record["telemetry"]` for a Codex route: the session block of no stream (`worker_stream.session_telemetry([])`, whose `no_result` problem is replaced by the existing `no_stream` problem, as `telemetry.derive_block` does for a worker record with no readable stream) with `job_seconds` and `dimensions(record)` (role, model, effort, `harness` `codex`, versions, `chain_position`/`chain_skipped` when selected). The tokens and cost of the tester are in its `usage` record (D6); the telemetry row shows them as unavailable, as `derive_block`'s row does for a record with no readable stream (no Codex worker exists before H4a, and a Codex review courier row has no block). `telemetry.rows`, `dimensions` and `is_worker_job` do not change, and a Claude tester's `telemetry` block is the one `launch_functional` already leaves.
- **D8. The first real round is operator-run and is a flow, not a mechanism.** `tests/test_codex_tester_live.py` gains an opt-in test (same guard, plus a recorded `verify-codex` build) that runs `codex_tester.launch_codex_functional` through `_functional_launch`'s Codex entry on the existing fixture and asserts: the outcome is `ran`, no breach and nothing unbound, the sandbox is removed by `review.settle_functional`, and `usage_rollouts` is non-empty (the usage figures are real). The lane then runs one functional round of a small throwaway item on Codex through the Controller (`--role-harness functional-tester=codex --role-model functional-tester=gpt-6.1-sol --role-effort functional-tester=high`, `workflow-controller verify-codex` first), and the result (record, usage block, telemetry row, any defect) is written to `docs/ACTIVE_MILESTONE.md` and the guide in place (this plan is not edited after approval). A defect the round exposes is filed as its own issue and not fixed here.

## Functional review

All flows are offline and unit-level, run one module at a time with `TMPDIR` set to the tester's scratch area (its `/tmp` is read-only and it has no user namespaces): `python3 -B -m unittest tests.test_route_select tests.test_codex_tester_launch tests.test_telemetry_harness tests.test_review_mode`, then `tests.test_functional_select` and `tests.test_functional_codex_route` (they use only fakes), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. `tests.test_functional_sandbox`, `tests.test_functional_lifecycle` and `tests.test_cli` are `environment` flows (they need user namespaces or a writable `/tmp`) and are operator-run; so is the live Codex round (`CONTROLLER_LIVE_CODEX_TESTS=1`, real `codex`, `bwrap` and a recorded `verify-codex` build). The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **A `feat:` whose Codex half is proven by one round.** The selection and usage figures are tested with fakes; the live round is one real turn on the operator's credentials. The default stays Claude, and nothing changes unless an operator configures a chain or routes the tester to Codex.
- **Selection and launch can disagree.** The probe checks the build and login before the spawn and the launch checks again; a change between them ends at the gate (after-spawn, never retried). This is the intended split (D2) and is documented.
- **`job.py` is large.** The single-entry branch is kept as it is and asserted unchanged; the new code is one probe and one call.
- **Telemetry row for a Codex tester shows unavailable figures (D7).** The cost is in the `usage` record; a token figure in the telemetry row is out of scope.
- **Out of scope:** the Codex worker (H4a to H4g); any change to `route_select`, `telemetry.rows`/`dimensions`, `review.launch_functional`, `verify-claude`/`verify-codex`, the Codex reviewer or the sandbox modules beyond `codex_tester`'s `usage_rollouts` step and `selection_error`.
