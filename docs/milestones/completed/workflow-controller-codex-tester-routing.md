## Goal

Everything the Codex tester needs exists and nothing calls it (`launch_codex_functional`, C10g-3b2b). This item makes `routing` accept `codex` for `functional-tester` and makes the functional job (`job._run_functional`) dispatch on the route's harness, so that a route that names Codex runs the Codex launch, with the Codex provider's usage admission, credential and record fields. Selection of a fallback entry, the telemetry grouping and the real operator-run Codex round are C10g-3c2.

## What exists

- `routing.NOT_YET_ROUTABLE = {(FUNCTIONAL_TESTER, "codex")}` is the one refusal of the pair, used by `check_role_harness`; its message names C10g-3c. Pinned by `tests/test_routing.py` and `tests/test_harness_table.py` ("the cell says no").
- `harness.CODEX` declares `reviewer` and `functional-tester` with `build_verification` `verify-codex`.
- `job._run_functional` is Claude-hardwired in five places: `usage_gate(route, provider=usage.PROVIDER_CLAUDE)`, the record's `functional.harness`, `captured_digest` and `operator_home`, `_review_usage_fields(review.CLAUDE, ...)`, and the call to `review.launch_functional` with `binary_name=functional.get("binary") or "claude"`. `_reconcile_functional` copies the credential back with `review.CLAUDE`.
- `cli._functional_options` builds `{automated, timeout_seconds, operator_home (the Claude home), binary}`.
- `codex_tester.launch_codex_functional` has the keyword shape of `review.launch_functional` and returns the same dict (plus `subagents`, `exit_code`); every refusal inside it is `functional_tester_unavailable`.
- `review.HARNESSES` maps a reviewer name to a `ReviewHarness` (`credential_file`, `keeps_sessions`, `default_binary`, `name`); `harness.get(name).reviewer_name` maps a routing harness to that key.
- `review_mode.worker_families` counts the harnesses of the roles whose adapter role is `worker` only.

## Decisions

- **D1. The registry's declaration is the only rule.** `NOT_YET_ROUTABLE` and its refusal text are deleted; `check_role_harness` then refuses a pair only when the adapter does not declare the role (`review-plan` and every worker role still refuse `codex` with the existing message). A settings file, `--role-harness` value or fallback entry naming Codex for the tester is accepted by every validator that reaches `check_role_harness`. Acceptance of the harness is not acceptance of the whole route: model and effort are still judged against the harness (D9).
- **D2. One dispatch point in `_run_functional`.** A small function `_functional_launch(route_harness, functional)` returns the `ReviewHarness`, the usage provider, the operator home, the binary name and the launch callable for the route's harness: `claude-code` gives `review.CLAUDE`, `usage.PROVIDER_CLAUDE`, the Claude home, `review.launch_functional`; `codex` gives `review.CODEX`, `usage.PROVIDER_CODEX`, the Codex home, `codex_tester.launch_codex_functional`. The Claude branch passes exactly the keyword arguments of today, so its records and tests do not change. The record's `functional.harness` is the `ReviewHarness.name` (`claude` as today, `codex` for Codex) and its `worker_route.harness` is the route's. The harness name is chosen once, before the record is written, from `route.harness`; an unknown harness name cannot reach it (`routing` validated it) and still refuses by name. The dispatch is resolved **before** `usage_gate` is asked, so a refusal in it admits no usage token. `review.settle_functional(result)` (the call that removes `result["sandbox"]`'s folder, which `launch_codex_functional` leaves for exactly this call) does not depend on the harness and is unchanged, so `_functional_launch` is the single place the step distinguishes the harnesses.
- **D3. The Codex tester's options come from the existing settings, no new setting.** `cli._functional_options` keeps its four keys and gains `harnesses`: `{"claude-code": {"operator_home", "binary"}, "codex": {"operator_home": <the Codex home>, "binary": "codex"}}`. The Codex binary is the harness default, not `reviewer.binary` (that setting belongs to the reviewer role and is not reused implicitly). `_run_functional` reads `functional["harnesses"][route.harness]` and, when a caller built `functional` without the key (every existing test), falls back to the top-level `operator_home` and `binary` for `claude-code`; a Codex route without the key is `functional_tester_unavailable` with the existing cause `functional_review.UNAVAILABLE_NO_BINARY` (no new cause, so `functional_review` gains nothing) and refusal text naming the missing option, never a guess. **The path that ends the step** (PLAN-R2-001): `_functional_launch` raises `functional_review.unavailable(UNAVAILABLE_NO_BINARY, <text naming the missing `harnesses["codex"]` option>)`; `_run_functional` catches that `TesterUnavailable` immediately after `route_options.resolve` and before `usage_gate`, so no usage token is admitted and no PLANNED or LAUNCHED tester record is written, and it returns `_no_launch_record(..., status=STATUS_GATE_BLOCKED, extra={"functional": {"gate": functional_review.GATE_TESTER_UNAVAILABLE, "head": head, "detail": exc.message, "cause": exc.evidence["cause"]}})` with a gate built by `_functional_gate_decision(..., GATE_TESTER_UNAVAILABLE, functional_review.gate_text(...))`, the way the `plan.stop` branch ends. That is exactly one `GATE_BLOCKED` record; its `functional` block carries `gate`, `head`, `detail` and `cause` (the `cause` field is how the test checks `no_binary`, since neither `stop()` nor the `plan.stop` record stores one) and has no `not_started` field, because no tester record exists to be "not started". The `TesterUnavailable` handler that wraps the launch call is not this path, because the launch is never reached.
- **D4. `_reconcile_functional` follows the record.** It selects the `ReviewHarness` from the record's `functional.harness` (default `review.CLAUDE` for a record without it) for the credential copy-back, as `_reconcile_review` does.
- **D5. Independence: the tester is outside the reviewer-independence rule.** The rule (H2/H10) compares the external reviewer's family with the families the workers run on (`review_mode.worker_families`, adapter role `worker`); the tester is an adapter-role `functional-tester`, produces flow evidence rather than a verdict, and today already runs on Claude whatever the workers are. A Codex tester therefore changes no reviewer-mode decision and no mixed-lane stop. A test pins both: routing the tester to Codex leaves `worker_families` and the reviewer choice unchanged, and a Codex-reviewer plus Codex-tester configuration is accepted. Whether the tester should differ from the implementer's family is a separate product question and is not decided here.
- **D6. Selection stays what it is.** `_run_functional` still takes `route_options.resolve(FUNCTIONAL_TESTER)`, the first entry of the chain. Walking the chain before the spawn and the list of selection-time `TesterUnavailable` causes are C10g-3c2; here an unusable Codex tester ends the step at `functional_tester_unavailable` exactly as an unusable Claude tester does.
- **D7. Usage figures are best effort for a Codex tester.** `_review_usage_fields(review.CODEX, ...)` reads `out["usage_rollouts"]`, which `launch_codex_functional` does not set; the record then carries an empty Codex usage record. Filling it from the tester's rollouts belongs with the telemetry dimensions in C10g-3c2; this plan says so in the guide.
- **D9. No Codex defaults: a Codex tester names its model and effort** (PLAN-EXT-001). `routing.resolve_route` resolves the tester's model and effort independently of the harness, and the tester's built-in route is `claude-sonnet-5-5` at `medium` (`ROLE_ROUTES[FUNCTIONAL_TESTER]`); `RoutingOptions.__post_init__` (via `check_route_values`) then judges them against the route's harness, and the Codex adapter declares only `gpt-6.1-sol` and the efforts `high`/`xhigh`. So deleting `NOT_YET_ROUTABLE` alone does not make `--role-harness functional-tester=codex` work, and this item does **not** add harness-aware defaults: that would add a rule to the precedence in `routing`'s docstring for every role, and which Codex effort suits the tester is an operator choice measured in C10g-3c2's live round. A working Codex tester configuration names all three: the harness, a model the adapter declares (`gpt-6.1-sol`) and a declared effort (`high` or `xhigh`), through a role entry, the settings file, or the command line (`--role-harness functional-tester=codex --role-model functional-tester=gpt-6.1-sol --role-effort functional-tester=high`); a fallback entry already names its model and takes `inherit` for an omitted effort. A harness-only or model-only selection stays what `check_route_values` already reports, a `RoutingConfigError` naming the role, the field, the value and what the harness declares, raised when the options are built, before any dispatch; the Claude defaults are not touched. The guides state the three-part configuration (CP3) and the tests pin the harness-only and model-only errors (CP1).
- **D8. The checklist-writer note is route-aware only in wording.** `functional_review.sandbox_limits_note()` (the carried C10g-3b finding) keeps stating the Claude limits because the row-37 launch writes the checklist before any tester is chosen; it is reworded to state the limits both testers share, and the test that pins it follows. The Claude and Codex limit lists are unchanged.

## Functional review

All flows are offline and unit-level, run one module at a time (`tests.test_routing`, `tests.test_harness_table`, `tests.test_functional_review`, `tests.test_functional_codex_route`, `tests.test_functional_lifecycle`, `tests.test_settings`, `tests.test_review_mode`, `tests.test_docs`), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. The tester's `/tmp` is read-only and these tests create temporary folders, so a flow runs with `TMPDIR` set to the tester's scratch area; a flow that cannot is `environment` and operator-run. There is no live flow in this item: the one operator-run Codex functional round (`CONTROLLER_LIVE_CODEX_TESTS=1`) is C10g-3c2. The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **A `feat:` before the proof.** Routing the tester to Codex is possible after this item but unproven end to end until C10g-3c2's operator round; the guide says a Codex tester needs `verify-codex` first and that the first real round is C10g-3c2, and the default stays Claude, so nothing changes unless an operator opts in.
- **`job.py` is large and the Claude path is exercised by many tests.** The dispatch is one function and the Claude branch passes today's arguments; a test asserts the Claude launch call is unchanged.
- **Usage figures of a Codex tester are empty (D7).** Telemetry already prints `telemetry unavailable` for a `codex` group; recorded and documented, fixed with the dimensions in C10g-3c2.
- **Out of scope:** walking the fallback chain before the spawn and the selection-time causes, telemetry's hardcoded `claude-code` for a functional job, the Codex usage readings, and the operator-run round (all C10g-3c2); the Codex worker (H4a to H4g); any change to `review.launch_functional`, the Codex reviewer, `verify-claude`, `verify-codex` or the sandbox modules.
