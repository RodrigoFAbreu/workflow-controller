## Goal

Build the sandbox a Codex functional tester would run in, and prove with real boundary probes that it holds. A Codex process launched on a disposable clone can run the checklist's commands, write test output into a scratch area, and nothing else: it cannot write the clone, write outside the scratch area, read the operator's real home, see the operator's environment, push, call `gh` or reach the network. Nothing is wired: no role is declared, no launch path calls the new module, and the proof runs only under an opt-in switch. The sandbox is also what the Codex worker (H4b) reuses.

## What exists, and what the tester can reuse from it

The Controller-run Codex review (C7, RB3) launches `codex exec -s workspace-write -C <copy>` with `code_mode_host` allowed by default but every other feature of `review.DISABLED_FEATURES` off, a Controller-written minimal `CODEX_HOME`, an allowlisted child environment (`review.child_environment`), and a disposable repository copy. `tests/harness_contract/codex/sandbox_probe.txt` (P1, P2) measured it. Reusable by the tester, unchanged: `review.DISABLED_FEATURES`, `review.HOME_CONFIG_TOML`'s content, `review.resolve_binary`, `review.interpreter_dir`, `review.JobLayout(area="functional")`, the credential copy (`review.build_home`, whose reviewer `config.toml` the tester overwrites), and the stand-in launchers (`functional_review.write_launchers`, which put a refusing `gh`, `claude`, `codex` and `ssh` first on `PATH`).

What the reviewer's sandbox does not give a tester, measured:

- `workspace-write` makes the `-C` directory **writable**. The reviewer wants that (it works in a throwaway copy). A tester must not be able to write the clone, so the clone cannot be the writable root.
- `workspace-write` and `:workspace` leave the **whole filesystem readable** (measured: a canary under the real home was read, `rc=0`) and write to the host `/tmp` (measured: the file landed on the host). A tester must not read the operator's home.
- The sandbox does not scrub the environment by itself (measured: an exported variable was visible in the sandboxed shell).

## Measurement on `codex-cli 0.163.0` (2026-10-27, `codex sandbox`, no model, no spend)

`codex sandbox -P <profile> -C <dir> -- <command>` runs a command under the same Linux sandbox `codex exec` uses, with no model call. A `-s read-only` flag does not exist on that subcommand; it needs a named permissions profile. Measured with the built-in `:read-only`, the built-in `:workspace` and a profile written into a scratch `CODEX_HOME/config.toml`:

| Profile | Write the clone | Write a scratch dir | Read a canary under the real home | Write `/tmp` | Network |
| --- | --- | --- | --- | --- | --- |
| `:read-only` | refused (read-only file system) | refused | **read** | refused | not measured |
| `:workspace` | written | written | **read** | **written on the host** | not measured |
| custom `tester` (below) | refused (read-only file system) | **written** | not found (hidden) | written inside a private `/tmp`, absent on the host | `Operation not permitted` (a TCP connect failed) |

The custom profile, which is the whole mechanism:

```toml
default_permissions = "tester"
[permissions.tester.filesystem]
":minimal" = "read"
"/usr" = "read"            # and /bin, /lib, /lib64, /etc
"<codex install root>" = "read"
"<clone>" = "read"
"<scratch>" = "write"
[permissions.tester.network]
enabled = false
```

Two further measurements: the profile needs the Codex install tree (D2 names the rule) readable (without it `bwrap` could not exec `codex` inside the sandbox: "execvp … No such file or directory"), and `-c 'shell_environment_policy.inherit="none"' -c 'shell_environment_policy.set={PATH="…"}'` leaves the sandboxed shell with only the set variables (plus `PWD`, `SHLVL`, `_` and `CODEX_SANDBOX_NETWORK_DISABLED=1`). Not yet measured, and settled by CP1 and CP2 (D6): that `codex exec --strict-config` accepts and **applies** `default_permissions`, and what a Unix socket connect to a host socket does.

## Decisions

- **D1. One mechanism: a restricted-read permissions profile, in a new module.** `controller/codex_sandbox.py` builds the tester's `CODEX_HOME/config.toml` (the reviewer's pinned lines plus the profile above), its child environment, its layout, its `codex exec` argv and its own startup-load check. `review.check_home` cannot be reused: it refuses unless `config.toml` hashes to `review.HOME_CONFIG_TOML`, which the tester's config never does. `codex_sandbox.check_home(layout, config_text)` therefore pins the SHA-256 of the tester's own deterministic config text and then applies the same entry rules as the reviewer's check, written over `review`'s public constants (`STARTUP_LOADED`, `CODEX_STATE_ENTRIES`, `CODEX_STARTUP_SUBENTRIES`) so `review.py` needs no edit. It is called by `build` and, in the live run (D6b), immediately before `codex exec` launches. **Pre-launch controls (D1b).** The reviewer runs five controls before each launch (`review._preflight`): `check_outside_layers`, `check_home`, `mcp list` + `check_mcp_list`, `features list` + `check_features`, and the composed-configuration check `check_effective` over `config/read` with layers. The tester runs, in this order, immediately before every `codex exec` and before the `codex sandbox` run of D6a: (1) `review.check_outside_layers(system_dir)`, reused unchanged (the files `review.SYSTEM_LAYER_FILES` names under `/etc/codex`; a file that carries content or cannot be read refuses); (2) `codex_sandbox.check_home(layout, config_text)` (above); (3) `codex mcp list`, built by `review.argv("mcp", binary=...)` and run against the tester's `CODEX_HOME` and child environment through `review.run_bounded`, checked by `review.check_mcp_list` (reused unchanged); (4) `codex features list`, built by `review.argv("features", ...)` the same way and checked by `review.check_features` (reused unchanged: a feature enabled outside `review.TOOL_ALLOWLIST` refuses, so a feature a newer build turns on stops the launch); (5) `codex_sandbox.check_home` again, after the two listings, as the reviewer does. `codex mcp list` composes every configuration layer, so an MCP server declared by a managed layer that is not a file (`enterpriseManaged`, `mdm`, `legacyManagedConfigTomlFromMdm`, which `compose.txt` shows do not come from files and which `check_outside_layers` cannot see) shows up there and refuses; MCP servers run outside the command sandbox (`sandbox_probe.txt`), so this is the control that matters for the isolation claim. `codex_sandbox.check_launch(layout, config_text, binary, env, system_dir=review.SYSTEM_LAYER_DIR)` runs (1) to (5) and raises `ReviewLaunchRefusedError`, naming the check and the offending file, server or feature, with nothing started; `build` runs only controls (1) and (2), which start no process, and returns the argv and environment; the live run calls `check_launch` just before each launch. **What is not covered, recorded:** the sixth reviewer control, the composed-values check `check_effective` (a tester sibling would need its own `effective_policy` with `default_permissions="tester"` and no `sandbox_mode`, plus the layer rules), is not built here. It is the first entry of `KNOWN_LIMITS` ("composed configuration values and non-file managed layers other than their MCP servers and features are not verified; a managed layer could still change a setting other than an MCP server or a feature"), and **C10g-3 builds the tester composed check before the sandbox is wired**; the guide paragraph of CP3 says so. The isolation claim of the Goal is therefore: proven by real probes under the profile and the controls (1) to (5), with that one named limit. `controller/review.py` is imported from and **not edited**: the reviewer's launch, argv contract, constants and tests are unchanged. `verify-claude` and `controller/claude_build.py` are not touched, and no `verify-codex` or digest cache is built (C10g-2).
- **D2. Layout.** `JobLayout(area="functional")` supplies `base`, `tree` (the clone), `home` and `codex_home`. The scratch area is `<base>/scratch/`, with `scratch/tmp` as `TMPDIR` and `scratch/fake-logs` for the stand-ins' logs. The clone, `<base>/bin` (the launchers), the Codex install roots, the interpreter directory and the Controller package directory are `read`; only `scratch` is `write`; nothing of the real home is listed. **Codex install roots** (rule, independent of how Codex was installed): the directory of the binary `review.resolve_binary` returns (the symlink is kept), the directory of its fully resolved target, and the package root of that target, meaning its nearest ancestor holding a `package.json`, searched upward only as far as the nearest enclosing `node_modules` directory (for an nvm install, `~/.nvm/versions/node/<v>/lib/node_modules/@openai/codex`; a stray `package.json` above a non-npm binary is never reached), falling back to the resolved target's directory when none exists; plus `review.interpreter_dir` when it is not `None`. **Stand-in interpreter** (rule, independent of how the Controller was installed): `build` passes `functional_review.write_launchers` an explicit `python=` that is the fully resolved `sys.executable`, and makes readable the directory of that resolved interpreter, `sys.prefix` (the venv root, under a pipx or other venv install, where `pyvenv.cfg` and the venv's site directory live) and `sys.base_prefix` (the standard library, which `controller/__init__.py`'s eager imports need), de-duplicated and subject to the overlap refusal. This holds whether the Controller runs from a source checkout with `/usr/bin/python3` or from `~/.local/share/pipx/venvs/workflow-controller` or a uv or pyenv Python under the home. **The Controller package directory** is the `controller` directory itself, never its parent: from a source checkout the parent is the checkout, and the default runtime root `<checkout>/.controller` lies under it, which would expose the job's own credential copy. The launchers run `-P -m controller.sandbox_fakes.<name>` with `PYTHONPATH=<parent>`; CP2 measures that this resolves with only `<parent>/controller` mounted. **Overlap refusal:** `readable_roots` and `build` refuse any readable root that equals or contains `<base>`, the runtime root or `codex_home` (and any that is contained by `scratch`), naming the offending root; they also refuse a readable root that is `/`, the operator's real home or one of its ancestors, and they never widen to make a launcher work. The stand-in `HOME` is `<base>/home`, which is not listed either, so it is not readable or writable.
- **D3. Environment.** The Codex process gets `review.child_environment`'s allowlist (with the scratch `TMPDIR`). Commands inside the sandbox get `shell_environment_policy.inherit="none"` plus `set` of `PATH` (`<base>/bin` first, then the system path), `HOME`, `TMPDIR`, `LANG` and `LC_ALL`. Neither carries the operator's variables.
- **D4. The launch argv.** `codex_sandbox.argv(...)` is a sibling of `review.argv`: the same `--disable` list, `--strict-config`, `--ignore-rules`, `--color never`, `-C <clone>`, `-o <verdict>`, but **no** `-s workspace-write` and `default_permissions="tester"` instead. **The full tester `-c` set** (the exact reference for `check_argv`): `model_provider="openai"`, `notify=[]`, `web_search="disabled"`, `project_root_markers=[".git"]`, `model="<model>"`, `model_reasoning_effort="<effort>"`, `service_tier="<tier>"`, `approval_policy="never"`, `projects={"<clone>"={trust_level="untrusted"}}`, `skills.bundled.enabled=false`, `default_permissions="tester"`, plus the two `shell_environment_policy` overrides of D3. Dropped from the reviewer's set: `sandbox_mode` and the whole `sandbox_workspace_write.*` family (the profile replaces them). `check_argv` refuses an argv that omits a pinned item, adds a `-c` outside this set, selects `-s`, or carries a banned flag (the reviewer's banned set).
- **D5. The probes, one per boundary, each a real attempt.** A probe command writes `PROBE <name> <RESULT>` lines in the shape of the Claude probes (a separate implementation; `functional_review.probe_command` is not refactored): write a tracked file, `.git/config` and a new file in the clone, rename over and delete a tracked file; write into scratch (expected `WROTE`); write outside scratch (the stand-in home, a sibling of the clone); write `/tmp` and `/var/tmp` (inside the sandbox they land in a private mount, so the line is informational and the host path must stay absent); read a canary file under a stand-in operator home (`BLOCKED` expected); read a canary environment variable (empty expected); read the tester's own credential copy `<codex_home>/auth.json` (`BLOCKED` expected; this is the probe that would catch the D2 overlap), `git push` to a scratch bare origin that the live test makes readable through an extra test-only read root (accepted by the overlap rule because it is neither under `<base>` nor a container of it), so the sandbox can read it and the push fails on the read-only file system rather than as "not found" (the capture file records the measured result); call `gh` by name (the stand-in, exit 127, logged) and `/usr/bin/gh auth status` by absolute path (fails: no credentials, no network); a TCP connection and a Unix socket connection to host listeners. `judge` fails closed on a missing, repeated or unexpected line.
- **D6. Two ways to run the probes; the second is the proof that matters.** (a) Through `codex sandbox -P tester` with the same `config.toml` and environment: no model, free, and it exercises the sandbox implementation and the profile. (b) Through `codex exec` with a real model, one short turn that runs the identical probe command once: this proves `codex exec` **applies** the profile, which (a) cannot. Both are opt-in live tests behind `CONTROLLER_LIVE_CODEX_TESTS=1`; both skip, decided before any run and reported with the reason, only when `codex` or `bwrap` is absent or the operator's Codex home has no credential file (`auth.json`); a `codex exec` turn that fails or returns no probe output is a test failure, never a skip. CI sets neither. If `codex exec` ignores `default_permissions`, CP1's argv step records that in the capture file and the builder passes the profile in the form the pinned build honours; a boundary that cannot be made to hold on `exec` fails the proof, it is not skipped.
- **D7. A probe that cannot hold is a recorded limit.** `tests/harness_contract/codex/tester_sandbox.txt` records, per probe, the expected and the **measured** result on 0.163.0. `KNOWN_LIMITS` is a table in the module whose first entry is the unbuilt composed-configuration check of D1b (reason, and C10g-3 as the step that closes it). A probe measured as not holding moves to the same table with its measured result and the sentence that goes in the guide; it is never dropped silently and never asserted as held. The honest facts already known: `/usr`, `/etc` and the Codex and Controller install trees are readable; `/tmp` writes go to a private mount; the stand-in `gh` only refuses by name.
- **D8. No fake-Codex support is added.** The offline tests assert the builder's outputs (config text, environment, argv, layout paths) and run `check_argv` against hand-edited argvs; they do not run the sandbox. `tests/fake_codex.py` and its contract test are unchanged.
- **D9. Released as `chore:`, with no release.** Nothing user-visible changes: no setting, option, exit code, gate, role or launch path, and the settings generation is untouched. The module is called only by its tests until C10g-3.

## Functional review notes

Every flow is unit level, offline and needs no `codex`, `claude` or `bwrap`: the cases of `tests.test_codex_sandbox`, the unchanged reviewer suites `tests.test_review` and `tests.test_fake_codex_contract`, `tests.test_ci_workflows`, and `python3 tools/check_docs.py`. The live module and the full suite are not flows.
