Work item: `workflow-controller-codex-worker-job-record`
Work item type: `product`
Governing workflow version: `2.2` (this repository's `docs/ai-workflow/WORKFLOW_CONFIG.json` default at creation)
Base commit: `0e7f3237a7581f2f4fe0fa97d951f055ca7c2248` ("docs: link the H4c issue from the roadmap row and the next action (#260) (#261)"), the tip of `main`.
Lifecycle authority: this repository's installed Workflow, automatic gates.
Roadmap slot: `docs/ROADMAP.md` row H4c (issue [#260](https://github.com/RodrigoFAbreu/workflow-controller/issues/260)), step 3 of the Codex worker in seven (H4a to H4g), split here into H4c1 (this item) and H4c2 (D1). It depends on H4b2 (done).
Released baseline: `workflow-controller 1.27.2`. A path no operator command reaches: the `codex` harness still declares no worker role, no setting selects it and no real launcher is registered, so the squash commit is a `chore:` and there is no release, as for H4a to H4b2.
Pull request title: `chore: record a Codex worker run as a job with derived usage behind the H3 seam for a fixture role (H4c1, #260)`

## Goal

Make a completed Codex worker run a proper job in the job layer: the same record a Claude worker job gets (status, `worker` block, `worker_outcome`, `telemetry`, `usage_record`, the transition verification), written from what `controller/codex_worker.py` returns, with the Claude path byte-for-byte unchanged. It is reached through a fixture route only: no real role, setting or option selects Codex.

## What exists

- `controller/codex_worker.py` (H4b2): `launch_codex_worker` returns a `worker.WorkerResult` whose `stream_diagnosis` carries `harness`, `readings`, `subagents`, `usage_rollouts`, `credentials`, `breach`, `subtype` and `detail`; `CodexLauncher` is its `WorkerLauncher`. It fixes the ownership tag to `job_id`, calls `on_spawn(pid, pgid)` (the review path's shape) and requires `cwd` to be the layout's worktree, `<runtime>/worker/<job>/worktree`, which it does not create.
- `controller/job.py`: `execute_step` resolves the route and the launcher (`worker_launch.for_harness`), writes the record PLANNED then LAUNCHED (`ownership_tag` is already the job id), and `_launch_job` then calls `launcher.launch(...)` with the Claude-only options (`stdout_path`, `stderr_path`, `claude_bin`, `pass_fds`, `on_spawn(worker_process, anchor=, ownership_tag=)`, `on_group_drain`, `on_state_change`, `disallowed_tools`, `supervisor_lock_path`, `drain_detach_seconds`, `permission_mode`). `CodexLauncher.launch` raises `TypeError` on every one of them. Its completion write reads the worker's stdout stream for `telemetry` and `usage_record` (`_telemetry_block`, `_worker_usage_fields`).
- `_run_functional` (C10g-3c1) is the precedent: it dispatches on the route's harness, calls `on_spawn(pid, pgid)` with `worker.capture_worker_process`, derives `usage_record` from the rollouts (`_review_usage_fields`, `usage_record.from_codex_rollouts`) and builds a streamless `telemetry` block (`_codex_tester_telemetry`).
- `controller/worker_launch.py`: `LAUNCHERS` keys must equal the worker-role adapters; `harness.CODEX.roles` is the reviewer and the functional tester.

## Decisions

Each decision states one principle.

- **D1. Split before the first review: H4c1 now, H4c2 after.** This item records a run that completed or failed inside the launcher. H4c2 (ownership, `resume`/`--abandon` liveness for a Codex worker and reaping after a Controller interrupt) is a second mechanism over the same record and is not here. The roadmap row H4c becomes H4c1 (done) and H4c2 (next, its own issue). The issue for H4c2 is filed by the lane orchestrator or the owner after this plan is approved (this command does not file issues); until it exists the roadmap row names #260 as the parent. The deadline kill is already the launcher's (`run_bounded` ends the group and every process carrying the job id on the deadline, H4b2 D4(f)); H4c2 adds what happens when the Controller itself dies. The timeout is passed as `_launch_job` resolved it: `DEFAULT_WORKER_TIMEOUT` is `None`, so a Codex job has no deadline unless the operator set one, exactly as a Claude worker has none ("Time is not termination"); that is intended and no bound is invented here, so the deadline kill applies only when a timeout is given. Nothing real reaches a Codex job before H4c2 lands: H4e is the first item that routes a real role, and its row depends on H4c2 **and on the tree and landing decision of D5**, which H4e needs as much as H4f does (CP3 edits the row).
- **D2. The job layer branches on the launcher, through one predicate.** `job._is_codex_launcher(launcher)` is `isinstance(launcher, codex_worker.CodexLauncher)`; it is on the launcher object, not on a harness name, because the route's launcher is what `for_harness` returned and a fixture adapter in a test is a different name (a test subclass of `CodexLauncher` takes the branch too). It is used in three places and nowhere else. (1) In `execute_step`, a single-entry route with a Codex launcher skips the usage gate (D7). (2) In `_launch_job`, the call-and-wait block (`launcher.launch` with its `try`) is replaced for such a launcher by `_run_codex_worker`, which takes the record and returns `(result, record, spawned)`. (3) In the same function's completion write, the `worker`, `telemetry` and `usage_record` fields come from the Codex helpers instead of the stream. Everything between and around them is shared and is **not** forked: the record up to the LAUNCHED flush, the protocol currency check before the spawn, the `completed` write, the protocol branch (`_protocol_resolution`, the Workflow's own `reconcile`) and steps 7 to 9 of the legacy branch. The Claude lines are guarded, not edited, and a Claude job is byte-for-byte the record it was. No change to `worker_launch`, `harness`, the tester or the reviewer, and their tests are not edited.
- **D3. Pure helpers live in a new module that never imports `job`; `job.py` keeps the writes and the existing helpers.** `controller/codex_worker_job.py` holds `launch_options` (the D4 mapping), `stream_texts` (the text each stream file receives) and `usage_builder` (the zero-argument callable that builds the `UsageRecord` of D7), each a function of the result and the route, none of which writes a file or starts a process. `DEPENDENCY_ORDER` puts the module before `job`, and `tests/test_package_structure.py::test_no_module_imports_one_later_in_the_dependency_order` forbids it to import `job`, so it holds none of the three `job.py` helpers and **none moves**: `_worker_dict` (D6), `_usage_fields` (the failure boundary of D7, which wraps the builder) and `_codex_tester_telemetry` (D7) stay in `job.py` and are called from there, unchanged. `job.py` keeps every `_persist`, so write containment and the record's single-writer discipline are unchanged, and `controller/job.py` gains no new import of a write primitive.
- **D4. The option mapping.** The branch passes `runtime_root`, `job_id`, `operator_home`, `cwd`, `timeout`, `on_spawn`, `model` and `effort` and nothing else. `operator_home` is the operator's **Codex home**, the directory holding `auth.json` (`review.build_home` reads `operator_home / "auth.json"` and `review.copy_back_credentials` writes it back there), not the operator's real home: the launcher's separate `real_home` option stays at its default `Path.home()` and is not passed. `_launch_job` receives no Codex home, so the branch takes it from a second module seam, `job.CODEX_HOME_RESOLVER`, a zero-argument callable returning a `Path`, whose default is `job._codex_home`, a restatement of `cli._codex_home`'s rule (`$CODEX_HOME`, else `~/.codex`) that `job.py` cannot import from `cli`; a test pins that the two give the same answer under both environments. A home with no `auth.json` is the launcher's own refusal, a `WorkerNotStarted` by D8. `on_spawn(pid, pgid)` writes `worker_process` with `worker.capture_worker_process(pid).to_dict()`, as `_run_functional` does, then the `worker_spawned` event; no anchor, no `on_group_drain`, no `on_state_change`: `worker_state` goes `STARTING` to `ENDED` through the existing "launch double" completion. `ownership_tag` stays the job id the LAUNCHED write already set; the launcher fixes the same value in the child's environment. `route.model` and `route.effort` are passed as routed; a missing value is the launcher's own refusal. The launcher's other options (`run`, `system_dir`, `system_path`, `real_home`, `binary_name`, `commands_dir`) are test seams the branch never passes; the offline tests reach them through a `CodexLauncher` subclass whose `launch` adds them to the eight keys (D9), which still takes D2's predicate.
- **D5. The tree is a seam, not a feature.** The launcher needs a prepared worktree at the layout's path. Preparing one from the managed repository and landing its commits back is an owner decision (a clone of the managed repository versus a worktree of it; how changes return), and it is needed by **H4e**, the first item that routes a real role: each of H4e's four roles writes the managed repository's plan, feedback or `WORKFLOW_STATE.json`, so with a tree that never lands no H4e job's effects reach the managed repository, and the two resolutions report it differently (below). The roadmap therefore names the decision as owner-open **before H4e** and H4e depends on it (CP3 edits the rows); H4f reuses it. This item does **not** decide it: the branch takes the worktree from a module-level seam `job.CODEX_WORKTREE_PREPARER`, a callable `(managed_repo, layout) -> Path` that is `None` by default. With `None` the branch refuses before the launch with `WorkerLaunchError` and writes `WorkerNotStarted` (the refusal already used for a worker that could not start), so a record that cannot run is terminal and needs no `resume`. A test sets the seam to a function that clones a scratch repository to the layout's path. Because the prepared tree is not the managed repository, the job's transition verification (which reads the managed repository) sees no change: the two resolutions the branch shares with the Claude path therefore answer differently for an unlanded clone, and the plan states both. On a **legacy (non-protocol) target**, steps 7 to 9 end the job `FAILED` with `phase_not_in_to_any_of`. On a **protocol decision**, `_protocol_resolution` (`controller/job.py`, the `no_progress` tail; `tests/test_protocol_outcome.py::ClassToResultTest::test_no_progress_after_a_successful_worker_is_a_terminal_finished_job_with_progress_none`) reconciles a successful worker whose effects never landed as `no_progress` and ends the job `FINISHED` with `transition_verified: true` and `protocol.progress: "none"`: not a failure, and the guard counts repeated `no_progress` loops (`no_progress_repeated` gate). A Codex job on an unlanded clone can therefore finish without landing its effects; D2 keeps that shared resolution on purpose, so the tree-and-landing decision, not the job record, is what makes H4e's jobs land. In both cases the record's `worker` block and `usage_record` are still written; these are the intended, visible limits, stated in the guide.
- **D6. The `worker` block, field by field.** `job.py` calls `_worker_dict` unchanged, over the launcher's result: `session_id`, `num_turns`, `total_cost_usd`, `permission_denials`, `terminal_reason` and `stop_reason` are `None` (Codex's `exec` gives none of them; the cost is in `usage_record`); `exit_code` is the process's; `is_error` is true for every outcome but `SUCCESS`; `subtype` is the launcher's (`success`, `timeout`, `terminated_by_signal`, `usage_limit`, `non_zero_exit`, `no_final_message`, `sandbox_breach`); `duration_ms` is the wall time the launcher measured; `result_excerpt` is the final message cut at 4000 characters; `stream_diagnosis` is the launcher's block (readings, rollouts, credentials result, breach entries, detail); `owned_processes_seen` is `None` (H4c2). `stdout_path` and `stderr_path` name the job's two stream files, which the branch fills after the run from `stream_texts(result)` through a `runtime` write primitive (a primitive missing for that is added to `runtime.py`, not to the new module). The Codex stdout is plain text, not stream-json, so the completion write sets the record's `worker_streams.format` to `text` for a Codex job (nothing in `controller/` reads the field by value; a test confirms `validate_record` accepts it and that a Claude record still says `stream-json`). A `sandbox_breach` is `FAILURE`; a job whose worker breached never ends `FINISHED`, whatever the transition check says.
- **D7. Usage is derived from the rollouts and flagged `derived`.** `usage_record` is `usage_builder(result, route)`, which wraps `usage_record.from_codex_rollouts(stream_diagnosis["usage_rollouts"], model=route.model, wall_ms=duration_ms)`, passed to `job._usage_fields`, the existing failure boundary (adapters-1): a run with no rollout gives the `unknown` record, a build that raises gives `usage_record_failed`. The `telemetry` block is the streamless block `job._codex_tester_telemetry` builds, **reused unchanged**: it already takes the harness from the record's `worker_route` (`telemetry.dimensions`), so a Codex job gets the `no_stream` problem, `job_seconds` (the launcher's wall time) and the dimensions with `harness` `codex` without a new parameter. The budget (`usage` block, windows, limit holds) is H4d, and the usage gate sees only the Claude provider by default, so a Codex job never takes a reservation here: in `execute_step`, a single-entry route whose launcher is a Codex launcher **skips `usage_gate`** (the gate is not called, `token` stays `None`, the record has no `usage` block and the end-of-job accounting does not run), and a fallback chain that selects a Codex entry under a gate, which would carry a `usage` block, is refused by `_run_codex_worker` before any spawn as `WorkerLaunchError`, so the record is `WorkerNotStarted` and `execute_step`'s existing handler releases the reservation with no charge. `usage_limit_of` stays `None` for a Codex job.
- **D8. Every path ends the record.** The rule is the Claude rule: `WorkerNotStarted` is keyed on no `worker_process` having been flushed. A `ControllerError` raised while `"worker_process"` is not in `spawned` is `WorkerNotStarted`, terminal and not counted by the apply relaunch bound, whichever refusal it is: `ReviewLaunchRefusedError` (an unverified build, a bad task, a placement refusal, an operator Codex home with no credential file), `CommandRenderError`, `MissingCommandsDirectoryError` and `UserOnlyCommandError` from `command_files.render_command`, a `WorkerLaunchError`, and the missing tree seam of D5 or a chain-selected usage reservation of D7 (both `WorkerLaunchError`). The protocol currency check before the spawn is the shared code of D2, so a stale decision ends the same terminal record. After a spawn, a returned result completes the record by D6 and D7 and then the shared code: for a protocol decision the Workflow's own `reconcile` (`_protocol_resolution`), otherwise steps 7 to 9; `KeyboardInterrupt` leaves the record LAUNCHED with `worker_process` flushed and propagates (the launcher has already killed the group and removed the credential copy; the Claude branch's orphan announcement and the liveness assessment of that record are H4c2, which is why nothing real may reach this branch before it); any other exception ends the record `FAILED` with the exception named, then re-raises: a non-`ControllerError` before the spawn, or any exception (a `ControllerError` included) once `worker_process` is flushed. The credential copy-back and removal are the launcher's and are asserted, not redone.
- **D9. Tests use the fake Codex of H4b2 and one opt-in live test.** The offline tests drive `execute_step` end to end with a fixture adapter and launcher registered by patching `harness.ADAPTERS` and `worker_launch.LAUNCHERS` for the test only (as H4b2's registration test does), a route to it, both seams set and the existing fake `codex`; the fixture launcher is a `CodexLauncher` subclass in the test whose `launch` adds the launcher's own test seams (`run`, `system_dir`, `system_path`, `real_home`) to the eight keys of D4, as H4b2's tests pass them. One opt-in test (`CONTROLLER_LIVE_CODEX_TESTS=1`, skipped by default and on CI with its reason) runs the fixture role through the job layer with a real `codex exec` turn and checks the record and the derived usage; its measured result goes to `tests/harness_contract/codex/worker_job.txt`.
- **D10. Release type.** `chore:`: no caller outside the fixture registration and the seam, no operator-visible change. If review finds one, the title becomes `feat:` before approval.

## Functional review

Every flow is offline and unit-level except the live flow. Run from the product clone with `TMPDIR` set to a writable scratch directory, one module at a time, `python3 -B` and no `PYTHONPATH=.`: `tests.test_codex_worker_job`, `tests.test_job_codex_worker`, then `tests.test_codex_worker`, `tests.test_worker_launch`, `tests.test_harness`, `tests.test_package_structure` and `tests.test_write_containment` (the neighbouring modules are unchanged), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. A flow that creates folders or runs git needs a writable `TMPDIR` and is `environment`-limited in a tester sandbox with a read-only `/tmp`; the job-layer modules are operator-run there. The live flow needs a real `codex`, `bwrap`, a recorded `verify-codex` build and a credential file and is operator-run. The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **A Codex job interrupted by a Controller death has no liveness rule yet.** D1 and D8 state it; the branch is unreachable by a real role, and H4c2 closes it before H4e. A test pins that no real launcher key exists.
- **The tree and landing are undecided.** D5 makes the seam refuse by default instead of guessing; a test-set seam proves the record, and both outcomes on a clone (legacy `FAILED` with `phase_not_in_to_any_of`, protocol `FINISHED` with `protocol.progress: "none"`, so a Codex job can finish without landing its effects) are stated, not hidden. The owner decision is named as a prerequisite of H4e, which needs it first.
- **Two launch shapes in one function.** The dispatch is one predicate used in three places (D2) and the Codex run is separate code, so the Claude lines are guarded and not edited and the shared prelude and tail (currency check, protocol resolution, steps 7 to 9) are not forked; the unchanged Claude tests are the proof.
- **The fake Codex can drift from the real one.** The captures under `tests/harness_contract/codex/` feed the fake, and the opt-in test is the only real check.
- **Write containment.** The branch writes only through `runtime` primitives and the existing `_persist`; `tests.test_write_containment` fails on a direct write or `.replace(` call.
- **`job.py` is large.** The new logic is a helper module plus one branch function; the guide records where it sits.
