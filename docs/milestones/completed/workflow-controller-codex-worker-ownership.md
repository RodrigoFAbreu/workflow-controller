## Goal

Make a Codex worker's **process** safe to lose its Controller. A Codex job (H4c1) writes a `LAUNCHED` record with `worker_process` and `ownership_tag`; this item decides what `resume` and `resume --abandon` do with such a record, so a Codex run never leaves an orphan `codex` or `bwrap` process of its tag and a restarted Controller can tell a live Codex worker from a dead one. The Claude worker path, the tester and the reviewer are unchanged. Nothing real reaches the branch.

## What exists

- `controller/job.py`, `_run_codex_worker` (H4c1): the record is `LAUNCHED` with `worker_state` `STARTING`, `ownership_tag` equal to the job id and `worker_streams` (two empty files created before the launch). `on_spawn(pid, pgid)` flushes `worker_process` (`worker.capture_worker_process`). There is no `worker_anchor`, no `worker_state` progress and no stream until the run ends: the two stream files are filled once, after it.
- `review.run_bounded` starts `codex exec` in its own session (`start_new_session`, so the pgid is the pid) with `close_fds=True`. On the deadline, on `KeyboardInterrupt` or any exception it kills the group and every process carrying the tag. Nothing runs when the Controller is killed outright (`SIGKILL`, a crash, a power loss): the worker is then an orphan.
- `worker.assess_worker_liveness` (boot-keyed verdict `active`/`inactive`/`unverifiable` over `worker_process`) and `worker.scan_recorded_owned_processes` (the recorded group plus every process carrying the tag in its environment) are version- and harness-independent. `job._owned_work_hold` already holds a `LAUNCHED` record on them, `job._abandon_supervision` already refuses on them, and `resume` already ends the process group of a **review** or **tester** record (`_end_review_group`, `_reconcile_review`, `_reconcile_functional`, D9 of the Codex reviewer) because those groups, like a Codex worker's, never held the lifecycle lock and have no stream to follow.
- `_supervise_record` (`resume` phase 1) re-attaches to any `LAUNCHED` record that carries `worker_state` and `worker_streams`: `worker.reattach` replays the stdout stream, signals a stdin anchor and classifies the stream. A Codex record has none of the three, so today a live Codex worker would be "followed" and then completed with a classification of an empty Claude stream. That is the defect this item closes before any real role can reach the branch.

## Decisions

Each decision states one principle.

- **D1. A Codex worker is never re-attached to: `resume` ends what it finds.** Re-attaching needs a stream to replay, a stdin anchor to release and a Controller to read the exit status; a Codex record has no stream (the files are filled after the run), no anchor, and the output pipe was the dead Controller's, so a live worker's output is lost and nobody can consume it. A live Codex worker found by `resume` is therefore an orphan, not a worker to wait for: `resume` (with the target root present; a missing root is the exception below) ends its process group and every process carrying the job's tag (the review and tester rule, D9 of the Codex reviewer), verifies them gone, and reconciles the record. `resume`'s phase 1 (`_supervise_records`) does not consider a Codex record, so `worker.reattach` is never called for one; `_supervision_candidate` itself is unchanged because `--abandon`'s phase 1 shares it and must still judge the record. This differs from a Claude worker on purpose and the guide says why. A target root that is no longer a directory is outside "`resume` ends what it finds": `resume` never reaches the Codex branch there, because `validate_record` fails the non-terminal record (`target_repo_unresolvable`) and `_resume_records` raises `StaleJobRecordError` whose clearing command is `resume --abandon`; so for that case the guidance names the recorded pid and pgid and the by-hand end (D7), never `resume`.
- **D2. The liveness verdict is the existing one, over the identity captured at spawn.** `worker.assess_worker_liveness(worker_process)` is unchanged and decides `active`, `inactive` or `unverifiable` from `worker_process` (`pid`, `pgid`, `start_ticks`, boot id, pid namespace, host) flushed by `on_spawn`; the tag scan (`scan_recorded_owned_processes`) adds every process that carries the job id, which is how a nested `bwrap` or tool process that left the group is found. There is one row per verdict, tested for a Codex record: `active` and an owned process alive end the group (D1); `inactive` with nothing owned reconciles; `unverifiable` is refused with `LifecycleWorkerUnverifiableError` (exit 45) before anything is ended, and nothing is reconciled, exactly as for a review record. An unlistable `/proc` is refused with the same error and exit code and nothing is reconciled, but it is **not** a "nothing is ended" case: `worker.assess_worker_liveness` can answer `active` from a matching leader's readable stat alone, `_end_review_group` then kills that group (`worker._kill_drained_group`), and only its ownership scan finds `/proc` unlistable and raises ("none is assumed gone"). This is the existing review and tester behaviour, kept byte-for-byte: ending an orphan is what `resume` is for (D1), the refusal leaves the record and the credential copy untouched, and the next `resume` finds the group gone and retries the scan. With no live leader there is nothing to end, so an unlistable `/proc` ends nothing in that case. A record with no `worker_process` (the Controller died between the spawn and the flush, or before the spawn) is judged by the tag scan alone.
- **D3. The lifecycle lock is not assumed; the record says so.** `review.run_bounded` uses `close_fds=True` and H4c1 passes no `pass_fds`, so a Codex worker does not inherit the lifecycle lock's descriptor and its death or life says nothing about the lock (a Claude worker, or its anchor, keeps it held). The liveness and reaping design above reads only `worker_process` and the tag. The record states it: a `codex_worker` block written **before the spawn** (D4) carries `lock_inherited: false`. The field is a record-only statement for operators and `inspect`: the Controller never reads it, and the lock refusal text and `resume`'s unreconcilable message are not edited. After `resume` has ended and verified the group, the existing "the worker has ended" wording is true on its own evidence and is left as it is; the message is not edited.
- **D4. The record carries what a lost Controller needs, written before the tree is prepared and so before any spawn.** The credential copy-back needs the digest of the operator's credential file as captured at launch (`review.copy_back_credentials(layout, operator_home, captured_digest, selected)` copies only over an operator file that still has that digest), and a Controller lost mid-run cannot rebuild it. Following the review and tester records (`review._sha256_file(operator_home / credential_file)` recorded in their blocks), `_run_codex_worker` persists, as its first write after the usage check and before the tree preparer, the Codex-home resolver's second use and the launch, a `codex_worker` block `{operator_home, captured_digest, lock_inherited: false}` (event `codex_worker_prepared`); the operator home is resolved once there and the same value is passed to `launch_options`. The block is read only by the Codex branches below, which read `operator_home` and `captured_digest` (never `lock_inherited`); `validate_record` accepts it (a test pins it) and a Claude record never has it. The digest is read by the job layer from the same file the launcher copies, so a change in between makes the copy-back answer `operator-changed` and write nothing, never overwrite.
- **D5. The Codex-record predicate is the record's `codex_worker` block, not a harness name and not a new kind.** `job._is_codex_worker_record(record)` is true for a non-review, non-tester record that carries a `codex_worker` block (D4). It reads nothing about the adapter's name: the H4c1 fixture adapter is `dataclasses.replace(harness.CODEX, name=FIXTURE, ...)` and `ResolvedRoute.to_record()` writes that name to `worker_route.harness`, so a harness-name test would be false for every record the tests build (H4c1's D2 rejected it for the same reason), and `resume` has no launcher object to ask. The block is persisted first in `_run_codex_worker`, so any record that can have spawned a process has it. A record interrupted before that write has spawned nothing and already reconciles to `INTERRUPTED` on the Claude rows. A Codex worker record keeps the Claude worker's `kind`, schema and status table, so every consumer (`status`, `inspect`, `explain`, `follow`, the apply relaunch bound) reads it as it reads a Claude worker record, and `resume`'s existing review and tester dispatch is not touched. It is read by `resume`'s phase 1 skip (D1), `resume`'s dispatch (D6), the drifted branch's credential settling (D6) and `--abandon`'s guidance and credential settling (D7).
- **D6. The `resume` branch: end, settle the credentials, then the shared reconciliation.** In `_resume_records` the Codex branch comes right after the review and tester branches and is taken only when the installation is **not** drifted (`not drifted`), because `_reconcile_launched` and `_reconcile_completed` have no drift handling of their own. **Under a drifted installation nothing about a Codex record changes**: `_refuse_drift_unless_decided` keeps counting it as pending (it is not a review or tester record), so a lone Codex record that `_drift_decides` does not admit is refused with `DriftedInstallationError` before phase 1 and before any write, and a live Codex orphan is **not** ended until the installation is repaired (the same as a Claude worker's record and a lone review record today). When every pending record is admitted by `_drift_decides` the Codex record falls through to the existing `drifted` branch: `_owned_work_hold` holds it if its group or a tagged process is alive (nothing ended), otherwise `_resume_drifted_protocol` fails it `workflow_release_changed`, after the credential settling of (b) below so the failed record leaves no credential copy. For a non-terminal Codex worker record (`PLANNED` stays `_reconcile_planned`; `LAUNCHED` and `COMPLETED` are this branch's, outside drift), `_reconcile_codex_worker` (a) ends the group and the tagged processes through `_end_review_group` generalised only in its display text (it names the record's kind instead of "review"; the review and tester messages are byte-for-byte what they are), (b) settles the credentials, `_settle_codex_credentials(record)`: copies the credential back when the block has a digest and the copy exists, and always removes the credential copy (`runtime.remove_tree`, the path the launcher uses), each step guarded so one failure never skips the next, and (c) hands the record to the existing `_reconcile_launched` or `_reconcile_completed` (so a protocol decision reaches `_reconcile_protocol` and the Workflow's own `reconcile`, as for a Claude record). The branch does not write a terminal status of its own: on an unlanded clone nothing durable happened in the managed repository, so the shared rows end the record `INTERRUPTED` (a fresh `step` may retry) exactly as they do for a Claude worker killed before it changed anything. The tree (`<runtime>/worker/<job>/worktree`) is left in place, as after a completed run: the tree-and-landing decision is the owner's, before H4e.
- **D7. `--abandon` follows Claude's rules and adds the credential settling.** `_abandon_supervision` already refuses a record whose worker is `active` or whose owned processes are alive (exit 45, "no flag overrides it") and refuses `unverifiable` without `--acknowledge-unverifiable-worker`; for a Codex record both refusals name `resume` (which ends the orphan, D1), through the same predicate: the `active` branch says `resume` instead of "Follow it", and the owned-processes branch (a tag-scan-only record, whose tagged process may be `codex exec` itself, so "the worker has ended" is not established) says that `resume` ends them instead of `_owned_guidance`'s "worker has ended ... then run `resume --abandon`". `_abandon_mark_failed` repeats the "Follow it" text in its `assessment.verdict == worker.ACTIVE` branch, which is reached without phase 1 only when the target root is no longer a directory, and there `resume` cannot help: it refuses the record with `StaleJobRecordError` and ends nothing, and its clearing command is `resume --abandon`, so naming `resume` would send the operator in a circle while the orphan runs. For a Codex record that branch (through the same predicate) therefore drops "Follow it" and keeps `_active_guidance`'s recorded pid and pgid and its by-hand end (`kill -TERM -- -<pgid>`, or wait), with `_active_guidance` taking a `then` command as `_owned_guidance` does and this branch passing `_abandon_command(...)` so the text ends "then run `resume --abandon <id>`"; it names `resume` only in `_abandon_supervision`'s branches, where the root exists. A Claude record keeps today's text. `_abandon_mark_failed` makes no tag scan, for a Codex record as for a Claude one: a record with no `worker_process` and a tagged process alive is marked `FAILED` there and the process is left running; this item does not change that (the scan runs in phase 1, which that path skips). For a dead or acknowledged worker, `_abandon_mark_failed` marks the record `FAILED` with `OperatorAbandoned` as for any worker, and for a Codex record first runs D6(b), so an abandoned run does not leave a credential copy or an unsaved refreshed credential. One test per row.
- **D8. An interrupt before the spawn leaves the record `LAUNCHED`, as the Claude branch does.** A `KeyboardInterrupt` during the `codex_worker` persist, the tree preparer or the Codex-home resolver raises through `_run_codex_worker` unchanged: no `worker_process` is flushed and the record stays `LAUNCHED` at `STARTING`, with or without the block. With the block, D6 finds nothing tagged and reconciles it; without it, the Claude rows do (nothing was spawned). Either way it ends `INTERRUPTED` (nothing durable happened). Ending it `FAILED` would count a never-started run as a failure for the apply relaunch bound and would write a terminal status from inside a `KeyboardInterrupt` handler; the Claude rule is kept. A `KeyboardInterrupt` after the spawn is the existing path: `run_bounded` has already killed the group and tag, and the launcher has removed the credential copy; the record stays `LAUNCHED` with `worker_process` and `resume` reconciles it (the group is already gone, D2 `inactive`).
- **D9. Tests use the fake Codex and one opt-in live test.** The offline tests drive `execute_step` with the H4c1 fixture adapter and `CodexLauncher` subclass and the existing fake `codex` (`tests/fake_codex.py` is not edited), with a test-side wrapper script for the nested child: it starts a child in its own session that waits on a readiness file (the `bwrap` stand-in), then execs the fake. A killed-Controller test runs `execute_step` in a child Python process, waits for the worker's readiness signal (never a sleep), and kills that Controller with `SIGKILL` (an orphan the next `resume` must reap) and with `SIGINT` (the launcher reaps); each test has its own job id and so its own ownership tag (a shared tag across parallel shards is the open flake #259). The one live test (`CONTROLLER_LIVE_CODEX_TESTS=1`, skipped by default and on CI with its reason) starts a real `codex exec` through the job layer in a child Controller, kills the Controller, runs `resume` and checks no process of the tag survives; its measured run goes to `tests/harness_contract/codex/worker_ownership.txt`.
- **D10. Release type.** `chore:`: no real role, setting, option, exit code or gate reaches the change. If review finds one, the title becomes `feat:` or `fix:` before approval.

## Functional review

Every flow is offline and unit-level except the live flow. Run from the product clone with `TMPDIR` set to a writable scratch directory, one module at a time, `python3 -B` and no `PYTHONPATH=.`: `tests.test_job_codex_worker_resume`, `tests.test_job_codex_worker_interrupt`, then `tests.test_job_codex_worker`, `tests.test_resume`, `tests.test_worker_launch`, `tests.test_codex_worker` and `tests.test_write_containment` (the neighbouring modules are unchanged), plus `python3 -B tools/check_docs.py` and `python3 -B tools/harness_table.py --check`. The tester's sandbox has a read-only `/tmp` and no user namespaces: the process and job modules create folders and processes there and are `environment`-limited, so they are operator-run, and the plan names them as few flows. The live flow needs a real `codex`, `bwrap`, a recorded `verify-codex` build and a credential file and is operator-run. The full suite is not a flow (`test_functional_sandbox` has a known CI flake, #206).

## Risks

- **Killing what `resume` finds.** D1 ends a live process, which a Claude `resume` never does. The kill is identity-checked and tag-checked (the review and tester machinery, unchanged), an `unverifiable` verdict ends nothing, and a test pins that a recorded process of another namespace is left alone; an unlistable `/proc` with a live readable leader does end the group before the refusal (D2), as for a review record.
- **A shared ownership tag.** The tag is the job id, unique per job; the open flake #259 is a test-side collision, avoided by giving every test its own job id (D9).
- **Timing on CI (4 vCPU).** The process tests wait on readiness files and on the settled state, not on sleeps; the repository's CI flake notes in `tests/process_fixtures.py` are followed.
- **`job.py` is large.** The new logic is one predicate, one reconcile function and the pre-spawn block; the Claude lines are guarded, and the unchanged `tests.test_job` and `tests.test_resume` are the proof.
- **The tree and landing are undecided.** The reconciliation reads the managed repository, so an unlanded clone reconciles to `INTERRUPTED`; the owner decision stays a prerequisite of H4e and the tree is left in place.
- **The fake Codex can drift from the real one.** The captures under `tests/harness_contract/codex/` feed the fake, and the opt-in test is the only real check.
- **Out of scope:** usage windows and limit holds (H4d); review roles on Codex (H4e); `milestone-implement` on Codex (H4f); the tree and landing decision; declaring the worker role on `CODEX`, a real launcher key, any setting, option, exit code or gate, and any change to the Claude worker, the tester or the reviewer.
