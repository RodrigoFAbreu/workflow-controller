## Goal

Close the five review leftovers of H4e ([#306](https://github.com/RodrigoFAbreu/workflow-controller/issues/306)) before H4e2 routes any real role to the Codex worker. They are one mechanism, the clone's evidence, durability and tests: after this item every record that ends with a clone still on disk names that clone's path in one place the guides point at, a record never says a clone is kept when it is gone, the landing tests cannot collide on their ownership tag, the drifted `resume` of a `LAUNCHED` Codex record has a test of its own, and the sandbox-only failures in the full suite are explained. No new mechanism: one helper that names a clone, one check that reads the path, tests and an investigation.

## Decisions

Each decision states one principle.

- **D1. One rule names a kept clone: after the tree is settled, if a tree still stands on disk, the ending's evidence carries its path.** A new helper in `controller/job.py` (next to `_codex_clone_path`), `_with_kept_clone(evidence, record, runtime_root)`, returns the evidence with `clone` set to the path only when that path **stands on disk** (the same stateless check D2 uses; `_codex_clone_path` alone returns a recorded path without looking, so a record whose tree is gone would be told "kept"), and only when the evidence has no `clone` **key** (a D2 `clone: null` is left alone, so the test is on the key, not the value). It reads the path and writes nothing else; an ending that removed the tree calls nothing. The existing `INTERRUPTED` branch of `_reconcile_codex_worker` uses the helper too, so that branch no longer names a clone from the record alone (the spawned branch of `_run_codex_worker`, `controller/job.py:9020`, and the live refusal, `:9314` through `clone_path`, still read the recorded path, but both settle with `keep_tree=True` just before, so the tree is on disk there; D1 leaves them). The endings that keep a tree, each a separate write with its own test, `FINISHED` included where the ending can be `FINISHED` (sites 1, 3 and 6 only: sites 4 and 5 always end `FAILED`) (a `FINISHED` record has no evidence of its own and gets `{"code": "CodexCloneKept", "clone": <path>, "message": ...}`):
  1. the `LAUNCHED` reconciliation in `_reconcile_codex_worker`, ending `INTERRUPTED`, `FINISHED`, `FAILED` or `INCOMPLETE`, named after its settle;
  2. the `LAUNCHED` reconciliation that **raises** (`_reconcile_launched` persists `FAILED` `UnreconcilableJobError` and then raises, `controller/job.py:2841`, so the code after the call never runs): `_reconcile_codex_worker` catches `UnreconcilableJobError`, and only when the record was persisted `FAILED` (the variant that persists nothing proves no worker gone and settles nothing) settles with `keep_tree=True`, names the clone in the persisted evidence, and re-raises. `_reconcile_protocol` has no raising ending of its own; CP2 confirms that by reading `_protocol_resolution`;
  3. a `COMPLETED` record's recovery through `_reconcile_codex_worker` into `_reconcile_completed`;
  4. `_resume_drifted_protocol`, for a `COMPLETED` record (after `_apply_codex_landing`) and for a `LAUNCHED` one (after its settle);
  5. the abandon of a `COMPLETED` record and of a `LAUNCHED` one in `_abandon_mark_failed` (`_with_landing_evidence` returns its input unchanged when the recovery is not refused, so these paths call the helper themselves);
  6. the live path's two terminal writes after `tree_left`, the protocol branch and the legacy branch (`tree_left` is held in memory until that write);
  7. **both exits** of the never-spawned branch of the live path (`controller/job.py:9011-9022`), which ignore the `left` value of `_settle_codex_worker_dir(keep_tree=False)`: (a) a `ControllerError` goes to `worker_not_started`, and a failed removal ends `WorkerNotStarted` with the clone named (the code stays `WorkerNotStarted`, so `never_launched` is unaffected); (b) any other exception raised before the spawn goes to the `else` branch and ends `FAILED` with `code` set to the exception's type (for example a launcher raising `RuntimeError`), and the same failed removal must name the clone there, with the code left as the exception's type. Both calls use the helper whatever `left` says, because `_settle_codex_worker_dir` returns `None` when its `scandir` fails even if the tree stands; each exit has its own test;
  8. `_abandon_replace`, for an unreadable record or one with another schema version: the path follows from the job id (`WorkerLayout(runtime_root, job_id).worktree`) and is named only when a tree stands there, in the evidence beside `code` and `original`.

  The guides' sentence "`rm -rf` of the exact path in `reconciliation_evidence.clone`" is then true for every ending that keeps a clone.
- **D2. A record never claims a clone is kept when its path is gone.** The refusal reports of `_apply_codex_landing` come from `recover`'s decision, which cannot know that an earlier `resume` already removed the tree in window (b) (the final block is persisted by the terminal write, which a second kill precedes) and that a later `resume` then judges `landing_unverified` because the operator moved the branch in between. (Window (d) cannot reach this refusal: `decide` returns from it with a final `landed` or `nothing` block and never refuses.) The fix reads the path instead of persisting before removing: after `_settle_codex_worker_dir`, a refused recovery whose tree is not on disk reports `clone_kept: false` and `clone_removed: true` in the landing block, clears the block's own `clone` (`_unreadable` puts the recorded path there, `controller/codex_worker_landing.py:354`, so a `landing_unreadable` recovery would otherwise read `clone_removed: true` beside a stale path) and sets `clone: null` in the evidence, with a message that the clone "is not on disk (an earlier recovery or the operator removed it)": a path check is stateless and cannot tell the two causes apart, and the guides tell operators to `rm -rf` a clone. The guide words `clone_removed: true` the same way. Persisting first would add a write to a path D7 of H4e made write nothing, and a path check is repeatable after any kill.
- **D3. Landing tests get per-test, per-process job ids.** The job id is the ownership tag `resume` and the tag scans use (`self.tagged(...)`, `_end_review_group`), and `JobFixture.next_id` yields `job1` in every test, so overlapping tests share a tag, the class of [#259](https://github.com/RodrigoFAbreu/workflow-controller/issues/259). One module-level helper in `tests/test_job_codex_worker.py` (beside `JobFixture`, which both modules already import) builds the form `t-<test name, last 24 characters>-<first 8 hex digits of sha256(the full test id, module.class.method)>-<os.getpid()>-<n>`; `LandingFixture` and `OrphanFixture` both override `next_id` to call it (round 6 review, I1: `OrphanFixture`'s own form, `<last 40 characters of the name>-<pid>-<n>`, collides for `DriftedTest.test_a_lone_codex_record_not_admitted_is_refused_before_any_write_and_the_orphan_keeps_running` and `ProtocolCodexTest.test_a_protocol_record_not_admitted_is_refused_before_any_write_and_the_orphan_keeps_running`, which share their last 40 characters and each spawn a real tagged worker that stays alive until cleanup). A truncated name alone is not unique: the two `ProtocolKilledLandingTest` methods at `tests/test_job_codex_worker_resume.py:844` and `:852` both end with `_release_changed_with_landing_unreadable`, so any suffix of their names up to that length yields the same id (round 5 review, I1); the digest of the full id is what separates them, and the readable tail is only for a human reading a tag. The constant `t-` prefix is load-bearing: the job id is a landing ref component and `gitrepo._landing_ref` requires `^[A-Za-z0-9][A-Za-z0-9._-]*$` (`controller/gitrepo.py:803`, `:808`), while the last 24 characters of a test name can start with `_` (measured at this base by counting `def test_` in the two modules: 12 of 73 names have a tail of 24 characters that starts with `_`, and 13 of 73 at 40 characters, the round-3 measurement; the form without the prefix failed 4 tests then, which the landing refuses as `fetch_failed` or before the kill point). `OrphanFixture`'s ids never reach a landing ref, so the prefix is not needed there, but sharing the helper keeps one form and costs nothing; the tests that use it read `record["job_id"]`, not the form (`tests/test_job_codex_worker_usage.py:107`), and the `job1` assertion at `:89` belongs to a `JobFixture` class that does not change. A short comment at the helper says the id must pass `_LANDING_JOB_ID`, so a later edit does not drop the prefix. `LandingFixture` also exposes `self.job_id` as a property computing the id of the job the test goes on to run (the same form with `n = 1`, computed from the test id and the pid, not read from a counter: `KilledLandingFixture.setUp` runs the `expected_phase` probe, which calls `next_id` once and then resets `self.ids`, so a stored "first id" would be the probe's, not the run's); the pid is what keeps two parallel copies of the same test from sharing a tag, and nothing needs the id to be the same in a re-run. `job_id` and `next_id` share one helper, so the two cannot differ. `ProtocolLandingTest` and `ProtocolKilledLandingTest` build their fixtures by composition (`LandingFixture("run_step")`, `KilledLandingFixture("run_step")`), whose own `self.id()` is the same for every test of the class, so the outer test's id must reach the fixture **before its `setUp`**: `self.fixture.id = self.id` (an instance attribute shadowing the method, which `next_id` reads at call time) before `self.fixture.setUp()`. Assigning `self.fixture.next_id` after `setUp`, as `ProtocolCodexTest` does at `tests/test_job_codex_worker_resume.py:297`, has no effect, because `JobFixture.setUp` has already patched `job._new_job_id` with the bound method (`tests/test_job_codex_worker.py:76`; measured: both tests of that class get `run_step-<pid>-1`); that dead assignment is deleted in CP1 (the class's tests do not depend on it) and `ProtocolCodexTest` gets the same one line instead, `self.fixture.id = self.id` before `self.fixture.setUp()`, because its fixture is an `OrphanFixture` (a `JobFixture`, not a `LandingFixture`) whose `next_id` reads `self.id()`, and without the line every test of the class would carry the shared id `run_step-<pid>-1`. Every `job1` in `tests/test_job_codex_worker_landing.py` and in the classes of `tests/test_job_codex_worker_resume.py` that build on these fixtures becomes `self.job_id`, including the ones inside longer literals (`refs/controller/landing/job1`, `tests/test_job_codex_worker_resume.py:770`). `JobFixture`'s direct users in `tests/test_job_codex_worker.py` keep `job1`: they have no landing and no kill, and the item does not widen. Every user of `OrphanFixture` (`RecordTest`, `VerdictRowsTest`, `DriftedTest`, `AbandonTest`, `ResumeSettlesTest` in the usage module, and `ProtocolCodexTest` by composition) gets the shared form through the one-line override.
- **D4. The drifted `resume` of a `LAUNCHED` Codex record is pinned by a test of its own, in `ProtocolCodexTest`.** `DriftedTest` builds on `OrphanFixture` and makes a record with no `protocol` block, which `_drift_decides` (`controller/job.py:3154`) refuses with `DriftedInstallationError`, so the `elif` branch of `_resume_drifted_protocol` is reached only by a protocol record. The new test in `ProtocolCodexTest` extends `test_an_admitted_record_with_nothing_alive_is_failed_release_changed_with_the_copy_removed` (`tests/test_job_codex_worker_resume.py:357`), which pins the status, the `workflow_release_changed` reason (in `reason`, not `code`) and the credentials but not the directory, so a mutant that removes the branch's `_settle_codex_worker_dir` call survives it today. The new test populates the job directory (`launch_that` writes only `auth.json`, so it adds sessions and other files) and asserts the directory holds only the tree and the retained sessions, no landing block is written and no landing ref exists. It is written first against the unchanged behaviour (CP1) and extended by D1 (CP2) to assert the clone is named. Its tag scan runs on the id the record actually carries (`record["job_id"]`), read from the record: `OrphanFixture` has no `job_id` attribute and D3 adds none, so the test asserts nothing against a fixture attribute, and the record's id is per-test through the line D3 gives `ProtocolCodexTest`.
- **D5. The sandbox failures are explained, not guessed.** `FakeLaunchTest` in `tests.test_review` and `tests.test_review_claude` passes here (75 tests, 13 s). The two messages (`the composing command did not run`, `` `features list` did not run ``) are Codex-side refusals: `controller/review.py:1303` is the composing helper that `_preflight` calls and `:1868` is `_preflight` itself, raised when a bounded command times out or exits non-zero, while `tests.test_review_claude.FakeLaunchTest` launches with `harness_name="claude"` and neither message appears in that module; the report records which module raised which message. The implementer's sandbox at `02269f8` is the environment of the two failing runs that [#306](https://github.com/RodrigoFAbreu/workflow-controller/issues/306) item 5 names, which the item page does not describe further; the report states what it could establish of it (its `HOME`, `PATH`, writable paths, CPU count) before reproducing. The investigation reproduces under pinned CPUs and parallel copies as for the CI flakes, then under the sandbox's own environment, records the cause with the command that shows it, and acts by cause: a **timing** cause gets a readiness fix in the test fixture (never a longer sleep), an **environment** cause gets the sentence in `docs/guide/development.md` that tells an implementer how to run the suite there, and **neither** is reported as an open question with the evidence, not closed. No file under `controller/` changes for this decision.
- **D6. Documentation follows.** `docs/guide/harnesses.md`, `docs/guide/workers.md` and `docs/common-problems.md` say the path is in `reconciliation_evidence.clone` for every ending that keeps a clone, name the `CodexCloneKept` code, add `clone_removed` to the landing block's field list (`docs/guide/harnesses.md:299`), drop the parenthesis that sends a drifted `resume` or `--abandon` to `codex_worker.clone.path`, replace the sentence "A `LAUNCHED` record ends `INTERRUPTED` naming its clone" (`docs/guide/harnesses.md:315`), which is no longer the only ending, and say what `clone: null` with `clone_removed: true` means (the clone is not on disk: an earlier recovery or the operator removed it). One window stays: naming is a second write on the `LAUNCHED` path (the terminal record, then the settle, then the name), so a kill between them leaves a terminal record without the name; site 2 (the raise) names in a second write after the `FAILED` persist, and site 3 does too unless the evidence is threaded into `_reconcile_completed` and `_reconcile_protocol`, which persist their own ending (on site 3 `codex_worker.landing.tree_left.path` also holds the path); the guides keep `codex_worker.clone.path` as the stated fallback for that window, and `resume` does not return to a terminal record. `python3 tools/check_docs.py` passes.
- **D7. In-flight declaration.** The generated template classifies this item's paths at both stages (the plan and `controller/`, `tests/`, `docs/guide/` and `docs/common-problems.md` as the H4e declaration has them); `SELF_REVIEWING_PLAN` confirmed that every path in the checkpoints' Files paragraphs is classified at both stages, so no hand edit is needed.
