## Goal

Settle the two things H4c1 left undecided ("the tree" and "how its commits return") so that a Codex worker job can do real work and the Controller can see it. A Codex worker runs in a **private clone** of the managed repository, never in the managed repository itself (owner decision, 2026-11-02). When the job ends, the **Controller** (never the worker) checks the clone and, only if every check holds, fast-forwards the managed branch to the clone's tip. After a landing the managed repository is as if the worker had worked in place, so the existing verification and the protocol decision's `reconcile` find the progress unchanged. Anything else ends the job `FAILED` with a named reason and keeps the clone. Nothing real reaches the branch: the seam stays dark until H4e2.

## What exists

- `job.CODEX_WORKTREE_PREPARER` (`controller/job.py`), `(managed_repo, layout) -> Path`, `None` by default; with `None` `_run_codex_worker` raises `WorkerLaunchError` before the launch and the record ends `FAILED` `WorkerNotStarted`. Tests set it to a clone they make.
- `codex_worker_sandbox.WorkerLayout(runtime_root, job_id)` with `.worktree` (`<runtime>/worker/<job>/tree`), `.home`, `.codex_home`, `.scratch`; `command_environment` (the sandboxed shell's environment: no inherited identity, no git configuration beyond the repository's own, `GIT_CONFIG_NOSYSTEM=1`), `check_worktree` (a real `.git` directory), `guard_digest`/`check_guard` (nothing under `.git` may change except what a commit or a plain `git gc` writes; a symlink, special file or alternates file refuses), and the `worker` profile that makes `.git/hooks` and `.git/config` read-only and the network off. `codex_worker.launch_codex_worker` already runs the guard before and after the run, and `_breach` (`controller/codex_worker.py:137`) turns three post-run checks (the guard, the nested-repository scan, the Codex build) into a `FAILURE` of subtype `sandbox_breach` (`codex_worker.SUBTYPE_BREACH`).
- `_run_codex_worker` (H4c1, H4c2, H4d): the `codex_worker` block (`operator_home`, `captured_digest`, `lock_inherited`) persisted before the preparer, `worker_process` flushed on spawn, usage admitted and accounted, `resume` ending an orphan and reconciling it `INTERRUPTED`.
- After the launch, `_launch_job` writes `COMPLETED`, then either `_protocol_resolution` (a protocol decision: the Workflow's `reconcile`) or `_verify_transition` over a fresh read of the managed repository (a legacy target). Both read only the managed repository. Today a Codex job never changes it, so `docs/guide/harnesses.md` records `phase_not_in_to_any_of` / `no_progress` as the documented consequence.
- `gitrepo` (`fetch`, `ref_commit`, `is_ancestor`, `commit_parents`, `head_state`, `tracked_changes`, `fast_forward`) with `_check_fetch_refspec`, which allows a fetch only into `refs/remotes/<remote>/`. `tracked_changes` runs `status --untracked-files=no` (`controller/gitrepo.py:231`), so it does not see an untracked file, and `fast_forward` takes no hardening; the landing needs a new untracked query and its own hardened writes (D2, D4); `review.build_copy`'s `_git_env` (a scrubbed environment: fixed `PATH`, `HOME` and `GIT_CEILING_DIRECTORIES` at the job base, no system config); `runtime.remove_tree` (refuses a path below a link, C10k); `milestone_branch` and `_branch_invariant_violation`, which verify the managed branch after a job.

## Decisions

Each decision states one principle.

- **D1. The clone is a separate repository with nothing connecting it back, and a known author.** `controller/codex_worker_tree.py` (new) has `prepare(managed_repo, layout, base) -> Prepared`. It refuses first (D2), then runs, in the scrubbed environment of `review._git_env`, `git clone --no-checkout --no-local --no-hardlinks --no-tags --single-branch --branch <branch> -c core.hooksPath=/dev/null -c gc.auto=0 -c maintenance.auto=false -- <managed root> <layout.worktree>`, deletes the clone's only remote (`git remote remove origin`) so the worker has no remote it could push to, writes `core.hooksPath=/dev/null`, `gc.auto=0`, `maintenance.auto=false` and the author identity (below) into the clone's own config, and checks out the branch at `base` through `gitrepo.checkout_branch_at(clone, branch, base)` (`git checkout -q -B <branch> <base>`, hooks off). **Where the checkout lives (B1):** `tests/test_no_rewrite_invariants.py` refuses any mutating Git subcommand, `checkout` included, outside `controller/gitrepo.py` when its argv is one literal, so `codex_worker_tree` calls this `gitrepo` function and spells no `checkout` itself; the choice is named rather than left to the scan's blind spot for an argv that is not one literal (`functional_review.py:2218`). `clone`, `remote` and `config` are not in the scan's mutating list. `--no-local` makes the clone fetch through `upload-pack` instead of copying the managed object store, so the clone holds only the objects reachable from the managed branch (a commit that exists only on another branch of the managed repository is absent from it), and a managed repository's `objects/info/alternates` is not carried into the clone, which would fail the guard. The cost is that `upload-pack` runs in the managed repository and reads its config; that config is the operator's own and is exactly what any clone the operator makes would read, and the scrubbed environment drops the operator's global and system configuration. The clone's `.git` is a real directory with its own object store; `codex_worker_sandbox.check_worktree` is run on the result, and `guard_digest` of the finished clone, **taken after the identity is written**, is recorded for the landing (D4). **Identity:** `command_environment` deliberately gives the sandboxed shell no identity and the sandbox makes `.git/config` read-only, so a plain `git commit` in the clone would fail with `Author identity unknown`. D1 therefore writes `user.name = Codex worker` and `user.email = codex-worker@controller.invalid` (module constants `WORKER_AUTHOR_NAME`/`WORKER_AUTHOR_EMAIL`) into the clone's config at prepare time, so a worker's plain commit succeeds and every commit it makes carries this fixed, recognisable author, never one the model invents with `-c`. A worker that sets another author with `-c` still lands (D5 does not judge authors); the constants only make the ordinary path deterministic. The managed repository's `info/attributes`, filters and `.gitattributes` run no program during the clone or the checkout: the clone's own config holds no `filter.*` key (a clone does not copy the managed repository's local config), so nothing selects a filter program there, and the scrubbed environment carries no global or system configuration (a test with a `filter=` attribute and a configured clean/smudge program in the managed repository proves nothing runs in the clone).
- **D2. The clone starts from what the Controller recorded, and only from a clean, unmoved managed branch.** The base is `pre_state["target_head"]`, the commit the Controller captured before the job (`_capture_pre_state`, set on every branch); `_launch_job` passes it down to the preparer. `prepare` refuses with `CodexTreeError` (named `cause`) when: `HEAD` is detached (`detached_head`); the checked-out branch is not at `base` (`managed_branch_moved`); the managed repository has any tracked change, staged change or intent-to-add entry (`gitrepo.tracked_changes`), or an untracked non-ignored file (a new `gitrepo.untracked_files`, `git ls-files --others --exclude-standard -z`, because `tracked_changes` passes `--untracked-files=no`) (`managed_tree_not_clean`); or the Controller's runtime root lies inside the managed root (`runtime_inside_managed`, I2 of round 6: the resolved `layout.runtime_root`, links followed, equal to the managed root or below it; the runtime ladder's row 3 is `<origin checkout>/.controller` and `--runtime-dir` may name any path, and a landing must never be able to add a file to the Controller's own state, see D3 (3) and D5); or the managed repository defines a config hook (`managed_hooks_configured`, the check D3 (3) makes again after the run; made here too so that a refusal costs no worker run, O2); or the clone cannot be made (`clone_failed`, with Git's stderr; a clone partly made is removed through `runtime.remove_tree` before the error is raised). **Every read of the managed repository here (`tracked_changes`, `untracked_files`, `ref_commit`, `head_state`) runs with `GIT_OPTIONAL_LOCKS=0` and `-c core.fsmonitor=false`** (I3): `git status` otherwise refreshes the index opportunistically and fires a managed `post-index-change` hook (measured with a stale index); `gitrepo.tracked_changes` and `untracked_files` take a `no_optional_locks` argument that the preparer, the landing and `resume` pass. The scrubbed environment (no `HOME`) also changes what is untracked: a file ignored only through the operator's own `~/.config/git/ignore` is untracked here and gives `managed_tree_not_clean` while the operator's `git status` is clean (O5); it fails closed and `docs/common-problems.md` says so. Ignored files are deliberately not part of "clean" (`.ai-review/` is ignored and holds the bundles and verdicts); D4 is what protects them. A clean tree is required because the clone sees only committed state, and a landing is a fast-forward of the branch: uncommitted work in the managed repository cannot be handed to the worker and could not be returned. This is stated as the cost of the owner's decision, not hidden: **the Workflow keeps plan files intent-to-add and `WORKFLOW_STATE.json` edits uncommitted between gates**, so a role that needs those (the review-side roles of H4e2) cannot yet run in a clone. H4e2 must settle that before it routes a role, and the guide and the item page say so (see Open decisions).
- **D3. The landing is a Controller act with one question: is this exactly a fast-forward, and nothing else.** `controller/codex_worker_landing.py` (new) has `land(managed_repo, prepared, runtime_root, job_id, *, worker_breach, on_intent) -> Landing` (`on_intent: Callable[[str], None]`, called once with `checked_tip` after every check and before the fetch, I1), run by `_launch_job` once the worker has ended and `COMPLETED` is written, under the lifecycle lock the job already holds (the Controller writes to the managed repository only here, never while a review job reads it: a change of refs or config during a Codex review ends it `ReviewRepositoryChanged`, and no review job runs inside a step). `worker_breach` is `result.subtype == codex_worker.SUBTYPE_BREACH`. In order, each refusal naming a `cause`: (0) **the launcher already judged the run untrustworthy**: `worker_breach` is true (`sandbox_breach`: the `.git` guard, the nested-repository scan or the Codex build failed after the run, per `_breach`), refused before any other check, whatever the commits look like, the clone kept; an ordinary failed worker (timeout, limit, error) is not a breach and still has its clone checked (D6); (1) the clone's `.git` is unchanged but for commits: `check_guard(prepared.guard, guard_digest(worktree))` (`clone_git_changed`: hooks, config including the identity, a link, alternates); (2) the clone has no ref but `refs/heads/<branch>` (and the `HEAD` symbolic ref to it) (`extra_refs`: a tag, another branch, `refs/stash`, notes); (3) the managed branch is still at `base` and `HEAD` is still that branch, and the managed tree is still clean (`managed_branch_moved`, `managed_tree_not_clean`), the runtime root still lies outside the managed root (`runtime_inside_managed`, the check D2 makes before the clone, made again from the `runtime_root` argument of `land` before the fetch, I2 of round 6: `--no-overwrite-ignore` stops an overwrite, not a new file, and a worker commit that force-adds `.controller/jobs/forged.json` would otherwise land a file that `resume` later reads as a job record; measured), and the managed repository defines no config hook (`git config --get-regexp '^hook\.'` under the scrubbed environment, **without `--local`**, so a hook in a file reached by `include.path` is found, which `--local` misses (measured, O1); `managed_hooks_configured`: D4 switches off the events it lists, and this refusal fails closed for an event the list misses, O1); every read here runs with `GIT_OPTIONAL_LOCKS=0` (D2); (4) the clone's branch tip, read once and kept as `checked_tip`, is the base itself (`nothing_to_land`, a success: no write) or a strict descendant (`not_a_descendant`: `is_ancestor(base, tip)`); (5) the range `base..checked_tip` is linear (checks (4) to (6) read through `-c core.commitGraph=false`, O1 of round 4: `GUARD_EXCLUDED_ROOTS` leaves all of `.git/objects` out of the guard, so `.git/objects/info/commit-graph` is writable by the worker and unseen by check (1), and `rev-list --parents` reads parents from it; measured, a forged graph hid a merge commit from `commit_parents` and `rev-list --merges --count`, while `cat-file` showed two parents; the fetch's `fsckObjects` does not see it; with the graph off the true answer is read): every commit has exactly one parent (`merge_commit`) and the count is within `MAX_LANDED_COMMITS` (200, `too_many_commits`); (6) the range touches no submodule **in any commit of it**: for each commit of the range, its own diff against its parent has no `.gitmodules` change and no gitlink (mode 160000) entry (`submodule`), so a gitlink added in one commit and removed in a later one is still refused. Then the landing calls `on_intent(checked_tip)` (`_launch_job` writes the intent block of D6 there, before anything changes in the managed repository), and fetches and moves the branch (D4). `on_intent` is **not** called for a refusal at checks (0) to (6) nor for `nothing_to_land`; an exception it raises is `landing_error` and nothing has been fetched. **A committed symlink (mode 120000) is allowed to land**, including one that points outside the repository: a fast-forward writes it as a link, never through one (Git refuses to write a path below a link), and the landing judges integrity, not content (D5); a CP2 test pins that the symlink lands as a link and that a file outside the repository it points at is untouched. **Unexpected failures:** `land` runs every check and write inside one guard; any `GitOperationError`, timeout or `OSError` not named above is `landing_error` (with the exception's message), a refusal like the others (D6), never an exception out of `land`. **A `landing_error` raised at or after the merge reads the branch before it reports `moved` (I1 of round 5)**: see D4; one raised before the merge (the checks, the fetch, `on_intent`) has moved nothing and says `moved: false`.
- **D4. The fetch cannot run anything of the worker's and every Git write in the managed repository runs no hook.** The clone's object database is read by `git fetch --no-tags --no-write-fetch-head -- <clone path> refs/heads/<branch>:refs/controller/landing/<job id>` in the managed repository (Git already refuses a fetch into the checked-out branch, and the destination here is never a branch), with `-c fetch.fsckObjects=true -c transfer.fsckObjects=true -c protocol.allow=never -c protocol.file.allow=always` and the scrubbed environment (`GIT_ALLOW_PROTOCOL=file`), so a crafted object, a path such as `.git/x` or a non-file transport is refused by Git itself (`fetch_failed`, with stderr). Running `upload-pack` in the clone reads the clone's config, which the worker could change only by defeating the sandbox's read-only `.git/config`; check (1) of D3 has already proved the config and hooks unchanged, so nothing the worker wrote is executed (a test plants `uploadpack.packObjectsHook` in the clone and shows the landing refuses at (1) before any fetch). **Reads and writes (I3):** the writes below go through one hardened runner; the status reads of the landing (D2 (3), the post-move check) run with `GIT_OPTIONAL_LOCKS=0` and `-c core.fsmonitor=false`, so no managed hook fires from an index refresh and no fsmonitor program runs. **One hardened option set, in one place:** `gitrepo` gets a constant `LANDING_CONFIG` (`core.hooksPath=/dev/null`, `core.fsmonitor=false` (O4: a `core.fsmonitor` program in the managed repository's own config fires on `git status`, measured; it is operator configuration the worker cannot set, the same class as the filters, and is switched off for every landing read and write rather than left to run), `gc.auto=0`, `maintenance.auto=false`, and `hook.<event>.enabled=false` for each of `reference-transaction`, `post-index-change`, `post-merge`, `pre-merge-commit`, `post-checkout`, `post-commit`, `post-rewrite` and `pre-auto-gc`, the list finalised by CP2's measurement against the installed Git) and one private runner, `_landing_git`, and **every** Git write the landing makes in the managed repository goes through it: `landing_fetch(repo_root, path, branch, job_id)` (its refspec check allows only `refs/heads/<name>:refs/controller/landing/<id>`: no `+`, no wildcard), `landing_merge(repo_root, sha)` and `landing_delete_ref(repo_root, job_id)` (O2: a config hook with a free friendly name and an `event` key, `hook.<name>.event=post-merge`, is switched off by `hook.post-merge.enabled=false`, measured; a config hook whose friendly name equals a known event name makes Git die with exit 128 under the hardened options, so the delete fails and the outcome is `ref_left`, D6). **`landing_delete_ref` is a stated, narrow exception to `gitrepo`'s "never deletes a ref" (I2 of the trunk-branch milestone) (B1):** it spells `update-ref -d` and only for `refs/controller/landing/<job id>`, the Controller's own private namespace, which is not a rewrite of anything the operator or the Workflow owns. CP2 corrects the module docstring to say so and changes `tests/test_no_rewrite_invariants.py` to admit exactly this one spelling (in `controller/gitrepo.py`, with a ref that starts `refs/controller/landing/`; O3: `_argv_nodes` maps a non-constant element to `None`, so the real argv `["update-ref", "-d", f"refs/controller/landing/{job_id}"]` scans as `["update-ref", "-d", None]`, and the scan is extended to read the leading constant of an f-string element; a variable that holds the ref, or an f-string whose leading constant is anything else, stays refused, and the test uses this real shape), with a test that any other `update-ref -d`, in `gitrepo.py` or elsewhere, and any other spelling of a ref delete (`update-ref --stdin` is not scanned, so the function builds its argv as one literal and the test pins that) still fails. The landing stays separate from `gitrepo.fast_forward`, which is used by the close-out and is left unhardened and unchanged. The fetch also triggers automatic maintenance and the merge does too, hence `gc.auto=0`/`maintenance.auto=false` on all three. **The fetched commit is the one examined:** after the fetch the landing compares `ref_commit(refs/controller/landing/<job id>)` with `checked_tip` and refuses on a difference (`tip_moved`: the clone's branch moved between the checks and the fetch, for example through a surviving worker process) before the merge. The branch then moves with `git merge --ff-only --no-overwrite-ignore <checked_tip>` through `landing_merge`: `--no-overwrite-ignore` makes Git refuse (exit 1, naming the file, branch and tree untouched) when the range adds a path that is an **ignored file in the managed repository**, which the clone does not hold, so a worker's `git add -f` of `ign/state` or of `.ai-review/...` cannot replace the managed file (`would_overwrite_ignored`). **A failed `merge --ff-only` does not necessarily leave the managed repository as it was (B2):** Git updates the working tree and the index first and the ref last, so a failure of the ref update (measured with `refs/heads/<branch>.lock` held: exit 128, `update_ref failed`, `HEAD` still at `base`, the worker's content staged) leaves the branch at `base` **with a moved tree**; a kill or the Controller's git timeout between the two steps reaches the same state (from Git's order of operations). So after any merge that did not succeed the landing reads the branch (`ref_commit`) **and** the tree (`tracked_changes`, `untracked_files`, `GIT_OPTIONAL_LOCKS=0`). Exit 1 with the "would be overwritten" or "would lose untracked files" text is `would_overwrite_ignored` (both shapes: an ignored file, and an ignored directory that the range replaces with a file, O3; told apart from the ref failure by exit code 1 against 128, and each has a test); any other failure with the branch at `base` and a clean tree is `fast_forward_failed`; **the branch at `base` with a dirty tree is `merge_left_tree_dirty`**, a refusal with `moved: false` whose record carries the dirty paths (`dirty`). The landing never repairs it (`reset --hard` and `checkout --` are forbidden); the operator's recovery is in `docs/common-problems.md` (read `git status`, inspect, then `git restore --staged --worktree .` or keep the worker's content as the operator decides, the clone being kept). **After any merge that did not succeed the branch is classified by where it stands, and every route to a moved branch goes through `verify_move` (I1 of round 5):** the merge may fail after its ref update committed (the Controller's git timeout kills at any moment and `gitrepo._run` turns that into `GitOperationError`, `controller/gitrepo.py:92`; measured with SIGKILL at the ref update: exit 137, the branch at the tip, the tree clean). So the landing reads the branch first: (1) **at `base`**: the rules above (`would_overwrite_ignored`, `fast_forward_failed` or `merge_left_tree_dirty`); (2) **at `checked_tip`**: the landing calls `verify_move`, the same function window (b) calls, giving `landed` (the merge did its work and only its report was lost) or `landing_unverified` with `moved: true`; (3) **at neither commit**: `landing_unverified` with `moved: true`, the same as window (c), the branch not touched. (4) **`landing_error` at or after the merge reads the branch before it reports `moved`**; when that read also fails the landing records `landing_unverified` with `moved: true` and says the branch could not be read, because a merge that raised or reported success cannot be shown not to have moved it; and a read that fails inside `verify_move` after a successful merge is `landing_unverified` with `moved: true` for the same reason. A test double of the Git runner that performs the merge and then raises `GitOperationError` makes (2) deterministic. **The landing ref is removed on every path after the fetch**, success or refusal, in a `finally` through `landing_delete_ref`. The landing then runs **the post-move check, one function `codex_worker_landing.verify_move(managed_repo, tip, branch)` that `land` and `recover` both call (I2 of round 4, so the live path and the recovery path cannot drift apart)**: the branch is `tip`, `HEAD` is that branch and the managed tree is clean (`tracked_changes` and `untracked_files` empty, `GIT_OPTIONAL_LOCKS=0`); any difference is `landing_unverified`: the branch is not touched again, the clone is kept and the job fails (D6). The merge runs under the scrubbed environment, which carries no global `filter.*` or `core.autocrlf`; a program a `.gitattributes` the worker committed selects from the **managed repository's own local config** is the operator's, run as it would run on any checkout the operator makes, so it is not refused, and a filter that makes the written bytes differ from the committed tree surfaces as `landing_unverified` through the clean-tree check. **A range that edits `.gitignore` (O4):** a commit that removes `ign/` from `.gitignore` lands, and the managed `ign/state` is then untracked, so the post-move check gives `landing_unverified` with `moved: true`: defined and safe, and the one way an otherwise clean commit reaches that outcome; CP2 has a test for it and the guide says so.
- **D5. What the landing judges is the integrity of the move, never the content of the commits.** The Workflow's own checks (approval fingerprints, `generation_head`, protected paths, trailers, `verify_plan_review_bundle`) judge content exactly as they do for an in-place worker, because a fast-forward keeps every commit id and tree byte for byte. A worker that changes a protected file stales the approval it covered here as it would in place; a worker cannot make the landing accept or skip any approval check, and the landing weakens none. So the landing does not check author, trailer shape or paths; it checks the range's shape (D3 5 and 6), that the move cannot overwrite a file the content checks do not see (an ignored file, D4), that it cannot add a file to the Controller's own runtime (`runtime_inside_managed`, D2 and D3 (3): a Codex worker in place would be inside the sandbox that denies it that write, so the landing must not give it the write through the Controller, I2 of round 6) and nothing else. This answers "ask rather than guess" by making the landing neutral, and is stated for review as a decision rather than an Open-decisions row.
- **D6. The outcome is a record block and the job's status follows it.** Before the fetch, in the `on_intent` callback it gives `land`, `_launch_job` writes `landing = {outcome: "started", base, tip: checked_tip, branch}` (the intent: the one fact that tells a record whose branch moved from one that never landed, see D7). After the landing it writes the final block `{outcome: "landed" | "nothing" | "refused", cause, base, tip, commits: [sha...], branch, clone_kept, moved, ref_left, dirty}` (`Landing` carries the same fields: `outcome`, `cause`, `base`, `tip`, `commits`, `moved`, `ref_left`, `dirty`) with the `COMPLETED` write's successor (`moved` is true only when the branch was moved, so `landing_unverified` is `refused` with `moved: true`). `landed` and `nothing` continue to the unchanged reconciliation (the tree is removed before the terminal write, D7) (legacy `_verify_transition`, or the protocol's `reconcile`), which now sees the landed commits; a job that landed nothing keeps today's `phase_not_in_to_any_of` / `no_progress`. `refused` ends the job `FAILED` with `reconciliation_evidence = {"code": "CodexLandingRefused", "cause": ..., "message": ..., "clone": <path>}`, whatever the worker's own outcome, and `transition_verified: false`, **the final `refused` block and the `FAILED` status being one `_persist` (I2)**, so no `COMPLETED` record with a `refused` block exists and a killed Controller cannot send a refused landing through the reconciliation, which judges only the Workflow state; every cause named in D3 and D4 (including `sandbox_breach`, `tip_moved`, `merge_left_tree_dirty`, `would_overwrite_ignored`, `managed_hooks_configured`, `landing_error` and `landing_unverified`) is a `refused` outcome. A refusal leaves the managed repository exactly as it was, except `landing_unverified` (the branch was moved, or a merge that raised or succeeded left it where it cannot be shown unmoved, and the record says `moved: true`; this includes a failed merge whose branch stands at `checked_tip` but fails `verify_move`, a branch at neither commit, and an unreadable branch after the merge, I1 of round 5; a failed merge whose branch stands at `checked_tip` and passes `verify_move` is `landed`) and `merge_left_tree_dirty` (the branch is at `base` but the tree and index hold the worker's content: the record says so with `moved: false` and the dirty paths, and the next job refuses `managed_tree_not_clean`). A failed landing-ref delete after a verified move cannot undo the move: the outcome stays `landed`, with `ref_left: true` and the ref's name in the block, and the guide names the one `git update-ref -d` command. The usage accounting is unaffected (it was written with `COMPLETED`). A worker whose own outcome was an ordinary failure (not a `sandbox_breach`) still has its clone checked and, if its commits are a clean fast-forward, landed: the Controller does not decide the worth of the commits, the reconciliation does.
- **D7. What happens to the tree on every path, and what `resume` does.** The rule: the clone is **removed at job end** through `runtime.remove_tree` (the whole `<runtime>/worker/<job>/` tree except the retained `codex-home/sessions`, the rollout a later admission reads, as for a review job, `review.settle_job_dir`'s rule) **unless the worker's commits are unlanded and may matter**, in which case `tree` alone is kept and named in the record. **The removal is made before the job's terminal write, not after it (O3 of round 4)**, as `_reconcile_review` settles the job directory before its own terminal write: a kill between a terminal record and a later removal would leave a tree that no record names, which `resume` reports and never reconciles and no retention removes; with the removal first, a kill leaves a `COMPLETED` record that window (d) below finishes, and the removal is repeated there. Per path: `landed`, `nothing` and every ordinary worker failure that is not a refusal: removed in `_launch_job` before the terminal write. A landing `refused` (any cause, including `sandbox_breach` and `landing_unverified`): kept. The launcher's own refusals before the worker is spawned (the build gate, the placement checks in `launch_codex_worker`, the controls, `worker_not_started`) and a `clone_failed` partway through: the worker never ran, so nothing of it is worth keeping and the tree is removed, in a `finally` around the section of `_run_codex_worker` that follows the preparer and in `prepare` itself. An exception that leaves `_launch_job` after the worker was spawned (`worker_process` is in `spawned`): kept and named in the record, like a lost Controller. **A kill between `prepare` returning and the `clone` block being persisted** (O3): `resume` ends the record `INTERRUPTED` and the record names no clone; the path is derived from the job id, `WorkerLayout(runtime_root, job_id).worktree`, and `resume` names that derived path in the evidence and keeps it (it never removes a tree no record names). The runtime root is never `/tmp` for a real run, and the tests' scratch runtime roots are removed in `tearDown` and have a `LEFTOVER_INVENTORY` row where the scan finds a process or clone construct. The operator removes a kept clone with `rm -rf` of the path (Git's object files are read-only, so `rm -r` on a terminal prompts for each, O6; the guide names the exact path, never a glob) in the record's `reconciliation_evidence.clone` (the guide says so; there is no `runtime` command and no retention or pruning, `docs/guide/workers.md`), and the next run does not reuse it (the job id differs). **`resume` never fetches or merges; it recovers a record by reading refs and the tree, and its only writes are the ones named below.** A `LAUNCHED` Codex record (the Controller was lost with the worker alive or ended) reconciles `INTERRUPTED` as today, its clone kept and named. **One recovery helper, called from every path that can end a `COMPLETED` Codex record (I1 of round 3).** `codex_worker_landing.recover(managed_repo, record) -> Recovery` is split in two (O2): a **decision part**, `decide`, which only reads (refs and the tree, `GIT_OPTIONAL_LOCKS=0`, `-c core.commitGraph=false`) and returns a `Recovery` (the final `landing` block, whether to delete the landing ref, whether to remove the tree, and whether the record is to end `FAILED` `CodexLandingRefused` or continue to the reconciliation); and an **applying part**, owned by CP3, which persists the block, deletes the landing ref through the hardened `landing_delete_ref` (the one write `recover` makes in the managed repository, in the Controller's own job-specific namespace, in windows (a) to (c)) and removes the tree. It is called by `_reconcile_codex_worker` (an undrifted `resume`, `controller/job.py:3613`), by `_resume_drifted_protocol` (a drifted installation, `controller/job.py:3103`) and by `_abandon_mark_failed` (`resume --abandon`, `controller/job.py:4851`). The drift and abandon endings keep their status and code (`workflow_release_changed`, the abandon code); the helper adds only the final `landing` block, the deletion of the landing ref and, in window (b) when `verify_move` holds and in window (d), the removal of the tree, and the evidence of those two endings carries the landing `cause` and the clone path when the landing did not land. For a record with a well-formed `clone` block the helper decides, in order (a `COMPLETED` Codex record with no `clone` block at all, or a malformed one, is `landing_unreadable` below): (d) **a final `landed` or `nothing` block is already there** (the Controller was killed after that write and before the terminal write, I2 of round 3): the record goes to the unchanged reconciliation (`_reconcile_completed`) and the tree is removed by this rule, because its commits landed or there were none, so `nothing` is removed as on the live path; no final block, then by the intent block: (a) **the branch is still at `base`** (killed before the fetch, after the fetch and before the merge, or in the merge): any `refs/controller/landing/<job id>` is deleted and the record ends `FAILED` `CodexLandingRefused`, the clone kept and named, nothing landed. The cause depends on the tree and on the intent (O5 of round 3): the **intent block exists** and the tree is clean: `landing_interrupted`; the **intent block exists** and the tree is dirty (the merge was in flight between its tree update and its ref update, B2): `merge_left_tree_dirty` with the dirty paths, nothing repaired; **no intent block** (the merge never ran, so a dirty tree is not its doing, for example the operator's own edits since the crash): `landing_interrupted`, with the dirty paths recorded in the block; (b) **the branch is at the intent's `tip`, a descendant of `base`** (killed after the merge and before the final block): the helper runs **the same post-move check as the live path, `verify_move` (I2 of round 4)**, through `GIT_OPTIONAL_LOCKS=0` reads: the branch is `tip`, `HEAD` is that branch and the managed tree is clean. If it holds, the helper deletes the landing ref, writes the final `landed` block (`recovered: true`) and the record continues to the unchanged reconciliation, **removing the tree** (the commits have landed and nothing else would remove it). If any part differs, the record ends `FAILED` `CodexLandingRefused` cause `landing_unverified` with `moved: true`, the clone kept, the landing ref deleted and the branch not touched, exactly as the live path ends it; a dirty tree here may also be the operator's own edits since the crash, and failing closed is the right answer for that too (the same repository state ends the same way whenever the Controller died: a range that removes `ign/` from `.gitignore`, a filter that rewrites bytes and a `HEAD` left on another branch all end `landing_unverified`, none `landed`); (c) **the branch is at neither `base` nor the intent's `tip`**, or there is no intent block and the branch is not at `base` (the intent's `tip` does not exist then, so the branch having moved is itself the finding): `FAILED` `CodexLandingRefused` cause `landing_unverified` with `moved: true`, the clone kept, the branch not touched and any landing ref deleted (R5: no ending leaves one). A failed ref delete in any window is recorded `ref_left` and changes no cause. **When `recover` cannot read the managed repository (I1 of round 4):** `ref_commit` returns `None` for a branch ref Git cannot read (measured with a garbage ref; `head_state` raises), and `decide` counts that `None` as unreadable, never as "the branch at neither commit" (O2 of round 6), so the recorded reason is `landing_unreadable` and not window (c)'s `landing_unverified`; after a merge the same `None` is `landing_unverified` with `moved: true`, which D4 already says. `decide` catches `GitOperationError`, `OSError` and a malformed `clone` or `landing` block (a missing field, a wrong type) and returns, instead of raising, a `Recovery` of cause `landing_unreadable` whose block says the branch could not be read, carries the reason and names the clone, which is **kept**, with no ref delete and no tree removal. **What reaches the helper, per caller (I2 of round 5):** `resume` runs `validate_record` (`controller/job.py:3586`) before it dispatches to `_reconcile_codex_worker` (`:3613`) or `_resume_drifted_protocol`, and its case 2 (`:2373`) rejects a managed root that is not a directory or whose Workflow state cannot be read; `resume` then raises `StaleJobRecordError` naming `--abandon`, writes nothing and leaves the record as it was (measured with `OrphanFixture`, and the comment at `:4874` says so). That existing behaviour is the right one and is unchanged: for such a root, drifted or not, **at the `job` level `resume` refuses with nothing written and `job.abandon` ends the record**, and `job.abandon` is the one caller that sees a missing root (`:4797`, `tests/test_job_codex_worker_resume.py:437`). **The command is stricter than the `job` level (I1 of round 7):** `cmd_resume` builds its target with `_inspect_target` before it calls `job.abandon` (`controller/cli.py:2468`), and `managed_repo.inspect` starts with `git rev-parse --show-toplevel` (`controller/managed_repo.py:173`), so on the CLI a missing root or an unresolvable Git directory refuses both `resume` and `resume --abandon` with `NotARepositoryError` (exit 20) before `job.abandon` is reached (measured by the reviewer with the real CLI). The no-lock path stays for a direct call of `job.abandon` and keeps its CP3 tests, and `landing_unreadable` over a missing root is reached only that way; through the command it is reached for an unreadable Workflow state (the Manager's `verify` and `status` exit 0 over a garbage `WORKFLOW_STATE.json`, so `--abandon` reaches `job.abandon`) and for a garbage `.git/index`. **A third state never reaches the helper at all (I1 of round 6): a root whose Git directory cannot be resolved (`.git` removed, or `.git/objects` removed).** `_resume_phases` takes the lifecycle lock before `validate_record` (`controller/job.py:3523`) and `lock.resolve_git_dir` (`controller/lock.py:80`) refuses with `GitDirectoryUnresolvableError`; `abandon` takes the same lock (`controller/job.py:4804`; its no-lock path is only for a root that is not a directory, `:4797`). So `resume` and `resume --abandon` both refuse there, nothing is written and the record stays `COMPLETED` on disk (measured with `OrphanFixture`); on the real CLI path `managed_repo.inspect` refuses even earlier (`NotARepositoryError`, exit 20, `controller/managed_repo.py:173`). Per caller: on the **abandon** and **drift** endings the unreadable result never stops the ending: the record ends with its usual code (`OperatorAbandoned`, `workflow_release_changed`) and the `landing_unreadable` block and the clone path in the evidence (`_abandon_mark_failed` exists to end records that may not parse field by field, and `abandon` reaches it with no lifecycle lock for a managed root that is no longer a directory, `controller/job.py:4797`, `tests/test_job_codex_worker_resume.py:437`); on an **undrifted `resume`** the unreadable result (a root `validate_record` accepts) ends the record `FAILED` `CodexLandingRefused` cause `landing_unreadable`, the clone kept, because a pending record would refuse every later step on that target and `resume --abandon` is the operator's way to dispose of it anyway. **A tree removal that fails (O1 of round 5)** (`runtime.remove_tree` raising `RuntimeContainmentError` or `OSError`, on the live path, in `recover`'s applying part or in `--abandon`) never stops the ending: it is recorded in the final block as `tree_left` with the reason and the path, the record ends as it would have, and the guide's `rm -rf` applies. ## Risks

- **Landing into the managed repository is the first worker-driven write there.** It is the narrowest write Git offers (a fast-forward of one branch), taken under the lifecycle lock, after a guard that proves the clone's config and hooks unchanged, with hardened fetch options and no hooks on all three writes, a refusal to overwrite an ignored file and a catch-all refusal for an unexpected failure; every refusal leaves the repository as it was (but for `landing_unverified`, where the branch moved, and `merge_left_tree_dirty`, where the tree and index hold the worker's content), and the tests assert exactly that after each cause.
- **The clean-tree requirement narrows what can run in a clone** (D2). The Workflow's uncommitted state (intent-to-add plan files, `WORKFLOW_STATE.json` edits, ignored `.ai-review/` bundles) is invisible to a clone and its worker's uncommitted writes do not land. The seam stays dark here for that reason; H4e2 must decide it before a role is routed.
- **Git behaviour differs by version** (config-based hooks exist only in newer Git; `GIT_CONFIG_*` handling; `merge --no-overwrite-ignore`). The hook-suppression and fetch-hardening tests run against the installed Git (2.56 for the review's measurements) and the measured facts are in the guide; an older Git without `hook.*` keys ignores the keys harmlessly and the file-hook suppression is `core.hooksPath`.
- **A bounded range.** `MAX_LANDED_COMMITS` (200) stops a runaway worker from landing an unreviewable stack; a worker that exceeds it fails with a named cause and keeps its clone.
- **A crash during the landing.** The intent block and the recovery helper's windows (D7), run from every ending of a `COMPLETED` Codex record, bound it: the branch either moved, with an account, or did not.
- **`job.py` is large.** The new logic is two small modules and a few call sites in `_launch_job`/`_run_codex_worker`/`_reconcile_codex_worker`; the unchanged Claude and review tests are the proof.
- **Timing on CI (4 vCPU).** The tests wait on readiness files, not sleeps, and give each test its own job id (the open flake #259 is a shared tag).
- **Out of scope:** routing any role to Codex (H4e2); `milestone-implement` on Codex (H4f); carrying the managed repository's uncommitted state into the clone and back; a setting or option for the clone; a retention or pruning command for kept clones; a `runtime` command; any change to the Claude worker, the tester or the reviewer; the Manager's and the Workflow's use.
