## Goal

Two building blocks, both dark. The **recorder** lets the Controller record a local review verdict in the managed repository through the Workflow's own writers, exactly as `/review-plan` or `/review-implementation` records it in place. The **read-only run** runs one of those two reviews as a Codex worker in H4e's private clone, on a copy of the bound bundle, and hands the verdict it returns to the recorder. Nothing calls the run outside its tests until H4e2b routes a role to it.

<!-- CP1 -->
- **D1. The Controller records a verdict through the Workflow's own writers, run from the installed script set.** A new module `controller/review_recorder.py` holds a small driver program and the code that runs it through `run_in_private_copy`, beside the digest-checked script set and under the same Git isolation. The Controller never imports Workflow code into its own process. The driver makes exactly the calls the command names, in its order, and prints one JSON result: `{"ok": true, ...}` or `{"ok": false, "cause": <cause>, "class": <Workflow class or null>, "message": ...}`. It has two operations, each taking the stage (`plan` or `implementation`) and the work item:
  - **`check`** runs before any launch and writes nothing. It makes the command's version and phase guards, then `validate_local_plan_review_preconditions_bound` (plan) or A1's `validate_local_implementation_review_preconditions` and A3's checks (implementation), then `assert_local_generation_matches`, `assert_bundle_not_rejected` and `assert_feedback_not_owned_by_other_work_item`. It recomputes the stage's `bundle_id` and `review_content_id` through the canonical entry point `REVIEW_PROTOCOL.md` names and compares both with `MANIFEST.md`. It probes the parameter names (`inspect.signature`) of every Workflow function the driver calls. For an implementation stage it also refuses staged content in the index (`recorder_index_dirty`), because the commit below refuses any staged content other than its own (`DirtyIndexBeforeStagingError`) and the refusal must come before the Codex turn is paid for. It returns the header values, `review_stage_gate_context(...)` for the stage, the round and the script digests it ran under. The round is the stage's local count plus one. This is deliberate: it is what recent rounds wrote and the commands' wording ("one more than the highest prior round on record") differs from it today on this very item, so CP1's comparison with the in-place sequence fixes the round on both sides rather than chasing the wording.
  - **`record`** takes the path of the composed verdict file, written by the caller under the runtime root (as `_ingest_review` does; the driver runs with `stdin=subprocess.DEVNULL` and one argument string is limited to 128 KiB against D4's 1 MiB verdict, so the text never travels in the argument list), the state identity the caller decided at and the digests `check` returned. Every timestamp the writers take (`now`, so `last_transition`, `completed_at` and the binding's `at`) is the composed `Completed at:` value, which keeps the file and the ledger in step and makes the byte comparison in CP1 deterministic. It first reads the file and runs `protocol.next_action(..., expect_state_identity=...)` with those digests, as `_ingest_review` does. It then repeats `check`'s guards and recomputation, and makes the command's write set in order: `assert_bundle_not_rejected`, `assert_feedback_not_owned_by_other_work_item`, `ensure_feedback_dir`, `assert_verdict_well_formed` on the composed text, `_write_review_feedback_atomically`, and `state_transaction(... record_local_plan_review | record_local_implementation_review(..., audit=local_review_audit(...), verdict_text=...))`. The feedback path it passes to `local_review_audit` is repository-relative, so the `run_ref` (`session:local <path>`) never names a clone. For an implementation `REVISE` it then calls `commit_pending_applying_review_feedback_entry` with no attribution lines.

  That commit needs the real index, so `run_in_private_copy` gains one keyword, `real_index=False`. With `True` it keeps every other isolation setting, does not copy the index, and adds `hook.<event>.enabled=false` for every event a commit fires (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`, `post-index-change`, `reference-transaction`) beside the hook-file switch-off already in force; each setting is checked to be in force the way the runner checks its own, and one that is not refuses with the runner's existing `query_git_not_isolated`. Only `record` passes it. The commit takes the author the managed repository's own Git configuration gives, as the in-place command's commit does.

  So the ledger, phase, binding, counts and optional findings are written by the Workflow's own code against its own validators. The Controller decides nothing about a state field. The refusals, one cause each:
  - `recorder_branch_unsupported`: an implementation item the command would route to its advisory branch, not A1-A7.
  - `recorder_feedback_foreign`: the feedback directory belongs to another work item.
  - `recorder_index_dirty`: an implementation stage with staged content in the index. Raised by `check` and repeated by `record` before its first write, so a file staged after `check` and before `record` gives this cause; nothing is written.
  - `recorder_identity_mismatch`: a recomputed `bundle_id` or `review_content_id` differs from `MANIFEST.md`.
  - `recorder_interface_changed`: a probed function's parameters differ; the message names the function. A Workflow release that changes a writer therefore fails closed before any launch.
  - `state_identity_changed`: `next_action` answered `stale_decision`. Nothing is written.
  - `workflow_release_changed`: the script digests differ from the ones `check` returned (`WorkflowReleaseChangedError`). Nothing is written.
  - `recorder_commit_pending`: for an implementation `REVISE`, the state transaction succeeded and `commit_pending_applying_review_feedback_entry` then refused (a file staged after `record`'s own guard, inside the one driver process, or a stray uncommitted field outside `REVIEW_STAGE_WRITE_COMMIT_FIELDS`, such as `technical_review_block_pins`, which makes `commit_pending_applying_review_feedback_entry` raise `ReviewStageWriteNotCommittableError` after the state write and which `check` does not look at). **The feedback and the state (`APPLYING_REVIEW_FEEDBACK`) are written; only the commit is pending.** `class` and `message` are the Workflow's own. Nothing is left for the operator to record: re-recording by hand cannot succeed, because the item has left its review phase. The next role, `/apply-implementation-review`, commits the pending entry itself (`.claude/commands/apply-implementation-review.md:131`), and the evidence says so.
  - `workflow_refused`: any other Workflow guard or writer raised before the state write; `class` and `message` are the Workflow's own. A crash inside `record` leaves what a crash of the in-place command at the same step leaves: the feedback file can be written while the state is not, so the item is still at its review phase and the next run reviews again.

  **Runner errors.** `check` and `record` run through `run_in_private_copy`, which raises rather than printing JSON when the runner itself refuses: `WorkflowQueryError` (for example `query_git_not_isolated` from an executable `post-index-change` hook, or a `next_action` refusal other than `stale_decision`) and `WorkflowProtocolFailedError`. The recorder does not catch them: they propagate unchanged out of `check` and `record`, and D5 gives their ending by where they arise. "Nothing was written" holds for every cause above except `recorder_commit_pending`, and for a runner error raised before `record`'s first write. A runner error during `record` is not known to have written nothing: the 120 s `query_timeout` can kill the driver after `state_transaction` published (`controller/workflow_contract.py:93`), the filter check and the private directory's removal raise after the driver has returned, and a driver that dies without printing JSON has no outcome of its own. The Workflow's state is the truth for all of them (D5).

- **D2. The role runs read-only in the H4e clone, on a copy of what the in-place reviewer reads.** A new module `controller/codex_review_role.py` holds `run_review(...)`. It takes the managed repository, the runtime root, a job id, the operator home, the stage, the work item, the base commit, the route's model and effort, the state identity, the timeout, an optional brief, an `on_progress` callback and a `launch` seam (default `codex_worker.launch_codex_worker`). `prepare` gains one keyword, `read_only=False`. With `True` it skips only the `managed_tree_not_clean` refusal and returns the dirty paths beside the clone. A read-only job lands nothing, so the refusal's reason ("a clone cannot receive and a landing could not return") does not apply. Every other refusal stands. The run then copies three inputs into the clone at their repository-relative paths: the bound bundle directory (`protocol.resolve_artifact(..., "review_bundle")`), `CHANGES_SINCE_REVIEW.md` when `changes_file_for` verifies it, and the previous `REVIEW_FEEDBACK.md` when one exists (`"review_feedback"`). It records an **input manifest** (path, mode, SHA-256). The committed tree at `HEAD` is the repository the review checks claims against, and the plan files a plan review needs are in the bundle (`current/files/`). Nothing else is copied, and nothing is ever copied back. After the run, the clone must be unchanged: under `.ai-review/` the files must be exactly the manifest's, with the same digests; elsewhere no tracked change and no untracked file that is not ignored; `HEAD` is still the branch at the base commit and no other ref exists. Anything else is `read_only_violated`. A write to `.git` is the launcher's `sandbox_breach`, as today.

- **D3. The role returns a verdict body; the Controller composes the file.** The prompt is `build_prompt` in a new local-stage form: the reviewer role is `LOCAL_MODEL_PLAN_REVIEW` or `LOCAL_MODEL_IMPLEMENTATION_REVIEW`; the bundle path, the bundle-text rule, the changes-file rule, the brief and the finding-format rules are C7's; in place of C7's header template it asks for a final message holding a `Status:` line, an optional `Review scope:` line and the eight sections `REVIEW_PROTOCOL.md`'s required structure lists (Blocking, Important and Optional findings, Missing tests, Architecture and maintainability, Migration and data-integrity, Usability, Required acceptance criteria), and asks the role to write no file. The external form is unchanged. `launch_codex_worker` gains one keyword, `prompt=None`. With it, the launcher still parses `task` (a malformed one is still refused) but sends that text on stdin instead of rendering the command; every other control is unchanged. **The final message is read from the file, not from `result`.** `WorkerResult` has no raw-bytes field and gains none: after the launcher returns, the run reads `WorkerLayout(runtime_root, job_id).last_message` as bytes, which the launcher left in place. The bytes must be valid UTF-8, at most 1 MiB and free of D4's armour line. Before the first `## ` line they may hold only the `Status:` line, one optional `Review scope:` line and blank lines. The run then writes the header itself from `check`'s values: the `# Review Decision` title, the role's `Status:`, `Reviewed bundle ID:`, `Reviewed base commit:`, `Work item:`, `Reviewed review_content_id:`, the stage's revision line as the command's template writes it, `Reviewer role:`, `Review round:`, the role's `Review scope:` when given, and `Completed at:`. It adds `Reviewer model: openai/<the route's model>` exactly when the gate context says `requires_distinct`, so the vendor and model are the Controller's fact, never the role's claim. The body follows unchanged. A composed file the Workflow refuses ends the run; it is never repaired.

- **D4. The deny set: one tuple `CAUSES`, one cause per refusal, one test each.** On the way in (D2's copy) a refusal ends the run before the launch. On the way out (D3's parse, D2's after-check) the verdict is discarded and nothing is recorded.
  - `special_file`: an input path that is not a regular file or directory (`lstat`), a symlink included.
  - `submodule`: an input path with a component named `.git`, a `.gitmodules`, or a gitlink.
  - `credential_input`: an input named `auth.json`, `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa`, `id_ed25519`, `.claude.json`, `.credentials.json` or `.claude/settings*.json`, or under a `.ssh`, `.aws` or `.codex` directory; or an input file whose whole content holds a PEM private-key armour line. An armour line matches, as one token, five dashes, `BEGIN`, optional upper-case key-type words, `PRIVATE KEY` and five dashes. Prose naming the markers separately passes; the tests build armour by concatenation.
  - `path_escape`: an absolute path, a `..` component, a path resolving outside the repository, or one under the Controller's runtime root.
  - `input_over_bound`: more than 2000 input paths, more than 64 MiB in total, or a file over 8 MiB.
  - `verdict_over_bound`: a final message over 1 MiB.
  - `verdict_unparsed`: invalid UTF-8; a message with no `Status:` line, or one whose `Status:` is not `APPROVE`, `REVISE` or `BLOCK`; or anything before the first section other than the two allowed lines (a forged `Reviewer model:` or a second `Status:` included).
  - `credential_in_verdict`: an armour line in the final message or in the `WorkerResult`'s `stdout` or `stderr`. **This check runs first, on every returned result, whatever its outcome**, before the outcome is mapped to an ending: a `codex` that prints a key to `stderr` and exits 1 is `credential_in_verdict`, not `CodexReviewWorkerFailed`, so the run's result never carries the text. The verdict is checked because its Optional findings are copied into `WORKFLOW_STATE.json`, which is committed. On this cause the run deletes `last-message.md` and returns the `WorkerResult` with `result`, `stdout`, `stderr` and `stream_diagnosis["detail"]` emptied and the message's digest and length in the evidence. The detail is cleared because, on a non-zero exit, `classify` returns the last 400 characters of stdout plus stderr as the detail (`controller/codex_worker.py:47-49`, `:62-63`) and the launcher stores it in `stream_diagnosis` (`:213`), which the job record persists (`controller/job.py:5198`); no field of the returned result, `stream_diagnosis` included, holds any line of the armoured block. That is all it removes: **the session rollouts stay in `codex-home/sessions`** and hold the assistant's message, because H4d's usage admission reads them on every Codex job. So the claim is only that the text reaches neither the managed repository nor any field of the run's result.
  - `read_only_violated`: D2's after-check, which also covers a crafted ref; a ref cannot reach the managed repository, because nothing is landed.

  H4e's `managed_hooks_configured` stands for the managed repository, and a hook the worker writes into the clone's `.git` is `sandbox_breach` (D5). Protected paths are not at risk: no file the role touches is copied back, and the only managed-repository writes are the feedback file, the state and, for an implementation `REVISE`, the Workflow's own commit of that state. The residual risk is a dishonest verdict, which an in-place reviewer could write equally and which the external stage exists to catch.

- **D5. One named ending for every path, the clone removed on each.** `run_review` returns an `Ending(code, cause, worker, evidence)`; the job status each code maps to is H4e2b's job wiring. The run calls `on_progress` with its `codex_review` block before the preparer (`{"read_only": true, "stage": "preparing"}`), before `record` (`"stage": "recording"`, with the composed verdict's digest) and after it (`"stage": "recorded"`, with the recorder's result). Whatever happens, a `finally` removes the clone with `remove_clone(runtime_root, job_id)` (`runtime.remove_tree` of the layout's `tree`, as `codex_worker_tree._remove_partial` does); a removal failure never raises and is named in the evidence as `clone_removal_error`. The rest of the job directory is the job's to settle. The run's endings:
  - `CodexReviewNotStarted`: a refusal before the spawn; no Codex turn is paid for. The cause is the recorder's (D1, including `recorder_index_dirty`), the preparer's (H4e's, unchanged), the input copy's (D4), **the launcher's** or **the runner's**. The launcher refuses by raising `ReviewLaunchRefusedError` before any exec (an unverified build, `controller/codex_worker.py:176-178`; placement, `:121-134`; the controls inside `build` and `check_launch`, `:190-200`): `run_review` catches a `ControllerError` raised by the launch call before the process is spawned and ends `CodexReviewNotStarted` with the error's own reason, the rule the job path already applies (`WorkerNotStarted`, `controller/job.py:9042-9043`). The runner's `WorkflowQueryError` and `WorkflowProtocolFailedError` from `check` are the same ending, cause `check` and the error's own reason; from `record` they are **`CodexReviewRecordRefused`** with the error's class as the cause and the composed verdict in the evidence, because the Codex turn is already paid for. The runner can raise after the driver published (a timeout, the filter check, the private directory's removal), so the evidence says the Workflow's state is the truth, as for `CodexReviewRecordInterrupted`, and offers a by-hand record only with that caveat: the phase guard refuses it if the state was written. A `ControllerError` raised after the spawn is an exception (the last bullet).
  - `CodexReviewWorkerFailed`: the worker's outcome is not success; the cause is the launcher's subtype, one of `timeout`, `terminated_by_signal`, `usage_limit`, `non_zero_exit`, `no_final_message` and **`sandbox_breach`**. The `WorkerResult` is returned as it is, so a `usage_limit` keeps its `usage_limit` fact for H4d's wait path, **after D4's armour check has run on its `result`, `stdout` and `stderr`**: armour there is `CodexReviewRefused` (`credential_in_verdict`) with those fields emptied, and the worker's own failure is named in the evidence.
  - `CodexReviewRefused`: a way-out cause of D4; nothing recorded.
  - `ReviewStateIdentityChanged`: `record` refused `state_identity_changed`; the composed verdict is returned in the evidence and discarded.
  - `workflow_release_changed`: `record` refused `workflow_release_changed`; nothing recorded.
  - `CodexReviewRecordRefused`: any other `record` refusal raised before the state write, and a runner error during `record`; the cause is the Workflow class (or the runner's), and the composed verdict is returned in the evidence so the operator can record it by hand. For a Workflow refusal raised before the state write the item is still at its review phase; for a runner error, or a driver that exits without printing JSON, the Workflow's state is the truth and the evidence says so.
  - `CodexReviewRecordPending`: `record` refused `recorder_commit_pending`. The feedback and the state are written and the item has left its review phase, so there is nothing to record by hand and the evidence does not offer it; it names the Workflow's refusal and says the next role (`/apply-implementation-review`) commits the pending entry. The clone is removed as on every ending.
  - `CodexReviewRecorded`: the verdict is recorded; the recorder's result is in the evidence.
  - An exception (not a refusal) from any step, before or after the spawn, propagates unchanged after the clone is removed.

  **Recovery.** `recover(runtime_root, job_id, block, path)` is what a job's recovery site calls for a record holding the `codex_review` block, with `path` one of `RECOVERY_PATHS` (`resume`, `abandon`, `drift`). It removes the clone, never calls `codex_worker_landing` (the module does not import it), never records again, and names no clone. One ending per path, and on `resume` one per stage:
  - **`--abandon`**: `OperatorAbandoned` for every stage, the code `abandon` writes today (`OPERATOR_ABANDONED_CODE`, `controller/job.py:3893`); a `recorded` block's result is carried in the evidence.
  - **drift** (`_resume_drifted_protocol`'s Workflow release change): `workflow_release_changed` for every stage, the reason that path writes today (`WORKFLOW_RELEASE_CHANGED_REASON`, `controller/job.py:1951`); a `recorded` block's result is carried in the evidence.
  - **`resume`**: `preparing` ends `CodexReviewNotRecorded` (the worker may have run; nothing was recorded, and the next decision reviews again); `recording` ends `CodexReviewRecordInterrupted` (the Workflow's state is the truth, whatever `record` did); `recorded` ends with the code its result names (`CodexReviewRecorded`, `ReviewStateIdentityChanged`, `workflow_release_changed`, `CodexReviewRecordRefused` or `CodexReviewRecordPending`).
  - A block with an unknown stage, or an unknown path, raises `CodexReviewRecoveryError` naming it, after the clone is removed.

  Wiring `recover` into `_reconcile_codex_worker`, `abandon`, `_resume_drifted_protocol` and the post-spawn exception handler of `_run_codex_worker`, and the job status of each code, are H4e2b's.

### CP1 -- The recorder: the Workflow's own writers, run by the Controller

**Files:** `controller/review_recorder.py`, `controller/workflow_contract.py`, `tests/test_review_recorder.py`, `tests/test_workflow_contract.py`, `tests/test_package_structure.py`

D1: the driver, `check` and `record`, the interface probe and the `real_index` keyword.

Done when the following hold, against the installed Workflow scripts on fixture repositories:
- **Plan stage.** On a fixture item bound at `AWAITING_LOCAL_PLAN_REVIEW`, `check` returns the header values, the gate context, the round and the digests. `record` of a composed `APPROVE`, `REVISE` and `BLOCK` leaves the state and feedback that the in-place command's function sequence leaves on a copy of the same fixture, compared byte for byte, with `record`'s timestamps taken from the composed `Completed at:` (`run_ref` relative, `reviewer_model` present exactly when `requires_distinct`). The Workflow's state validator and the protocol's `next-action` accept the result.
- **Implementation stage.** The same at `AWAITING_LOCAL_IMPLEMENTATION_REVIEW`.
