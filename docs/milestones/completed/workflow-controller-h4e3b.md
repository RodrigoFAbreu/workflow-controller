## Goal

One mechanism: **the guarded generator run**. After a Codex apply role's landing and carry out, H4e3 stops at the Controller's own gate `carry_bundle_regeneration_pending`, because `scripts/prepare-ai-review.sh` runs `python3` over `scripts/` and over the repository root, and a worker's landing can put code on that path. This item lets the Controller run the generator itself, and only when it can show that nothing the worker could have written is on what the interpreter loads. When it cannot show that, the lane stops at the same gate as today, now naming the cause. No new setting, no new gate and no new Codex path: the carry, the landing, the reconcile and the gate are H4e3's, used unchanged.

## The findings this closes

- **H4E3-R5-001.** A worker lands `scripts/sitecustomize.py`; the generator puts `scripts/` on `PYTHONPATH`, so the interpreter imports it at startup, with the Controller's authority.
- **H4E3-R6-001.** The same class by other routes: a module at the repository root or in `scripts/` that shadows a standard-library module (the generator's `python3 -` heredocs put the working directory first on `sys.path`), and a forged `.pyc` that Python loads in place of the source it claims to be compiled from, in `scripts/__pycache__` or as a sourceless `scripts/<name>.pyc`.
- **H4E3B-EXT-001.** Not code execution but disclosure: the generator copies files into the bundle that it archives, and its two copy loops trust a worker-editable name. `scripts/prepare-ai-review.sh` lines 550-552 copy each changed path that passes `[[ -f ]]`, which follows a landed symlink to a file outside the repository, and lines 576-593 copy each line of `CONTEXT_FILES.txt` that passes the same test, so an absolute path or a `..` traversal to an operator-readable private key lands under `files/` and in the archive. Replacing the operator's manual regeneration with a Controller-authorized run is what introduces the exposure, so this item closes it.

## What exists

- `job._carry_resolution` ends a carried-out apply at `GATE_BLOCKED` with `reconciliation_evidence.code` `carry_bundle_regeneration_pending` (`job.CARRY_BUNDLE_GATE_CODE`) when the Workflow's reconcile answers `FINISHED`, or, for the plan role, answers exactly the expected stale-bundle result (`job._is_expected_stale_bundle`). `job._carry_gate_text` writes the steps the operator runs, including `scripts/prepare-ai-review.sh <base> plan|post-fix <work item>`. It has two call sites: `_run_codex_apply` (`controller/job.py:9629`) and `resume`'s `_reconcile_codex_carry` (`controller/job.py:9684`). `abandon` and the post-spawn (drift) handler end through `_end_carry_without_carry_out` and never run the generator; they are unchanged.
- `.workflow-manager/installation.json` records, under `managed`, the sha256 of every file the Workflow installed, including every file of `scripts/` and `scripts/prepare-ai-review.sh`. `controller.protocol.read_managed` and `protocol.script_set` read it and digest the files without following links.
- `workflow_contract.run_in_private_copy` runs a Workflow query from verified bytes in a private directory under `-B -E -s`, and `workflow_contract._git_isolation` gives the run a Git with hooks, filters, fsmonitor and transports switched off (and, with `real_index`, the target's own index). The generator cannot run from a private copy: it finds its modules through `git rev-parse --show-toplevel` and `$REPO_ROOT/scripts`, and it writes `.ai-review/` and the index of the repository it is run in.
- The generator is bash; it starts `python3` thirteen times (`scripts/prepare-ai-review.sh` lines 82, 206, 237, 253, 359, 473, 564, 625, 629, 705, 776, 792, 905), from the repository root, without `-I`, `-E` or `-s`, in four kinds: seven heredocs written `PYTHONPATH="$REPO_ROOT/scripts:${PYTHONPATH:-}" python3 -` (lines 82, 253, 473, 564, 705, 776, 792), one `python3 -c` (206), one bare heredoc without `PYTHONPATH` (359) and four script-path starts `python3 "$REPO_ROOT/scripts/workflow_fingerprint.py"` (237, 625, 629, 905). The project requires Python 3.12, so `PYTHONSAFEPATH` is available.

## Decisions

Each decision states one principle.

<!-- CP1 -->
- **D1. The guard judges the tree as it is, and the landing's name-status diff is the second, independent check of what changed.** Two facts are needed and neither implies the other. The tree check sees what the interpreter would load now, including ignored and untracked files a diff of commits never shows (a forged `.pyc`, a file written after the landing). The diff check sees what the worker changed, which matters because `.workflow-manager/installation.json` is itself a committed file: a landing that edits `scripts/workflow_state.py` and the record's digest together passes any check that trusts the record alone. So the run needs **both**: `generator_run.check_landing(carry_base, landed_head)` and `generator_run.check_tree(root)`.
- **D2. The landing check refuses any landed path on the execution surface.** It runs `git diff --name-status -z --no-renames` through `gitrepo`'s hardened option set over `carry_base..landed_head` (`--no-renames` lists both sides of a rename as a deletion and an addition) and refuses (`surface_landing_touched`, naming each path and its status letter) a path that is under `scripts/` or `.workflow-manager/`, whatever the status (added, modified, deleted or type-changed). A range the diff cannot read, or a landed head that is not a descendant of the carry base, refuses with the same cause. The plan role makes no commit, so its range is empty; the tree check is its whole guard. The report of a refusal names the paths for the operator, which is what the gate text asked the operator to read by hand.
- **D3. The tree check compares the present bytes to the record and the directory to the record's names.** For `scripts/`: every `managed` key under it must be a regular file, opened without following links, whose sha256 equals the record's (`surface_script_modified`), and `scripts/prepare-ai-review.sh` must be one of them (`generator_not_managed`); the directory may hold no other entry than those, `__pycache__`, and names starting with `.` (`surface_foreign_entry`, naming it: this refuses a `sitecustomize.py`, a stdlib-named module, a sourceless `.pyc`, an extension module or a package directory). An unreadable record or directory is `surface_unreadable`. `__pycache__` is allowed because D4 makes it unreadable to the run, not because it is trusted.
- **D4. The run gives the interpreter only what D3 verified.** `workflow_contract` gains one public entry, `run_in_place`, which builds the environment as `_git_isolation(real_index=True)` does today and adds: `PYTHONSAFEPATH=1` (the working directory and a script's directory are not put on `sys.path`, so a root-level `secrets.py` or `json.py` is not importable), `PYTHONNOUSERSITE=1`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONPYCACHEPREFIX` set to an empty private directory (no cached bytecode, forged or not, is read, and none is written into the managed tree) and `PYTHONPATH` set to a second, non-empty private directory that the Controller creates and keeps empty (five pins; H4E3B-L1-001: with no `PYTHONPATH` the generator's `"$REPO_ROOT/scripts:${PYTHONPATH:-}"` expands to `<root>/scripts:` and CPython reads the trailing empty entry as the working directory, the repository root, which `PYTHONSAFEPATH` does not remove; with the private entry the value is `<root>/scripts:<private>` and no empty element exists); it removes every other `PYTHON*` variable, `BASH_ENV` and `ENV`; and it puts a private `bin/` first on `PATH` holding one symlink, `python3`, to `sys.executable`, so the generator's `python3` is the Controller's own interpreter and not whatever `PATH` finds first. What each kind of start then gets on `sys.path`: the seven prefixed heredocs `scripts/` (D3 verified it) and the private empty directory; the `-c` start and the bare heredoc only the private empty directory; the four script-path starts neither the root, `''` nor `scripts/` (`PYTHONSAFEPATH` drops the script's directory), which works because `workflow_fingerprint.py` imports no sibling module on those paths (its one deferred `import workflow_state` is reached only from a prefixed heredoc). A Workflow release that adds a sibling import on a script-path start ends as `generator_failed` at the gate, the safe fallback. The child's `sys.executable` is the private symlink's path, so the proofs compare `os.path.realpath`; a Controller run from a virtual environment loses it through the symlink (CPython looks for `pyvenv.cfg` next to the invoked path), which is harmless because the Workflow scripts use only the standard library. The run is `scripts/prepare-ai-review.sh <base> <stage> <work item>`, with the item's `base_commit`, stage `plan` for the plan role and `post-fix` for the implementation role (the two invocations the gate names), from the repository root, with a fixed bound of 600 seconds, output bounded to the last 4 KiB of each stream and scanned for key armour (`codex_review_role.ARMOUR`) before anything is recorded.
- **D5. The tree is checked again after the run.** The generator is the one process that ran with the managed tree writable under it; if D3's check no longer passes afterwards, the bundle is not trusted (`surface_changed_during_run`, with the bundle left for the operator to remove). This closes the window between the check and the run that D3 alone leaves open, which the Controller's lock and the finished worker make narrow but do not close.
- **D5a. The run is refused unless every path the generator will copy resolves inside the repository, and the same check runs again afterwards.** `generator_run.check_copy_sources(root, stage, base_commit, work_item_id)` is the third check, run after D2 and D3 and before the generator, and it reads exactly what the generator will read, as data, never executing it. (a) The changed paths, as the generator will see them: the union of the tracked diff, `git diff --name-status -z <base_commit> -- .`, and the generator's own untracked candidates, `git ls-files --others --exclude-standard -z -- .` (`scripts/prepare-ai-review.sh` lines 139-142 mark exactly these intent-to-add before their diff, and reset them on exit, so a plain diff run beforehand or afterwards never lists them; H4E3B-EXT-001, round 3: an untracked symlink to an external file, for example a local link that a landing exposed by removing an ignore rule, would otherwise be followed by lines 550-552), both through `gitrepo`'s hardened option set, minus deletions and `.ai-review/source/`, where each path must be a regular file, not a link, with no link among its parent components, and its `os.path.realpath` must lie under the repository's `realpath`; a link of any target is refused, because a link that stays inside the repository is not something a review bundle needs. (b) The context list: the file the generator copies into the bundle as `CONTEXT_FILES.txt` (for `plan`, `<plan_inputs_dir>/CONTEXT_FILES.txt`; for `post-fix`, `<bundle_dir>/CONTEXT_FILES.txt`), read without following a link; each non-empty line that is not under `.ai-review/source/` (the generator skips those) must be relative, contain no `..` component and no NUL, and, when the file exists, resolve by `realpath` under the repository root with no link among its parent components; a line naming a file that does not exist is left to the generator's own warning, since nothing is copied. A refusal is `copy_source_unsafe`, naming the list or the diff, the offending path and the reason (`absolute`, `traversal`, `link`, `escapes`), and ends at the existing regeneration gate with the generator not started, so no canary byte reaches `files/` or the archive; the operator removes the line or the link and runs the steps the gate names. The check is run a second time after the run with D5's tree check: the lists and paths are worker-writable and the generator reads them later than the check, so a source that no longer passes ends as `surface_changed_during_run` with the bundle left for the operator to remove, as D5 does. This item does not change `scripts/`, which is the installed Workflow's, and so the guard sits in the Controller, where the same refusal covers both roles.

## Risks

- **The record is not an anchor on its own.** It is a committed file the worker can land. D1 pairs it with the landing's diff; a plan-role run has no landing, and its carried members are data the generator reads, never code.
- **Reading is not executing, and copying is not safe by itself.** The generator reads carried members and the declaration as data. It does **not** refuse a context-list path that escapes the repository or a changed-file link (`[[ -f ]]` only), so D5a makes the Controller refuse them before the run and check them again after it; the guard cannot see a file the generator would choose to read by another route, and none is known (the other `files/` writers are pinned copies of declared plan paths).
- **Interpreter and `PATH`.** The generator's `bash`, `git` and coreutils come from the operator's `PATH` as every Controller subprocess does; only `python3` is pinned. A hostile `PATH` is outside the threat this item draws (the worker cannot write there).
- **A Workflow release that changes the generator's invocation.** The stage names and argument order are the two the gate text already names; a release that changes them fails `generator_failed` with the generator's own usage output and stops at the gate.
- **Sizing.** One mechanism, the guarded run; the carry, the gate and the reconcile are reused unchanged.
- **Out of scope:** the carry and recovery of the two apply roles (H4e3, done), `milestone-implement` (H4f), a setting to turn the run off, and running any other script of the managed repository.

## Open decisions

This repository has no `docs/TECHNICAL_DECISIONS.md`, so no open decision row there is touched. Three choices are the plan's own and are stated so the reviewers can overrule them: the guard requires both the landing's diff and the present tree rather than either alone; the run is on by default for a Codex apply route that passes the guard rather than behind a setting (a refusal falls back to H4e3's gate, and the route itself is opt-in); and `python3` is pinned to the Controller's interpreter through a private `PATH` entry rather than by editing the generator.
