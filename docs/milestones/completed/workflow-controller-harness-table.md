## Goal

Close [#166](https://github.com/RodrigoFAbreu/workflow-controller/issues/166). Which harness can take which role is declared in `controller/harness.py` and applied by `routing.check_role_harness`, but nothing shows it to a reader, and a hand-written table would drift the first time a later item (the Codex tester, the Codex worker) adds a role to an adapter. This milestone adds one page whose table is **generated** from those two modules, and makes the normal documentation check fail when the page is not what the generator prints.

One concern only: **the generated table and its currency check**. Out of scope: supported models and efforts per harness (H8), the launch seam (H3), fallbacks (H9), any Codex worker or tester, and changing which pairs are accepted. The registry is not changed: it already declares every column the table needs (`family`, `reviewer_name`, `roles`, `can_restrict_agents`, `can_restrict_tools`, `usage`, `pinned_version`, `fails_closed_on_unknown_version`).

## Decisions

Each decision states one principle.

- **D1. The generator is a pure function of the two modules, and nothing in the table is typed by hand.** A new `tools/harness_table.py` (standard library plus the Controller's own `controller.harness` and `controller.routing`) holds `render() -> str`, which returns the Markdown of two tables and reads every cell from the registry: harness names, families and reviewer names from `harness.ADAPTERS`; roles from each adapter's `roles`; the accepted routing pairs by calling `routing.check_role_harness(role, name)` for every routing role and every registered harness, so the page shows exactly what a settings file, a routing file and `--role-harness` accept, with the refusal as the other branch; the routing roles and their adapter role from `routing.ADAPTER_ROLE`. The only text the generator owns is the wording of the fixed vocabularies: one sentence per adapter role and one per usage mode. Each is a dictionary keyed by the registry's constants (`harness.WORKER`, `harness.USAGE_DERIVED` and the rest), and `render()` raises `ValueError` naming the missing key when the registry holds a role or a usage mode the dictionary lacks, so a new constant cannot be rendered with a blank cell. The usage sentence renders in the first table's usage column; the adapter-role sentences render in a legend (D2). The generator reads `harness.ADAPTERS` and calls `routing.check_role_harness` through the module attribute at call time (`harness.ADAPTERS`, never `from controller.harness import ADAPTERS`), so a test that patches the registry changes what it renders.
- **D2. Two tables, in registry order, with a fixed shape.** The first table has one row per registered harness: name, the `reviewer.harness` value it is chosen by (or `-` when it cannot review), model family, the roles it declares (the adapter roles, in the registry's order), whether it can restrict subagents and whether it can restrict tools, how it reports usage (the sentence for its `usage`), its pinned version, and whether an unknown version is refused (`fails_closed_on_unknown_version`). The second table has one row per routing role, in `routing.ROLE_ROUTES` order: the role, the adapter role it runs as, and one column per registered harness holding `yes` or `no` from `check_role_harness`. Booleans render as `yes`/`no`; a pinned version renders as it is declared. After the second table comes a legend: one line per adapter role, `` `role`: sentence ``, for each role that at least one registered adapter declares, in the order the roles first appear across the registry (the order of `harness.ADAPTERS`, then each adapter's `roles`); a role the routing table names as an adapter role but no adapter declares is also listed, after those, so the legend covers every role either table shows. The output is deterministic and ends with one newline.
- **D3. The page owns the prose and marks the generated region.** The new `docs/guide/harnesses.md` is an ordinary user page (header, back link) whose generated region sits between the lines `<!-- harness-table:begin -->` and `<!-- harness-table:end -->`. Everything outside the markers is hand-written (what the page is for, how a routing role maps to an adapter role, that the table shows what is accepted today and changes when an adapter declares a role, and how to regenerate). `python3 tools/harness_table.py --write` rewrites only the region between the markers and refuses a page that lacks either marker; `--check` prints nothing and exits 0 when the region equals `render()`, else exits 1 with the first differing line and the command that fixes it. Without a flag the script prints the table, so a reader can see it without touching the page. This is the existing pattern of this repository's generators (`tests/golden/generate_*.py` with `--check`), applied to a documentation page.
- **D4. The currency check is part of the normal documentation check, and therefore of the test run.** `tools/check_docs.py` gains a seventh rule, `check_harness_table(root, through)`, next to the digest rule it resembles. It calls `harness_table.check(root)` rather than parsing the markers a second time, so `--check` and the documentation check cannot disagree about what a missing, duplicated or reversed marker is: the page `docs/guide/harnesses.md` (registered as a user page and as the rule's own page, both active from the next checkpoint number) must exist, must hold exactly one begin and one end marker in that order, and its region must equal `harness_table.render()`; each failure is one line naming the page, and the mismatch line names `python3 tools/harness_table.py --write`. `check_tree` runs it, and `tests/test_docs.py`'s existing live-repository test (`check_tree(REPO_ROOT)` is empty) is what makes a registry change that is not followed by a regeneration fail the suite. A synthetic-tree test proves each failure; a registry-change test proves the contract itself by rendering from a registry with an added adapter role and showing the page then fails.
- **D5. No change to what the Controller does.** `tools/` is not part of the installed package, and `controller/` is read, not edited. A later item that adds a role to the Codex adapter changes the page's table through a regeneration, with no edit to this milestone's code; that is the point of D1.

## Out of scope

Everything listed under Goal, plus a model or effort column (H8), a generated table in any other page, and a pre-commit hook.

### CP1 -- The generator, the currency check and their tests (#166)

**Files:** `tools/harness_table.py`, `tools/check_docs.py`, `tests/test_harness_table.py`, `tests/test_docs.py`

The generator is imported unconditionally inside `check_harness_table` (not inside the `if build_parser is None ...` branch of `check_tree`, so a caller that injects all three still reaches it), and `tools/harness_table.py` inserts the repository root into `sys.path` itself, so `python3 tools/harness_table.py` works from a checkout without `PYTHONPATH`. `ACTIVE_THROUGH` stays at 5 here and is raised to 6 in CP2, with the page, so the repository check is unchanged until the page exists (the convention the constant's comment states): a page registered one checkpoint ahead of the constant is not checked, and `tests/test_docs.py`'s guard `test_every_activated_page_has_a_checkpoint_and_the_lists_are_constants` is changed from `range(1, 6)` to `range(1, check_docs.ACTIVE_THROUGH + 2)`, so it allows a page registered one checkpoint ahead and keeps tracking the constant afterwards.

Tests, in `tests/test_harness_table.py` over the real modules and in `tests/test_docs.py` over synthetic trees (`through=6`):
- the guard `test_every_activated_page_has_a_checkpoint_and_the_lists_are_constants` uses the bound `range(1, check_docs.ACTIVE_THROUGH + 2)` and passes with `HARNESS_PAGE` and its `USER_PAGES` entry registered at 6 while `ACTIVE_THROUGH` is 5;
- the import is unconditional: `check_tree` with `build_parser`, `cli_module` and `contracts` all injected still runs the harness-table rule;
- the first table has a row per `harness.ADAPTERS` key whose cells equal the adapter's fields, and the second a row per `routing.ROLE_ROUTES` key in order, whose `yes`/`no` cells equal `check_role_harness` (claude-code `yes` for every routing role, codex `no` for every one today);
- the second table's shape follows the registry: with `harness.ADAPTERS` patched to add `functional-tester` to the Codex roles, exactly the `functional-tester` row's Codex cell flips to `yes` and no other cell moves;

- `render()` is deterministic (two calls are equal) and ends with one newline;
- `write` replaces only the marked region and keeps the text outside byte for byte, is idempotent, and refuses a page missing a marker, with the markers reversed, or with a marker twice;
- `--check` exits 0 on a current page and 1 on a stale one with the fix command in its output; `--write` then makes `--check` exit 0; the no-flag form prints exactly `render()`;
- `check_harness_table` reports a missing page, a missing or duplicated marker, and a stale region, and nothing for a current page; a tree whose `through` is below 6 reports nothing for the page.
