Work item: `workflow-controller-orchestrator-stops`
Work item type: `product`
Governing workflow version: `2.2` (this repository's `docs/ai-workflow/WORKFLOW_CONFIG.json` default at creation)
Base commit: `07a87a2def79392b848a9a1603070df8dfa100ca` ("fix: refuse a user-only command named with wrapping punctuation (TK1, #247) (#249)"), the tip of `main`.
Lifecycle authority: this repository's installed Workflow, automatic gates.
Roadmap slot: `docs/ROADMAP.md` row NF3 (issue [#244](https://github.com/RodrigoFAbreu/workflow-controller/issues/244)), before H4b.
Released baseline: `workflow-controller 1.27.0`. The owner-facing alert was wrong: 18 of the 20 `user_gate` events sent since 2026-10-26 asked for a decision nobody had to make. Fixing a wrong announcement is a `fix:` (a patch release). One new event name joins the `events` section the way `checks_wait` did (NF2); it is on by default, takes no new setting key beyond that event's entry, and changes no exit code, step count, gate or gate identity.
Pull request title: `fix: announce a stop the orchestrator handles as a wait, not a user decision (NF3, #244)`

## Goal

`user_gate` ("Your decision is needed", `ACTION_REQUIRED`, `HIGH`) is sent only for a stop that needs a person. A stop that an orchestrator session resolves is announced as an event of its own, at a severity that is not a request, and the decision is made from the Workflow's own protocol facts, never from message text.

## What exists

- `controller/job.py` `derive_job_event`, `GATE_BLOCKED` branch: a lifecycle gate (`human_gate_pending` of a phase other than the branch gate) gives, in order, nothing for pending checks that were not waited for, `checks_wait` or `lane_blocked` for a spent wait on pending checks, `lane_blocked` when the record's `protocol` block has the disposition `blocked` or the tester's gate is `functional_unchanged`, `review_wait` for a review wait (`_review_wait_title`), and otherwise `user_gate`.
- A step that stops before any launch writes its record through `_no_launch_record`. That record has no `protocol` block (so the `blocked` exit cannot see a disposition). `protocol_gate` = `{row, disposition, action_id}` is written only at the fall-through of `_decide_protocol_current` (`job.py:8344`), and `_review_wait_title` reads it. That fall-through also returns `no_progress_repeated`, `decision_unstable` and the `_automatic` refusals (`unknown_action`, `user_only_action`, `invocation_mismatch`), so those records already carry `protocol_gate` with the Workflow's disposition (`validation` for the 8 `no_progress_repeated` stops) but no code. The gates returned through their own `_no_launch_record` call (the review-mode refusals at `job.py:8297`/`8313`, the external cap at `job.py:8324`, the tester's pre-run stops) carry no `protocol_gate`. A Controller-coded gate (made through `protocol_decision._Context.blocked`/`gate_for`: `no_progress_repeated`, `review_round_cap_reached`, the tester's `isolation_breach` and the reporter's `pr_report_*` stops) has its code only as the first word of `what_is_required` and of the first evidence line. `workflow_unhealthy` is built directly in `protocol_decision.preflight`, with no `protocol` at all, so it has no Workflow answer to record beside it. `gate_evidence_unmet` and `condition_refused` are Workflow reason codes (disposition `blocked`), not Controller codes.
- The Workflow's reason code of the answer (`pr_evidence_needed`, `functional_evidence_needed`, `pr_approval_needed`, `review_blocked` ...) is in the answer the Controller already holds when it builds the gate and is not recorded in the job record.
- `controller/notify.py` `EVENT_TABLE` maps an event name to a kind; the name is also the `notifications.events` settings key, and `state` is `INFO`/`LOW`. `DerivedEvent.supersedes` makes a stop whose old notice was already handled not be announced again (`review_wait` uses it with `user_gate`).
- The 20 `user_gate` events since 2026-10-26 (issue #244): 2 real (`review_round_cap_reached`), 8 `no_progress_repeated`, 4 acceptance waiting for a pull-request fact (row 38f, `external_gate`), 3 `gate_evidence_unmet` (disposition `blocked`), 2 `condition_refused` (disposition `blocked`), 1 `workflow_unhealthy`.

## Decisions

Each decision states one principle.

- **D1. The rule reads two recorded facts: the gate's code and the Workflow's reason code with its disposition.** A gate record carries `protocol_gate` with `row`, `disposition`, `action_id`, `reason_code` (the Workflow's reason code for the answer, `null` when there is no answer) and `code` (the Controller's own gate code, `null` for a gate the Workflow answered itself). It is written by one helper, from the gate's `Decision`, by the three writers of a gate record: `_no_launch_record` (every gate decision, with or without a protocol; the existing fall-through keeps its three keys and gains the new ones), the tester's `finish` (so an `isolation_breach` record carries it) and the reporter's record (so a `pr_report_*` stop carries it). `Decision` gets an optional `gate_code`, set by `_Context.blocked` (and so `gate_for`) and by `preflight` for `workflow_unhealthy`; a `preflight` gate has no protocol, so its block is `{row: null, disposition: null, action_id: null, reason_code: null, code: "workflow_unhealthy"}`. The fields are additive; a record written before has fewer keys and is judged as in D4.
- **D1a. Precedence.** A non-null `code` decides alone, **over the existing `review_wait` exit's protocol-gate source too**: of `_review_wait_title`'s two sources, only the manual-external `protocol_gate` match (`job.py:5269-5273`) treats a `protocol_gate` with a non-null `code` as no review wait (it keeps matching a fall-through record whose `code` is null or absent). The tester's `functional`-block source (`job.py:5264-5268`, which returns before the protocol-gate match) is untouched: a tester record routes exactly as today (a fault gate other than `isolation_breach` -> `review_wait`, `isolation_breach` -> `user_gate`, `functional_unchanged` -> `lane_blocked`) although D1 now gives it a `protocol_gate` with a non-null `code`; the closed tables of D2/D4 are read only for a record the `functional` block does not route. Without this, writing `protocol_gate` from every gate would make the external cap `review_round_cap_reached` (`job.py:8320-8327`) and the two `review_mode_unavailable` refusals (`job.py:8294-8317`), all built by `gate_for` over a review decision (disposition `external_gate`, action `plan.review.external`/`implementation.review.external`, at a manual-external phase), match `_review_wait_title` and become a `review_wait`; they carry a Controller code, so they stay `user_gate` (D3). The rule: the stop is a wait only if the code is in `ORCHESTRATOR_HANDLED_CODES`, a blocker only if it is in `ORCHESTRATOR_BLOCKED_CODES`, otherwise `user_gate`, whatever the Workflow's `reason_code` or disposition says. The Workflow's `reason_code` and disposition are consulted only when `code` is null (a gate the Workflow answered itself). So a tester `isolation_breach` or a reporter `pr_report_refused`/`pr_report_stale`/`pr_report_forge_unavailable`/`pr_report_no_pull_request` stop, whose Controller code is set over a row-38e/38f answer, stays `user_gate`: each of them means the report could not be made or was refused, which a person has to look at. The one reporter code that is a wait is `pr_report_unchanged` (D2), and only over row 38f: `ORCHESTRATOR_HANDLED_CODES` maps each handled code to the row it is handled at (`no_progress_repeated`: any row; `pr_report_unchanged`: `38f`), and the rule reads the recorded `protocol_gate.row`. Over row 38g (the reporter acts there too, `pr_report.REPORT_ROWS`) an unchanged report is the ordinary state while the pull request waits for a person's approval, so `pr_report_unchanged` with `row` `38g`, or with no recorded row, stays `user_gate`.
- **D2. A stop that no person has to act on is announced as one of two events, by what the lane must do.**
  - **A stop the lane clears by itself or by waiting** sends the new event `orchestrator_wait` (kind `state`, so `INFO`/`LOW`, on by default; title `Waiting: <stop> (<work item>)`, the message the gate's own text and next command). These are, with a null `code`: reason code `pr_evidence_needed` (row 38f: a pull-request fact is awaited) and reason code `functional_evidence_needed` (row 38e: functional evidence is awaited); and the Controller codes `no_progress_repeated` (the loop guard; the orchestrator re-runs or repairs the step) and `pr_report_unchanged` (the reporter's form of the same row-38f wait, **only over row 38f**: the report changed nothing, the pull request's state is as the Workflow already holds it, so the pull-request fact is still awaited and nobody has to decide; without it the same wait would be `orchestrator_wait` when the reporter does not apply and `user_gate` when it does. Over row 38g the unchanged report waits for a person's approval and stays `user_gate`, D3). The `code` of both is set by the context (D1), so a 1.27.0 record of either (a `protocol_gate` without `code`) stays `user_gate` (D4).
  - **A stop that needs a repair but not a decision** sends `lane_blocked` (the existing `BLOCKER`), as a disposition of `blocked` already does for a launched job (gate-policy D7): with a null `code`, any gate whose recorded disposition is `blocked` (`gate_evidence_unmet`, `condition_refused`); and the Controller code `workflow_unhealthy`.
  The event name is `orchestrator_wait`, a plain name for who handles the wait; a settings entry may turn it off or change its severity like any other event.
- **D3. A person's decision keeps `user_gate`.** Any other stop: every `human_gate` disposition (approval, acceptance, a BLOCK resolution, merge permission), `review_round_cap_reached`, `isolation_breach` and the reporter's `pr_report_refused`, `pr_report_stale`, `pr_report_forge_unavailable` and `pr_report_no_pull_request` stops (D1a: unchanged, a Controller code outside the tables), `pr_approval_needed` (row 38g: someone approves the pull request) and `pr_report_unchanged` over row 38g (the same approval, reported unchanged: after the first report every step at 38g gives it, so it must not hide the request), a review wait the existing rule already routes, and every `external_gate` whose reason code is not in D2's list.
- **D4. Unknown defaults to the owner's side.** A record without the new `code`/`reason_code` keys (written by an earlier release, including a 1.27.0 `no_progress_repeated` record with its `protocol_gate` but no `code`; a legacy target), and a code, reason code or disposition D2 does not name, stay `user_gate`. The cost of a false alert is a glance; the cost of a missed decision is a stalled lane. The classification is a closed table in code (`ORCHESTRATOR_HANDLED_CODES`, code to handled row, for `no_progress_repeated` (any row) and `pr_report_unchanged` (`38f` only), `ORCHESTRATOR_HANDLED_REASONS` for the two reason codes, `ORCHESTRATOR_BLOCKED_CODES` for `workflow_unhealthy`), so a new stop is `user_gate` until a milestone adds it.
- **D5. A stop already announced is not announced again.** Both new routes set `supersedes="user_gate"` on the event, with the unchanged stop identity, so a `user_gate` an earlier release delivered (or attempted and spent, in the recovery path) suppresses the new event, as `review_wait` does. A re-derived event for the same stop has the same key, so it is a duplicate, not a second notice.
- **D6. Only the announcement changes.** Which stops are gates, the gate identities and every exit code are untouched, and so is `_review_wait_title` for every record it routes today: a tester record (the `functional` block, whatever `protocol_gate` it now also carries) and a fall-through record with a null or absent `code`; its single change is D1a's: in the manual-external `protocol_gate` match only, a non-null `code` is no review wait. The `events` section accepts the new name through `EVENT_TABLE`; the settings generation does not change.
- **D7. Release type.** `fix:`: owner alerts were wrong. The new event name and its settings key are the same kind of addition `checks_wait` was in the patch 1.22.1.

## Functional review

Every flow is offline and unit-level (no real Claude, Codex, network or `gh`). Run from the product clone with `TMPDIR` set to a writable scratch directory, one module at a time, `python3 -B` and no `PYTHONPATH=.`. A flow that builds a job record writes under a temporary folder, so on a tester sandbox with a read-only `/tmp` it is `environment`-limited and operator-run; the checklist names it. The full suite is not a flow.

## Risks

- **A real decision hidden as a wait.** Mitigated by D3/D4: the handled set is a closed list of Controller codes (`no_progress_repeated`, and `pr_report_unchanged` over row 38f only, so the row-38g approval request is never hidden) and two reason codes read only when the Controller code is null, and the Controller code decides alone (D1a); every other code, an unknown one and a legacy record stay `user_gate`. A test per real decision pins it.
- **A `lane_blocked` is still `CRITICAL`.** The blocked rows are real repairs, not noise, and the Workflow already calls them blockers (gate-policy D7); the issue accepts `lane_blocked` for them. A settings entry can lower it.
- **Old job records.** They carry no `protocol_gate` keys for Controller-coded gates, so recovery of an old record re-derives `user_gate` as before (D4).
- **Out of scope:** which stops are gates, new gates, new exit codes, the Manager watchdog's own alerts (fixed on its side), H4b.
