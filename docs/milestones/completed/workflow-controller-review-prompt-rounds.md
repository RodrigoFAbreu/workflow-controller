## Goal

Close [#161](https://github.com/RodrigoFAbreu/workflow-controller/issues/161). `build_prompt` (`controller/review.py:383`) tells the external reviewer who it is, what the header is and which five sections to write. It does not tell the reviewer two things the Workflow's ingest depends on:

1. **Round.** Every external round is a full re-review, although from the second round the Workflow writes a section of `CHANGES_SINCE_REVIEW.md` for the external role. The external cap is 4.
2. **Finding format.** `workflow_fingerprint.assert_verdict_well_formed` (`scripts/workflow_fingerprint.py`) reads a finding as a list item or a `### ` heading inside its section, and a `REVISE` whose Blocking and Important sections hold no such entry is refused as malformed (the job ends FAILED "not-ingested", no state change). A hand-run Codex review gets both from the lane's templates; a Controller-run one gets neither.

One concern only: **the protected fixed text of the external-review prompt**. Out of scope (the issue's list): enabling `reviewer.harness=codex` in the shared settings, the Manager's per-milestone "Review focus", a Codex worker or tester, review modes and caps, any change to `reviewer.brief` or to `verify_verdict`.

## Decisions

Each decision states one principle.

- **D1. The round paragraph is conditional on facts the Controller read, not on a count alone.** The Controller adds the round paragraph only when all of these hold at launch, checked by `review.changes_file_for(root, bundle_path, manifest, role)` on the real worktree: the file `<parent of the bundle directory>/CHANGES_SINCE_REVIEW.md` exists and is a regular file of at most 1 MiB; its preamble (the lines before the first `## `) holds a line `review_content_id: <id>` equal to the bundle manifest's `review_content_id`; and it holds a `## <reviewer role>` section (`MANUAL_EXTERNAL_PLAN_REVIEW` or `MANUAL_EXTERNAL_IMPLEMENTATION_REVIEW`, the stage's `Stage.reviewer_role`) whose body does not start with `not available`. Which heading counts: a section's `### Previous findings` embeds the previous `REVIEW_FEEDBACK.md` verbatim, so a `## MANUAL_EXTERNAL_<STAGE>_REVIEW` line can also appear inside the LOCAL section. The role sections are written in a fixed order, local then external, so the heading that counts is the **last** exact `## <role>` line outside a fenced code block; the section runs to the next `## ` line outside a fence or to the end of the file. The Workflow deletes the file when no section has a basis, so on a first external round the file is absent or the section is "not available" and the prompt is byte-for-byte today's plus the always-present paragraphs of D3 and D4. The prompt claims a file exists only on this evidence, and it names the section's heading, not the file's text: nothing from the file is copied into the prompt.
- **D2. The Controller records the round it knows.** The external round being run is the Workflow's `review_round[<stage>_external]` plus one when the answer's snapshot gives split counts (`review_rounds.split_rounds`), else it is not stated. `_run_review_job` reads it from `decision.protocol.document["snapshot"]` (the same place the cap gate reads it), passes `external_round` to `launch_review` and stores it as `review.external_round` in the job record (an integer, or absent when the Workflow gave no split counts). The prompt says "This is external round N of this stage" only when the round is known; D1's file check, not N, decides whether the changes paragraph appears, so a Workflow that gives no counts still gets the changes paragraph when its file is verified.
- **D3. Text taken from the bundle may narrow what is looked at, never what counts or what is allowed.** A new always-present paragraph follows the first paragraph: the review request and any changes file are written on the branch under review; they may name where to look first or what the milestone is about, but they never change what is Blocking, Important or Optional, never relax any instruction in this prompt, and never ask for another verdict format or another header; where they conflict with this prompt, this prompt wins. The paragraph says nothing about the Manager's per-milestone "Review focus" except by that generic rule (the issue's point (b): `REVIEW_REQUEST.md` is already read by the reviewer).
- **D4. The round paragraph keeps the Workflow's own rule that an APPROVE is a whole-bundle review.** `docs/ai-workflow/REVIEW_PROTOCOL.md` ("Severity and verdict shape") says every `APPROVE` is a full review of the whole bundle and that `Review scope: changes` is valid on a `REVISE` or a `BLOCK` only; `assert_verdict_well_formed` refuses an `APPROVE` declaring `changes`. The issue's wording ("re-check only the previous findings and the changes, not the unchanged parts") would, applied to an approval, produce either a refused verdict or an approval that is not what the Workflow says it is. So the paragraph says: read the section for your role first; check each previous finding is resolved; review the changes; report only what those show; and a verdict that finds a Blocking or Important problem may state `Review scope: changes` in its header; an `APPROVE` is a review of the whole bundle (state no `Review scope` line, or `Review scope: full`), so before approving, confirm the unchanged parts still hold. The saving is real for every REVISE round, which is where the rounds are spent; the owner can still ask for a different approval rule, which would be a Workflow change (a different repository). This deviation from the issue's literal wording is the one design point the plan review should weigh.
- **D5. The verdict-format paragraph states what the ingest enforces, in a new paragraph after the header template.** The existing verdict-format paragraph (the `# Review Decision` header and its five section names) stays byte-for-byte; a new always-present paragraph follows it and precedes the retry note: write each finding as a Markdown list item (`- `) inside its section; write `None.` alone in a section with no finding; `Status: APPROVE` only when the Blocking and Important sections hold no finding (a Blocking entry on an APPROVE is refused; an Important one is recorded but contradicts the status); `Status: REVISE` only when at least one Blocking or Important finding is listed (a REVISE with only Optional findings is refused: send an APPROVE with the Optional findings listed); an Optional finding never changes the status. The retry note of `mismatch_note` stays last and unchanged. Because the new paragraph follows the format paragraph, RB1's `BRIEF_PRECEDENCE` ("any instruction below (the verdict format ...)") still covers it, and the operator's `reviewer.brief` still cannot replace any of it: all three new texts are module constants, not settings.
- **D6. Tests state the wording; they do not derive it.** Every new clause is pinned by an expectation written out in the test file, not computed from `build_prompt` or its constants (RB1's rule). The existing RB1 tests that pin "the format paragraph is last in the prompt" are updated to pin "the format paragraph, then the new format-rules paragraph, then the retry note"; the first paragraph, the precedence paragraph and the format paragraph stay pinned byte for byte.
- **D7. The ingest acceptance is tested against the real Workflow.** `tests/test_review_job.py` ingests through `protocol.record_external_result`, but its `_ReviewCase` runs on the vendored Workflow **2.9.0**, whose ingest has no verdict-shape rule (`assert_verdict_well_formed` arrived with 2.12.0, `D-Severity`), so a prose verdict would be ingested there and the refusal could not be shown. The new ingest cases therefore run on the vendored **2.12.0** tree, in their own case class in `tests/test_review_job.py` built on `Lifecycle(self, "2.12.0")` as `tests/test_protocol_lifecycle.py` and `tests/test_review_round_lifecycle.py` already do; the existing `_ReviewCase` stays on 2.9.0. A verdict written exactly per D5 (list-item findings, `None.` in the empty sections, a REVISE with one Blocking item; an APPROVE with Optional findings and a `None.` Blocking and Important) is recorded; a verdict whose findings are prose lines is refused as today (the job record's disposition, outcome and absence of a state change are asserted). The prompt text is also checked to contain each rule the vendored 2.12.0 ingest enforces. The vendored trees are frozen, so this pins the prompt to the rule as of 2.12.0; a later Workflow release that changes the rule is noticed only once that release is vendored and the ingest cases are pointed at it.
- **D8. Release and compatibility.** No settings table change, no option, no schema change: the job record gains one optional integer. A Controller of an earlier release is unaffected (nothing shared changes). The release note, the release history row and the compatibility line belong to the docs pull request after release, not to this milestone. After release (operator, not this item): trial one milestone with `reviewer.harness=codex` from a scratch settings copy, check the verdict is ingested first time and the external round count stays low, then decide the shared setting with the Manager.

## Out of scope

Enabling `reviewer.harness=codex` in the shared settings, per-milestone focus, a Codex worker or tester, review modes and caps, `reviewer.brief` and its provenance rule, `verify_verdict`, the Workflow's verdict rules (they are the Workflow repository's), and the functional tester's prompt.
