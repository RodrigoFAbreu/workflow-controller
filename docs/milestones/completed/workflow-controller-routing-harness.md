## Goal

Close [#158](https://github.com/RodrigoFAbreu/workflow-controller/issues/158). Routing decides a model and an effort for each role; nothing decides **which harness** runs it, and the harness registry (`controller/harness.py`) declares which roles each harness can take but nothing reads that declaration when a route is chosen. This milestone makes the harness a third routable field, validates it against the registry **when the routing is loaded**, and records it. It adds no launch code: a role is still launched on Claude Code, and the later items (H3 the launch seam, H4a to H4g the Codex worker, C10g the Codex tester) are what make a second harness runnable.

One concern only: **the `harness` field of a routing entry, its validation and its precedence**. Out of scope: supported models and efforts per harness (H8), the role-by-harness documentation table (H6), fallback chains (H9), the independence rule (H10), the harness in telemetry (H11), any launch path (H3), `reviewer.harness` and the review modes, and any change to the functional tester.

## Decisions

Each decision states one principle.

- **D1. `harness` is a third routable field, and its vocabulary is the registry's.** `routing.FIELDS` becomes `("model", "effort", "harness")`, so `default`, each `roles.<role>` entry of the `routing` section, and the `--routing-config` file all accept it. Unlike a model or an effort, whose vocabulary belongs to the `claude` CLI, a harness name belongs to this repository: a new `routing.check_harness(value)` accepts only a key of `harness.ADAPTERS` (`claude-code`, `codex`), raising `ValueError` that names the registered names; the reviewer alias `claude` is **not** accepted, because `routing` names the harness a worker session runs on, not a verdict family. `controller/routing.py` imports `controller.harness` (which itself imports only `controller.errors`), so the package-structure order is unchanged.
- **D2. A routing role maps to one adapter role, and the registry decides what a harness may take.** A new `routing.ADAPTER_ROLE` maps every key of `ROLES` to the adapter role the Controller launches it as: `functional-tester` is `harness.FUNCTIONAL_TESTER`; **every other routing role is `harness.WORKER`** (a lifecycle worker session, including the local review and the validator roles). The Controller-run external review gates are not routing roles at all (they are chosen by `reviewer.harness` and the review mode) and are untouched. A test holds `ADAPTER_ROLE` equal to `ROLES` as a set, so a role added later cannot be left unmapped. `routing.check_role_harness(role, harness)` then refuses a harness whose adapter does not declare that adapter role.
- **D3. Exactly these pairs are accepted after this item, and everything else is refused with a message that names the role, the harness and what the harness does declare.** `claude-code` declares `worker`, `reviewer` and `functional-tester`, so it is accepted for **all 15 routing roles**. `codex` declares `reviewer` only, so it is accepted for **no routing role**: any `harness: codex` in a routing entry is refused at load, in the shared settings file, a `--routing-config` file and on the command line alike (D4), until a later item (C10g-1 for the tester, H4a to H4e for the worker roles) adds the role to the Codex adapter's declaration, at which point the same check accepts it with no change here (and, as D6 says, without a settings table generation bump). The refusal reads, for example, `role 'review-plan' runs as a 'worker' and harness 'codex' declares only ['reviewer']`, and carries `role`, `adapter_role`, `harness` and `declared_roles` as evidence. That the accepted set is, today, "claude-code everywhere" is stated plainly in the guide: this item gives the choice a name and a check, and the choice becomes useful as the registry grows.
- **D4. Validation happens at load, for every entry and every source, so a bad harness never reaches a launch.** `validate_routing_mapping` checks each `roles.<role>.harness` with `check_role_harness`, and checks `default.harness` against **every routing role that has no `harness` of its own** (the roles the default would apply to), refusing at the first role in sorted order and saying how many further roles it would also have applied to. The check is deliberately conservative: it does not know `--role-harness`, so a `default.harness` that every role overrides on the command line is still refused at load, and an implementer must not "fix" that. A value that is not a registered name, or a pair the registry refuses, is a `RoutingConfigError` carrying the dotted `key` (as every other value refusal does), exit 20 before any job record is written, **in strict mode (a `--routing-config` file) and in the shared settings file alike**: an unsupported role and harness pair is never replaced by a fallback and never launches, because the owner's rule is a named refusal at load. `validate_routing_mapping` keeps its two-item return and its two callers (`routing.parse_routing_config`, reached through `routing.load_routing_config`, and `settings._check_routing`) change only by gaining the check; there is no third "rejected" channel and no change to `SettingsFile` or `warn_unknown`. An **unknown field** keeps its present treatment: refused in a `--routing-config` file, left out with one warning in the settings file. Command-line assignments are checked by argparse, not here: an invalid `--role-harness` is a usage error, exit 2 (CP2), like `--role-model` and `--role-effort`; a hand-built `RoutingOptions` raises `ValueError`.
- **D5. Precedence is the existing one, minus the global option.** For one role the harness resolves, highest first: `--role-harness ROLE=HARNESS` (`role-cli`), the routing config's entry for the role (`config-role`), that config's `default` (`config-default`), then the built-in `claude-code` (`default`). There is **no `--harness`**: a single harness for every role cannot be valid for any harness but `claude-code` (D3), so such an option would be either redundant or always refused. `--routing-config` replaces the settings file's `routing` section whole, as it already does for model and effort. The harness resolves independently of model and effort. `RoutingOptions` carries `cli_role_harnesses` (checked with `check_role_harness` on construction, raising `ValueError`, so a hand-built option set cannot hold an invalid pair); `resolve_route` returns the harness and its source in `ResolvedRoute`.
- **D6. The shared settings file stays readable by an older Controller, and a newer file is refused by this one only for a pair this registry rejects.** Adding a field to the routing schema is a table change, so `settings.TABLE_GENERATION` becomes **15**. An older Controller reading a file with a `harness` entry warns once that the key is unknown and ignores it (the existing `routing.validate_routing_mapping(unknown="ignore")` and `settings._routing_unknown` path, which read `routing.FIELDS`), and its `settings clean` refuses a file filled by a newer release, exactly as for the routing roles added in generations 3, 9, 10, 11 and 13. An older Controller given a `--routing-config` file with `harness` refuses it (that file is strict by design). The Controller **writes no `harness` default** into the file: the built-in applies implicitly, so no existing value moves and `_defaults_written` is unchanged. **The newer-registry direction:** once a later item lets the Codex adapter take a role, a file holding `roles.functional-tester.harness: codex` is valid for that release and is refused by this one at load (D4), naming the role, the harness and what it declares; the remedy is to update the Controller or remove the entry, and `docs/compatibility.md` states this in its 1.21.0 paragraph. This is accepted on purpose over a silent fallback to `claude-code`. Tests: a read of the file at generation 14 (the field list without `harness`; the fixture carries `_table_generation: 15`, without which `settings clean` would strip the entry and a fill would rewrite the stamp) asserts the warning and the ignore, that `settings clean` refuses it and that a defaults fill leaves it; a settings file holding `roles.<role>.harness: codex` is exit 20 through `settings.load`, through `fill` and through the CLI before any job record exists, and the same value in a `--routing-config` file is exit 20.
- **D7. The resolved harness is recorded, additively, with one vocabulary, and launch ignores it.** `ResolvedRoute` gains `harness` and `harness_source` (defaults `claude-code` and `default`, so every existing hand-built route is unchanged); `to_record()` gains `harness` and `sources.harness`. **`worker_route.harness` means the adapter name (`claude-code` or `codex`, the registry's) for every job kind.** The current literals do not hold that: the tester record (`controller/job.py:7529`) writes `review.CLAUDE.name`, which is `"claude"`, the reviewer alias, over the value the route resolved, and the review record (`job.py:6919`) writes the reviewer harness name. So the two literals are **removed** and the record takes the route's value: the tester's route comes from `resolve` and names `claude-code` with source `default`; the Controller-run review builds its `ResolvedRoute` with `harness=adapters.get(harness.name).name` (`adapters` is the registry module, imported into `job.py` under that name because `harness` is a local holding the reviewer object; the reviewer name `claude` maps to `claude-code`, `codex` to `codex`) and the source `reviewer.harness` (the Codex review) or `review.mode` (the same-provider review). The one visible change is that a same-provider review record's `worker_route.harness` reads `claude-code`, not `claude`; the `review` block's own `harness` key keeps the reviewer vocabulary, untouched. Readers: `job.py:2512`/`2533` require only a string, `job.py:3211`/`6821` read the `review` block, `observe.py` and `telemetry.py` read `role`/`model`/`effort` (telemetry's `harness` is its own constant), so nothing depends on the old `"claude"` value. Readers read `worker_route` with `.get`, so an older record without the key and a newer one both read. Because only `claude-code` is accepted for a routing role (D3), no resolved harness can differ from what `controller.worker.launch` runs today; **H3** is the item that makes the launch read `route.harness`.

## Out of scope

Everything listed under Goal, plus a model or effort check against the harness (H8), a `--harness` option, a repository-level default, and changing `explain` (it prints no routes today; the resolved harness is visible in the job record and the routing section is visible in `settings show`).
