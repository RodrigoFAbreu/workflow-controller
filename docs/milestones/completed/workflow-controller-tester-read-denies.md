## Goal

Close the points of [#115](https://github.com/RodrigoFAbreu/workflow-controller/issues/115) that name the job's private Claude home, the operator's Claude directory and account file, the `file://` origin and the summary; the copies of the same credential that other Controller jobs keep under the shared runtime root are a named remainder, recorded as a roadmap follow-up (Out of scope, I2 round 3). Today the Claude functional tester's sandbox limits writes but not reads: its shell can read the job's private Claude home (a copy of the operator's credential file, `<runtime>/functional/<job>/claude-home`) and the operator's own Claude directory, and whatever it learns it can put in its `summary`, which the Workflow's `ingest_functional_evidence` stores verbatim in `WORKFLOW_STATE.json` (a committed file) and copies into the findings file. Separately, `review._local_origin_refs` treats a `file://` origin as a URL and never reads it, although Git reaches it, so the second detection layer (the refs of a real local origin compared before and after) is blind to that origin. One mechanism is new (a read deny list in the tester's settings); the other two points are a parse rule and a length bound.

## Decisions

Each decision states one principle.

- **D1. The tester's sandbox denies reading the places a credential or an account identity lives.** `functional_review.tester_settings` gains a required keyword `deny_read` and writes it as a `denyRead` list in `sandbox.filesystem`. The list comes from one helper, `functional_review.read_denies(job_claude_home, operator_home)`, and holds, in this fixed order: the private entries of this job's Claude home, by name (`.credentials.json`, the copy `build_claude_home` writes, `review.CLAUDE_CREDENTIAL_FILE`; `.claude.json`, and `backups`), then the operator's whole Claude home (the `operator_home` the launch was given, where the original `.credentials.json` lives), then the operator's global account file, the real user's `$HOME/.claude.json` (I1, round 3: `tests/harness_contract/claude/state_entries.txt` (Readings) records that without `CLAUDE_CONFIG_DIR` the global config lives at `$HOME/.claude.json`, beside `~/.claude` and not inside it, so denying the operator home does not cover it; it holds the same `oauthAccount`, `userID`/`machineID` and usually the operator's MCP server definitions, whose `env` can carry tokens). It is resolved from the Controller process's own home before the launch replaces `HOME` for the tester, and it is **always** listed, whether or not `CLAUDE_CONFIG_DIR` is set: when it is unset and the operator home is the default, the file is the only entry that covers it; when it is set the entry is redundant at worst and keeps the document a pure function of its inputs. Why those entries: `tests/harness_contract/claude/state_entries.txt` (Readings) records that the CLI writes `.claude.json` into `CLAUDE_CONFIG_DIR` holding `oauthAccount` (`emailAddress`, `accountUuid`, `organizationUuid`, `displayName`) and `userID`/`machineID`, with copies under `backups/.claude.json.backup.<ms>`, and says to treat them as private (I1, round 2). A tester that could `cat` them could put the operator's address and ids in a `summary` that is committed, the same leak path as a token. Each entry is written as given and, when `os.path.realpath` of it differs (a `~/.claude` that is a link into a dotfiles tree), its resolved form follows it, so the list has five entries, or up to ten. The job home is **not** denied as a whole: the contract records no `shell-snapshots/` entry in `CLAUDE_CONFIG_DIR` (`CLAUDE_STATE_ENTRIES`, `controller/review.py`, does not list one either), so whether the sandboxed shell sources anything from the job home is unmeasured, and a whole-home deny could break every tester command. The entries left readable are `projects`, `sessions`, `session-env`, `.last-cleanup` and `mcp-needs-auth-cache.json`: the first three hold only this job's own session transcript and ids, the last two hold a timestamp and the names of claude.ai connectors the job does not enable (`ENABLE_CLAUDEAI_MCP_SERVERS=false`); none is a credential or an account identity. The D3 probe measures which job-home entries the shell actually reads on the pinned build and the plan is revised if it shows a secret there. A named entry that does not exist yet (the CLI creates `.claude.json` and `backups` at run time) is still written, so the deny is in force when the file appears. The operator's home is never the tester's `CLAUDE_CONFIG_DIR`, so denying it whole costs the shell nothing. The Claude CLI process itself is not sandboxed (only the shell commands it runs are), so it still reads its own files; the deny binds the tester's shell. `read_denies` takes the operator's global account file as a third argument. `Sandbox.settings` derives the list from values the Controller already holds; `build_sandbox` receives the operator's Claude home and the operator's global account file as new keyword arguments so the document is a pure function of the sandbox and `check_functional_settings` can compare the settings file to it as today.
- **D2. A read deny is never contradicted by a write allowance.** Extending D1 of the existing layout invariant: no `allowWrite` entry equals or lies below a `denyRead` entry (checked lexically and through symbolic links, by the same routine as the write deny, `assert_writes_not_below_denies`, generalised to take both lists). The launch also refuses, as `functional_tester_unavailable` with the enforcement cause, when the runtime root or the sandbox folder lies inside the operator's Claude home or equals it, because the deny would then cover the tester's own working folders; that check runs in `launch_functional` **before** `build_sandbox` (O1, round 3), because `build_sandbox` would otherwise reach `tester_settings`' `ValueError` first and re-raise it as a plain `ValueError`, not a `TesterUnavailable`. `check_functional_settings` additionally requires the on-disk `denyRead` to be exactly the list `read_denies` derives (D1, the resolved forms included).
- **D3. A read deny is proved on the pinned build, never assumed.** The test double (`tests/fake_functional_tester.py`) enforces `denyRead` the way it enforces `denyWrite` (a path is resolved through links, then refused when it equals or lies below an entry), and a unit test shows a read of the credential copy and of a file in the operator's Claude home refused while a read of the clone is allowed. A release-side live test (`CONTROLLER_LIVE_CLAUDE_TESTS=1`, beside the boundary probes in `tests/test_functional_enforcement.py`) puts a canary file in a directory named in `denyRead`, asks the real tester CLI to `cat` it through the Bash tool, and requires that the canary text does not appear in the result and that a file outside the deny is still readable. If the installed Claude build does not enforce `sandbox.filesystem.denyRead`, CP3 stops and reports it: the Controller never ships a deny it cannot show working. The probe also runs an ordinary command in the clone (`pwd`, then `git status`) and requires it to succeed with no shell-snapshot error, so a deny that broke the tester's shell (I3) is told apart from a build that does not enforce `denyRead`, and it puts a canary in a scratch `HOME/.claude.json` named in `denyRead` as the operator's global account file and requires it unread (I1), denies `.claude.json` and `.credentials.json` of a scratch Claude home while a sibling file of that home (`.last-cleanup`) stays readable, and the shell lists `$CLAUDE_CONFIG_DIR` and reads each entry, so the probe reports any job-home entry that is readable, not denied and secret-looking (D1). The proof is a release-side test, not a new `claude-build verify` probe: a new probe would change what every recorded verified build attests, which is its own item. **`claude-build verify` builds the same settings (I2):** `claude_build._Run` calls `tester_settings`, so it passes `deny_read` from the same helper (the verify job's own private entries, the operator home verify was given and the operator's global account file), keeping the verified shape the launched shape. `verify_build` already holds `operator_home`, so `_Run.__init__` takes it, and the global account file, as new keyword arguments and builds the settings there (O1, round 2); a verify runtime root or base inside the operator's Claude home, which D2's invariant makes `tester_settings` refuse with `ValueError`, is caught in `verify_build` beside `TesterUnavailable` and `OSError` and reported as `BuildNotVerified("host", ...)`, never a traceback. Records are keyed by the build's digest and hold no settings, so existing records stay valid and are not re-verified; the gap this leaves is that no recorded build attests `denyRead` enforcement, which the release-side probe covers for the pinned build.
- **D4. A `file://` origin is a local path (#115, point 2).** `_local_origin_refs` parses an origin that starts with `file://` as a path: the part after the scheme, percent-decoded, the authority is dropped whatever it is, as Git does (`git ls-remote file://otherhost/<abs path>` reaches the local repository, checked on Git 2.56.0; I1), and the absolute path that remains is read. A `file://` origin with no absolute path after the authority is not guessed at: it raises `OSError`, which the run reports as an `origin:` breach (it fails closed, never `None`). All other URL and `host:path` forms behave as today, and the existing read (`git for-each-ref` on the path, an unreadable path is an `OSError` the run reports as a breach) is reused unchanged. The Codex tester shares this function, so both testers get it.
- **D5. A tester summary is bounded where it enters the Controller (#115, point 1).** `parse_results` truncates an entry's `summary` to `SUMMARY_LIMIT` (2000) characters and appends a marker naming how many characters were omitted, so the stored record and the findings file carry a bounded string. The log file and its digest are untouched, the entry stays valid, and a summary within the limit is unchanged byte for byte. Truncating, not refusing, because an over-long summary is an honest tester's verbosity as often as a leak, and the whole text remains in the log the operator can open.
- **D6. The Codex tester is covered already and says so.** `codex_sandbox.profile_toml` is a restricted-read profile (`:minimal` plus named roots), so the operator's home and the tester's own credential copy are not readable (`docs/guide/harnesses.md`, measured in `tests/harness_contract/codex/tester_sandbox.txt`); this item changes nothing there and the documentation says which tester each control covers.
- **D7. The documentation follows the change.** `docs/guide/automation.md` (the tester's sandbox: the read deny, the `file://` case, the summary bound) and `docs/guide/harnesses.md` (which tester each control covers) describe D1 to D6; `docs/ROADMAP.md` marks C10h done and drops the follow-up for #115; `docs/ACTIVE_MILESTONE.md` is updated at acceptance. The release note, the release history row and the compatibility line belong to the docs pull request after the 1.27.6 release, as for every earlier release. The pull request closes #115; the runtime-root remainder lives in its own roadmap follow-up.

## Out of scope

The copies of the Claude credential and account identity that other Controller jobs keep under the shared runtime root (`<runtime>/reviews/<job>/claude-home/`, a `claude-build verify` scratch `verify-*/claude-home/`, and any copy a killed job left behind, which `sweep_retained` never removes): the tester knows the runtime root and can read them by absolute path (I2, round 3). Denying them needs a name for every sibling `functional/*` folder, which `denyRead` cannot give without a pattern the build is not shown to accept, and a deny on the runtime root's other top-level entries would miss entries created later, so a partial deny would claim more than it proves. It is the same class as the allowlist item and is recorded as a roadmap follow-up, together with deleting an abandoned job-home copy; the documentation names the remainder. A general read allowlist for the Claude tester (every absolute path outside the clone and the scratch folders), other credential stores (`~/.ssh`, `~/.config/gh`, the operator's Codex home: the tester's `HOME` is a private scratch folder, so only an absolute path reaches them, and closing that is the allowlist item), a new `claude-build verify` probe, redaction of secrets from a summary, and a change to the Codex tester's profile.
