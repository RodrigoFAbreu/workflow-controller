## Goal

A checklist flow that needs the PID-namespace launcher (`unshare --user --map-current-user --pid --fork --kill-child --mount-proc`, as `tools/run_tests.py --namespace require`, `NamespaceKillProofTest` and the wrap probe use) cannot run in the functional tester's sandbox: the launcher answers "Operation not permitted" (seen on [NS1](../items/workflow-controller-ns1.md), flows 1, 2, 4 and 6). Today neither tester is told, so each such flow is attempted, fails with whatever the launcher printed, is retried or misjudged, and costs tester turns before an operator reruns it by hand. After this item both testers' prompts and the checklist writer's note **state the limit and what to do about it**: the tester tries the launcher once, and if it is refused, records the flow as `failed` with reason `environment` and quotes the launcher's message in the summary, with no retries and no `defect`; and the existing `environment_limited` outcome and `GATE_FLOWS_NOT_RUNNABLE` stop carry it to the operator, who runs the flow on the host and records it with `record-external-result --kind functional_evidence`.

One mechanism: **one new sandbox limit, stated once** in the single text the prompts already share. Nothing is allowed, nothing is faked, no sandbox profile or setting changes.

## What exists

- `controller/functional_review.py` `SANDBOX_LIMITS` is the Claude tester's stated limits; its first five entries are `SHARED_SANDBOX_LIMITS`, the limits **both** testers state word for word, and the note the row-37 launch gives the checklist writer (`sandbox_limits_note`), because the tester is not chosen when that checklist is written. `controller/codex_bridge.py` `SANDBOX_LIMITS` repeats the shared five and adds the Codex sandbox's own.
- `tester_prompt` already tells the tester that a flow the sandbox cannot run is `failed` with `reason` `environment`, and the run already ends `environment_limited` (no findings, no applier) when every failed flow is `environment` (`gate_text(GATE_FLOWS_NOT_RUNNABLE)`: "Run those flows by hand and record them, or change the checklist so they run offline").
- The Claude tester's sandbox is Claude Code's own shell sandbox (bubblewrap with a seccomp filter, configured only by the `--settings` document `tester_settings` writes); the Codex tester's is the `tester` permissions profile `codex_sandbox.py` writes into its `config.toml`. Neither has a setting that admits a nested user namespace, and a nested namespace is not something the Controller can grant from outside the harness's own sandbox.
- A fake launcher cannot honestly stand in: `FAKE_PROGRAMS` stand-ins (`gh`, `claude`, `codex`, `ssh`) *refuse and log*, which is the same outcome as the real refusal. A stand-in that ran the command **without** the namespace would make a `kill(-1)` proof pass for the wrong reason, or send a real `kill(-1)` at the tester's own sandbox, which is the hazard NS1 exists to remove.
- Tests pin the text: `tests.test_functional_review` (the prompt hash, `test_it_states_the_sandbox_limits_and_the_copy_rule`, `test_the_row_37_note_shares_the_limits`), `tests.test_codex_bridge` (the limits against the profile).

## Decisions

- **D1. State the limit, never allow it or fake it.** Of the item's three mechanisms, the plan takes the third in its cheapest form (mark such flows as not runnable by the tester, from the start) and rejects the other two. Allowing the launcher widens the tester's attack surface (an unprivileged user namespace grants a capability set in that namespace and exposes the kernel's namespace code to a model-driven shell), is not configurable from the Controller, and is the owner's decision (O1). A fake launcher either repeats the refusal (no gain) or runs unisolated (false evidence and the NS1 hazard). Stating the limit gives the tester a deterministic answer and the operator the existing hand-off.
- **D2. One new entry in the shared limits, worded try-first.** `SANDBOX_LIMITS` in `controller/functional_review.py` gains, as its sixth entry (index 5, right after the five shared ones, so `SHARED_SANDBOX_LIMITS` becomes `SANDBOX_LIMITS[:6]`), a sentence that says: the launcher that makes a new user or PID namespace (`unshare --user ... --pid`, so `python3 tools/run_tests.py --namespace require` and any flow that proves a namespace's isolation) has been refused in this sandbox; a flow that needs it tries the launcher once, and if the launcher is **refused** the flow is `failed` with `reason` `environment`, its summary quotes the launcher's message, and the tester does not retry or work around it; an operator runs the flow on the host. The sentence names **every observable form of the refusal**, because the two common paths to a namespace flow do not print an error: `unshare` answering "Operation not permitted"; `--namespace require` refusing with "no PID namespace here" (`tools/run_tests.py:113`, quoted, not paraphrased); the default `--namespace auto` mode's notice "running the shards without a PID namespace" or its summary line `namespace: none (<reason>)` (`tools/run_tests.py:114-115`), where the run goes on unwrapped and green; and a namespace test skipped with "no PID namespace on this host" (`NamespaceKillProofTest`, `tests/test_run_tests.py:646-653`, which ends `OK (skipped=1)`). It also says that a flow that proves a namespace's isolation is `passed` **only on evidence that the namespace was used** (the run's summary line is exactly `namespace: isolated`, or `isolated for N of M shards` with N above 0 and the flow's module in a wrapped shard, never `isolated for 0 of M shards`, which wraps nothing; or the proof test ran and was not skipped); otherwise the flow is `failed` with `reason` `environment` and the message or skip text quoted. The sentence words the Controller-specific forms as examples ("for example, in the Controller's own test runner ..."), so the limit stays general for every managed product's tester and short. The sentence never tells the tester to skip the attempt: the outcome comes from what the launcher does, so the tester prompt's existing "a flow the sandbox cannot run is `environment`" is not read as a must-not-run instruction. `codex_bridge.SANDBOX_LIMITS` repeats it word for word, after its `PATH` entry (the two lists are not index-aligned, since the Codex list states its read limit at index 4; the existing test checks the shared limits by membership, not position). The slice, the note and the per-tester tails stay as they are, so no other code changes. Evidence for the refusal: one functional round, NS1's (flows 1, 2, 4 and 6, recorded in `docs/items/workflow-controller-ts1.md`); `controller/codex_sandbox.py` says nothing about user namespaces or `unshare`, so the Codex tester's refusal is not observed. That is why the sentence is conditional: if the Codex tester's launcher runs, the flow passes, and if it is refused the flow is `environment` with the message as proof, either way without a wrong prompt.
- **D3. The statement is not a probe.** The Controller does not detect whether the launcher works before a launch: the sentence is a conditional instruction to the tester, who runs the launcher as part of the flow. If a later Claude or Codex build admits the launcher, a flow that ran it successfully simply passes, and the text ("has been refused", not "never", and "if the launcher is refused") cannot make a passing run wrong. The evidence rule in D2 also closes the silent-pass path: a run under `auto` that went unwrapped, or a namespace test that skipped, is green without any namespace, and the tester is told to treat that as `environment`, never as `passed`. A real probe by the Controller (running the launcher inside the sandbox before the launch) would be a second mechanism and is not planned.
- **D4. The checklist writer is told the same, once.** `sandbox_limits_note` reads `SHARED_SANDBOX_LIMITS`, so it carries the new limit with no edit, and a checklist written afterwards prefers flows that avoid the launcher or says in the flow that an operator runs it. Existing checklists are not rewritten.
- **D5. The `GATE_FLOWS_NOT_RUNNABLE` text names the launcher.** Its list of what the sandbox lacks gains "no PID-namespace launcher (`unshare`)", and the remedy keeps its words ("Run those flows by hand and record them") and adds the recording command's form (`record-external-result --kind functional_evidence`, as `docs/run.md` already states) so an operator needs no other page.
- **D6. `workflow-manager` on the tester `PATH` is not part of this item.** The item says "also consider" it. The tester's `PATH` is deliberately only the sandbox's `bin/` and the system directories; adding a real tool, or a stand-in for one, is a separate trust decision with its own proof (what the tool may read and write inside the sandbox). It is offered as owner decision O2 and recommended as its own item.
