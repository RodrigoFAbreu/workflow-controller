# Release history

> For: anyone who wants to know what each Controller release changed. Last checked with: Controller 1.22.2; Workflow 2.6.0, 2.7.0, 2.8.0, 2.9.0, 2.10.0, 2.11.0, 2.12.0 and 2.13.0.

One line per release, newest first. Release notes exist from 1.3.0 and are
linked. Which Workflow each release admits is on the
[compatibility page](compatibility.md).

| Release | What changed | Notes |
|---|---|---|
| 1.22.2 | Fix: the Controller-run Codex external review (`reviewer.harness=codex`) is no longer refused at launch on `codex-cli 0.163.0`: its three newly enabled features `api_key_cyber_access_programs`, `cli_daybreak` and `code_mode_interrupt` are disabled unconditionally with `--disable` (accepted by 0.163.0) and are not in the allowlist; `PINNED_VERSION`, the Codex adapter's `pinned_version`, the fake Codex's version and default feature capture move to 0.163.0, and `features_list.0.162.1.txt` is replaced by `features_list.0.163.0.txt` (the other captures and digests are kept); only the feature list and the `--disable` acceptance were re-measured, not the real `codex exec` runs or the sandbox probe; a later update that changes a checked surface still fails closed at launch; enabling `reviewer.harness=codex` stays the operator's settings change (#168) | [1.22.2](releases/1.22.2.md) |
| 1.22.1 | Fix: a pending-checks stop (the `merge.wait_seconds` budget spent while the pull request's checks still run, or a step in a repository without auto-merge) sends the new info event `checks_wait` (kind `state`, INFO, LOW, on by default, title `Waiting for the pull request's checks (<work item>)`) instead of `lane_blocked` (CRITICAL); `lane_blocked` is sent only once the checks have been pending longer than four hours (a fixed limit, not a setting), measured from the newest event of the work item's binding record; a failed check still reaches `lane_blocked` through the pull-request defect loop; the event identity is the stop's own, and a stop already announced as `lane_blocked` before the upgrade is not announced again; the `events` section accepts `checks_wait`; no settings generation change, exit code, step count or gate identity change (#170) | [1.22.1](releases/1.22.1.md) |
| 1.22.0 | Each harness adapter declares the models and efforts it supports (`controller/harness.py`); routing checks the resolved model and effort against the resolved harness once, on resolved routes, before any job record is written, and a model or effort the harness does not declare, valid until now, is refused at the next `run` or `step` with exit 20, naming the role, harness, field and the declared values (`None` inherits and is never refused); new settings row `harness.models`, a map from a harness name to a list of extra model names, no command-line option, table generation 16; the generated table in the harness guide gains Models and Efforts columns; the lane's routing is checked by the committed fixture `tests/fixtures/lane_routing.json` (H8) | [1.22.0](releases/1.22.0.md) |
| 1.21.1 | Fix: the prompt of the Controller-run external review (Codex and same-provider Claude reviewer, plan and implementation stages) gains three protected paragraphs that `reviewer.brief` cannot replace: a round paragraph, added only when the Controller verified it is the second or later external round and the stage's section of `CHANGES_SINCE_REVIEW.md` names the bundle's review content ID, which points the reviewer at that section and allows `Review scope: changes` only on a round that reviewed changes; a paragraph saying bundle text may narrow what is looked at but never the severity bar or a rule; and a paragraph after the header template stating the verdict format the ingest enforces (`- ` bullet findings, `None.` for an empty section, a consistent Status); the job record gains one optional integer, the external round the Controller knew; no setting, option or schema change (#161) | [1.21.1](releases/1.21.1.md) |
| 1.21.0 | A routing entry gains a `harness` field (the `routing` section of the settings file, a routing config file, and the new option `--role-harness ROLE=HARNESS`), default `claude-code`, checked against the roles the harness adapter declares: `claude-code` is accepted for every routing role, `codex` for none; an unknown harness or an undeclared role and harness pair is a named refusal at load with exit 20 from every source; precedence is `--role-harness`, the routing config's role entry, its default, the settings, then `claude-code`; `ResolvedRoute` and the job record gain `harness` and `harness_source`; launch ignores the resolved harness; settings generation 15 (#158) | [1.21.0](releases/1.21.0.md) |
| 1.20.0 | New setting `reviewer.brief` (optional string, at most 2000 characters; settings generation 14) and a built-in default brief added to every Controller-run external review prompt (Codex and same-provider Claude reviewer, plan and implementation stages, retry prompt): judge only what the milestone changed, call a finding Blocking or Important only for real harm, treat wording, polish, double faults and extra hardening as Optional; a brief is used only from a settings file outside the target repository, its worktree and the review bundle or disposable copy, else the default is used and the run says so once; a control character other than newline and tab exits 20; no per-command option (#150) | [1.20.0](releases/1.20.0.md) |
| 1.19.3 | Fix: a wait for the external review verdict and the functional-review tester stops (except `isolation_breach`) send the new info event `review_wait` (INFO, LOW) instead of `user_gate`, which stays for approvals, acceptance, merges that need the owner, BLOCK-resolution gates and legacy gates; a gate's job record keeps the Workflow's decision in a new `protocol_gate` field; `checks_pending` is unchanged (#149) | [1.19.3](releases/1.19.3.md) |
| 1.19.2 | Fix: `verify-claude` names a host write in a sandbox-start error instead of hiding it behind `inconclusive`, keeps its host-listener folder short whatever `TMPDIR` is (no more `AF_UNIX path too long`), takes `--claude-binary` without a `claude` on `PATH`, and turns an `OSError` during setup into a named refusal with exit 20 instead of a traceback; the live tests skip without credentials (#132, #133) | [1.19.2](releases/1.19.2.md) |
| 1.19.1 | Fix: the functional tester's sandbox layout now puts its writable folders outside the clone (`<sandbox>/writable/<name>/`) behind links, so no allowed write sits below a denied path and Claude Code 2.1.304 and later pass `verify-claude`; the post-run walk accepts only the Controller's own intact links; `verify-claude` gains a `link` probe; the settings check compares resolved paths (#129) | [1.19.1](releases/1.19.1.md) |
| 1.19.0 | New command `workflow-controller verify-claude [--force]` runs three live probes (boundary, retry, missing_component) against the `claude` a launch would run and, on a clean pass, records its SHA-256 digest in `verified-claude-builds.json` in the runtime root; the functional-tester launch admits the built-in list (Claude Code 2.1.303) plus recorded digests and executes the one file it hashed and probed (#113, #114); exit 20 on a refusal; builds from 2.1.304 are refused until #129 ships | [1.19.0](releases/1.19.0.md) |
| 1.18.0 | Under an automatic acceptance gate the Controller runs the functional review itself at row 38e: the committed checklist in an isolated Claude tester (job kind `functional_test`, bubblewrap sandbox, fake `gh`, `claude`, `codex` and `ssh`, scratch origin), one `functional_evidence` per flow, acceptance by policy when all pass, findings for `/apply-functional-review` on a `defect`; needs `bwrap`, `socat` and a verified `claude` build (Claude Code 2.1.303); `functional.automated` and `functional.timeout_seconds` (settings generation 13) | [1.18.0](releases/1.18.0.md) |
| 1.17.0 | Two review round caps per stage, `review.local_round_cap` (default 6) and `review.external_round_cap` (default 4), on the Workflow's split counts (protocol 1.5, Workflow 2.15.0 and later); the external review is capped too; `review.round_cap` and `--review-round-cap` are deprecated (settings generation 12) | [1.17.0](releases/1.17.0.md) |
| 1.16.1 | A patch release (a refactor): the Claude and Codex seams and the git host sit behind adapter registries, and every worker and review job record gets a `usage_record` key in one format beside `telemetry`; the price table ships empty, so a cost is `unknown` unless the harness reports one (no new setting) | [1.16.1](releases/1.16.1.md) |
| 1.16.0 | `/satisfy-gate` is routed by stage: Haiku 5.5 `high` for plan and technical approval, Sonnet 5.5 `medium` for acceptance (new `satisfy-gate-acceptance` role; settings generation 11), and twelve follow-up issues are fixed (no new setting) | [1.16.0](releases/1.16.0.md) |
| 1.15.0 | Under an automatic acceptance gate the Controller reports the pull request's state to the Workflow itself (a vetted `gh`; `run` waits for pending checks) and launches `/apply-pr-review` (the `apply-pr-review` role; settings generation 10), so a pull request whose checks were pending or whose defect was fixed reaches acceptance without a person; a CI-only wait sends no request | [1.15.0](releases/1.15.0.md) |
| 1.14.0 | Under an automatic gate the Controller launches the Workflow's `/satisfy-gate` itself (the `satisfy-gate` role; settings generation 9), so a satisfied gate passes without a person and a refused one stops naming the unmet requirement; a value a protocol 1.x minor release adds is advisory, ignored or a stop, never a refusal; a stop the Workflow calls blocked sends `lane_blocked` | [1.14.0](releases/1.14.0.md) |
