## The Controller can run the cross-model review itself (1.10.0)

**An unattended run no longer stops at the external review gates, if you opt in.** Until now `step`
and `run` stopped at `plan.review.external` and `implementation.review.external`, and a person or a
lane script gave the bundle to a reviewer of another model family and pasted the verdict back. With
`reviewer.harness: codex` in the settings file, the Controller starts a Codex reviewer itself, checks
the verdict and hands it to the Workflow. It is off by default: with the setting unset, every
decision, record, route and exit code is as in 1.9.0.

**How a review job runs.**

- It applies only at the two manual external review gates (rows 14 and 28 at their
  `AWAITING_MANUAL_EXTERNAL_*_REVIEW` phases) of a target in protocol mode (Workflow 2.7.0 and
  later). Every other gate still stops for a person.
- It passes the usage gate for the Codex provider before it starts, so a hold exits `17` like any
  other job. The readings come from your Codex home and from every review home the Controller keeps.
- The reviewer works in a disposable copy of the worktree with its own one-commit repository. The
  real `.git` is never copied, and the copy is removed on every exit path.
- The Controller reads the exact header values from the bundle's `MANIFEST.md`, puts them in the
  prompt, and compares the verdict's header lines with them exactly. A mismatch is retried once.
- A verdict enters the Workflow only through `record-external-result` (`--run-ref codex:<job id>`),
  which applies every Workflow guard and may refuse.
- The job is a job record of kind `review` (job `schema_version` 2), with its route (harness, model,
  effort), a `review` block and a Codex `usage` block.

**The boundary the reviewer runs inside.** It is enforced before every Codex invocation, not only
detected afterwards:

- a `workspace-write` sandbox limited to the copy and its private temporary directory, approval
  policy `never`, network access for commands off, web search off;
- a minimal Codex home that the Controller writes (`CODEX_HOME`), holding a private copy of your
  credential file and no MCP servers, hooks, `notify` command or profiles. Your own `~/.codex` is
  not loaded, and a refreshed credential is copied back only when your file is unchanged;
- an exact environment allowlist and a pinned model provider;
- a refusal when a configuration layer outside that home carries anything: a non-empty
  `/etc/codex/` file (`config.toml`, `managed_config.toml`, `requirements.toml`), a managed or MDM
  layer with any setting, an MCP server, an unlisted feature, a managed provider or
  `model_catalog_json`. The refusal names the check, and no reviewer is started.

A before-and-after snapshot of the real repository, its feedback directory and the Workflow state is
added to that boundary: any change voids the verdict.

**Every verdict is recorded.** Each verdict the reviewer produced, a header-mismatch first attempt and
a `REVISE` included, is kept in the job record with its digest, `Status:` and what became of it, and
its text under `<runtime>/reviews/<job id>-verdict-<n>.md`. The Controller never edits a verdict. A
retry whose `Status:` differs from the first verdict's is not ingested.

## Outcomes

| outcome | exit | when |
|---|---|---|
| `FINISHED` | — | the verdict matched and the Workflow recorded it; the next step re-decides with `next-action` |
| `FAILED` | 30 | the header still did not match after the retry, the retry changed the `Status:`, the Workflow refused the ingest, the reviewer failed with no limit, or the launch boundary was not reproduced (`ReviewLaunchRefused`, `not_started: true`) |
| `INCOMPLETE` | 35 | a usage limit, `reviewer.timeout_seconds` passed, no verdict, or the repository or Workflow state changed during the run |
| refusal | 20 | `reviewer.harness` names a harness that is not registered; nothing is recorded |

In every case but `FINISHED` the gate stays open, so the manual route still works. A usage limit is
recognised only from Codex's own rollout record, never from words in the transcript. After a limit the
next `run` is held at admission until the Codex window resets, because the review's retained rollout is
counted. Ctrl-C kills the reviewer's process group and ends the record `INCOMPLETE`; `resume` (and
`resume --abandon`) ends the group, copies the credential back, removes the copy and closes the
record. See [the troubleshooting entry](../common-problems.md#a-review-the-controller-ran-did-not-finish).

**Sub-agents.** Codex offers no switch that removes its sub-agent tools, so they stay allowed. The
prompt asks the reviewer not to spawn one; when it does, the job record (`review.subagents`) and the
step's event name the spawn and its token usage, because a spawn roughly doubles the spend.

## Configuration

- **Settings generation 6.** The settings file gains five `reviewer.*` rows: `harness` (unset),
  `model` (unset, built-in `gpt-6.1-sol`), `effort` (unset, built-in `high`), `timeout_seconds`
  (3600) and `binary` (unset, built-in `codex`). See
  [the settings file](../guide/runtime.md#what-it-holds).
- `reviewer.model` and `reviewer.effort` are not the worker `routing` section, which does not apply
  to a review.
- The operator's view is [letting the Controller run the external review](../run.md#letting-the-controller-run-the-external-review).

## Also in this release

- **Workers use `command rm -f` and `command cp -f`.** The worker lifecycle note now says so, so an
  `rm -i` or `cp -i` alias in the operator's shell cannot make a background command wait for an
  answer (follow-up 24). This changes every Claude worker's prompt by that one line, whether or not
  the reviewer is configured. A script of your own that a worker runs needs the same.

## Known limitations

- **Only Codex is registered.** Any other `reviewer.harness` value is refused.
- **Pinned to `codex-cli 0.162.1`.** The boundary was captured against that version
  (`tests/harness_contract/codex/`). A Codex release that renames a feature, a configuration layer or
  a state entry stops the launch, naming it, until the pinned set is updated.
- **Not yet captured from a real run:** a usage-limit event, refresh-token rotation, and a way to
  relocate `/etc/codex` (which is therefore required to be absent or empty).
- **A limit during the job is not waited out in place.** The job ends `INCOMPLETE` and a new `run`
  re-admits after the reset; an in-run wait is C8b.
- **The Workflow-side paragraph is pending.** The Workflow confirmed the courier reading with five
  conditions (workflow#28, recorded in ADR 0013); the protocol paragraph that names it ships with
  Workflow 2.12.0 (W8).
- Implementation and planning workers stay Claude-only; the functional review is C10, which reuses
  this seam.

## Upgrading

The settings file moves from generation 5 to generation 6 automatically the first time `step` or
`run` fills it; your own values are kept. A 1.9.x Controller sharing the file afterwards warns about
the unknown `reviewer` section and ignores it. With `reviewer.harness` unset nothing else changes.
Install 1.10.0 as you installed 1.9.0 (see the [update page](../update.md)).

**Downgrading.** A review job record (job `schema_version` 2) cannot be read by 1.9.0 or earlier,
which refuse it. `resume` any unsettled review job with 1.10.0 before you downgrade; see
[compatibility](../compatibility.md#downgrading-after-a-review-job).

**Lanes that run the review by hand.** A lane that opts in should stop running `codex exec` itself at
these two gates for a Controller-driven repository. This is a lane change outside this repository.
