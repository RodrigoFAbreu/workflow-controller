## A usage limit reached mid-job is waited out (1.11.0)

**A run that meets the usage limit half way through a job no longer just fails.** The usage budget
(1.8.0) forecasts a job and holds it back if it would not fit, but a forecast can be wrong and other
lanes share the account, so a worker can still reach the provider's limit while it runs. Until now
such a job ended `FAILED` and the run stopped with exit 30, although nothing the operator did was
wrong. From 1.11.0, a job that reached the limit before it changed anything is recorded as
interrupted, `run` waits for the reset, and the step is repeated.

**How the limit is recognised.** Only from structured fields of the worker's stream, all three
required:

- a `rate_limit_event` whose status is `rejected`;
- a final `result` that is an error with API status 429;
- a finite reset time (`resetsAt`).

Text such as "You've hit your session limit" never counts, because it is localised and can be
reworded. An earlier `rejected` event followed by a successful turn does not count either. The fact
(the reset time and, when known, the window: `five_hour` or `weekly`) is kept in the job's stream
diagnosis with the reason `usage_limit`. A limit type the Controller does not map is still a limit;
its window is shown as `unknown`. See
[how a usage limit is recognised](../guide/workers.md#how-a-usage-limit-is-recognised).

**What counts as "changed nothing".** The job is `INTERRUPTED` (reconciliation code
`UsageLimitReached`) only when all of these are unchanged since the launch:

- the phase (in protocol mode the Workflow's `reconcile` must also answer `no_progress`);
- `HEAD`, so no commit;
- every dirty tracked path: its status entry, its worktree bytes, its executable bit and its staged
  blob. A second edit of a file that was already dirty, a partial staging and a `chmod` all count as
  changes. Untracked files do not count.

Any other limited job stays `FAILED` (exit 30) and carries the limit in its
`reconciliation_evidence`, so you can see why it stopped. That includes a job whose transition was
already verified when the limit hit. Repeating a step over half-done work is left to the Workflow and
to a later step (C12).

**What `run` does with it.** It waits for the reset plus `usage.resume_grace_seconds` (180 s by
default), the same pause as before a job: no lock is held, `usage_paused` is recorded and notified,
and the wait is bounded by `usage.max_wait_seconds`. This happens whether or not `usage.enabled` is
on. It then repeats the step through the whole orchestration boundary (fresh state, fresh decision,
fresh admission). The interrupted attempt uses no step of `--max-steps`. Three limited attempts in a
row, with no finished step between them, stop the run, so a reset time the provider never honours
cannot make it spin.

## Outcomes

| case | exit | what it says |
|---|---|---|
| `step`, the job reached the limit and changed nothing | 17 | "stopped at the usage limit reached mid-job: the worker ran and changed nothing, so the step can be repeated", the reset time, and that a new `step` or `run` repeats it |
| `run`, the reset is farther away than `usage.max_wait_seconds` | 17 | the same start, the reset time, and "run again after it"; nothing is slept |
| `run`, three limited attempts in a row | 17 | the same start, and that the reported reset time is not trusted: check the clock and the usage reading |
| the job reached the limit after it had changed state | 30 | an ordinary failed outcome, with the limit in the evidence; not repeated |
| `step` or `run`, a job recorded `INTERRUPTED` without a limit (for example a protocol job whose worker timed out having changed nothing) | 40 | the job was interrupted and changed nothing; a new `step` repeats it |
| `resume` reconciles a limited record to `INTERRUPTED` | 40 | as before, and the line now names the reset time |

No new exit code was added: a script that already handles 17 as "wait, then run again" is right for
the mid-job case too. None of the 17 lines above says "nothing was started", because a worker did
run. Ctrl-C during the mid-job wait prints one line that says the same. See
[exit codes](../exit-codes.md) and
[a worker hit a usage limit while it ran](../common-problems.md#a-worker-hit-a-usage-limit-while-it-ran).

## Configuration

None. `usage.resume_grace_seconds` and `usage.max_wait_seconds` already existed (1.8.0); the
settings file stays at table generation 6.

## Also in this release

- **The first job after a five-hour reset is measured.** A job admitted after the window had reset
  was charged conservatively and gave no forecast sample, because the stored reading belonged to the
  old window (a follow-up from the C8 review). Its first reading in the new window is now its
  baseline, so its usage is measured and feeds the forecast. A job admitted before the reset keeps
  the conservative charge. No ledger or reservation format changed.
- **`step` and `run` no longer crash on an `INTERRUPTED` job.** In protocol mode a timed-out or
  signalled worker that changed nothing could end a job `INTERRUPTED`, which `step` and `run` had no
  exit code for (they raised `KeyError`). They now exit 40, the code `resume` uses for the same
  status.
- **Every job records its tracked-change baseline.** The job record's pre-state gains
  `tracked_changes`, and the record may carry a `usage_limit` block. Taking the baseline costs one
  extra read-only `git ls-files --stage -z` per launch; no hook or filter runs. See
  [the runtime guide](../guide/runtime.md).
- **A lifecycle scenario covers it.** `scenario-usage-limit-mid-job-waits-and-repeats` replays a
  sanitised real limited stream through a fake worker, waits and repeats the step; see
  [lifecycle scenarios](../guide/development.md#lifecycle-scenarios).

## Known limitations

- **A limited job that changed state is not repeated.** It ends `FAILED` (exit 30). Of the two real
  limited streams this was built from, the plan-review one is the case that is now repeated; the
  sixteen-minute implementation one most likely left tracked edits and would still fail.
- **Only Claude workers.** The Codex reviewer (1.10.0) still ends `INCOMPLETE` (exit 35) at its own
  limit, and a new `run` re-admits after the reset.
- **`explain` does not show an ordinary limited failure** (ROADMAP follow-up 30):
  `controller/observe.py` filters out a stream diagnosis whose only reason is `usage_limit`. The
  limit is in the job record and in the exit-30 evidence.
- **Recognition depends on Claude's stream format.** If the provider renames these fields, the job
  is an ordinary failure again, as in 1.10.0; it is never wrongly repeated.

## Upgrading

Nothing to do. The job record keeps `schema_version` 1 (a review job stays at 2), and the settings
file is unchanged. Install 1.11.0 as you installed 1.10.0 (see the [update page](../update.md)).

**Downgrading.** 1.10.0 reads the records 1.11.0 writes: it ignores the new `tracked_changes`
pre-state member and the `usage_limit` block. A pending job it reconciles is judged by the 1.10.0
rules, so a limited job ends `FAILED` there instead of `INTERRUPTED`.
