## A review loop stops at a round cap (1.12.0)

**An unattended run no longer reviews a stage for ever.** Review loops took about 65% of worker usage
over six milestones, and plans took 11 to 16 local review rounds each, because the Controller kept
launching review and apply workers for as long as the Workflow called them automatic. From 1.12.0 a
protocol target's plan stage and implementation stage each stop at a **round cap**
(`review.round_cap`, default 4). At the cap the Controller launches nothing and stops at a gate that
says which stage, which round and what you can do. It never accepts at the cap itself.

**Where the round comes from.**

- On Workflow 2.12.0 and later, from the Workflow: its `next-action` answer carries `review_round`
  per stage (protocol 1.4). The gate says the round was "given by the Workflow".
- On an older Workflow, or when the Workflow gives no number, the Controller counts it from its own
  job records of that repository and work item. For the implementation stage the count is 1 plus each
  rise of `implementation_revision`, the same field the Workflow uses. For the plan stage it is the
  number of distinct `plan_revision` values seen at a plan-review phase. That plan count is a **lower
  bound**: the Workflow counts published contents, and a plan round can publish new content without
  raising `plan_revision`. So the cap can fire later than the Workflow's own number would, never
  earlier. The gate then says the round was "counted from the Controller's job records" and, for the
  plan stage, that the Workflow's own count may be higher.

A republication that leaves the revision unchanged (`same_content`) is not a new round. A bounded
functional-review fix raises `implementation_revision`, so it counts toward the implementation round.

**What is stopped, and what is never stopped.**

| action | stopped when |
|---|---|
| `plan.apply_review`, `implementation.apply_review` | the round is at the cap or above (applying would open the round after the cap) |
| `plan.review.local`, `implementation.review.local` | the round is above the cap |

Nothing else is stopped: authoring, implementing, self-review, recording a manual verdict and the
external review the Controller can run itself (1.10.0) all go on as before. A target on Workflow
2.5.1 or 2.6.0 (the legacy path) is not capped. When the loop guard (`no_progress_repeated`) and the
cap both apply, the loop guard's gate is the one shown.

**The gate.** `step` or `run` exits `10`, the ordinary gate status, with the reason code
`review_round_cap_reached`. No worker is launched, nothing is written to the Workflow's state, and the
stop is one `GATE_BLOCKED` job record, which no round count, loop guard or telemetry row includes. The
text reads, for example:

```text
review_round_cap_reached: <item> is at plan review round 4 (given by the Workflow), at the round cap
of 4 (review.round_cap), so plan.apply_review is not launched. ...
```

and then names the three ways on, in this order:

1. **Raise the cap and run again**: `workflow-controller run --review-round-cap N <repo>`, or set
   `review.round_cap`. The flag applies to that one command, so the next plain `run` stops again at the
   next capped action of the item.
2. **Accept at the cap** with `/approve-review`, where the Workflow's gate is reachable (after a
   `REVISE`, with the confirmation it asks for). This is a person's step.
3. **Withdraw and re-scope** with `/milestone-plan <work-item-id>`.

The stop fires on any `REVISE` at the cap. It does not try to tell "only minor findings left" apart:
since Workflow 2.12.0 a `REVISE` must name a Blocking or Important finding, and a verdict with only
minor findings is an `APPROVE`. See
[a run stopped at the review round cap](../common-problems.md#a-run-stopped-at-the-review-round-cap).

**`explain`** prints the same gate text as the step would, with the setting's cap. It has no
`--review-round-cap` flag, so a cap you raised on one command is not shown there.

## Rounds and usage per stage in `telemetry`

Each job row now carries `action` (the protocol action id), `stage` (`plan`, `implementation`,
`functional` or `none`), `round` and `round_source` (`workflow` or `jobs`). They are worked out from
the job records when `telemetry` runs and never written back. A job's round is the same with and
without `--since`. `--by` gains four groupings:

| `--by` | groups the jobs by |
|---|---|
| `action` | the kind of step, for the cost of each |
| `stage` | plan, implementation, functional or none |
| `stage,round` | stage and round: `stage=plan, round=4` for a round the Workflow gave, `stage=plan, round=4~` for one counted from job records, always in separate groups |
| `work_item,action` | work item and kind of step |

Only plan and implementation jobs have a round. The existing groupings (`role`, `model`,
`role,model`) print the same jobs as before in the same form (but see the reviews the Controller ran
itself, below), and the JSON rows gain only the four new keys.

**Comparing before and after.** Jobs recorded before 1.12.0 carry no `review_round`, so their rounds
are counted and shown with `~`; jobs recorded on Workflow 2.12.0 afterwards carry the Workflow's
number. A `~` plan round is a lower bound and not the same measure, so compare `~` groups with `~`
groups. To split the figures at a date:

```bash
workflow-controller telemetry --by stage,round --since 2026-10-01
workflow-controller telemetry --by stage,round --since 2026-10-17
```

`--since` keeps the jobs created at or after the date, so the second query is the "after" and the
"before" is the first query minus the second. See [the runtime guide](../guide/runtime.md) and
[`telemetry`](../guide/commands.md#telemetry).

## Configuration

| setting | type | default | bounds | flag |
|---|---|---|---|---|
| `review.round_cap` | integer | `4` | 1 to 100 | `--review-round-cap N` on `step` and `run` |

The flag wins for that command; a value outside 1 to 100 is a usage error (exit `2`). There is no
"off" value: a long loop is a cap of 100. The settings file moves to table generation 7: the first
1.12.0 command that writes it, such as `step` or `run` (a read-only command such as `explain` only
reads it), adds the `review.round_cap` row with its default, and moves nothing else.

## Also in this release

- **`telemetry` lists the reviews the Controller ran itself.** A Codex review job (with
  `reviewer.harness` set) keeps no worker stream, so `telemetry` used to skip it. It is now a row with
  its action, stage and round, counted as "telemetry unavailable". On a runtime that holds such jobs,
  the job counts include them, so they are higher than under 1.11.0; no figure of theirs is added to
  a total.
- **A lifecycle scenario covers the cap.** `scenario-review-round-cap-stops-and-continues` runs a
  plan loop with `run --review-round-cap 1`, checks that `explain` prints the same gate, then continues
  with `--review-round-cap 2` to the next stop; see
  [lifecycle scenarios](../guide/development.md#lifecycle-scenarios).

## Known limitations

- **A plan round counted from job records is a lower bound**, as described above: on a Workflow older
  than 2.12.0 the plan cap fires late.
- **The plan cap has no effect on a `"1"`-governed work item** unless it is 1
  ([#67](https://github.com/RodrigoFAbreu/workflow-controller/issues/67)). Such an item's plan-review
  phase is not one the count reads, and Workflow 2.12.0 gives no plan round for it, so its plan round
  always reads 1.
- **A review the Controller ran itself always shows a `~` round**, even on Workflow 2.12.0, because
  it stores no decision snapshot; the local reviews and applies around it show the Workflow's number.
  The runtime guide does not say this yet, and its before-and-after steps are looser than the ones
  above ([#64](https://github.com/RodrigoFAbreu/workflow-controller/issues/64)).
- **Working out the rounds takes time that grows with the square of the number of job records**
  ([#63](https://github.com/RodrigoFAbreu/workflow-controller/issues/63)). The figures are right; it
  took 0.22 s over 1745 records.
- **Two test gaps:** no test drives the cap with a real Workflow 2.12.0 answer (the lifecycle tests use
  the vendored 2.7.0, so they cover only the counted round,
  [#65](https://github.com/RodrigoFAbreu/workflow-controller/issues/65)), and no test pins the
  Controller's copy of the plan-review phases
  ([#66](https://github.com/RodrigoFAbreu/workflow-controller/issues/66)).
- **The gate has no exit code of its own.** It exits `10` like every gate; the reason code
  `review_round_cap_reached` tells it apart.

## Upgrading

The cap is **on by default**. An item whose loop is already at round 4 or past it stops at its next
capped action (the table above) the first time 1.12.0 runs it; raise the cap to continue.
To keep a lane's runs as they were under 1.11.0, set `review.round_cap` to 100 in the settings file.

Nothing else changes: the job record keeps `schema_version` 1 (a review job stays at 2) and gains no
field. Install 1.12.0 as you installed 1.11.0 (see the [update page](../update.md)).

**Downgrading.** 1.11.0 reads the job records 1.12.0 writes; a cap stop is an ordinary `GATE_BLOCKED`
record to it. A 1.11.0 Controller sharing the generation-7 settings file warns about the unknown
`review` key, ignores it, and its `settings clean` refuses, because the file was last filled by a newer
release. Under 1.11.0 a review loop is not capped.
