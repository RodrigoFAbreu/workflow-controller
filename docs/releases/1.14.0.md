# Workflow Controller 1.14.0

[Back to the documentation map](../README.md)

These notes were written after the release from the archived narrative
(`docs/milestones/completed/workflow-controller-gate-policy.md`) and the plan
(`docs/ai-workflow/CONTROLLER_GATE_POLICY_PLAN.md`, revision 5). The milestone was
`workflow-controller-gate-policy` (ROADMAP C10a, the first of the three gate-policy steps), accepted on
2026-10-17 by gate policy. It was released from pull request #81 (squash `8a38a85`).

## A satisfied gate passes without a person (1.14.0)

**The Controller now runs the Workflow's gate-policy validations itself.** On Workflow 2.8 and later,
plan approval, technical approval and acceptance follow the repository's gate policy. When a gate is
automatic, the Workflow answers with the disposition `validation` and one of the action ids
`plan.satisfy`, `implementation.satisfy` or `acceptance.satisfy` (rows 14a, 28a and 38h). Earlier
Controllers did not know that disposition, so every run stopped there and a person ran `/satisfy-gate`
by hand. 1.14.0 launches `/satisfy-gate plan <id>`, `/satisfy-gate implementation <id>` or
`/satisfy-gate acceptance <id>` as a worker, as it launches a review, and the run goes on when the gate
is satisfied.

- **The Workflow decides; the Controller only launches.** It launches only those three action ids,
  only under the disposition `validation`, only for a worker the Workflow marks as a `validator` and
  never for a `user_only` one. Anything else is blocked before a launch, as an unknown value always
  was. The Controller reads no `GATE_POLICY.json` and checks no requirement itself: that is
  `/satisfy-gate`'s job. A human gate still stops for a person.
- **A new routing role, `satisfy-gate`:** Opus (`claude-opus-5-5`) at `xhigh`, single-agent (the
  `Skill`, `Agent` and `Workflow` tools are disallowed), because the validation records a decision in a
  transaction that commits and must not hand it on. Change it like any role, with
  `--role-model satisfy-gate=...`, `--role-effort satisfy-gate=...`, a `--routing-config` file or the
  settings file (see [the role table](../guide/commands.md)). `telemetry --by role` groups these jobs
  under the name.
- **A refused validation is a stop, not an approval.** When a requirement is unmet, `/satisfy-gate`
  writes nothing and the phase stays where it was. The step ends with no progress and sends only
  `step_done`. Two such steps in a row stop the run at `no_progress_repeated` before a third launch.
  `explain` shows the unmet requirement from the worker's report after the first refusal (the text
  output, and `last_worker_report` with `--json`); once the loop guard has stopped the run, the report
  is part of the gate's `what_is_required`.
- **`approval_recorded` means an approval was recorded.** It is sent for a `/satisfy-gate` job only when
  the work item's phase moved, and `milestone_accepted` only when it reached `MILESTONE_COMPLETE`.

**What changes for an existing repository.** On Workflow 2.8 or later, a run no longer stops at an
automatic gate whose policy is satisfied: the Controller records the approval or the acceptance, each
with a paid Opus worker. By default all three gates are automatic for a version 2.2 work item, and fewer
for an older one (the [run page](../run.md) lists them). A repository on Workflow 2.7 or earlier, and a
human gate, behave as under 1.13.1. To keep a gate with a person, make it human in the gate policy (see
"Human gates" on the run page).

## A protocol minor release no longer refuses the answer

**A value a protocol 1.x minor release adds is handled, not refused.** Before 1.14.0, a value that the
vendored protocol schema's closed enums did not list (as the `warn` check status of protocol 1.1 once
was) made the whole answer "outside the protocol" (exit 20). Now `protocol_schema.ENUM_RULES` gives each
of the schema's twenty enum locations a rule for such a value:

| Rule | What happens | Examples |
|---|---|---|
| `advisory` | shown, changes nothing | a new `verify` check status, shown like a `warn` line |
| `blocked` | the step stops naming the value | a new action id, worker role or disposition: a blocked gate before any launch, as before; a new reconcile class or record stage, which arrives after the worker ran: the job ends `FAILED` with the evidence reason `workflow_unknown_value` |
| `ignored` | the Controller reads no decision from it | the policy gate and mode, the forge source, the functional-evidence status |

Only a protocol major change is still refused. A test fails if the vendored schema holds an enum location
the table does not name, so a later schema cannot add one unclassified. The design is recorded in
[ADR 0015](../adr/0015-gate-policy-validations-and-open-enums.md), and the rule is described in
[Protocol mode](../guide/automation.md#protocol-mode-workflow-27-and-later).

## A blocker is not a request for a decision

**A stop the Workflow itself calls blocked sends `lane_blocked`, not `user_gate`.** A job that ends
`GATE_BLOCKED` on a Workflow answer whose disposition is `blocked` sends the `lane_blocked` notification,
titled "Blocked: <work item>", because no person's decision is asked for. A human gate, an external gate
(for example a pull request whose checks are still running), a legacy target and the Controller's own
gates (the round cap, a merge left to a person, a usage pause) still send `user_gate`.

## Also in this release

- The advisory of `inspect` and `explain` that lists the action ids this release cannot launch (and
  `unknown_action_ids` in `inspect --json`) no longer names the three `.satisfy` ids. `pr.apply_review`
  is still listed: it is not launched yet.
- The guides, the compatibility page, the common-problems page and the run page say what the
  Controller now does at an automatic gate.

## Configuration

No setting is added. The new routing role is set like the others:

| role | built-in route | override |
|---|---|---|
| `satisfy-gate` | `claude-opus-5-5` at `xhigh`, single-agent | `--role-model satisfy-gate=...`, `--role-effort satisfy-gate=...`, a `--routing-config` file, or `routing.roles.satisfy-gate` in the settings file |

The settings file moves to table generation 9 because of the new role name. It adds no key and moves no
value; the first 1.14.0 command that writes the file records `"_table_generation": 9`. An older Controller
sharing the file uses it as before. It warns only about a key it does not know, such as an entry for
`satisfy-gate` under `routing.roles`, which it ignores, and its `settings clean` refuses (run that from
the newest installed release). An older Controller refuses the role in a `--routing-config` file and in
`--role-model`.

## Known limitations

- **Some automatic acceptance stops still need a person.** The Workflow can still answer with a gate the
  Controller cannot satisfy yet, and it sends `user_gate` there: functional evidence (row 38e,
  `functional_evidence_needed`, until the automated functional review); pull request evidence and
  approval (rows 38f and 38g, `pr_evidence_needed` and `pr_approval_needed`); and `pr.apply_review`
  (row 38d), which this release does not launch. The pull request rows wait for the pull request defect
  loop.
- **The pull request evidence stop does not clear itself.** Once a refused `/satisfy-gate acceptance` has
  stored a pull request whose checks were pending, the answer stays `pr_evidence_needed` after the checks
  turn green. Run `/satisfy-gate acceptance <id>` by hand, as the [run page](../run.md) says. Reporting a
  fresh `pr_review_result` does not help: the Workflow then answers `pr.apply_review`, which is not
  launched.
- **The Controller's vendored schema is still Workflow 2.9.0's.** The enum Workflow 2.12.0 adds
  (`review_round.current`) is classified when a later step moves the schema; the test over the schema
  then holds it.
- **The milestone's flows used fake workers.** A real `/satisfy-gate` worker and a real GitHub query were
  not exercised by them; this repository's own acceptance was a real one.
- **Minor review findings kept for the next clean-up milestone:**
  - a validation's evidence line says `(automatic)`, not `(validation)`
    ([#83](https://github.com/RodrigoFAbreu/workflow-controller/issues/83));
  - a refusal report loses its unmet requirement when "unmet:" appears again after the list, which
    affects only the `explain` diagnostic
    ([#84](https://github.com/RodrigoFAbreu/workflow-controller/issues/84));
  - the compatibility page's 1.7.1 note reads as if no release launches `/satisfy-gate`
    ([#85](https://github.com/RodrigoFAbreu/workflow-controller/issues/85));
  - a docstring in `controller/job.py` describes four return values where there are five
    ([#86](https://github.com/RodrigoFAbreu/workflow-controller/issues/86));
  - the automation guide does not say that the worker report moves to `gate.what_is_required` once the
    loop guard stops the run ([#87](https://github.com/RodrigoFAbreu/workflow-controller/issues/87)).
- **A test flakes under load** ([#82](https://github.com/RodrigoFAbreu/workflow-controller/issues/82)):
  `test_killed_and_broken_pipe_followers_leave_the_worker_and_exit_code_alone` can end with exit -14
  (`SIGALRM`); test only.

## Upgrading

Install 1.14.0 as you installed 1.13.1 (see the [update page](../update.md)). Read "What changes for an
existing repository" above first: under automatic gates the Controller now records approvals and
acceptance itself, and each validation is a paid Opus worker. An orchestrating session that ran
`/satisfy-gate` by hand at these stops no longer needs to. A lane that alerts on `user_gate` gets
`lane_blocked` for a stop the Workflow calls blocked. The job records keep their schema versions (1, and
2 for a review job).

**Downgrading.** 1.13.1 reads the job records and the settings file 1.14.0 writes. It stops again at every
automatic gate (`workflow_unknown_disposition`), refuses a `--routing-config` file or `--role-model` that
names `satisfy-gate`, ignores that role in the settings file with a warning, and its `settings clean`
refuses a file 1.14.0 filled.
