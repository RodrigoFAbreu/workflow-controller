## A pull request's state reaches the Workflow without a person (1.15.0)

**The Controller now closes the pull request rows of an automatic acceptance gate itself.** Under 1.14.0 a
run stopped wherever the Workflow needed a pull request fact (rows 38f and 38g) or a pull request defect
applied (row 38d). 1.15.0 handles all three. The design is recorded in
[ADR 0016](../adr/0016-pull-request-report-and-apply.md) and described in
[The pull request defect loop](../guide/automation.md).

- **A reporter, not a worker (rows 38f and 38g).** For a work item with a milestone-branch binding and a
  pull request, the Controller runs the Workflow's one fixed `gh pr list` query for the item's anchor
  commit and hands the verbatim output to the Workflow with `record-external-result --kind
  pr_review_result`. It parses nothing and records nothing itself: the Workflow reads the result. The step
  is a Controller step with its own job record (kind `pr_report`), not a paid worker.
- **A vetted `gh`.** The reporter uses a `gh` vetted like the Workflow's resolver: never one inside a
  repository, inside a second worktree of it, or in a world-writable place. A repository therefore cannot
  fake an approval with its own `gh`.
- **A report that would change nothing is not made.** A query output equal to the last one sent is not sent
  again: the step stops `pr_report_unchanged`. A person waiting on an approval may see one refused
  `/satisfy-gate acceptance` worker after such a report, because the Workflow then answers row 38h before it
  returns to 38g.
- **Pending checks are waited for only by `run`.** When the checks are pending and `ci_green` is the one
  thing the Workflow waits for, `run` polls within `merge.wait_seconds` at `merge.poll_seconds`. `step` never
  waits: it stops `pr_checks_pending`, naming the pending checks ("no checks reported" when there are none).
  Pending checks never hide anything else: an approval in a repository without CI, and a
  `CHANGES_REQUESTED` objection, are reported at once even while checks are pending.
- **`pr.apply_review` is launched (row 38d).** It runs as `/apply-pr-review <id>` on the new
  `apply-pr-review` role, only for a worker the Workflow marks as `applier`. The Workflow's command chooses
  the branch: it refreshes the fact so acceptance can pass, or, for a red pull request, a
  `CHANGES_REQUESTED` decision or a changed head, it reopens the same work item into remediation, and the
  item comes back to acceptance afterwards. The Controller reads no fact and chooses no branch. A
  `user_only` worker, a wrong role, a changed invocation or a missing work item is blocked with its code.
- **A person is asked only where one is needed:** row 38g with the approval still missing, row 38g under a
  human acceptance gate (the Controller reports nothing there; `/accept-milestone`), a stop the Controller
  itself ends in (`pr_report_no_pull_request`, `pr_report_forge_unavailable`, `pr_report_refused`,
  `pr_report_stale`) and row 38e (functional evidence, still C10c).

**What changes for an existing repository.** On Workflow 2.8 or later, under an automatic acceptance gate,
a run no longer stops for a pull request whose checks were pending, or whose defect the Workflow can apply:
it waits (under `run`), reports and goes on, and `/apply-pr-review` is a paid Opus worker. A repository
without a milestone-branch binding keeps the old row 38f stop, and a human acceptance gate keeps its stop.
This also removes the 1.14.0 limitation that a `pr_evidence_needed` stop did not clear itself after the
checks turned green.

## Notifications

- A wait for CI alone sends no request: a step that did not wait ends `pr_checks_pending` with no
  notification.
- A `run` whose `merge.wait_seconds` budget ran out with only the checks pending sends `lane_blocked`.
- A reported result sends `step_done`. Only the stops that need a person send `user_gate`.

## Configuration

No setting is added. The new routing role is set like the others:

| role | built-in route | override |
|---|---|---|
| `apply-pr-review` | `claude-opus-5-5` at `xhigh`, not single-agent | `--role-model apply-pr-review=...`, `--role-effort apply-pr-review=...`, a `--routing-config` file, or `routing.roles.apply-pr-review` in the settings file |

The settings file moves to table generation 10 because of the new role name. It adds no key and moves no
value; the first 1.15.0 command that writes the file records `"_table_generation": 10`. An older Controller
sharing the file uses it as before. It warns only about a key it does not know, such as an entry for
`apply-pr-review` under `routing.roles`, which it ignores, and its `settings clean` refuses (run that from
the newest installed release). An older Controller refuses the role in a `--routing-config` file and in
`--role-model`.

## Known limitations

- **A red pull request after acceptance is not looped.** In the merge flow of the milestone-branch
  workflow, a pull request that turns red still ends at that flow's `checks_failing` stop, with a person.
  Looping it is step C10d of the [roadmap](../ROADMAP.md).
- **Row 38e still needs a person.** Functional evidence (`functional_evidence_needed`) stays a stop until
  the automated functional review (C10c).
- **The milestone's flows used fakes.** A real `/apply-pr-review` worker and a real GitHub query were not
  exercised by them; this repository's own acceptance was a real one. Its flows 1-8 and 10-12 passed, and
  flow 9 (notification wiring) was re-tested outside the tester's sandbox.
- **Minor review findings kept for the next clean-up milestone (CU2):**
  - `pr_report.pending_checks` finds the `ci_green` requirement by a plain substring over the stop text,
    not by its `ci_green:` token; the current Workflow text cannot trigger it
    ([#93](https://github.com/RodrigoFAbreu/workflow-controller/issues/93));
  - the tests of the Controller's `gh` vetting assert only the exception, not the "world-writable" message,
    lack a world-writable executable case and carry stray blank lines
    ([#94](https://github.com/RodrigoFAbreu/workflow-controller/issues/94));
  - `Context.forge` spots the real forge with an always-true `getattr(forge, "vet_root", False) is None`;
    clarity only ([#95](https://github.com/RodrigoFAbreu/workflow-controller/issues/95)).
- **Two tests fail locally under Git 2.56** (`test_release_notes`, `test_pull_request_lifecycle`) and one
  flakes under load ([#82](https://github.com/RodrigoFAbreu/workflow-controller/issues/82)); test only.

## Compatibility

Controller 1.15.0 is checked against Workflow 2.13.0 (the milestone's flow 12 repeated the nine lifecycle
scenarios on the installed 2.13.0 with no difference) and against Workflow 2.12.0, whose test tree the
Controller vendors. See the [compatibility page](../compatibility.md).

## Upgrading

Install 1.15.0 as you installed 1.14.0 (see the [update page](../update.md)). Read "What changes for an
existing repository" above first: the Controller now reports the pull request's state and launches
`/apply-pr-review` itself, and the latter is a paid Opus worker. An orchestrating session that ran
`/satisfy-gate acceptance` by hand at a `pr_evidence_needed` stop no longer needs to. The job records keep
their schema versions (1, and 2 for a review job).

**Downgrading.** Checked against the 1.14.0 code: 1.14.0 reads the settings file and the job records
1.15.0 writes. A `pr_report` job record carries schema version 1 and is not a review record; 1.14.0's
`telemetry` and job listing read it without error and count it as no worker job. 1.14.0 ignores a
`routing.roles.apply-pr-review` entry with a warning, refuses that role in a `--routing-config` file and in
`--role-model`, and its `settings clean` refuses a file 1.15.0 filled. It stops again at rows 38d, 38f and
38g, as 1.14.0 did. Not exercised: a full `status`, `explain` or `resume` of 1.14.0 over a repository
holding a `pr_report` record.
