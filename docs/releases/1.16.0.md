## `/satisfy-gate` is routed by stage (1.16.0)

**The three automatic approvals no longer share one model.** Under 1.14.0 and 1.15.0 a single `satisfy-gate` role ran
plan approval, technical approval and acceptance at Opus `xhigh`. 1.16.0 splits it by what the worker does
([#91](https://github.com/RodrigoFAbreu/workflow-controller/issues/91)):

| role | stages | built-in route | single-agent |
|---|---|---|---|
| `satisfy-gate` | `plan.satisfy`, `implementation.satisfy` | `claude-haiku-5-5` at `high` | yes |
| `satisfy-gate-acceptance` | `acceptance.satisfy` | `claude-sonnet-5-5` at `medium` | yes |

Plan and technical approval are a mechanical check and one transaction. Acceptance does more: it writes the
milestone narrative, the roadmap and `ACTIVE_MILESTONE` edits and the table of minor findings.

**Proven before release.** In an isolated scratch installation, one real Haiku 5.5 `high` plan approval and one real
Sonnet 5.5 `medium` acceptance were run. Both completed their transaction and were verified.

Both roles are set like the others: `--role-model`, `--role-effort`, a `--routing-config` file, or
`routing.roles.<role>` in the settings file.

## Configuration

No key is added and no value moves. The new routing role is set like the others (see above).

The settings file moves to table generation 11 because of the new role name; the first 1.16.0 command that writes
the file records `"_table_generation": 11`. An older Controller sharing the file uses it as before. It warns only
about a key it does not know, such as an entry for `satisfy-gate-acceptance` under `routing.roles`, which it
ignores, and its `settings clean` refuses a file a newer release filled (run that from the newest installed
release). An older Controller refuses `satisfy-gate-acceptance` in a `--routing-config` file.

## Known limitations

- **A value pinned for `satisfy-gate` now covers two stages.** An owner who pinned a model or effort for
  `satisfy-gate` under 1.14.0 or 1.15.0 set it for all three stages. It now applies to plan and technical approval
  only. Acceptance takes its own built-in route (Sonnet 5.5 `medium`) until you name `satisfy-gate-acceptance`.
- **Not part of this release:** the two review round caps
  ([#88](https://github.com/RodrigoFAbreu/workflow-controller/issues/88)) wait for a Workflow release that counts
  local and external rounds separately (workflow#43).
- **One minor review finding is kept** as [#100](https://github.com/RodrigoFAbreu/workflow-controller/issues/100):
  `fake_claude` writes the hang-child pid file without an atomic rename, which can leak a test helper under load
  (test only).
- **Two tests fail locally under Git 2.56** (`test_release_notes`, `test_pull_request_lifecycle`); test only.

## Compatibility

Controller 1.16.0 speaks the same protocol (1.4) as 1.15.0. This repository runs Workflow 2.14.0 and CU2 was
accepted on it. See the [compatibility page](../compatibility.md).

## Upgrading

Install 1.16.0 as you installed 1.15.0 (see the [update page](../update.md)). Read "A value pinned for
`satisfy-gate` now covers two stages" above first if you set a route for that role. The job records keep their
schema versions.
