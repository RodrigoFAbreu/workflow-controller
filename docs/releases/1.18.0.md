## The functional review runs itself (1.18.0)

**At row 38e the Controller runs the committed checklist in an isolated tester.** Under an automatic acceptance gate
it no longer stops for a person to test the head. It runs a `functional_test` job: an independent Claude tester inside
Claude Code's bubblewrap sandbox. The sandbox is a fresh clone of the item's branch whose `origin` is a scratch bare
repository, with a fake `gh`, `claude`, `codex` and `ssh` first on `PATH` (each logs its arguments and refuses), a
scratch home, no network and no Unix socket. The tester's `TMPDIR` is a short private `wcf-*` folder under
`$XDG_RUNTIME_DIR` or `/tmp`.

**One result per flow.** The tester writes one entry per checklist flow. The Controller checks that the real
repository, its origin and the job's private Claude home are unchanged, then records one `functional_evidence` per
flow. When every flow passed, acceptance by policy follows. When a flow failed as a `defect`, the Controller writes
`FUNCTIONAL_REVIEW.md` for `/apply-functional-review` and the item goes round again. A flow that failed as
`environment` (it could not run in the sandbox) is recorded and stops at `flows_not_runnable`.

**New stops.** `functional_tester_unavailable`, `checklist_unrecognised`, `results_invalid` (the stop text quotes the
tester's final message), `isolation_breach`, `tested_bytes_unbound`, `recording_refused`, `functional_unchanged` and
`functional_rounds_exhausted` (three tester runs ended in findings). Each message names its remedy. See
[the automated functional review](../guide/automation.md#protocol-mode-workflow-27-and-later) and
[the run stopped at the functional review](../common-problems.md#the-run-stopped-at-the-functional-review-row-38e).

**`explain` shows the plan.** At row 38e it prints the head, the checklist, the flows, the previous tester job and the
`.gitignore` patterns the sandbox does not make writable.

## Requirements

The tester needs `bubblewrap` (`bwrap`), `socat`, a kernel that accepts a seccomp filter and a `claude` build whose
SHA-256 is in `VERIFIED_NATIVE_BUILDS`. In 1.18.0 that is only Claude Code 2.1.303. Any other build, a launcher or a
script-launched `claude` stops at `functional_tester_unavailable` before any launch, and a person reviews by hand.

## Configuration

The settings table is now generation 13. It adds `functional.automated` (default `true`; `false` keeps the person's
stop at row 38e) and `functional.timeout_seconds` (default 3600, 60 to 86400), and the routing role
`functional-tester`, to a file filled by an earlier release. An older Controller that shares the file warns about the
unknown keys. See the [runtime guide](../guide/runtime.md).

## Known limitations

- **Pull-request flows are unsupported in the sandbox.** Such a flow is `environment` and ends at
  `flows_not_runnable` until a person runs it.
- **A copy edited under the tester's own `TMPDIR` is not detected.** The prompt forbids it, and the record names the
  digest, reporter and run reference for an audit.
- **`passed` is the tester's report**, trusted as the Workflow trusts a person's.
- **Open follow-ups** (ROADMAP follow-ups 67 to 74):
  [#112](https://github.com/RodrigoFAbreu/workflow-controller/issues/112) (probe the tester before usage admission),
  [#113](https://github.com/RodrigoFAbreu/workflow-controller/issues/113) (verify a newer `claude` build; planned
  next), [#114](https://github.com/RodrigoFAbreu/workflow-controller/issues/114),
  [#115](https://github.com/RodrigoFAbreu/workflow-controller/issues/115) (deny the tester reads of credentials;
  planned next), [#116](https://github.com/RodrigoFAbreu/workflow-controller/issues/116),

  documentation pull request after this release),
  [#118](https://github.com/RodrigoFAbreu/workflow-controller/issues/118) and

## Compatibility

Controller 1.18.0 admits the same Workflow releases as 1.17.0. It was checked against the vendored Workflow 2.12.0
tree's row 38e answers. See the [compatibility page](../compatibility.md).

## Upgrading

Install 1.18.0 as you installed 1.17.0 (see the [update page](../update.md)). Check the requirements above first: a
host without them stops at `functional_tester_unavailable` at the next acceptance, and `functional.automated` set to
`false` restores the old stop.
