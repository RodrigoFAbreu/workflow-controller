# Workflow Controller 1.19.3

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_NOTIFICATION_FIX_PLAN.md`). The milestone was
`workflow-controller-notification-fix`. It was released from pull request #153 (merge `981e11a`, title `fix: review and
functional-review waits send review_wait, an info event, not user_gate (#149)`), on 2026-10-25. The title is `fix:`, so
this is a patch release. It closes issue #149. Only the notification a stop sends changes.

## Review waits are an info event (1.19.3)

**The problem.** A `user_gate` (ACTION_REQUIRED, HIGH) must mean that a person decides something. The Controller sent it
for every blocked lifecycle gate, also for a stop that only waits for a reviewer or a tester the operator is already
running (#149).

**A new event type, `review_wait`.** It is an INFO event with LOW severity. It is sent for the wait for the external
review verdict and for the functional-review tester stops. The one tester stop that still sends `user_gate` is
`isolation_breach`.

**`user_gate` is kept for decisions.** It is still sent for approvals, acceptance, merges that need the owner,
BLOCK-resolution gates and legacy gates.

**The Workflow's decision is recorded.** A gate's job record has a new `protocol_gate` field that keeps the Workflow's
decision. The Controller reads it to tell a wait for a verdict from a gate that needs a person.

**`checks_pending` is unchanged.**

**The event can be configured.** `review_wait` is an event type like the others, so the `events` section of the settings
file can raise, lower or switch it off. There is no new setting.

**The documentation names the new type.** The [automation guide](../guide/automation.md) and the
[commands guide](../guide/commands.md) list `review_wait`.

## Requirements

Unchanged from 1.19.2.

## Known limitations

- **One stop may be announced twice after the upgrade.** A stop already announced as `user_gate` may be announced once
  more as `review_wait`. A guard suppresses the second message when the earlier `user_gate` was sent, or was a
  duplicate. A failed or rejected earlier send never suppresses it.

## Upgrading

Install 1.19.3 as you installed 1.19.2 (see the [update page](../update.md)). No new `verify-claude` run is needed.
