# Workflow Controller 1.22.0

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_HARNESS_MODELS_PLAN.md`). It was released from pull request #173 (merge `6755619`, title
`feat: a harness declares its models and efforts, and routing refuses a pair it does not support (H8)`), on 2026-10-26.
The title is `feat:`, so this is a minor release. A routing or settings file that was valid until now can be refused
after the upgrade; read "Upgrading" below.

## A harness declares its models and efforts (1.22.0)

**The problem.** A model or an effort in a routing entry was checked only for being a non-empty string. Once a second
harness can take a worker role, a model of one harness routed to another would fail at launch, in the middle of a run.

**Each adapter declares what it supports.** The harness adapters in `controller/harness.py` now declare the models and
the efforts they support. `claude-code` declares the four full model ids, the aliases `opus`, `sonnet` and `haiku`, and
the efforts `low`, `medium`, `high`, `xhigh` and `max`. `codex` declares `gpt-6.1-sol` and the efforts `high` and
`xhigh`.

**One check, on the resolved routes.** Routing checks the resolved model and effort against the resolved harness once,
after the command line, the routing config and the built-in table are combined, and before any job record is written.
An unset model or effort (`None`, which inherits) is never refused.

**A refusal is named.** A model or an effort the harness does not declare is refused at the next `run` or `step` with
exit `20`. The message names the role, the harness, the field and the values the harness declares, and where each of
the three values came from.

**A new setting, `harness.models`.** It maps a harness name to a list of extra model names the operator accepts for that
harness. It has no command-line option and there is no command for it: the operator edits the settings file entry. No
setting extends the effort list. The settings table generation is now 16.

**The harness table.** The generated table in the [harness guide](../guide/harnesses.md) gains a Models and an Efforts
column. The entries of `harness.models` are the operator's and are not in the table.

**The lane's routing.** The values of the lane's own routing are checked by a committed fixture,
`tests/fixtures/lane_routing.json`.

**The documentation.** The [runtime guide](../guide/runtime.md), the [commands guide](../guide/commands.md), the
[compatibility page](../compatibility.md) and the [common problems page](../common-problems.md) describe the check, the
setting and the refusal.

## Requirements

Unchanged from 1.21.1.

## Known limitations

- **An earlier Controller warns about the new key.** A Controller before 1.22.0 that shares the settings file warns about
  the unknown `harness` section, ignores it, and its `settings clean` refuses.

## Upgrading

Install 1.22.0 as you installed 1.21.1 (see the [update page](../update.md)). No new `verify-claude` run is needed.

**Who is affected.** Anyone whose settings file or `--routing-config` file names a model or an effort the harness does
not declare. Until 1.21.x the `claude` CLI was the only authority, so such a file was valid. It is now refused at the
next `run` or `step` with exit `20`. This includes a role routed to a harness that does not declare the built-in default
model.

**How to fix it.** Use a value the harness declares (the [harness guide](../guide/harnesses.md) lists them). To keep a
model the harness does not list, add it to the `models` key of the settings file's `harness` section:

```json
"harness": {"models": {"claude-code": ["your-model-name"]}}
```

An unsupported effort is changed in the routing. See "Upgrading to 1.22.0" on the
[compatibility page](../compatibility.md).
