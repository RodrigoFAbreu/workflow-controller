# Workflow Controller 1.22.1

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_CHECKS_WAIT_PLAN.md`). It was released from pull request #177 (merge `f00c3cf`, title
`fix: a pending-checks stop sends the info event checks_wait, and lane_blocked only after four hours (#170)`), on
2026-10-26. The title is `fix:`, so this is a patch release. It closes issue #170. Only the notification a pending-checks
stop sends changes.

## A pending-checks stop sends `checks_wait`, not `lane_blocked` (1.22.1)

**The problem.** A stop that only waits for the pull request's checks sent `lane_blocked` (`CRITICAL`), although nothing
was wrong and the checks were still running (#170).

**What is sent now.** A pending-checks stop sends the new event type `checks_wait` instead: the `merge.wait_seconds`
budget spent while the pull request's checks still run, or a step in a repository without auto-merge, which cannot wait.
It is of kind `state`, `INFO`, `LOW`, on by default, with the title `Waiting for the pull request's checks (<work item>)`.

**When `lane_blocked` is still sent.** Only once the checks have been pending longer than four hours. The limit is fixed,
not a setting. The age is measured from the newest event of the work item's binding record. A failed check still reaches
`lane_blocked` through the pull-request defect loop.

**No duplicates.** The event identity is the stop's own, so nothing is announced twice. A stop already announced as
`lane_blocked` before the upgrade is not announced again as the info event (the NF1 upgrade guard).

**The `events` section.** The `events` section of the settings file accepts `checks_wait` like any event type: raise it,
lower it or turn it off. The settings generation does not change.

**Unchanged.** Exit codes, step counts and gate identities.

**The documentation.** The [commands guide](../guide/commands.md) lists the event type and the
[automation guide](../guide/automation.md) describes the rule.

## Requirements

Unchanged from 1.22.0.

None new.

## Upgrading

Install 1.22.1 as you installed 1.22.0 (see the [update page](../update.md)). No new `verify-claude` run is needed.
There is nothing to do. An operator who set event preferences in the settings file may now also set `checks_wait`.
