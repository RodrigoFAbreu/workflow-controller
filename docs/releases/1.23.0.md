# Workflow Controller 1.23.0

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_FALLBACK_SELECT_PLAN.md`). It was released from pull request #204 (merge `1a39cbc`, title
`feat: select a role's fallback chain entry before a worker is spawned (H9b, #202)`), on 2026-10-27. The title is `feat:`,
so this is a minor release. It closes issue #202. The worker launch now chooses an entry of a role's fallback chain.

## A role's fallback chain is used before a worker is spawned (1.23.0)

**What changes.** The routing configuration could already declare, validate and resolve a fallback chain per role (H9a, merged
without a release of its own), but nothing read it. The worker launch now walks the chain in order, before a worker is spawned and never after, and launches the first
entry that is neither unavailable nor held by a limit. The new module `controller/route_select.py` holds the selection.

**What skips an entry.** An entry is skipped when its launcher cannot be resolved (cause `launcher_unavailable`), or when
the usage gate holds its provider (cause `usage_held`). A hold skips the whole provider once: every later entry of a held
provider is skipped without a second admission, because the readings are account-wide and a model-specific limit is not
detected. A later entry on another provider is admitted normally, and only the chosen entry reserves budget.

**When no entry can be launched.** If any entry was held, the result is the usage hold with the earliest resume time
among the waitable ones, so the existing wait and exit codes apply. If every launcher is unavailable, the first entry's
refusal is raised, as for a single-entry role today. There is no new status, exit code or gate.

**Never after the worker started.** A worker that fails or is interrupted after it started is not retried on another
entry. The next `step` or `run` selects again from the first entry. `resume` and the drain path read the recorded route.

**The record.** For a role with a fallback chain, `worker_route` gains a `selection` block:
`{"position", "length", "skipped": [{"position", "harness", "cause"}]}`. The existing fields describe the chosen entry,
and the job schema version is unchanged. A role without a chain writes exactly the record it wrote before.

**Telemetry.** `telemetry` reports `chain_position` and `chain_skipped` for a record with a `selection` block. A worker
record now reports the harness from its `worker_route`, falling back to the worker adapter's name; a Controller-run
external-review record keeps its value.

**Honest reach.** With the harnesses shipped, only `claude-code` takes the worker role and all its entries share one
provider, so a chain of Claude entries records position 0 and waits exactly as today. A later entry is chosen only once a
second worker harness exists. The reviewer and tester launches are untouched.

**Unchanged.** No new setting, option, gate code or exit code.

**The documentation.** The [commands guide](../guide/commands.md), the [runtime guide](../guide/runtime.md) and the
[workers guide](../guide/workers.md) describe the selection, the record block and the telemetry dimensions.

## Requirements

Unchanged from 1.22.2.

## Known limitations

A hold of a provider holds every entry on it: a model-specific limit is not detected, so a same-account entry is never a
fallback for a hold.

## Upgrading

Install 1.23.0 as you installed 1.22.2 (see the [update page](../update.md)). No new `verify-claude` run is needed.
There is nothing to configure. A role with a fallback chain gains a `selection` block in its `worker_route` records; a
role without one is unchanged.
