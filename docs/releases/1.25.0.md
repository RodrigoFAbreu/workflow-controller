## `verify-codex`, the Codex build verification command (1.25.0)

**What changes.** `workflow-controller verify-codex [--force] [--codex-binary PATH]` runs the Codex tester sandbox's
boundary probes against the `codex` a launch would run and, only when every probe holds and the build did not change
meanwhile, records the build's SHA-256 digest. It takes no repository. `--codex-binary` is local to this command and
names a different build; the command then notes that a launch runs the `codex` on `PATH`, or that there is none.

**The two probes.** Each runs in its own fresh scratch job, against host fixtures the sandbox could otherwise reach (a
TCP and a Unix listener, a push origin, a canary file), and `exec` runs only when `sandbox` held:

- `sandbox`: `codex sandbox`, no model, no spend;
- `exec`: one short `codex exec` turn on your Codex credentials. **Cost:** one short model turn; the usage budget gate
  is not consulted. A token Codex refreshes during the turn is copied back to your Codex home (never over a file you
  changed meanwhile), and the scratch credential copy is removed, also after a refusal.

**The record.** A pass is written to `verified-codex-builds.json` in the runtime root (never to the settings file, which
this command never creates, fills or updates): the digest, with the version, the time, the Controller version and the
probe results, the same shape as the Claude record. Nothing at launch reads it yet.

**Verify on first use.** A digest already recorded is reported "already verified" and not probed again; `--force`
probes it again. A record that was ignored prints its reason and the build is probed. A build edited after it was
recorded has a different digest and is probed. The digest is taken before the first probe and again after the last; a
different value is the refusal `build_changed` and records nothing.

**Exit codes and refusals.** `0` for a verified or already verified build. Anything else exits `20`, names the refusal
and records nothing: `identity` (the layout cannot be bound to a digest), `host` (no `codex` or `bwrap`, no short
folder, a fixture that cannot be prepared), `credentials` (no `auth.json` in your Codex home), `launch_controls`,
`sandbox` or `exec` (a probe line or a host effect failed, named), `model_unreachable` (a login, credit, limit or
timeout cause, or no output: neither verified nor shown broken, run it again), `exec_failed` (the turn failed for
another cause, with its exit code and the end of stderr) and `build_changed`. A record that cannot be written is exit
`20`, not a traceback.

**Nothing launches on the record.** The Codex tester is declared in C10g-3, so the build-verification entry for `codex`
stays "none" and no launch consults the record. The Codex reviewer is unchanged and keeps its own launch checks, and
`verify-claude` and its record are unchanged. No new setting and no new exit code.

**Earlier slices, shipped without a release.** The modules this command joins were merged earlier and had no release of
their own: `controller/codex_sandbox.py` (C10g-1, the sandbox layout, launch controls and boundary probes, which only an
opt-in test ran) and `controller/codex_build.py` (C10g-2a, the build digest and the record). This release is the first
that exposes them, through the command.

**The documentation.** The [commands guide](../guide/commands.md#verify-codex) describes the command, the
[runtime guide](../guide/runtime.md) the record, the [harness](../guide/harnesses.md) and
[workers](../guide/workers.md) guides that nothing consults it yet, and the [exit codes](../exit-codes.md) page lists it
under exit `20`.

## Requirements

Unchanged from 1.24.0 for existing use. Running `verify-codex` needs the real `codex` and `bwrap`, and an `auth.json` in
your Codex home (`$CODEX_HOME`, else `~/.codex`).

## Known limitations

A recorded digest is not used by any launch yet. A build replaced after the record is written runs unverified in
principle; the record defends against the sandboxed tester, which cannot write the install tree, as for `verify-claude`.
A `model_unreachable` result decides nothing about the build.

## Upgrading

Install 1.25.0 as you installed 1.24.0 (see the [update page](../update.md)). There is nothing to configure. Running
`verify-codex` is optional until the Codex tester ships, and costs one short model turn.
