# Workflow Controller 1.26.0

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_CODEX_TESTER_ROUTING_PLAN.md`). It was released from pull request #237 (merge `0b52128`, title
`feat: route the functional tester to Codex (C10g-3c1, #223)`), on 2026-10-31. The title is `feat:`, so this is a minor
release. It closes issue #223. A configuration can now route the functional tester to Codex, and the functional job
runs it.

## Routing accepts Codex for the functional tester (1.26.0)

**What changes.** Routing accepts the harness `codex` for the `functional-tester` role at every entry point: a role
entry, the default, `--role-harness functional-tester=codex` and a fallback entry. A settings file that 1.25.0 refused
for this pair is now valid. Every other role still refuses `codex` (the Codex adapter declares the reviewer and tester
roles only), and a Claude-only configuration is unchanged. The Codex tester is off unless a routing entry selects it.

**Name the model and the effort.** There are no Codex defaults for the tester: its built-in route is a Claude model at
`medium`, which the Codex adapter does not declare. A Codex tester names all three, the harness, the model
`gpt-6.1-sol` and an effort `high` or `xhigh`, in a role entry, the settings file or on the command line:

```
--role-harness functional-tester=codex --role-model functional-tester=gpt-6.1-sol --role-effort functional-tester=high
```

A fallback entry names its own model and takes `inherit` for an omitted effort. A harness-only or model-only selection
is refused when the options are built, before any dispatch, with an error naming the role, the field, the value and what
the harness declares.

**The functional step launches it.** For a route whose harness is `codex`, the functional job step launches the Codex
tester (`launch_codex_functional`) in place of the Claude tester. The usage budget gate is asked for the Codex provider,
the credential captured is the digest of `auth.json` in your Codex home, and the job record's `functional.harness`
reads `codex`. When the job is reconciled afterwards, the credential copy-back follows the record's harness. The
Codex binary is the harness default, `codex`; no new setting, option, exit code or gate is added.

**`verify-codex` first.** The launch refuses a build `verify-codex` has not recorded. That refusal, like any refusal
inside the launch (no binary, a control, a clone mismatch), ends the step at `functional_tester_unavailable`, with the
sandbox and the credential copy removed. Log in to Codex as for the reviewer.

**Not in this release.** Selection still takes the first entry of the chain. Walking the fallback chain before the
spawn, telemetry dimensions and Codex usage figures for the tester (its usage record is empty for now), and the first
real Codex functional round come later.

**Earlier pieces, shipped without a release and now usable together.** The Codex tester sandbox, the build digest and
record, the composed-configuration check, the sandbox bridge and run, and the launch gate were merged in earlier
slices and had no release of their own, apart from `verify-codex` in 1.25.0. With this release routing can select them.

**The documentation.** The [harnesses](../guide/harnesses.md), [automation](../guide/automation.md),
[workers](../guide/workers.md), [commands](../guide/commands.md) and [runtime](../guide/runtime.md) guides and the
[compatibility page](../compatibility.md) describe the routing and the launch.

## Requirements

Unchanged from 1.25.0 for existing use. Running the Codex tester needs the real `codex` and `bwrap`, a Codex login
(`auth.json` in `$CODEX_HOME`, else `~/.codex`) and a build recorded by `verify-codex`.

## Known limitations

The Codex tester is unproven end to end until its first real round. Selection takes the first chain entry, so an
unusable Codex tester ends the step at `functional_tester_unavailable` rather than falling back. Its usage figures are
empty. A settings file naming Codex for the tester is refused by 1.25.0 and earlier.

## Upgrading

Install 1.26.0 as you installed 1.25.0 (see the [update page](../update.md)). Nothing changes unless you route the
tester to Codex. To do so, run `workflow-controller verify-codex` first, then name the harness, `gpt-6.1-sol` and an
effort as above.
