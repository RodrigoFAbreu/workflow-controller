# Workflow Controller 1.27.0

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_CODEX_TESTER_FALLBACK_PLAN.md`). It was released from pull request #239 (merge `24ef55d`, title
`feat: functional-tester fallback, Codex usage figures and the first Codex round (C10g-3c2, #236)`), on 2026-10-31
(18:17 UTC). The title is `feat:`, so this is a minor release. It closes issue #236. With this release the functional
review can run on Codex end to end once `verify-codex` has recorded the build and routing selects it. A Claude-only
configuration is unchanged.

## The functional tester's fallback chain is walked before the spawn (1.27.0)

**What changes.** A `functional-tester` chain longer than one is walked before the worker is spawned, as a worker's
chain is. Until now the functional step took the first entry and ignored the rest. An entry is skipped at selection time
(cause `launcher_unavailable`) when:

- its launcher binary cannot be resolved;
- for a Codex entry, its functional options carry no Codex home and binary;
- for a Codex entry, the Codex home has no `auth.json` (no login); or
- for a Codex entry, the Codex build is not the one `verify-codex` recorded.

A held provider skips its remaining entries (`usage_held`). The first admitted entry is chosen. A Claude entry is probed
for its binary only.

**A started tester is never retried.** Every other refusal happens after the spawn (a control, a breach, a bridge
error): the job ends there, at `functional_tester_unavailable` or its findings gate, and the next entry is never tried.

**When no entry can run.** When every entry is unavailable, the step ends at `functional_tester_unavailable` with the
first entry's reason and writes one gate record that also carries the skipped entries; no usage is admitted and no
tester record is written. When every entry is held, the step returns the usage hold and writes nothing. A chain of one
selects nothing and behaves as before.

**The record and the telemetry.** The job record's `worker_route.selection` shows the chosen entry's `position`, the
chain `length` and the `skipped` entries, so `telemetry` reports `chain_position` and `chain_skipped` for a functional
job. Choosing a fallback tester changes no reviewer decision: the tester stays outside the reviewer-independence rule.

## A Codex tester's usage and telemetry

**Usage.** A Codex tester's usage record is now built from its rollouts, so the usage budget and the `usage` command read
its cost as they do for a Codex review. A Claude tester's figures are unchanged.

**Telemetry.** A launched Codex tester now has a `telemetry` block with the harness `codex`, the role, model, effort and,
when selected, the chain position. The row shows the tokens and the cost as unavailable, as it does for any record with
no readable stream; the figures themselves are in the `usage` record. A tester that did not start has no block.

**The first real Codex round.** The first real functional round on Codex ran on 31 October 2026 on `gpt-6.1-sol` at
effort `high`, through the job on a scratch item. It ran to `findings`: the tester reported the one flow as failed for a
real reason (the fixture's `README.md` has no heading), the credentials were `unchanged`, the sandbox was removed, and
the usage record held 12,594 input, 46,080 cache-read, 1,061 output and 93 reasoning tokens (`derived`, cost unknown).
The [compatibility page](../compatibility.md) names the Codex build it ran on. An opt-in live test
(`CONTROLLER_LIVE_CODEX_TESTS=1`) now also runs the Codex launch through the job's launch entry.

**No new surface.** No setting, option, exit code or gate is added. A Codex tester is still off unless a routing entry
selects it, as in 1.26.0.

**The documentation.** The [automation](../guide/automation.md), [harnesses](../guide/harnesses.md),
[workers](../guide/workers.md) and [runtime](../guide/runtime.md) guides and the [compatibility page](../compatibility.md)
describe the selection, the usage figures and the round.

## Requirements

Unchanged from 1.26.0 for existing use. Running the Codex tester needs the real `codex` and `bwrap`, a Codex login
(`auth.json` in `$CODEX_HOME`, else `~/.codex`) and a build recorded by `verify-codex`.

## Known limitations

The Codex tester has run one real round. Its `telemetry` row shows tokens and cost as unavailable (they are in the
`usage` record, and the cost of that round was unknown). A tester that failed after it started is not retried on
another entry. The Codex login is checked at selection for a Codex entry only; a Claude entry with no login ends after
the spawn like any other later cause. A defect found by the live round is filed as its own issue and is not fixed here.

## Upgrading

Install 1.27.0 as you installed 1.26.0 (see the [update page](../update.md)). A configuration with a one-entry
`functional-tester` chain, or a Claude-only one, behaves as before. To use Codex for the functional review, run
`workflow-controller verify-codex` first, then route the tester to it as described in the
[1.26.0 notes](1.26.0.md); a longer chain now falls through to its next entry when the first is unavailable.
