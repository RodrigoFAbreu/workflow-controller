The title is `fix:`, so this is a patch release. It closes issue #288.

## The functional checklist reader reads bold Flow headers (1.27.10)

**The problem.** A functional review checklist that wrote its flows as bold lines starting with the word `Flow`
(`**Flow 1: Title.**`) was not read as flows. When the checklist also held a flow the reader did recognise, the bold
`Flow` lines were dropped without a word, so the automated tester never ran them (#288).

**What changed.**

- **Bold `Flow` headers are read as flows.** A bold header may now start with the word `Flow` (any case), then a label:
  `**Flow K: Title.**`, `**Flow K. Title.**`, `**Flow K) Title.**`, `**Flow K - Title.**` (a hyphen, en dash or em dash set
  off by spaces) and `**Flow K**` alone. `**Flow 1: Log in.**` is flow `1`. An optional qualifier may come first, as in
  `**Optional, Flow 2: x**`. Such a header starts a flow and ends the one above it, as `**K. Title.**` does.
- **A bold `Flow` line that no shape reads is refused.** The line is no longer dropped next to a recognised flow. The
  checklist stops at the existing `checklist_unrecognised` gate, and the message and evidence name the file line (the first
  eight, with a count of the rest). Examples that are refused: `**Flow: Title**` (no label), `**Flow 1 Title**` (no mark
  after the label), `**Flow 1**: Title` (text after the closing bold). The same line is named when the checklist has no
  flow at all.
- **A three-digit Flow label is refused.** `**Flow 123: Title**` is not accepted as a label. When the bold shape decides,
  it is refused as a partly recognised checklist and the evidence names the label (`123`), wherever the line sits outside
  a code fence.
- **Mixed spellings are refused.** A checklist whose flows are bold `**Flow K: ...**` lines and which also has a
  `### Flow 10 ...` heading flow is refused, and the message names the odd flow. Give the section one shape.
- **Where a bold `Flow` line is not refused.** Inside a flow's own text, inside a code fence, in a table row of a table
  that decided, or in a region that is not a flow (below a `### Setup`, `### Test data`, `### Known limitations` or
  `### Out of scope` heading). A region that a bold line opened (`**Setup.**`) now ends at the next bold `Flow` line.
- **Wording.** The gate message and the shapes list now show `**Flow K: ...` as a bold flow header.

The documentation: [common problems](../common-problems.md#the-run-stopped-at-the-functional-review-row-38e) and the
[automation guide](../guide/automation.md#protocol-mode-workflow-27-and-later) describe the new shapes and the refusal.

## Requirements

Unchanged from 1.27.9.

## Known limitations

- Only the word `Flow` is guarded. A bold line that starts with another word, such as `**Step 1:**`, next to a recognised
  flow stays unread and is not refused, and `**Flow1: x**` (no space) is not a `Flow` line.
- A qualified near-miss of the new spelling, such as `**Optional, Flow 9 y**` or `**Optional Flow: y**`, is dropped as before.
- `**Optional extra Flow 1.**` is not a header and stays inside the flow above it, as before.
- A `**Flow K**` line with trailing text on the same line is not read as a header.
- The reader does not merge two shapes in one checklist.

## Upgrading

Install 1.27.10 as you installed 1.27.9 (see the [update page](../update.md)). There is nothing to configure. If a run
stops at `checklist_unrecognised` naming a line that begins `**Flow`, write it as `**Flow K: Title.**` or as a heading
`### Flow K: Title`, or put it inside the flow it belongs to.
