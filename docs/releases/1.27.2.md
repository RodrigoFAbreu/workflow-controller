# Workflow Controller 1.27.2

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_ORCHESTRATOR_STOPS_PLAN.md`). It was released from pull request #250 (merge `1ddc3e3`, title
`fix: announce a stop the orchestrator handles as a wait, not a user decision (NF3, #244)`), on 2026-11-01. The title is
`fix:`, so this is a patch release. It closes issue #244. Only the notification a stopped gate sends changes.

## A stop the orchestrator handles is announced as a wait (1.27.2)

**The problem.** The Controller sent `user_gate` (category `ACTION_REQUIRED`, severity `HIGH`, "Your decision is needed")
for every blocked gate stop except a few. Stops that need no person produced false alarms: a repeated no-progress
acceptance, an external gate waiting for a pull request, unmet gate evidence. Of the 20 `user_gate` events sent since
2026-10-26, 18 asked for a decision nobody had to make (#244).

**What is sent now.** A gate record of a Workflow-governed target carries a `protocol_gate` block (the table row, the
disposition, the action, the Workflow's reason code and the Controller's own gate `code`), and the announcement reads
those recorded facts, never the message text.

- **`orchestrator_wait`, a new event type.** It is of kind `state`, so `INFO` and `LOW`, and on by default, with the title
  `Waiting: <stop> (<work item>)`. It is sent for a stop the orchestrator clears by itself or by waiting: a
  pull-request fact or functional evidence that is awaited (rows 38f and 38e), `no_progress_repeated` (the loop guard),
  and `pr_report_unchanged` over row 38f only.
- **`lane_blocked` (`CRITICAL`).** It is sent for a stop that needs a repair but no decision: a stop the Workflow answers
  with the disposition `blocked` (unmet gate evidence, a refused condition) and the Controller's `workflow_unhealthy`.
- **`user_gate` for a real decision.** Every other stop stays `user_gate`: an approval, an acceptance, a merge left to
  a person, a BLOCK resolution, a review round cap, an isolation breach, a pull-request approval (row 38g, also when
  the reporter's report is unchanged) and every other reporter stop.
- **Unknown stays with you.** A record written by an earlier release (without the new keys), an unknown code, reason
  code or disposition, and a legacy target are all `user_gate`, because a false alert costs a glance and a missed
  decision stalls the lane. A Controller-coded gate is a `user_gate` even at a review phase.

**The `events` section.** The `events` section of the settings file accepts `orchestrator_wait` like any event type: raise
it, lower it or turn it off. The settings generation does not change. Because it is `LOW`, a repeated
`orchestrator_wait` for the same stop (`no_progress_repeated`) is the signal to look.

**No duplicates.** Both new routes keep the stop's identity and supersede `user_gate`, so a stop already announced as
`user_gate` before the upgrade is not announced again.

**Unchanged.** Which stops are gates, the gate identities, the exit codes and the step counts. The wait for an external
reviewer and the functional tester's fault stops still send `review_wait`.

**The documentation.** The [automation guide](../guide/automation.md#notifications-from-an-unattended-run) states the
rule, the [commands guide](../guide/commands.md#notifications) lists the event type and
[ADR 0012](../adr/0012-signalhub-notifications.md) says what it is derived from.

## Requirements

Unchanged from 1.27.1.

## Known limitations

The classification is a closed table in the code, so a new kind of stop is a `user_gate` until a release adds it. A gate
record written by an earlier release is still judged as a `user_gate` when it is re-derived.

## Upgrading

Install 1.27.2 as you installed 1.27.1 (see the [update page](../update.md)). No new `verify-claude` or `verify-codex`
run is needed. There is nothing to configure. An operator who set event preferences in the settings file may now also
set `orchestrator_wait`.
