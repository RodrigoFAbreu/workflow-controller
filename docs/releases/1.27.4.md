# Workflow Controller 1.27.4

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_CHECKLIST_CROSS_SHAPE_PLAN.md`). It was released from pull request #274 (merge `744fb74`, title
`fix: a functional checklist flow that another shape recognised is refused, not dropped silently (FL2, #271)`),
on 2026-11-03. The title is `fix:`, so this is a patch release. It closes issue #271. Only the reading of the
"Functional review checklist" section changes.

## A flow that another shape recognised is refused, not dropped (1.27.4)

**The problem.** The Controller reads the flows of the "Functional review checklist" section in one of four shapes: table
rows, bold labelled paragraphs, headings, or a numbered list. When a section mixes shapes, one shape decides and the others
were ignored. A flow that one shape recognised and the deciding shape did not read was dropped without a word: the tester
ran the flows of the deciding shape only, and the round could pass with a flow never tested (#271). Release 1.27.3 refused
a checklist that one shape read only in part, but not this case across shapes.

**What is refused now.** After the deciding shape has read its flows, every item that another shape recognised must be
accounted for. It is, when it starts inside the text of a flow that was read (a numbered list inside a bold flow, a case
table inside a heading flow), or, when the table decided, when it shares a line with a row of that table. An item that is
neither is refused with the existing `checklist_unrecognised` gate, before any job, sandbox or usage reservation exists.
The message names the deciding shape, the number of flows it read and the dropped items (the first eight, then a count),
for example "the table shape decided 3 flow(s); 2 item(s) another shape recognised neither start inside one of them nor hold
a row of a table that decided, and would not run". The evidence carries `shape`, `recognised`, `total` and `unrecognised`
as before, and now also `dropped`: the `shape` and `label` of each flow that would not run (at most 20).

**What is deliberately not refused.** Items in the checklist's own non-flow regions are not flows. A heading below the
section's own that starts with `Setup`, `Test data`, `Known limitations` or `Out of scope` covers everything up to the next
heading of the same or a higher level. A bold line that opens one of these (`**Setup.**`) covers everything up to the next
heading, labelled bold paragraph, bold line that opens another section, or bold line that starts with `Flows` (such as
`**Flows.**`). `Flows` itself is not such a region, because a checklist lists its flows there.

**Unchanged.** There is no new setting, option, exit code or gate. The refusal keeps its code, and a checklist that was
already read whole is read as before.

**The documentation.** The [automation guide](../guide/automation.md#protocol-mode-workflow-27-and-later) states the rule
and the regions, and the [common problems](../common-problems.md#the-run-stopped-at-the-functional-review-row-38e) and
[troubleshooting](../guide/troubleshooting.md) pages mention the new case.

## Requirements

Unchanged from 1.27.3.

## Known limitations

None new. The cross-shape case that 1.27.3 listed as a limitation (#271) is closed by this release.

## Upgrading

Install 1.27.4 as you installed 1.27.3 (see the [update page](../update.md)). No new `verify-claude` or `verify-codex`
run is needed. There is nothing to configure. A checklist that mixed shapes and was partly run before may now stop at
`checklist_unrecognised`: put each flow the message names inside a flow of the shape used, give the section one shape, or
run the flows by hand.
