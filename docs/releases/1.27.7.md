# Workflow Controller 1.27.7

[Back to the documentation map](../README.md)

These notes were written after the release from the milestone plan
(`docs/ai-workflow/CONTROLLER_SANDBOX_PRECHECK_PLAN.md`). It was released from pull request #282 (merge `886cfa7`, title
`fix: the functional tester's availability is checked before usage is reserved (C10i, #112)`), on 2026-11-04. The title is
`fix:`, so this is a patch release. It closes issue #112.

## An unavailable functional tester is found before usage is reserved (1.27.7)

**The problem.** The causes that make the functional tester unavailable on a host (no `claude` binary, a refused role,
no `bwrap` or `socat`, no seccomp filter, a `claude` build that is not in the verified list) were only found when the
tester was launched, after the Controller had already reserved usage for it (#112).

**What changed.** The Controller now runs a static check of the host before it reserves any usage, for a
`functional-tester` chain of one as well as a longer chain. For the Claude tester it checks the role, the binary and the
sandbox probe (`bwrap`, `socat`, the seccomp filter and the verified build). For the Codex tester it checks the binary,
the Codex login (`auth.json`) and that the build is the one `verify-codex` recorded. When a check fails:

- the step stops at `functional_tester_unavailable`, as before;
- the job keeps one record, whose `functional` block names the cause in `functional.cause` (for example `no_binary`,
  `role_refused` or `enforcement`);
- no usage is reserved, and the record has no `functional.launched` block, because nothing was admitted or started.

**A fallback chain.** In a `functional-tester` chain longer than one, a Claude entry that fails the same check is now
skipped (cause `launcher_unavailable`) and the next entry is tried, as a Codex entry already was. When every entry fails
the check, the step ends at `functional_tester_unavailable` with a cause.

**The launch still checks.** The launch makes the same checks itself, through the same code, so a host that changes
between the selection and the launch still ends at the gate. The causes that need a job or a built sandbox (the fresh
clone not matching the manifest, no folder short enough for `TMPDIR`, a runtime root inside your Claude home, a tree with
a submodule, an untracked checklist or an existing sandbox folder) still arise at launch, after a reservation.

The documentation: the [automation guide](../guide/automation.md#what-the-controller-automates-and-how-it-stays-safe) and
[common problems](../common-problems.md#functional_tester_unavailable) describe the above.

## Requirements

Unchanged from 1.27.6.

## Known limitations

- The causes that need a job or a built sandbox are not found by the early check; they still stop the step at launch.

## Upgrading

Install 1.27.7 as you installed 1.27.6 (see the [update page](../update.md)). There is nothing to configure.
