# Workflow Controller 1.3.0

[Back to the documentation map](../README.md)

1.3.0 lets the Controller drive a target repository that runs the released
**Workflow 2.6.0**, beside 2.5.1. A target on Workflow 2.5.1 behaves exactly
as it did under 1.2.1. It also carries the notes for two behaviour changes
that shipped in 1.2.1, which had none.

The design record is
[ADR 0006](../adr/0006-workflow-release-admission-and-per-release-contracts.md)
and the plan
`docs/ai-workflow/CONTROLLER_WORKFLOW_2_6_INTEGRATION_PLAN.md` (work item
`workflow-controller-workflow-2-6-integration`). The generation stays 1, and
the exit-code contract is unchanged.

## Workflow 2.6.0 admitted

- `VALIDATED_WORKFLOW_RELEASES` is `{2.5.1, 2.6.0}`. Admission stays by
  exact release: 2.5.0 and 2.6.1 are refused as `unvalidated_release`, and
  2.7.0 as `outside_supported_line`
  ([Supported Workflow releases](../guide/installation.md#supported-workflow-releases)).
- For a 2.6.0 target the Controller no longer keeps its own rules for two
  facts, and asks Workflow instead
  ([Workflow's queries](../guide/automation.md#workflows-queries-260-and-later)):
  - the feedback path, from `scripts/workflow_fingerprint.py
    --resolve-feedback-path <id>`. This fixes the one case where the old
    rule was wrong under 2.6.0: a newly created, `scoped` work item whose
    feedback directory does not exist yet;
  - whether a plan-review bundle is current, from `scripts/workflow_state.py
    --plan-review-publication-status <id>`, at every plan-stage phase of a
    `"2.1"`/`"2.2"` item and in the plan-stage job's verification.
- A query executes only the admitted release's script bytes: the Controller
  checks both scripts' sha256 against the digests it holds for the release,
  and runs exactly those bytes from a private copy in a temporary directory,
  never from the target's `scripts/`. The Git commands those scripts run
  start no program the target configures: they read a private copy of the
  index, use no transport, and run with every hook, filter driver and
  fsmonitor switched off. A query gives Workflow's answer or none, so a
  program whose absence could change the answer refuses the query
  (`query_git_not_isolated`) instead: a `post-index-change` hook, which
  `git diff` fires, or an fsmonitor program (with Git before 2.36, which
  runs a boolean as a program, any `core.fsmonitor` but an empty one),
  before the query runs; a filter's `clean` or `process` program, where Git
  would run it, which the Controller finds after the query through a probe
  of its own. So do a hook command in the target's own Git configuration,
  a populated submodule, and a Git before 2.31. A query writes nothing to
  the target, `.git` included (a split index's shared file only has its
  modification time moved on, by Git's read).
- Under 2.6.0, `/milestone-plan` and `/apply-plan-review` end by binding the
  plan-review bundle; the Controller verifies that Workflow then reports it
  `BOUND`. A revision published but not bound (row 9) is recovered by the
  same explicit-id command, automatically. The Controller never launches
  `/milestone-plan` at a plan-review-ready phase, where 2.6.0 would withdraw
  the item.
- The installed Workflow release is read again before every decision and
  before every job verification, and a job is verified under the release its
  record carries.

## New error codes, reasons and gates

Both new error codes exit `20`
([Troubleshooting](../guide/troubleshooting.md#workflow-releases-and-workflows-queries)):

- **`WORKFLOW_QUERY_FAILED`**: a Workflow query could not give an answer the
  Controller may act on (reasons `query_script_modified`,
  `query_private_copy_failed`, `query_git_not_isolated`,
  `query_launch_failed`, `query_timeout`, `query_failed`,
  `query_output_invalid`). It is never answered by the 2.5.1
  rule. During a job's verification the job instead ends `FAILED` with
  reason **`workflow_query_failed`**.
- **`WORKFLOW_RELEASE_CHANGED`**: the target's installed release changed, or
  cannot be read, after `inspect` admitted it. The refusal says what the
  repository preflight had already done, including a completed close-out.
  During a job's verification the job instead ends `FAILED` with reason
  **`workflow_release_changed`**. A `resume` while the installation manifest
  is unreadable refuses at `inspect` and leaves the job record as it was.

Neither failure at verification leaves a pending job.

New plan-stage gates, for `"2.1"`/`"2.2"` items on a 2.6.0 target:

- the stale-plan-bundle gate from Workflow's status (rows 4a-4c), at every
  plan-review-ready phase, `AWAITING_PLAN_APPROVAL` included, where it
  replaces the approval gate. For rows 4b and 4c its steps restore the
  author files in the directory 2.6.0's generator reads, then regenerate.
  For row 4a (the working tree drifted from the bound content) the
  Controller offers no restore, and the gate's command is a valid
  `workflow-controller --work-item <id> explain <repo>`;
- `plan_review_binding_inconsistent`: Workflow refuses the status (rows 4d
  and 6);
- `unexpected_plan_review_status`: an answer outside the contract.

No `safe_resume_command` names Workflow's withdrawal. The `REJECTED`-marker
gate gives the same author-file steps at every plan-review-ready phase under
2.6.0.

## Visible changes for 2.5.1 targets

- **Refusal evidence key renamed.** An `UNSUPPORTED_WORKFLOW_VERSION`
  refusal's evidence carries `supported_workflow_lines`, a sorted list
  (`["2.5", "2.6"]`), in place of `supported_workflow_line`, a string. Its
  message names the supported lines and the validated releases.
- The `integration_required` gate and the `milestone-binding --abandon`
  refusal name both Workflow releases. What they require is unchanged:
  neither release has a transition that moves a work item's base, so trunk
  integration stays the documented manual merge (ADR 0006, E1-E5).

Nothing else changes for a 2.5.1 target: its decisions, gates, job records,
worker arguments, CLI output and exit codes are those of 1.2.1, pinned by
the unchanged decision goldens. The one new act is the installed-release
re-check, a plain read of `.workflow-manager/installation.json`, which
changes nothing unless the release changed or the file cannot be read.

## Behaviour changes shipped in 1.2.1

1.2.1 was a bump-only release of the adaptive-test-sharding milestone, whose
two Controller changes (both in `controller/worker.py`) had no release notes:

- **An owned process's `source` label follows its current ownership basis**,
  not the one it had when first seen, and a relabel is published. For
  example, a background process that leaves the worker's group with
  `setsid` is now always reported as owned by `tag`. Which processes are
  owned is unchanged.
- **The drain detach bound is 10800 s (3 hours)**, up from 600 s: a worker's
  background processes may outlive it that long before `step`, `run` or
  `resume` detaches with exit `45`
  ([the drain bound](../guide/workers.md#owned-processes-the-daemon-list-and-the-drain-bound)).
  It is an interim constant; making it configurable is planned.

## Upgrading

Install 1.3.0 as any release
([Upgrade](../guide/installation.md#upgrade)). Upgrade the Controller before
moving any target to Workflow 2.6.0, and move targets between milestones
([Moving a target](../guide/installation.md#moving-a-target-to-another-workflow-release)).
Rolling back to 1.2.1 restores 2.5.1-only admission: a target already on
2.6.0 is then refused.
