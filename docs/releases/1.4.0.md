# Workflow Controller 1.4.0

[Back to the documentation map](../README.md)

1.4.0 moves the Controller's release and pull-request machinery to squash
merges and tag-derived versions. A repository policy may now choose the
`conventional_commit` release trigger: the pull request title is a
Conventional Commit, it becomes the squash commit's subject, and its type
decides the release. The Git tag is the only version authority. A repository
whose policy keeps the `version_change` trigger and no `merge_method` behaves
as it did under 1.3.0, except for the explicit base of the next
`/milestone-plan` (below).

1.4.0 is the first release of this repository made the new way. The code was
merged with a merge commit and released nothing; the cutover pull request,
which switches this repository's `pyproject.toml` and policy, was then
squash-merged under a `feat:` title, and `main.yml` derived 1.4.0 from
`v1.3.0` and that title.

The design record is
[ADR 0007](../adr/0007-tag-derived-versions-and-squash-merges.md) and the plan
`docs/ai-workflow/CONTROLLER_SQUASH_MERGE_TAG_VERSIONING_PLAN.md` (work item
`workflow-controller-squash-merge-tag-versioning`). The generation stays 1,
and the exit-code contract is unchanged.

## Releases from pull request titles

- The policy gains the trigger `conventional_commit`
  ([Releasing](../guide/ci-and-releases.md#releasing)). It requires
  `release.change_types`, a table from commit type to `minor`, `patch` or
  `none`, and forbids `version_source`. A title's `!` gives a major release;
  `!` on a type that releases nothing is refused. This repository's table:
  `feat` minor; `fix`, `perf`, `refactor`, `revert`, `build` and `style`
  patch; `docs`, `chore`, `ci` and `test` nothing.
- `main.yml` computes the version from the highest release tag in the
  commit's history and the types of the first-parent commits since it. A
  commit made under the old trigger contributes nothing. A `docs`, `chore`,
  `ci` or `test` merge publishes nothing.
- **New failing state `INVALID_SUBJECT`**: a commit on `main` whose subject
  cannot be classified fails the release run and tags nothing. It is settled
  only by listing the commit in the new optional `release.bump_overrides`, in
  a pull request. An override of a commit that does classify refuses.
- A release tag left without a published release is resumed first
  (`RESUME` at its own commit), even when later commits would bump the
  version; the next run releases the bump.
- With no release tag at all and nothing to release, classification is
  `NO_CHANGE` at `0.0.0`, so no `v0.0.0` is ever published by accident.
- `tools/release.py build` and `verify` take the classified version from the
  `RELEASE_VERSION` environment variable, which `main.yml`'s build job sets.
  Their command lines are unchanged, so a `RESUME` at a commit carrying
  1.3.0's tooling still builds.
- **New `PR title` check** (`.github/workflows/pr-title.yml`), running
  `tools/release.py check-title` on the title. Under `version_change` it
  passes and reports that the title is not release input.

## The version comes from the tags

- With `dynamic = ["version"]` in `pyproject.toml`, a release build takes its
  version from the release tag, and a local build, a source runtime and a
  pinned source snapshot report the highest `vMAJOR.MINOR.PATCH` tag
  reachable from their commit, or `0.0.0` without one (a shallow clone, for
  example). A checkout between two releases reports the last release it
  contains; `BUILD_INFO.json` and the second `--version` line tell a local
  build apart ([Runtime identity](../guide/runtime.md)).
- A `pyproject.toml` with a static version keeps 1.3.0's behaviour.
- `tools/release.py version` prints the version a local build of the
  checkout carries. `verify-wheel --tag` expects the tag's version.

## Squash merges

With `milestone_branches.pull_request.merge_method: "squash"` in the policy
([Milestone branches and pull requests](../guide/milestone-branches.md)):

- **The plan declares the pull request title**, as one header line
  ``Pull request title: `<Conventional Commit>` ``. The Controller reads it
  from the committed plan, titles the Draft PR with it, and puts it back
  whenever the title on GitHub differs, until the PR is ready.
- At readiness the title and body are synced before the checks are read, and
  any edit ends the step at `checks_pending` so the re-run `PR title` check is
  sampled. **New gate `pr_title_invalid`**: the plan declares no valid title
  and the PR's own title is not valid; set a valid title on GitHub.
- The PR body becomes the squash commit's body. From 1.4.0 on, a milestone's
  release notes are its PR body: a milestone cannot know its version before
  its merge.
- Gate texts say "Squash and merge". Keep the squash subject GitHub proposes
  (the title and ` (#<number>)`): it is what the release reads.
- **New state `MERGED_SQUASHED`**, closed out like `MERGED` once the squash
  is verified against the reviewed head. A merge it cannot verify (a rebase,
  an edited subject, a different tree, a conflict, a configured merge driver)
  is `MERGED_REWRITTEN`, as before. Verifying a squash of a branch that `main`
  moved past needs Git 2.38; an older Git refuses and writes nothing.
- The local `milestone/<id>` branch is left in place; delete it with
  `git branch -D` after close-out.

Without `merge_method`, or with `"merge"`, titles, bodies, gate texts and
close-out are those of 1.3.0.

## The explicit base, for every repository with milestone branches

With milestone branches enabled, the automatic bootstrap of the next
milestone names `/milestone-plan <trunk tip>`, the full commit id the trunk start proved
equal to the remote trunk, instead of a bare `/milestone-plan`. A repository
without a policy, or with milestone branches disabled, still gets the bare
command.

## Upgrading

Install 1.4.0 as any release
([Upgrade](../guide/installation.md#upgrade)): check that
`workflow-controller status` shows `active: none`, then
`pipx install --force` the wheel.

- **This repository.** After the cutover, 1.3.0 refuses every lifecycle
  command here: its policy parser does not know the post-cutover policy. It
  names the first key it does not know,
  `milestone_branches.pull_request.merge_method`. Install 1.4.0 before the
  next lifecycle step.
- **Rolling back** to 1.3.0 is refused on this repository for the same
  reason. Revert the cutover pull request instead (a `revert:` title, which
  is a patch release), or keep running 1.4.0 or later.
- **Adopters on `version_change`** are unaffected: their policy parses with
  the same meaning, and their releases, titles, gate texts and close-out are
  unchanged. Only the next `/milestone-plan` carries an explicit base.
