## A usage budget that pauses a run before a limit (1.8.0)

**The Controller now watches the Claude and Codex usage windows itself.** Before each job it reads
the five-hour and weekly windows, forecasts what the job will cost from earlier jobs of the same
role and model, and does not start one that would not fit. Until now two shell scripts outside
the Controller paused at a fixed 85% between steps. They had no forecast, so a long step could hit
the limit half way, and two lanes could both pass on the same headroom.

**Lanes share one record.** The readings, the other lanes' reservations and the spend so far live
in `usage.json` in the runtime root. A job reserves its forecast before it starts, so another lane
sees that share as taken. A job that is still running renews its reservation. A reservation whose
holder has gone stops counting against the account windows once its lease lapses, and is settled
later.

**What a hold does.**
- A timed pause (a window would be reached) is waited out by `run`. It sleeps, with no lock held,
  until the window resets plus `usage.resume_grace_seconds`, then goes through the whole boundary
  again with a fresh decision. The wait does not count as a step. Ctrl-C works while it waits.
- `step`, a wait longer than `usage.max_wait_seconds`, and a run or repository cap stop with
  **exit 17** and start nothing. The check runs before the job record exists, so a hold leaves
  nothing for `resume` to reconcile.
- A cap names no resume time. A run cap is never lifted by a reset (raise it, or start a new run);
  a repository cap counts only the current five-hour window.
- A missing reading disables only its own account check, never a cap or the other window, so a
  fresh machine runs.

**Exit code 17.** The new code means "stopped before starting because of the usage budget; nothing
was started". It is on the [exit-code page](../exit-codes.md) and in
[ADR 0001](../adr/0001-controller-generation-1-architecture.md#exit-codes).

## The `usage` command

`workflow-controller usage` shows the readings, the thresholds, the reservations and the forecast
for Claude and Codex, as text or with `--json`. It also gives a worker you start yourself the same
gate a Controller job has:
- `--check` asks whether a job would be admitted, without reserving.
- `--wait --reserve` waits for a window and prints a reservation token.
- `--renew TOKEN` keeps that reservation alive; `--release TOKEN` settles it, with `--outcome` and
  `--stream` for what the worker did.
- `--provider`, `--role`, `--model`, `--repo` and `--run-id` say what is being gated. A cap it is
  not told about is not evaluated, and the output says so.

The command is described under [`usage`](../guide/commands.md#usage). It also appends `usage_paused`,
`usage_resumed`, `usage_released` and `usage_reservation_expired` to `usage-events.jsonl`; turning
those into notifications is a later roadmap step.

## Settings generation 4 and the cap flags

- The settings file gains sixteen `usage.*` rows (table generation 4): `enabled`, the Claude and
  Codex five-hour and weekly pause thresholds (85% and 95% by default), `resume_grace_seconds`,
  `max_wait_seconds`, `reservation_seconds`, the default forecast for each provider and window, and
  the run and repository caps (off by default). See
  [the settings file](../guide/runtime.md#what-it-holds).
- `usage.enabled: false` turns the budget off.
- `--usage-cap PERCENT` caps a run's Claude usage on `run`, `step` and `usage`. `--usage-codex-cap
  PERCENT` does the same for Codex on `usage` only, because the Controller launches no Codex
  worker yet. A bad value is a usage error (exit 2).

## Known limitations

- **A usage limit hit inside a worker is not recognised yet.** The budget forecasts; it cannot stop
  a job that goes over its forecast. A job that meets the limit mid-way still fails with exit 30.
  Check `workflow-controller usage`, wait for the reset, run `explain`, and run again.
  Recognising this and waiting for the reset automatically is a roadmap item (C8b).
- A repository cap is one number in that repository's settings file; a per-repository cap map is a
  later step (C8c).
- A Codex worker started by the Controller does not exist yet; Codex is enforced only through
  `usage`.
- Deleting `usage.json` forgets every lane's reservations and spend. A damaged record is never
  overwritten; see [common problems](../common-problems.md#the-usage-record-cannot-be-read).

## Upgrading

The settings file moves to generation 4 automatically the first time `step` or `run` fills it; your
own values are kept. Releases before 1.8.0 ignore the new `usage` rows with their unknown-key
warning, and a 1.7.x `settings clean` refuses the filled file. Install 1.8.0 as you installed
1.7.1 (see the [update page](../update.md)).
