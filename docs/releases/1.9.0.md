## The Controller pushes its events to SignalHub (1.9.0)

**A run you leave alone can now tell you what it is doing.** The Controller becomes a producer for
SignalHub, the owner's notification platform, and posts events to its `POST /api/v1/events`. Until
now the lane orchestrator sessions did this by hand with a script that reads
`~/.config/signalhub/events.json`. The Controller derives each event from a record it already
keeps (run-log lines, job records, the branch-binding events a step's preflight writes and the
lines of `usage-events.jsonl`), so no event has two sources. No read-only command sends anything.

**What is sent.** There are 14 event types in four kinds. A kind sets the default category and
severity; an event type can override them.

| kind | default category / severity | event types |
|---|---|---|
| `state` | INFO / LOW | `step_done`, `run_finished`, `usage_paused`, `usage_resumed`; **off by default:** `usage_released`, `usage_reservation_expired` |
| `info` | INFO / NORMAL | `milestone_started`, `milestone_planned`, `approval_recorded`, `milestone_accepted`, `pr_merged`, `release_published` |
| `gate` | ACTION_REQUIRED / HIGH | `user_gate` (a human gate, or a merge the policy leaves to a person) |
| `blocker` | BLOCKED / CRITICAL | `lane_blocked` (a failed or incomplete job, a fail-closed refusal with exit 20 of `step`, `run` or `resume`, and every branch gate that needs a person to fix something) |

`usage_released` is off by default because it is written for every job. Some stops are a run's
normal end and send nothing: a held lock (45), a pending handoff (50), `--max-steps` (16, so no
`run_finished`) and a declined action (15). A branch gate that is only a wait (`checks_pending`,
`merge_pending`, `release_pending`, `pr_head_not_accepted`) sends nothing, unless a run that waited
ends on one when its wait is spent. `merge_accepted` sends nothing either; the later
`merged_squashed` sends `pr_merged`.

## Configuration

- **Settings generation 5.** The settings file gains seven `notifications.*` rows: `enabled`,
  `url`, `api_key_file`, `timeout_seconds` (5), `attempts` (3), `retry_seconds` (2) and `events`.
  See [the settings file](../guide/runtime.md#what-it-holds).
- **Master switch.** `notifications.enabled: false` stops every notification.
- **Per-kind and per-event overrides.** `notifications.events` holds a `kinds` layer and an `events`
  layer of `{enabled, category, severity}`. A field resolves from the kind's built-in default, then
  the file's kind entry, then the file's event entry. A known field with a value that is not allowed
  is refused (exit 20). An unknown kind, event type or field is ignored with the usual unknown-key
  warning. See [the notifications section](../guide/runtime.md#the-notifications-section).
- **Pasting the lanes' `events.json`.** A field whose name starts with `_` is ignored silently, so
  the `kinds` and `events` objects of the lanes' file can be pasted in whole. The Controller does
  not read `events.json` itself.

## Credentials

- **URL:** `$SIGNALHUB_URL`, else `notifications.url`, else the first line of
  `<signalhub config dir>/url`.
- **Key:** `$SIGNALHUB_API_KEY`, else the file named by `$SIGNALHUB_API_KEY_FILE`, else the file
  named by `notifications.api_key_file`, else `<signalhub config dir>/api-key`.
- The config directory is `$SIGNALHUB_CONFIG_DIR` or `~/.config/signalhub`. The lanes' kill switch
  file `<signalhub config dir>/disabled` is honoured.
- **The key is never stored in the settings file** (`notifications.api_key_file` is a path) **and is
  never written to a log.** It is read once, held in memory and sent as a bearer token. One
  Controller process uses one key, whichever repository it drives.
- Without a URL or a key the notifier is inert after one `not_configured` line that names the
  places it looked.

## The `notifications` command

`workflow-controller notifications` prints the effective configuration: the master switch, where the
URL and key were found (never the key), the kill switch, and one row per event type with its kind,
whether it is on, its category and severity and which layer set each. `--json` prints the same as
one object.

`notifications --test` sends one `info` test event through the real transport (`milestone_started`,
so it follows your setting for that type). It takes no repository and writes nothing under the
runtime directory. Exit codes:

| exit | meaning |
|---|---|
| 0 | the event was `sent`, or the server already had it (`duplicate`) |
| 1 | the server rejected it, or answered `422` (a conflict) |
| 2 | nothing was sent: not configured, disabled (kill switch or master switch), or the test event's type is disabled |
| 3 | every attempt failed (network errors, timeouts, `429` or `5xx`) |

Exit 3 is returned by this command alone; see [exit codes](../exit-codes.md) and
[the command](../guide/commands.md#notifications). If nothing arrives, see
[common problems](../common-problems.md#no-notifications-arrive).

## Delivery guarantees

- **Delivery never blocks or changes a step.** `emit` puts the event on a bounded queue (256) and
  returns; one daemon thread sends one event at a time, with a timeout per attempt and a bounded
  number of attempts with exponential waits. Network errors, timeouts, `429` and `5xx` are retried;
  any other `4xx` is a rejection. After three events in a row spend their attempts, sending pauses
  for 300 seconds.
- **Bounded exit wait.** A run's close flushes the queue for at most the timeout plus five seconds,
  and after a Ctrl-C the flush waits at most two seconds.
- **No double notice.** Each event carries an `Idempotency-Key` built from the event type, the
  repository and the identity of the occurrence (a job id, the run id, the work item and pull
  request, a release tag, and so on). The title, message and metadata carry no job id, run id, clock
  or wait deadline, so an event derived again by another process repeats the stored body and the
  server answers `200` with no push. A retry or a `resume` does not notify twice. A `422` is recorded
  as `conflict` and not retried.
- **Bounded recovery on `resume`.** `resume` derives again the notice of a job it reconciled to a
  terminal state, and of an already-terminal job last updated within 30 minutes, when the run's log
  shows a configured notifier and records no outcome that spent its attempts or that the server
  holds for that key. `step`, `run` and `resume` also derive `pr_merged` from a binding already in
  `MERGED` or `MERGED_SQUASHED` at command entry.

## Outcome records

One line per event outcome (`sent`, `duplicate`, `conflict`, `rejected`, `failed`, `skipped`,
`dropped`, `not_configured`, `disabled`) goes to `runs/<run_id>/notifications.jsonl`, or to
`notifications.jsonl` at the runtime root outside a run. Each line holds the event's key and never
the API key. A run with a configured notifier starts its log with a `notifier_active` line, and the
run's own `events.jsonl` ends with a `notifications_summary` event holding the counts. Nothing in
the lifecycle reads these files except the recovery on `resume`.

## Known limitations

- **No persistent outbox.** An event whose attempts were spent is `failed`, recorded and not
  retried. A process killed after the state change but before the event was queued loses that
  notice; `resume` repairs it only within the bounds above, and a branch-gate notice is repaired by
  the next `step`, which observes the same gate. If a close-out persists `CLOSED` and the process
  dies before `pr_merged` is queued, that one notice is lost.
- **Named residuals of the usage and recovery keys** ([ADR 0012](../adr/0012-signalhub-notifications.md),
  decision 4): (a) more than 50 foreign `usage-events.jsonl` lines between two pauses of one hold
  send one extra `usage_paused`; (b) a repository cap with no reading whose accounting window is
  re-placed by a later charge sends one extra notice per move; (c) a reservations-only cap pause less
  than five hours after a matching pause, with no `usage_resumed` between, sends no notice; (d) two
  processes appending at once may each record their own occurrence, which sends one extra notice; (e)
  an event type that was disabled when its record was written and is enabled within 30 minutes sends
  one late notice on `resume`.
- **Checkouts that share a directory name share keys.** The repository in the key and in the body's
  `context` is the directory name.
- The Manager and Workflow repositories send nothing, and there are no notifications yet for C7, C8b
  and C8c, which do not exist.

## Upgrading

The settings file moves from generation 4 to generation 5 automatically the first time `step` or
`run` fills it; your own values are kept. A 1.8.x Controller sharing the file afterwards warns about
the unknown `notifications` section, ignores it, and its `settings clean` refuses. With no URL and
key configured the notifier does nothing. Install 1.9.0 as you installed 1.8.0 (see the
[update page](../update.md)).

**Lanes that hand-send events.** After they run 1.9.0, the lane orchestrators should stop sending
the events the Controller now sends (`step_done`, `usage_*`, `pr_merged`, `release_published`,
`milestone_*`, `user_gate`, `lane_blocked`) for a Controller-driven repository, and keep sending
only what no Controller observes (Codex review rounds, their own approvals; plan decision D9). Their
restart path should run `resume` before `run --max-steps 1` after a killed Controller process, and
every launch path should find a key: set `notifications.api_key_file` once, or export
`SIGNALHUB_API_KEY_FILE` from `start-run.sh`. These are lane changes outside this repository.
